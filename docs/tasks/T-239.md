## Investigation

Problem investigator, 2026-11-19, main @ dc6aa15d → c4d449d5. Tools: Serena (`find_symbol` on `Writer::drain`, `Writer::advance`, `OpenSink`) and grep for the test helpers, history and docs. Context7 was not needed, because no library API is involved.

**Frame.**
- Observed: in T-132's top gate (load ~42), three `call_session` tests panicked in `drained()`: "the writer took Mic up to 59000/65000 ms". The whole binary finished in 36 s, with 80 tests running in parallel.
- Expected: `drained()` returns once the subtitle consumer holds every fed sample of both tracks.
- The same two tests failed in T-176's gate at load ~29 and passed on re-run.
- The question to answer: does the product writer starve the Mic lane, or are the test's feed and its budget the problem?

**Hypotheses.**
1. *The 20 s budget is a throughput ceiling.* The backlog is fixed before the wait and its processing time grows with host load. Confirms if both lanes keep progressing and finish after more than 20 s. **Confirmed.**
2. *Drain fairness starves Mic (F-031's mechanism, product).* Confirms if the Mic count stalls while System keeps growing and a producer is still feeding. **Refuted as the cause.** The test thread feeds the whole burst synchronously (`FakeSource::feed`, a `while` over `sink.block`) before `drained()` starts, so nothing refills a lane during the wait. A lane is held off only for the other lane's finite backlog. Any drain order ends both lanes at the same total time, so a fair drain would not move the end.
3. *Blocks dropped, so `drained()` can never be satisfied.* Refuted. The capacities 16 384 and 8 192 are above the largest burst (3 250 blocks), and every probe run reached the exact `want`.
4. *The writer stalls* (a pause or a held command). Refuted: both counts rise in every 1 s sample.
5. *A second path, or this class was fixed before.* `drained()` and these three tests were added in T-149 (12b455f7, 2026-11-09), before T-203's fix (2026-11-10). T-203 touched neither. F-031 fixed "a tick taken as proof of consumption", and these tests never used a tick as proof. So this is not a recurrence of F-031. It belongs to the core-tests class "no verdict races a clock the test does not control: host load" (`docs/decisions/core-tests.md`; F-013 "fixed wall-clock ceilings went red under host load", F-021). There, a hang-ending wait must be "sized far above the time the awaited outcome needs", and a 6 000-event backlog in a debug build under load is not.

**Measurement.**
- Setup: a throwaway git worktree at c4d449d5 under `/root/.claude/jobs/e136a9f6/tmp`, removed afterwards. `drained()` became a sampler that writes both consumer block counts every 1 s and the end time. Command: `scripts/tw-test core --tree <copy> -j2 --test call_session cant_hear`, under `agent-tests.slice`, load ~47. Log `.teamwright/logs/test/core-20261119T103058Z-c4d449d-1bd7c4ff7735.log`.
- Samples, shown as m = Mic blocks, s = System blocks handled:
  - `cant_hear_you…` upto 59000: `0ms m0/s9 … 11000ms m0/s2741, 12005ms m179/s2950 … END 21900ms m2950/s2950`.
  - `cant_hear_other_party…` upto 59000: `… 12012ms m2858/s0, 13002ms m2950/s134 … END 27813ms m2950/s2950`.
  - `no_cant_hear…` upto 65000, both tracks: `… 13009ms m0/s3205, 14017ms m120/s3250 … END 28379ms m3250/s3250`.
  - The later 63 s runs took 25.6 s, 20.9 s, 13.8 s and 14.5 s. The short runs (2 980 ms, 2 000 ms) took about 1 s.
- Throughput: about 210-270 writer events/s, roughly 4 ms per 20 ms block in the debug build (record on: Opus encode, timeline, subtitle feed). Each 59-65 s burst therefore needs over 20 s on this host. The real `drained()` would have failed 4 of 9 large waits in this run.
- Control: `cant_hear_you…` alone at load ~56 took 40 s for 190 s of audio (`core-20261119T102659Z-dc6aa15-4dd98b6c390e.log`), which passed.
- Why the message says Mic: `drained()` checks `Track::Mic` first. In two of the three tests the writer, woken during the System feed, empties System first, so Mic is last. In `cant_hear_other_party` Mic is drained first and still missed 20 s in the gate, where 80 tests run on 8 threads. The total work, not the order, decides.

**Root cause.** Each failing `drained()` waits, under the fixed 20 s `BUDGET`, for a backlog fed in one burst (59-65 s of audio per track, ~6 000 writer events). Under host load the debug writer needs 22-28 s for that backlog, so the budget caps throughput instead of ending a hung wait. All three symptoms and the T-176 sighting follow from this. No evidence contradicts it.

**Product drain fairness.** `Writer::drain` does hold one lane off for the whole backlog of the other. The probe saw Mic wait 12 s behind 2 950 System blocks. In the product each lane is fed in real time (50 blocks/s), and a lane is held off only while the other lane has a backlog. T-203's follow-up hypothesis is still not demonstrated by this task: a lane held off past `STALL` (500 ms mono), zero-filled by `Writer::advance`, then its real blocks placed late. It needs its own red test on a lane refilled during the wait, and this test family cannot show it. Recommend a separate task only if the owner wants it pursued. It is not the cause here.

**Invariant.** A test wait on a backlog of product work fails only when no progress has been seen for the whole budget. Its verdict never depends on how long the total work takes.

**Seam.** `call_session.rs::drained`, built on a new progress wait in `tests/common::timing`. The wait succeeds when `done()` is true. It fails only when `progress()` (the summed consumer counts of the awaited tracks) has not grown for `budget`. Every consumption wait on a backlog already goes through `drained()` (all call sites in `call_session.rs`, `cant_hear_run`'s `run` included). `barrier()` and `wait()` await one event, so they keep `eventually`. `consumer_has()` waits on 200-600 ms feeds and may move to the same helper.

**Approach options.**
- **A (recommended).** Progress-based `drained()`.
  - Why it holds: a slow writer always makes progress and passes; a hung writer (or a lane that never gets its blocks) stops progressing and fails after `BUDGET`. The verdict no longer reads host speed, and I2 holds: the clock only ends a stall and never decides how long the work may take.
  - Red first: a deterministic test of the helper in `tests/common`'s timing seam tests. A counter thread advances one step every 20 ms for 60 steps, and the wait has a 300 ms budget. The old `eventually`-style total wait is red; the progress wait is green. A second leg stops the counter, and the progress wait must be red within the budget, so a hang is still caught.
  - Optional red at the call site: `FakeSubtitles` gets a test-only per-call delay, so `drained()` over a 2 s backlog with a short local budget fails before and passes after. The writer held through `CallSession::pause_writer` must still fail.
  - Then run the three tests 100× under load (Acceptance; about 15-40 s each under load, so plan the run while no top gate runs).
  - Risk: a lane that never gets its blocks while the other progresses would wait until the other lane ends, then fail after `BUDGET`. That is still bounded. Rollback: revert the helper and `drained()`.
- **B.** Feed and drain in ≤5 s steps inside `cant_hear_run` and the 65 s feeds.
  - Each wait gets ~8× margin, but the margin is still finite: a heavier gate brings the failure back, and every new large feed must remember the rule. Rejected as the primary fix.
  - Could be added on top of A to shorten single waits.
- **C (workaround).** Raise `BUDGET` (e.g. 120 s). This is still a ceiling and hides real hangs for longer. Labelled a workaround, not recommended.
- **Not an option: a fair `Writer::drain`.** It only reorders the lanes, and both lanes still end when the total work is done.

**Earlier patches of the class.** F-031's T-126 fix (1eace2e0) and T-203 fixed a different mechanism (a tick as proof). Neither covered `drained()`'s budget. The T-176 sighting was filed under F-031 as "the same drain-fairness mechanism", which this measurement refutes. In the core-tests host-load class, T-080, T-089 and T-110 removed wall-clock ceilings from measured times (I2). Hang-ending waits sized against the total work they await were not checked: `core-tests.md` only says "sized far above".

  - Cause: a hang-ending wait capped the total time to process a 59-65 s burst (~6 000 writer events) at 20 s; the debug writer needs 22-28 s under load.
  - Rule: a test wait on a backlog fails only on no progress for the budget (`tests/common::timing` progress wait), never on total time.
  - Tier T1 (review) until a checker exists.

Breaks if violated: green on an idle host, red on a loaded gate, and the message names the lane checked first, which looks like a product starvation."
