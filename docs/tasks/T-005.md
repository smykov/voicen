## Context

FR-15 (v4: user-written text is shown as is). Catalog `i18n/en.json`, `i18n/ru.json` at the repository root, read by Rust (`include_str!`) and by the UI (alias `$i18n`). Every feature adds its keys here; a test fails when a key lacks a non-empty text in either language. Needed by toasts (T-007) and the settings window (T-004). Owns all of `voicen_core::i18n` — catalog embed, `UiLanguage`, `text()`, `MESSAGE_IDS`, `resolve_ui_language(os_tag)` (spec 004 T010, T011, T046, T048) — which T-003's `defaults()` consumes (decision #21).

## Acceptance

- [ ] `voicen_core::i18n::text(lang, id, args)` and the UI `t(id, args)` render the same text for the same id
- [ ] OS language Russian → `ru`; any other → `en`
- [ ] Failure branch: a key present in `en.json` but missing or empty in `ru.json` makes the catalog test fail with the key name (core and vitest); an unknown OS language falls back to English (core `resolve_ui_language` test); the UI renders English until a language is set (vitest)
- [ ] Test that fails without the change: `crates/voicen-core i18n tests (conformance fixture, parity, resolve_ui_language); src/lib/i18n/i18n.test.ts`

## Investigation

Investigator, 2026-10-03.

**Tools.** Serena and context7 were not connected in this session: no `mcp__serena__*` or `mcp__context7__*` tools were available. Instead I used grep and file reads for both Rust and TypeScript. For SvelteKit, Vite and Vitest I read the installed sources and ran probes against the pinned versions (`@sveltejs/kit` 2.70.3, `vite` 8.3.2, `vitest` 5.0.3, `svelte` 5.57.1, `typescript` 6.0.3; `node_modules/@sveltejs/kit/src/exports/vite/index.js:304-338` sets `server.fs.allow`, and `utils.js:26-57` turns `kit.alias` into Vite aliases). The probes ran in a scratch project at `/tmp/t005-probe` that symlinks the repo's `node_modules`. They did not touch the repo; I was not permitted to delete the directory afterwards.

### Frame

- **Observed:** there is no `i18n/` directory, no `voicen_core::i18n` (`crates/voicen-core/src/lib.rs:3` exports only `build_info`) and no UI translation layer. The only UI strings are hard-coded English: `src/routes/+page.svelte:10` ("Cannot read build info: …"), `:18` (the "Voicen" heading) and `src/lib/buildInfo.ts:10` ("Voicen {version} ({commit})"). The shell has no user-visible text yet. `src-tauri/src/lib.rs:23` writes a log line, and logs are not localized: CI greps for that line in English.
- **Expected:** FR-15 v4 and spec 004 FR-011/FR-012 as stated in research R-7. One flat catalog serves both Rust and the UI, rendering is identical in both, a parity gate exists, and the OS language maps to `ru`, otherwise `en`.
- **Where it reproduces:** everywhere. This is a new capability, not a regression.

### Hypotheses

1. **A catalog or i18n code already exists somewhere** → refuted. `ls i18n` fails, and `grep -rn -i "i18n\|catalog"` over `crates/`, `src/` and `src-tauri/src` finds nothing.
2. **The same concern is handled on a second path** → confirmed in the specs, not in the code:
   - Spec 001 `tasks.md:43` (T007) creates the same `i18n/en.json` and `i18n/ru.json`, plus its own `MessageKey` enum and a completeness test in `crates/voicen-core/src/messages.rs`. That would be a second registry and a second catalog check beside `MESSAGE_IDS`.
   - Spec 003 `plan.md:113` places the catalog at `src/lib/i18n/{en,ru}.*`, which contradicts decision #13.
   - Spec 002 `tasks.md:156` (T037) adds "a test that both locales have every key", which would be a third parity test.
   - Without a shared renderer, Rust and TS would each implement placeholder substitution, which is two paths for one cross-cutting value (P-010, P-011).
3. **This class was fixed before** → refuted. `docs/failures.md` holds only the placeholder row F-001, `docs/decisions/` holds only `_area-template.md`, and `recurrence_of: []`. No earlier task or commit touches i18n (`git log --oneline` shows only planning commits mentioning the catalog: c1df4a6, 32361f3).
4. **"Renders the same text" holds automatically because both sides read the same files** → refuted. Shared data does not give a shared renderer:
   - JS `String.replace` treats `$&`, `$'` and `` $` `` in the replacement as patterns. `node -e` shows `'Using {device}'.replace(/\{device\}/g,'Mic $& 1')` → `Using Mic {device} 1`, and `replaceAll('{device}', "a$'b")` → `Using ab`. Rust `str::replace` inserts literally.
   - Device names are user content shown as is (FR-15 v4) and fill `notice.mic_fallback {device}` (spec 001 `contracts/messages.md`).
   - Sequential per-argument replacement re-expands an argument whose value contains `{other}`.
   - The fixture must pin all three.
5. **Tooling cannot reach a repo-root `i18n/`** → refuted by probes:
   - **Rust in Docker:** `TW_RUN_PRINT=1 scripts/tw-run core -- cargo test -p voicen-core` shows `-v /projects/voicen:/work -w /work`, so the whole repo is mounted. In `voicen-rust:1.99`, a crate at `crates/probe/src/lib.rs` with `include_str!("../../../i18n/en.json")` and `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../../i18n/ru.json"))` passed its test. Note that from `src/i18n.rs` the relative path needs three `..`, not two. `include_str!` also records the file as a build dependency, so editing the catalog rebuilds the crate.
   - **Windows CI:** `actions/checkout@v5` checks out the full tree before `cargo test --workspace` and `pnpm tauri build`.
   - **UI:** with `kit.alias: { $i18n: "i18n" }`:
     - `svelte-kit sync` writes `"$i18n": ["../i18n"]` and `"$i18n/*": ["../i18n/*"]` into `.svelte-kit/tsconfig.json`.
     - `svelte-check` reports 0 errors and `vitest run` imports `$i18n/en.json` and `$i18n/ru.json`.
     - `vite build` bundles the Cyrillic text into `build/_app/immutable/nodes/*.js`.
     - `vite dev` answers `/i18n/en.json?import` with 200. The raw `/i18n/en.json` gets 403, so `fs.allow` is active but does not block module imports, and no `server.fs.allow` change is needed.
     - `tsconfig.json` already has `resolveJsonModule: true`.
     - The repo's file is `vite.config.js`, not `.ts` as spec 004 T003 says. The alias does not go there in any case.

### Root cause

This is a need, not a defect. There is no shared catalog and no shared rendering rule. The risk the design has to close is drift between the Rust and TS renderers (hypothesis 4) and between parallel catalog paths planned in specs 001–003 (hypothesis 2).

### Decisions this analysis settles (inputs for the developer; owner items are flagged)

1. **Seams.**
   - **Catalog:** files at the repo root (decision #13).
   - **Core:** `crates/voicen-core/src/i18n.rs` is the one place that parses, looks up and renders in Rust.
     - `Catalog::from_json(en, ru) -> Result<Catalog, CatalogError>` is the implementation.
     - `text()` uses the embedded catalog, parsed once in a `std::sync::OnceLock`.
     - If the embedded files fail to parse, `text()` returns the id rather than panicking. The parity test fails on a parse error, so the gate catches it.
   - **UI:** `src/lib/i18n/index.ts` (plan T012 layout) has pure `lookup` and `render` over an injected catalog, plus `t(id, args)` over the imported catalogs and the current language.
   - **Alias:** `kit.alias` in `svelte.config.js` is the only definition. It reaches Vite, Vitest (`vitest.config.ts` uses the `sveltekit()` plugin) and TS (`svelte-kit sync`). Do not add `paths` to `tsconfig.json`: SvelteKit warns against it (`write_tsconfig.js:176`).
2. **Placeholder syntax** (identical in Rust and TS):
   - A placeholder is `{name}` with `name` matching `[a-z][a-z0-9_]*`. There is no escaping.
   - Any `{` or `}` that does not form a valid placeholder makes the parity test fail. No release-1 message needs a literal brace (spec 001 `contracts/messages.md`, spec 003 `data-model.md:93`).
   - Rendering is one left-to-right scan: a known placeholder is replaced by its argument value inserted literally; an unknown placeholder stays verbatim; extra arguments are ignored. In TS this means a replacer function or a manual scan, never a string replacement pattern.
   - Rust args are `&[(&str, &str)]`; TS args are `Record<string, string>`.
3. **Proof of equal rendering.** `i18n/conformance.json` holds its own small `catalog` (`en`, `ru`) and `cases` (`lang`, `id`, `args`, `expected`). The core test `include_str!`s it and the vitest imports it through `$i18n`. Both run every case through their `Catalog` / `lookup + render` built from the fixture's catalog, and through nothing else.
   - **Why a separate catalog in the fixture:** the real catalog grows with every feature, while the fixture stays stable.
   - **Cases to include:** plain text; one and two placeholders; a repeated placeholder; adjacent `{a}{b}`; a missing argument; an extra argument; a value containing `{b}`; values containing `$&` and `$'`; Cyrillic text and values; an empty value; `ru` empty → `en`; an unknown id → the id.
   - **Why the shared lookup is enough:** `text()` and `t()` read the same two files, so equal lookup plus equal render means equal text for every real id.
   - **Optional:** one case with a real id (`app.build_info`) ties in the real files.
4. **Initial catalog:** the ids existing code needs, so the layer has real users and the UI id check bites.
   - `app.build_info` = en "Voicen {version} ({commit})", ru "Voicen {version} ({commit})" (product name and version; the same text is fine).
   - `app.build_info_error` = en "Cannot read build info: {reason}", ru "Не удалось прочитать сведения о сборке: {reason}".
   - `+page.svelte` and `formatBuildInfo` move to `t()`. The English output is unchanged, so `e2e/build-info.spec.ts` and the `version_check` in `.teamwright/config.yml` still match.
   - The "Voicen" heading is the product name and stays a literal, like `tray.tooltip.idle`.
   - **How other tasks add theirs:** each task adds its ids to both JSON files (en and ru together; the parity gate forbids one without the other). A Rust-originated id is added in the same commit to the `messages!` declaration in `i18n.rs`. Spec 004 T051 ("complete ru last") is moot because ru can never lag.
   - **Alternative** (not recommended): a single seed id with no user.
5. **`MESSAGE_IDS` belongs here** (decision #21, `contracts/core-traits.md:88`). Hand-kept, it is an allowlist: a literal `text(lang, "tray.exit", …)` that is missing from the list passes every check (P-002). The recommendation is option A:
   - `pub struct MessageId(&'static str)` with a private field. A `messages! { TRAY_EXIT = "tray.exit", … }` macro in `i18n.rs` emits the constants and `MESSAGE_IDS`, and `text(lang, MessageId, args)` accepts only those ids. `MessageId` serializes as its string for IPC.
   - This closes "every Rust id exists in both catalogs" by construction plus one test.
   - It deviates from the contract signature `text(lang, id: &str, args)`, so `contracts/core-traits.md` must be updated in the same commit (P-014).
   - Today no Rust code uses an id, so `MESSAGE_IDS` starts empty. The check function gets its bite from a synthetic list run against the fixture catalog. The first real entries come from T-003 (`error.<code>` for each `FieldError` code) and from T-006/T-007.
   - Spec 001's `MessageKey` (T-007) should map to `MessageId` and drop its own catalog files and completeness test, and spec 002 T037's parity test is likewise covered by T-005's gate. These are notes for those tasks; this task does not change them.
   - **Option B:** keep `text(&str)` with a hand-kept `MESSAGE_IDS`. It matches the contract but is the allowlist shape described above.
6. **Language resolution.**
   - Only core `resolve_ui_language` maps an OS tag to a language. The shell reads `GetUserPreferredUILanguages` (spec 004 `plan.md:104`, `os_language.rs`, a shell task) and passes the tag to T-003's `defaults(os_tag)`.
   - The UI gets its language from `SettingsView.settings.ui_language` and `settings://changed`; T-004 wires that. Until then it renders `en`.
   - The UI must not read `navigator.language`. Doing so would be a second resolver, and it would also break US3-5, where the saved choice must win over the OS.
   - **Owner/orchestrator item:** the Acceptance failure branch says the unknown-OS-language fallback is "verified by core and vitest tests". The UI has no OS input. The vitest can only show that `t()` renders English before a language is set. I suggest rewording to "verified by core tests; the UI renders English until a language is set (vitest)".
   - The part of spec T046 saying "a saved `ui_language` is never re-derived on load" belongs to T-003's `load_or_init` tests, not here.
   - `UiLanguage` is `enum { En, Ru }` with serde `"en"|"ru"` (data-model). It has no `Default` derive, because its default is `resolve_ui_language`. TS uses `type UiLanguage = "en" | "ru"`.
7. **Dependencies.**
   - **Core:** add `serde_json = "1"` to `crates/voicen-core/Cargo.toml`. It is consented by decision #9 and already resolved in `Cargo.lock` (1.0.151), so it is not a new owner decision. No regex crate: the placeholder scanner is hand-written.
   - **UI:** no new package (no i18n library, per research R-7).
   - **Owner flag:** none needed.
8. **Test file names.** The Acceptance says `src/lib/i18n.test.ts`; plan T012 says `src/lib/i18n/i18n.test.ts`. Recommend the latter (it matches the `src/lib/i18n/` seam) and align the Acceptance text.

### Red tests in Acceptance order

1. **AC1 same text:**
   - core `i18n::tests::conformance_fixture` and vitest `conformance fixture` over `i18n/conformance.json`.
   - core `text_uses_embedded_catalog` (`app.build_info` with args, en and ru).
   - vitest `t renders app.build_info`.
   - Red: no module exists. The `$&` and `$'` cases pin the TS replacer, and the `{b}`-in-value case pins single-pass rendering.
2. **AC2 OS language:** core `resolve_ui_language` table from spec T046 (`ru`, `ru-RU`, `RU-ua`, `ru-Latn` → Ru; `en-US`, `en-GB`, `de-DE`, `uk-UA`, `""`, `None` → En), plus `ru_RU` → Ru and `rus` → En.
3. **AC3 failure branch:**
   - Core `catalog_parity_reports_*`, run on in-memory pairs. Each case names the id: an id missing in ru, an empty ru text, a different placeholder set, a stray brace, a non-string value. The same check then runs on the real files.
   - Core `message_ids_exist_in_both_catalogs`, with bite from a synthetic id list.
   - Vitest: en and ru have the same ids and non-empty texts (failure message names the id); `t()` renders `en` before a language is set; an unknown id renders as the id.
   - The `$i18n` import itself is proven by these vitests and by `pnpm lint` (`svelte-check`). Typing `MessageId = keyof typeof en` turns an unknown literal id in `t("…")` into a `svelte-check` error, which covers spec T012's "every literal id exists" more completely than a source scan.
4. **AC4:** the gate (`make check`) runs both suites.

**Rollback:** revert the commit. Nothing consumes the module yet, and T-003, T-004 and T-007 wait on this task.
