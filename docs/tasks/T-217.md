## Context

Owner decision #304 (2026-11-17), asked for by the monitoring session: every worktree under `/projects/voicen.worktrees/` builds `voicen-core` and its dependency tree from cold into its own `target/`, and the throwaway copies of the validator did the same (about 21 GB each). The VPS disk reached 85%. A shared `CARGO_TARGET_DIR` was rejected: cargo locks the build directory, so parallel worktrees would wait for each other, and branches would overwrite each other's artifacts.

Chosen: `sccache` in the `voicen-rust` image (`docker/rust.Dockerfile`, rebuilt with `make core-image`), used as `RUSTC_WRAPPER` for runs through `scripts/tw-run core`. The cache lives in one host directory shared by the main tree, every worktree and every throwaway copy. Each tree keeps its own `target/`.

Constraints:
- `.teamwright/config.yml` is changed only through `.teamwright/config.next.yml` and `tw-install.py apply --config` (state guard). `scripts/tw-run` is a kit file: prefer config keys (an absolute `cache:` entry, environment) over editing it. If the kit cannot express a shared host directory, say so in the analysis and propose the smallest change; a kit change goes to `/teamwright:feedback`.
- Windows CI does not change (its Rust cache is `rust-cache`); the Linux gate's results must stay the same.
- The image tag in `.teamwright/config.yml` and in CI (`scripts/ci/area-image.sh`) stays consistent; a tag change follows `docs/decisions/ci-toolchain.md`.
- A guard path (`Makefile`, `scripts/ci/`) in the diff needs `checker: true` and `analysis.decides_on` (P-020); avoid one if possible.

## Acceptance

- [ ] `scripts/tw-run core -- 'sccache --show-stats'` works in the main tree and in a worktree, and both report the same cache location (one host directory, outside any tree's `target/`).
- [ ] After a core build in the main tree, the first `scripts/tw-gate core` in a fresh worktree reports sccache hits for the dependency crates (`sccache --show-stats`: non-zero cache hits); the time of both runs is recorded under `## Tests`.
- [ ] `make check` stays green, and its results match a run without the wrapper.
- [ ] Failure branch: the cache directory is missing or not writable → the build still succeeds (sccache falls back to plain `rustc`, or `tw-run` runs without the wrapper) and prints one line saying so; verified by a run with the directory made read-only.
- [ ] The cache has a size cap (`SCCACHE_CACHE_SIZE`), and the docs say where it lives and how to clear it (`CLAUDE.md` Commands or `docs/decisions/ci-toolchain.md`).

## Investigation

Orchestrator note (analyze stage, 2026-11-17): the kit installer is in the plugin root (`scripts/tw-install.py`); its config validation (lines ~140-190) checks only known area keys and does not reject unknown ones, so a new `shared_cache:` area key passes `apply --config`. `scripts/tw-run` must still be edited to read it (local kit-file change, upstream request in `docs/kit-feedback.md`).

How I looked: read `scripts/tw-run`, `docker/rust.Dockerfile`, `.teamwright/config.yml`, `Makefile` (core targets, `core-image`), `.github/workflows/ci.yml` (gate job), `.teamwright/installed.json`, `docs/decisions/ci-toolchain.md`, `docs/decisions/licenses.md`, `docs/failures.md`, `docs/kit-feedback.md`; grep for `TW_CACHE_ROOT`, `TW_DOCKER_ARGS`, `.teamwright/cache`, `docker run`, `ENTRYPOINT` and the stdout consumers of `tw-run core`. These are shell, YAML and Docker files, so I used grep and file reads rather than Serena. sccache behaviour comes from the context7 docs for `/mozilla/sccache/v0.17.0` (the newest indexed version). The kit sources (`tw-install.py`) are not on this host, so I could not check whether `apply --config` accepts a new area key.

**What config alone can express:** no host directory shared across trees. Each docker cache path is `${TW_CACHE_ROOT:-$ROOT}/.teamwright/cache/<area>/...`, so it belongs to one tree. `copy_env` applies only under `TW_RUN_COPY=1`, and only into the same per-tree directory. `TW_DOCKER_ARGS` is the caller's environment, not config, and `e2e.sh` and the WER docs overwrite it. So a kit change is needed: one optional area key, `shared_cache:`, mounted from the main checkout's cache directory, which is found through `git rev-parse --git-common-dir`. The mount happens only when that host directory already exists, so the shared cache is opt-in per machine and CI never gets it. The change is small (about 8 lines). Owner decision #304 already names `tw-run`, and #145 is the precedent for a local edit to a kit file plus a `docs/kit-feedback.md` item. So it does not block. Until upstream adopts it, a kit update would overwrite the edit (no hook checks kit hashes; `session-check.sh` only compares plugin versions).

**What the image alone can do:** `tw-run` starts `$IMAGE sh -c ...`, so an `ENTRYPOINT` in the image wraps every core command without a kit change. That makes the image the single place where `RUSTC_WRAPPER` gets set. The wrapper must not go into `.cargo/config.toml`, because the Windows job reads that file.

**Design risk found (changes the naive design):** sccache's local disk cache supports one server at a time. Concurrent servers race and cause spurious build failures (sccache docs/Local.md). Each `tw-run` container is a separate PID and network namespace and starts its own server, and up to 10 worktrees run in parallel. A plain shared `SCCACHE_DIR` would therefore bring in flaky builds. Recommended mitigation: the first container to get `flock -n` on `/tw-sccache/.rw.lock` runs `READ_WRITE`, every other container runs `READ_ONLY`, and a server that fails to start means plain rustc plus one line. The docs do not say whether a `READ_ONLY` reader is safe while the single writer inserts or evicts. A concurrency probe must prove it. If the probe fails, option B applies: one daemon container in `SCCACHE_CLIENT_SIDE=1` mode over a UDS. B adds a long-lived service.

**Other facts the developer needs:**
- Cache keys depend on paths. Every tree and copy is mounted at `/work`, and the registry is at `/usr/local/cargo/registry`, so keys match across trees without `SCCACHE_BASEDIRS`.
- Incremental crates (the workspace members in the dev profile) and linking crates (proc-macros, build scripts, bins) are never cached. The hits will come from registry dependencies. C compiles inside build scripts (aws-lc-sys, libopus) are not wrapped either. The time saved is partial.
- Leave `CARGO_INCREMENTAL` as it is, so results stay identical.
- Stats live only as long as one container. Acceptance 2 needs the stats printed by the same container (`TW_SCCACHE_STATS=1` through `TW_DOCKER_ARGS`).
- The entry script must write nothing to stdout. `sccache --stop-server` prints stats, so send them to `/dev/null` or stderr. `scripts/licenses/rust.sh`, `ban-canary.sh` and `shell-test-layout.sh` parse stdout.
- uid: `tw-run` runs as `-u $(id -u):$(id -g)`. A cache directory owned by another host user is unwritable. That is the fallback path, not an error.
- Where the cache lives and how to clear it: a new subsection in `docs/decisions/ci-toolchain.md` (host path, `SCCACHE_CACHE_SIZE`, `rm -rf <main>/.teamwright/cache/core/shared/_tw-sccache`, the one-time `mkdir`), plus one line in `CLAUDE.md` Commands.

**Expectation gap (not blocking, for the owner):** sccache saves compile time, not disk. Each tree still keeps its full `target/`, and the shared cache adds up to `SCCACHE_CACHE_SIZE` on top. The 21 GB throwaway copies are a `target/` problem. The kit already offers `copy_env: {CARGO_TARGET_DIR: "{cache}/target"}` for copies, and the core area does not use it. That is a possible follow-up, not part of this task.

**Size:** one concern (the core runner's compiler cache) with two coupled edit points: the image entry and the `tw-run` host mount. Config and docs follow from them. It can stay a task and does not need Spec Kit, provided the single-writer design is accepted. That design stays inside #304's "one shared host directory", so I see no blocking owner question. The concurrency probe is the gating evidence.

**Guard paths:** none. The diff is `docker/rust.Dockerfile`, `docker/voicen-core-entry.sh`, `scripts/tw-run`, `.teamwright/config.yml` (through apply) and docs. `checker` stays `false`. The checks stay manual probes recorded under `## Tests`. Wiring a self-test of the entry script into `make check` would touch `Makefile` and need a `checker: true` task.
