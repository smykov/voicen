## Investigation

**Frame.** Observed: on push d9116cc to main (CI run 37498788064) the Gate job fails at its third step, `actions/setup-node@v5`, after 10 s with `Unable to locate executable file: pnpm`. `make ui-image`, the `tw-run ui` install, `make core-image`, the cargo cache and `make check` never ran, and the Windows job was skipped. Expected: setup-node puts host node 20.19 on PATH and the Gate runs `make check` with the ui area in voicen-ui:1.63.0. It reproduces on every Gate run since 376e1ac (T-064). This was the first main push that contained it; the previous run 37465516406 had a green Gate. It does not reproduce on the dev host, which has pnpm at /usr/local/bin/pnpm (nvm symlink).

**Hypotheses.**
1. *setup-node's automatic package-manager cache needs host pnpm.* Confirms: the log's inputs show `package-manager-cache: true`, the error comes right after "Environment details", and the v5 source (below) does exactly this. **Confirmed.**
2. *Something else in the Gate step list needs host pnpm or host node.* Checked below: nothing needs host pnpm. Host node is needed only by `scripts/ci/e2e-entry.test.sh`. **Refuted for pnpm.**
3. *The image build or the uid-1001 `tw-run ui` install would fail next.* Not observable: those steps never ran. Partly covered by hand in T-064 (Validation: uid 1001 in the image, `pnpm install --frozen-lockfile`, lint, test and `pnpm e2e` with `--network none -e CI` passed). **Open until the first green run.**
4. *The same concern on a second path.* The windows job also uses setup-node@v5, but runs `pnpm/action-setup@v4` first and sets `cache: pnpm`, so pnpm is on PATH. It was green on its own merits in earlier runs. **Not affected.**
5. *This class was fixed before.* See Recurrence below.

**Evidence.**
- `gh run view 37498788064 --log-failed`: `package-manager-cache: true` … `node: v20.19.6 npm: 10.8.2 yarn: 1.22.22` … `##[error]Unable to locate executable file: pnpm`. The run summary shows every later Gate step `-` (skipped), and the Windows job `-`.
- actions/setup-node, ref `v5` (tag commit a0853c24), read with `gh api` (not from memory; context7 not used):
  - `action.yml`: `package-manager-cache` "Set to false to disable automatic caching based on the package manager field in package.json", `default: true`.
  - `src/main.ts`: `else if (resolvedPackageManager && packagemanagercache) { … restoreCache(resolvedPackageManager, …) }`, reached when `cache` is not set.
  - `src/cache-utils.ts`: `getNameFromPackageManagerField()` matches `^(npm|yarn|pnpm)@`; for pnpm, `getCacheFolderPath` runs `pnpm store path --silent`. That command is the missing executable.
  - README › Caching: caching "is turned on by default when a `packageManager` field is detected"; `package-manager-cache: false` turns it off.
- `package.json`: `"packageManager": "pnpm@8.15.0"`, `"engines": {"node": ">=20.19"}`.
- For reference: in setup-node `v6` the automatic path is limited to npm (src/main.ts logs "Auto caching has been enabled for npm"). A bump to v6 would also remove the cause, but it touches the windows job's step as well and is not the minimal fix.
- **Other host dependencies in the Gate** (grep of the Makefile `check` prerequisites and their scripts: scripts/ci/*.sh, scripts/licenses/*.sh, scripts/e2e.sh):
  - Host bash, awk and python3: check-shell-layout(-fixtures), check-helper-windows-fixtures (reaches the core image), check-ci-credentials.
  - Core image: check-core, check-shell-windows, licenses-rust, licenses-fixture.
  - `tw-run ui`: licenses-unit/-bundle/-npm/-generate, and check-ui `pnpm lint` / `pnpm test`.
  - `scripts/e2e.sh` on the host uses bash, python3 and docker, then re-enters `tw-run ui -- pnpm e2e`.
  - `scripts/ci/e2e-entry.test.sh` needs host python3 and **node**. It uses its own fake pnpm/npx/docker, and runs the real `node_modules/@playwright/test/cli.js` with host node for the three host-config cases.
  - No bare `pnpm`/`npx`/`npm`/`corepack` on the host anywhere else. The grep found no matches outside comments and the fakes.
- Simulation: `env PATH="<dir with only a node symlink>:/usr/bin:/bin" scripts/ci/e2e-entry.test.sh` → `command -v pnpm` empty, `ok: 15 cases as expected`, exit 0 (node 20.20.2 here, not CI's 20.19.6). So after the fix the only host-node consumer works without pnpm.
- Image and install steps, not run in CI yet:
  - `make ui-image` is a `docker build` of `mcr.microsoft.com/playwright:v1.63.0-noble` (~956 MB pull, network available on the runner) + `npm install -g pnpm@8.15.0` as root in the build.
  - `scripts/tw-run ui -- pnpm install --frozen-lockfile` runs with `-u $(id -u):$(id -g)` (runner 1001:<runner gid>, no passwd entry in the image), `HOME=/tw-home` mounted from `.teamwright/cache/ui/home`, which tw-run creates as the runner, so it is writable. There is no `-it` (no TTY in CI), and the ui area has no `cache:` dirs, so the pnpm store is downloaded fresh on each run (cost only). node_modules is written by uid 1001 into the runner-owned checkout, so the host fixture can read it.
  - T-064 Validation covered uid 1001 by hand with gid 1001; CI's gid differs, which does not matter for runner-owned mounts. "CI uid 1001 in the image is not covered by any local test" (T-064 Tests) still holds.

**Root cause.** setup-node v5 caches for the `packageManager` named in package.json unless told not to, and that path needs pnpm on the host. T-064 removed host pnpm from the Gate job but kept setup-node with its defaults. This explains all symptoms: the error text, the 10 s failure, the skipped later steps and Windows job, and why the gate was green locally (pnpm on the dev host's PATH). Contradicting evidence: none.

**Invariant.** In the Gate job no step needs pnpm on the host. Host node exists only for the host fixtures, with setup-node's automatic package-manager features off. Every ui command runs through `scripts/tw-run ui` in voicen-ui:1.63.0 (E3).

**Seam.** The Gate job's setup-node step (`.github/workflows/ci.yml`, job `gate`) and its comment. The windows job is a separate path and stays as it is: it needs host pnpm for `pnpm tauri build`, sets it up first and caches it explicitly.

**Approach.**
- **(A) Recommended: `package-manager-cache: false` on the Gate setup-node step.** It removes the cause: with `cache` unset and the auto flag false, main.ts runs no restoreCache and no `pnpm store path` (its post step, cache-save, then has no package manager state to save). Node stays pinned at 20.19 for e2e-entry.test.sh (engines >=20.19). Extend the comment: "package-manager-cache: false — setup-node would otherwise cache the packageManager (pnpm) and needs pnpm on the host; no ui command runs on host node". Red → green: run 37498788064 (red at setup-node) vs the fix's run (Gate green, Windows job runs). Risk: low. It may expose the next unproven CI premise (H3: image pull or build, uid-1001 install); that would be a new finding, not a regression of this fix. Rollback: revert the one line.
- **(B) Drop setup-node from the Gate.** It also removes the cause, but the host node version would then float with the ubuntu-24.04 runner image. I did not verify which node that image ships, and the fixture and engines need >=20.19. Not recommended.
- **(C) Put `pnpm/action-setup` back** so the auto cache works. That brings back host pnpm, which T-064/E3 removed on purpose, and caches a host store that nothing uses. Rejected.
- **Host pin (acceptance "failure branch").** A small `make check` tripwire (a sibling of `check-ci-credentials`, with a fixture): every `actions/setup-node` step in a job that has no earlier `pnpm/action-setup` must say `package-manager-cache: false`. It decides on a switch written in the workflow, not on a model of the action's behaviour, so it is acceptable under F-003's rule. It still encodes a v5 default; under v6 only npm is auto-cached, so the rule stays sufficient. If the developer does not add the tripwire, the F-entry must record why: the real proof is a CI run, and the class belongs to T-066.
- **Proving it before main.** `ci.yml` `on:` is `push: branches [main]`, `tags ["v*"]`, `pull_request`. **A push to `wip/T-068` alone triggers nothing.** Instead, push `wip/T-068` and open a draft PR into main; `pull_request` runs both jobs on the merge ref. The orchestrator or owner pushes; DEV sessions never push, and `TEAMWRIGHT_PAUSE` blocks pushes. Cite that run in Validation, then land on main.

**Recurrence.** The class is "a premise that only CI can check, written on the Linux host, first checked by a push to main". This instance is *not* Windows: it is a GitHub Action's default in the Linux Gate job, and the dev host masks it because pnpm is on its PATH. Its outer mechanism is the same as F-002/F-005/F-007/F-009 (and F-008): the premise is unprovable locally, `ci.yml` has no trigger before main except a PR, and the first run is on main. T-064 even noted it ("a red first Gate run would be a regression of this task"). T-066's invariant names *Windows-only* premises, so as written it would not catch this one. Its proposed remedy (a branch / `workflow_dispatch` / PR probe before landing) would have.
- Recommend: **do not absorb T-068 into T-066.** Main is red (P1), and deferring would leave it red. Fix it now as a bounded config fix through this task.
- Recommend: log **F-011** under class `ci-toolchain` (count 2 → 3; tier T3 only if the tripwire lands), with "related: windows-premise-unchecked-on-host (same outer mechanism)".
- Recommend: add F-011 / T-068 to T-066's evidence, and ask the owner to **widen T-066's invariant from "Windows-only premise" to "CI-only premise"**: runner tools, action defaults, the CI uid, image builds in CI. A T-066 exit (c), and/or a small (a)/(b) such as `workflow_dispatch` or `push: branches: [wip/**]` triggers, would then cover both the Linux Gate and the Windows job.

I lean towards linking with the trailer and leaving T-068 a `bug`, because the rca task for the class already exists. I did not change `recurrence_of`.
