## Context

From T-043 review 2 finding #1. In CI run 39375257460 (wip/T-043 @ b5b82e6, windows job), `crates/voicen-whisper/tests/transcribe_wav.rs` took 265.55 s for 10 tests. In run 39366493906 it took 236.81 s. `WhisperModel` asks for min(available parallelism, 8) ggml threads (`crates/voicen-whisper/src/lib.rs:36`, `:169`), and libtest runs the tests in parallel on a 4-vCPU runner. T-043 found that ggml-cpu's barrier is a pure spin wait, so oversubscribed threads cost far more than they add: Silero went from minutes to 10.7 ms per decision at one thread. Whisper's graphs are large and may gain from several threads in a single run, so the Silero answer does not carry over. One transcription has to be measured alone and under the harness's parallelism. Then choose the engine's thread count, the test binary's concurrency, or both. The production case, one transcription with a VAD decision next to it on a user's machine, feeds T-102 and NFR-01.

## Acceptance

- [ ] The cause of the `transcribe_wav` run time on windows-latest is named with measurements (one transcription alone; the suite under libtest's parallelism)
- [ ] The thread count (or test concurrency) is chosen from those figures and recorded, and the Windows log prints the figure, with no wall-clock ceiling (F-013)
- [ ] Failure branch: the existing `transcribe_wav` guarantees (abort, quiet child, errors as LocalEngineFailed) still hold
- [ ] Test that fails without the change: <named by the test-writer, or the printed figure if F-013 rules out a failing test>

## Investigation

**Frame.** Observed: the `transcribe_wav` binary on windows-latest takes 236.81 s, 265.55 s, 280.73 s and 283 s for 10 tests in four runs: 39366493906, 39375257460, 40030080179, and 39299815752 (from T-099 r1#5). That adds about 4.5 min to every Windows job. Expected: seconds, as `silero_clips` became after T-043, which went from 1020.92 s to 0.34-0.36 s. It reproduces on every windows run. On Linux it cannot reproduce, because whisper.cpp is built only in Windows CI (the gate lints with `DOCS_RS=1`). Only the symptom is proven, the suite time. The uncontended time of one transcription has never been measured on any host.

**Tools.** I used Serena `get_symbols_overview` on `crates/voicen-whisper/src/lib.rs`. Serena `find_referencing_symbols` on `SpeechModelLoader` returned nothing (empty, which is not proof of absence), so I found the callers with grep over `crates/` and `src-tauri/`. The only production user is `local_models::residency` (`SharedModel = Arc<Mutex<Box<dyn SpeechModel>>>`, one transcription at a time). `src-tauri` does not link voicen-whisper yet (T-102). I read the ggml/whisper.cpp facts in the vendored whisper-rs-sys 0.15.0 source (`.teamwright/cache/core/.../whisper-rs-sys-0.15.0`), not in context7: the pinned version's own source is the stronger source. I downloaded the CI logs with `gh run view -R <repo> --job <id> --log` (gh is authenticated) for jobs 120681277478, 118475401141 and 118447805367.

From 22:15:39 on, three or four models (and from 22:17:36 a child process as well) compute at the same time, each with 4 ggml threads, on 4 vCPUs. A 1 s clip costs about 90 s, linear in the number of clips (2 clips took 187 s). The other two runs have the same order and the same 60 s warnings.

**Hypotheses.**
1. *Thread oversubscription of the spin barrier (libtest parallelism × engine threads).* Confirmed in mechanism, not in size. Available parallelism is 4 (the `silero-timing` line in the same job). libtest defaults to that many test threads, and `ci.yml:173` passes no `--test-threads`. `thread_count()` = min(4, 8) = 4. `ggml_barrier` (ggml-cpu.c:547) spins on `n_barrier_passed` with `ggml_thread_cpu_relax()` and returns at once only for `n_threads == 1`. OpenMP is off (whisper-rs-sys build.rs:289-290; the `openmp` feature is not enabled, pinned by `direct_dependencies_are_voicen_core_and_whisper_rs`). The same shape cost Silero 40 s per decision against 17-20 ms (T-043 table), and the fix there had the predicted effect on Windows. What would refute it: one transcription alone also taking tens of seconds. That figure is missing (see below).
2. *whisper.cpp built without optimisation under `cargo test`.* Refuted. whisper-rs-sys build.rs:267-275 sets `RelWithDebInfo` under `debug_assertions`, with `.profile("Release")` (build.rs:184). `.cargo/config.toml` forces `/O2` for both build types. T-043 Investigation reached the same result for the same build.
3. *The work itself is large (30 s encoder window per call; the 60 s abort baseline).* Partly true, but not the cause. Every call encodes at least one 30 s mel window, and `pre_requested_abort_returns_promptly` encodes two windows plus decoding. That is the longest single piece of work, but the 1 s clip tests alone cost 90-190 s each. `pre_requested_abort_returns_promptly` finished 13 s after the last other test ended (22:19:55 → 22:20:08), which fits fast progress once it ran alone. That is an inference, not a measurement.
4. *A second path handles the same concern.* Yes, and it is already fixed: `SileroDetector` has a fixed `VAD_THREADS = 1` (silero.rs:43, T-043). `thread_count` has a single caller (`WhisperLoader::load`). In production, `residency` serialises transcriptions. Upcoming paths that will run ggml next to a transcription: T-102 (shell VAD gate, a 1-thread decision before the engine call) and T-135 (Silero speech spans for the call final pass, possibly next to a transcription of another track). Their combined thread budget is not owned by any task yet (see D1).
5. *This class was fixed before.* Yes, for the detector only. T-043 review 1 #1 (Silero) was fixed by `VAD_THREADS = 1`. T-099 r1#5 (this binary, 283 s, "serialise the model tests with one lock") and T-043 r2#1 are open in T-060's follow-ups and were spun off as this task. No CI run was red: this is cost, not a failure, so there is no F-entry, and `recurrence_of` stays empty. This is not a recurrence after a fix: T-043 deliberately left the whisper half to this task. **No rca is needed.** If a third ggml user (T-102 / T-135) shows the same symptom, an rca on a process-wide ggml thread budget is due.

**Recurrence check against docs/failures.md.**
- F-013 / F-021 (class `os-answer-deadline-race`, P-010): these govern the *test*, not the cause. Its I2 (no wall-clock ceiling, since T-110 not even a spec tolerance) is enforced only in voicen-core by clippy `disallowed-methods`. voicen-whisper is outside that switch (T1, review only). So: (a) Acceptance 4 cannot be a time test, and the evidence is a printed figure, as T-043's `silero-timing`. (b) `pre_requested_abort_returns_promptly` already holds a clock-decided verdict, `aborted * 4 <= baseline` (transcribe_wav.rs:292), a ratio of two wall-clock readings. T-099 r1#5 flagged it as a T-107-class flake risk under this exact load. The file lock removes the load during the reading. It does not make the verdict clock-free, because the aborted run's own work before the first encoder callback (mel of 60 s) is real time. Leave the assertion as it is in this task, and note it as a follow-up for review (a candidate replacement: a count of encoder callbacks instead of a ratio).
- F-019 (window-build ceiling) and F-018/F-020 (ordering signals) are not related.
- No F-entry covers ggml threads. The class has no entry because nothing went red.

**What is missing and how the implement stage gets it.** There is no Windows figure for one transcription alone, at any thread count. Without it the engine policy (Acceptance 2) would be a guess, and the Silero answer (1 thread) does not carry over (T-043 r2#1 (b)). The way to get it: the first commit on `wip/T-109` adds the print-only `whisper-timing` test. It runs as a child of the test binary (the `quiet_child_run` shape: `--exact <child> --ignored --nocapture --test-threads=1`) while the parent holds the file lock, so nothing else in the process computes. Per count n ∈ {1, 2, 3, 4} it loads tiny and times 3 runs each of the 1 s clip and `long_audio(30)`. It prints `whisper-timing: threads n, 1 s clip best X ms, 30 s best Y ms, available parallelism P` to stderr past libtest's capture. The developer cites the run id and the lines under `## Tests`. The parent asserts only that the child passed. No figure is compared to a limit. A Linux surrogate (as T-043) is optional, because the Windows log is the evidence.

**Recommended exit:** n/a (bug, not rca). Single seam per side: the test file lock, and the policy function in `lib.rs`.

**Owner decision points.**
- **D1, the production thread policy for WhisperModel** (after the figures). Options: (i) keep min(parallelism, 8); (ii) min(4, parallelism), whisper.cpp's own default (src/whisper.cpp:5910); (iii) the measured best count capped below parallelism (for example min(4, parallelism − 1), at least 1), which leaves a core for the VAD decision and the desktop, because a spin barrier with as many threads as CPUs stalls whenever any other process takes a CPU (T-043: Silero at 4 threads alone on 4 pinned CPUs took 403-1657 ms against 29-105 ms on 6 CPUs). Recommendation: (iii), with the exact cap taken from the `whisper-timing` table. If 4 threads alone are clearly fastest on the 4-vCPU runner, take (ii). (i) is not recommended either way: 8 spinning threads on a typical 8-logical-CPU laptop leave nothing for the VAD, the UI or the paste.
- **D2, the test-only thread knob.** A `#[doc(hidden)] pub fn WhisperLoader::with_threads(NonZero<usize>)` kept for the timing test, or a throwaway measurement commit that is reverted. Recommendation: keep it, because it lets the printed line show the chosen count against the alternatives in every run (T-043 r2#2 noted that nothing shows a regression of `VAD_THREADS`, and the same holds here). It is not a user setting (no settings field, no env variable).
- **D3, where the decision is written.** No decisions file owns the built-in engine yet. `VAD_THREADS` lives only in a code comment and in T-043. Recommendation: a short `docs/decisions/builtin-engine.md` (from `_area-template.md`) with both thread invariants (VAD 1, engine policy plus the table, the barrier mechanism, what breaks if violated), plus a `docs/decisions.md` row for D1.
- Not an owner decision, for review: whether `pre_requested_abort_returns_promptly`'s timing ratio is replaced (see F-013 above). Recommendation: a separate follow-up, not part of T-109.
