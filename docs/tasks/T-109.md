## Context

From T-043 review 2 finding #1. In CI run 39375257460 (wip/T-043 @ b5b82e6, windows job), `crates/voicen-whisper/tests/transcribe_wav.rs` took 265.55 s for 10 tests. In run 39366493906 it took 236.81 s. `WhisperModel` asks for min(available parallelism, 8) ggml threads (`crates/voicen-whisper/src/lib.rs:36`, `:169`), and libtest runs the tests in parallel on a 4-vCPU runner. T-043 found that ggml-cpu's barrier is a pure spin wait, so oversubscribed threads cost far more than they add: Silero went from minutes to 10.7 ms per decision at one thread. Whisper's graphs are large and may gain from several threads in a single run, so the Silero answer does not carry over. One transcription has to be measured alone and under the harness's parallelism. Then choose the engine's thread count, the test binary's concurrency, or both. The production case, one transcription with a VAD decision next to it on a user's machine, feeds T-102 and NFR-01.
