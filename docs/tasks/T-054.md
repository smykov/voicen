## Context

Split from T-008 by decision #64 (T-008 analysis Q3): the one-time `notice.logs_unwritable` when the log goes Degraded (through T-053's overlay or T-007's notifier), and the Windows test that a dictation still works with the logs dir denied. Narrowed 2026-10-07 (orchestrator, T-071 Notes): the tray item "Open logs folder" moved to T-071 (`ShellExecuteExW`, no plugin; it creates the folder when missing, spec 006 FR-017).

## Acceptance

- [ ] Windows CI: with the logs dir denied, the app starts, a dictation still delivers, and the notice is shown exactly once
- [ ] Failure branch (restated by the analysis; the previous one was the tray item's, moved to T-071): the log fails before the dictation session exists (at start), from a thread that holds the session lock, or a second time in the same session (a roll blocked by a reader that does not share delete, or a failure after `LogsRecovered`). In every case exactly one notice is shown for the session, nothing deadlocks, and the dictation still delivers. Verified by core tests on Linux (latch orders, the under-lock writer, catalog) and by Windows CI (ACL-denied folder; blocked roll, which pins the reason Windows gives for it)
- [ ] Test that fails without the change: `src-tauri/tests/diag.rs` (Windows CI)

## Investigation

**Frame.** Expected (spec 006 FR-009, Clarification Q3; FR-20 failure branch): when the logs folder cannot be created or written, the app keeps working and shows "Logs cannot be written: <reason>" at most once per session. A later recovery writes again with no new notice. Observed in the code: the log degrades and calls `on_unwritable` once (T-008, proven on Linux for `NotADirectory` and `DiskFull`, and on Windows for a file at the logs path). The release wiring passes a no-op closure, so the user sees nothing. This is a missing feature, not a defect.

**Hypotheses.**
1. *The callback is simply unwired.* Confirmed: `lib.rs::release_parts` passes `diag::start(paths::log_dir(), Box::new(|_| {}))`, and its comment says "T-054's one-time notice; until then the log only degrades".
2. *A direct wire-up is enough.* Refuted for two reasons:
   - **Ordering.** `Log::open` (`diag/log.rs:137-147`) calls the callback before it returns, inside `release_parts`. That is before `wire()` starts the overlay and before `start_dictation` builds the session (`lib.rs::run`, `:371-392`), so at start there is nothing to call.
   - **Lock re-entry.** `dictation.rs` `Shared::publish` calls `Indicator::set_tray` with the state lock held (`:189-207`). `tray.rs` `Shared::want` runs `apply` inline when it is on the main thread (`:119-131`), and `render` writes `tray_failed` (`:224`). So the first failure can be raised on a thread that holds the session mutex. A callback that called the session inline would deadlock, because std `Mutex` is not re-entrant.
3. *The same concern is handled on a second path.* Checked. Every other notice raised outside a job goes through `RecordingController` under the session lock, from inside `DictationSession`:
   - `notice.choose_engine`: the press gate (T-051);
   - `notice.mic_fallback`: the press (T-012);
   - `notice.hotkey_unavailable`: `hotkey_registration` (T-055).

   None of them is raised by a log writer on an arbitrary thread, so there is no path to reuse. `DictationSession` has no public notice method (searched for `pub fn` in `dictation.rs`).
4. *This class was fixed before.* No. `docs/failures.md` has no entry of class `diagnostics-log` (`docs/decisions/diagnostics-log.md` says so too), and none on notices or lock re-entry (searched for: diagnostic, notice, deadlock, callback, unwritable, once). The work was planned and deferred: T-008 → T-054 by #64, P1 → P3 by #69, and the tray item went to T-071.
5. *T-007's notifier is needed.* Refuted. Precedent: `notice.choose_engine` and `notice.hotkey_unavailable` are shown on the overlay now, and "the toast comes with T-007's notifier on the same path" (`specs/001-dictation-via-api/contracts/messages.md`). T-053 and T-057 fix the route: T-054's messages reach the overlay only as `OverlayState` through the controller. The overlay is wired in release (`ShellIndicator::new` → `overlay::part`; `overlay::start` in `wire`). T-057 is DEFERRED, but its code is in the tree (absorbed by T-065, DONE, `tail_code` ratified).

**Root cause, invariant, seam, approach:** see the `analysis` block.

**Notes item: Windows error 32 on the roll.**
- **std's mapping (proven from std 1.99.0 source).** `library/std/src/sys/io/error/windows.rs::decode_error_kind` has no arm for `ERROR_SHARING_VIOLATION` (32) or `ERROR_LOCK_VIOLATION` (33). The kind is `Uncategorized`, so `diag::log::unwritable` returns `Other(Some(32))`. These files were fetched from the `rust-lang/rust` 1.99.0 tag, because the `voicen-rust:1.99` image has no `rust-src` component.
- **What the roll actually reports (unproven).** `fs::rename` (`library/std/src/sys/fs/windows.rs::rename`) calls `MoveFileExW` first. Only on `ERROR_ACCESS_DENIED` does it retry through a `DELETE`-access handle and `FileRenameInfoEx`, and on failure it returns the first error. So if `MoveFileExW` reports 5 rather than 32 for a source held open without `FILE_SHARE_DELETE`, the reason is `PermissionDenied`. Which one Windows gives has never been observed. Red test (6) measures it and pins it, and `diagnostics-log.md` § Windows notes is updated with the measured result.
- **How the notice treats it (decided).** A blocked roll is "not writable", like any other failure: one notice and Degraded. The alternative ("retry without degrading") means either appending past `roll_bytes`, which breaks the invariant "The log files never total more than 10 MiB, at any instant", or dropping lines, which is Degraded anyway. The reason's wording, including whether it gets its own text, is OQ-35 (2). This closes the item in `diagnostics-log.md` § Open.

**Details for the developer.**
- **Where the latch is attached.** In `start_dictation`, right after `app.manage(session)` and before `HotkeyThread::start`. The startup `notice.hotkey_unavailable` comes later and replaces the logs notice in the single message slot (`RecordingController::notice_with`: the newest message wins). The more actionable message stays visible. A press drops either one.
- **Deliveries.** A delivery at attach runs on `start_dictation`'s thread, which holds no session or tray lock. A delivery after attach runs on one spawned thread. If that spawn fails, the notice is lost; there is nothing to log it to.
- **Where the ACL test lives.** `src-tauri/tests/diag.rs` (Acceptance line 3). It can use core fakes for the clipboard and the paster, so it needs none of the runner's SendInput or clipboard capabilities. `Win32_Security_Authorization` is not among the shell's `windows` features. Use either `icacls`, bounded and observable under the F-006 rule (null stdin, `CREATE_NO_WINDOW`, killed at a budget), or that feature added under dev-dependencies (no new crate, #9). Remove the deny ACE before `TempDir` cleanup. The runner's user is an administrator; a deny ACE still applies to that token, because std opens without backup semantics. The precondition probe asserts this loudly instead of assuming it.
- **What is proven only by review.** No test reaches `release_parts`: it uses the real `paths::log_dir()`. Review checks that it passes `latch.callback()` instead of `|_| {}`. The install smoke is unchanged. A logs notice at first launch would add a visible overlay window, but the smoke's logs dir is writable.
- **Docs to update in the same commit.**
  - `docs/decisions/diagnostics-log.md`: the "reported once" invariant gains the notice path and the latch; Windows notes get the measured code; § Open loses T-054's items.
  - `specs/006-diagnostics-and-release/contracts/ipc.md`: the `logs_reason.*` rows and the RU text.
  - `contracts/core-diag.md`: the latch.
  - `specs/001-dictation-via-api/contracts/messages.md`: a "Since T-054" sentence.
  - `specs/006-diagnostics-and-release/plan.md:148-149`: `DictationRecord` → `DictationLine` (T-008 review round 2 Low, "at the next touch of spec 006").
  - `src-tauri/src/lib.rs` comments at `:177` and `:384`: they name T-054 as the owner of the notices for a failed settings-window open and a failed dictation start, which are not in this task's scope. Correct them; do not widen the task.

**Size verdict: small.** It is one behaviour, the notice hand-off from `on_unwritable` to the controller. It adds to existing seams: the core catalog and a public session method, as T-055 did, and the shell's start wiring. There are about 6 red-test groups: 4 on the Linux gate and 2 on Windows CI. The behaviour is settled by spec 006 FR-009, Clarification Q3 and the overlay precedent. Only the copy is open (OQ-35, non-blocking; proposals apply).
