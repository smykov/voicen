**Finding (FAIL).**
1. The refused case of `api_pipeline::no_event_or_failure_carries_key_query_or_transcript` is one of the four T-047 call sites (`api_pipeline.rs:1019`). It fails on windows-latest at 9fedb17, and will fail the same way on every run there. The scenario runs under `ms = Timeouts { connect: 2 s, api_transcription: 300 ms, .. }` (`api_pipeline.rs:1020-1024`). On Windows a refused loopback connect is answered only after about 2 s of SYN retries, so the 300 ms total timeout fires first and `classify` returns `Timeout`, not `CannotReach`. Review 2 says this call site is "robust on Windows" because "a connect timeout gives [CannotReach] too". That reasoning misses the 300 ms total. T-047's own fix did not cause the defect: the test came from T-001, and the old released-port helper would refuse just as slowly on Windows. But T-047's Windows claim (decision #53: "the first Windows CI run confirms it") is not proven. The run that was supposed to prove it is red on a T-047 call site, and 2 of the 4 call sites never ran there.
