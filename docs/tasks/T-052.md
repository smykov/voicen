## Context

Split from T-006 by decision #64. Tray icons per `IndicatorState` (incl. the error state) and menu; `prevent_exit` only for user-initiated exits (tauri 2.12.1 `RunEvent::ExitRequested { code: None }`), so closing the first-run window no longer ends the app (#38 interim); the single-instance plugin (a second launch opens settings); every non-main-thread caller of `settings_window::open` goes through one main-thread hop (T-037 review round 1 note); tray menu rebuilt on a UI-language change and the notifier on `SettingsService::subscribe()` (#34); the install smoke's window predicate revisited for tray/tool windows (T-037 review round 2 note, F-003 rule: decide on raw window facts). The "Open logs folder" tray item is T-054's. Adds tray-icon / plugin features in one Cargo.toml change, then `make licenses`.

## Acceptance

- [ ] Windows CI: the tray icon exists after start and reflects the indicator state; closing the settings window keeps the app running; a second launch opens (or focuses) the settings window and exits
- [ ] Failure branch: two concurrent `open` requests from non-main threads leave exactly one settings window (focus, no "already exists"); exit from the tray menu ends the process — Windows CI
- [ ] Test that fails without the change: `src-tauri/tests/tray.rs`, `src-tauri/tests/single_instance.rs` (Windows CI) and the install-smoke second-launch check

**Hypotheses.**
1. *Parts exist under other names.*
   - True in core: `TrayState`, priorities, `tray_menu_opened`, `retry_available` publication, dedupe under the lock, `SettingsService::subscribe`, `startup_action`, `autostart::launched_by_autostart`, `i18n::text`. The settings window primitive exists too (`open`, `on_ready`).
   - False for the tray, the exit policy, the instance check, the tray ids in the catalogs, and any `Indicator`/`ShellRequests` implementation.
2. *The same concern on a second path.* Five risks, each closed by the invariant:
   - (a) The startup side effects run outside the instance check. A second launch runs `lib.rs:135-161` before `build()` decides (`app.rs:2607`). Its effects, all on the primary's files:
     - a `started` line in the primary's log, and a roll that renames the file the primary holds (the T-008 note);
     - a `.part` deleted by `cleanup_at_start` while the primary is downloading;
     - a `Reset` that moves an unreadable `settings.json` aside;
     - a Run-value reconcile.

     The T-008 note named only the first. Closed by (1).
   - (b) Several `open` callers on different threads (Ready, tray, second instance, T-006's engine-none press). The T-037 note expected "already exists". The source shows a worse outcome: the label check (`manager/window.rs:70-72`) and the insert (`:116-117`) bracket the OS window creation (`window/mod.rs:390-415`). Two builders can both pass, two windows are created, and the second insert replaces the first in the map, leaving an unmanaged window on screen. In the real runtime the gap is a whole WebView2 creation (`create_window` waits for the main thread, runtime-wry `lib.rs:300-335`). Closed by (2).
   - (c) A naive `set_tray` that calls `TrayIcon::set_icon`. It waits for the main thread (`menu/mod.rs:26-40`) while it holds the session lock. If the main thread is itself waiting for that lock (the tray handler calling `tray_menu_opened` inline), this is a deadlock. Closed by (3).
   - (d) Tray, overlay and Retry each keeping their own tray state, or the tray reading `Pipeline::pending()`. Closed: `retry_available` arrives only through `set_tray` (dictation-session.md).
   - (e) A tray built from `tauri.conf.json` `app.trayIcon`. tauri builds it inside `build()` before the plugins (`app.rs:2590-2607`), so a second instance would flash a tray icon before it exits. Closed: the tray is built in code after `build()`.
3. *The class was fixed before.* No.
4. *`ExitRequested { code: None }` means "the user asked to exit".* Refuted for our app. In 2.12.1 its only source is the last window's `Destroyed` (runtime-wry `lib.rs:4255-4270`). Every programmatic exit carries `Some(code)` (`lib.rs:4300-4311`, `app.rs:581-587`).
   - A Loaded start, which has no window, never emits it.
   - The tray "Exit" (`app.exit(0)`) is `Some(0)`.
   - So the rule is: prevent `None`, pass `Some(_)`. tauri ignores a prevent only for `RESTART_EXIT_CODE` (`app.rs:90-93`).
5. *A `run_on_main_thread` hop serialises `open` and can be proven on Windows CI.* Half refuted.
   - In the real runtime every hop runs on the one main thread (`lib.rs:263-279`), so the calls are serialised.
   - But in the mock runtime the shell tests use, a task runs inline on the calling thread while the loop is not running (`mock_runtime.rs:84-96`). A two-thread test would race exactly as before, so it would not be red without the hop.
   - A main-thread caller runs the hop inline, so the second-instance callback (inside the primary's `WM_COPYDATA` window proc, `windows.rs:156-169`, while the second process blocks in `SendMessageW`) would build WebView2 inside an event handler. tauri documents that case as a deadlock on Windows (`webview_window.rs:56-59`).

   Hence option B below, the same pattern T-053 chose for the overlay ("every window operation on one overlay thread").
6. *One seam.* Refuted; see the size verdict.

**Library facts used by the design (pinned sources).**
- `AppHandle::run_on_main_thread` is fire-and-forget: from another thread it posts through the event-loop proxy, and on the main thread it runs inline (runtime-wry `lib.rs:263-279`, `:2626-2627`). tauri's `TrayIcon::set_*` and `TrayIconBuilder::build` wait for the main thread (`menu/mod.rs:26-40`, `tray/mod.rs:351-383`, `:499-526`). Inside a main-thread task they run inline.
- Tray events (tray-icon `windows/mod.rs:418-452`, `:499-506`):
  - `WM_RBUTTONUP` gives `Click{Right, Up}`, and `WM_LBUTTONUP` gives `Click{Left, Up}`;
  - the event is sent first, then the menu is shown (`TrackPopupMenu`) when `menu_on_right_click`, or `menu_on_left_click` for a left click;
  - both default to true (`lib.rs:246-258`; tauri `show_menu_on_left_click`, `tray/mod.rs:309-322`).

  So "menu opened" = `Click{Right, Up}`, or `Click{Left, Up}` while the left-click flag is set. That is one constant, used both for the builder and for the handler (P-010).
- The menu cannot be updated "on open": the event reaches tauri through the event-loop proxy, after `TrackPopupMenu` has started. Language changes must be pushed (a subscriber).
- `TrayIcon::rect()` (tauri `tray/mod.rs:620-627`, tray-icon `windows/mod.rs:304-306`) is `Shell_NotifyIconGetRect`. It is `Some` only once the shell knows the icon: a raw fact for "the icon exists". The first push shows whether `windows-latest` has a notification area (probe).
- tray-icon tolerates a missing Explorer at start and re-registers on `TaskbarCreated` (`:160-163`, `:374-383`). FR-013's "tray icon reappears after an Explorer restart" therefore comes for free; it is the owner's check.
- `tauri::include_image!` (tauri `lib.rs:86`) embeds PNGs at compile time, so the `image-png` feature is not needed.
- `MenuEvent { pub id }` (`menu/mod.rs:46-49`) and `TrayIconEvent::Click{..}` (only the enum is `non_exhaustive`) can be built in tests, so the handlers can be called directly. `MenuItem::text()` is readable (`menu/normal.rs:87`). There is no visibility toggle, so the menu is rebuilt with `set_menu`.
- Plugin 2.5.2, other facts:
  - the second instance grants the primary foreground rights before it sends (`windows.rs:82-86`), so a focus from the primary is allowed;
  - the primary releases the mutex on `RunEvent::Exit` (`:122-126`);
  - argv arrives as `Vec<String>`, which `autostart::launched_by_autostart` accepts (`autostart.rs:38-45`);
  - if the primary's window is not found yet (simultaneous launches), the second instance falls through and runs as a full instance (`:73-107`). This is residual plugin behaviour, not closed here.
  - It needs no capability (no commands).
- tao and tauri: `App::run_return` (`app.rs:1422-1430`) returns the exit code without `process::exit`, and `Builder::any_thread` (`app.rs:1694-1706`; tao `event_loop.rs:175-180`) lets a libtest thread run the real Wry loop. T-053's shell half (T-057) plans the same for `overlay.rs`.

**Design (option A, recommended).**
1. **One assembly body, primary-only side effects** (`lib.rs`):
   - `assemble(builder, context, parts: impl FnOnce() -> Parts)`:
     - `commands(builder).build(context)?` (plugins' setup run here);
     - then `parts()` (`diag::start`, `LocalModels::open` with its cleanup warning, `load_settings`, the autostart flag);
     - then `wire(&app, parts)`: manage `service` / `local_models` / `log`, the change bridge, the opener, the tray, the follower.
   - `build_app(builder, context, service, local_models, log)` stays as `assemble(builder, context, move || ...)`, so the six test call sites do not change.
   - `run()` = `assemble(Builder::default().plugin(tauri_plugin_single_instance::init(on_second_instance)), generate_context!(), release_parts)` and `.run(on_run_event)`.
   - The second instance never returns from `build()`, so it opens no log and touches no file, registry value or tray. Today's order (log first, then settings) is kept *after* `build()`; T-006 adds the session at the end of `wire` or right after `assemble`.
2. **Serial settings opener** (`settings_window.rs`):
   - `request(app, OpenTarget) -> Receipt` sends to one `std` thread ("settings-window", FIFO `mpsc`) that runs `open`. Every runtime caller uses it and drops the receipt: `on_ready` (Ready), the tray item, the second instance, and T-006's `ShellRequests`.
   - tauri executes the build on the main thread (`create_window` posts and waits), so the window is still created there. That is tauri's own advice for creating windows (`webview_window.rs:56-59`, the "separate thread" examples), and no window is built inside an event handler.
   - Nobody waits for the opener: the main thread never waits on it, and receipts are waited on only by tests.
   - A failed open writes the one `warning kind=settings_window_failed os_code=..` line on the opener thread, so the `run()` Ready handler no longer logs. Fix the `lib.rs:176-178` comment there (T-008 r2 Low #1): after a failed open, the user's way back is the tray "Settings" item or a second launch; the one-time notice is T-054's.
   - S1 holds: `open` is still the only constructor.
3. **Tray** (`tray.rs`, core `voicen_core::tray`):
   - Built in `wire`, after `build()`, with the icon for `TrayState::Idle` and the language of `service.snapshot()`, read after `service.subscribe()` (`service.rs:317-328`). The session publishes nothing at start (dictation-session.md), so the tray must start Idle.
   - State: `Mutex<TrayView { state, retry_available, lang }>` plus a "task pending" flag. `TrayPart::set_tray(state, retry)` and the follower (one more `subscribe()`, its own thread, acting only on a `ui_language` change) store the value and, if no task is pending, post one `run_on_main_thread` apply task. They never call a `TrayIcon` setter themselves.
   - The task takes the latest view and applies:
     - `set_icon(include_image!(icon kind))` and `set_tooltip(text(lang, tooltip(state)))`;
     - `set_menu` when `(lang, retry_available)` changed;
     - an `applied` record for tests.
   - Menu: core `menu(retry_available)` = `[OpenSettings, Exit]` in T-052. T-007 adds Retry (only while `retry_available`), T-054 adds "Open logs folder", feature 005 adds History. Item ids are `TrayAction::as_str()`.
   - Handlers:
     - `OpenSettings` → `request` (Q2 default below);
     - `Exit` → `app.exit(0)`;
     - "menu opened" → stamp `Instant::now()` on the main thread, then hand `session.tray_menu_opened(at)` to a non-main thread (`tauri::async_runtime::spawn_blocking`). The session is looked up with `try_state::<Arc<DictationSession>>()`, which is `None` until T-006 manages it.

     The main thread therefore never takes the session lock. A press holds that lock across `AudioSource::start`, which may be slow with cpal, and any `Indicator` call would otherwise run inline on the main thread (T-053 hypothesis 2(c)).
   - Failure to build the tray or spawn a thread writes a typed `Warning` (new `WarningKind`(s) in core `diag` with their format literals and the exhaustive `diag_format` case; #45). Without a tray, `prevent_exit` is not applied (rule 4).
4. **Exit policy** (`on_run_event`):
   - `Ready` → `on_ready(...)`, as today, through the opener;
   - `ExitRequested { code: None, api, .. }` with the tray installed → `api.prevent_exit()`; anything else passes.
   - Exit ends the process (tao `process::exit`) without dropping the session. In-flight and queued results are dropped, as the spec's exit edge case says (spec.md:155). This settles T-051 Q3 for app exit with no core change: `DictationSession::drop`'s join is not used at exit. Audio deletion on exit (FR-032) is T-007's (`delete_all` on `RunEvent::Exit`).
5. **Second launch:**
   - `on_second_instance(app, argv, _cwd)` → core `second_launch_action(launched_by_autostart(argv))` → `TrayOnly` for `--autostart` (spec 004 FR-019: a logon start opens no window), otherwise `request` per Q2.
   - The callback does nothing else: no log line, no file.
6. **Subscribers (#34).**
   - The tray menu and tooltip get their own `subscribe()` (above). The `settings://changed` bridge stays the only emitter (J3).
   - The Notifier needs no subscriber: T-007's toasts render with `snapshot().ui_language` at each notify, which is what spec 004 FR-013's "the next notification" asks (P-013). Route this to T-007 Notes.
7. **Dependencies (one `Cargo.toml` commit):**
   - `tauri = { version = "2", features = ["tray-icon"] }` and `tauri-plugin-single-instance = "2.5"`, each on one line (MIT OR Apache-2.0, accepted; consented by #9).
   - The plugin also brings `tracing` (facade only, already in the lock; no subscriber is installed, per diagnostics-log.md), `tokio` (net), `windows-sys 0.61` and `thiserror 2`, all already in the lock, and `zbus ^5.9` for Linux, which is new to `Cargo.lock`.
   - `about.toml` `targets = ["x86_64-pc-windows-msvc"]` keeps zbus out of the notices. tray-icon and the plugin join `THIRD-PARTY-NOTICES.txt` (tray-icon is not in it today).
   - Resolve the lock and run `make licenses` with network (CLAUDE.md gotcha). The zbus tree adds a few MB to the registry cache; the disk is near full.
   - T-056's `check-shell-windows` needs the same crates.
8. **Capabilities:** unchanged. The tray and the plugin have no webview commands.

**Options.**
- *Serialising `open`:*
  - **B. One opener thread (recommended).** Removes the race for every caller. Deterministic in the mock (red test below). No window is built inside an event handler or a `WM_COPYDATA` handler. Cost: one idle thread; `on_ready` becomes asynchronous, so the five T-037 `on_ready` tests wait on its receipt. Risk: a window build waits for the main thread, but no one waits for the opener. Rollback: revert `request`; callers call `open`.
  - **A. `run_on_main_thread` hop for non-main callers.** Correct in the real runtime, but not provable in the mock, which runs tasks inline (hypothesis 5). It builds inline from the main-thread callers (the second instance inside `WM_COPYDATA`).
  - **C. A mutex inside `open`.** Deadlocks: the main thread blocks on the mutex while the holder waits in `create_window` for the main thread. Rejected.
  - **D. `WebviewLabelAlreadyExists` treated as focus.** Does not close the two-window case (hypothesis 2(b)). Harmless only as an extra.
- *Primary-only side effects:*
  - **assemble (recommended).** The order is enforced by construction, and the tests share the body.
  - Keeping `run()`'s order and adding a hand-written mutex check before `diag::start`. That is a second instance mechanism beside the plugin (P-011), so rejected.
  - Registering the plugin in `build_app`. That is the silent-pass hazard above, so rejected.
- *Proving "exit from the tray ends the process":*
  - **`lifecycle.rs` on the real Wry runtime with `any_thread` + `run_return` (recommended).** Calls the same `on_run_event` and the tray's menu handler with the `exit` id, on the main thread. Bounded by a watchdog thread that ends the exe non-zero.
  - Mock only: `app.exit` hits `unimplemented!()` (`mock_runtime.rs:150-152`), so it can at most show a panic.
  - Smoke through UIA (right-click the icon, invoke "Exit"): it depends on Explorer and the overflow flyout on the runner, and on tray-icon's private `WM_USER_TRAYICON = 6002`. Kept only as the owner's manual check.
