## Context

Session review of 2026-10-23. In the T-116 agents' transcripts, commands that should take under a second took 1–2 min between `tool_use` and `tool_result`: `sed -i '460{/^$/d}' … ; sed -n …` 2.1 min, a `python3 -` in-place edit 1.3 min, `grep -n … | head` 0.9 min, a `cat >> …/mutants.py <<'PY'` 1.6 min. No build ran at those moments in that agent. Candidates: PreToolUse hooks (`scripts/hooks/`, the teamwright gates), the permission/auto-mode check, host load from a parallel agent or gate. Unknown which; nothing is changed until the cause is measured.

## Acceptance

- [ ] The cause is measured, not guessed: per-call timings of hooks vs. the command itself (hook timing log or `time` around the hook scripts), on a reproduction with a trivial command
- [ ] Either a fix (hook made cheaper, matcher narrowed) with before/after timings, or a recorded finding that the latency is outside the repository (runtime or permission layer), with the evidence
- [ ] Failure branch: a hook that must refuse (e.g. the VERIFY GATE on a shell write to a verify record) still refuses after any change; shown by one refused call
- [ ] Any change to `scripts/hooks/` follows the guard rules if it touches a guard path; `make check` stays green

## Tests

## Investigation

Investigator, 2026-10-24. Serena loaded but not needed (no code symbols involved: shell hooks, JSONL logs, transcripts); evidence read with python (`-I`) and the Bash tool.

**Frame.** Observed: in the T-116 transcripts four calls whose shown text is trivial took 0.9-2.1 min from `tool_use` to `tool_result`. Expected: about 1 s. Guesses in the Context: hooks, the permission/auto-mode check, host load.

**Hypotheses.**
1. PreToolUse hooks are slow. Confirms: a hook taking tens of seconds. Refutes: hook timings well under 1 s. Result: refuted.
2. The permission or auto-mode check is slow. Confirms: a long gap with `PermissionRequest` events, or long pre->post gaps on calls that really are trivial. Refutes: those calls take about 1 s. Result: refuted for the cited calls. It cannot be separated from hook time, but the two together are about 1 s.
3. Host load. Confirms: light calls slow down while unrelated heavy processes run. Result: confirmed as a secondary effect, worth seconds not minutes (up to 14 s).
4. The measurement is wrong: the "trivial" calls are not trivial. Confirms: the full `tool_use` input holds a heavy step. Result: **confirmed for all four.**
5. A second path / fixed before: no `agent-latency` class and no latency entry in `docs/failures.md`. The hooks are the only repository code on the tool path (`.claude/settings.json`; the teamwright 0.12.2 plugin ships no `hooks.json` and its `plugin.json` declares no hooks). Not a recurrence.

**Evidence.**
- Hook config (`.claude/settings.json`). PreToolUse on Bash runs `journal`, `analysis-gate`, `review-gate`, `verify-gate` and `test-guard`. PostToolUse runs `journal` (plus the three gates on Edit/Write). `defaultMode: auto` is set in `~/.claude/settings.json`.
- Hook timings: each hook run 3 times on a trivial `sed -n` payload, `bash scripts/hooks/<h>.sh < input`. Results: journal 0.12-0.15 s, analysis-gate 0.12-0.15 s, review-gate 0.18-0.27 s, verify-gate 0.13-0.21 s, test-guard 0.12-0.14 s. Claude Code runs matching hooks in parallel, so the PreToolUse cost is about 0.3 s. (After the first loop the state guard refused further hand-fed hook runs, so the write-style inputs were not timed.)
- Join of the transcript `tool_use`/`tool_result` timestamps with the journal `pre`/`post` (`tools.jsonl`) for every Bash call in both sessions (663 calls; ad-hoc script `/tmp/t162s/steps.py`, not kept):

  | cited call | total | tool_use->pre | pre->post | what the full command also ran |
  |---|---|---|---|---|
  | `sed -i '460{/^$/d}' …` | 127.8 s | <1 s | 127 s | `scripts/tw-run core -- cargo fmt --check && cargo clippy …; scripts/tw-run core -- cargo test -p voicen-core call::codec` |
  | `python3 -` edit | 75.1 s | <1 s | 75 s | a second python write, then `tw-run core -- … cargo test … sixty -- --nocapture` (result: "has been running for over 60 seconds") |
  | `cat >> mutants.py <<'PY'` | 93.7 s | -0.5 s | 94 s | `/tmp/t116-bite/run.sh` (mutant runs W0, W13, W20-W23, each a cargo test) |
  | `grep -n … \| head` | 54.3 s | <1 s | 54 s | `cat mod.rs; scripts/tw-run core -- cargo test -p voicen-core call::codec` |

  The journal `pre` lands within 1 s of `tool_use` every time, so the hooks start at once. `perms.jsonl` has no `PermissionRequest` for these calls.
- Calls with no build, test, wait or `find /` step (419 calls): `tool_use->tool_result` median 1.2 s, p90 3.8 s, p99 23 s. The p99 and the max of 61.7 s are `systemd-run … tw-test` runs the filter missed.
- Current host: 8 cores, load average 26.8, `/proc/pressure/cpu` some avg10 76%. The host is shared with other projects (elektrik-calc `tw-gate`, flutter, gradle, pytest, Playwright). Even so, this investigation's own trivial calls ran 1-2 s pre->post (journal agent `a7291d608e7cf3890`).
- Worst genuinely light calls: 13.9 s (`grep -n` on `diag_pipeline.rs`), 11.9 s and 10.7 s (`sed -n`), all at 2026-10-24 20:29-20:30. Five problem-investigators ran in parallel then, one of them a `find / -type d -name whisper-rs-sys…` (55 s), which is the likely source of the IO and CPU contention. Not proven per process; no per-process load record exists.
- `agent-tests.slice`: `systemctl show` gives CPUQuota 600% (a `set-property` drop-in in `/etc/systemd/system.control/` overrides the unit file's 500%), CPUWeight 50, IOWeight 50, MemoryHigh 14 GiB, MemoryMax 16 GiB. Only `systemd-run --slice` scopes and the docker containers live in it. Hooks, trivial commands and the Claude processes run outside it, so the slice does not throttle trivial calls. Its CPUWeight 50 de-prioritises builds against them.

**Root cause.** All four symptoms come from a measurement artefact: the session-review script showed only the head of each command (the Context's `…` and "No build ran" are exactly that), and every cited call chained a build or test run in the same Bash call. None of hooks, permission check or the runtime adds minutes; their measured share is about 1 s. No contradicting evidence. The one open item is the 10-14 s light calls, attributed to host contention by correlation only.

**Invariant / seam.** No repository defect, so no code seam. Rule for future timing reviews: attribute a duration to a call only by its full command text, and split a call into steps before calling it trivial.

**Approach.**
- (A, recommended) Close as a recorded finding (Acceptance option 2). Nothing changes in `scripts/hooks`, `scripts/ci` or `Makefile`, so `checker: false` stays. Acceptance 3 (a refusing hook still refuses) is met without any change. During this investigation the VERIFY GATE refused a shell command naming a verify-record write at 2026-10-24T20:39:16Z, logged in `.teamwright/logs/gates.jsonl`. Acceptance 4 is moot.
- (B) Also keep a timing-extraction script in the repo (`scripts/metrics/`) that prints full commands and the journal pre/post split, so the next review does not repeat the artefact. Risk: low. It is a new script, not a guard, and the kit owns `scripts/metrics`, so the change belongs upstream.
- (C) Cap host contention: `find /` and other host-wide scans would go through `systemd-run --slice=agent-tests.slice`, or another project's gates would move into its own slice. This is host and owner policy, not repository code.

**Side findings** (outside T-162's scope; separate tasks or kit issues):
1. `scripts/hooks/test-guard.sh` `PREFIX` holds `nice`, `ionice`, `timeout`, `env`, … but not `systemd-run`, and its options (`--scope -q --slice=…`) are not stripped. Read from source only, because the state guard forbids feeding the hook. The host-load memory rule asks for every heavy run to be wrapped in `systemd-run … --`, so `systemd-run … make -k check` or `… cargo test` bypasses the guard and the tw-gate/tw-test cache as a matter of course. The guard arrived with kit 0.12.0 (f1b1d0ce, 2026-10-24), after the T-116 runs, so it played no part in the cited latency. The fix is in a kit-owned hook (upstream teamwright). `scripts/hooks/` is not on the pre-commit guard-trigger path list (`scripts/ci/`, `scripts/licenses/`, `Makefile`, `*.mk`), so `checker: true` is not mechanically required. It is still a word-model guard under P-020, so the task should carry `decides_on` (token on the stripped prefix list).
2. The state guard let `for h in …; bash scripts/hooks/$h.sh < file` through on the first try, because the variable-expanded path was not resolved; later spellings were refused. As a result `journal.sh` appended 3 probe lines (session `t162-probe`, agent `t162probe`) to `.teamwright/logs/tools.jsonl`. They are harmless for metrics but not genuine runtime records. This is a kit guard gap.
3. Gate false positives that cost turns, not seconds. The state guard refused a read-only `grep -n "flock\|>>" scripts/hooks/journal.sh`, and the review gate refused a heredoc to `/tmp` whose text named the `.teamwright/logs` path.
4. `tools.jsonl` holds 2 interleaved lines (indices 23735, 23754, 2026-10-05), so concurrent journal appends are not atomic. They are old, and readers must skip bad lines.
