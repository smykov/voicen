## Context

Found by the T-030 analysis (decision #34). The `windows` job of `.github/workflows/ci.yml` has been red since T-003: runs 37147276182 (c0e2113) and 37151218166 (fcc04be). `cargo test --workspace` (ci.yml:57) stops at the voicen-core doctest `secrets.rs:16`, which fails to link on windows-latest (LNK2001 `mainCRTStartup`, `memcpy`, `__CxxFrameHandler3`). The last green run, 37044674209 (0e73b52), had no runnable doctest, so no doctest has ever linked on this runner; unit, integration and `voicen_lib` test binaries link fine. Because the job stops there, `pnpm tauri build`, the silent install and the smoke never run, so no `deploys: true` task can be verified (T-030 waits on this task). Investigator's candidate, unproven: `cargo test --workspace --all-targets` on Windows (skips doctests; they keep running on the Linux gate) — the analysis must find the cause before choosing it.

## Acceptance

- [ ] The `windows` job of the CI run for this task's commit is green end to end: tests, `pnpm tauri build`, silent install, launch and the commit check in the start log line
- [ ] Every voicen-core doctest still runs in some gate (the Linux gate at least) — none is silently dropped; if Windows skips doctests, that is written down with the reason in the docs the analysis names
- [ ] Failure branch: a doctest that fails (not one that fails to link) still turns a gate red
- [ ] Test that fails without the change: the CI run of the parent commit (red, run 37151218166) vs this task's run (green)

## Investigation

Investigator, 2026-10-03.

**Tools.** Serena indexes TypeScript only (decision #3), so I used grep and file reads for Rust and YAML. Library sources come from the exact locked versions in the core image's registry cache (`.teamwright/cache/core/_usr_local_cargo_registry/cache`): tauri-build 2.7.1, tauri-utils 2.10.1, tauri-winres 0.3.6 and embed-resource 3.0.11. Cargo source comes from the `rust-1.99.0` branch of rust-lang/cargo via `gh api`, the toolchain pinned at ci.yml:51. context7 was not used: the question is about cargo and tauri-build internals, and the pinned source is the primary record. The CI logs come from `gh run view --log-failed` / `--log`. I did not make a local Linux reproduction (a scratch two-crate workspace in the core image): the sandbox denied a direct `docker run`, and `tw-run` would have meant writing files into the repo. It is not needed, because the failing link line itself shows the mechanism (below).

**Frame.** Observed: on windows-latest, `cargo test --workspace` (ci.yml:57) builds everything. The voicen_lib, voicen-core unit and integration binaries link and pass. The `compile_fail,E0277` doctest (secrets.rs:6) passes because it fails at type-check, before any link. The runnable doctest secrets.rs:16 fails to link with LNK1120 (14 unresolved). Expected: it links and passes, as it does on the Linux gate. It reproduces in both runs since T-003 (37147276182 at c0e2113, 37151218166 at fcc04be). Green run 37044674209 had `Doc-tests voicen_core` -> `running 0 tests`, so no doctest has ever linked on MSVC in this workspace.

**Hypotheses.**

1. *A workspace build script poisons the doctest's library search path.* Confirmed (evidence below).
2. *The self dev-dependency (`voicen-core = { path = ".", features = ["test-fakes"] }`) makes rustdoc link two copies of voicen-core or the wrong rlib.* Refuted. The link line lists exactly one `libvoicen_core-3d37a2c2368bc49a` rlib. Two copies would give LNK2005 duplicates or missing *voicen-core* symbols. Every missing symbol here is a C runtime symbol referenced by std, alloc, core, panic_unwind and compiler_builtins.
3. *Toolchain or profile settings (`panic = "abort"`, `+crt-static`, RUSTFLAGS, `.cargo/config`, `rust-toolchain`).* Refuted. There is no `.cargo/` directory and no `rust-toolchain*` file. `[profile.release] panic = "abort"` does not apply to the `test` profile. The step's env has no RUSTFLAGS or RUSTDOCFLAGS (log: CARGO_HOME, CARGO_INCREMENTAL, CARGO_TERM_COLOR, CACHE_ON_FAILURE, VOICEN_COMMIT). The link line asks for `/defaultlib:msvcrt`, i.e. a dynamic CRT, which is normal for MSVC test builds.
4. *The same concern is handled on a second path.* Yes, and it explains the asymmetry. The shell's own targets (voicen_lib tests, the voicen bin, `pnpm tauri build`) get tauri's compensating `rustc-link-arg`s (`/NODEFAULTLIB:msvcrt.lib`, `/DEFAULTLIB:libcmt.lib`, `libvcruntime.lib`, `ucrt.lib`), so the stub never matters there. The voicen-core unit and integration binaries are built by rustc invocations that get only the search paths of their own dependency graph, which does not include `voicen`. Only doctests get the global set of search paths without the link-args.
5. *This class was fixed before.* No. `docs/failures.md` has only the placeholder row and no `ci-toolchain` class. `git log -- .github/workflows/ci.yml src-tauri/build.rs src-tauri/tauri.conf.json` shows 0afeaf3 (skeleton), ca9b61d (T-002, smoke paths) and 0324516 (T-027, registry cache), none about linking. No other task has `class: ci-toolchain`.

**Evidence (the mechanism, link by link).**

- *The stub.* src-tauri/build.rs calls `tauri_build::build()`. tauri-build-2.7.1 `src/lib.rs:914-915` calls `static_vcruntime::build()` on `msvc` when `should_static_link_vc_runtime` is true (`:938-950`: env `STATIC_VCRUNTIME`, else `WindowsAttributes::static_vc_runtime`, else `config.build.windows.static_vc_runtime`). tauri-utils-2.10.1 `src/config.rs:3910-3926` sets the default to `true`, and `src-tauri/tauri.conf.json` has no `build.windows`. `static_vcruntime.rs:29-57` writes a ~100-byte COFF object named `msvcrt.lib` into `OUT_DIR` and prints `cargo:rustc-link-search=native=<OUT_DIR>`. `:14-25` prints the `rustc-link-arg`s that make the shell's own links work anyway.
- *Cargo hands it to every doctest.* At cargo `rust-1.99.0`, `src/compiler/build_runner/mod.rs:301-312` inserts every build script's `library_paths` into `compilation.native_dirs`, one set for the whole invocation. `src/ops/cargo_test.rs:231-233` passes `-L <dir>` for each of them to every `rustdoc --test`. In contrast, `mod.rs:251-270` adds `-C link-arg=` only from the build scripts of the doctest's own package (`find_build_script_metadatas(unit)`).
- *What link.exe saw* (run 37151218166, `Doc-tests voicen_core`, secrets.rs line 16): `"/defaultlib:msvcrt"` ... `"/LIBPATH:...\atlmfc\lib\x64"`, `"/LIBPATH:...\windows_x86_64_msvc-0.52.6\lib"`, `"/LIBPATH:D:\a\voicen\voicen\target\debug\build\voicen-6de42dc96d3ba620\out"`, `"/LIBPATH:...\vswhom-sys-...\out"` and `"/LIBPATH:...\webview2-com-sys-...\out\x64"`. These are the search dirs of the tauri dependency graph, none of them a voicen-core dependency, and there is no `/NODEFAULTLIB` or `libcmt`. Then: `D:\a\voicen\voicen\target\debug\build\voicen-6de42dc96d3ba620\out\msvcrt.lib : warning LNK4003: invalid library format; library ignored`. `/LIBPATH` is searched before the `LIB` env dirs, so the stub shadows the real msvcrt.lib. Once it is ignored, no CRT import library is linked: LNK2001/LNK2019 for `mainCRTStartup`, `memcpy`, `memmove`, `memset`, `memcmp`, `strlen`, `wcslen`, `atexit`, `_tls_index`, `__chkstk`, `_fltused`, `__CxxFrameHandler3`, `_CxxThrowException` and `type_info` vftable (14 total). Every one of them comes from msvcrt, vcruntime or ucrt. Run 37147276182 has the identical LNK4003 line and LNK1120.
- *Why Linux passes.* `make check` runs `cargo test -p voicen-core` in the Linux image. There is no MSVC branch in tauri-build, and src-tauri is not even in the invocation.

**Root cause** (explains every symptom: only MSVC; only doctests; only voicen-core's doctests, while voicen_lib doctests would get the link-args; only since a runnable doctest exists; the compile_fail doctest unaffected): the stub `msvcrt.lib` that tauri-build's static VC runtime puts on the shell's link search path reaches voicen-core's doctest, because cargo shares all build scripts' search dirs with every doctest of the invocation but not the link-args that make the stub harmless. No diagnostic CI run is needed. If one were wanted, `cargo test -p voicen-core --doc -vv` alone would show the same rustdoc command without the voicen `/LIBPATH` and link green.

**Options.**

- **A (recommended): split the Windows test step by package.** ci.yml:57 becomes:
  ```yaml
  # The shell's build script (tauri-build static VC runtime) puts a stub msvcrt.lib on its
  # search path; cargo gives every build script's search dirs to every doctest of the same
  # invocation, so other crates' doctests must not share a run with `voicen` (T-033, F-001).
  - run: cargo test --workspace --exclude voicen
  - run: cargo test -p voicen
  ```
  It removes the cause: `voicen`'s build script does not run in the first invocation, so `native_dirs` holds only the voicen-core graph's dirs. That is the same set with which voicen-core's unit and integration binaries already link on this runner. The shell's own tests (and any future voicen_lib doctest) get tauri's link-args through `mod.rs:263-268`. Every doctest still runs, on both Linux and Windows, so nothing is dropped (Acceptance 2), and a failing doctest turns both the gate and the Windows step red (Acceptance 3). Red -> green: secrets.rs:16 on the windows job, red in 37151218166, green in this task's run. Risk: resolver-2 feature sets may differ between the two invocations, so shared deps such as serde may compile twice (build time only). A future crate whose build script uses the same trick must also be tested alone (the comment and the invariant name this). Rollback: revert the one-line change.
- **B (workaround): `cargo test --workspace --all-targets` on Windows.** This was the T-030 candidate. It runs no doctests on Windows, so the symptom goes away but the cause stays, and any future doctest only runs on Linux. It needs a written exception (Acceptance 2). It also skips a voicen_lib doctest, which would link fine. Not recommended: A costs the same and keeps coverage.
- **C (workaround): `RUSTDOCFLAGS=-Ctarget-feature=+crt-static` for the Windows test step.** The doctest then asks for libcmt instead of msvcrt, so the stub is never looked up. It is plausible but unproven without a Windows run, and it links doctests against a different CRT than the test binaries. It hides the shared search path instead of removing it. Not recommended.
- Rejected: `build.windows.staticVCRuntime: false` in tauri.conf.json. It removes the stub, but it changes the shipped binary: `voicen.exe` would need the VC++ redistributable on the user's PC. That is a product and installer decision outside this task, and it would mean an owner decision and a decisions.md row.
