## Notes

- **Cause of the step-12 failure (read from the log and the pinned sources, not fixed):** `tauri-plugin-single-instance` 2.5.2 (`src/platform_impl/windows.rs:66-67`, `:203-232`, in `.teamwright/cache`) creates a top-level, unowned message window of class `<identifier>-sic`, title `<identifier>-siw`, with `WS_EX_NOACTIVATE | WS_EX_TRANSPARENT | WS_EX_LAYERED | WS_EX_TOOLWINDOW`, then sets `WS_VISIBLE | WS_POPUP`: the same shape as tao's event-target window. Before T-057 the predicate skipped every `WS_EX_TOOLWINDOW` window, so this window never counted. T-057 (commit `1545ecf`) removed that exclusion and kept only the class `Tao Thread Event Target` (`scripts/ci/visible-windows.ps1` header and `Shown()`, `docs/decisions/overlay.md` §5). Its premise "that one window exists in every tauri process … no exception other than tao's own window" is false since T-052 added the single-instance plugin. This run is the first in which T-057's predicate ran against the installed app (earlier runs stopped at step 10), so the defect was not visible before.
- What it means for T-057's smoke predicate: the predicate is not flaky, it is wrong for this app. It counts an invisible (layered, transparent) helper window as "shown". As it stands, the first-launch step fails always, and the Loaded-launch step (expects zero shown windows) would fail always. `smoke_predicate.rs` cannot catch this: it only builds EDIT windows in its own exe, not a tauri process with the plugin. This is the same shape as T-037's review round 1 (a framework's `WS_VISIBLE` helper window counted by the predicate). For the investigator: decision §5's "Don't" forbids an exception by class or title for *our overlay*; whether a raw-fact rule (for example `WS_EX_LAYERED | WS_EX_TRANSPARENT`, or zero size) or a second class exclusion is right is an analysis/owner question, not decided here.
