## Context

Split out of the T-086 audit (decision #124). Two guards share the same YAML skeleton: indent and step tracking, a scalar reader and a comment cutter. Both leak.
- `scripts/ci/ci-wip.sh`: the workflow runs on `main` and `wip/**`, and no step saves a cache off `main`.
- `scripts/ci/setup-node-cache.sh`: no setup-node step needs host pnpm.

The probes, all of which PyYAML reads as the violating step:
- W1: a flow-mapping step `- {name: "cache #1", uses: actions/cache@v4, ...}`.
- W2: an explicit key `? uses` / `: actions/cache@v4`.
- S1: `"cache": pnpm`.
- S2: `? cache` / `: pnpm`.

release-guard R7 already pins the trigger inside `scripts/ci/release-header.yml`. ci-wip's setup-node clause is stricter than setup-node-cache's. The proposal:
- the trigger is asserted as lines of the owned header literal;
- the raw tokens `uses`, `actions/cache`, `setup-node`, `rust-cache`, `cache/save` and `pnpm/action-setup` occur only on owned lines or blocks;
- an unlisted action stays refused.

## Acceptance

- [ ] One guard, or two that share no grammar reader, decides only on owned literals and raw tokens. It keeps no YAML key, scalar or comment reader, and its `decides_on` is named.
- [ ] Failure branch: W1, W2, S1 and S2 are refused, and each fixture is red against the old guards. The existing ci-wip and setup-node-cache guarantees still hold: a cache saved off `main`, a trigger change, setup-node with pnpm cache, an unlisted action.
- [ ] `docs/decisions/ci-toolchain.md` (the guard table from T-086) is updated. `make check` is green.

### 2. Root cause and class

Both guards are the T-086 shape: the pass comes from their reading of YAML finding nothing. ci-wip's `key()`/`val()` read only `key:` lines at the step's key indent. Its backstop counts raw `uses:` lines, but only after the shared comment cutter `sub(/[ \t]#.*$/, "", t)` removes W1's ` #1", uses: …` tail, so the count matches. ### 3. Where the rule belongs: release-guard.sh

- **Premises are already there.** A raw `uses` or `setup-node` is only a P-020 token if YAML cannot spell it another way. In release-guard that is R6 (no `\x`/`\u`/`\0` escape, no backslash before a line break) and R8 (no `!!`, `!<`, `%TAG`). Quoted, folded or block-scalar keys still hold the word on a line (`? |-` / `  uses` puts `uses` on its own line). A separate script would rest on another script's rules or copy them, which is the reason T-087 rejected its option B.
- **The trigger is already a literal there.** R7 pins `release-header.yml`, which holds `push: branches: [main, "wip/**"]`, but only in a file holding `  release:` (W4). Widen it to "ci.yml and any file with `  release:`". W3 needs R12. That rule also closes release-guard's own Not caught entry ("a column-0 key such as `env:` put between two jobs"). Both counts were checked: the real ci.yml has no column-0 line after `jobs:`, and no ok-* fixture does.
- **Scope gets wider, not narrower.** release-guard reads every regular file in the dir; the old guards read `*.yml`/`*.yaml` only.
- **Fixture cost is small.** The 149 release-guard fixtures use only checkout, upload-artifact and download-artifact lines, all owned. Two v-* fixtures (`Actions/Upload-Artifact`, `softprops/action-gh-release`) already exit 1 and gain an R11 line. All three ok-* headers equal `release-header.yml`.
- **Cost:** release-guard.sh grows by about 60 lines and three rules, and its name now undersells it. Renaming is optional and out of scope: it touches CLAUDE.md, Makefile and the docs.

### 4. Design notes for the developer

- **The load-bearing token is the word `uses`.** Every action run, reusable-workflow call and local action is a `uses` key, and every owned line carries its full action reference. A value continued on the next line makes an invalid reference, which fails loudly. The five name tokens are the decisions #124 belt: they cost only rewording the comments that name them.
- **Fragment end.** A fragment must end on a line that closes the step: the next `      - ` line or a job key. A comment line does not close it (PyYAML probe: an `if:` after a comment line joins the step above). The pnpm-save step is followed by the T-077 comment block, so either move that block below the next step's name line (as T-087 moved the T-026 block) or let the fragment run through it.
- **Place of a fragment is not pinned, on purpose.** Each fragment is self-contained (option (a): `package-manager-cache: false`, no `cache:`; save `if:` / `save-if:` on main). A copy inside a block scalar does not run, and a copy in another job or an alias of a whole job behaves the same. So R10's leading-space walk is not needed. This holds only while no merge key exists, hence R13 (M2).
- **What gets narrower.** setup-node-cache's options (b) `cache: npm` and (c) pnpm/action-setup earlier in the job no longer pass unless they are written into an owned fragment. Neither is in use, and a change to one is a reviewed edit of the owned copy and ci.yml together.
- **Literal checks on the guard's own copies** keep the retired guards' meaning when someone edits the owned copy (see `seam`). They read only owned text, so they are not foreign-grammar readers.

### 5. Not caught (carried over or new)

Carried over from ci-wip:
- a cache written by a run step (`docker buildx --cache-to type=gha`, a script calling the cache service);
- an `if:` that is always false on main.

New:
- an action input supplied through the environment: a job or workflow `env: INPUT_CACHE: pnpm`, or a run step writing it to `GITHUB_ENV`. The runner's input passing was not read, so this is unverified. A raw `input_` token would close only the literal `env:` case, because bash can re-spell the `GITHUB_ENV` write (T-086 L1).
- a YAML parser beyond 1.1/1.2.

Whether GitHub honours merge keys at all was not checked (no docs tool). R13 is fail-closed either way, and ci.yml has no merge key. T-060 r2#5 (a bare block-scalar indicator under `steps:` turns the steps into a string) applies here too. It is loud: the workflow is invalid and nothing runs.
