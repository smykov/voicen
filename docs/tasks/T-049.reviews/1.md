## Verdict rationale

The code is right and does what the analysis said. It sits in the named seam: `build.rs` `try_build` + `AppManifest::commands(&APP_COMMANDS)`, both capability files, and `.gitignore`. It keeps the invariant: 10 grants to `settings`, `overlay_ready` only to `overlay`, no `deny-*`, no wildcard, no `remote`. The UI calls the same command set: grep over `src/**` finds 9 settings-page invokes plus `get_build_info` from `About.svelte`, and `overlay_ready` from `overlayApi.ts`. The tests bite and ran on Windows. T4 is a real fail-closed probe on the release context, and T2-effect checks state (service snapshot and `settings.json` bytes), not text.

On the developer's notes:
- `APP_COMMANDS` repeating the `generate_handler!` list is a P-010 duplication that tauri-build's `&'static` API forces (the build script runs before the crate). It is acceptable because two things tie the lists together: `make check-app-acl` checks set equality mechanically, and tauri refuses at runtime whatever the list misses (fail-closed).
- Updating spec 001 `contracts/ipc.md` (`overlay_ready`) is in scope and correct: that contract describes the command, and P-018 asks for exactly this.
- No line-number citations in the docs this diff changed; the task record's Investigation cites vendored source lines, which is outside P-018's docs scope.
