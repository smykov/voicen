## Context

US5 (recover from a failed final pass), US5 #1–#7. Spec FR-027, FR-028, FR-037 (cancel). Area core, seam the queue part of `crates/voicen-core/src/call/final_pass.rs`. Needs the pass (T-138) and recovery (T-144).

## Acceptance

- [ ] Passes run one at a time, FIFO; a call stopped during another's pass is Queued and starts after it (T062, T063)
- [ ] Recording is allowed during a pass (T062)
- [ ] "Transcribe again" on a `failed` call redoes only the failed track; on a `ready` call it clears and redoes both; speaker names are kept (T062)
- [ ] Failure branch: a 401 gives `failed: key`; after the key is fixed a retry succeeds (T062)
- [ ] Deleting a transcribing call cancels the pass first (cancel token) (T062)
- [ ] Exit or crash during a pass restarts it at the next start (T062)
- [ ] Failure branch: `transcribe` on a `recording` call is refused as `recordingCall` (T062)
- [ ] Test that fails without the change: the queue tests of `call/final_pass.rs`

## Investigation

**Frame.** Feature, not a defect. Expected (spec 007 FR-027, FR-028, FR-037; data-model "CallState transitions", "FinalPass and the queue"; tasks.md G32 T062/T063): passes one at a time from a FIFO, "Transcribe again" redoes only the failed track (failed) or both (ready) keeping speaker names, cancel before delete, restart after exit or crash, `recordingCall` refusal. Observed: only the single pass of T-138 exists.

**How I looked.** Serena `get_symbols_overview` and `find_symbol` on `call/final_pass.rs` (`run_pass`, `run_pass_with`, `pass`, `PassDeps`, `PassCall`, `PassOutcome`, `Run`, `Lane`, `write_ready`); `find_referencing_symbols` on `run_pass` returned nothing although `tests/final_pass_http.rs` and `examples/wer.rs` call it (index misses tests/examples), so callers were found with grep: no shell or core caller outside tests and the WER example. Grep for `cancel|TrackSet|PassQueue|enqueue|RecordingCall` over `crates/voicen-core/src/call/` (only the `CallErrorCode::RecordingCall` variant). Read `storage.rs` (`CallStore::recover`, `read_meta`, `TrackResult`, `CallErrorCode`), `transcript.rs::merge`, `session.rs` stop path, `docs/decisions/call-final-pass.md`, contracts `core-call.md` and `ipc.md`.

**Dependencies.** T-138 DONE (pass runner); T-144 CODE_COMPLETE (`recover`, `release`), enough under `process.ready.after: code_complete`. Not blocked. T-139 (shell pass worker) is TODO but not needed: this task is core only and tested with fakes.

**Size verdict.** One area (core), one seam: the queue in `call/final_pass.rs` with two small extensions of the same pass (track mask, cancel token) and one meta transition function using `storage::write_meta` (plus, for Q2, reuse of `recover`'s per-folder step, which means extracting it in `storage.rs`). Medium-large but not a spec-sized split: the shell plumbing is already its own tasks (T-139 stop wiring, T-147 `calls_transcribe` and start-up restart, T-152 delete, T-148 UI). If the reviewer wants it smaller, split off the transcribe transition and `recordingCall` refusal (storage side, Q2-Q4) from the queue, mask and cancel (final_pass side).

**Unsettled by the spec, decided at developer level (see `analysis.decides_on`, to be recorded in `docs/decisions/call-final-pass.md`).** Q1 cancelled-pass outcome and log literal (contract `core-call.md` lists only `ready|failed`); Q2 a released `recording` call (write failure this session, listed Recovered with Transcribe offered by T-148) — recommended: recover in place and queue, because refusing would show `recordingCall` on a row the UI calls Recovered; Q3 dedup; Q4 `ioFailed` on `calls_transcribe` (ipc.md lists only `recordingCall`, `notFound`); Q5 engine ref and mode of a one-track redo. None is a product decision needing the owner: each picks between behaviours the spec leaves open without changing what the user is promised. If the reviewer reads Q2 as product behaviour, it becomes an OQ for the owner; recommended option as above.

**Risks for later tasks (not this one).** The pass writes the `meta.json` it read at its start, so a speaker or title rename during `transcribing` would be overwritten at the end (T-152 must route renames through the queue or re-read before the final write). Cancel waits for in-flight HTTP up to the FR-24 transcription timeout (`thread::scope` joins workers); T-152 should call it off the IPC thread.
