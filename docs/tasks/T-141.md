## Investigation

**How context was gathered.** Serena: `get_symbols_overview` on `call/storage.rs` and `call/transcript.rs`, `find_symbol SyncWrite`. Plain reads (sed and grep) of `call/events.rs` (`CallState`, `FailReason`, `CallId` grammar), `settings/roots.rs` (`effective_root`, `reason_of`, `UnwritableReason`), `settings/file.rs::write_tmp_and_rename`, `overlay.rs` (the fixture-pin test), spec 007 (`tasks.md#g27`, `contracts/ipc.md`, `contracts/core-call.md`, `research.md` R18, spec FR-033/034/035/036), `docs/decisions/call-storage.md`, `docs/decisions/ipc-acl.md`, `src-tauri/capabilities/`, the T-125 and T-123 records and the T-197 follow-ups. Context7 `/websites/doc_rust-lang_stable_std` › `fs::rename`: it replaces an existing `to`. On Windows it is `MoveFileExW` with a fallback to `SetFileInformationByHandle`; from 1607 it behaves as on Unix where `FileRenameInfoEx` is supported, and `to` must not be a directory. These are the stable docs, not docs pinned to 1.99; the rename contract has not changed. No new crate.

**Frame.** This is a feature. Expected: core turns the store's list and a call's files into the contracts/ipc.md wire, refuses any `{root, id}` it did not hand out without touching the disk, and writes an export with no partial file. Observed: none of this exists. `CallStore::list` returns `PathBuf`s and the snake_case file enums; there is no `get`, no guard and no export.

**Hypotheses.**
1. *Nothing exists yet*: confirmed. Grep for `CallSummary|CallDetail|calls-wire|resolve_call|export` in `crates/` and `src-tauri/src` finds no code; `e2e/fixtures/` has no `calls-wire.json`.
2. *The same concern already has a path elsewhere (a second path)*: confirmed. Each of these must be reused, not copied:
   - Current root: `settings::roots::effective_root`.
   - Id grammar: `CallId::parse`.
   - Reading a call folder: the private `load_entry`/`read_meta` in storage.rs. `get` must call them, so a call that lists as damaged cannot open as fine.
   - Markdown: `render_markdown`; copy (T-142) and export share one bytes function.
   - io kind → reason: `settings::roots::reason_of`.
   - tmp+sync+rename: `write_atomic`.
   - Fixture pin: the overlay, settings and local-models wire tests.
3. *This class was fixed before*: no call-side history (docs/failures.md has no call-storage entry). The nearest precedents are `settings/file.rs` (a `create_new` reservation so a backup is never overwritten, plus tmp+rename) and T-125's `create_dir` instead of `create_dir_all`. Both point the same way: never open a name we did not create.
4. *Export can reuse `write_atomic` unchanged*: refuted for a user folder. `write_atomic` opens `<name>.tmp` with `File::create`. In the user's chosen folder that truncates a user file named, say, `notes.md.tmp`, then renames it over the target or removes it on failure. In the call folder this is right: the tmp is ours, and a stale `meta.json.tmp` left by a crash must be replaced, or every later `write_meta` fails. So the two callers need different tmp *openers* and the same *tail*. Hence the internal split in option A.
5. *A wire guard needs a filesystem check (canonicalize, starts_with)*: refuted. The roots are a closed list in `CallSettings`. Exact equality of the opaque string against `wire_root` of each list member, plus `CallId::parse` (no separator, no `..`), is enough and touches no file. Canonicalize would be an fs access the acceptance forbids.

**T-197 and `write_atomic`.** Export reuses `write_atomic`'s tail. It does not call `write_atomic` itself, for the reason in hypothesis 4. The developer splits `write_atomic` into tmp open + `fill_and_rename(file, tmp, target, bytes)` (private). `write_atomic` keeps its signature and behaviour, and T-138 still calls it for `transcript.*`. `export_to` opens its tmp with `create_new` and calls the same tail. So there is still one tmp+sync+rename tail on the call side. The settings helper (`FsSettingsFile::write_tmp_and_rename`) stays as it is: merging it is T-197's line T-125 r2#2, out of this seam. Add a note to that line: the call-side tail is now `storage::fill_and_rename`, and the merge should route settings through it. As a side effect the split makes the tmp write/sync failure branch testable with a fault writer, which T-125 could not run (T-125 mutant table, "not runnable locally").

**Wire details pinned here** (developer-level; written into contracts/ipc.md in the same commit; the owner may override them, none is blocking):
- **D1 Damaged summary.** `CallSummary` requires `title` and `startedAt`, but a damaged entry has no meta. Use the same default title a new call gets (`calls.title_default` from the stamp, UI language), `startedAt` = the stamp as local `YYYY-MM-DDTHH:MM:SS` with no offset, and `durationMs: null`. So `CallStore` wire builders take `UiLanguage`.
- **D2 `calls_get` on a damaged call** gives `ioFailed`; a folder that is gone gives `notFound`. The UI offers only Open folder and Delete for damaged rows.
- **D3 Detail lines.** No `transcript.json` gives `lines: []` (recording, queued, failed). One that is present but unparsable or fails `validate` gives `ioFailed`: showing it as empty would hide a broken transcript. Line `speaker`, `track` and `lang` are copied from the validated `SegmentV1`. `speakers` come from meta.json, the source of names (FR-035).
- **D4 `ioFailed.reason`** is the existing `UnwritableReason` snake_case word through `reason_of` (`missing`, `not_a_folder`, `access_denied`, `disk_full`, `other`; `relative` cannot come from an io error). This is the vocabulary `FieldError.reason` already uses (#196), and it avoids a second serialization of one enum. The camelCase rule covers field names and the listed `code`/`state`/`failReason` values. The UI text of each reason is T-143/T-128's job (no catalog ids exist for these reasons yet; grep of `i18n/en.json`).
- **Export without a transcript** (not `ready`) gives `ioFailed{reason: missing}`. The `{saved}` result and the save dialog are the shell's (T-142). Core takes the full `target` path from the dialog. A target with no parent or no file name gives `ioFailed{other}`. A target that is a directory fails at rename and gives `ioFailed`, leaving no tmp.
- **`wire_root`** is the path's UTF-8 text. A root that is not valid Unicode (possible on Windows) gets a lossy string that no wire value can match, so such a root lists but cannot be opened. That is accepted and noted in the decision record.

**Test notes.**
- The gate runs core tests in Docker as the caller's uid; it is root on this host (`id -u` = 0), so `chmod` read-only does not bite (the same limit T-125 hit). The "read-only target" acceptance is proved three ways:
  - (i) real-fs faults that root cannot bypass: a missing target folder gives `missing`; a target whose parent is a file gives `not_a_folder`;
  - (ii) the tail run over a fault writer that fails exactly one call (write or sync, `PermissionDenied`), asserting no tmp and no target left and `reason: access_denied` (F-024);

- "No filesystem access" for the guard: `resolve_call` takes no `CallStore` and no fs handle (pure signature). The test hands it a root that is a real folder holding a valid planted call, which is not in settings, and expects `notFound`.
- The fixture test sits in storage.rs `mod tests`, like `overlay::tests::e2e_overlay_wire_fixture_matches_core`. Its `_format` key names the builders and says "never edit by hand".
