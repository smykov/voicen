## Context

Owner, 2026-10-07: long dictations and the internal Whisper server need configurable limits. Decision #97 changes FR-24 from fixed timeouts to settings whose defaults are today's values: connect 5 s, transcription via API 30 s, via local server 60 s, post-processing 15 s, built-in engine 120 s. `docs/requirements.md` FR-24 is updated in the same task.

## Acceptance

- [ ] The settings hold the timeouts with the FR-24 defaults. They are validated within sane bounds (the analysis proposes the bounds), editable in the settings window (en/ru), and applied to the next job without a restart (P-013).
- [ ] Failure branch: an out-of-range value is refused on save with a field error, and nothing is saved; a job that exceeds the configured timeout fails with `failure=timeout` as today.
- [ ] `docs/requirements.md` FR-24 and the spec contracts are updated.
- [ ] Test that fails without the change: named in `## Tests`.

## Investigation

Investigator, 2026-10-08, at 7ffc3fd. Serena tools were not exposed in this session; context was gathered with grep and file reads over `crates/voicen-core/src`, `src-tauri/src`, `src/`, `e2e/`, `specs/`, `docs/`. No library API is newly used (reqwest `connect_timeout`/`timeout` stay as called today), so no docs lookup was needed.

**Frame.** Feature, not a defect. Today the durations are fixed (FR-24); decision #97 makes them settings with the FR-24 values as defaults. Expected: the user edits five limits in the settings window, out-of-range values are refused on save with a field error, and the next dictation uses the saved values without a restart.

**Where each timeout lives today.**

| Role | Value | Defined | Read by (runtime) |
|---|---|---|---|
| connect | 5 s | `timeouts::Timeouts::default` | `engine::openai::OpenAiCompatibleEngine::send` (`Client::builder().connect_timeout`); `local_models::download` (`Downloader`, constructed once in `src-tauri` `release_parts` with `Timeouts::default()`) |
| API transcription | 30 s | same | `OpenAiCompatibleEngine::send`, `Endpoint::Api` (per-request `.timeout`, connect to last body byte) |
| local server | 60 s | same | `OpenAiCompatibleEngine::send`, `Endpoint::LocalServer` |
| post-processing | 15 s | same | nobody yet: `post_process::PassThrough` ignores it; T-020 (ANALYSIS) widens the port to `PostProcessInput { …, timeouts }` |
| built-in | 120 s | same | nobody yet: the built-in engine is T-017 (TODO) |
| download no-data | 30 s | same | `Downloader` (per read). Not in FR-24's user list or decision #97: stays fixed |

The pipeline is the single funnel for dictation: `Pipeline::build` stores one `Timeouts` (always `Timeouts::default()` via `Pipeline::new`; `with_timeouts` is `cfg(test | test-fakes)`), and `Pipeline::process` copies it into each `TranscribeRequest`. Engines store no duration (timeouts.rs module doc, architecture.md "timeouts" row). The settings snapshot each job uses is taken at press (`PressContext.settings`, docs/decisions/dictation-session.md), so a value derived from the job's snapshot is applied to the next recording after a save with no restart, and never to a running one (Clarification 4).

**Hypotheses checked.** (1) A second path that applies timeouts outside the pipeline: yes, the model `Downloader` (connect, no-data), built once at startup; see Q1. Test connection (T-013, TODO) will be a third reader and must take the form's values. (2) Earlier fixes in this class: none; `class: settings-timeouts` is new; `docs/failures.md` has no P-013 entry for timeouts. The relevant past rule is the settings invariant "Defaults come from one function" (docs/decisions/settings.md): `Timeouts::default()` would become a second source of the FR-24 numbers unless both read one table. (3) Out-of-range values bypassing save: yes, through a hand-edited file. Load does not validate (`SettingsService` only normalizes on save), so `history.size: 0` loads today; a `connect_s: 0` would make reqwest fail every request at once. Hence the clamp in the conversion.

**Settings schema (proposal).**

```json
"timeouts": { "connect_s": 5, "api_transcription_s": 30, "local_server_s": 60, "post_processing_s": 15, "builtin_local_s": 120 }
```

- `TimeoutSettings` (u32 whole seconds) in `settings/mod.rs`, with a container-level `#[serde(default = "default_timeouts")]` returning `defaults(None).timeouts` (the settings invariant; no field-level default).
- `schema_version` stays 1. No migration step: research R-2 says missing fields take their defaults, and an older app ignores unknown fields. A wrong type (`"5"`) makes the whole file unreadable (Reset with a backup), which is the existing R-2 rule for every field. It is not changed here.
- Bounds (one table in `timeouts.rs`: default / min / max per role; `defaults`, `validate` and `from_settings` all read it):

| Field | Default | Min | Max | Why |
|---|---|---|---|---|
| `connect_s` | 5 | 1 | 60 | Under 1 s a TLS handshake on a slow link fails. A connect over a minute means a dead host, not a slow one |
| `api_transcription_s` | 30 | 5 | 600 | The longest recording is 10 min (FR-03): about 19 MB WAV, about 150 s upload at 1 Mbit/s, plus the server's time |
| `local_server_s` | 60 | 5 | 1800 | CPU Whisper servers on 10 min of audio can run slower than real time (the owner's case) |
| `post_processing_s` | 15 | 5 | 300 | A slow local LLM rewriting about 1500 words. A failure only falls back to the raw text, so a long limit only delays |
| `builtin_local_s` | 120 | 10 | 1800 | The same reasoning as for the local server. Large models on CPU |

  No cross-field rule (connect ≤ total): reqwest's total deadline still bounds a long connect.
- `FieldId`: `TimeoutsConnect` `timeouts.connect`, `TimeoutsApiTranscription` `timeouts.api_transcription`, `TimeoutsLocalServer` `timeouts.local_server`, `TimeoutsPostProcessing` `timeouts.post_processing`, `TimeoutsBuiltinLocal` `timeouts.builtin_local`. Update `FieldId::ALL` (21 → 26) and the tests' `expected_field_id`, and add a `settings.field_label.<id>` per id (rule L, `i18n::tests::every_field_id_has_label_text`).
- `ErrorCode::TimeoutRange` `timeout.range` → `error.timeout.range` ("Enter a whole number of seconds within the range shown." / "Введите целое число секунд в указанном диапазоне."). `FieldError` has no params, so each field's range is shown in a static hint under the control (`fields.ts::hintId`, the T-072 pattern), e.g. "1–60 s, default 5" / "1–60 с, по умолчанию 5". The alternative is five codes (`timeout.connect_range` …), which would mirror `history.size_range` with numbers in the message. Recommended: the one code plus hints. It needs fewer catalog ids and the user sees the range before the error. A core test should check that each hint's numbers equal the table, so the hint and the table cannot drift.
- Validation: all five fields, on every save, whatever engine is selected (like `history.size`). The group is always visible, so an error is always reachable on a control. The save path needs no change: `SettingsService::save` step 3 `validate` runs before the hotkey, autostart, key and file steps, so a refused save writes nothing (this is already pinned for other codes, and T-073 adds one test for `timeout.range`).

**Applying without a restart (P-013).** `Pipeline::process` builds `TranscribeRequest.timeouts` from `Timeouts::from_settings(&job.settings.timeouts)`. The struct field becomes `Option<Timeouts>`, set only by `with_timeouts` (test-only, so the existing millisecond tests in `tests/api_pipeline.rs`, `tests/local_server.rs`, `tests/diag_pipeline.rs`, `tests/openai_client.rs` keep working). `production_constructor_uses_default_timeouts` changes to "the production constructor uses the snapshot's values". The P-013 proof covers the runtime reader through the real loader path: a snapshot with a non-default value reaches the engine request, and a real HTTP job through `Pipeline::new` times out at the configured value. `docs/architecture.md`'s timeouts row ("`Pipeline::new` always uses the defaults") must change in the same commit.

**UI.** The tabs today are Engine, Recording, Output, History and General (the post-processing tab is T-021, not built yet). Recommendation (Q2): a "Timeouts" group at the bottom of the General tab, all five fields always shown, each a whole-number input reusing `History.svelte`'s entry rule (non-whole or empty entry → 0 on the wire, so core refuses with `timeout.range`; the range is core's rule only), with `data-field=<FieldId>`, a label, the range hint and `FieldMessage`. Labels en/ru: Connect timeout / Таймаут подключения; Transcription via API / Распознавание через API; Local server / Локальный сервер; Post-processing / Постобработка; Built-in engine / Встроенный движок; group heading "Timeouts (seconds)" / "Таймауты (секунды)". The e2e pattern follows `e2e/settings-engine-url.spec.ts`: import `test`/`expect` from `./support/boot`, use `installTauriMock` with `firstRunView` from the core-checked `e2e/fixtures/settings-wire.json`, `queueSaveOutcome` for the scripted Refused, `calls` for the recorded `settings_save` request, and literal en/ru strings asserted from `i18n/*.json`.
