## Context

T-192 review 1, finding 3. A stage session started by `scripts/tw-launch` can push `wip/<ID>`, but cannot read the run (the kit's deny on `Bash(gh:*)`, kept by #219). Nothing makes it stop after the push: each stage session repeats "CI unread" and commits a note until the loop ends. On 2026-10-31 T-102 ended `outcome: limit` at 12 stages and T-122 ended `stuck`.

**Owner's answer (decisions #228, 2026-11-01): (a).** Allow `gh run list` and `gh run view` for stage sessions: read-only, and the session finishes its own stage. Every other `gh` command stays denied.

## Acceptance

- [ ] After its `wip/<ID>` push a worktree task spends no further stage session until the run's result is available to it
- [ ] The result reaches the task's `## Tests` as `CI: <run> @ <sha>` by the path the owner chose
- [ ] Failure branch: a red run returns the task to its stage with the failed job named, not to a repeated wait

## Investigation

**Frame.** Observed: after `scripts/tw-wip-push`, each stage session tries `gh run list`, gets refused, commits a Notes entry ("CI unread", owner question) and stops; the loop starts the same stage again. Expected (#228): the session reads its own run with `gh run list` / `gh run view` only and finishes its stage. Reproduces in every worktree launched through `scripts/tw-launch` (T-102, T-111, T-122, T-156).

**Hypotheses.**
1. *The gh deny alone blocks the read* (confirmed): `scripts/tw-launch --print-args` shows `--disallowedTools '... Bash(gh:*)'`; T-156.log shows about 25 refusals of `gh run list`, alone and in compound commands. The sessions did not use `gh api` or `curl`, which would have bypassed the refusal.
2. *The loop has no "waiting for CI" state* (confirmed, a contributing cause): kit 0.15.0 `tw-parallel.py::run` decides `moved` by HEAD or status change. A Notes commit counts as progress, so only `limit` (12) or two empty stages (`stuck`) end the loop. This is kit-owned and the owner did not choose this path (#228 option b). With option a, a session that waits for the result inside its stage never produces the empty-commit loop.
3. *An allow rule could add `gh run list/view` next to the kit deny* (refuted): Claude Code evaluates deny, then ask, then allow, and the first match decides; "an allow rule can't carve an exception out of a deny rule" (context7 `/websites/code_claude`, permissions page). Removing `Bash(gh:*)` instead opens all of gh, because `--allowedTools` allows `Bash` for every command.
4. *A second path* (checked): the kit's `skills/red-tests` step 4 orders `gh run watch` (no gh → ask the owner) under the kit's own gh deny, and `skills/implement` step 3 confirms green by the same run. The review stage also needs the `CI:` line (T-122 was stuck in review). So one reader has to serve every stage. The main-tree orchestrator's plain `gh` is not affected.
5. *Fixed before* (a gap carried over, not a fix): T-111 asked the owner the same question. T-192's `analysis.seam` included a run read that was then dropped (review 1 #3). The orchestrator wrote the `CI:` line by hand for T-111 (5df7cfd4) and T-156. None of these changed the launch, so the loop came back each time.

**Why a program and not a permission rule.** #228 says only `gh run list` and `gh run view`, and every other gh command stays denied. As platform rules this cannot be stated: the deny must stay for "every other", and while it stays it also refuses the two allowed commands. A program the session runs by name is not matched by `Bash(gh:*)`, because the rule sees the command text and not the script's body (same mechanism as `scripts/tw-wip-push` under the push denies, #219). The program owns the gh argv, so the "two commands only" rule is a literal the program holds, not a list of denies. This matches the owner's choice. It is implemented through `scripts/tw-launch` (the prompt sentence) plus one new script, so the orchestrator should confirm the form with the owner (see below).

**Wait.** The 8 latest `ci.yml` runs took 33 to 41 min. Background tasks are disabled in these sessions (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`), and a foreground Bash call is cut at 10 min. So `tw-wip-run` waits at most about 9 min per call and returns "pending" with its own exit code; the prompt sentence tells the session to call it again in the same stage. The developer fixes the overall ceiling (for example 90 min); past it the session escalates, naming the run. If the push changed only `docs/tasks/**`, no run starts (`paths-ignore`, T-083). The reader reports "no run for <sha>" as a separate result, so the session does not wait forever.

**Red run.** `gh run view <id> --json jobs` gives the failed jobs (and steps). The reader prints them, and the session keeps the task in its stage with the job named. In red-tests, an expected red is the stage's evidence, not a failure; the session judges which case it has.

**Not changed.** Kit code (`tw-parallel.py`, skills) is not changed. Kit feedback: red-tests orders `gh run watch` under the kit's own gh deny. Also, finding 3 asks to correct T-192's "A stage session that has pushed stops" sentence. T-192 is DEFERRED (absorbed by T-198), so the orchestrator should place that correction in T-198 or here.

**Owner question (for the orchestrator).** Does #228 cover this form: the two read commands run only by `scripts/tw-wip-run`, with `Bash(gh:*)` kept denied, rather than a raw `gh run list/view` in the session? Recommended: yes. The raw form either cannot pass the deny or needs an open deny list (option B).

The state files of T-102 and T-122 were overwritten by later runs, so their stage counts come from T-192 review 1 #3. Serena was not used: the seam is Python and shell scripts, read directly.
