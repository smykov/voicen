### Notes items

- **Dead worker, unwind builds (T-051 r1 #2).** Confirmed by reading:
  - `run_worker` has no guard around `pipeline.run_job(job)`. A panic ends the thread and drops `jobs`, the receiver.
  - `stop_recording` then queues with `let _ = queue.send(job)`, so the `Err` is dropped.
  - The controller has already counted the job in `queued`, so the overlay stays `Processing` and nothing is logged.
  - The session lock is poison-tolerant (`lock` uses `PoisonError::into_inner`), so the rest of the session keeps running.
  - Detection seams: a drop guard in `run_worker`, like `StopInFlight`, which marks the worker dead under the lock, clears `queued`, shows the notice and writes a log line; and the `send` result in `stop_recording`. No message id or `FailureReason` exists for this: Q1.
- **Release with `panic = "abort"` (T-051 r2 #5).** In `voicen.exe` a `run_job` panic ends the process. T-100's panic hook writes a `crash-*.txt`, and the next start's `Session::begin` gives the previous-session verdict (`docs/decisions/diagnostics-log.md`, "One record per abnormal session end"). FR-032 deletes the stale temp audio at that start, so the pending retry is lost by spec. The Open line in `docs/decisions/dictation-session.md` ("If `run_job` ever panicked ... no restart is built") is amended after Q2 is decided.
- **Logs-folder notice (T-071 r1 #3).** `logs_folder::request` → `open` → `warn` writes only `WarningKind::LogsFolderFailed`. Spec 006 FR-017 and contracts/ipc.md name the id `error.open_logs_folder` ("Cannot open the logs folder: {reason}"); it is not in `i18n/en.json`. Hook: in the `logs-folder` thread, on `Err`, call `DictationSession::notice_with(error.open_logs_folder, [reason])`. That thread is not the main thread, and the session lock is free there. `{reason}` maps the `io::ErrorKind` to the existing `logs_reason.*` nested ids, and the OS text is never shown. Surface: Q6.
- **Which settings snapshot a Retry uses (T-073 note).** Already decided, so it needs no owner question. Spec Clarification 4 and FR-027 say: "the settings current at the moment Retry is clicked (engine, base URL, model, key, language)". Timeouts are settings (decision #99) and are derived per job with `Timeouts::from_settings` from the job's snapshot (FR-018, `Pipeline::process`). A retry job carrying the click snapshot therefore uses the new limits with no extra code. The snapshot is taken on the input thread (`SettingsService::snapshot`, as at a press). The pending slot is read only on the worker, which keeps the dictation-session invariant "`retry_available` is the pending slot, read on the worker".

### Toast activation (technical risk behind Q5)

research.md R-16 plans `CreateToastNotifierWithId(AUMID)` and an `Activated` handler. Microsoft's docs (context7, learn.microsoft.com "author-coclasses") say a desktop app's toast button reaches the app from Action Center only through a COM activator. That takes an `INotificationActivationCallback` registered with `CoRegisterClassObject`, `PKEY_AppUserModel_ToastActivatorCLSID` on the Start-menu shortcut, and `HKCU\Software\Classes\CLSID\{...}\LocalServer32`. The `Activated` event only covers a click on the popup while that toast object is alive. With Focus Assist on, a toast goes straight to Action Center, so an `Activated`-only design would fail exactly in scenario 6's setting. The installer's `CreateOrUpdateStartMenuShortcut` sets only `SetLnkAppUserModelId`. This is from documentation only; it has not been run on a runner.
