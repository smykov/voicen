**What was verified**
- **One stop path.** `dictation::stop_recording` is the only code that stops a capture for a job. It is used by `hotkey_released`, the toggle branch of `hotkey_pressed` (`press_while_live`) and `tick`/`run_timer`. `esc_pressed` queues nothing, so it does not take `releasing` (documented in dictation-session.md).
- **Lock order.** `releasing` is always taken before the state lock. `hotkey_pressed`'s live check is a plain `if` condition, so its temporary guard drops before `stop_recording`. `run_timer` drops `st` before `tick(shared, now)` and re-locks after. No path takes `releasing` while holding `state`. `Drop` holds no lock while joining.
- **Esc claim follows `live_id` alone.** `Shared::publish` syncs `CancelKey::set` from `ctrl.live_id().is_some()` before the `stopping` early return, once per change (`published_claim`). A failed capture gets no claim (publish runs after `capture_failed`).
- **Shell registration.** `win/hotkey.rs` registers ids 3 (`ESC_ID`, bare + `MOD_NOREPEAT`) and 4 (`ESC_MOD_ID`, the active hotkey's modifiers | `MOD_NOREPEAT`, OQ-21 (1)a). It does so only on a `Request::CancelKey` from the session, on the window's own thread. It unregisters on `set(false)` and in `release_all` at thread end. The ids differ from `HOTKEY_ID`/`SPARE_ID` (1/2). The shell reads no mode and decides no "recording on" (windows-shell.md rule 1 kept).
- **Refused Esc.** A refused Esc is reported once per claim (`cancel_key_result(esc && esc_mod)`). The session emits one `Warning{EscUnavailable}` only while a recording is live, and the hotkey thread writes no line of its own. The recording continues (test `refused_cancel_key_keeps_recording_and_emits_esc_unavailable`, Windows `a_refused_esc_claim_*`).
