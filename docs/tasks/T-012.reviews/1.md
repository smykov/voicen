#### Developer's deviations
1. **No `end=device_lost` in the diag line.** This is a follow-up, not needed now. The diag line has no `end=` pair for *any* job-closed recording (`Released`, `Toggled` and `MaxLength` have none either). The analysis note assumed a format that does not exist. FR-033 does not require the end reason. `diagnostics-log.md` records the choice. Adding `end=` for all job-closed ends together is a log-format change of its own (finding #1).
2. **`ipc.unavailable` on a failed listing.** Correct. A broken listing stays distinct from "no microphones" (silent-degradation avoided). It uses the closed shape of the other settings commands and is pinned on both sides: shell `a_device_list_that_cannot_be_read_rejects_…` and the e2e rejected-list case with a canary. `contracts/ipc.md` is updated.
3. **`FakeAudioSource::default_device()`.** Fine. It is one named fake used by every impl that needs "one default device", so there is no repeated literal.
4. **`RecordingController::notice_with`.** Fine: it is the same rule as `notice`, with params. Low nit: `notice` could delegate to it (finding #5).
5. **Shutdown guard in `stop_recording`.** Justified. It closes the window where the loss thread (or the timer) passed its own shutdown check before `Drop` set the flag. After shutdown the capture and queue are gone, so returning without effect is the only correct outcome. It changes no pre-shutdown behaviour.
6. **Unnamed device listed as "Microphone".** Acceptable. The name is display only and the case is rare. The English literal is not localized (finding #3).
7. **Unreadable or duplicate ids left out.** Acceptable. A device whose id cannot be read cannot be opened by id, so listing it would offer a choice that always fails. WASAPI endpoint ids are unique, so the duplicate guard is defensive. The one edge: if the Windows default's own id is unreadable, no entry is flagged default and every press is `NoDevice` (finding #4).

**OQ-24 (open).** It does not block code review. The task proceeds on proposal (A), recorded as non-blocking and reversible. The core behaviour (one `notice.mic_fallback{device}` per change) is proven. However, with the overlay rule as it is, a recording longer than 3 s never shows the notice, so the owner's Acceptance check "one notice naming it" cannot pass before T-007's toast or an OQ-24 answer (finding #2).
