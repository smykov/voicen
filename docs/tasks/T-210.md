## Context

Part 3 of the T-007 split (decision #274). T-007 adds the core `Notifier` port, the controller outbox and `DictationSession::retry`; this task implements the port in `src-tauri` and the shell's Retry routes. The T-007 analysis (`## Investigation`, sections "Constraints already decided" and "Toast activation") is the starting point.

- Toast notifier: WinRT toast on its own thread (`Show` is a COM call; never under the session lock), AUMID as the Start-menu shortcut's.
- Retry from the toast (Q5 (a)): a COM activator — `INotificationActivationCallback` registered with `CoRegisterClassObject` while the app runs; the NSIS hook writes `PKEY_AppUserModel_ToastActivatorCLSID` on the Start-menu shortcut and `HKCU\Software\Classes\CLSID\{...}\LocalServer32`. Works from Action Center, where toasts go under Focus Assist. A cold activation (app not running) only starts the app: the pending audio is gone by FR-032. The toast argument is `retry:<id>` only (FR-20, NFR-04). The uninstaller removes what the installer wrote.
- Tray Retry: `on_menu_event` Retry arm → `spawn_blocking` → `session.retry(None)` (the main thread never takes the session lock, `docs/decisions/windows-shell.md`); the menu-rebuilt-while-shown risk named there becomes reachable here.
- Logs-folder notice (Q6, T-071 r1 #3): on a failed "Open logs folder", `DictationSession::notice_with(error.open_logs_folder, [reason])` from the `logs-folder` thread — overlay 3 s and toast, tray state unchanged; `{reason}` is a `logs_reason.*` id from the `io::ErrorKind`, never the OS text.

So the toast needs exactly one implementation point (`DictationPorts.notifier`), with no per-message code. `notice.mic_fallback` comes for free (T-007 test `the_fallback_notice_is_offered_to_the_notifier_once_without_retry`).
3. **Already partly done by T-007 (checked, to avoid duplication):** T-007 did the core `TrayAction::Retry` row (mutants 31-35 are `crates/voicen-core/src/tray.rs::menu`/`ALL` only), the catalog ids `action.retry`, `tray.retry_last` and `error.open_logs_folder`, and `DictationSession::retry`/`notice_with`. In the shell it added only compile-through: the `NoToasts` struct, `notifier: Arc::new(NoToasts)` (T-007 wt `dictation.rs:185`), the empty Retry arm, and `FakeNotifier` in `tests/tray.rs` and `tests/hotkey.rs`. T-210 replaces those three shell stubs and adds nothing in core that T-007 has.
4. **Core blockers the brief does not name (confirmed):**
   - `PendingId(pub(crate) u64)` (T-007 wt `platform.rs:40`) has no accessor, so the shell can neither write `retry:<id>` nor parse it back. T-209 hit the same wall: "`PendingId`'s field is `pub(crate)`".
   - The `io::ErrorKind` → `logs_reason.*` map is the private `diag::log::unwritable` (T-007 wt `log.rs:385`). Writing a second map in the shell would make two maps that can drift (P-010 / P-011).
   - `LaunchArgs::parse` ignores `-Embedding` (`settings/gate.rs:100-138`). A COM launch of a second process while the primary is up but has not yet registered its class object (startup) would therefore pop Settings to the front.
5. **Class fixed before:** none (see Recurrence).

### Constraints carried over (T-007 history › "Constraints already decided", "Toast activation")

- **The main thread never takes the session lock** (`docs/decisions/windows-shell.md` line 35, the `tray_menu_opened` pattern). So the Retry arm and the activator only stamp `Instant::now()` and hand off with `spawn_blocking`. `retry` takes the lock (T-007 wt core `dictation.rs:631`), and that lock can be held across a ≤3 s `AudioSource::start` (windows-shell.md invariant 2). The same holds for `Activate`, which runs on a COM RPC thread: it must return promptly.
- **The Notifier must not block** (T-007 wt `platform.rs:165-173`; `docs/decisions/dictation-session.md` "The Notifier is called once per shown message, outside the session lock" › Don't). `notify` is called from the hotkey, worker, timer and logs-folder threads. It posts to the toast thread and returns. `Show` is a COM call.
- **FR-20 / NFR-04 / P-009:**
  - The toast argument is `retry:<id>` only.
  - Toast text is a catalog message. No message carries a transcript, and the `{device}` and `{host}` params are user-visible already.
  - The failure line is `toast_failed` with the HRESULT only, never the OS text.
  - Build the XML with the DOM, so a device name holding `<`/`&` cannot change the toast.
- **Activation path (author-coclasses):** the `Activated` event covers only the popup while the toast object lives. Action Center, where Focus Assist sends toasts, reaches a desktop app only through the COM activator. A cold launch (app not running) gets `voicen.exe -Embedding`. FR-032 deleted the pending audio at that start, so nothing is retried. The app just starts, tray only when settings are Loaded (`startup_action` ignores the args).

### Seam details and residual risks

- **Toast thread:** follow the `win/audio_notify.rs` pattern (`CoInitializeEx(COINIT_MULTITHREADED)` at :166, `#[implement]` with `windows-core` as a direct dependency).
  - Keep the thread alive for the process: the class object lives in the MTA.
  - Revoking at `RunEvent::Exit` is optional, because the process ends in `process::exit`.
  - If the thread cannot be spawned or COM init fails, write one line and drop the offers. The overlay and tray carry the messages (Acceptance 5).
- **Notifications off:** with notifications off for the app, `Show` does not fail, but `ToastNotifier::Setting()` is not `Enabled`.
  - Treat that as "cannot be shown": one `toast_failed` line without `os_code`.
  - Recommended: once per change of the setting, not once per toast. The reviewer decides this against `docs/decisions/diagnostics-log.md`. A registration failure of the activator is a separate kind or the same one, also the reviewer's call there.
- **Toast surface:** contracts/messages.md marks `notice.logs_unwritable` as overlay-only, while T-007's I1 offers it. The filter is a core predicate (Linux-tested) used by the shell notifier, so I1 stays "offer everything".
- **Tray menu rebuilt while shown** (windows-shell.md line 175): this becomes reachable here. A failure that ends while the menu is open flips `retry_available` and rebuilds the menu during `TrackPopupMenu`.
  - The mock runtime cannot drive a shown menu, so no CI test can bite this.
  - Recommended: add it to the owner's manual check (open the menu, let a slow failing request end), and update the line 175 note to say it is reachable since T-210.
- **ACL** (`docs/decisions/ipc-acl.md`): no new `#[tauri::command]`, no page invokes anything new, so `build.rs APP_COMMANDS` and the capabilities do not change.
- **Upgrade path:**
  - `CreateOrUpdateStartMenuShortcut` returns early in `$UpdateMode` (`installer.nsi:900-906`), so the CLSID must be set in `NSIS_HOOK_POSTINSTALL` on the existing `.lnk`. Do not edit the fork.
  - A `/UPDATE` uninstaller that deletes the CLSID key is harmless: the following POSTINSTALL writes it again.
  - `/NS` (no shortcut) installs and dev builds get no toasts at all. That is the failure branch, and it is an accepted limit: FR-028 says the overlay and tray report.
- **NSIS COM write:** no NSIS built-in sets a `VT_CLSID` property. The hook does `IShellLinkW` → `IPropertyStore::SetValue(PKEY_AppUserModel_ToastActivatorCLSID {9F4C2855-9F79-4B39-A8D0-E1D42DE1D5F3},26)` → `Commit` → `IPersistFile::Save` through `System::Call`, like tauri's `SetLnkAppUserModelId`. Only the install smoke proves it.
- **Test isolation:** a CLSID registration is per process and HKCU is per user, so `feedback.rs` tests that register the activator serialise or register once per binary (F-012 class). Any `pwsh` in a shell test goes through the bounded helper (F-006).
