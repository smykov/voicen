## Investigation

Investigator, 2026-10-24. Serena loaded but not needed for code symbols: the evidence is role text, the Makefile and shell scripts, which the language server does not parse. Read with `cat`/`sed`/`grep`. Hook code was read, not run: the state guard refuses hand-fed hook payloads.

**Frame.** Observed (T-116): the test-writer handed over red tests holding a `#![allow(clippy::…)]` line. The developer's first full gate stopped at `check-clippy-lines` after about 3 min. A `make -k check` then took about 19 min, the test-writer was resumed, and the gate ran again. Expected: a seconds-long tripwire catches the line before handover, and the developer runs the gate once, after targeted tests.

**Hypotheses.**
1. *The role text names no pre-check.* Confirmed. `test-writer-core.md` / `-ui.md` step 5 reads "Lint the tests." and names no command. `developer-core.md` / `-ui.md` step 5 reads "Run the full area gate `make check`", and no step says to run targeted tests first.
2. *The kit already fixed this and the project did not take it (render drift).* Confirmed. The installed kit is 0.12.2 (`.teamwright/installed.json` `@kit`). Its `template/.claude/agents/test-writer.md` step 5 is "Fast checks on what you wrote, before handing over" (`lint_command` + formatter through `scripts/tw-run`). Its `developer.md` step 1 runs only the task's tests through `scripts/tw-test`, and step 5 runs "the full area gate **once**" through `scripts/tw-gate`. 0.12.0 and 0.12.2 are identical in these lines. Kit upgrade f1b1d0ce (0.8.2 → 0.12.0) did not touch `.claude/agents/`. The sha256 of 7 of the 9 role files differs from `installed.json` (local edits: T-082, #194), so the upgrade kept the local copies, and the bodies are still the 0.8.2 text. T-160 found the same for the test-writer bite check.
3. *Clippy itself would have caught it.* Refuted. The lints named in the allow line are valid, so `clippy --all-targets -D warnings` stays clean. The T-116 test-writer ran clippy, and it passed (`docs/tasks/T-116.md`, the bite-check paragraph). Only the token guard refuses such a line. So the kit's step 5 (lint + formatter) alone would **not** have caught T-116: the project needs to add the token tripwires.
4. *The token tripwire sees the test-writer's files.* Partly refuted. This is the key finding. `scripts/ci/clippy-lines.sh` scans `git ls-files` only. The test-writer does not commit, so a new test file is untracked, and the line was in such a file (`codec.rs`, new in 53190cd). Dry run in a throwaway worktree, with a probe `.rs` holding the T-116 allow line:
   - untracked → `clippy-lines: ok: 44 line(s) owned`, exit 0 (missed);
   - after `git add -N <file>` → `t161_probe.rs:3: clippy: a line holding the token clippy that is not owned …`, exit 1;
   - the same line appended to the tracked `lib.rs` → exit 1.

   `scripts/ci/core-test-os-answer.sh` uses `find`, so it sees untracked files without help (0.1 s).
5. *A second path / the class was fixed before.* `docs/failures.md` has no entry for gate latency or a missed pre-check, and no task carries `class: gate-latency` except this one. Searched: `grep -i 'tw-gate\|full gate\|latency\|lint\|clippy-lines'` in failures.md, and `class:` over docs/tasks. The nearest earlier fix is the kit's own: tw-gate, tw-test and test-guard came with 0.12.0 for the incident "the full gate ran five times on the same code" (`docs/process/gates.md` › Gate runs). It reached this project's hooks and scripts, not its role text. Recurrence: none in this project. Do not open an rca task: the class is closed by merging the kit text, plus one project line.

**Costs measured.**
- `make check-clippy-lines` = the self-test `clippy-lines.test.sh`: 45 cases on temp trees and repository copies, **1 m 42 s**. That is why the first gate took about 3 min to reach it: it is the 7th target of `check:`.
- `scripts/ci/clippy-lines.sh` on the real repository: **0.5 s**.
- `scripts/ci/role-tools.sh`: 0.5 s, green today.

The pre-check therefore names the scripts, not the make targets. Both are existing commands: no Makefile or `scripts/ci` change is needed, so this is not a guard change, and `checker: false` stays.

**test-guard (read, `scripts/hooks/test-guard.sh` `builtin`, `config_matchers`, `allowed_in_run`).**
- Refused: `make check` and `make -k check` (the positional `check`).
- Not refused: `make check-<x>` (the regex `(test|tests|check)|test[-_:].*` must match the whole word, and the prefix matcher compares whole words); `scripts/tw-run core -- '<lint_command>'` (exact lint_command); `scripts/ci/*.sh`.
- So the developer role's "`make check`" text names a command the hook refuses, and `scripts/tw-gate core` is the form that works. `tw-gate` has no keep-going option.
- Side finding, static reading only: a command that starts with `systemd-run` (the owner's host-load form from 2026-10-24, passed in spawn prompts) is neither stripped as a prefix nor treated as a runner, so `systemd-run … make -k check` passes the guard and bypasses tw-gate's cache. This is probably how T-116 ran `make -k check`; the transcript was not available to confirm it. Relevant to T-162.

**Root cause.** Render drift. The kit-0.12 "fast checks before handover" and "targeted tests, then the gate once via tw-gate" rules never reached the locally edited role files. On top of that, the project has a gap of its own: its decisive cheap check (the clippy token guard) is not a lint, and it ignores untracked files.

**Invariant.** Before handover, the test-writer's working tree, with every new file intent-to-added, passes every area pre-check that needs no implementation build: core = `lint_command`, `scripts/ci/clippy-lines.sh`, `scripts/ci/core-test-os-answer.sh`; ui = `lint_command`. The developer runs the full gate only after the targeted tests are green, and re-runs it only after a change.

**Seam.** Role bodies only:
- `.claude/agents/test-writer-core.md` and `test-writer-ui.md`: Project parameters "Run tests" row, run paragraph, Steps 3 and 5, Return block (new line `Pre-check: <command — result>`).
- `.claude/agents/developer-core.md` and `developer-ui.md`: "Area gate" row → `scripts/tw-gate core|ui` (runs `make check`), run paragraph, Step 1 (tw-test while working), Step 5 (once, tw-gate, exit-75 rule), Return "Gate:".

Front matter and the `teamwright:tools` block stay byte-identical, so `scripts/ci/role-heads/*` and `make check-role-tools` are unaffected. The fallback lines that role-tools requires are inside the Tools block. The project addition goes outside the markers, as #194 did, so `/teamwright:reconfigure` keeps it. A later kit upgrade still skips these files, which is the existing drift, not a new one.

**Options.**
- **A (recommended): hand-merge kit 0.12.2 test-writer step 5 and developer steps 1/5 into the four files, and add the core pre-check line.** "`git add -N` each new file, then `scripts/tw-run core -- '<lint_command>'`, `scripts/ci/clippy-lines.sh`, `scripts/ci/core-test-os-answer.sh`; fix what they report in your files; report each in the Return block".
  - Removes the cause: the check the developer's gate failed on now runs at the test-writer, on files git can see.
  - Proof, for role text (no code test is possible): the Investigation's dry run repeated and recorded under `## Tests` (untracked → exit 0; after `git add -N` → exit 1), plus `make check` green with check-role-tools.
  - Risk: low. `git add -N` touches the index of the task's tree (the orchestrator stages these files anyway); merge conflicts with T-160 and T-114.
  - Rollback: revert the commit.
- **B: make `clippy-lines.sh` also scan untracked files** (`git ls-files --others --exclude-standard`), so `git add -N` is not needed and the local gate stops passing untracked `.rs` files.
  - Today a developer's untracked new file with an allow line also passes a local `make check` and fails only in CI.
  - It is a guard change: `checker: true`, `decides_on: token` (unchanged), new fixtures in `clippy-lines.test.sh`.
  - Better as its own checker task. It is not needed for T-161 when A uses `git add -N`.
- **C: run `clippy-lines.sh` in `scripts/hooks/pre-commit` on staged files.** It catches the line at the orchestrator's red-test commit, but the hook is kit-owned (installed.json). That moves the drift into a hook. Not recommended.
