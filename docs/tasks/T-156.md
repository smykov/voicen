## Context

US10 (uninstall never silently deletes calls). Spec FR-041, SC-010; research R15; contracts/installer-ci.md "Uninstaller". Area installer-ci, seams `src-tauri/windows/installer-hooks.nsh`, the uninstall steps of `ci.yml`, and `scripts/ci/nsis-fork.sh` with its test (checker). No prerequisite; ordering rule: it reaches `main` before T-128 (Record reachable), because today's POSTUNINSTALL would delete calls.
First acceptance (R15): prove that the forked template never runs `RMDir /r "$INSTDIR"`.

## Investigation

Tools: Serena was loaded, but the change has no Rust symbols. The only Rust fact used is `paths::data_dir` (`src-tauri/src/paths.rs`), read directly. NSIS, PowerShell, YAML and shell were read with grep and file reads. Context7 has no NSIS library: `resolve-library-id "NSIS"` returned only unrelated libraries. No NSIS docs or source exist on the host (searched with `find / -iname '*makensis*'`). So every NSIS runtime fact below is marked as unconfirmed until the Windows runner shows it.

**Frame.** Expected (FR-041, SC-010, decisions #170 and #180 #1): `/S` and `/P` keep `%LOCALAPPDATA%\Voicen\calls`; only `/PURGECALLS` or an interactive Yes removes it; no other root is ever touched. Observed (code): `/S` and a user `/P` set `$VoicenPurgeData=1` (`installer-hooks.nsh:88-90`), and POSTUNINSTALL runs `RMDir /r "$LOCALAPPDATA\Voicen"` (`:132`), which takes `calls\` with everything else. Nothing breaks yet, because no build writes `calls\` before T-128. That is why the ordering rule is G42 before G14.

**Hypotheses checked.**
1. *The fork deletes recursively somewhere (R15 first acceptance).* Refuted. `grep -n -i rmdir src-tauri/windows/installer.nsi` finds `:796` `RMDir /REBOOTOK "$INSTDIR\\{{this}}"` (resources_ancestors; resources sit at the root, so the loop is empty), `:798` `RMDir "$INSTDIR"` (not recursive; it fails on a non-empty folder, which leaves the folder in place while `calls\` exists) and `:811` (Start-menu folder). Fork edit 2 removed the stock checkbox's recursive removal. The proof is only a grep today, and nothing pins it. That gap is why `nsis-fork.sh` gets extended.
2. *`$INSTDIR` is not the data folder.* Refuted: `installMode: currentUser` plus `installer.nsi:492` gives `$INSTDIR = $LOCALAPPDATA\Voicen`, which equals `paths::data_dir`. So the program, `uninstall.exe` and user data share one folder, and `calls\` sits under `$INSTDIR`. Any recursive `$INSTDIR` delete would break FR-041.
3. *A second deletion path.* Searched `installer.nsi` and `installer-hooks.nsh` for `RMDir`, `Delete` and `ExecWait`. Everything else deletes named files only (`:764-793`, shortcuts `:810-825`). The `--purge-credentials` ExecWait touches Credential Manager, not files. The only path is the hooks' `:132`.
4. *This class was fixed before.* `docs/failures.md` has no installer or uninstall entry. The installer invariant came from the T-025 analysis, not from an F-entry (`docs/decisions/installer.md`). No recurrence.
5. *The existing "files left" check breaks on kept calls.* Confirmed by reading: `:133` `${FileExists} "$LOCALAPPDATA\Voicen\*.*"` is true whenever `calls\` is kept. An interactive keep would then show `VoicenFilesLeft`, a false error. The check must exclude `calls\`.

**What T083 has to change (per R15 and the contract).**
- PREUNINSTALL, after `$VoicenPurgeData`, computes `$VoicenPurgeCalls`, starting at 0:
  - `$UpdateMode = 1` → 0.
  - `${GetOptions} $CMDLINE "/PURGECALLS"` found → 1.
  - `${Silent}` or `$PassiveMode = 1` → 0.
  - Otherwise, only if `$LOCALAPPDATA\Voicen\calls` exists (and `$LOCALAPPDATA` is not empty): `MessageBox MB_YESNO|MB_ICONQUESTION|MB_DEFBUTTON2 ... /SD IDNO`, and only Yes → 1.
  - The folder is named in the message by concatenation, `"$(VoicenRemoveCalls)$\r$\n$LOCALAPPDATA\Voicen\calls"`. That does not depend on NSIS expanding variables inside a LangString (unconfirmed, no docs).
- POSTUNINSTALL:
  - On PurgeCalls: `RMDir /r "$LOCALAPPDATA\Voicen\calls"`.
  - On PurgeData: when calls are purged too, `RMDir /r "$LOCALAPPDATA\Voicen"` is still acceptable. Simpler and closer to the contract: always remove top-level entries one by one with a `FindFirst`/`FindNext` loop that skips `.`, `..` and `calls`, then a plain `RMDir "$LOCALAPPDATA\Voicen"`. This removes the folder only when it is empty.
  - The "files left" check looks for any entry other than `calls`.
  - The registry bookkeeping stays keyed on PurgeData.
- `/KEEPDATA /PURGECALLS` is not in the contract table. R15 says "calls\ alone is removed ... (and the rest per $VoicenPurgeData)", so it removes `calls\` and keeps the rest. Add that row to the `installer.md` table.

**CI (T082, red on `wip/T-156` before T083).**
- The W4 step (`ci.yml:1170`) plants `calls\2026-01-01_000000\meta.json` (fake content) before `/S`.
  - The done loop (`:1206`) and the assertion (`:1212`) change from "`$dir` absent" to "`$dir` holds only `calls\`, and the planted `meta.json` exists".
  - It is red today because `:132` removes it.
- New step after W4: `setup.exe /S -Wait` (pattern of W3 `:1162`, installing over a calls-only folder). Then plant `$env:RUNNER_TEMP\calls-elsewhere\2026-01-01_000000\meta.json`. Optionally also write `settings.json` with `calls.storage_root` pointing there, so a future uninstaller that read settings would be caught; the app is not started. Then run `uninstall.exe /S /PURGECALLS`, poll up to 60 s, and assert:
  - `$dir` is absent;
  - `calls-elsewhere` still exists;
  - no `Voicen/` credential or Run value is left;
  - cleanup runs (credentials only through `scripts/ci/credentials.ps1`, F-009).
  - It is green on today's hooks and acts as the regression pin. The W4 assertion is the test that fails without the change.
- `ci.yml` is an owned file, not a guard path. None of its byte-identical fragments (release, Telegram, action lines) are touched, so `scripts/ci/*.yml` and `action-lines.txt` stay unchanged. Check with `make check`.

**Guard (checker).**
- Guard paths staged: `scripts/ci/nsis-fork.sh`, `scripts/ci/nsis-fork.test.sh`, a new `scripts/ci/nsis-rmdir-lines.txt`, and the `Makefile` comment of `check-nsis-fork`. So `checker: true` (already set) and `analysis.decides_on` are required (gates.md › Guard trigger).
- Why decide on owned lines and not on a raw token: a token such as `/r` already occurs legitimately in the fork (`/R` restart flag, comment at `:722`). A reader of RMDir flags and argument order would be a P-020 model.
- Scope: the fork only, as R15 asks. The hooks' deletions are proven by the CI steps, which run the real uninstaller. Extending the owned-lines list to `installer-hooks.nsh` would also pin them but add churn. Developer's choice, recorded in the guard row if taken.
- Not caught: deletion through a header included from outside the fork, or through `ExecWait cmd /c rd`. None exist today; write this in the guard row.

**Risks and missing evidence.**
- *Junctions.* If a user made `calls\` (or any top-level entry) a junction to another drive, it is not confirmed whether NSIS `RMDir /r` follows it (no docs reachable). Following it would delete another root, which breaks FR-041. Recommended in T083: before any `RMDir /r` on an entry, read its attributes (`System::Call 'kernel32::GetFileAttributesW(w "<path>") i .r0'`). If `FILE_ATTRIBUTE_REPARSE_POINT` (0x400) is set, remove only the link with a plain `RMDir`. Optional CI probe: plant a junction `calls\link -> $RUNNER_TEMP\calls-elsewhere` in the `/PURGECALLS` step and assert the target survives.
- *`$LOCALAPPDATA` vs `%LOCALAPPDATA%`*: an existing residual risk (installer.md), unchanged.
- The interactive EN/RU question can be checked only by the owner (quickstart 9, `verify_exception`).
- Docs drift found, not caused by this task: `installer.nsi:4` still says the gate compares `pnpm-lock.yaml`, which T-093 retired. Fix it when touching the header, or leave it.

**Owner decision points.**
1. `/KEEPDATA /PURGECALLS` removes `calls\` and keeps the rest. *Recommendation:* yes, it follows from R15; record it in `installer.md`. No owner input is needed unless the owner wants `/KEEPDATA` to win.
2. Junction handling: never follow a reparse point; remove only the link. *Recommendation:* yes, it is the FR-041 reading ("never delete any other root"). Ask only if the owner wants it out of scope.
3. None blocking: the behaviour is settled by FR-041, R15, #170 and #180.
