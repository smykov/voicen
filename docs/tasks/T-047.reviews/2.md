**Does the 4 s bound still bite?** (`api_pipeline.rs:748-756`)
- `refused_addr()` and its probe run before `h.run`, so the probe (~2 s on Windows) is not inside `took` (`Harness::run`, `:159-170`, times only `run_job`).
- *Waiting out the connect timeout*: production `Timeouts::default().connect` is 5 s, and 5 s ≥ 4 s, so the test goes red on both OSes. *Waiting out the total*: 30 s, red. This is the guarantee "at once" stands for (FR-24: a refusal is not waited out).
- *A sleep or backoff of ~4 s*: on Linux the refusal is immediate, so `took` is about 4 s + ε, not below 4 s: red. On Windows it is about 6 s: red.
- *Two connect attempts on Windows*: about 2 × 2 s plus the job's own work, which is just over 4 s. That is red, but by a margin of only about 0.1–0.2 s, so this bite is thin. Nothing in the code makes a second attempt: the address is a literal IPv4 (no happy-eyeballs fallback), and `src/` has no retry or backoff in the engine or pipeline path (grep). I note it here; it is not a finding.
- Windows headroom for the real path: one refused connect takes ~2.1 s, against 4 s.
- The bound references `Timeouts::default().connect` instead of a second literal (P-010).

**Does anything else in voicen-core tests bound a refused connect below ~2.1 s?** No assertion does. Every other refused connect is cut short only by a 2 s **connect limit**, and in every case a connect timeout maps to the same expected reason:
