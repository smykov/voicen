**What I checked against the points raised**
- *Does `127.0.0.1:1` work on the Windows runner?* Acceptable. Windows Firewall does not filter loopback by default, and nothing listens on TCP 1 on a hosted runner. A refused loopback connect already works there: in the Windows job of run 37183609259, `openai_client`'s `refused_loopback_port_is_cannot_reach_host_port` passed with the old released-port helper, and the port number does not change that path. If a firewall dropped the SYN instead, the probe would get `TimedOut` and panic with a message that names decision #53. That is a loud environment failure, not a flake, which is what #53 chose. The first Windows CI run after push confirms it.
- *Does the 5 s probe slow the tests?* On Linux the refusal is immediate (the binaries took 1.2–1.6 s with the probes). On Windows, a refused loopback connect takes about 2 s, because Windows retries the SYN after an RST. In the same CI log, the refused test finished about 2.1 s after its binary started. That is inside the 5 s bound, and the probes in one binary run in parallel, so the cost is about 2 s of wall time per binary that uses `common`. Acceptable.
- *Does compiling `common` into more binaries add any binds?* No. `common` has no code that runs at load time. `Server::start`/`start_on` bind only when a test calls them, and `openai_client`/`api_pipeline` call neither. `refused_addr_tests` only connect. One caveat is in #3.
- *Is `local_download_refused` consistent with #53?* It keeps its own bind-and-release helper in its own binary, as #53 decided. It now also runs the 3 `refused_addr_tests` (#3).
- *Bite.* `refused_addr_port_is_below_the_ephemeral_range` fails on the old helper (its `bind(0)` port is ≥ 32768 by construction) and on any fixed port inside the range. `refused_addr_is_refused_by_a_connect_probe` fails on an address with a listener and on a dropped SYN. The mutation above covers the client classification.
