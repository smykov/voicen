## Context

Found in the T-044 analysis (decision #57): tauri 2.12.1 checks app (`#[tauri::command]`) invocations against capabilities only when the app defines permissions (webview/mod.rs:2076-2084; tauri-build 2.7.1 acl.rs:412-421). Voicen defines none (`tauri_build::build()`, no `src-tauri/permissions/`), so every app command (`settings_get`, `settings_save`, `settings_speech_languages`, the T-044 `local_models_*`) is callable from any local webview; decision #45's least-privilege limit to the `settings` label covers plugin commands (event, window) only. Today there is one webview, so the exposure is theoretical; the overlay (T-006) adds a second. Define app permissions (tauri-build `AppManifest` / `permissions/`) so only the `settings` window may invoke the settings and local-model commands, and pin it with an ACL test from another label.

## Acceptance

- [ ] Windows CI: `settings_get`, `settings_save` and `local_models_*` invoked from the `settings` window pass the real ACL; invoked from a window with another label they are refused
- [ ] Failure branch: a new app command without a permission entry is refused (or the build fails) — test or guard
- [ ] Test that fails without the change: `src-tauri/tests/*.rs` ACL test over `generate_context!(test = true)` (Windows CI)

## Investigation

Tools: Serena not used (its MCP tools were not loaded in this session), so grep and file reads over `src-tauri/src`, `src-tauri/tests`, `src/`; tauri sources read from the pinned crates in `.teamwright/cache/core/_usr_local_cargo_registry/src/*/` (Cargo.lock: tauri 2.12.1, tauri-build 2.7.1, tauri-codegen 2.7.1, tauri-macros 2.7.1, tauri-utils 2.10.1). context7 not used: the pinned source is the primary reference. Nothing was built or run: the shell builds only in Windows CI.

**Frame.** Observed: every `#[tauri::command]` in `lib.rs::commands` runs for an invoke from any local-origin window, whatever its label. Expected: settings and local-model commands run only for label `settings`. Reproduces: today only by reading the code (one webview is open at a time in practice, but the `overlay` window from T-057 is a second label that exists now). No test shows it, because every wrong-label test under the release context invokes plugin commands only (`settings_window.rs::another_window_label_gets_no_permission`, `overlay_ipc.rs` capability test).

**Inventory (today).**

| Command | Defined in | Called by (UI) | Window that needs it |
|---|---|---|---|
| `get_build_info` | `lib.rs` | `src/lib/buildInfo.ts` (About in the settings page; also `src/routes/+page.svelte`, the root page, which no window loads) | `settings` |
| `settings_get`, `settings_save`, `settings_test_connection`, `settings_speech_languages`, `settings_list_microphones` | `settings_ipc.rs` | `src/lib/settings/settingsApi.ts` | `settings` |

| `overlay_ready` | `overlay.rs` | `src/lib/overlay/overlayApi.ts` | `overlay` |

Window labels: `settings` (`settings_window::LABEL`, built only by `settings_window::open`) and `overlay` (`overlay::LABEL`, built only by the overlay thread). `tauri.conf.json` has `app.windows: []`; `tauri-plugin-single-instance` and the tray make no webview. The overlay page imports only `overlayApi` and `i18n` (no `settingsApi`). Note: some command names start `local_model_` (singular), not `local_models_`: the task title's `local_models_*` means all four.

**Hypotheses.**
1. *The app ACL switch is off because no app permission exists.* Confirmed. Evidence in `analysis.evidence`. The webview check rejects a local app command only when `has_app_acl_manifest` is true (webview/mod.rs:2080). That flag is `acl.contains_key("__app-acl__")` (T-044's note said `__app__`; that is tauri-build's package name for the app's permission files in OUT_DIR, acl.rs:276, not the ACL key). tauri-build inserts the key only for a non-empty app manifest (acl.rs:417-422).
2. *The same concern is handled on a second path* (another way page code reaches Rust). Refuted for the paths searched. `grep` over `src-tauri/src` finds no `register_uri_scheme_protocol` / `register_asynchronous_uri_scheme_protocol`, no `on_navigation` / `on_page_load`, no `listen_any` / `.listen(` (Rust listeners a JS `emit` could reach; `plugin:event|emit` is not granted anyway, settings_window.rs test), no `Channel<`, and no `initialization_script`. The channel fetch command is exempt in tauri (`FETCH_CHANNEL_DATA_COMMAND`, webview/mod.rs:2082) and reads only channels Rust created. Plugin commands are already ACL-checked (decision #45). So `on_message` is the only enforcement point.
3. *This class was fixed before.* No. `docs/failures.md` has no IPC/ACL entry (the only "permission" row, F-015, is the GitHub token, another class). No task other than T-049 has `class: ipc-acl`. Related work, not a defect of this class: T-037 / decision #45 (plugin capability for `settings`), T-057 (overlay capability), T-044 / decision #57 (the finding, pinned as "app commands not ACL-checked" in `docs/decisions/model-download.md` › "App commands are not ACL-checked from local origins").
4. *`generate_context!(test = true)` does not carry the real ACL, so a mock-runtime test cannot prove it.* Refuted. tauri-codegen context.rs:377-410 reads `acl-manifests.json` and `capabilities.json` from OUT_DIR and resolves them; the `test` flag (`running_tests`, context.rs:146) only gates the macOS plist (:284). `test::get_ipc_response` calls `Webview::on_message` (test/mod.rs:302), the same check as a real webview. Only `mock_context` has an empty ACL (test/mod.rs:143).
5. *Switching the ACL on breaks existing tests.* Mostly refuted. All app-command tests over `mock_context(noop_assets())` (settings_ipc, autostart, diag, local_models `world`, settings_window, tray, lifecycle, crash, single_instance, overlay) keep running unchecked. The release-context tests that call app commands are `local_models.rs::local_model_commands_pass_the_real_acl_from_the_settings_window` (label `settings`) and `overlay_ipc.rs::overlay_ready_*` (label `overlay`). They pass only if the permission files grant exactly those labels, so they already pin the allow side. `REMOVE_UNUSED_COMMANDS` is unset (tauri-utils acl/build.rs:399-406), so `generate_handler!` drops no command (tauri-macros handler.rs:92-110).

**Root cause** (one mechanism, explains the whole finding): see `analysis.root_cause`. It is a configuration gap at one seam (tauri's ACL inputs), not code on many paths.

**Mechanics of the fix (from the pinned sources).**
- Default glob without `AppManifest`: `permissions/**/*`, `.toml` or `.json` (tauri-build acl.rs:304-327; tauri-utils acl/build.rs:36). A `[[permission]]` with `identifier = "settings-window"` and `commands.allow = [...]` is an app permission. A capability names it without a prefix (key `__app-acl__`, tauri-utils acl/resolved.rs:406). An identifier is lowercase alphanumerics with one `-` separator chain (acl/identifier.rs:157-200). Do not define a `[default]` set: none is needed, and it would be one more name to grant by mistake.
- An unknown permission named in a capability fails the build (`validate_capabilities`, tauri-build acl.rs:347-400). A typo is therefore a Windows CI build failure, not a silent pass.
- With the manifest present, a command that no capability allows is rejected. In debug builds the message is `resolve_access_message` (authority.rs:315-420: "... not allowed on window ..." or "... not allowed ... Command not found"); in release builds it is "Command X not allowed by ACL" (webview/mod.rs:2101-2104). Both contain "not allowed", the predicate `is_acl_refusal` already uses (settings_window.rs).
- `build.rs` emits `rerun-if-changed=permissions` once the directory exists (acl.rs:305-309). `src-tauri/gen/schemas` is gitignored; regenerated schemas are not part of the diff.

**Invariant / seam:** see the analysis block. Decided per window, not per command prefix: the owner of a command is the window whose page invokes it.

**Options.**
- **A (recommended): hand-written permission files, one per window.** `src-tauri/permissions/settings-window.toml` allows the ten settings-page commands; `src-tauri/permissions/overlay-window.toml` allows `overlay_ready`. Add `"settings-window"` to `capabilities/default.json` and `"overlay-window"` to `capabilities/overlay.json`. `build.rs`, `Cargo.toml` and `lib.rs` stay unchanged. Why it removes the cause: a non-empty app manifest turns on tauri's default-deny for all app commands, and the capability gives each window exactly its own commands. Risk: a missed command is refused in the shipped app. The UI e2e tests mock IPC and would not see it; only test (3) below and the install smoke's window would. Rollback: delete `permissions/` and the two capability entries.
- **B: `tauri_build::try_build(Attributes::new().app_manifest(AppManifest::new().commands(&[...])))`** plus eleven `allow-<cmd>` entries split over the two capabilities. Same enforcement. Cost: tauri-build writes `src-tauri/permissions/autogenerated/*.toml` into the source tree on every build (acl.rs:281-287), files that must be committed or ignored. It also adds a third list (build.rs) next to `generate_handler!` and the capabilities, and changes `build.rs`, which T-035 / F-002 keep minimal.
- **C: A plus a `make check` literal guard.** The `generate_handler![...]` block in `lib.rs` is byte-identical to an owned fragment (e.g. `scripts/ci/app-commands.txt`, which the ACL test also reads, as `helper-windows.txt` is read by tests and a tripwire). Under P-020 it decides on `literal`. It makes every new command touch the owned list, but it closes only the fail-closed drift (a command refused everywhere), which tauri already makes safe. It also adds one more pair to edit together. Not recommended now.

**Red tests (Windows CI only; `src-tauri/tests/app_acl.rs`, a new file over `voicen_lib::build_app(mock_builder(), generate_context!(test = true), ...)` and `get_ipc_response`; the invoke URL is the window's own `url()`, as `local_models.rs::invoke_at` does, so the origin is Local):**
1. `a_registered_command_without_a_permission_is_refused_from_the_settings_window`: the failure branch of Acceptance 2. A test-only `#[tauri::command] fn probe()` is registered with `mock_builder().invoke_handler(generate_handler![probe])` on the release context and invoked from label `settings`. Expect an ACL refusal. Red today (returns `Ok`). Bite: the app manifest removed (no `permissions/` file, or `build.rs` given an empty `AppManifest`), which re-opens every app command at once. This pins tauri's own switch (`has_app_acl`); no text guard has to model `lib.rs`.
2. `every_app_command_is_refused_from_every_label_but_its_window`: a literal table of the 11 commands with their owner label, crossed with labels `settings`, `overlay`, `other`. Every non-owner cell must be an ACL refusal (30 cells, all red today). Windows are built with `WebviewWindowBuilder` on the label at the page's URL, or with `settings_window::open` for `settings`, as the existing harnesses do. The refusal comes before the handler, so no side effect is possible. Bite: a wildcard or extra label in a capability, the settings permission added to `overlay.json`, or a command placed in the wrong permission file.
3. Owner cells: not an ACL refusal. Commands that take arguments get malformed args (`{}`), so the handler rejects at argument decoding and nothing runs (`settings_save`, `settings_test_connection`, `local_model_download`, `local_model_cancel_download`, `local_model_delete`). The zero-argument ones are harmless (`settings_get`, `settings_speech_languages`, `settings_list_microphones` (device enumeration; the CI runner's capability facts apply, `docs/decisions/windows-ci-runner.md`), `local_models_list`, `get_build_info`, `overlay_ready`). Green today, so not a red test. It keeps a missing grant from shipping. The existing release-context allow tests stay.
Before implementing, run (1) and (2) red on `wip/T-049` (P-016), then add the files.

**What a real webview adds.** Not needed for the ACL decision: `get_ipc_response` is the same `on_message` path. The install smoke (release `run()`, real WebView2, `generate_context!()`) shows a visible `Voicen` window, but not that `settings_get` succeeded. A page whose `settings_get` is refused still shows a window. So the smoke does not prove the allow side; test (3) does. If the orchestrator wants a release-binary proof, an option is a smoke assertion on a log line the settings page causes (for example the save line). That is a separate, larger change. Not recommended here.

**Windows-only.** Everything in this task lives in `src-tauri` (permission files, capabilities, tests). The Linux gate (`make check`) neither builds nor reads them. The proof is the Windows job's `cargo test -p voicen --no-fail-fast` (ci.yml:138) on `wip/T-049`. Locally only docs can be checked; no `scripts/tw-run core` step applies (core is unchanged). If anything is built locally for another reason: cargo `-j2`, one heavy gate at a time.

**Docs to update in the same commit (P-014):** `docs/decisions/model-download.md` › "App commands are not ACL-checked from local origins" (superseded: replace it with the per-window invariant, or move it to `docs/decisions/windows-shell.md`); `docs/decisions/settings-ui.md` S1 ("exactly `core:event:allow-listen` ..." gains `settings-window`; the Don't list gains "grant an app permission to another label"); `docs/decisions/overlay.md` (overlay capability gains `overlay-window`); `specs/004-settings-and-first-run/contracts/ipc.md` line "the app commands above are not ACL-checked"; `docs/architecture.md` rows "Settings window and startup" and `overlay_payload` (capability contents); the descriptions in both capability JSON files; the comment in `local_models.rs::local_model_commands_pass_the_real_acl_from_the_settings_window` (it says app commands are not checked). A `docs/decisions.md` row recording the command→label table (it extends #45 and closes #57's follow-up).

**Size / decisions.** Small: one seam (tauri ACL inputs in `src-tauri`), behaviour settled by the task for 9 of 11 commands. Agent-level choices for the orchestrator (decision #45 precedent, no owner-facing behaviour): (Q1) `get_build_info` → `settings` only (its only live caller is About; the root page `/` is loaded by no window, and leaving `/` unable to show build info is harmless); (Q2) `overlay_ready` → `overlay` only; (Q3) option A over B/C. No owner decision needed.

**Recommended exit / next step:** option A; red tests (1) and (2) first.
