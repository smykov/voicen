## Context

Found in the T-044 analysis (decision #57): tauri 2.12.1 checks app (`#[tauri::command]`) invocations against capabilities only when the app defines permissions (webview/mod.rs:2076-2084; tauri-build 2.7.1 acl.rs:412-421). Voicen defines none (`tauri_build::build()`, no `src-tauri/permissions/`), so every app command (`settings_get`, `settings_save`, `settings_speech_languages`, the T-044 `local_models_*`) is callable from any local webview; decision #45's least-privilege limit to the `settings` label covers plugin commands (event, window) only. Today there is one webview, so the exposure is theoretical; the overlay (T-006) adds a second. Define app permissions (tauri-build `AppManifest` / `permissions/`) so only the `settings` window may invoke the settings and local-model commands, and pin it with an ACL test from another label.

## Acceptance

- [ ] Windows CI: `settings_get`, `settings_save` and `local_models_*` invoked from the `settings` window pass the real ACL; invoked from a window with another label they are refused
- [ ] Failure branch: a new app command without a permission entry is refused (or the build fails) — test or guard
- [ ] Test that fails without the change: `src-tauri/tests/*.rs` ACL test over `generate_context!(test = true)` (Windows CI)

## Investigation

Tools: Serena was not connected in this session, so I used grep and file reads. Context7 was not needed: the tauri crates were read directly from the vendored sources pinned by Cargo.lock, in `.teamwright/cache/core/_usr_local_cargo_registry/src/*/` (tauri-2.12.1, tauri-build-2.7.1, tauri-utils-2.10.1, tauri-codegen-2.7.1, tauri-macros-2.7.1). Nothing was built.

**Frame.** Observed: any local webview, whatever its label, can invoke every app command. Expected: only the window whose page uses a command may invoke it. It reproduces by reading the code paths below. No test exercises it yet, because the only release-context invoke of an app command (`local_models.rs::local_model_commands_pass_the_real_acl_from_the_settings_window`) comes from the right label.

**Hypotheses.**
1. *No app manifest → app commands unchecked.* Confirmed (evidence in front matter).
2. *A second path reaches commands outside the ACL.* Refuted. Commands are reachable only through `Webview::on_message` (webview/mod.rs:2005-2167). The ACL check there (:2080) runs before both the plugin handler and the app invoke handler (:2165). The only exemption is the channel-fetch command (`FETCH_CHANNEL_DATA_COMMAND`, :2082), which is not ours. A remote origin is already refused (:2080, `!is_local`).
3. *Fixed before / recurrence.* No. Decision #45 (T-037, T-057) scoped plugin commands; T-044 found this gap and decision #57 deferred it here. It is not a recurrence.
4. *`AppManifest::commands` alone restricts per label.* Refuted. It only creates permissions; it grants nothing. After it, every app command is refused from every window until a capability grants `allow-<cmd>` (authority.rs:462-488). So the capability files must change in the same commit, or the app breaks on Windows only.
5. *The build catches a command missing from the manifest.* Refuted. `generate_handler!` does not consult the ACL. Only a capability naming a permission that does not exist fails the build: `validate_capabilities`, tauri-build acl.rs:340-398, which also runs under Linux `make check-shell-windows` (`cargo check` runs build.rs). A forgotten command is refused at runtime (fail-closed), and shows only on Windows → T4 and the optional T5.

**How tauri does it (cited).**
- Defining app permissions: `tauri_build::try_build(Attributes::new().app_manifest(AppManifest::new().commands(&[..])))` (tauri-build lib.rs:44-49 doc, :553, :653; `build()` = `try_build(Attributes::default())`, :634-647). `commands` takes `&'static [&'static str]` (acl.rs:104), so a `const APP_COMMANDS: [&str; 11]` in build.rs works. The list is written as `./permissions/autogenerated/<cmd>.toml` with `allow-<cmd with _→->` / `deny-..` (tauri-utils acl/build.rs:289-317; tauri-build acl.rs:278-293). The build script's cwd is `src-tauri`, so the files land in the source tree; gitignore them like `/src-tauri/gen/schemas`. A stale file for a removed command stays local only. Files under `src-tauri/permissions/**` are also read (acl.rs:296-332); a duplicate id overwrites (tauri-utils acl/manifest.rs:85-88).
- Capabilities reference app permissions without a prefix (`"allow-settings-get"`). A prefixless id resolves to the `__app__` key (tauri-utils acl/resolved.rs:406; tauri-build acl.rs:360).
- Refusal: `resolve_access` (authority.rs:462-488) matches the window or webview label and the origin. A deny entry ignores labels (authority.rs:440-460), so no `deny-*`.
- Test path: `generate_context!(test = true)` embeds the OUT_DIR ACL and capabilities that build.rs wrote (tauri-codegen context.rs:377-410). `get_ipc_response` goes through `on_message`, so the real ACL decides. The existing pattern is `overlay_ipc.rs` (`release_context`, `invoke`, `is_acl_refusal` = contains "not allowed"; debug build text from authority.rs:315-420). Tests built on `mock_context` keep `Resolved::default()` (test/mod.rs:143) and stay unchecked; those files need no change.

- Capability set narrower than tauri's: the guard globs `capabilities/*.json` (:162); tauri-build parses `./capabilities/**/*` (tauri-build acl.rs:449) with extensions json, toml (json5 with a feature) (tauri-utils acl/build.rs:41-47, :204-215). Inline capabilities are not in tauri's `capabilities.json` output either (acl.rs:462 saves `capabilities_from_files`), so this half must be a token rule on the tree.
- Fact correction (also in `root_cause`/`evidence`): the app ACL key is `__app-acl__` (tauri-utils acl/mod.rs:50, :351-354); `__app__` is only the permission package name (tauri-build acl.rs:276).
