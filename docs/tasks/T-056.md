## Context

Owner decision #63: try a Linux-side type check of the Windows shell so compile errors are caught before a push (each Windows CI round costs ~25 min). Spike: can `src-tauri` (tauri 2.12.1, windows 0.62, aws-lc-rs via rustls) pass `cargo check --target x86_64-pc-windows-gnu` in the voicen-rust image with mingw-w64 and the target installed (image change in docker/rust.Dockerfile, `make core-image`)? It needs a built frontend (`pnpm build`) for tauri's context macro. If it works, add a `check-shell-windows` target to `make check`; if not, record why (docs/decisions/ci-toolchain.md) and close. Follow F-001/F-002 rules (shell tests and doctests).

## Acceptance

- [ ] `make check` runs a Windows-target type check of src-tauri on Linux and it passes on the current code, or the task records with evidence why it cannot (and the gate is unchanged)
- [ ] Failure branch: a deliberate type error in src-tauri/src makes the new step fail locally (shown once, reverted)
- [ ] Test that fails without the change: the new make target (or the recorded spike result)

## Investigation

Investigator, 2026-10-04, on HEAD 68ade03. Every result below was run and observed in this session. Nothing in the main tree, its `target/`, its `.teamwright/cache/` or the `voicen-rust:1.99` image was changed.

### Frame

- **Observed:** `make check` builds no part of `src-tauri`. `check-core` runs cargo with `-p voicen-core` only. On Linux the shell cannot even be checked for the host target: `lib.rs:87-129` makes every `release_*` fn a `compile_error!` under `cfg(not(windows))`. `tests/credentials.rs:9` and `tests/autostart.rs:11` are `#![cfg(windows)]`, and the Windows-only parts of `tests/local_models.rs` and `tests/settings_ipc.rs` sit under `#[cfg(windows)]`. A compile error in shell code therefore first shows in the windows job, after review. In run 37223044944 the gate job took 5m40s (image 2m10s, `make check` 2m41s), and the windows job then took 7m02s.
- **Asked (decision #63):** can the shell pass `cargo check --target x86_64-pc-windows-gnu` in the core image with mingw-w64 and the target added? If yes, add a `check-shell-windows` step to `make check`.

### Need, invariant, seam

See the `analysis` block. The gnu target is a different toolchain from the shipped msvc one, so the check covers **types only**:
- The gnu build-script output has none of the msvc link configuration. Its only link line is `rustc-link-arg-bins=…resource.lib`: no static-VC-runtime search dir, no `/NODEFAULTLIB`, and the msvc-only `embed_manifest_for_tests()` returns early.
- So F-001/F-002-class link and start failures stay with the windows job, and a gnu link or test build would not be a proxy for them.
- No shell source or test uses `target_env`, so the gnu and msvc checks see the same Rust code.
- Possible false red: a future dependency that cannot build for gnu. That would show as a red `check-shell-windows` with a green windows job, and would need a decision, not a workaround.

### Approach (exact lines for the developer)

**Recommended exit: (a)-style code change**, gate extension per decision #63. This is not an rca task.

`docker/rust.Dockerfile`, first `RUN` (proven package in P-slim; the full `gcc-mingw-w64-x86-64` meta package also works, P2, at about 180 MB more):

```dockerfile
# gcc-mingw-w64-x86-64-win32 (x86_64-w64-mingw32-gcc; its binutils bring -windres) and the
# x86_64-pc-windows-gnu std: make check-shell-windows type-checks src-tauri for Windows on Linux
# (T-056, decisions #63). Even under cargo check, aws-lc-sys's build script compiles aws-lc with
# it, and tauri-build compiles the app resource with windres. Nothing is linked.
RUN apt-get update \
 && apt-get install -y --no-install-recommends cmake clang libclang-dev gcc-mingw-w64-x86-64-win32 \
 && rm -rf /var/lib/apt/lists/* \
 && rustup component add rustfmt clippy \
 && rustup target add x86_64-pc-windows-gnu
```

The target must be in the image. In CI, tw-run runs as the runner uid, and adding the target at run time would download 138 MB on every run. The installed files are world-readable (checked).

`Makefile`: add `check-shell-windows` to `.PHONY` and to `check:` (after `check-core`):

```make
# Windows-target type check of the shell on Linux (T-056, decisions #63; docs/decisions/ci-toolchain.md):
# lib + bin with the release features, then the test crates (every src-tauri/tests/*.rs and the
# lib/bin unit-test crates) with the dev-dependency features; --tests alone would check the lib
# with test-fakes on. cargo check never links and builds no doctest: linking stays the windows job's.
check-shell-windows:
	scripts/tw-run core -- 'cargo check -p voicen --target x86_64-pc-windows-gnu && cargo check -p voicen --target x86_64-pc-windows-gnu --tests'
```

Optional and not proven here: a preflight that prints "run make core-image" when `rustup target list --installed` lacks the target, instead of the bare E0463 from P0.

**Time budget.** No time budget for `make check` is written down (searched PRINCIPLES.md, AGENTS.md, docs/process, docs/decisions.md, docs/architecture.md).
- Locally (warm `target/`): about 10 s more per `make check`, plus a one-time cold build of 3.5-6 min after the image change. `target/` grows by about 2 GB (the probe target dir was 2.0 GB).
- CI gate job: about 30 s more for the image build (56 MB of debs, 138 MB rust-std), plus one cold check per run, because the gate does not cache `target/`. On this 6-core host the cold check took 214 s (52 + 162) and 372 s at load 14-16.
- The GitHub runner was not measured. The first CI run after the change gives the real number; record it in the verify record.
- A `target/` cache in the gate job is an optional follow-up, not needed for correctness.

**Must not be added or scanned (F-001..F-003):**
- no `cargo test`, `--no-run`, `cargo build` or link step for gnu;
- no `--doc` and no `rustdoc` anywhere: `check` builds no doctests, and the raw scan of `.github/workflows` must stay clean, which needs no ci.yml change;
- no `#[cfg(test)]` in `src-tauri/src`;
- the target does not touch the shell-test-layout check;
- do not use the new ability to expand the shell for Windows to bring back a rustdoc-based doc scan (F-003; decisions/ci-toolchain.md Rejected approaches). The rustdoc row there gives "needs webkit2gtk the gate never builds" as one reason; that premise goes stale, but the row's other reasons (unstable JSON extraction, protects only doc style, the F-003 rule) still stand. Say so when updating the file.
- tauri-build writes `src-tauri/gen/schemas/*.json` during the check (gitignored, `/src-tauri/gen/schemas`).

**Option B** (orchestrator or owner): replace `cargo check` with `cargo clippy … -- -D warnings` (both invocations) and add `cargo fmt --check -p voicen`. This is a superset of the type check, clean today (exit 0, +11 s / +8 s warm). It brings the shell under the core area's stated lint convention, but goes beyond #63.

**Rejected:**
- `--tests` alone or `--all-targets`: P-F3 shows they pass a release-only error.
- A gnu link or test build: no msvc link configuration, so it is not an F-001/F-002 proxy.
- cargo-xwin for the msvc target: downloads the MSVC CRT and Windows SDK under Microsoft's license terms, and is not needed for a type check.
