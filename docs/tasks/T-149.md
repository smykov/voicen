## Context

US6 (device changes), US6 #1–#7. Spec FR-006, FR-010, FR-012, FR-013; research R4, R21. Area core, seams `crates/voicen-core/src/call/session.rs` / `capture.rs`, with a fake `DeviceEvents` stream and the fake clock. Needs the session (T-126).

## Acceptance

- [ ] A default-output change reopens the system track on the new default; a gap of at most 2 s is filled with silence and recorded in `device_changes` and `call_device … gap_ms=` (T068, T069)
- [ ] Mic loss reopens on the default input with `mic_changed`; the call is not stopped (T068)
- [ ] Failure branch: a track not reopened within 2 s, or with no device left, records silence from then on, warns `track_lost`, logs `call_track_silent rule=lost` and retries every 2 s (T068)
- [ ] `CommunicationsCheck::differs` at start gives `communications_device_differs`; `E_NOTFOUND` counts as no difference (T068)
- [ ] More than 60 s of system silence while the mic has speech gives `cant_hear_other_party`, the mirror case `cant_hear_you`; each fires once per stretch and re-arms after speech (T068)
- [ ] Warnings stay until dismissed; a dismissed kind re-arms on its next trigger (T068)
- [ ] Test that fails without the change: the device-event tests of `call/session.rs` / `capture.rs`

## Investigation

Analysed on main at 2bf6e415. Tools: Serena `get_symbols_overview` on `call/session.rs` and `call/capture.rs`, then direct reads of the bodies; grep over `crates/`, `src-tauri/`, `specs/007-call-mode-record/` and `docs/` for `DeviceEvents`, `CommunicationsCheck`, `advance_to`, `track_lost`, `cant_hear`, `gap_ms`, `E_NOTFOUND`. Context7 was not used: this task adds no new library call (`EnergyDetector`, `Timeline` and the diag grammar are all in-repo).

**Frame.** Observed: after start, a lost track (`TrackEvent::Lost`) only stops getting samples. Nothing reopens it, warns, logs or writes to `meta.json`, and the track no longer grows. Expected (FR-012, US6 #2–#4): reopen within 2 s, silence-filled gaps, `call_device` and `device_changes`, and track_lost with retries otherwise. FR-010 (comms check) and FR-013 (can't-hear) are placeholders today (`comms_differs=false`, `*_silent=false`).

**Hypotheses checked.**
1. *Already partly built on a second path?* No. The only loss handling is `step_of` → `Timeline::lost`. No other caller opens a track after start (Serena overview: `open_tracks` and `open_mic` are called only from `open_call` and `toggle_subtitles`).
2. *Grammar, schema or i18n missing?* No. `CallDeviceChanged`, `CallTrackSilent`, `DeviceCause` (6), `SilentRule`, `DeviceChange`, the `CallWarning` variants, `WarningKind` and the warning ids all exist (T-118, T-119, T-125). So this task changes no log, schema or catalog.
3. *Can the reopen go where the existing threads are?* No. `OPEN_BUDGET` = 3 s (`src-tauri/src/win/capture.rs`), which is longer than the 2 s bound. On the writer, an open blocks the other track's drain (bounded channel, so drops). Under the session lock it blocks tray and hotkey (windows-shell.md rule 2). This is why the design needs a separate device thread.
4. *Fixed before?* No class history: `docs/failures.md` has no call-devices entry. The nearest precedent is dictation's mic fallback (#108) and T-104/F-016 (non-loss cpal kinds). T-127's map already follows F-016.

**Findings that shape the design.**
- No caller of `Timeline::advance_to`: a paused loopback (no packets, #244) or a dead track leaves its file short. `duration_ms` = min of the two tracks then shrinks, and the FR-013 rule never sees 60 s of silence. R3 asks for the advance. Since T-149 owns lost and silent tracks, it is in scope.
- Under 200 ms the timeline's `Report::Gap` stays silent, so `gap_ms` of a device change comes from positions (first-sample position minus the position at the trigger), not from `Report::Gap`. The revive's own `Report::Gap` is suppressed, so one change gives one line.
- Which Windows signal shows a default-output change is open: `track_capture.rs` says both "default handle follows" and "`DeviceNotAvailable` = default changed". So core treats a `Lost` on the system track and a `DeviceEvent::DefaultOutputChanged` as the same trigger, and absorbs the second one. Core then does not depend on the answer, which is T-150's owner check.
- `CommunicationsCheck` is called under the session lock at start. T-150 must keep it bounded and on a COM-initialised thread. `DeviceEvents` comes from a factory called on the device thread, so registration lives there (R4).
- `src-tauri/tests/call_capture.rs` constructs `CallDeps`. The Linux gate does not compile it, so only the `wip/T-149` Windows CI run (P-016) proves the added fields.
- Toasts for warnings (FR-006 "and as a toast") need T-007's notifier: out of scope here, as in T-144.

**Developer choices to record in `docs/decisions/call-session.md`:** a mic-default change shows `MicChanged` like a loss (FR-012 "loss or change … with a notice"); a comms-check `Err` other than `E_NOTFOUND` is "none" (no false warning, no log line: the grammar has none); a `TrackLost` warning stays after a later reopen (until dismissed, FR-006); FR-013 "while the other track has speech" = at least one speech second of the other track in the silent stretch (R21).

**Coordination.** `CallSession::dismiss_warning` exists only on `tw/T-130` (BLOCKED on the owner's S5 question). The recommendation is that T-149 adds it in core with the same signature (`dismiss_warning(&self, id: u32) -> bool`, under the lock, republishes), with re-arm by kind through `WarningList`; T-130 then rebases and drops its copy. T-144 also edits `session.rs` and `tests/call_session.rs`, so run it after T-149 or rebase it.

**Owner or device needed:** none for this task's acceptance (surface none, Linux fakes and fake clock). Real device switches are T-150's `verify_exception`.
