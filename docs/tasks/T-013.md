## Investigation

Tools: Serena and context7 are not connected in this session, so I used grep and file reads. Nothing was run. This analysis replaces the pre-split one of 2026-10-04 (git history, commit before ba7bb85). Decision #51 adopted that version as T-046's design, and T-046 is DONE. What is left is the UI half.

**Frame.** Spec 004 US4 asks for a "Test connection" button for the api and local_server engines.
- It uses the form values, unsaved ones included, and the stored key when the key field is untouched.
- It shows "OK, <n> ms" or the reason it failed.
- It is disabled with progress while it runs, and it saves nothing.
- A result that arrives after the window closed is discarded.
- A result refers to the values at the click and is kept when the draft changes afterwards.

Core and shell are done (T-046). The window has no call, button, result, mock command or e2e spec.

**Hypotheses.**
1. *Only the UI wiring is missing.* Confirmed: `settings_test_connection` is registered (`lib.rs:47`), and no TS file names it.
2. *A second path for the same concern.* This is a risk in three places. Each one gets a single site:
   - the request: `draft.testRequest`, next to `saveRequest`. Same key edits, no trim and no validation in the UI, because core does `normalize`, `key_step` and `validate`;
   - the message mapping: one switch in `connectionTest.ts`;
   - field errors: `errorsByField`, the U2 path.

   A UI-side URL or key check before the call would copy core's rules, which U1 and #38 reject.
3. *State in `Engine.svelte`, as #51 literally places it.* Refuted as the owner of the state. `+page.svelte:299-311` mounts only the selected tab, so the test state would be lost on a tab round trip. The button would come back enabled while the shell still runs the first test, which breaks `ipc.md:12`. #51's "discarded on close/unmount" is kept, applied to the page. The button and the result still render in `Engine.svelte`.
4. *Kind → text needs core message ids.* Not needed. T-046 review 1 accepted kinds without ids, and the existing `failure.*` texts cover every kind except ok and invalid. A closed TS switch with literal `MessageId`s is type-checked by svelte-check, so it is not a third `as MessageId` cast (i18n.md). Its completeness has two checks: the vitest test over the core-pinned fixture, and the recommended exhaustive `match` in the core pin.
5. *This class was fixed before.* No. There is no F-entry for the connection test or for settings-ui, so recurrence is none. Related invariants exist: D (close only through destroy), "No edit is lost to an in-flight save" (the run must not replace the draft) and U3 (the key typed for a test stays a `Replace` in the draft, is never shown, and is never sent as `{Replace: ""}`, because `resetKey` covers an emptied field).

**Details for the developer.**
- `MessageArgs` are strings (`i18n/index.ts:28`), so `latency_ms` and `status` go through `String(...)`.
- The en texts: `settings.test_connection.button` "Test connection", `running` "Testing…", `ok` "OK, {ms} ms", `invalid` "Check the highlighted fields". The same ids with Russian text go into ru.json.
- "HTTP {status}" (T053) reuses `failure.server_error` ("Server error (HTTP {status})"); no new id.
- A click clears the previous result. A save while a test runs is allowed. The fieldset disables the button during a save because the button sits inside it.
- The request is built at the click, so later edits do not change it.
- `invalid`: `draft = applyTestErrors(draft, errors)` highlights the fields on their tab. The result region shows `settings.test_connection.invalid` and lists by label (`fieldLabelId`) every field with no control on the page. The `timeouts.connect` → General case is a vitest case on the pure part, because the fixture's only `invalid` sample is `engine.api.base_url url.malformed` and e2e uses no hand-written results.
- Close paths that advance the generation:
  - `onClose` when not prevented (clean draft: tauri destroys the window);
  - `discard()` before `destroyWindow`;
  - the `onMount` cleanup.

  Keep editing leaves the run alive. If `destroyWindow` fails, the result stays discarded and `ipcFailed` shows as today.
- The UI logs nothing. The mock records the request, including a fake key. Test data uses obvious fake keys only.

**Non-blocking choices (orchestrator; defaults proposed, no owner decision).**
- (i) `applyTestErrors` replaces `draft.errors`, the same way the next save outcome replaces them, and keeps `formError`. The alternative is to keep test errors outside the Draft, as warnings are, but then they do not drive `aria-invalid`. Default: replace.
- (ii) The engine is switched while a result is shown, for example from api to local_server. Default: per #51 and edge case 148, keep the result shown until the next click. The alternative is to show it only while the selected engine equals the tested one.
- (iii) The exhaustive `match` in core's fixture pin. Default: include it in this task; it is test-only. The alternative is a follow-up task.

**Open questions for the owner.** None. US4, its edge cases, FR-017 and #51 settle the behaviour. OQ-06 (the clip) was closed by #59 in T-046.
