## Investigation

Investigator, 2026-11-07. Serena was used for core symbols (`overlay.rs`, `call/session.rs`). The Serena index answered for Rust core; shell files were read with grep and sed. Pinned sources were read from the core image's cargo cache (`.teamwright/cache/core/_usr_local_cargo_registry/...`): tauri 2.12.1, tao 0.37.1, wry 0.57.0, tauri-runtime-wry 2.12.1. Context7 has only the generic v2 tauri docs, so the drag permission was confirmed against the pinned `drag.js`.

**Frame.** This is a feature, not a defect. FR-005 needs an interactive, movable, topmost window that never takes the focus from the call app (the user is talking in Zoom or Telegram; a stolen focus loses their keystrokes). Today the core publishes indicator state into a port that nothing in the shell implements.

**Hypotheses / what is open**
1. *ADR-007 primary (WS_EX_NOACTIVATE) gives clicks and drag without activation on WebView2.* Confirm: spike rows 3 and 4 green under variant N. Refute: the target loses the foreground at the click (WebView2's browser-process child calls SetFocus or activates), or the HTCAPTION move loop activates or does not move the window. No evidence either way on this machine; Windows CI only.
2. *A second webview adds a top-level helper window.* Unlikely. tao's event-target window is per event loop. single-instance is not registered in tests. WebView2 adds child windows. `helper-windows.txt` is keyed by crate@version, and T-130 adds no crate or feature (`windows` is a `binding` entry, and all needed Win32 features are present). The spike's census before/after is the proof; if it finds a new class, the task becomes `checker: true` per its Context.
3. *A second path handles the same concern.* Yes: the dictation overlay (`src-tauri/src/overlay.rs`, overlay.md invariants 1-4) solves the same build/show/destroy race and the same non-activating show. The indicator must follow the same rules, not a parallel variant. Hence the shared `OverlayLifecycle` reducer and the same "built hidden, one raw SW_SHOWNOACTIVATE, no tao setter afterwards" rule. A tao setter on a raw-shown window would diff the flags and `SW_HIDE` it or `SW_SHOW` it (overlay.md §3, tao `window_state.rs:405-467`). This also forbids tauri `set_position` for the clamp: the position goes into the builder, and every later move is a raw `SetWindowPos(SWP_NOACTIVATE)`.
4. *This class was fixed before.* No `docs/failures.md` entry of class `overlay`. F-003 and F-008 (smoke predicate) apply to the census: the indicator is a product window and is never listed as a helper (R12, overlay.md §5).

**Spec inconsistencies found (resolved without the owner, by #235 and NFR-03):**
- ADR-007 (owner-accepted, "its text stands", #235) makes WS_EX_NOACTIVATE the primary and "topmost window that returns focus" the fallback. R12 and T032's "focusable" describe that fallback as the primary. The spike tries the ADR order. The developer corrects R12 to the variant the spike proves, and the acceptance line "focusable" is read as "takes clicks".
- contracts/ipc.md and R12 say "hidden at stop, shown at each Record start", which keeps a WebView2 alive after the first call. NFR-03 says webviews are "created on demand and destroyed when closed". The requirement wins: destroy at stop, rebuild at the next start (overlay pattern), and ipc.md is updated in the same commit. **Conditional owner question:** if the spike measures a build-to-shown time over 1 s (US1 #1 "within ≤ 1 s the indicator shows"), NFR-03 and US1 #1 conflict, and the owner chooses (keep hidden / accept the latency / pre-build at the first Record). Not opened as an OQ now, because no evidence says the conflict exists.

**What the spike must prove in Windows CI** (each row a test in `src-tauri/tests/call_indicator.rs`, on the real Wry runtime, serialised, with the overlay harness):
| Row | Fact (raw Win32, F-003) | How |
|---|---|---|
| S1 | No `call-indicator` window after `build_app`, or before the first `recording=true` state | `get_webview_window(LABEL)` is None and the census is unchanged after build |
| S2 | Shape: TOPMOST, TOOLWINDOW, no APPWINDOW, undecorated (no WS_CAPTION), unowned top-level; NOACTIVATE in variant N | `GWL_EXSTYLE`/`GWL_STYLE`, `GetWindow(GW_OWNER)`; stable for SETTLE |
| S3 | Show keeps the foreground | `TestWindow` target in front (`bring_to_front` precondition), `ForegroundSampler` every 5 ms across show; no focus-loss message on the target |
| S4 | A click reaches the page and keeps (N) or gets back (F) the foreground | SendInput click at the centre; the test page turns a pixel on mousedown (`screen_pixel`); the sampler shows target-only (N), or the target again within budget (F) |
| S5 | Drag moves it | SendInput down/move/up on the page's `data-tauri-drag-region`; `GetWindowRect` moved; foreground as in S4. Needs the real capability (`core:window:allow-start-dragging`) in the test context. If the harness cannot carry it, S5 is the owner's check only, and this is recorded |
| S6 | Census | all top-level windows of the process (visible or not, with class) before the build and after the show: the difference is exactly the indicator HWND |
| S7 | Fallback stop | if S3-S5 fail in both N and F: the test stays red, and the evidence plus the native-window question go to the owner (#235) |
| S8 | Build-to-shown time | logged by the test (not asserted); feeds the conditional question above |
Topmost above a full-screen app and real dragging on a real desktop remain the owner's check (verify_exception, T-159).

**Recommended approach:** see `analysis.approach`. The core pieces (`dismiss_warning`, `remember_indicator_position`, `clamp_to_monitors`, the generalised reducer) are small and have Linux tests. If the orchestrator wants them separate from the Windows-only spike, they split cleanly into a sibling core task that lands first. T-149 later extends `dismiss_warning` with re-arm by kind (G35); T-130 only removes by id.

**Areas:** shell (main), core (session, indicator, settings, overlay reducer), docs.

**Risks**
- WebView2 may activate its host on click even with WS_EX_NOACTIVATE; that is the spike's subject.
- With NOACTIVATE some Windows builds move the window only at the end of a drag (no live move); this is acceptable, but the owner should note it.
- SetForegroundWindow in variant F is refused if our process is not foreground at that moment; restore inside the command, right after the click.
- The 10 Hz tick emit adds IPC load during a long call; the thread coalesces to the newest tick.
- `IndicatorControl` stays unset until T-128 wires the session: the commands return `null` and do nothing (tested), so the order T-130 before T-128 is safe.
- The overlay reducer change touches a pinned overlay path. Its existing `lifecycle_tests` and `overlay.rs` must stay green unchanged.
