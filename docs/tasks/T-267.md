## Investigation

Context: Serena (`get_symbols_overview` on `src-tauri/src/call_indicator.rs`) plus file reads and grep of `src-tauri/tests/call_indicator.rs`, `src-tauri/tests/overlay.rs`, `src-tauri/tests/timing_support/mod.rs`; CI logs via `gh run view <id> --log-failed`. No Windows run made here (shell tests are Windows CI only); no library API is relied on beyond what the code already calls, so no Context7 lookup.

**Frame.** Observed: in 2 Windows CI runs on unrelated branches, S4 panics at its first pixel premise with `Some((255, 255, 255))`; the rest of the binary (s5, which builds the same page the same way, included) passes. Expected: the indicator's page (PAGE_RGB `(32,160,64)`) is on screen before the click. Reproduces only on the hosted runner, intermittently.

**Hypotheses.**
1. *The premise samples the screen once, before WebView2 composed the first frame* (most likely). Confirms: `before = screen_pixel(at)` has no wait; the receipt (163 ms, 617 ms) is below `PAGE_LOAD_WAIT`, so the show followed `PageLoadEvent::Finished`, and still the screen was white; overlay.rs's equivalent check polls and is stable. Refutes would be: a white pixel that stays white (s5 on the same page in the same exe passes; T-130's green runs pass S4). **Confirmed as far as the logs allow**; what is missing is a pixel trace over time from a failing run (the test records one sample only).
2. *The dev_url defect is back (WebView2 error page, white).* Refuted: `wry_rig` still sets `context.config_mut().build.dev_url = None` before `set_assets`; that defect was deterministic (T-130 round 1, run 44414670702: S4, S5, S7 red together), while here s5/s7 pass in the same exe.
3. *Another window covers the centre (a white window above the indicator).* Refuted: the hit premise (`hit_root(at)` equals the indicator) is asserted before the pixel one and passed in both runs.
4. *The page load wait timed out (2 s) and the window was shown before load.* Refuted for both runs: the whole receipt took 163 ms / 617 ms, below the 2 s bound, so `Shared::wait_loaded` returned on Finished.
5. *Second path / fixed before.* Second path: the only other pixel reads in src-tauri/tests are overlay.rs's, already an `eventually` poll; S4's post-click `painted` is a poll too. The single `before` sample is the one site. Fixed before: T-130 round 1 had the same message from another mechanism (dev_url, an error page), fixed in 79a693c5; after it the premise stayed a single sample, so it now fails only when the first paint is late.

**Root cause.** S4 takes its "page painted" premise as one screen sample right after the shell's receipt, and the receipt guarantees load-finished-and-shown, not composed-on-screen; a slow first composition on the runner leaves the sample white.

**Recurrence check.** `docs/failures.md`: no class `flaky-timing-test` in the Classes table; no F-entry for S4 or for a pixel/paint premise. Closest rows and why they differ: `os-answer-deadline-race` (F-005, F-013, F-019, F-021: a verdict races a clock ceiling; here there is no ceiling, there is no wait at all), F-014 (`windows-synthetic-input-timing` candidate: a SendInput hold ending early; other mechanism), `test-event-subscribed-after-trigger` (F-018; shape "observe after the effect", but an event listener, not a screen read). Sibling T-266 (same task class) has another mechanism: a sample count tied to wall-clock pumping in call_dictation.rs. timing_support's rule ("a positive wait is `eventually`") is what S4 skipped by not waiting; no guard can see a missing wait. `docs/decisions/windows-shell.md` › "A real-Wry shell test of the call indicator clears build.dev_url…" covers the T-130 defect only. So: no recurrence of a logged class; first sighting of this mechanism. Suggest the orchestrator logs an F-entry (symptom: the two runs; cause: single-sample screen premise after a shown-not-painted receipt; rule: the invariant above, T1 review-only) and, optionally, adds the "receipt = shown, not painted; screen facts are polled" line to that windows-shell.md section in the fix commit.

**Seam and approach.** See `analysis`. Notes for the developer:
- Bound: with the poll, a never-painting page waits `HANG` (120 s); the click, the `painted` and `regained` waits must be skipped then (return early), otherwise the driver can run 3 × 120 s and the 240 s watchdog ends the exe with code 3 instead of the premise message.
- `wry_rig`'s comment "Bite: with the line removed s4 sees a white pixel" stays true, but that bite now fails after HANG instead of at once; update the comment.
- Residual: PAGE_RGB on screen does not strictly prove the inline mousedown listener ran; the parser runs the inline script before the tiny document's first paint in practice, and if not, the post-click check fails loudly (a false red, never a false green).

**Product note (owner question).** `docs/decisions/overlay.md` (call indicator) and `IndicatorThread::build_window`'s doc say the show waits for page load "so it never shows blank". These two runs show the shown window's centre was still white on screen after Finished, so a real user may see a brief white/blank frame at the indicator's first show. Not proven for the real Svelte page (its background and timing differ). Fixing the test does not need a decision; whether the product should wait for a first-paint signal from the page (option C) or the docs should be reworded to "shown after load; the first frame may lag" is the owner's call.

**Recommended exit**: not an rca task; ordinary bug fix in the test (option A).
