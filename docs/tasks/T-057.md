**Library facts re-checked (the shell's traps).**
1. `create_window` off the main thread sends `Message::CreateWindow` and blocks on `rx.recv()` (runtime-wry `lib.rs:300-336`). On the main thread `send_user_message` runs it inline (`:263-279`). tauri documents window creation in sync commands and event handlers as a deadlock on Windows (`webview/webview_window.rs:56-59`). → build only on a thread that holds no lock and is not the main thread.
2. `destroy()` is only posted (`lib.rs:2129-2136`). The label stays in tauri's manager until `Destroyed` (`app.rs:2709-2715` → `manager/mod.rs:643-644`). A build before that fails with `WindowLabelAlreadyExists` (`manager/window.rs:70-71`). A sub-0.3 s tap then a new press gives Recording → Hidden → Recording.
3. **Order of Destroyed** (new, settles how the thread learns it): runtime-wry calls `callback(RunEvent::WindowEvent{..})` first (`lib.rs:4224-4229`). That reaches tauri's `on_event_loop_event`, which frees the label. Only then does it run the window's own `on_window_event` listeners (`:4230-4233`). So a `Destroyed` listener registered on the overlay window, which only posts "destroyed" into the mailbox, fires after the label is free. A rebuild triggered by it cannot hit the label error.
4. tao: `focusable(false)` → `WS_EX_NOACTIVATE` (`window_state.rs:293-295`). `focused(false)` sets both the window and the webview builder (`webview_window.rs:586-590`) and makes the creation show `SW_SHOWNOACTIVATE` through `MARKER_DONT_FOCUS` (`window.rs:1265`). That marker is removed at the end of creation (`:1415-1420`). After creation, any flag change on a visible window rewrites `GWL_EXSTYLE` from tao's flags (`window_state.rs:412-431`), which drops a raw `WS_EX_TOOLWINDOW`, and ends in `ShowWindow(SW_SHOW)` (`:455-467`). A setter whose flags do not change is a no-op (`:318-320`). A hidden window only gets `SW_HIDE` (`:405-409`).
5. **Last window → exit** (new): when the window map becomes empty on `Destroyed`, runtime-wry raises `ExitRequested{code:None}` and exits unless prevented (`lib.rs:4256-4270`). `on_run_event` (`src-tauri/src/lib.rs`) prevents it only while `tray_by_id(TRAY_ID)` exists. Today only the settings window triggers this. With the overlay, every Hidden with no settings window open triggers it. With a tray, nothing changes. Without one (tray build failed: `tray::install` logs and goes on), the app exits after its first dictation's Hidden. Q1 below.

**Hypotheses.**
1. *Parts already exist under other names.* True for core and the UI (above). False for the shell window, the thread, the command and the capability: grep `overlay|Overlay` over `src-tauri/{src,capabilities,tauri.conf.json}` finds only the no-op and comments.
2. *Same concern on a second path.* Three candidates:
   - (a) A second window owner. `settings_window` has its own opener thread for label `settings`. The overlay gets its own thread for label `overlay`, and no other code path creates or destroys that label. The capability grants no `destroy` to the page.
   - (b) A second state source. `overlay_ready` must read the same mailbox as the emits, never a separate copy, or the seq rule on the page breaks.
   - (c) A second exit rule. The last-window exit (fact 5) now has two triggers. The guard in `on_run_event` stays the one place that decides.
3. *The class was fixed before.* No overlay entry in `docs/failures.md` (F-001..F-005: ci-toolchain, guard-model, test-port-race, windows-refused-connect-timing). `recurrence_of: []` stands. Rules of other classes bind:
   - F-001/F-002: `src-tauri/tests/overlay.rs` only; no `#[cfg(test)]` in `src-tauri/src`; features in the one-line array.
   - F-003: the smoke predicate decides on raw facts. Counting tool windows is the fix; an "it is our overlay" exception (class/title) is not.
   - F-005: every wait (appear, Destroyed, foreground sampling) polls against a Windows-sized budget. Runner run B showed ~1 s scheduling gaps.
4. *Building visible with `focused(false)` keeps focus.* Supported by reading (fact 4). That holds only while no tao setter follows. Whether `SW_SHOW` on a `WS_EX_NOACTIVATE` window activates is not settled by reading; the CI test settles it, and invariant (3) avoids the question.
5. *One seam.* Mostly yes; see the size verdict.

**Design (recommended).**
- **Reducer (core, pure).** State: `phase` None | Live | Destroying, plus `wanted` (seq, is_hidden).
  - On a new wanted state or on Destroyed it returns the next action:
    - None and not hidden → Build;
    - Live and not hidden → Emit(seq) if seq is newer than the last emitted;
    - Live and hidden → Destroy;
    - Destroying → Nothing until Destroyed, then decide again.
  - A Build failure (Err from `build()`) moves back to None. Retry only on the next state change, never in a loop.
- **Shell thread.**
  - Loop: wait on the condvar; take the newest mailbox entry; ask the reducer; execute.
  - Build: `WebviewWindowBuilder::new(app, "overlay", WebviewUrl::App("overlay"))` with the flags in `approach`. Register `on_window_event(Destroyed → post to mailbox)`. Then `emit_to("overlay", "overlay://state", payload)`. A webview that is not listening yet catches up through `overlay_ready`.
  - `lang` = `SettingsService::snapshot().ui_language`, read on this thread.
  - Nothing about the payload is logged. A build or emit error writes a typed warning (kind + os_code only, #45). That needs a new `WarningKind`, e.g. `overlay_failed`, in core `diag`.
- **Command.** `overlay_ready` (sync is fine: it reads the mailbox only, no window call) returns `overlay_payload(mailbox state, lang, seq, now - received_at)`.
- **Capability.** `capabilities/overlay.json`: `windows: ["overlay"]`, `core:event:allow-listen`, `core:event:allow-unlisten`. `default.json` stays settings-only (guard: `another_window_label_gets_no_permission`, `settings_window.rs:930`).
