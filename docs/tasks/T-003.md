## Context

FR-13 (fields, per-engine required fields per v4), FR-21 (defaults incl. v4 additions), NFR-04 (keys only in Credential Manager), spec 004 clarifications Q1 (all-or-nothing save) and Q4 (unreadable file → backup + defaults). Pure core with fakes.

Split by decision #23: this task is the types and pure rules; `SettingsFile`, `SettingsService` (load outcomes, save transaction, `subscribe`) and their tests move to T-032. The hotkey grammar (`Hotkey`, parse/format, spec 004 T030/T039) is in this task; fakes are public behind cargo feature `test-fakes`; `DownloadedModels::list() -> Vec<String>`; new message ids go into both catalogs. The rest of this paragraph describes the seam both tasks share.

Scope after the re-plan (decisions #20–#22): this task owns the one settings/key seam that specs 001–004 share — `secrets` (`KeySlot`, `Secret`, `KeyEdit`, `KeyPresence`, `CredentialStore`), `settings` (`Settings`, `FieldId`, `defaults()`, `SettingsFile`, validation, `SettingsService` with `load_or_init` / `save` / `snapshot` / `view` / std `subscribe`, startup gate), the `HotkeyRegistrar` and `DownloadedModels` traits with fakes (implemented later by T-006 and T-016), and the `post_process::settings` data type with `STARTER_PROMPT` and its defaults (validation stays with T-020/T-021). Not here: the Credential Manager implementation and the settings IPC (T-030), the `Autostart` trait and save step (T-014), hotkey grammar/step wiring with the real registrar (T-006/T-010), the built-in model rule with the real store (T-016/T-017), wiring subscribers in the shell (T-030). `resolve_ui_language` comes from T-005. Dependencies: `serde_json`, `url`, `zeroize`, `chrono`, `thiserror` (decisions #9, #17); no `tokio` (#22).

### Frame

- **Observed:** `crates/voicen-core` contains only `build_info` (`src/lib.rs:3`). Its dependency list is `serde` with `derive` (`Cargo.toml:10`). There is no `tests/` directory. ### Hypotheses

1. **Settings code already exists in part** → refuted. `grep -rn -i "settings\|credential" crates/ src-tauri/src` finds only the `description` field of `Cargo.toml`.
2. **The same concern is handled on a second path** → **confirmed in the plans, not yet in code.**
   - Spec 001 plans its own `CredentialStore { transcription_api_key() -> Option<SecretString> }` and a `SettingsSource`/`DictationSettings` with its own defaults and JSON loader in `crates/voicen-core/src/settings.rs` (specs/001 `contracts/core-traits.md:85-99`, `tasks.md:46-47`), plus a `CredReadW` impl in `src-tauri/src/win/credentials.rs` (`tasks.md:80`).
   - Spec 003 calls the same port `SecretStore`/`Secret` (`specs/003 tasks.md:143,156`); spec 002 calls it `SecretRef` (`specs/002 tasks.md:121`).
   - Spec 004 plans `CredentialStore { read/write/delete(slot) }` and `src/settings/mod.rs`. Rust cannot have both `settings.rs` and `settings/mod.rs`.
   - If T-001 is implemented as written after T-003, there will be two defaults sources, two readers of `settings.json` and two Credential Manager impls (a P-010/P-011 violation).
3. **This class was fixed before** → refuted. `docs/failures.md` has only the placeholder row. No other task has `class: settings-persistence`. `git log -- crates/voicen-core src-tauri` shows only the skeleton commit `0afeaf3`.
4. **The spec's own serde guidance would break the defaults** → **confirmed.** data-model.md says "every field `#[serde(default)]`". In serde_derive 1.0.229 (`de.rs:765-787`), a field-level `#[serde(default)]` fills a missing field with the field type's `Default::default()`. Only a container-level `#[serde(default = "...")]` reads the value from the container's default. Taken literally, an older file without `auto_paste` would load `false`, a file without `history.size` would load `0` (invalid), and a file without `api.base_url` would load `""`. Each nested struct (`api`, `local_server`, `history`, `post_processing`) needs a container default that comes from the one `defaults()`. Unknown fields are ignored unless `deny_unknown_fields` is set (`de/struct_.rs:285-289`), as R-2 wants.
5. **The shell part of 004 Phase 2 is owned by another task** → refuted. No `docs/tasks/*.md` mentions `credentials.rs`, `settings_ipc`, `CredWrite` or spec T016/T017. T-004 is UI with mocked IPC; T-006 is the 001 dictation shell.

### Approach

**Option A (recommended): core-only T-003 with the cut from point 5. The shell part goes to a new `deploys: true` task.**
- Why it removes the cause: one seam, `secrets` + `settings`, is defined before 001 and 003 can create parallel ones. Every guarantee is proven on the Linux gate with fakes and a real temp dir.
- Risk: it adds a task, and dependencies must be re-pointed (T-004 and T-006 → the shell task).
- Rollback: revert the module; nothing consumes it yet.

**Option B: T-003 as written plus the shell part, `deploys: true`.** It needs a Windows CI round-trip test and a verify record from the Windows job. The upside is one task delivers end-to-end key storage. The cost is two areas, a long red/green cycle through Windows CI, and the cross-feature gaps (D5) blocking the core part.

**Option C: T-003 as written but core-only, without the cut.** The scope is honest about the shell part, but the task still blocks on 001, 002 and 003 contracts (hotkey registrar, downloaded models, post-processing validation) or invents placeholders for them (a P-010 risk).
