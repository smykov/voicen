## Context

FR-13 (fields, per-engine required fields per v4), FR-21 (defaults incl. v4 additions), NFR-04 (keys only in Credential Manager), spec 004 clarifications Q1 (all-or-nothing save) and Q4 (unreadable file → backup + defaults). Pure core with fakes.

Scope after the re-plan (decisions #20–#22): this task owns the one settings/key seam that specs 001–004 share — `secrets` (`KeySlot`, `Secret`, `KeyEdit`, `KeyPresence`, `CredentialStore`), `settings` (`Settings`, `FieldId`, `defaults()`, `SettingsFile`, validation, `SettingsService` with `load_or_init` / `save` / `snapshot` / `view` / std `subscribe`, startup gate), the `HotkeyRegistrar` and `DownloadedModels` traits with fakes (implemented later by T-006 and T-016), and the `post_process::settings` data type with `STARTER_PROMPT` and its defaults (validation stays with T-020/T-021). Not here: the Credential Manager implementation and the settings IPC (T-030), the `Autostart` trait and save step (T-014), hotkey grammar/step wiring with the real registrar (T-006/T-010), the built-in model rule with the real store (T-016/T-017), wiring subscribers in the shell (T-030). `resolve_ui_language` comes from T-005. Dependencies: `serde_json`, `url`, `zeroize`, `chrono`, `thiserror` (decisions #9, #17); no `tokio` (#22).

## Acceptance

- [ ] A fresh data folder yields exactly the FR-21 v4 defaults; a file missing fields (`{}`, `{"schema_version":1}`) takes the missing values from `defaults()`, not the field types' defaults
- [ ] A valid save persists atomically (tmp + rename) and a reload returns the same values; keys never appear in the settings file
- [ ] `startup_action` / `blocked_actions` decide first-run, tray-only start and engine-none behaviour (spec 004 analyze HIGH fix)
- [ ] Failure branch: empty base URL for the API engine → save refused with field id `engine.api.base_url` (decision #18), nothing written, old values and key slots kept; an unreadable settings file → kept as a timestamped backup, defaults loaded, notice raised; the file cannot be moved aside, or a read fails with an I/O error other than not-found → defaults in memory, the file neither written nor moved, saves refused with a notice (decision #19) — verified by core tests on a temp dir
- [ ] Test that fails without the change: `crates/voicen-core settings tests (validation, atomic write, unreadable-file branch)`

## Investigation

Investigator, 2026-10-02. Tools: serena indexes only TypeScript (decision #3), so I used grep and file reads for Rust. context7 is not connected in this session (no `mcp__context7__*` tools). Library facts come from the crate source in the core cargo cache (`.teamwright/cache/core/_usr_local_cargo_registry/src/*/serde_derive-1.0.229`). The image has no `rust-src`, so `std::fs::rename` semantics on Windows are **unverified here** (see the Windows note under Approach).

### Frame

- **Observed:** `crates/voicen-core` contains only `build_info` (`src/lib.rs:3`). Its dependency list is `serde` with `derive` (`Cargo.toml:10`). There is no `tests/` directory. The baseline `cargo test -p voicen-core` runs 2 tests, both in `build_info`. `src-tauri/src/lib.rs` has no settings or credential code; the data directory appears only inline in `log_dir()` (`src-tauri/src/lib.rs:11-18`).
- **Expected:** FR-13 (v4 fields, per-engine required fields), FR-21 v4 defaults and NFR-04 (keys only in Credential Manager), plus spec 004 Q1 (all-or-nothing save), Q4 (unreadable file → backup + defaults) and Q5 (pre-filled API and local-server URLs). All of it should be provable on the Linux gate with fakes.
- **Where it reproduces:** everywhere. This is a new capability, not a regression.

### Hypotheses

1. **Settings code already exists in part** → refuted. `grep -rn -i "settings\|credential" crates/ src-tauri/src` finds only the `description` field of `Cargo.toml`.
2. **The same concern is handled on a second path** → **confirmed in the plans, not yet in code.**
   - Spec 001 plans its own `CredentialStore { transcription_api_key() -> Option<SecretString> }` and a `SettingsSource`/`DictationSettings` with its own defaults and JSON loader in `crates/voicen-core/src/settings.rs` (specs/001 `contracts/core-traits.md:85-99`, `tasks.md:46-47`), plus a `CredReadW` impl in `src-tauri/src/win/credentials.rs` (`tasks.md:80`).
   - Spec 003 calls the same port `SecretStore`/`Secret` (`specs/003 tasks.md:143,156`); spec 002 calls it `SecretRef` (`specs/002 tasks.md:121`).
   - Spec 004 plans `CredentialStore { read/write/delete(slot) }` and `src/settings/mod.rs`. Rust cannot have both `settings.rs` and `settings/mod.rs`.
   - If T-001 is implemented as written after T-003, there will be two defaults sources, two readers of `settings.json` and two Credential Manager impls (a P-010/P-011 violation).
3. **This class was fixed before** → refuted. `docs/failures.md` has only the placeholder row. No other task has `class: settings-persistence`. `git log -- crates/voicen-core src-tauri` shows only the skeleton commit `0afeaf3`.
4. **The spec's own serde guidance would break the defaults** → **confirmed.** data-model.md says "every field `#[serde(default)]`". In serde_derive 1.0.229 (`de.rs:765-787`), a field-level `#[serde(default)]` fills a missing field with the field type's `Default::default()`. Only a container-level `#[serde(default = "...")]` reads the value from the container's default. Taken literally, an older file without `auto_paste` would load `false`, a file without `history.size` would load `0` (invalid), and a file without `api.base_url` would load `""`. Each nested struct (`api`, `local_server`, `history`, `post_processing`) needs a container default that comes from the one `defaults()`. Unknown fields are ignored unless `deny_unknown_fields` is set (`de/struct_.rs:285-289`), as R-2 wants.
5. **The shell part of 004 Phase 2 is owned by another task** → refuted. No `docs/tasks/*.md` mentions `credentials.rs`, `settings_ipc`, `CredWrite` or spec T016/T017. T-004 is UI with mocked IPC; T-006 is the 001 dictation shell.

### Settled questions

**1. Seams (core).** All in `crates/voicen-core`:
- `secrets.rs`: `KeySlot` (targets `Voicen/transcription-api`, `Voicen/local-server`, `Voicen/post-processing`); `Secret` (`Debug`/`Display` = `***`, no `Serialize`); `KeyEdit`; `KeyPresence`; and the `CredentialStore { read, write, delete }` trait (absent = Ok on delete; `CredentialError` holds an OS code and no key material).
- `settings/mod.rs`: `Settings`, `FieldId`, `defaults()`.
- `settings/file.rs`: the `SettingsFile { read, write_atomic, move_aside }` trait, plus `FsSettingsFile::new(dir)` over `std::fs` (platform-independent, so it lives in core).
- `settings/url.rs`: `check_base_url`. `settings/validate.rs`: the validation rules.
- `settings/service.rs`: `SettingsService` with `load_or_init`, `save`, `snapshot` and `view`.
- `settings/gate.rs`: `dictation_gate`, `blocked_actions`, `startup_action`.
- Fakes (credential store with injectable failures and a call log, settings file, clock) go in `crates/voicen-core/tests/support/`. Integration tests cannot see `#[cfg(test)]` items, and spec 001 T010 puts its fakes in the same place.
- `Autostart`: see D4.

**2. Scope of the Windows Credential Manager impl → not this task (flagged, D1).** With `deploys: false` the verify gate never asks for the Windows CI run, which is the only place `src-tauri` is built (decision #5). Shell code inside T-003 could therefore reach `DONE` without its only proof (P-006). Two things are orphaned today: spec 004 T016 (Credential Manager over `CredWriteW`/`CredReadW`/`CredDeleteW` with a Windows round-trip test) and T017 (`settings_get`/`settings_save` IPC, `SettingsService` wired into the shell, data dir passed in). Spec 001 T028 plans a second, read-only impl.
- **Recommendation:** a new shell task, `deploys: true`, depending on T-003. It holds spec 004 T002 + T016 + T017 and absorbs 001 T028, so there is one Credential Manager impl. T-004 and T-006 should depend on it.
- **Alternative:** keep the shell part here, set `deploys: true`, and add a Windows CI integration test (write → read → delete → read none on a throwaway target). That makes an already large task cross two areas.
- Either way, the title "… API keys in Windows Credential Manager" overstates a core-only T-003. Suggested: "… API keys behind the `CredentialStore` port".

**3. `AppPaths` overlap → do not introduce it here.** The core file impl takes a directory (`FsSettingsFile::new(dir)`) and owns the one file-name constant `settings.json` (P-010 holds: a single `dir.join(SETTINGS_FILE)`). Nothing in T-003 resolves `%LOCALAPPDATA%`, because there is no shell wiring. The 006 contract leaves `settings_file()` to 004 (`specs/006 contracts/core-diag.md:14`). ### Approach

**Option A (recommended): core-only T-003 with the cut from point 5. The shell part goes to a new `deploys: true` task.**
- Why it removes the cause: one seam, `secrets` + `settings`, is defined before 001 and 003 can create parallel ones. Every guarantee is proven on the Linux gate with fakes and a real temp dir.
- Risk: it adds a task, and dependencies must be re-pointed (T-004 and T-006 → the shell task).
- Rollback: revert the module; nothing consumes it yet.

**Option B: T-003 as written plus the shell part, `deploys: true`.** It needs a Windows CI round-trip test and a verify record from the Windows job. The upside is one task delivers end-to-end key storage. The cost is two areas, a long red/green cycle through Windows CI, and the cross-feature gaps (D5) blocking the core part.

**Option C: T-003 as written but core-only, without the cut.** The scope is honest about the shell part, but the task still blocks on 001, 002 and 003 contracts (hotkey registrar, downloaded models, post-processing validation) or invents placeholders for them (a P-010 risk).

**Red tests for option A, in Acceptance order.** Each is red before the code exists.
1. **AC1, fresh folder → FR-21 v4 defaults.**
   - `settings::tests::defaults_match_fr21_v4` checks every field, including the Q5 URLs and model, an empty local-server model and `STARTER_PROMPT`.
   - `settings::tests::missing_fields_take_defaults` deserializes `{}` and `{"schema_version":1}` and expects `defaults()`. It goes red if field-level `#[serde(default)]` is used (H4).
   - `tests/settings_service.rs::first_run_writes_defaults` uses a temp dir and the real `FsSettingsFile`: the outcome is `FirstRun`, and the file now exists and parses to the defaults.
2. **AC2, atomic save + reload + no key in the file.**
   - `file::write_atomic_replaces_and_leaves_no_tmp`.
   - `file::leftover_tmp_is_deleted_and_never_read`.
   - `file::failed_write_keeps_previous_file`: a real-fs failure made by putting a **directory** at `settings.json.tmp`, which fails even when the container runs as root. The old file must stay byte-equal.
   - `settings_service::save_round_trips_through_a_new_service` (P-013, the real loader).
   - `secrets::secret_debug_and_display_are_masked`, plus a `compile_fail` doctest showing `serde_json::to_string(&Secret)` does not compile.
   - `settings_service::save_never_writes_key_bytes`: a marker key in all three slots is absent from the file bytes and from the `SettingsView` JSON.
3. **AC3, startup and gate.**
   - `gate::startup_action_table`: FirstRun/Reset × autostart on/off → `OpenSettings(Engine)`; Loaded × on/off → `TrayOnly`.
   - `gate::blocked_actions_no_engine` == `[Notify(notice.choose_engine), OpenSettings(Engine)]`.
   - `gate::dictation_gate_blocks_only_none`.
4. **AC4, failure branches.**
   - `validate::api_empty_base_url_refused` names the field id per D7(a). A malformed-URL table covers `api.openai.com`, `htp://x`, `https://` and `ftp://host`; local-server rules; fields of unselected engines are not validated.
   - `settings_service::refused_save_changes_nothing`: file bytes, `snapshot()` and the fake store's slots and call log are unchanged, with no write or delete call.
   - `file_write_failure_restores_keys`: the restore runs in reverse order and slots return to their pre-save values.
   - `key_store_failure_refuses_with_key_store_failed`: no file write and no other storage.
   - `unreadable_file_reset` for invalid JSON, a wrong field type and `schema_version` 2: the backup is byte-equal to the original, named `settings.json.bad-<fake clock UTC>`; the outcome is `Reset` with `SettingsView.reset_notice = true` (the notice the shell shows); defaults are written; the credential fake recorded zero calls.
   - `move_aside_never_overwrites_existing_backup`.
   - The move-aside failure test (a directory at the backup name) follows D7(b).
5. **AC5:** the tests named above, in `crates/voicen-core/src/{secrets.rs,settings/*.rs}` and `crates/voicen-core/tests/settings_service.rs`.

**Windows note.** Replacing an existing `settings.json` by `std::fs::rename` on Windows (R-2 says `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`) is not verified here: there is no rust-src and context7 is unavailable. The Linux tests prove POSIX rename only. The shell task's Windows CI test should save twice over an existing file.
