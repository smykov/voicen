## Context

FR-29 (v4: loopback only is local). Decision #52: the rule is core's `is_insecure_remote` over the `url` crate (P-010, contracts/core-traits.md:102, #38 Q1 precedent); `Warning` gains `message: MessageId`; the UI renders `Saved.warnings` as given, kept outside the Draft.

## Acceptance

- [ ] `http://example.com/v1` → warning; save still allowed
- [ ] Failure branch: `http://LOCALHOST:8000/v1`, `http://127.0.0.1`, `http://[::1]` → no warning — verified by vitest and Playwright
- [ ] Test that fails without the change: core `settings::url` `is_insecure_remote` table and `settings::service` save-warning tests; UI `src/lib/settings/draft.test.ts` (`warningsByField`) and `e2e/settings-warning.spec.ts` (decision #52: the rule lives in core, no `src/lib/url.ts`)

## Investigation

1. **Frame.** Expected (FR-29, spec 004 FR-020, US6-1..4): when the user saves an `http://` base URL in use on a non-loopback host, the save succeeds and a warning says the key travels unencrypted. Loopback means `localhost` in any letter case, `127.0.0.0/8` or `::1`, and `https` never warns. Observed: no warning on any path. Core always returns `warnings: []` (service.rs:383-386), and the UI ignores the field (draft.ts:127).

2. **Where the rule lives.** It belongs in core. Evidence:
   - The contract names it: `is_insecure_remote(&NormalizedUrl)` in `settings/url.rs` (contracts/core-traits.md:102). research R-8 describes the classification on the parsed URL.
   - tasks.md Phase 8 splits the work: T060/T062 (area core: rule + `Saved.warnings`) and T061/T063 (area ui: render + en/ru text).
   - T-032 already declared `Warning`/`WarningCode::EndpointInsecure` for T-015 (service.rs:82, T-032 Notes), and the wire is pinned (service.rs:2438-2486, ipc.md:28-30).
   - There is direct precedent. Decision #38 Q1 resolved an Acceptance that needed a UI copy of core validation by keeping the rule in core: same user-visible result, P-010.
   - settings.md rejects a hand-written URL parser (#17).

   **Conflict:** the task's Acceptance names `src/lib/url.test.ts`, which implies a TS rule (Option B). That conflicts with P-010, U1 ("build no rule in the UI") and the contract. Proposed fix: Acceptance line 3 becomes "core `settings::url` `is_insecure_remote` table and `settings::service` save-warning tests fail without the change; UI: `draft.test.ts` › warningsByField and `e2e/settings-warning.spec.ts`". The vitest + Playwright check of the failure branch stays (scripted outcome without warnings). This is a task-record decision for the orchestrator, not a product question.

3. **Edge cases.** Probed `url` 2.5.8, the crate's version in Cargo.lock and the parser reqwest and `check_base_url` use. I ran a scratch crate outside the repo in `voicen-rust:1.99`, offline, against the cached registry.
   - `LOCALHOST`, `LocalHost` and fullwidth `ｌｏｃａｌｈｏｓｔ` parse to `Domain(localhost)`.
   - `127.1`, `0x7f.1` and `2130706433` parse to `Ipv4(127.0.0.1)`. `127.1.2.3` is loopback.
   - `[::1]` and `[0:0:0:0:0:0:0:1]` parse to `Ipv6(::1)`.
   - These are not loopback: `[::ffff:127.0.0.1]` (std `is_loopback` false), `0.0.0.0`, `[::]`, `localhost.` (also from `localhost%2e`), `foo.localhost`, `127.0.0.1.nip.io`.

   Following the spec's closed list ("loopback only"), everything in the last group gets the warning. That fails safe, because the warning never blocks. A TS rule would have to reproduce the WHATWG host parser exactly, including IPv4 shorthand and IDNA, to agree with what the client connects to. A hand-written TS regex would not. Note also that in JS `new URL("http://[::1]").hostname` is `"[::1]"`, with brackets.

4. **Fields.** These carry base URLs: `engine.api.base_url` (in use when engine = api), `engine.local_server.base_url` (engine = local_server) and `post_processing.base_url` (in use while `post_processing.enabled`). The engine field has no UI control yet (T-021), and core does not validate it yet (post_process/settings.rs:1-4). Core therefore warns on it only when it passes `check_base_url`; it is never refused for it here. A malformed post-processing URL produces no warning, and refusing it is T-020/T-021's job. Only the selected engine's URL warns (spec US6-1), so a stale `http://192.0.2.10` local-server URL under engine api stays quiet.

5. **Where it shows.** On the Engine tab, under the base-URL input, in a non-error style:
   - The warning element is referenced by `aria-describedby`. `aria-invalid` stays false and the "Saved" status also shows.
   - A warning for a field with no rendered control is listed at form level by `t(fieldLabelId(field))` with the warning text, the same mechanism as rule L (`renderedFields`). This covers saving from another tab, where the Engine panel is not mounted, and `post_processing.base_url` before T-021.
   - The text is a catalog id. Recommended: `Warning` gains `message: MessageId`, mapped by `WarningCode::message_id()` (FormError precedent, service.rs:101-108). The id `settings.warning.endpoint_insecure` is declared in `messages!` and so covered by `message_ids_exist_in_both_catalogs`. The UI types it `MessageId` at the boundary and adds no cast, per i18n.md "type it MessageId where it enters the UI".
   - Fallback if the orchestrator prefers no wire change: a rule-built `warning.<code>` with a third documented cast in draft.ts. That needs a core completeness test over a `WarningCode::ALL` (i18n.md requires it).
   - en text, roughly: "This address uses http:// on a non-local host: the API key is sent unencrypted." ru: «Адрес использует http:// на нелокальном хосте: API-ключ передаётся без шифрования.»

6. **Pitfall found.** For our own save, the shell's change bridge emits `settings://changed`. `receive` → `applyView` on a clean draft returns `draftFromView`, which resets everything in the Draft (draft.ts:78-79; mock tauriMock.ts:9-15 emits it after the save returns). Warnings stored in the Draft would disappear right after showing. Keep them in page state set from the outcome, beside `saved`, and clear them when the next save starts. The e2e test must assert the warning is still visible after the echo event.

7. **Size.** One concern through one pre-built wire. It touches two areas: core `settings/{url,service}.rs`, `i18n.rs`, `i18n/*.json`; UI `settingsApi.ts`, `draft.ts`, `+page.svelte`, `tabs/Engine.svelte`, one e2e spec. That is the Phase 8 shape (T060–T063), small (about 150 lines plus tests), and needs no shell change: `settings_save` already serializes `SaveOutcome`. The verdict is one task. A split into core and UI is possible but not needed. `surface: ui` stays right. The Playwright run uses the mocked IPC, so the core behaviour is proven by the core tests in the gate. Doc updates in the same commit: contracts/core-traits.md (built surface; drop "not yet in code" for T-015), contracts/ipc.md (Warning `message`), docs/decisions/settings.md (new invariant "Insecure-endpoint warning is decided in core"), docs/decisions/settings-ui.md (U1/U2 note: warnings rendered as given, not in the Draft).

8. **Hypotheses checked.**
   - (a) A rule already exists somewhere. Refuted: grep found no `is_loopback`/`is_insecure`/`loopback` logic in `crates/`, `src/`, `src-tauri/src`, and Serena was not used. `host_port` (openai.rs:241) only formats `host[:port]` for error text and does not classify.
   - (b) A second path handles the concern. The only other producer of `SaveOutcome` is the e2e mock, which never validates (decision #38) and scripts outcomes.
   - (c) The class was fixed before. docs/failures.md F-001..F-003 contain no warning or URL-classification entry. The closest is the F-003 *class* (deciding on a model of another tool's parser), which argues against Option B.
   - (d) The warning could be live while typing. Refuted by the spec ("When the user saves").
