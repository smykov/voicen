## Context

`crates/voicen-core/tests/call_session.rs::indicator_changes_inside_the_lock_and_shell_requests_after_it` (a T-126 test) failed once more, in the unmutated baseline of `scripts/tw-mutants core T-149` during T-149 validation 1 (2026-11-09, main @ 486eee9b): all 20 ticks had `mic_level` 0.0. It then passed 61 runs in a row (1 failure in 62).

This is the symptom T-126 saw on 2026-11-07 (run T-126-20261107T025757Z: 1060 ticks, `mic_level` 0.0). The developer analysed it then as a test timing fault (the wait loop fed 200 ms per pass without waiting for the writer; the 64-slot channels filled and every freed slot took a zero-filled Dropped event) and rewrote the loop to at most 20 passes, one 200 ms span each, waiting for a new tick per pass (`docs/tasks/T-126.md`, "Flake fix"). In that note the fix is labelled F-018, but `docs/failures.md` F-018 is a different defect (a `settings://changed` listener subscribed after the trigger): the T-126 flake has no F-entry of its own. T-149 did not change the test; it did change the session's device thread and the mic lane (`session.rs`, `capture.rs`).

Recurrence of a known defect after its fix → this rca task (CLAUDE.md › Rules). Owner of the analysis: `problem-investigator`. Exits (`docs/process/lifecycle.md` §6): (a) code, (b) architecture review, (c) process amendment — (b) and (c) are the owner's.

## Investigation

Problem investigator, 2026-11-10, main @ eecf045e. Serena was used for the session.rs overview and the test body. Text search covered helpers, history and the failures/decisions tables. The context7 lookup was not needed: no library API is involved.

**Frame.** Observed: 20 passes, each with a new tick, all with `mic_level` exactly 0.0. Expected: by pass 1 or 2 a tick with the mic near 0.5 and the system at 0.0. Rate: 1 in 62 (T-149 validation 1), and the first sighting before the T-126 fix. Exactly 0.0 means the mic level was never set, or every mic level window was all zeros.

**Hypotheses.**
1. *The writer starves one track* (drain empties one channel before it reads the other, while the producer keeps refilling). Confirmed: reproduced, see below.
2. *Channel full, so zero-filled drops* (T-126's explanation). Refuted as the cause of this sighting: the repro shows no Dropped event before the failure. The first 64 queued mic blocks are real audio, so drops alone cannot give exactly 0.0 on every tick. Drops are a later consequence of starvation.
3. *T-149's second path* (`Writer::advance` stall zero-fill, `OpenSink` retire, the device thread). Refuted for this test: `advance` runs only after `round()` returns, and the repro logs no `advance_track` call. The test sends no device events.
4. *This class was fixed before* (T-126 commit 1eace2e0). Confirmed incomplete: it paced passes on "a new tick", which does not mean "the pass was consumed".

**Mechanism** (`crates/voicen-core/src/call/session.rs`):
- `Writer::drain` runs, per track, `loop { rx.try_recv() → handle }`: the mic until it is empty, then the system until it is empty.
- `Writer::apply` → `maybe_tick` publishes the latest `rec.mic.level` / `rec.system.level` at the first placed step once 100 ms of fake mono time has passed since the last tick.
- The test (`feed_both` = System, then Mic) waits only for the tick count to grow, polling every 5 ms (`common::timing::eventually`). Then it advances mono and feeds 10 more blocks per track.
- Say the writer wakes in the narrow window after `feed(System)` and before `feed(Mic)` of pass 0, and its per-event cost times 10 exceeds the test's pass cycle (a loaded host: the mutants baseline on a fresh copy, all of `call_session` in parallel). Then the system loop never sees an empty channel. Each pass's tick comes from a system block, the mic is never read, and its level stays at the initial 0.0 (`recording()` sets `level: 0.0`).
- The rare combination of these two conditions explains the 1/62 rate. The developer's 15 ms-per-event copy passed (T-126 note) because it kept the usual mic-first order.

**Reproduction** (throwaway worktree copy `/tmp/t203-copy`, removed afterwards, nothing committed; instrumentation = `eprintln!` in `Writer::{handle, apply, advance_track, maybe_tick}` plus a `T203_DELAY_US` per-event sleep in `handle`):
- `slow_sysfirst_*`: the committed body; pass 0 is `pause_writer` → feed System → release → wait for a tick → feed Mic; 1 ms per event. Result: 5/5 FAIL at the final `got` assertion, 20 ticks, all mic 0.0. Mic events handled: 0. System events handled: 43 of 200 fed.
- `slow_micfirst_*`: the same with Mic first. Result: 5/5 PASS.
- Logs: `.teamwright/logs/test/core-20261110T005319Z-eecf045-c355f02552b9.log` (both variants), `core-20261110T005532Z-eecf045-71e5ea1895d3.log` (ADV/apply traces: no mic step, no ADV), `core-20261110T005118Z-eecf045-1da2197958ba.log` (no delay: the mic loop held the system lane off for 30 blocks).
- 48 parallel copies of the unmodified body passed (`core-20261110T004848Z-…`), consistent with a rare race.

**Recurrence.** T-126 2026-11-07 (run T-126-20261107T025757Z, at adebac90) → fix 1eace2e0 → T-149 validation 1, 2026-11-09 (`T-149-20261109T093115Z.txt`, baseline log gone with its tmp copy). Why the fix did not hold: it bounded how many passes ran, not what the writer had consumed. `docs/failures.md` has no entry for this class. F-018 (`test-event-subscribed-after-trigger`) was wrongly cited for it, and F-021/I2 (no wall-clock ceiling) still binds the fix. A related, already sound pattern: T-149's tests use subtitles on plus `drained()`, and `barrier()` only after `drained()`.

**Approach options.**
- **A (recommended, test only).** Rewrite the test: `toggle_subtitles(true)` before `started`; `feed_both(0, 200, 0.5, 0.0)` (10 blocks per track, no drop at capacity 64); `drained(&rig, &[Mic, System], 200)`; `let tick = barrier(&rig, &[(Track::Mic, 0.5), (Track::System, 0.0)], 200)`; assert `tick.mic_level > 0.1 && tick.system_level < 0.01`. The other assertions (held flags, shell outside the lock) stay.
  - Why it holds: both tracks' levels come from a fully drained span, so the drain order no longer matters.
  - Red first: the copy harness above (system-first pass 0 plus 1 ms/event) is red on the current body (5/5) and must be green on the new body. Then run the new test at least 100 times (Acceptance) and re-run the T-126 and T-149 mutant catalogs.
  - Risk: subtitles-on adds `set_state` calls, which stay inside the lock, so the bites still hold. Rollback: revert the test.
- **B.** Add a test-fakes barrier `CallSession::settle_writer()` (returns after a writer round in which both channels were empty), so the test needs no subtitles. Deterministic too, but it adds core API and docs. Take this one if review rejects the subtitles coupling.
- **C (product, not this exit).** Make `Writer::drain` fair (bounded batches or round-robin per track). This removes starvation but does not make the test deterministic: the tick would still be used as the consumption proof.

**Follow-up (hypothesis, not demonstrated; propose a separate task).** In the product, under sustained writer overload, the track drained second can be starved. Its `Seen.last_event` then ages past `STALL` (500 ms). When drain finally returns, `Writer::advance` may zero-fill that track up to the other track's `last_end` − 200 ms while its real blocks still wait in the channel. They would then be placed late and head-dropped. Not reproduced: needs a red test on a starved lane.

**F-entry draft (F-031)** for `docs/failures.md`:
- Date: 2026-11-07 / 2026-11-09.
- Sighting: `call_session::indicator_changes_inside_the_lock_and_shell_requests_after_it` red under load; every tick had `mic_level` 0.0 (T-126 run T-126-20261107T025757Z; T-149 validation 1 mutants baseline).
- Cause: the test took a new tick as proof the writer had consumed its feed. A tick proves only one block of one track after a 100 ms mono step. `Writer::drain` empties one track's channel before it reads the other, so a writer slower than the feed starved the mic lane for the whole test.
- Rule: a call_session assertion on placed audio follows `drained()` (or `barrier()` right after `drained()`); never a tick count.
- Tier: T1 (review).
- Tasks: T-203; T-126, T-149 (sightings).
- Class row: `test-infers-writer-progress-from-tick | F-031 | 1 | T1 (review only): nothing checks that a call_session wait on ticks follows drained()`.

**Recommended exit**: (a) code. The class lives in one seam: the test's consumption barrier in `crates/voicen-core/tests/call_session.rs`. A deterministic barrier already exists there (`drained()`), so the test closes the class without a product change. Not (b): one seam, no cross-service shape. Not (c): F-021/I2 and the existing helpers already cover the rule; it was just not applied here. The size is small: one test plus docs (failures.md, the T-126 note, the test comment, the barrier() doc).
