## Hang bound (re-entry 2026-11-14)

Changed waits (tests only; `src-tauri/src/**` untouched):
- `call_shell_support::CallRig::recording` no longer takes the session lock on the test thread: it polls `CallSession::try_is_recording` inside `eventually` (which pumps this thread's messages between polls) and panics `HANG: the session lock stayed held ... (test <name>)` at the hang bound. Every `eventually(|| rig.recording())`, `!rig.recording()` and `holds_for_a_while(.. rig.recording() ..)` in `call_launch.rs` and `call_tray.rs` goes through it, assertions unchanged.
- New `CallRig::stop_call`: the end-of-test `session.stop(StopReason::User)` (two sites in `call_launch.rs`) runs on a helper thread while the test thread pumps; panics `HANG: CallSession::stop did not return ... (test <name>)`.
- New `timing_support::HangWatch` / `watch_for_hang(what)`, held by every `CallRig` (last field, dropped after the app): if the test is still running `2 * HANG` later (a rig build, `start_calls`, a drop or a request that never returns) it prints `HANG: test <name> ...` and exits 101, so the run turns red with a name instead of holding the job. Dropping the rig cancels it. No clock is read (`recv_timeout` only), no product time is bounded (F-019/F-021).
- `SERIAL` stays an unbounded `lock()` on purpose: its holder is now always bounded (above), and a bound on queue time would be a ceiling that races the runner.

Static diagnosis (from the code at 38bd4d2f; the job log gives no stack, so this is ranked, not proven):
1. libtest prints "running for over 60 seconds" for every started test, also those parked on `SERIAL`. The 6 finished tests ran first; so exactly one of the four holds `SERIAL` and hangs, and the other three are queued behind it. `a_launch_without_the_switch_never_starts_call_mode` starts nothing and cannot hang by itself: it is a queued victim (or the hung one only through the shared mechanism below).
2. Most likely holder: `a_first_launch_with_the_switch_applies_it_once_after_the_tray_exists` (the only one of the four that records). The worker holds the session lock through `begin_call`, which calls `ShellCallIndicator::set_call_recording` -> `TrayPart::want` -> `run_on_main_thread(apply)`, and the mock runs that task inline on the worker: `render` calls tray-icon / muda setters and builds a menu from a thread that does not own the tray window, and `docs/decisions/windows-shell.md:33` says tauri's tray setters wait for the owning thread. The test thread meanwhile called `rig.recording()` = `is_recording()` = a blocking `lock()` with no pump: lock-order cycle (test thread parked on the session lock, worker under it waiting for a message the test thread would pump). The other recording tests (AC1, stop, tick) passed on the same path, so it is a race on when the 10 ms poll lands, which fits one test of the group. The test-side fix is the bounded, pumping read above. If it still hangs, the `HANG` text names it and the developer should check that nothing under the session lock (`set_call_recording`, `ShellCallShell`) waits on the main thread: the tray flag should be published after the lock or only posted.

Other holder candidates: `a_second_launch_refused_on_the_runner_keeps_the_app_running` (real `CpalTrackSource::open` of the system loopback or the `NotifyFactory`/`ComCheck` COM calls blocking in the worker under the lock; its own waits were bounded, so a hang there needed the unbounded `rig.recording()` at its end) and `a_refusal_reaches_the_notifier_once` (no tray flag, only `Refusing`; a hang here would be the rig drop or the worker, which the `HangWatch` now names).
