## Context

"Deployed" means the Windows CI job (requirements §9) — it needs the GitHub repository (decisions #4). Owner step: create the public repository and push `main`. Then make both jobs of `.github/workflows/ci.yml` green and record the observed Windows facts (install path, log path, runner image) in spec 006 research.

## Acceptance

- [ ] `origin` points to the public repository; `main` is pushed by the owner
- [ ] CI run on `main`: job `gate` green (`make check` in `voicen-rust:1.99`), job `windows` green (installer built, installed silently, launched, start log line contains the commit)
- [ ] The installer artifact is downloadable from the run
- [ ] Failure branch: a commit whose start log line lacks the commit (e.g. `VOICEN_COMMIT` unset) makes the `windows` job fail with "start log line with commit … not found" — verified once by a deliberately broken run or by reading the job's check step
- [ ] Test that fails without the change: `the `windows` job's smoke step itself (it fails without a matching log line)`
- [ ] Install paths (decision #15): a green `windows` run on a commit that contains ca9b61d shows `found voicen.exe at …\AppData\Local\Voicen\voicen.exe`, `found uninstall.exe at …\AppData\Local\Voicen\uninstall.exe` and `found Voicen.lnk at …\Start Menu\Programs\Voicen.lnk`; failure branch (by reading the step): any missing path fails the job with `<name> not found at <path>` before the app is launched

## Investigation

Checked with `gh` (not the orchestrator's summary), file reads and grep. Serena does not index YAML or Markdown (decision #3). context7 tools were not available in this session, so the Tauri template was read from the pinned `@tauri-apps/cli-linux-x64-gnu@2.12.1` binary (`strings`, NSIS template embedded). The installer artifact was not unpacked because no 7z or bsdtar is on the host, and none was installed.

**Hypotheses considered**
1. *Green run already proves all facts.* Refuted: the job log has no line naming the install dir, `uninstall.exe` or a `.lnk`, and the step asserts none of them.
2. *Failure branch might not bite, because a fallback commit could still match.* Refuted: `build.rs` falls back to git, but the step's `$expected` comes from the same unset env var and becomes `() started`, which never matches.
3. *A second path observes install facts.* None found: grep of `.github/` and `src-tauri/` finds the install/launch only in ci.yml:47-64. `cargo test --workspace` on Windows does not touch the installer.
4. *This class was fixed before.* No: `docs/failures.md` holds only the placeholder row. The only other `class: ci-deploy` task is T-026 (TODO, release publishing), a sibling and not a recurrence. ci.yml has one commit in its history (0afeaf3, walking skeleton).

**Approach options**
- **(A) recommended:** exact-path assertions plus printed paths in the smoke step, an owner push, then record the observed values in research.md. Its cost is small, and T030 will build `uninstall.exe /S`, `/KEEPDATA` and the shortcut check on these paths. A path that is wrong now would otherwise surface only there, mixed with uninstall-hook failures.
- **(B) no CI change:** record what run 37035261228 observed, keep the uninstaller and shortcut marked **confirm on Windows** with a note "deferred to T030", and leave the install dir as "under `%LOCALAPPDATA%\Voicen`, exact dir unprinted". This needs no push. It satisfies T-002 Acceptance, but design_ref T002 stays only partly done, and the owner should accept that explicitly.
- Rejected: recording the template's predictions as observed. That breaks P-006, because these are docs and not data.

Both options update research.md R9/R11/R14 with run id 37035261228 (or the new run) and the runner image, and update the matching "confirm on Windows" marks in `contracts/installer-ci.md`. Docs follow in the same commit (P-014). spec 006 tasks.md T001 also asks for `docs/plan.md` stage 0 to be updated, which is not done yet.
