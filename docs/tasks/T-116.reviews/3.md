What I verified:

- **Corruption gives `HashMismatch`, not another read error.** I checked ogg 0.9.2 (`src/reading.rs`):
  - Before the CRC check, `PageParser` only parses the header fields. Granule bytes are stored and never validated.
  - The segment table only sets sizes, and the body is read as raw bytes.
  - `parse_packet_data` (l. 316-340) then compares the CRC and returns `HashMismatch`.
  - So both `corrupt_run` kinds yield `HashMismatch` and nothing else: a body bit flip at 2/3 of the page, and a granule byte flip at `start + 7`. Neither kind changes the capture pattern, the segment count or the body length, so the reader stays aligned and the next page parses normally.
  - The tests also confirm this behaviourally. In `next_audio`/`after_bad_page`, any non-`HashMismatch` error on a page in the run returns `Truncated` (`codec.rs:352`, `:365`). So the `Damaged` result asserted by `consecutive_bad_pages_before_a_valid_page…` proves that every page of each run produced `HashMismatch`, followed by an `Ok(Some)` from the first valid page.
- **The invariant is pinned for runs.**
  - Test 1 covers runs of 2 and 3 bad pages at every start k ≥ 3 with at least one valid page after them. That includes the case where the only valid page after the run is the EOS page (k = last − run).
  - Through `assert_prefix`, test 1 asserts:
    - scan `Damaged`;
    - windows `Err(DecodeEnd::Damaged)`;
    - duration = granule of page k−1 − pre-skip;
    - audio = the full decode's prefix.
  - Test 2 covers every run from k ≥ 3 to the last page and asserts `Truncated` and the same prefix.
  - Every run of length ≥ 2 mixes both corruption kinds, because the kind alternates by page index.
- **Bite, by reading** (the mutants are trivial to trace, so I ran none):
