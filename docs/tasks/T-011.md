## Context

FR-23; delivery slot assigned at recording stop (spec 001 FR-029). Built on T-001's `Pipeline::run_job` private `process`/`release` halves: put the queue between them. Note from T-001 review rounds 1–2: `keep_pending` holds the slot lock across store and swap, but that is only a safeguard — `release` still runs on one delivery thread, because the clipboard write → modifier wait → Ctrl+V sequence in `deliver` interleaves across concurrent jobs (research R-10); `process` may run concurrently.

## Acceptance

- [ ] A then B: A delivered to A's window, then B to B's
- [ ] Failure branch: A fails → B still delivered, A follows FR-11; A with no speech leaves the order without blocking B — verified by core tests with a fake engine
- [ ] Test that fails without the change: `crates/voicen-core delivery-order tests` — each fails under its named bite (thread per job, LIFO, start window at delivery, queue halted on failure), shown by a temporary local mutation recorded under ## Tests (decisions #310)

## Investigation

**Frame.** FR-23 / spec 001 FR-029 asks for four things: a press during processing starts a new recording; results arrive in recording order; each result goes to its own start window; a failed or no-speech earlier recording does not block later ones. Retry ordering (Clarification 3) is part of FR-029 too. The question for this old task: does the code already do this?

**Hypotheses.**
1. *Already built by T-051's FIFO worker*: **confirmed.** `dictation::run_worker` is the only caller of `run_job` / `retry`, and jobs are pushed in stop order under the session lock (the `releasing` mutex orders stops from the hotkey thread and the timer). `PressContext` holds the start window from the press. A failure or no-speech is a `JobEnd`, and the worker moves on to the next job.
2. *A second path delivers outside the worker*: **refuted.** grep `.run_job(` finds only the worker and tests. `Pipeline::retry` is called only by the worker (`Job::Retry`; dictation-session.md invariant 1).
3. *Order holds, but a failure or no-speech blocks or reorders B when they overlap*: **not refuted by a test, but refuted by reading the code.** `run_worker` handles every `Done` variant and loops on. No existing test overlaps them: the failure and no-speech tests wait for each job before the next press.
4. *Each job goes to its own window when they overlap*: covered for one job (`start_window_and_settings_are_taken_once_at_press`). No test has two overlapping jobs in W1 and W2.
5. *This class was fixed before*: no `delivery-order` entry in docs/failures.md, and no earlier task of the class.

**What is not built:** the parallel `process` of research R-10 / tasks.md T052 (a `DeliveryQueue` in queue.rs, a thread per job, one delivery thread). Today a later dictation's stop→paste time includes the earlier job's remaining engine time. This affects neither FR-23's Acceptance nor NFR-01 as it is measured (sequential phrases, one at a time). T-051 chose the FIFO design deliberately. Decision #48 and T-051 Notes still describe T-011 as replacing the worker, so the docs disagree with each other until Q1 is decided.

**Owner question Q1 (blocks IN_PROGRESS; scope decision against design_ref T052 / decision #48):**
- **(A) recommended:** narrow T-011 to three overlapping characterization tests (two windows; failing A; no-speech A) on the existing FIFO worker. Restate the third Acceptance line as "fails under its named bite". Update the docs that still promise the parallel design. Cost: small. Latency: unchanged; the head-of-line wait exists only while dictations overlap and is bounded by the 30 s (+15 s) timeouts.
- **(B):** build R-10's parallel processing with a seq-keyed DeliveryQueue and one delivery thread. Benefit: B's wait ≈ max(A remaining, B's own time) instead of their sum. Cost and risk: concurrent use of the one local whisper model (residency), pending-slot and retry seq ordering, and rewriting dictation-session.md invariant 1. Better as its own task once a benchmark shows overlapping dictations are common and slow.
- **(C):** close T-011 as done by T-051 with no new tests. This leaves the overlapping failure, no-speech and two-window cases pinned only by reading the code.

**Tools.** Serena `get_symbols_overview` / `find_symbol` on dictation.rs. Serena `find_referencing_symbols` failed on the `Pipeline/run_job` name path, so callers were found with grep. grep was also used for docs, specs and the test file. No test was run (all the cited tests are existing ones; nothing is claimed red).
