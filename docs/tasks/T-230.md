## Investigation

Main tree, main 7b0f4fa9, 2026-11-18. Tools: grep and sed for YAML, bash and markdown (Serena does not parse them, so it was not used for those files); gh for the run timings (read only); context7 `/github/docs` for step env precedence and the custom-shell syntax.

**Frame.** Four review tails in one umbrella. Symptom 1: a hanging shell test held run 43577968221 for 86 min, until someone cancelled it (the bound would have been 360). Symptom 3: the "awaiting CI" wait inside a stage rests on a prompt sentence only.

**Hypotheses.**
1. *No bound anywhere on the windows job* (confirmed): no `timeout-minutes` in the job head or on the cargo test steps (evidence).
2. *The token-holding contour steps read config the session can write* (confirmed for git, python and gh by reading the steps): the push step has no `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`, `--template=` or `PYTHONNOUSERSITE`, and pre-push runs `python3 -c`. The staging step has no `BASH_ENV` or PATH pin. The chain steps run `gh` with `GH_TOKEN`, the inherited PATH and `$HOME/.config/gh`.
3. *The same concern is handled on a second path* (confirmed, and it widens the scope): the task text names only the push and staging steps, but both chain steps (`Chain: the next stage`, `Chain: the stage failed`) hold `GH_TOKEN` too, with no pin. A planted `gh` on a `GITHUB_PATH` entry, or a gh config `http_unix_socket`, receives the token there. The invariant therefore covers every post-session step that holds a token, not a list.
4. *The class was fixed before* (partly): T-202 r1 put the pins on the push step (BASH_ENV, PATH, the extraheader with no config file, the hooks from BEFORE instead of the session tree). T-206 added the scan. Each fix pinned one step, and no guard pins the step text, so the next step down was missed (the staging step in T-206, the chain steps in T-202). This is why the approach makes the whole post-session tail an owned literal. It is not an rca recurrence: T-202 and T-206 each fixed what their review named.
5. *Hooks from BEFORE are trusted* (refuted as a guarantee): BEFORE = `git rev-parse HEAD` after `git checkout -B task/<ID> FETCH_HEAD`, the head a previous contour stage pushed. Nothing reviewed it, so a stage-N edit of pre-push governs the push of stage N+1.

**Timing evidence (gh, 40 green ci.yml runs, main and wip).** Workspace cargo test: at most 10 min. `cargo test -p voicen`: at most 7 min. Windows job: at most 30 min. None of these runs had a cold cache, so the developer should read one cold wip run before fixing 30/30/120.

**Root cause.** See `analysis.root_cause`. The common mechanism of part 2: protection is per step and by hand, and the session shares the OS user with every later step. Each step that misses a pin, or loses one later, silently reads session-writable state.

**What stays open after Option A (goes to ci-toolchain.md Not caught).** (i) Whether a step's own `env:` wins over a value the session wrote to the GITHUB_ENV file: docs are silent (context7 `/github/docs`, `actions-env-var-note.md` covers only step versus job and workflow). (iv) The session runs Docker (Rust only in images; preflight `docker info`), which makes it root-equivalent on the runner host.
