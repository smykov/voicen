## Investigation

Tools: Serena was not connected in this session; context came from file reads and grep over `crates/voicen-core`, `src-tauri`, `src`, `specs/001-dictation-via-api`, `docs/`. cpal behaviour was read from the pinned cpal 0.18.2 sources in the core image's registry cache (`.teamwright/cache/core/.../cpal-0.18.2`), not from context7 or memory. No Rust was run: every finding below is a code fact, and the behaviour is new (a feature), so there is no failing run to reproduce.

### Frame

- Expected (FR-27; spec 001 US6, FR-030/FR-031; data-model `MicrophoneChoice`): the selected microphone is used when present; when missing, the Windows default input device is used and `notice.mic_fallback` "Using {device}" is shown once per device change, until the selected one returns; a device lost mid-recording stops the recording and the captured audio is processed; no device at all → FR-04 failure branch (no recording state, "microphone unavailable: no input device"). Also owned here (decision #64): `settings_list_microphones` (`[{ id, name, is_default }]`, spec 004 contracts/ipc.md) and the Recording-tab microphone field.
- Today: every press records cpal's default input device; the saved `settings.microphone` is never read; a lost device ends the frames silently and the recording stays on (hold: until release; toggle: until the next press or the 10-minute stop); `RecordingStarted.device` is always `Selected`.

### Hypotheses (feature: "what is missing and where would a second path come from")

1. **No device notion in the port** — confirmed: `platform::AudioSource::start(sink)` has no device argument and no enumeration; `CpalSource::open` calls `default_host().default_input_device()`.
2. **Device loss has no signal** — confirmed: `win::capture::build` passes `|_err: Error| {}` as cpal's error callback (comment: "T-012 owns its notice"); `FrameSink` has only `frames`; `RecordingController` has no loss input and `RecordingEnd` no `DeviceLost` (its doc: "T-010 and T-012 add the other variants").
3. **A second path for the same concern** — risk, not present yet: the device list for the settings UI and the device choice at a press could be two enumerations with two matching rules (P-010). The approach makes `AudioSource::devices()` the one list for both.
4. **The fallback decided in the adapter** — the easy shape (`start(preferred_id)` tries the id, else the default) puts FR-27's decision in Windows-only code provable only on Windows CI, against the architecture rule "the adapters carry out and stamp, they decide nothing" (`docs/architecture.md`, dictation wiring row; decision #64). Rejected as option B below.
5. **This class was fixed before** — no: class `audio-device` has no other task and no `docs/failures.md` entry.

### Evidence from the pinned cpal 0.18.2 (shapes the shell half)

- Identity: `DeviceTrait::id()` → `DeviceId(HostId::Wasapi, <IMMDevice::GetId endpoint id>)`, persisted via `Display`/`FromStr`; `HostTrait::device_by_id`, `input_devices()`; display name from `description()?.name()`. Research R-3 asked for the endpoint id "when the pinned cpal exposes one": it does, so the saved `Microphone.id` is the endpoint id string and matching is by id only (the name is for display).
- Enumeration lists `DEVICE_STATE_ACTIVE` endpoints only (`host/wasapi/device.rs`, `EnumAudioEndpoints(eAll, DEVICE_STATE_ACTIVE)`): an unplugged USB mic is absent from the list, which is what "missing" means.
- A stream built from `default_input_device()` (`DeviceHandle::DefaultInput`) gets a `DefaultDeviceMonitor`: a default-device change emits `StreamInvalidated` (or `DeviceNotAvailable` if no default is left) **and the stream keeps running** on the old endpoint (`host/wasapi/stream.rs` `process_commands_and_await_signal`, `default_device_change_error`: "WASAPI never rebinds the IAudioClient"). A stream from a `Specific` device has no monitor (`default_device_monitor` returns `None`), and in `run_input` every `emit_error` is followed by the loop ending (the `realtime` boost error is the only exception, and that feature is off: `src-tauri/Cargo.toml` `cpal = "0.18"`, cpal `default = []`). So **opening by id makes "error callback called" equal "capture ended"**, which is the loss signal FR-031 needs, and also removes the monitor's COM-apartment concern recorded in `docs/decisions/windows-shell.md` (T-006 review 1 #5). Unplugging maps `AUDCLNT_E_DEVICE_INVALIDATED` → `DeviceNotAvailable` (`host/wasapi/mod.rs`).
- Lock contract (`platform.rs` `AudioSource`/`CaptureHandle` docs, `docs/decisions/windows-shell.md` invariant 2): the session may drop a live handle under its lock, and dropping a cpal stream joins its stream thread. So the error callback must never take the session lock, directly or through the sink: the sink's `device_lost` must only record and hand off without blocking.

### Root cause / rationale

Feature gap: the capture port was built for the default device only (T-051/T-006 scope, decision #64 moved device choice and loss here), so neither the choice, the notify-once rule nor device loss has a place to live yet. See `analysis.root_cause`.

### Invariant

See `analysis.invariant`. Closed form: (1) one decider for the device (core `microphone::choose`, inputs = selected id + the list taken at that press); (2) one producer of the fallback notice (the tracker, committed only after the capture opened, so a fallback that then fails to open shows "microphone unavailable" and notifies on the next successful one); (3) one route for an unrequested end of capture (`FrameSink::device_lost` → session loss channel → `RecordingController::device_lost(id, at)` → `stop_recording`), stale ids ignored.

`choose` rules (closed): selected `Some(id)` and present → `Use{id, Selected}`; selected `None` → the device flagged default, `Selected` (data-model: none selected = default, no notice); selected missing → the default, `Fallback`; no device flagged default (incl. an empty list) → `NoDevice` (FR-04 branch, no `start` call). Tracker: notice on `Selected→Fallback(x)` and `Fallback(x)→Fallback(y)`; none on `Fallback(x)→Fallback(x)` or `→Selected`; in memory only (OQ-24).

Implementation notes for the developer (not a design change):

- Device loss: the sink records `lost_at` once under its own short lock and sends `(RecordingId, Instant)` on an `mpsc::Sender` (never blocks, never takes the session lock); a session "capture-watch" thread (spawned in `DictationSession::start`, joined in `Drop` after the senders are gone) calls `stop_recording(shared, at, |c| c.device_lost(id, at).map(Ended::Stop))`. Using the timer's condvar instead would miss wake-ups (the flag is not under the session mutex). `device_lost` for a stale or already-ended id → `None`; a later hold release is then `Release::Ignored` (no live recording). It always yields a ticket (no `MIN_HOLD` discard: "process what was captured"; the speech gate decides an almost-empty one). `held` = loss instant − start.
- `RecordingEnd::DeviceLost` is added to the log format (`diag`, `end=device_lost`) in the same change; `RecordingStarted.device` comes from the `LiveCapture`'s kind instead of the literal `Selected`; no device name or id goes into any event (FR-033 allowlist).
- The notice: `notice.mic_fallback` with param `device` = the device's display name, through `RecordingController::notice` after `start` succeeded, inside the lock, `publish` after; add the id to `messages!` and the en/ru catalog (contracts/messages.md already lists it). Toast: T-007's notifier on the same path (OQ-24).
- Shell: `CpalSource::devices()` = `input_devices()` with `id()`, `description()?.name()` and `is_default` (the default's id compared), in `open_bounded`; `start(id)` = `device_by_id` (missing → `NoDevice`) then the existing format match; the error callback calls `sink.device_lost(Instant::now())` once (an `AtomicBool`), whatever the error kind. `settings_list_microphones` returns `[{ id, name, is_default }]`; the Recording tab shows "System default" (null) plus the list, and a saved id that is absent as "<name> (not connected)" (spec 004 contracts/ipc.md). UI: unit + Playwright e2e with the mocked IPC (surface `ui`).
- Tests on Windows CI: the runner has no capture endpoint (`docs/decisions/windows-shell.md`), so `src-tauri/tests/capture.rs` proves the error map, `devices()` returning whatever the runner has without panicking, `start` on an unknown id → `NoDevice`, and the error-callback → `device_lost` once (through the injected/WAV source the task list T055 names); a real unplug is the owner's check (quickstart §3 step 5).
- Docs in the same commit: `docs/architecture.md` (platform traits row, dictation wiring row), `docs/decisions/dictation-session.md` (new invariant: the device choice and device loss), `docs/decisions/windows-shell.md` (open by id; error callback = capture ended), spec 001 contracts/core-traits.md (`AudioSource`/`FrameSink`), research R-3 (endpoint id is exposed).
