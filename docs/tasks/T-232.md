## Context

OQ-87 → decisions #306 (owner, 2026-11-18): spec 007 US9 #3 / FR-33 — when the call hotkey is taken by another program at startup, a notice only (no settings window, no tray hotkey-error state, dictation works), and the Calls tab marks the call hotkey. T-129 keeps the mark in the shell as `CallHotkeyMark` (`voicen_lib::dictation::call_hotkey_mark`, read by tests only); no wire carries it to the UI, and T-155 marks the field only from a save error.

Decided: (a) a `SettingsView` field read by `settings_get`, so the Calls tab shows the mark whenever it opens while the startup registration of the call slot failed. `specs/007-call-mode-record/contracts/ipc.md` gains the field (the settings commands' shape changes by one read-only field). Areas: core (view field), shell (fill from `CallHotkeyMark`; cleared when a later registration of the call slot succeeds, e.g. after a save), ui (Calls tab mark). Depends on T-155 (the tab).

Owner, decisions #373 (2026-11-26): the mark comes from the saved view and **stays while the user edits the call hotkey until a successful save** (not hidden while the draft differs). Taken with it: field `call_hotkey_unavailable`, always a bool; text `error.hotkey.unavailable`; Calls tab only, a draft's own save error on the field wins; no live update while the window is open. `surface: ui` (the mark is user-visible; verify runs the e2e case).

## Acceptance

- [ ] `settings_get` returns the startup call-hotkey conflict as a read-only `SettingsView` field: set while the call slot failed to register, absent/false otherwise; documented in `contracts/ipc.md`
- [ ] The Calls tab marks the call hotkey field when the field is set, without a save; no mark when it is not set (unit + `e2e/settings-calls.spec.ts` with the mocked wire)
- [ ] The mark clears after a save that registers the call hotkey successfully (the next `settings_get` reads it cleared)
- [ ] Failure branch: the call slot is taken at startup → notice only, no settings window, dictation works, and opening Settings → Calls shows the mark (shell test in `src-tauri/tests/call_hotkey.rs` for the field; UI e2e for the mark)
- [ ] Test that fails without the change: `<core view test>`, `src-tauri/tests/call_hotkey.rs` field case, `e2e/settings-calls.spec.ts` startup-mark case

## Investigation

Context: Serena tools loaded; code read through grep and file reads of the named symbols (Svelte and the task docs are not covered by the language server in this tree). No library API is involved (no Context7 lookup needed: serde `Serialize` on a `bool` field, Tauri `State` unchanged).

**Frame.** Observed: with Ctrl+Alt+R taken at startup the shell offers `notice.call_hotkey_conflict` and sets `CallHotkeyMark` (T-129, proven by `src-tauri/tests/call_hotkey.rs`), but opening Settings → Calls shows no mark; the field is marked only after a refused save (`hotkey.unavailable`, T-155). Expected (US9 #3, FR-004, decisions #306 (a)): the tab marks the call hotkey whenever it opens while the startup registration failed.

**What T-155 already built** (DONE): the Calls tab `src/lib/settings/tabs/Calls.svelte` with the shared `HotkeyField` (`field="calls.hotkey"`, `errors={draft.errors}`), the `provider_host` view field as the precedent for a read-only core-computed `SettingsView` field (filled in `view_with`, pinned by `e2e_settings_wire_fixture_matches_core` and `call_settings.rs` fixture tests, read in the tab from `draft.baseline`), the `refused_call_hotkey_unavailable` fixture and the e2e case that marks the field from a save error. Nothing reads `CallHotkeyMark` outside tests.

**Hypotheses.**
1. The view has no input for the mark (confirmed: `view_with` reads only settings, keys, `self.load` and `provider_host_of`; `SettingsDeps` has no state read; `HotkeyRegistrar` is write-only).
2. A second path builds a view (refuted: `view()` and `save()` both call `view_with`; the change bridge and `settings_get` call `view()`; the only other `SettingsView {` literal is a service.rs test). This is why the fill belongs in `view_with`, not in `settings_get`.
3. The mark would be stale in the Saved view after a call-hotkey save (refuted: `save()` step (8) commits before `view_with`; the shell's `commit_within` waits for `done`, which the thread sends after `call_result(true)` cleared the mark). Residual: on a `REQUEST_BUDGET` timeout the commit is unconfirmed and the view would still say true — conservative, acceptable.
4. This class was fixed before: not a defect class; the same gap shape (UI needs a core-owned fact) was closed by `provider_host` (decisions #319), and the same placement is used here.

**Exactly one mark state.** Today `start_dictation_with` creates the mark and `app.manage`s it; the registrar handle is created earlier in `run()` (`lib.rs`, `HotkeyRegistrarHandle::new()`) and given to `load_settings_with`. Moving the `Arc<CallHotkeyMark>` into `HotkeyRegistrarHandle` (created with it) and having `start_dictation_with` take it from `ports.hotkeys` keeps one state for the thread's `CallPort`, the test reader `call_hotkey_mark` and the view. Before the call slot starts the field is false (no failure observed yet); `settings_ipc::load_settings` (no thread) also reads false.

**Clearing.** The thread clears the mark on any later success of the call slot: a save that changes `calls.hotkey` to a free combination (commit), or a resume/unlock reassert. A save that leaves `calls.hotkey` unchanged does not re-register (`save()` (4b) runs only when the hotkey text differs), so the mark rightly stays and the Saved view still carries true.

**Split?** No. The wire change is one field that must land atomically in core (field, fixture), contract, TS type and the tab; the shell part is a few lines (handle owns the mark) and is proven only by Windows CI (`call_hotkey.rs`). Decision #306 already scoped it as one task over three areas. If the owner wants the Linux-provable part separate, the split would be core+ui (with the fake registrar) vs shell, but the shell task alone would carry the end-to-end Acceptance line; not recommended.

**Minor defaults taken (owner may override):** (d1) field name `call_hotkey_unavailable`, always present as a bool (like `provider_host`, the key is never omitted); (d2) the mark reuses the save-error text `error.hotkey.unavailable` (no new catalog id); (d3) the mark shows only on the Calls tab (no form-level list and no tab switch when Settings opens on another tab), and a draft error on `calls.hotkey` takes precedence; (d4) the mark is from the baseline, so it is shown even while the draft's call hotkey is edited but unsaved — alternatively hide it while the draft value differs from the saved one; (d5) not live: a reassert that changes the state while the window is open is seen at the next `settings_get` / Saved / `settings://changed`.

**Note for the orchestrator:** `surface: "none"` while the change has a UI-visible part (Calls tab mark) and a shell part; check whether the surface should name the UI so the verify record covers it.
