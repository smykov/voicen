## Context

Cut from T-025 by decision #76. FR-034 / FR-28 v4: all app data, WebView2 included, lives under `%LOCALAPPDATA%\Voicen`, so the uninstaller's folder removal takes it too. tauri 2.12.1 `src/manager/webview.rs:559-564` uses `app_local_data_dir()` (`%LOCALAPPDATA%\dev.voicen.app`) when a window sets no `data_directory`; `settings_window::open` (settings_window.rs:83) and the overlay build (src-tauri/src/overlay.rs:347) set none. One helper (e.g. `paths::webview_dir()`) used by every window builder; depends on T-057 because it touches `overlay.rs`. T-057 is DEFERRED and its overlay work landed in T-067 (DONE), so the dependency is T-067 (2026-11-11, contour run 42969717639: the router refused T-062 as not ready while it waited on the deferred T-057).

## Acceptance

- [ ] Windows CI: after the settings window and the overlay are opened, WebView2 data exists under `%LOCALAPPDATA%\Voicen\webview` and `%LOCALAPPDATA%\dev.voicen.app` does not exist
- [ ] Failure branch: a new window builder that does not use the helper fails a check (test or gate) — Windows CI / Linux gate
- [ ] Test that fails without the change: the Windows CI step / test named by the analysis

## Investigation

**Tools.** Serena was not loaded in this session: `ToolSearch` returned only the context7 tools. So code was read with grep and file reads, scoped to `src-tauri/src`, `src-tauri/tests`, `src-tauri/*.json` and `.github/workflows/ci.yml`. context7 was not needed. The pinned crates are not in `.teamwright/cache/core/_usr_local_cargo_registry` or `~/.cargo`. I downloaded them from static.crates.io into `/tmp`, checked each sha256 against `Cargo.lock`, and read the source there.

**Frame.** Observed: every build writes WebView2 data to `%LOCALAPPDATA%\dev.voicen.app`, and nothing removes it (`docs/decisions/installer.md:69`). Expected (FR-28 v4, spec FR-034): all app data, WebView2 included, lives under `%LOCALAPPDATA%\Voicen`, so the uninstaller's folder removal takes it too. The uninstall hook enumerates `Voicen\*.*` (`installer-hooks.nsh:236-247`), so a `webview\` subfolder is covered with no hook change.

**Window inventory (re-verified; the task's line numbers moved).**
- `settings_window::open`: `settings_window.rs:86-91` (was :83). No `data_directory`.
- `OverlayThread::build`: `overlay.rs:439-455` (was :347, then :353). No `data_directory`.
- Not found: other builders, `WebviewBuilder`/`add_child`, config windows (`tauri.conf.json:13` `"windows": []`) or `app_*_dir` uses in `src-tauri/src`.
- The call indicator (1a, OQ-52 (a)) is not built yet. The About box is muda's native dialog, not a webview.
- Test-only builders in `src-tauri/tests/*.rs` (app_acl, overlay_ipc, settings_window, local_models, settings_ipc, autostart, diag) are out of the product invariant.

**How tauri 2.12.1 picks the folder** (verified in source):
- `WebviewManager::prepare_webview` (`manager/webview.rs:559-569`, `impl<R: Runtime>`, so the mock runtime too) fills an unset `data_directory` with `app_local_data_dir()`, then runs `create_dir_all` on it (:571-575).
- `app_local_data_dir` (`path/desktop.rs:265-271`) is `dirs::data_local_dir()/identifier`, unless `app.app_directories_override` is set (`path/mod.rs:397-437`; an absolute path is used as is, :479-481).
- tauri-utils 2.10.1 `config.rs:3397-3404`: the override reaches "Tauri itself (the default webview data directory on Windows and Linux) and plugins". The only exception is a window's `dataDirectory` config.
- `Context::config_mut` (`lib.rs:420-438`) is documented for setting it at runtime before build.
- WebView2 constraint: tauri-runtime-wry keeps one `WryWebContext` per `data_directory` key (`lib.rs:4706-4737`). Windows with different browser args or options must have different folders (`webview_window.rs:1075`; config.rs:2279). One shared resolution keeps both windows in one environment.

**Other writers of `dev.voicen.app`.**
- tauri-plugin-single-instance 2.5.2 (Windows) uses the identifier only as a mutex/window name (`platform_impl/windows.rs:59`). It writes no files.
- tauri itself calls `app_local_data_dir()` only at `manager/webview.rs:563`.
- Hypothesis, not verified on a runner: `cargo test -p voicen` (`ci.yml:193`) runs before the install. Its tests with `generate_context!(test = true)` (identifier `dev.voicen.app`) build windows on the mock runtime, so `create_dir_all` probably leaves an empty `%LOCALAPPDATA%\dev.voicen.app` behind. So the new smoke step removes any leftover and logs whether it was there before it launches. Its verdict then speaks only about the installed app.

**Hypotheses.**
1. *No window sets a data directory, and tauri defaults to the identifier folder.* Confirmed (above).
2. *A second path writes the folder* (a plugin, a tauri internal, a config window). Refuted for single-instance, the tauri internals and the config. The test-process leftover is above.
3. *This class was fixed before.* No: `docs/failures.md` has no WebView2 or data-folder entry (grep `webview`, `dev.voicen.app`). The T-025 analysis cut this item out (decision #76) and did not patch it.
4. *A per-window helper is the right seam* (spec 006 T027, `window.rs webview_window(...)`). Weaker than the override, see Option B.

**Root cause.** Need, not defect. See `analysis.root_cause`.

**Options.**
- **A (recommended): app-level override in the release context.**
  - What: `paths.rs` gets `webview_dir()` and one helper that sets `context.config_mut().app.app_directories_override = Some(AppDirectoriesOverride::Directories(AppDirectoryOverrides { local_data: Some(root.join("webview")), ..Default::default() }))`. `run()` calls it with `paths::data_dir()` on `tauri::generate_context!()` before `assemble`.
  - Why it removes the cause: tauri's own default now resolves inside the data folder, so every webview, current or future, lands there without per-builder code. That is an invariant (P-002), not a call-site list. The path comes from the one resolver (P-010), not from tauri's `$LOCALDATA` known-folder lookup, which differs from `paths::data_dir`'s env-var read.
  - Not in `tauri.conf.json`: there `generate_context!` in the shell tests would get it too, and they would write the runner's real `%LOCALAPPDATA%\Voicen\webview`.
  - Red, then green:
    1. The new install-smoke step: settings window + hotkey-hold overlay, then `Voicen\webview\EBWebView` exists and `dev.voicen.app` does not.
    2. `src-tauri/tests/webview_data.rs`: the helper with a TempDir root makes `root\webview` appear after `settings_window::open` and the overlay build; without the helper it does not.
    3. The tripwire fixtures.
  - P-013 (the config reaches the runtime) is proven by the smoke on the installed exe.
  - Risks:
    - msedgewebview2 children that outlive voicen can lock `webview\` for the later uninstall steps (`ci.yml:1379`, `:1601`). `Stop-AllVoicen` (`hotkey-hold.ps1:111-118`) waits only for `voicen`; extend it to wait for msedgewebview2.
    - The first launch after the upgrade starts with an empty WebView2 profile. Nothing is kept in the webview today; settings live in `settings.json`.
    - The old `%LOCALAPPDATA%\dev.voicen.app` on a user machine stays. A one-time cleanup is a product choice and not part of this task; the orchestrator raises it as an open question if wanted.
  - Rollback: remove the `run()` call.
- **B: per-window helper** (`window::builder(app, label, url)` with `.data_directory(paths::webview_dir())`, spec T027) and a tripwire that `WebviewWindowBuilder::new` occurs only in that module.
  - Closes the class only for builders spelled that way: `WebviewBuilder` + `Window::add_child`, `WebviewWindow::builder` and config windows bypass a call-name list. That is the F-008 shape (an identity list beside a graph that changes).
  - The helper reads the real `paths::data_dir()`, so every shell test that calls `settings_window::open` would write the runner's real `%LOCALAPPDATA%\Voicen\webview`, unless the root is injected through the app.
  - Rejected.
- **C: `.data_directory(...)` on the two builders.** A case list, and it repeats B's test problem. Rejected.

**Failure branch (acceptance 2).** With A, a new builder that does nothing is already covered. The only way around is an explicit per-window data directory: `.data_directory(...)`, or a config window's `dataDirectory`, which the override does not affect (tauri-utils config.rs:2273, :3404). The other failure is losing the override. The tripwire refuses both cases on the Linux gate, and its fixtures prove it bites. It decides on raw tokens it owns (P-020), see `analysis.decides_on`. Guard paths touched: `scripts/ci/webview-data.sh`, its fixtures, the `Makefile` target, `scripts/ci/hotkey-hold.ps1`. So `checker: true` is set, and the `decides_on` row goes into the guard table of `docs/decisions/ci-toolchain.md`.

**Size.** Small: one seam (the release context's app-directory resolution, one helper in `paths.rs`, called once in `run()`). The behaviour is settled by FR-28 v4 and decision #76. The CI step and the tripwire are its proof, not a second seam. No spec tool needed. Spec 006 T027's `window.rs` helper is superseded by Option A; note it as built in the spec.

**Recurrence.** None. No F-NNN of the class. Related rules: F-008 (an identity list beside a dependency graph) argues against Option B's call-name tripwire. P-010 and P-011.
