## Investigation

Tools: Serena was not loadable in this session (ToolSearch found no `mcp__serena__*`); context came from grep and file reads over `src-tauri/src`, `crates/voicen-core/src`, `src/lib`, `i18n/`, `specs/`, `docs/`. Context7 was not needed (no library API changes).

**Frame.** Observed: on Windows, an input endpoint whose name cannot be read is listed as `Microphone` in the settings select, and the fallback notice says `Используется Microphone` in the RU UI. Expected: the RU UI and notice say `Микрофон` (decisions #203). The literal is in Windows-only code, so the symptom cannot be seen end to end on Linux.

**Hypotheses.**
1. The shell turns "no name" into English display text before any renderer sees it. Confirmed: `capture.rs` `UNNAMED`, used in `list`. After that the name is opaque user content (`pick`, `list_microphones`, `MicrophoneField`).
2. A renderer drops a localised name. Refuted: both renderers pass the name through correctly. `i18n::text` localises only `NESTED_IDS` values (`render_with_nested`), and the UI's `t()` only fills `{name}`.
3. The same concern is handled on a second path. Checked and refuted. `description()` / `.name()` occurs only in `capture.rs::list`. The call-mode capture (`win/track_capture.rs`) shows no device names. `CaptureError::Other` literals in `capture.rs` never reach the user, because `MicCause::of` maps them to `mic_reason.other`. The only renderer of `notice.mic_fallback` is `overlay_payload`, since the T-007 toast is still `TODO`.
4. This class was fixed before. `docs/failures.md` has no entry for user-visible English text that bypasses the catalog. The search covered the terms locali*, ru ui, russian, hard-coded, untranslated, english-only. The nearby rules are `docs/decisions/windows-shell.md` ("Don't spell a menu id, catalog id or tooltip in the shell") and `docs/decisions/i18n.md` (nested ids for language-independent params, T-042). No recurrence, so no rca.

**Persistence.** `settings::Microphone { id, name }` stores the last known name for display only. Devices are matched only by the whole id (`microphone::choose`; settings-ui.md P says "Don't ... match a saved device by name"). So the fix does not change selection. After the fix a newly saved nameless device stores `name: ""`, and `MicrophoneField` shows it as `t("mic_name.unnamed")`. The model has no validation of `name`, and an empty string parses (`partial_microphone_object_is_unreadable` requires only that both keys exist). Residual: a `settings.json` saved before the fix keeps `"name": "Microphone"`. That name appears only in the "not connected" or pending option and is indistinguishable from a real device called Microphone. No migration is proposed.

**Known limitation (extend i18n.md).** A real device named exactly `mic_name.unnamed` would render as the fallback text. This is the same documented limitation as the `mic_reason.*` ids (i18n.md "Known limitation").

**Docs to update with the fix.** `platform.rs` `InputDevice.name` doc ("empty = no name"). The `capture.rs` const and doc. `docs/decisions/i18n.md` (nested group gains `mic_name.unnamed`; the UI renders the same id with `t()` for the list). `docs/decisions/settings-ui.md` P (empty name option text). `specs/004-settings-and-first-run/contracts/ipc.md` (`name` may be `""`). `specs/001-dictation-via-api/contracts/messages.md` `notice.mic_fallback` row (`{device}` is the name or the unnamed text).

**Size.** Small. One contract (`InputDevice.name`) has one producer (shell) and two consumers (core notice param, UI select) that route through one catalog id. Behaviour is settled by #203. No open question, no blocker.
