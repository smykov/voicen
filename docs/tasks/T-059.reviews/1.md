What was read and checked:
- **Win32 calls.** Each was checked against the windows 0.62.2 / windows-result 0.4.1 sources in `.teamwright/cache/core`.
  - Signatures and `Result` handling match:
    - `GlobalUnlock` is `BOOL.ok()`. Its last unlock gives `Error::from_thread()` with last error 0, and `code()` then returns `HRESULT(0)` (`nonzero_hresult` → `S_EMPTY_ERROR`, `error.rs:72-77,123-129`). So `runner_probe.rs:828-833` treats it as success, correctly.
    - `GlobalFree`'s NULL success arrives as `Err`, and its result is dropped (:846-849).
    - `GlobalFree` runs only on the lock, unlock or `SetClipboardData` failure paths, never after a successful `SetClipboardData` (:812-842).
    - `CloseClipboard` runs on every path after a successful open, through `Opened`. It is created only right after `open_clipboard` succeeds (:539-546, :903, :917, :531).
    - No handle type has a `Drop`.
    - `SetForegroundWindow`, `PeekMessageW` and `TranslateMessage` return raw `BOOL`s and are read with `as_bool`.
  - Every item used needs only its module feature, and all eight modules plus `Win32_Foundation` are on the one release line. Hypothesis 6 holds. `Cargo.lock` and `THIRD-PARTY-NOTICES.txt` are untouched, and windows 0.62.2 has no optional deps.
- **Message pumping.**
  - `PeekMessageW(None, PM_REMOVE)` takes at most `PUMP_MAX` = 10 000 messages per pump, and every `poll` is bounded by `WAIT`.
  - The developer's deviation: in the hotkey and async polls, keyboard messages (`WM_KEYFIRST..=WM_KEYLAST`) are taken from the queue but neither translated nor dispatched (:625-643). **Judged correct and necessary.**
    - When `RegisterHotKey` fails, Space reaches the window. A dispatched `WM_SYSKEYDOWN`/`WM_SYSCHAR` Space then makes `DefWindowProc` raise `SC_KEYMENU` and open the system menu, a modal loop inside `DispatchMessageW`. The thread would hang there with Ctrl and Alt held, and `Release` would never run.
    - Non-keyboard messages, `WM_HOTKEY` (0x312) included, are still dispatched and recorded.
    - The `GetKeyState` queue state updates on removal, and `GetAsyncKeyState` is asynchronous, so not dispatching costs no measurement.
    - Leftover keyboard messages after the last pump are discarded at `DestroyWindow` and thread exit, never dispatched.
- **Key release.**
  - `Release` is armed before each key-down `SendInput`: `VK_A` at :769→:772, the hotkey batch at :951→:964.
  - The hotkey release (mask 0xE8 down/up, then Space↑ Alt↑ Ctrl↑) is sent unconditionally at :983, even when 0 or a partial count was inserted. On a short insert, the drop retries once.
  - Unwinding also sends it.
- **Owning thread.** `UnregisterHotKey` runs through `Hotkey` at the end of `hotkey_and_async_keys`. Then `ClipboardCleanup` and then `DestroyWindow` (`Window`) run in reverse declaration order at the end of `window_facts`. All of this is on the window thread. Every guard is bound to a named `_x`, never to a bare `_`.
- **Bounded time.**
  - Worst case for the window thread: about 15 s (3+3+2+3+3+0.5).
  - `phase` uses `recv_timeout` up to the 60 s deadline. Late facts after the deadline go into a dropped receiver and are never printed.
  - `settle` waits at most `WAIT` per thread with `is_finished` and joins only finished threads.
  - Total: at most about 66 s plus compile time. The step's 10-minute timeout is the backstop for a process-exit hang.
  - With `--test-threads=1`, libtest waits on `rx.recv()` and prints no 60 s warning.
  - A cross-process `SendMessage` (`EmptyClipboard` → `WM_DESTROYCLIPBOARD` to a hung foreign owner) is the only unbounded call, and the watchdog covers it.
- **No red on a missing capability.**
  - Every capability path returns a `Fact`, and there is no `unwrap` or `expect` on OS results.
  - The `try_into().unwrap()` calls inside the bindings take lengths of 256 and ≤5.
  - No arithmetic can overflow.
  - Both threads send all 6 of their facts on every path (`window_facts` sends 6 `skipped(no_window)` lines when `CreateWindowExW` fails).
  - So the assert at :286 fires only on a panic, an early end or a duplicate.
- **Exactly once.** `accept` rejects duplicates and facts from the wrong thread (:234-243). The timeout fill covers only facts not yet printed (:274-278). The end count is `printed.len()`, which is always 12.
- **Sanitising and privacy.**

  - Only class names of foreign windows are printed (`before`, `now`, `focus`), never titles.
  - No user name, host name or pid is printed (the pid sits only inside the fake clipboard text), and the clipboard is emptied at the end.
