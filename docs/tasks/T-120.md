## Context

Foundational for spec 007. Spec FR-004, FR-031, FR-038, FR-039, FR-040; req FR-33, FR-59, FR-67, FR-80; data-model.md "CallSettings". Area core, seam `crates/voicen-core/src/settings/` (`validate.rs`, `mod.rs`, `service.rs`) and `e2e/fixtures/settings-wire.json`. Phase 2 starts after T-116.

## Acceptance

- [ ] The `calls` section has the data-model.md defaults; an older `settings.json` without it loads with them and `SCHEMA_VERSION` stays 1 (T012, T013)
- [ ] Failure branch: a call hotkey equal to the dictation hotkey is refused from either side (`FieldId::CallHotkey`) (T012)
- [ ] Failure branch: an unwritable storage root (`.voicen-write-probe` create and delete fails) is refused as `StorageRoot unwritable{reason}` (T012)
- [ ] A new root appends the old one to `earlier_roots`, without duplicates (T012)
- [ ] Failure branch: an unknown primary language is refused (`PrimaryLanguage`) (T012)

- [ ] Test that fails without the change: the `settings/` validation and wire tests

## Investigation

Tools: Serena was not loaded this session; code was read with grep/sed over `crates/voicen-core/src/settings/`, `src-tauri/src/settings_ipc.rs`, `src/lib/settings/`, `e2e/fixtures/settings-wire.json`, `i18n/`. No library API is new (the `url` crate's `Host` is already used by `url::is_insecure_remote`), so no docs lookup was needed.

**Frame.** A feature: the `calls` section and its rules do not exist. Symptom-equivalent: the T012 tests cannot be written against any current symbol.

**Hypotheses checked.**
1. *Second path for loopback*: confirmed risk. `settings::url::is_insecure_remote` holds the only loopback match; a second copy for the provider host would drift (T-015's bite comments in `url::tests::is_insecure_remote_table` list exactly the near misses: `localhost.`, `foo.localhost`, `127.1.2.3`, `LOCALHOST`). Extract one `is_loopback_host(&url::Host)`.
2. *Second path for the write probe*: confirmed risk. R19 runs the probe at save (this task) and at every Record start (T-125 T022). One function, called by both.
3. *Defaults outside `defaults()`*: `docs/decisions/settings.md` forbids field-level `#[serde(default)]` and defaults built in consumers; the section follows the container-default pattern.
4. *Earlier fix of this class*: none. `docs/failures.md` has no settings/call-settings entry; class `call-settings` is new. Not a recurrence.
5. *Probe on every save*: would make every unrelated save fail while a chosen root (USB drive) is unplugged; the same reason the autostart step runs only on change (settings.md, autostart "Don't"). Probe only when the effective root changed.

**Findings the developer needs.**
- `validate` is pure by its module doc, so the probe and the earlier-roots append belong in `SettingsService::save`, after step (3) validate and before step (4) hotkey prepare (the earliest step with a side effect), so a refused root releases nothing.
- The equality rule lives in `validate` over the whole draft, so "from either side" (changing the dictation hotkey to the call hotkey, or the reverse) is one rule. `parse_hotkey` rejects non-canonical text (`hotkey::tests::rejects_non_canonical_text`), so compare parsed values; a call-hotkey grammar error is also refused on `CallHotkey` with the existing `hotkey_code` mapping.
- Edge: a release-1 file whose dictation hotkey is already `Ctrl+Alt+R` loads fine (no validation on load), but then every save is refused on the Calls tab's field until the call hotkey changes. Worth a test and a line in the decision doc; not a reason to change the default without the owner.
- `SettingsView`/`Settings` wire is snake_case; `FieldId` serializes as its dotted `as_str` (`recording.hotkey`). contracts/ipc.md writes `callHotkey`/`storageRoot`/`primaryLanguage`; these read as variant names. Proposed wire ids following the tab-prefix convention: `calls.hotkey`, `calls.reminder`, `calls.primary_language`, `calls.storage_root` (and `FieldId::ALL` 27 -> 31, `expected_field_id` arms).
- New ErrorCodes are not named by the spec: proposed `hotkey.equals_dictation`, `storage.unwritable`; primary language reuses `language.unsupported`. Each needs `error.<code>` in EN and RU (i18n test), and each new FieldId needs `settings.field_label.<id>`; T-119 (catalog, TODO, not a dependency) lists the labels too — whichever lands second must not duplicate; consider `depends_on` or a merge note.
- `{reason}`: `FieldError` is `{field, code}`, `Copy`, and the UI renders `t("error.<code>")` with no parameters (`FieldMessage.svelte`). The contract's `unwritable{reason}` and `settings.calls.storage_unwritable` "This folder can't be written: {reason}" need either a closed `UnwritableReason` (proposed `missing | access_denied | not_a_folder | other`, from `io::ErrorKind`; never the path or the OS text) carried as an optional `reason` on the wire, or one ErrorCode per reason. Either is a wire change the UI task G41 depends on; pick one and pin it in the fixture.
- Primary language default "the UI language": a container default cannot see `ui_language` (the same limitation `settings/mod.rs` documents for `ui_language`), so an older RU file would load `primary_language: en`. Faithful option: deserialize the section's field as optional and fill it from the loaded `ui_language` in one post-deserialize step (documented in settings.md as the one exception); simpler option: accept `en` like `ui_language` and record it. Not decided by the spec; developer proposes, reviewer checks against FR-038.
- `earlier_roots` with a default old root: the default root (`data_dir()/calls`) is known only to the shell (`src-tauri/src/paths.rs::data_dir`). Approach (A) injects it (`SettingsDeps`), so `settings_ipc::load_settings` and 7 core test constructors change and the diff reaches `src-tauri` (P-016 wip run required). Approach (B) avoids that but moves "the default root is always listed" to T-125.
- Unspecified: a relative or empty `storage_root` (proposed: refused as `storage.unwritable` with reason `not_a_folder`/`missing`), and whether the probe creates a missing root (T-126 lists `reason=missing` for a Record start, which suggests it does not).
- Server-owned fields: the settings window sends the whole draft (`draft.ts::saveRequest`); `earlier_roots`, `warned_hosts` and `indicator_position` will be written by other paths (provider notice, indicator drag). Taking them from the snapshot in force in `save` closes the stale-draft overwrite before those writers exist; this is a design choice beyond the Acceptance and should be stated in `docs/decisions/settings.md`.
- "A host is never logged": the settings service logs nothing itself; the shell logs `settings_load` only. The closed log grammar (T-118) is the structural guarantee; here the rule's return type should not implement `Display`, and a test can assert that a save with a cloud base URL leaves the fake log empty of the host.
- UI side effects within this task: only the fixture regeneration (all views in it change). `settingsApi.ts::Settings` gains `calls` in G41; the JSON deep copy in `draft.ts::copy` keeps the section on save meanwhile, so no silent reset.

**Size.** One area (core) and one seam family (`settings/`), but with the gaps above (reason wire shape, ids, the RU default) it is at the edge of "behaviour settled". None of them is a product decision except possibly the primary-language default for upgraded RU files; the rest are wire/naming choices inside the contract. No `blocked_on` proposed.
