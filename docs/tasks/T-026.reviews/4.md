## Why this is a recurrence

- **Mechanism.** The guard is a host-side awk model of three foreign parsers: YAML scalar styles, comments and flow mappings; bash word and command splitting; and gh's argument parsing. It passes whenever its model sees no violation. F-003's rule says: "a guard decides on a switch or on raw text the tool cannot reinterpret, never on a model of another tool's parser". 6e7e7a8 does not apply that rule. It extends the model with a new shell tokenizer, `publishes()`, and a YAML comment and flow-mapping reader, `envtok()`.
- **The test question.** If one more workflow shape appears tomorrow, will the defect return? Yes. I reproduced it on a `git archive 6e7e7a8` copy under `/root/.claude/jobs/97682091/tmp/r4probe`, with the probe in `/root/.claude/jobs/97682091/tmp/r4-probe.py`. Each fixture below is `ok-release` plus one step, and each gives exit 0 (`ok: 1 step(s) publish a release`) although the workflow publishes without the guard's conditions:
  - **A.** In the windows job: `run: >` folded, with lines `gh release` and `upload v0.1.0 x.exe`. PyYAML reads `gh release upload v0.1.0 x.exe\n`.
  - **C.** In the windows job: a plain multi-line scalar `run: gh release` continued by `upload v0.1.0 x.exe`. PyYAML reads `gh release upload v0.1.0 x.exe`.
  - **B, E.** In the windows job: `${GH:-gh} release upload ...` and `GH=gh; $GH release upload ...`.
  - **D.** The check step's env is `{ TAG: ..., NOTE: "x, GH_TOKEN: none", RUN_NUMBER: ... }`, with no token (the developer's noted gap). PyYAML gives no `GH_TOKEN` key.
- A and C are fail-open in the new code that claims to be fail-closed. A release could be written from a job with no tag `if:`, no `needs` and no release-check. That is the same class as the F-003 / T-038 story, where each unmodelled clause was a silent pass.
