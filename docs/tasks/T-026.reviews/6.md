## Investigator's three concerns

1. **gh's 'release not found' as an unowned literal: does not block.**
   - It fails closed, as above. gh has no distinct exit status for "not found": `release view` and `gh api` both exit 1 on 404 and on 401. So any alternative still decides on gh's output text.
   - Run #207 (`v0.1.250`) proved the runner's gh still prints this text.
2. **Installer name containment vs equality: does not block (Low, follow-up finding 3).**
   - The installer comes from this run's own artifact. It must be the single `*-setup.exe`, and `version-stamp.sh` names it `Voicen_<V>_x64-setup.exe`.
   - A two-version name such as `Voicen_0.1.9_x64_0.1.8_-setup.exe` would need a build defect that also writes such a name.
   - A cheap strengthening that pins neither product name nor arch: also require that the first `_N.N.N_` in the name, which the refusal message already extracts, equals `X.Y.Z`.
3. **The mask covers exact bytes only: does not block.**
   - No path in the job prints an encoded token: `GH_DEBUG` is unset and nothing sets `-x`.
   - GitHub Actions also masks the `github.token` value in the log.
   - Masking encodings would be a model of gh's debug format, which P-020 argues against.
