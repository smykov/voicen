## Context

Split from T-003 by the re-plan (decisions #20, #21). The single Windows implementation of T-003's `CredentialStore` over Credential Manager (`CredWriteW` / `CredReadW` / `CredDeleteW`, generic, `CRED_PERSIST_LOCAL_MACHINE`, absent = Ok, targets per `KeySlot`); it replaces spec 001 T028. Also the IPC commands `settings_get` / `settings_save` over T-003's `SettingsService`, the event `settings://changed`, the data directory passed to `SettingsService` (one resolver in the shell, P-010), and the shell wiring of `subscribe` (the `settings://changed` bridge; tray rebuild and notifier move to T-006, which builds the tray — decision #34). Also (decision #34): the OS UI-language read passed to `load_or_init` (spec 004 T049; `Win32_Globalization` feature of the consented `windows` crate), the command `settings_speech_languages` returning core's `WHISPER_ISO_639_1` (#30), the core serde wire form of the settings IPC types, and the CI smoke check that `settings.json` exists after first launch with `engine` = `none` (the `settings.json` half of spec T028, moved from T-004). Subscribers that need other tasks' implementations (001 hotkey registrar, 002 model store, 005 history) are wired by those tasks. `src-tauri` is built and tested only on Windows CI (decision #5), so this task deploys.

## Acceptance

- [ ] Windows CI: a key written to each `KeySlot` reads back equal, delete makes it absent, a missing target reads as absent (Ok), and the key bytes never appear in `settings.json` or the log
- [ ] Windows CI: `settings_save` twice over an existing `settings.json` replaces it (rename over an existing file on Windows, unverified on Linux — T-003 investigation)
- [ ] `settings_get` returns T-003's `SettingsView` (keys as presence only); `settings_save` returns `Saved` / `Refused(field errors)` and emits `settings://changed` only on `Saved`
- [ ] Failure branch: Credential Manager write refused → `settings_save` returns `Refused(key_store_failed)`, the settings file is unchanged and no other storage is used (NFR-04, no fallback) — verified by a Windows CI test with an injected failing store
- [ ] First run on Windows with a Russian UI language writes `ui_language: "ru"` (OS language read, spec 004 T049); `settings_speech_languages` returns exactly `WHISPER_ISO_639_1`; the CI smoke finds `%LOCALAPPDATA%\Voicen\settings.json` with `engine` = `none` after the first launch

### Settled design (not left to the developer)

**1. `WinCredentialStore` (`src-tauri/src/credentials.rs`, spec T016, R-1).**
- `windows = { version = "0.62", features = ["Win32_Foundation", "Win32_Security_Credentials"] }` goes under `[target.'cfg(windows)'.dependencies]`. It resolves to the already-locked 0.62.2, so there is no new crate; feature flags are allowed under #9.
- Add `"Win32_Globalization"` only if item 7 is taken.
- `pub struct WinCredentialStore { prefix: String }` has two constructors:
  - `new()`: empty prefix, used by the release app.
  - `with_target_prefix(p)`: used by tests, so they never touch a user's real `Voicen/...` entries; spec T016 asks for a throwaway prefix.
  - `target(slot) = prefix + slot.target_name()`, encoded as NUL-terminated UTF-16. `release_store_targets_are_slot_target_names` pins the release mapping. The prefix is a constructor value, not a test-only branch: both constructors run the same three calls.
- `write`:
  - `CREDENTIALW { Type: CRED_TYPE_GENERIC, Persist: CRED_PERSIST_LOCAL_MACHINE, UserName: "voicen", CredentialBlob: secret.expose().as_bytes() (UTF-8, no copy), .. }`, then `CredWriteW(&cred, 0)`.
  - Its error becomes `CredentialError { os_code }`, with `os_code = WIN32_ERROR::from_error(&e).map(|w| w.0 as i32).unwrap_or(e.code().0)`.
- `read`:
  - `CredReadW(target, CRED_TYPE_GENERIC, None, &mut p)`.
  - `ERROR_NOT_FOUND` (1168) → `Ok(None)`.
  - Otherwise the blob is copied into a `Vec<u8>`, the system buffer is zeroed, and then `CredFree`.
  - `String::from_utf8` → `Secret`. Invalid UTF-8: the Vec is zeroized and the result is `Err(CredentialError { os_code: 13 /* ERROR_INVALID_DATA */ })`.
- `delete`: `CredDeleteW`; `ERROR_NOT_FOUND` → `Ok(())`.
- The store does no logging and has no `Debug` that shows a key. No other storage is touched on any error (NFR-04).

**2. Wire form: in core, as serde impls, tested on the Linux gate.**
- If it were in shell DTOs, every byte of the contract would be tested only on Windows, and the field and code strings would be re-spelled (P-010).
- UI → shell: `settings_save { request: { settings: Settings, keys: { transcription_api, local_server, post_processing } } }`.
  - Each `KeyEdit` is `"Untouched"`, `"Clear"` or `{ "Replace": "<key>" }`, externally tagged like `SaveOutcome` in the ipc.md example. All three slots are required.
  - `Secret` gets `Deserialize` from a string. It still has no `Serialize`, so the compile_fail doctest stays.
  - `KeyEdit`'s `Deserialize` is hand-written, and every error is a fixed text (`invalid key edit`).
  - Why the fixed text: Tauri returns `invalid args \`request\` for command \`settings_save\`: <serde error>` to the window (`tauri error.rs:59`). serde's `unknown variant \`sk-...\`` would put a mistyped key into that text, and so into UI text or the console (P-009, J1).
- Shell → UI:
  - `SettingsView`: as now.
  - `SaveOutcome`: `{"Saved":{"view":…,"warnings":[…]}}` or `{"Refused":{"errors":[…],"form_error":null|FormError}}`.
  - `FieldError`: `{"field":"<FieldId::as_str>","code":"<ErrorCode::as_str>"}`. The UI maps it to `error.<code>` (data-model).
  - `Warning`: `{"field":…,"code":"endpoint.insecure"}`.
  - `FormError`: `{"kind":"write_failed"|"settings_unavailable"|"partially_restored","message":"<MessageId>","not_restored":[FieldId…]}`, with `not_restored` only on `partially_restored`. Carrying `message` keeps `FormError::message_id()` the one mapping.
  - `MessageId` serializes as its id string. This closes the core-traits.md:121 note.
- ipc.md and data-model.md get these shapes in the same commit (P-014). T-004's mock (spec T013) implements exactly them.

**3. Service construction and failing-store injection (J4). No test-only path in release code.**
- `pub fn load_settings(data_dir: PathBuf, credentials: Arc<dyn CredentialStore>, os_language: Option<&str>) -> (Arc<SettingsService>, LoadOutcome)` builds the `SettingsDeps`:
  - `FsSettingsFile::new(data_dir)`
  - the given `credentials`
  - interim `NoDownloadedModels`: `is_downloaded` is false and `list` is empty. That is the true state until T-016 exists, so `builtin_local` → `model.not_downloaded`.
  - an interim `HotkeyRegistrar` whose `prepare` returns `Err(Unavailable)` and whose `commit`/`abort` do nothing. It fails closed and is never called until T-010. T-006 replaces it.
  - `SystemClock`
- `pub fn commands<R: Runtime>(b: Builder<R>) -> Builder<R>` holds the one `invoke_handler(generate_handler![get_build_info, settings_get, settings_save, settings_speech_languages])`.
- `run()` calls `commands(tauri::Builder::default()).manage(service)` with `WinCredentialStore::new()` and `paths::data_dir()`.
- The tests call `commands(tauri::test::mock_builder()).manage(service)`, with the service built by the same `load_settings` over a `TempDir`. The failure-branch test passes `FakeCredentialStore` after `fail(Write, TranscriptionApi, CredentialError { os_code: 5 })`.
- The fake and `TempDir` come from `voicen-core` feature `test-fakes`. `src-tauri` enables it only in `[dev-dependencies]`, together with `tauri = { version = "2", features = ["test"] }`. Neither adds a crate.
- Release check (validator): `scripts/tw-run core -- cargo tree -p voicen --target x86_64-pc-windows-msvc -e normal,features | grep -c 'test-fakes\|"test"'` → 0.
- `settings_save` runs off the main thread (`#[tauri::command(async)]`, which tauri-macros 2.7.1 runs as `sync_threadpool`): a save is up to 9 credential calls plus an fsync.

**4. `settings://changed`: a subscribe bridge, not an emit in the command (J3, P-011).**
- `spawn_change_bridge(app, service)` is started in `.setup()`. It subscribes, and for every received snapshot it calls `app.emit("settings://changed", service.view())`. An emit error is ignored, so it never turns a `Saved` into a failure.
- Why a bridge:
  - Saves that do not come through `settings_save` must reach open windows too. Examples are T-016's "deleted selected model → engine none" (FR-28) and later tray toggles.
  - core already guarantees exactly one message per `Saved` and none per `Refused` (I6).
- Cost: three credential reads per save.
- "After a reset" (ipc.md): at startup no window exists yet. T-004's executor opens the window, and the window reads `reset_notice` through `settings_get`, so no startup emit is needed.

**5. One data-dir resolver (J2, P-010).**
- `paths::data_dir()` is `%LOCALAPPDATA%\Voicen`, falling back to `temp_dir()\Voicen` when the variable is unset. That keeps today's log fallback, so there is a single rule.
- `log_dir()` becomes `data_dir().join("logs")`. `log_start` takes the directory, so the leak test can point it at a `TempDir`.
- Tests never call `data_dir()` for writing: the CI runner's real folder must stay clean for the smoke.

**6. `settings_speech_languages` (decision #30) belongs here, not in T-004.**
- It is a Rust command (`-> &'static [&'static str]`, `WHISPER_ISO_639_1` in core order, 97 entries). Only a Windows CI test can prove it, and T-004 is verified with Playwright against a mocked IPC.
- ipc.md gets the row, and T-004's picker and mock consume it.

**7. OS language (spec 004 T049): a planning gap.**
- No teamwright task owns it. T-004 owns the executor (spec T025: "`None` until T049"), but this task is the one that calls `load_or_init`.
- With `None`, a first run on Russian Windows writes `ui_language: "en"` into `settings.json`. That value then persists as `Loaded`, which breaks FR-15/FR-21.
- Recommended: add it here. That is `os_language()` (the first entry of `GetUserPreferredUILanguages(MUI_LANGUAGE_NAME)`; `None` on error, spec FR-011) plus a Windows test that it returns a non-empty tag. Otherwise open a task for it before T-004.

**8. Not wired here** (with their owners):
- tray rebuild, notifier and `settings_list_microphones` (spec T042): T-006. No tray exists (`lib.rs`; `tauri` without `tray-icon`).
- the real `HotkeyRegistrar` and the hotkey save step: T-006/T-010.
- `ModelStore` as `DownloadedModels`: T-016.
- history subscriber: T-022.
- opening windows from `LoadOutcome` and the `notice.settings_reset`: T-004. `run()` keeps the outcome for it.
- R-11 log lines: T-008.
- `settings_test_connection`: T-013.

The Context's "shell wiring of `subscribe` (tray rebuild, notifier)" therefore has no target in this task: the only subscriber here is the event bridge.

#### Hypotheses

1. **The test exe has no manifest, so comctl32 v5.82 binds and a v6-only import is missing.** Confirmed by source; not observed in the binary.

Because `src/main.rs` exists, embed-resource emits `cargo:rustc-link-arg-bins=<resource>` (embed-resource `lib.rs:443`). Cargo applies `Bin` link-args where `target.is_bin()` and `Test` link-args where `target.is_test()` (cargo `custom_build.rs:271,273`). So integration-test exes never get the resource.
   - **The import.** All `windows`/`windows-sys` functions are imported by name through `raw-dylib` (windows-link 0.2.1 `link!`). rustc passes `/OPT:REF` in debug too (`linker.rs:1017-1021`), so only reachable imports remain.
   - **Callers of a v6-only comctl32 export.** I grepped the whole registry cache for `TaskDialog`, `TaskDialogIndirect`, `LoadIconMetric` and `LoadIconWithScaleDown`. Apart from binding definitions, only two crates call one:

     - tauri-runtime-wry `dialog/windows.rs:90`. It runs only under `not(debug_assertions)` (`lib.rs:4680`), so it is absent from debug test exes.
   - **Path from the tests.** `harness()` calls `WebviewWindowBuilder::build`. The chain is: tauri `manager/menu.rs:77` → `muda::Menu::init_for_hwnd_with_theme` → `attach_menu_subclass_for_hwnd` (`mod.rs:305-309`, which installs `menu_subclass_proc`) → `show_about_dialog` (`mod.rs:1175,1234`) → `TaskDialogIndirect`.

#### Root cause

tauri-build scopes its Common-Controls v6 manifest to bin targets only, so the integration-test exe binds comctl32 v5.82 and cannot resolve muda's `TaskDialogIndirect` import, which tauri's default feature `common-controls-v6` compiles in. This explains every symptom:
- only `settings_ipc` fails;
- it fails before `main`;
- `credentials` and the release exe are fine.

No evidence contradicts it. The open point is the binary-level confirmation of the import name.

**Decision rule (no Windows host here).** The next windows run with the fix is the discriminating experiment:
- (i) `settings_ipc` and `autostart` print `running N tests` → the cause is confirmed. The manifest on test targets is the only change.
- (ii) Still `0xc0000139` → the cause is refuted. Add a one-off diagnostic step after `cargo test -p voicen --no-run`: `dumpbin /imports` on `target\debug\deps\settings_ipc-*.exe` (dumpbin found through `vswhere -find **\Hostx64\x64\dumpbin.exe`), then look at the `COMCTL32.dll` block and any other DLL. Then run the exe with loader snaps (`gflags /i <exe> +sls` under `cdb -g -G`) to name the missing entry point.
- (iii) A link error in the test link (for example `LNK1158 cannot run 'mt.exe'` or `CVT1100 duplicate resource`) → the fix mechanism failed, not the cause. Switch to fallback B.

#### Invariant and seam

See the `analysis` block. In short: every voicen exe that cargo links on Windows carries tauri-build's Common-Controls v6 manifest. The release bin gets it only from tauri-build, unchanged. The test targets get it from `src-tauri/build.rs` through `rustc-link-arg-tests`.

`rustc-link-arg-tests` does not reach lib unit-test exes: cargo has no selector for them (`custom_build.rs:264-277`). So tauri-linking shell tests stay in `src-tauri/tests/`. Today `src-tauri/src` has no `#[cfg(test)]`.

#### Options

- **A (recommended): test-only linker manifest in `build.rs`.**
  - Change: keep `tauri_build::build()`, then on `CARGO_CFG_TARGET_OS == "windows"` and `CARGO_CFG_TARGET_ENV == "msvc"` (build-script env, not `#[cfg]`) emit:
    - `cargo:rustc-link-arg-tests=/MANIFEST:EMBED`
    - `cargo:rustc-link-arg-tests=/MANIFESTINPUT:{CARGO_MANIFEST_DIR}\windows-app-manifest.xml`
    - `cargo:rerun-if-changed=windows-app-manifest.xml`
  - `src-tauri/windows-app-manifest.xml` is a byte copy of `tauri-build-2.7.1/src/windows-app-manifest.xml`: one `dependentAssembly`, `Microsoft.Windows.Common-Controls` 6.0.0.0, `publicKeyToken 6595b64144ccf1df`. Its header comment names the source file and the version.
  - Why it removes the cause: the test exes load with the same comctl32 v6 activation context as the release exe. This is the pattern upstream uses for its own tests.
  - Red/green: red is run 37159339288; green is the next windows run on a commit with the fix and T-014 (see `approach`).
  - Risk:
    - link.exe adds its default UAC `trustInfo` (asInvoker) to the test manifests. This is harmless for tests and is what upstream ships.
    - Upstream also adds `/WX`. That is not recommended here without a run: it would turn any unrelated test-link warning into an error.
    - If tauri-build changes its default manifest in a later version, the copy can drift. The pin comment and the `docs/decisions/<area>` entry make that visible on upgrade.
  - Rollback: revert the build.rs lines and the file.
  - Impact on the release exe: none, by construction.
    - `tauri_build::build()` is byte-unchanged, so the release resource and its manifest are unchanged.
    - The new directives are `-tests` only. cargo applies them only where `target.is_test()`. `pnpm tauri build` links the bin and the cdylib/staticlib, never a test target.
    - Proven in the same CI run: `pnpm tauri build`, install and the smoke pass.
    - Optional extra check: `mt.exe -inputresource:target\release\voicen.exe;#1 -out:CON` prints the tauri default manifest.
- **B (fallback if A hits a linker/mt problem): `embed_resource::compile_for_tests`** with a two-line `.rc` (`1 24 "windows-app-manifest.xml"`).
  - It uses the same `rc.exe` path that tauri-build already runs successfully in CI.
  - embed-resource is already in Cargo.lock (via tauri-winres), but as a direct build-dependency it is outside decision #9's consented list, so it needs owner consent.
- **C (rejected): drop tauri's default feature `common-controls-v6`.** List `wry`, `compression`, `dynamic-acl`, `x11`, `dbus` explicitly in both `[dependencies]` and `[dev-dependencies]`, because features unify across the two.
  - It changes the release: the muda About dialog and the release "WebView2 missing" dialog become `MessageBoxW` without a hyperlink.
  - It is a case list: the next v6-only import brings the defect back. Examples: our own `TaskDialog`, `LoadIconMetric`/`LoadIconWithScaleDown` for tray icons in T-006, or tray-icon's `muda-common-controls-v6`.
- **D (rejected): `WindowsAttributes::new_without_app_manifest()` plus `cargo:rustc-link-arg` (all targets) `/MANIFEST:EMBED /MANIFESTINPUT`.**
  - One mechanism would cover lib unit-test exes too.
  - But the release manifest would then be generated by link.exe, which adds `trustInfo` by default, so the release manifest changes. That violates "release manifest unchanged".
  - Keeping tauri's resource and adding all-target link args instead would give a duplicate `RT_MANIFEST` id 1 (`CVT1100`) in the release link.
