## Context

Opened by T-026 review round 4 (`REJECT_RECURRENCE`). The trigger was set by T-026 review 3: "If another YAML-model gap turns up in this guard after that, it should go to an rca under class `guard-model`."

`scripts/ci/release-guard.sh` is a host-side awk reader. It re-implements three foreign parsers: the YAML of the workflow (scalar styles, comments, flow mappings), bash word and command splitting, and gh's argument parsing. It decides "pass" whenever its model does not see a violation. Each round found shapes the model passed silently (fail-open):

- T-026 validation 1 M6 (fixed in 2fe375a): `|| true`, `; true`, `if`, `set +e`, pipe around the check call.
- T-026 review 2 (fixed in 2e90f89): `#` line closing a quote opened on the call line; `\n` escapes in a quoted scalar.
- T-026 review 3 #1 (logged as a Low in T-060): folded `run: >` with a `#` line before the call.
- T-026 validation 2 (fixed in 6e7e7a8): `gh --repo R release upload`, `gh release --repo R upload`; `env: # GH_TOKEN: ...` (a YAML comment); `NOT_GH_TOKEN`.
- T-026 review 4 (open, reproduced on a copy of 6e7e7a8):
  - `run: >` folded scalar `gh release` / `upload ...` in the windows job;
  - a plain multi-line scalar `run: gh release` / `upload ...` in the windows job;
  - `${GH:-gh} release upload` and `GH=gh; $GH release upload`;
  - `env: { NOTE: "x, GH_TOKEN: none" }` with no real token.
  Each gives exit 0 (`ok: 1 step(s) publish a release`). PyYAML reads the first two as one `gh release upload ...` command, so a release is written from a job with no tag `if:`, no `needs` and no release-check.

F-003 (class `guard-model`, rca T-038) already holds the rule: "a guard decides on a switch or on raw text the tool cannot reinterpret, never on a model of another tool's parser". The release guard was built as such a model, and each fix extends the model. Smaller siblings in other guards are in T-060 (T-049 r1 #4 `app-acl.sh` block comments, T-079 r1 #1 `http-client-builder.sh` missed constructors).

## Acceptance

- [ ] Invariant: a workflow change that lets a GitHub Release be written (by any step, in any job) without (1) a v* tag push `if:`, (2) `needs: [gate, windows]` and (3) an earlier step whose exit status is release-check.sh's own (with GH_TOKEN) fails `make check`. The rule must not depend on a host model of YAML scalar styles, shell word splitting or gh flag parsing. It must decide on raw text the runner cannot reinterpret, or on a real parser's output, with every unread shape refused (fail-closed).
- [ ] Failure branch: every shape listed under Context (the fixed ones and the 4 open ones from review 4) is refused, with a fixture each.
- [ ] The real `.github/workflows/ci.yml` passes. The T-026 acceptance (release job, release-check.sh) is unchanged.
- [ ] Test that fails without the change: the release-guard fixture suite, including the review-4 shapes.
- [ ] The analysis names the exit: (a) code in the guard's seam, (b) `/arch-review` (for example, move check and publish into one script so the workflow holds one literal line; or read the workflow with a real YAML parser), or (c) a `PRINCIPLES.md` amendment, because F-003's rule is not checked when a new guard is designed. Exits (b) and (c) are the owner's call.

**§3 Hypotheses.**

- H2 (confirmed, changes the fix): the concern is decided on a second path, by GitHub: a step can write a release only with a token that has `contents: write`. Draft amendment for the owner (not applied; agents do not edit `PRINCIPLES.md`):
> **P-020 — A guard decides on a switch or a literal it owns, never on a model of another tool's parser** (minor bump, 1.3.0). A guard (`checker: true`: a tripwire over text that another tool interprets: workflow YAML, shell, Rust, Cargo, JSON) passes only on (1) a platform-enforced switch pinned as literal text (a permission, a compiler or cargo flag), (2) byte-exact comparison with a block or line the guard owns, or (3) the absence of a raw token anywhere in the scanned files (fail-closed: any occurrence refuses).
