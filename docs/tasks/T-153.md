**Windows claim mechanics (the part only CI proves).** Windows checks sharing in `CreateFile` only when the new open asks for data access (read, write or delete). An `access_mode(0)` open (std documents it as metadata-only) never conflicts. So the claim must ask for `DELETE` access. It must also set `share_mode(FILE_SHARE_DELETE)` only:
- a holder with any read or write access then makes the claim fail with a sharing violation, whatever share mode the holder used (also std's default `READ|WRITE|DELETE`);
- while the claim is held, any new open for read or write fails;
- core's later `fs::remove_file` (`DeleteFileW`) still succeeds, because the claim shares delete.

`delete_folder` drops the claims before `remove_dir`, which is the right order for a delete-pending file. `FILE_FLAG_OPEN_REPARSE_POINT` stops a link inside the folder from being followed to a file elsewhere.

None of this is verified on this host. The red test therefore holds `mic.opus` two ways: `FILE_SHARE_READ`, as the `local_models.rs` precedent does, and std's default share mode. The second holder catches an access-0 claim, a too-wide share mode, and a delete that reports success but only deletes on close.

**Hypotheses checked.**
1. *A second path deletes or renames a call.* Grep in `src-tauri/src` and `crates/voicen-core/src/call` finds no other `remove_dir_all` or `remove_file` on a call folder. Rename goes through `rewrite_names` only (T-152). The shell must call `PassQueue::delete`, not `CallStore::delete_folder`, or a transcribing call loses its cancel. This is invariant (1).
2. *This class was fixed before.* `docs/failures.md` has no entry for `call-ipc`, sharing violations, `FILE_SHARE` or half-deleted folders. The only class sibling is T-142, which closed with no F-entry. No recurrence.
3. *A blocking wait on an IPC worker.* Confirmed risk: `PassQueue::delete` waits for a cancelled pass for up to the FR-24 timeout. That is why it runs on `spawn_blocking`, as `calls_export` does (#42). Renames only wait for the meta lock, which is held around file IO only (call-storage.md), so they stay plain async commands like `calls_get`.
4. *T-145 is needed first.* No functional dependency, but the owner orders T-153 after T-145's merge to main (decisions #348 Q1; `depends_on` carries T-145). T-153 uses only `CallStore`, `PassQueue` and the commands section, all on main. But `origin/task/T-145` rewrites the same file in several places:
   - in `call.rs`: `CallPorts`, `start_calls`, `CallPart`, `ShellCallShell` (358 changed lines in `call.rs`);
   - `call_shell_support/mod.rs`, `lib.rs` and `win/mod.rs`.

   One merge conflict there already went back to implement (decisions #340). To keep the overlap small, the deleter is not a `CallPorts` field and `start_with` is unchanged. What still overlaps: `lib.rs generate_handler!`, `win/mod.rs`, and `ShellCallShell::changed` (via `emit_changed`).
