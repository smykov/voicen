#### New in the fix
The round-1 finding offered two options: say that `release` must not run concurrently, or hold the lock. The developer held the lock. That part is fine. The developer also rewrote the `Pipeline` doc to the opposite of the first option: "jobs may run on several threads at once". core-traits.md:161 now describes "concurrent failing jobs" as a supported case. That is true for the pending slot only. It is false for delivery. `deliver` (`delivery.rs:53-81`) writes the clipboard, waits up to `MODIFIER_WAIT` = 1 s for modifiers, checks the front window and then sends Ctrl+V. Nothing serializes these steps across jobs. Take two concurrent `run_job` calls. B's clipboard write can land inside A's 1 s wait. A's Ctrl+V then pastes **B's transcript into A's start window**, and B pastes it a second time. Research R-10 rules this out ("Delivery itself (clipboard + paste) runs on one delivery thread, so pastes never interleave"). So does this task's own analysis: T-001.md lines 67, 154 and 157 say T-006 uses one std worker running `run_job` FIFO, and T-011 uses workers for `process` and one delivery thread for `release`. The next consumer, T-006, reads exactly this doc comment when it picks its threading. Round 1 framed concurrency only around the slot, so that finding was incomplete. A fix suggested by a review still has to meet the same bar.
