## Investigation

Tools: Serena was not connected (no `mcp__serena__*` tools in this session), so I used grep and file reads over `crates/voicen-core/{src,tests}`, `src-tauri`, `scripts`, `Makefile` and `docs`. Context7 was not used: the reqwest 0.13.5 and tokio 1.53.1 behaviour below comes from the pinned sources in `.teamwright/cache/core/_usr_local_cargo_registry/src/index.crates.io-*/` (the versions in `Cargo.lock`). I did not redo the triggering failure's evidence; it is in `docs/tasks/T-107.md` › Investigation and I reuse it here.

**Frame.** In CI 39296012262 (windows), `post_process_timeout::default_deadline_skips_a_silent_server_at_15_s` got the right outcome (`Skipped(Timeout)`) and passed `at_least(took, 15 s)`. It failed `within_spec` with a stage of 16.394 s against 15 s ± 0.5 s. A runner-wide stall of about 1.4 s overlapped the measured window. The owner's decision #149 (OQ-39 (A)): SC-003's tolerance is checked by its outcome, and an overshoot caused by a host stall is not a defect.

**Hypotheses.**
1. *The ceiling itself races the host.* Confirmed by T-107: 56 of 57 windows samples within about 67 ms; the outlier sits next to a 1.42 s stall in an unrelated binary; the sibling tests ended on time.
2. *The product deadline is late.* Refuted. Today's `at_least` passed and the distribution has no drift. In reqwest 0.13.5 the blocking side (`blocking::wait::timeout`) and the async side (`total_timeout`, a tokio `Sleep` with an absolute deadline) each bound the call.
3. *A second path holds the same concern.* **Confirmed, and new.** `within_spec` has two callers, not one as T-107 and core-tests I2 say. `configured_post_processing_timeout_delivers_the_raw_transcript` also asserts `within_spec(run.took.less(baseline), 5 s, SLACK, "SC-003")` through the whole pipeline. It carries the same risk, and a stall in its timed run would turn it red in the same way. A grep of the whole tree for other stall-sensitive verdicts in core tests found one more, of a different shape: `dictation_session::realtime_source_pushes_nothing_after_stop_or_drop` asserts `count > 0` after a fixed `thread::sleep(ms(200))`. The source pushes chunk 0 as soon as its thread runs. If that thread is not scheduled within 200 ms, the stop arrives first (`try_recv` sees it), nothing is pushed, and the test is red. The test never failed in CI as far as the logs I have show, so this is a matching shape, not a proven flake.
   The rest of the grep came back clean:
   - Every other `recv_timeout`, `eventually` and `BUDGET`/`HANG`/`END_WAIT` use only ends a hung test, with 10 to 60 s budgets.
   - `SETTLE`/`QUIET` sleeps come before absence checks, which a stall can only make pass.
   - `dictation_session` lines 1803 and 1808 order instants around the event.
   - `pipeline.rs`'s `trace.ms <= room` compares one window to an enclosing one.
   - `local_download`'s `at_most_per_second` only gets wider when the host is slow.
   - `src` unit tests: no clock-based ceiling (`grep` for comparisons against `Duration`, `since(` and `instant()` in asserts).
4. *This class was fixed before.* Yes. The earlier patches, and why none held:
   - F-005 / T-048: a budget per OS answer.
   - F-013 / T-078 (`5762a9c`, branch `tw/T-078`, absorbed by T-080): a min-of-3 baseline. It removed the false red from a cold baseline, not a stall in the timed run.
   - T-080 (`8007a71`, `bdea75c`, `0dc234e`; decisions #100 and #107): one rule. Every ceiling became a lower bound or an outcome, except SC-003, which stayed a ceiling through `within_spec` on the premise that "the reference load" bounds it.
   - T-089 (`8f1ddfe`): moved I2's clock-read ban into the compiler, which leaves ceilings expressed through `within_spec` untouched.

   Each patch shrank the set of ceilings and kept the premise that a tolerance holds under a stated load. The shared VM's stalls are not bounded by any load profile, so every ceiling that is left is a flake waiting for its stall.
5. *The bracket itself races a stall.* Refuted for false reds, from source:
   - The bracket server's bytes arrive at least 15.5 s after the request reached it. That is after accept, and accept is after both timers started: the async `total_timeout` is set when the core thread creates the `PendingRequest`, and the blocking deadline in `wait::timeout` right after the send.
   - tokio 1.53.1 `time::Driver::park_internal` runs `handle.process(clock)` after every park. Any driver turn that delivers the socket's readiness has therefore already fired the expired 15 s `Sleep`.
   - reqwest 0.13.5 `PendingRequest::poll` polls `total_timeout` before `in_flight`, and the response body inherits `total_timeout`.
   - So every poll after the answer gives `TimedOut`. The blocking side, which polls the channel first, can only receive that error or hit its own deadline.
   - A stall on the server side only delays the answer, which is the safe direction.
   - The only cost is a rare false green: a wrong deadline inside (15.5 s, 15.5 s + stall) could still give `Timeout`. That is the trade the owner accepted in #149.

**Root cause.** The class lives in the verdict, not in the product. The SC-003 check, at both of its callers, is a wall-clock ceiling on one sample taken on a shared VM. A VM stall inside the window pushes the return past the ceiling while the deadline is correct. No baseline or tolerance tuning removes this, because a stall has no upper bound.

**Recommended exit: (a) code.** It is one seam (`tests/common::timing` and the callers it serves) with no product code. The owner already allowed it in #149, which amends #107's measurement wording, so no further owner decision is needed. The class does not cross seams or services and is not a hotspot (T-107: `tests/common` and `post_process` are absent from the recurring areas and hotspots of `teamwright-metrics`). Nothing is missing from the process either, since review and validation followed the rule as written; the rule itself is what changes, and #149 already decided that.

**Invariant (closes I2).**
- A core test's verdict on a deadline comes only from two things: `at_least(took, deadline)`, and the outcome of a server that answers after the deadline plus the spec tolerance (right deadline: Skipped/Timeout; a deadline past the tolerance: Applied).
- No core test asserts that a call returns, or that an event happens, before a wall-clock limit.
- `Took` is read only by `at_least` and `at_most_per_second`.
