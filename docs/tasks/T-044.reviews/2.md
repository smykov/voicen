- *Lock order with `list()` mutating the map.* No new edge.
  - `list()` takes the transient lock twice, one after the other, never nested:
    - The first guard (`lock(&self.transient).clone()`, service.rs:146) is a temporary. It drops at the end of that `let`.
    - The second guard (:175) is taken only after `store.states()`. That call is `fs::metadata` only (store.rs:95-107, 136-139) and takes no lock.
  - `list()` never takes the downloader slot, so the order stays as in round 1:
    - `download`: transient, then slot (across `start`).
    - The worker: slot, released at download.rs:377, then transient in `record()`, never nested.
    - `cancel`: slot only. `list`: transient only.
  - When `list()` runs inside `emit` (the recorder does this), it runs after `record()` has dropped its guard. When `list()` runs on another thread while `download()` holds the transient lock, it only waits for `start`, and `start` waits on nothing that `list` holds.
- *"Only if the entry is still that same Failed".* The check holds for every case that can happen. It compares by value (`current.get(&id) == Some(&failed)`), so it is not an identity check.
  - A download that started in between left a `Downloading`, which is never removed.
  - Only a value-equal `Failed` of a *new* download could be removed by mistake. For that, all of the following must happen between the two locks of one `list()` call:
    - the final file disappears after `states()` read it (otherwise `start` refuses with `AlreadyDownloaded`);
    - a whole new download starts and fails with the same reason.

    The window is a few metadata reads long. Even then the result agrees with the disk: the model lists as `not_downloaded`, without the reason. Not a finding.
