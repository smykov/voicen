## Context

Split from T-016 by decision #49 (T-016 analysis, option A). The shell half of the local-model download: `src-tauri/src/local_models.rs` with the commands and `local-model://` events from specs/002 contracts/ipc.md over T-016's core `ModelStore` / `Downloader`; the models dir `paths::data_dir().join("models")` in `paths.rs` (one resolver, P-010); one `Arc<ModelStore>` shared by `SettingsDeps.local_models` (replacing `NoDownloadedModels`, settings_ipc.rs) and the IPC commands; `ModelStore::cleanup_at_start` at startup; the Windows free-space probe behind core's `DiskSpace` trait (a `windows` crate feature flag such as `Win32_Storage_FileSystem`, no new crate). Shell tests only in `src-tauri/tests/*.rs` (decisions #36/#37), built and run in Windows CI. Logging of download outcomes waits for T-008. Note from T-016 review round 1: core's `DownloadError` also has `NotInCatalog` (an id missing from the catalog) and `CannotStart` (the OS refused the worker thread), which have no wire code in specs/002 contracts/ipc.md yet — map both here (and add them to ipc.md).

## Acceptance

- [ ] Windows CI: `local_models_list` reports the catalog with each model's state from disk; a download started through the command emits progress events and ends with the model listed as downloaded; settings validation accepts `builtin_local` with that model (same store)
- [ ] Failure branch: a failed or cancelled download leaves no `.part` file and the model not downloaded; a `.part` left from a previous run is deleted at start — Windows CI tests over a local mock server and a TempDir
- [ ] Test that fails without the change: `src-tauri/tests/local_models.rs` (Windows CI)

## Investigation

**Frame.** Expected (spec 002 US1, contracts/ipc.md, decision #49): the settings window lists the five models with their disk state. It starts one download and receives progress and end events, can cancel it, and can save `builtin_local` with a downloaded model. A `.part` left by an earlier run is deleted at start. Observed: none of this is wired (see `analysis.root_cause`). This is a need, so there is nothing to reproduce. Tools: Serena was not used (decision #3: TypeScript only; Rust was read with grep and file reads). context7 was not used: the tauri 2.12.1, tauri-build 2.7.1, tauri-utils 2.10.1 and windows 0.62.2 sources were read in `.teamwright/cache/core/.../index.crates.io-*/`, all matching Cargo.lock.

**Hypotheses checked.**
1. *A second path handles models.* Refuted. Grep for `models`, `DownloadedModels` and `local_model` over `src-tauri/` finds only `NoDownloadedModels` (settings_ipc.rs:112-125). Nothing in src-tauri reads the models dir.
2. *The class was fixed before.* No. Class `model-download` has only T-016 (planned split). `docs/failures.md` has no entry in this class.
3. *New commands need a capability entry.* Refuted for tauri 2.12.1 with this build.rs (ACL evidence in `analysis.evidence`). The existing `settings_*` commands get no permission at all: they pass because the app has no ACL manifest. A consequence: today any local-origin window of any label could call app commands. The `settings` label restriction of decision #45 covers only plugin commands (event/window). No test proves an app command passes the real ACL; existing invokes use `mock_context`, whose `Resolved::default()` has no manifest (tauri test/mod.rs:143). Test (7) pins it.
4. *Blocking reqwest on the command thread (T-013 finding).* Refuted for the core API as it stands: `start` does a file metadata read, the disk probe and a thread spawn; the client lives on the worker (download.rs:404-409). Rule for the developer: the shell adds no reqwest call and drops no reqwest object on a command thread. `local_models_list`/`local_model_download` may be `#[tauri::command(async)]` with a sync body (precedent `settings_save`, settings_ipc.rs:98-104) to keep file and disk calls off the main thread. `cancel` can stay sync.
5. *The disk probe silently skips its check on the first download.* Likely, needs the Windows test. The models dir does not exist until the first download creates it (download.rs:421, after the response). Win32 `GetDiskFreeSpaceExW` expects an existing directory (from the API docs, not verified here). A probe error lets the download proceed (R-9, download.rs:257). So the probe walks up to the nearest existing ancestor; test (6) proves it on Windows.

**Design points (agent-level; the orchestrator can confirm):**
- *Ordering.* Core clears the slot, then emits the end event; a refusal emits nothing. A fast failure (e.g. 500) can end before `start` returns. So `local_model_download` emits no event itself. It sets the transient `Downloading{0,total}` while holding the transient-map lock across `start` (core never calls the callback inside `start`), and removes it on `Err`. The callback takes that lock to update, releases it, then emits. Never emit while holding a lock: `emit` runs Rust `listen_any` handlers inline (event/listener.rs:208-231), and a handler that invokes a command would deadlock.
- *Wire mapping* (added to contracts/ipc.md in the same commit, P-014):

  | Core value | Code |
  |---|---|
  | `Busy` | `download_busy` |
  | `AlreadyDownloaded` | `already_downloaded` |
  | `NotEnoughDiskSpace{needed}` | `not_enough_disk_space{needed}` |
  | `NotInCatalog`, or an id string `ModelId::parse` rejects | `not_in_catalog` |
  | `CannotStart` | `download_cannot_start` |

  Each needs a `messageKey`. Add `download.busy`, `download.already_downloaded`, `download.not_in_catalog`, `download.cannot_start` to core `i18n` with en/ru texts (T-039 is DONE, so there is no catalog conflict). `local_model_cancel_download` with an unknown id returns `false` (the contract has no error for it).
- *View fields.* `nameKey` needs catalog ids. Proposal: `local_model.name.<id>` for the five models, en/ru added here, so the `MESSAGE_IDS` test never sees a key without text. `loaded` is always `false` until T-017's residency exists.
- *Events "to the settings window only".* `emit_to(EventTarget::webview_window(settings_window::LABEL), …)` keeps the events from App- and other-label-targeted Rust listeners. Any webview's default-target JS `listen` still receives them. The real limit is decision #45's capability (only `settings` may listen). `settings://changed` uses `app.emit`, so the two differ on purpose; say so in the module doc.
- *Logging:* none until T-008. Never print a URL (contains the pinned path) or OS error text. Startup `cleanup_at_start` errors: one fixed stderr line, like the #45 interim.
- *Layout rules:* no `#[cfg(test)]`/`#[test]`/non-`text` doc fences in `src-tauri/src` (F-002, F-003; `make check` refuses them).
- *Install smoke (cheap proof that `run()` wires `open`):* before the first launch, put `%LOCALAPPDATA%\Voicen\models\ggml-tiny.bin.part`; after the start line, assert it is gone. This is the only proof that the release path runs the cleanup, the same way the smoke proves `on_ready`.

**Recurrence check (docs/failures.md).** None for this class. Rules that bind this task:
- F-001: the shell is tested in its own cargo invocation.
- F-002: shell tests live only in `src-tauri/tests/*.rs`; build.rs embeds the manifest.
- F-003: guards decide on switches or raw text; `doctest = false`; no `--doc`.
- F-004: a refused address never comes from a released port.
- F-005: Windows refusals take ~2.17 s; deadlines come from `REFUSAL_BUDGET`; timeout tests use a slow server. Recommended: no refused or stall case in the shell tests at all.

**Keeping Windows CI rounds few.** No Linux build of `src-tauri` exists. `lib.rs` has `compile_error!` off Windows (:72-103), Linux tauri needs webkit system libs (decision #5), and the image has only `x86_64-unknown-linux-gnu`. Mitigations:
1. Option A: logic and wire JSON go into core, proven by `make check` on Linux.
2. Mechanical churn is the main compile risk. `load_settings` gains a models argument (16 call sites in `tests/settings_ipc.rs`, `settings_window.rs`, `autostart.rs`); `build_app` gains `local_models` (4 sites). Change each file's helper first, then the direct calls, and grep the call count before committing.
3. `rustfmt --check` on the shell files runs in the core image (it parses but does not compile).
4. `make check-shell-layout` runs locally.
5. Add `--no-fail-fast` to `cargo test -p voicen` (ci.yml:62), so one red binary does not hide the others (F-005's lesson, applied to the shell step).
6. Not tried, owner decision: a `cargo check -p voicen --tests --target x86_64-pc-windows-gnu` step in the core image. It needs `rustup target add` (download), `mingw-w64` for tauri-winres' windres, and a built `build/` for `generate_context!`. The sources of tao/wry/webview2-com and the windows_x86_64_gnu crates are already in the registry cache. It would catch type and signature errors before a push. Separate spike task.

**Size.** One task under option A: core coordinator, wire types, mapping and i18n ids (~10 core tests, Linux); the shell module, wiring, Cargo feature, CI flag and smoke step (~8 Windows tests plus call-site churn in 3 test files); docs (ipc.md, architecture.md, a `docs/decisions/` note). If the orchestrator prefers, the core half can be its own Linux-proven commit series before the shell commits. Not a separate task.

**Recommended:** option A. First red tests: core `local_models_service` (wire JSON + error mapping), then `src-tauri/tests/local_models.rs::download_through_ipc_emits_progress_then_downloaded_and_settings_accepts_it`, followed by the failure-branch and cleanup cases.
