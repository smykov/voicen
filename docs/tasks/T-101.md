### 1. Frame: what is missing, and where

- Observed: no symbol file is kept from any build. There is no `pdb` anywhere in `src-tauri/`, `scripts/ci/` or `.github/` (grep -ri). The only artifact is the installer (`ci.yml:1594-1600`, v* tags only, #119). Whether a PDB is linked today: see hypothesis 1, corrected in §10.
- Expected (FR-014 as amended by #135): a tag release carries `voicen-<version>-symbols.zip`, so a `voicen.exe+0x…` frame from a crash file can be mapped to a function and line.

### 2. Hypotheses

1. **The profile prevents a PDB** (`Cargo.toml:17 strip = true`). **Status: refuted 2026-10-31 (§10).** rustc 1.99.1 passes `/DEBUG` at every strip value. The earlier "cannot be printed locally" was wrong: a `no_core` crate prints the MSVC link arguments without the MSVC std.
2. **A PDB exists but nothing keeps it.** True in any case: nothing in ci.yml names one. This is the CI half of the seam.
3. **A second path publishes assets.** Refuted. `gh` appears only in the release block (release-guard R5), and `gh release create` appears once (`release.sh:90`).
4. **This class was fixed before.** Refuted (see §6).
5. **The PDB could leak into the installer.** Refuted. `tauri.conf.json` `bundle.resources` holds only `THIRD-PARTY-NOTICES.txt`, and NSIS packs the exe and resources. The exe embeds the PDB file name only; rustc adds `/PDBALTPATH:%_PDB%`, also from source knowledge, so the runner path does not end up in the exe.

### 3. Why option A keeps the owned literals almost untouched

- release-guard **R9** allows the token `upload-artifact` exactly once in the workflows dir. A second upload step for the zip is therefore refused. Putting the zip in the **same** upload step means a two-line `path:`.
- upload-artifact uses the least common ancestor of all search paths as the artifact root. If the zip is written into `target/release/bundle/nsis/`, the LCA is that directory and the artifact stays flat. The release job's `download-artifact` into `dist` then gives `dist/<installer>` and `dist/voicen-X.Y.Z-symbols.zip`. `scripts/ci/release-job.yml` (R2) needs **no edit**; #135 allowed one but does not require it.
- Every existing consumer globs `*-setup.exe`, so a zip in that directory changes none of them: install smokes (`ci.yml:225, 963, 1067, 1112, 1274, 1366, 1417`), Telegram (`:1606`), SHA-256 step (`:1663`), release-check premise and failure branch (`:1669, :1684`).
- The release-check premise already runs on that directory on every ref. Once `release-check.sh` requires the zip, every `wip/` and `main` run exercises the pass path with the real zip, as the Acceptance asks.
- `if-no-files-found: error` fires only when *no* file matches. A missing zip alongside a present installer is caught by `release-check.sh`, not by the upload step. That is why the release-check case is the red test.

### 4. Build side effect of `debug` (found while checking T-117 overlap)

- When the profile's debug is on, Cargo sets `DEBUG=true` for build scripts.
- cmake-rs 0.1.58 `Config::get_profile` then picks `RelWithDebInfo` (`(OptLevel::Release, true)`) and passes it as `--config` at build time. This happens even when the crate defines `CMAKE_BUILD_TYPE` itself, which only replaces the configure-time `-DCMAKE_BUILD_TYPE`.
- whisper-rs-sys 0.15.0 is safe: its `build.rs:184` sets `.profile("Release")`.
- opusic-sys 0.7.5 only `define`s `CMAKE_BUILD_TYPE=Release` (`build.rs:200`). Under the default Visual Studio (multi-config) generator it would be built as `RelWithDebInfo`, while its `CMakeCache.txt` still says `CMAKE_BUILD_TYPE:STRING=Release`. That is exactly the line T-117's checker pins. The cache check would pass while the real configuration changed, and the cc crate would add debug flags to C deps.
- Hence the decision (#200 D1): line tables only for the workspace packages. The premise that a dependency's build script takes `DEBUG` from that dependency's profile is now checked on the real graph (§10). The opusic-sys `cmake --build … --config Release` line in the wip build log remains the final proof.
