## Context

The owner asked on 2026-10-07 for a tray menu item to look at the log ("В трее добавить пункт меню посмотреть лог"). While diagnosing T-006 they had to find `%LOCALAPPDATA%\Voicen\logs\voicen.log` by hand. FR-20 defines the log: local, rotating, with no transcript, audio or keys, so opening it shows nothing secret. The tray menu lives in `src-tauri/src/tray.rs`.

## Acceptance

- [ ] The tray menu has an item "Open log folder" ("Открыть папку логов"), both strings in the en/ru catalog (FR-15). Clicking it opens `%LOCALAPPDATA%\Voicen\logs` in Explorer, with the newest `voicen.log` selected or simply the folder (the analysis decides).
- [ ] Failure branch: the folder is missing or cannot be opened → it is created if missing, and if Explorer cannot be started a warning line is written to the log (no path or user name beyond what FR-20 already logs) and the app keeps running. Verified by a shell test.
- [ ] Test that fails without the change: named in `## Tests`.

## Investigation

**Tools.** Serena and context7 were not callable in this session (no `mcp__serena__*` / `mcp__context7__*` tools exposed). I used grep and file reads instead. windows 0.62.2 signatures come from the crate source in `.teamwright/cache/core/.../windows-0.62.2` (the version in the lock), not from memory.

**What is there.**
- Core table: `voicen_core::tray` has `TrayAction::{OpenSettings, Exit}` and `menu(_) = [OpenSettings, Exit]`. The shell renders it with `i18n::text` (`src-tauri/src/tray.rs::build_menu`). `on_menu_event` runs on the main thread: `OpenSettings` posts `settings_window::request`, `Exit` calls `app.exit(0)`, and `None` does nothing (no catch-all, per `docs/decisions/windows-shell.md` "Menu items ... come from one core table").
- Tests drive a click with `tray::on_menu_event(rig.handle(), MenuEvent { id: MenuId::new(action.as_str()) })` (`tests/tray.rs::menu_item`), over `build_app` with the mock runtime, `serial()` and `eventually()` pumping. The `Applied.menu` expectations are derived from `table::menu`, so they follow the new item without edits. Two tests list `"open_logs"` as an unknown id and must change: core `menu_item_ids_are_distinct_words_that_map_back_to_their_action` and shell `an_unknown_menu_id_does_nothing`.
- Log dir: `paths::log_dir()` (`data_dir()\logs`, falling back to `temp_dir()\Voicen\logs` without LOCALAPPDATA) is the one resolver (P-010). `release_parts` passes it to `diag::start`, and `Log::open` → `open_active` runs `create_dir_all`. So the dir normally exists after start. It is missing only if the folder was unwritable (Degraded) or was deleted while the app runs, which is why the click path creates it again.
- Warning format: `LogEvent::Warning { kind, os_code }` gives `warning kind=<snake> [os_code=N]` (`diag/format.rs`). A new kind needs `WarningKind` plus `warning_kind()` plus the exhaustive table in `crates/voicen-core/tests/diag_format.rs`. Caveat: if the logs dir cannot be written, the warning about it is dropped by the Degraded log. That is acceptable and should be documented.
- Catalog: `i18n/en.json` and `i18n/ru.json` (one catalog for shell and UI, T-005), with ids declared in `messages!` (`crates/voicen-core/src/i18n.rs`). Parity is checked by `Catalog::parity_problems`, `message_ids_exist_in_both_catalogs` and the UI parity test.

**How to open Explorer (options).**
- **A (recommended): `ShellExecuteExW`** with verb `open`, `lpFile` = the dir, `SEE_MASK_NOASYNC | SEE_MASK_FLAG_NO_UI`, on its own thread under `CoInitializeEx(COINIT_APARTMENTTHREADED)`. Its failure is a `windows::core::Error` (GetLastError), which gives an `os_code`.
  - Dependencies: feature flags `Win32_UI_Shell` (already in dev-deps) and `Win32_System_Com` on the existing windows 0.62.2. No new crate (#9). `helper-windows.txt` keys `windows@0.62.2` as `binding` without features, so the F-008 tripwire is unaffected.
  - Safety: no command line and no shell parsing, so no injection.
  - Guard: check `is_dir()` before the call, because verb `open` on a file would execute it.
- **B: `std::process::Command::new("explorer.exe").arg(dir)`.** No dependencies, and no injection because there is no cmd.exe.
  - Explorer's exit code is meaningless (it returns 1 on success), so only a spawn failure is observable. That leaves the "cannot be opened" branch untestable beyond spawn.
  - `/select,<file>` has comma parsing quirks.
  - A shell test would start an external process (F-006 class).
- **C: `tauri-plugin-opener`** (consented in #9; spec 006 ipc.md names it). It is not in Cargo.lock, so it adds a crate graph, needs `make licenses` and a helper-window manifest review. That is heavier for one call.
- **Select `voicen.log`?** That needs `SHOpenFolderAndSelectItems` with PIDLs, or the `/select,` quirks. I decided to open the folder only. The newest file is obvious by name (`voicen.log` next to `voicen-<stamp>.log`).

**Threading.** `on_menu_event` runs on the main thread, and ShellExecuteEx can block on shell extensions. So `request` hands the work to a short-lived named thread, as the tray already does with `spawn_blocking` for `tray_menu_opened`. A failed spawn also logs `logs_folder_failed`.

**Test seam.** `FolderOpener` is a port that the tray handler looks up as managed state, the same way it looks up `Arc<DictationSession>`. `run()` installs the Win32 opener after `assemble`. Tests install a fake over a `TempDir`, so no Explorer window opens on the runner.
- If the state is absent (not installed), the click does nothing. That matches the session lookup, but a forgotten `install` in `run()` would be silent. The owner's manual check covers it (`verify_exception`).
- The real adapter is checked on CI only on its failure branch (a missing path gives Err with code 2 under `FLAG_NO_UI`). That is a Windows premise, so it runs on `wip/T-071` before review (P-016).

**Hypotheses checked.**
1. A second path already opens folders: no. Grep found no ShellExecute, `explorer` or opener in `src-tauri/src`.
2. A fix of this class was made before: no. The item was planned and deferred (T-008 → T-054 by #64; T-054 → P3 by #69).
3. The log dir has another resolver: no. Only `paths::log_dir()`.

No recurrence. The relevant failure classes are rules to follow, not recurrences:
- `ci-premise-unchecked-before-main`: P-016, run on `wip/T-071`.
- `windows-ci-external-process` (F-006): no test spawns explorer.exe.
- `parallel-tests-share-session-state`: `serial()` first in every new `tray.rs` test.

**Conflicts for the orchestrator (not blocking the analysis).**
1. **Overlap with T-054.** T-054's title and Acceptance include this tray item, and decisions #64, `docs/decisions/diagnostics-log.md` (lines 5 and 71), `docs/decisions/windows-shell.md` §"Menu items", the core `tray.rs` doc comment and T-052's notes all name T-054 for it. Narrow T-054 to the one-time notice, and update those references in the T-071 commit.
2. **Texts.** The contract `specs/001-dictation-via-api/contracts/messages.md` has `tray.open_logs` = "Open logs folder" / "Открыть папку журналов". This task's Acceptance says "Open log folder" / "Открыть папку логов". Keep id `tray.open_logs`. Either confirm the Acceptance texts and update the contract row (and spec 006 `ipc.md` `tray.open_logs`) in the same commit, or use the contract texts.
3. **Failure behaviour.** Spec 006 FR-017 also requires a user notice "cannot open the logs folder: <reason>" on failure. There is no notifier yet (T-007), so this task logs only, and the notice stays with T-054/T-007. T-054's Acceptance ("with the folder missing it creates nothing") contradicts FR-017 and this task ("creates it"). This task follows FR-017.
4. Spec 006 `ipc.md` names `tauri-plugin-opener` for `open_logs_folder`. Option A replaces it. Record the choice in `docs/decisions/windows-shell.md` and fix the ipc.md row.

**Recommended:** option A. Red tests first: core `tray::tests` (menu, id, label, en/ru texts) and `diag_format` (`logs_folder_failed`), then the shell `tray.rs` tests named in `approach`.
