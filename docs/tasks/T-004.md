## Context

FR-13, FR-21, NFR-10. Svelte settings window over IPC `settings_get` / `settings_save`, first launch opens it on the Engine tab with engine none. Verified with Playwright against the built UI with mocked IPC. Also owns spec 004 T013 (IPC mock), the `error.<code>` texts of every `ErrorCode` (spec T044) and `notice.settings_reset`, and `SettingsView.unavailable` so the window shows `notice.settings_unavailable` on open (decision #38). The startup executor and the settings window lifecycle (spec T024/T025, the window half of T028) moved to T-037 by decision #38; its `settings.json` check is T-030's (#34). The speech-language picker gets its list from core (`WHISPER_ISO_639_1`) over IPC (`settings_speech_languages`, built by T-030), never a UI copy (decision #30).

## Acceptance

- [ ] First run (mocked `settings_get` returns first-run) opens on the Engine tab with engine = none and the v4 defaults shown
- [ ] Choosing API, entering URL, model and key, then Save calls `settings_save` once with those values; the key field is masked
- [ ] A saved change is reflected without reload (event `settings://changed`); changing `ui_language` re-renders visible text in the new language without reload — Playwright (T-005 review round 1 #2: the `$state` language store has no unit test, vitest loads Svelte's server build)
- [ ] Failure branch: Save with an empty base URL → `settings_save` is called once and returns core's `Refused [engine.api.base_url: required]` (scripted in the mock; the UI has no validation rule of its own, P-010, decision #38) → the field is highlighted with `error.required`, the draft is kept, the saved view is unchanged and no `settings://changed` follows; a `Refused [recording.hotkey: hotkey.unavailable]` → the hotkey field shows `error.hotkey.unavailable` and the saved value stays — verified by Playwright
- [ ] Every `ErrorCode` core can return has a non-empty `error.<code>` text in both catalogs (core test); with `SettingsView.unavailable` the window shows `notice.settings_unavailable` on open
- [ ] Test that fails without the change: `e2e/settings-first-run.spec.ts`

Investigator, 2026-10-04. Tools: Serena and context7 were not connected in this session (no `mcp__serena__*` / `mcp__context7__*` tools). I used grep and file reads over `src/`, `e2e/`, `src-tauri/`, `crates/voicen-core/`, `docs/` and `specs/004-*`. For Tauri I read the pinned sources in the cargo cache (`.teamwright/cache/core/.../tauri-2.12.1`, `tauri-runtime-wry-2.12.1`, `tauri-macros-2.7.1`) and `node_modules/@tauri-apps/api` 2.12.1 (pnpm-lock.yaml:447). Svelte/SvelteKit/Playwright APIs were not looked up. Nothing in this analysis depends on an API that is not already used in the repo.

### 1. Frame

- **Expected** (FR-13, FR-21, spec US1, Acceptance):
  - A first start opens a settings window on the Engine tab with engine none and the v4 defaults.
  - The user picks API, enters URL, model and key, and saves once.
  - A saved change, `ui_language` included, re-renders without reload.
  - Refusals show on their field.
- **Observed:**
  - UI: `src/routes/` has only `+page.svelte` (build info) and `+layout.ts` (`ssr = false`). `src/lib/` has `buildInfo.ts` and `i18n/`, and nothing for settings.
  - The e2e mock is inline and only knows `get_build_info`, with `transformCallback: () => 0` (`e2e/build-info.spec.ts:7-11`), so `listen` cannot work.
  - Catalog: 6 ids (`app.*`, `notice.choose_engine`, `notice.settings_unavailable`, `settings.write_failed`, `settings.partially_restored`). No field labels, no `error.*`, no `notice.settings_reset`.
  - Shell: `run()` keeps `_load_outcome` unused (`src-tauri/src/lib.rs:96`) and builds a static 800x600 "Voicen" window at every start (`tauri.conf.json:13-19`; no label, so it is `main`).
- **Where it reproduces:** everywhere. This is a gap, not a fault.

### 2. Hypotheses (need-style) and what the evidence says

1. **Only UI work is missing.** Refuted. The shell never opens a window from the outcome (lib.rs:96). The static window would show beside a `settings` window. Two more shell problems: the capability covers only `main`, and closing the last window exits the app (points 3c and 3d).
2. **The backend lacks something the Acceptance needs.** Partly confirmed:
   - `hotkey.unavailable` exists as a wire code. `ErrorCode::HotkeyUnavailable` → `"hotkey.unavailable"` (settings/mod.rs:260, 282). It is serialized in `Refused.errors` as `{"field":"recording.hotkey","code":"hotkey.unavailable"}`, pinned by `save_outcome_wire_form` (service.rs:2429).
   - Nothing produces it yet. The registrar is interim and fails closed, and it is never called (settings_ipc.rs `InterimHotkeyRegistrar`). The hotkey save step is T-010 (validate.rs:6, decision #23 N1).
   - So T-004 can and must test it only through the mock. The Acceptance's spelling `hotkey_unavailable` is 001's IPC/message spelling (`failure.hotkey_unavailable`, spec 001 contracts). On this wire it is `hotkey.unavailable`, and the text id is `error.hotkey.unavailable`.
   - Also missing:
     - `SettingsView` has no "unavailable" flag (service.rs:49-54). `Unavailable` sets only `LoadState.unavailable` (service.rs:229). So the window cannot show `notice.settings_unavailable` when it opens, only after a refused save (`FormError::SettingsUnavailable`).
     - `notice.settings_reset` exists in no catalog and no `messages!` (i18n.rs:71-83). T-032 left it to T-004 (T-032 Investigation §9).
3. **The same concern is handled on a second path.** This is the main design risk, not an existing defect:
   - Validation: core `validate` is the only rule. An empty base URL is `required` after `normalize_base_url` trim (validate.rs:101-107), and only for the selected engine. A UI pre-check ("settings_save is not called") would be a second copy of an engine-dependent rule (P-010, R-8 "one URL rule"). See Q1.
   - Defaults: the UI must not build them. The first-run view comes from `settings_get`. In e2e the mock's view should come from core's `defaults()` (option A3), not a hand copy.
   - Language list: comes from `settings_speech_languages` only (#30, decisions/settings.md "One language list").
   - Language: the UI never derives it (decisions/i18n.md). `setLanguage(view.settings.ui_language)` runs on every applied view.
   - Hotkey key set: the closed 82-key set is core's (R-6, #26). `HotkeyField` maps `KeyboardEvent.code` → token by a mechanical rule (`KeyA`→`A`, `Digit1`→`1`, `F5`→`F5`, `Numpad0`→`Num0`, `ArrowUp`→`Up`, `Space`, `Insert`…) and keeps no allowlist. Core refuses anything else with `hotkey.invalid`.
4. **This class was fixed before.** No. `docs/failures.md` has F-001 and F-002, both `ci-toolchain`. The class `settings-ui` appears only in this task, and `git log -- src e2e src-tauri/tauri.conf.json src-tauri/capabilities` shows only T-005, T-027 and T-030 work. One constraint does carry over from F-002 (#36, #37): shell tests may live only in `src-tauri/tests/*.rs`, with no `#[cfg(test)]`/`#[test]` and no doc code blocks in `src-tauri/src` (`make check` → `check-shell-layout`).
5. **Tauri behaviour makes the naive shell change wrong.** Confirmed from source:
   - (a) ACL: `plugin:*` commands are always checked against the window label (tauri webview/mod.rs:2080-2107), and `capabilities/default.json:6` lists only `main`. A `settings` window without a capability entry gets "not allowed" for `plugin:event|listen`, so `settings://changed` would never arrive. App commands (`settings_get`/`settings_save`) still pass, because there is no app ACL manifest. Playwright cannot see this.
   - (b) `getCurrentWindow().onCloseRequested` calls `this.destroy()` (`@tauri-apps/api` window.js ~2030), which needs `core:window:allow-destroy`. That permission is not in `core:window:default` (tauri permissions/window reference).
   - (c) The last window destroyed → `RunEvent::ExitRequested { code: None }` → the process exits unless `prevent_exit()` (tauri-runtime-wry lib.rs:4256-4270). Closing the first-run window therefore quits the app today.
   - (d) Config windows are created in `setup` on `RuntimeRunEvent::Ready` (tauri app.rs:1442-1447, 2688-2694). `.setup()` never runs in `build_app`/tests (decisions/settings.md J4). So the executor belongs in the `run()` callback on `RunEvent::Ready`, as a function the tests call directly.
   - (e) An unknown asset path falls back to `index.html` (tauri manager/mod.rs:375-415). So URL `settings?tab=engine` reaches the SvelteKit SPA route `/settings` without prerendering.

### 3. Root cause (need)

The settings backend was finished one layer at a time (T-003 → T-032 → T-030), but the two consumers of its outputs were never built:
- the window, which consumes `SettingsView`, `SaveOutcome` and `settings://changed`;
- the startup executor, which consumes `LoadOutcome` and `startup_action`.

So FR-21's "first start opens settings" and FR-13's "change any setting" have no code path. This one statement covers every Acceptance line, including both failure branches (they need the UI's `FieldError` → field mapping and the `error.<code>` texts). No evidence contradicts it.

### 4. Invariants

- **U1 — one source per value; the window derives nothing.** Every value shown comes from a `SettingsView`. `settings_get` at mount, the `Saved` outcome's `view` and the `settings://changed` payload all go through one `applyView(view)`. It does three things: replace the saved baseline; reset the draft when not dirty; call `setLanguage(view.settings.ui_language)` on every view. The window holds no defaults, validation rules, language list or language derivation.
- **U2 — every refusal is shown, localized, on its field.** For each `FieldError`, the input carrying `data-field="<FieldId>"` is highlighted (`aria-invalid`), and `error.<code>` is shown next to it. A `form_error` shows its `message` id at form level. A rejected `invoke` shows `error.ipc_unavailable` and never the rejection text (ipc.md "Errors"). The draft is kept in every case.
  - Closed by a core test in `i18n::tests`: every `ErrorCode` (list pinned by a wildcard-free match, e.g. `ErrorCode::ALL`) has a non-empty `error.<code>` in both embedded catalogs. A code added later by T-010, T-014, T-020 or T-021 fails the gate until its texts exist.
  - In TS, error ids are built as `` `error.${code}` `` through one narrow helper, so the UI holds no third list of codes. `text()` already falls back to the id, so a missing entry would show as the raw id; the core test prevents that.
- **U3 — no key value is shown or kept.**
  - `KeyField` shows presence only ("key saved"). Its input is `type="password"` and starts empty.
  - It sends `Untouched` (default), `{Replace: typed}` once typed, or `Clear` (button). It resets to empty/Untouched on `Saved`.
  - The key value exists only in the one `settings_save` request (J1).
- **S1 (shell task) — one way to open a window.**
  - `settings_window::open(app, tab, field)` is the only window constructor. Label constant `settings`, URL `settings?tab=<tab>[&field=<FieldId>]`.
  - If the window exists: `set_focus` plus emit `settings://focus {tab, field}`.
  - At startup: `execute_startup(app, startup_action(&outcome, launched_by_autostart(args)))` on `RunEvent::Ready`.
  - `tauri.conf.json` declares no window, and the capability lists `settings`.

### 5. Seam and component structure (UI)

- **`src/lib/settings/settingsApi.ts`** holds two things:
  - TS wire types exactly as in contracts/ipc.md: `SettingsView`, `Settings`, `KeyEdit = "Untouched" | "Clear" | { Replace: string }`, `SaveRequest`, `SaveOutcome`, `FieldError`, `FormError`, `Warning`.
  - The only `invoke`/`listen` calls: `getSettings`, `saveSettings`, `speechLanguages`, `onSettingsChanged`, and later `onSettingsFocus`.
- **`src/lib/settings/draft.ts`** (pure, vitest per spec T037): draft vs baseline, dirty, `KeyEdit` state per slot, `errorsByField(outcome)`, `applyView`. vitest can test pure TS, but not the `$state` store (T-005 review #2), so the store is tested in Playwright.
- **`src/routes/settings/+page.svelte`**: the tab bar (Engine, Recording, Output, Post-processing, History, General); the initial tab from `?tab=`, else `engine`; `?field=` focuses that input; Save button; form-level messages; a reset banner when `reset_notice`.
- **Tabs** (fields → FieldId, the dotted strings of data-model):
  - **Engine**: `engine.kind` (none/api/builtin_local/local_server).
    - API: `engine.api.base_url`, `engine.api.model`, `engine.api.key`.
    - Local server: `engine.local_server.base_url`, `engine.local_server.model`, `engine.local_server.key`.
    - Built-in: `engine.builtin_local.model_id`, a placeholder for 002's `LocalModelList` (T-016).
    - `engine.speech_language`: "auto" plus the codes from `settings_speech_languages`, named with `Intl.DisplayNames(currentLanguage)`.
  - **Recording**: `recording.hotkey` (`HotkeyField`), `recording.mode`. `recording.microphone` is out of scope (no `settings_list_microphones`, Q5).
  - **Output**: `output.auto_paste`.
  - **History**: `history.enabled`, `history.size`.
  - **General**: `general.ui_language`. `general.start_with_windows` belongs to T-034.
  - **Post-processing**: the tab shell only; the fields belong to T-021.
- **Catalog**: T-004 owns the en/ru ids for its tabs and labels (spec T027 and T044, which no other task owns), plus:
  - every `error.<code>` of the 14 current `ErrorCode`s, so `error.autostart.failed` (T-034) and `error.hotkey.unavailable` (T-010) exist before those tasks;
  - `error.ipc_unavailable`;
  - `notice.settings_reset`, also declared in `messages!` so T-006's notifier can use it.
  - Later codes (003's, `endpoint.insecure`) are added by their owners, and the core test enforces it.

### 6. IPC mock shape (spec T013, `e2e/support/tauriMock.ts`)

- **API:** `installTauriMock(page, { view, speechLanguages, saveOutcomes? })` installs one init script. It defines:
  - `window.__TAURI_INTERNALS__ = { invoke, transformCallback, unregisterCallback, metadata: { currentWindow: { label: "settings" }, currentWebview: { windowLabel: "settings", label: "settings" } } }`;
  - `window.__TAURI_EVENT_PLUGIN_INTERNALS__.unregisterListener` (`_unlisten` calls it, event.js).
  - Init scripts must be self-contained, so `@tauri-apps/api/mocks` cannot be imported there. Its `mockIPC` (mocks.js) is the model for the callback registry.
- **Commands:**
  - `settings_get` returns the state's view.
  - `settings_speech_languages` returns the list.
  - `settings_save { request }`:
    - records the call;
    - if a scripted outcome is queued, returns it and changes nothing;
    - otherwise returns `Saved { view, warnings: [] }`, where `view.settings = request.settings` and presence comes from the KeyEdits (Replace non-blank → true, Clear → false, Untouched → keep), stores that view and emits `settings://changed` with it, as the bridge does (J3).
    - The mock never validates. A refusal is always scripted, so the mock holds no copy of core rules.
  - `plugin:event|listen` / `unlisten` keep the handler ids.
  - Any other command rejects, as today, so a call outside the contract fails the test.
- **Node-side helpers:** `calls(page, cmd)`, `storedView(page)`, `emit(page, event, payload)` (runs every registered callback with `{ event, id, payload }`), `queueSaveOutcome(page, outcome)`.
- **Assertions on stored state** (P-006, api_verify "assert the effect"):
  - `storedView` after `Saved` has `keys.transcription_api === true` and no key string anywhere in its JSON;
  - after a scripted `Refused` it is unchanged and no `settings://changed` was emitted.
- **Option A3 (recommended, cheap):** the first-run view and the 97 language codes come from a committed fixture `e2e/fixtures/settings-wire.json` that a core test compares with `serde_json` of `view` over `defaults(None)` with `first_run: true` and with `WHISPER_ISO_639_1`. This is the same pattern as `i18n/conformance.json`. Then "the v4 defaults shown" asserts core's `defaults()`, not a TS copy (P-010). Without A3 the mock hand-copies the defaults, and drift goes unnoticed.

### 7. Startup executor and window (spec T024/T025; proposed shell task)

- **`src-tauri/src/settings_window.rs`:**
  - `pub const LABEL: &str = "settings"`.
  - `pub fn open<R: Runtime>(app: &AppHandle<R>, tab: SettingsTab, field: Option<FieldId>) -> tauri::Result<()>`: if `get_webview_window(LABEL)` exists, call `show` + `unminimize` + `set_focus` and `emit_to(LABEL, "settings://focus", {tab, field})`. Otherwise `WebviewWindowBuilder::new(app, LABEL, WebviewUrl::App("settings?tab=…[&field=…]".into()))` with title "Voicen" and the old size. The window is destroyed on close, which is Tauri's default.
  - `pub fn execute_startup(app, action: StartupAction)`: `OpenSettings(tab)` → `open(tab, None)`; `TrayOnly` → nothing.
  - It never decides anything itself (`startup_action`, gate.rs:62).
- **`run()`:**
  - `let action = startup_action(&outcome, launched_by_autostart(std::env::args_os()))`.
  - Then `.run(move |h, e| if let RunEvent::Ready = e { settings_window::execute_startup(h, action) })` (point 2.5d).
  - Reset and Unavailable notices: the window shows them from `SettingsView` (`reset_notice`, and the proposed `unavailable` flag, Q4). The toast form waits for T-006's notifier.
- **`tauri.conf.json`:** `app.windows: []`. **`capabilities/default.json`:** `"windows": ["settings"]`; add `core:window:allow-destroy` only together with the discard dialog (point 2.5b).
- **Tests:**
  - Windows CI `src-tauri/tests/settings_window.rs` over `mock_builder()` + `build_app` (no `.setup()`, J4):
    - `execute_startup(OpenSettings(Engine))` → exactly one webview window `settings` whose URL path/query is `settings?tab=engine`;
    - `TrayOnly` → no window;
    - a second `open(Recording, Some(RecordingHotkey))` → still one window, plus one `settings://focus` event with that payload;
    - for the capability: build with `generate_context!(test = true)` if it compiles with the mock runtime (unverified), else assert from `capabilities/default.json` that `LABEL` is listed.
  - Install smoke (ci.yml, the first-launch step):
    - after the first launch the process has a visible top-level window (`MainWindowHandle -ne 0`);
    - on a second launch over the written `settings.json` (`Loaded`), none within N s.
  - The `settings load outcome=first_run` log line of spec T028 is an R-11 line, so T-008 owns it (#23 N6 routed R-11 to T-008). `settings.json` = engine none is T-030's (#34).
- **Linux vs Windows:**
  - Linux: Playwright (built UI, mocked IPC) proves U1–U3 and the mock contract; core tests prove the catalog completeness and fixture tests.
  - Windows CI proves the window lifecycle, `startup_action` execution, the capability, the install smoke, and that a real `settings_save` reaches `settings://changed` in the window. Only the owner's T066 check proves the last one end to end, since no automated test drives the real webview.
- **Interim between this task and T-006 (Q3):**
  - With no static window, a `Loaded` start shows nothing, has no tray, and runs until killed.
  - Closing the first-run window exits the app (point 2.5c).
  - `prevent_exit` belongs with T-006's tray and its Exit item (a tray app must stay alive; FR-01). Before that a tray-less app would be unkillable without Task Manager.

### 9. Approach options

- **A (recommended): split by seam.**
  - **T-004 = UI** (sections 5 and 6, U1–U3, the core error-catalog test and the A3 fixture test):
    - `surface: ui`, verified by Playwright against the built UI with mocked IPC. `deploys` is the orchestrator's call: the UI ships in the installer, but its verify evidence is Playwright.
    - Red first: `e2e/settings-first-run.spec.ts`, the four cases in `approach`. It is red today: `/settings` is not a route.
    - Further red cases: `src/lib/settings/draft.test.ts` (dirty, KeyEdit transitions, FieldError → field), and the core `every_error_code_has_catalog_text` (red until the 14 `error.*` ids exist).
  - **New shell task** (section 7, S1):
    - `surface: none`, `deploys: true`, `depends_on: [T-004, T-030]`.
    - Red first: `src-tauri/tests/settings_window.rs` (Windows CI) and the window assertions in the install smoke.
    - Risk: low; it is a new file plus a config change. Rollback: revert, and the static window returns.
