## Investigation

Tools: Serena was loaded but not used for `src-tauri` (Windows-cfg crate). I used file reads and grep on `src-tauri/src/overlay.rs`, `overlay_class.rs`, `call_indicator.rs`, `src-tauri/tests/overlay.rs`, `lifecycle.rs`, `overlay_ipc.rs` and core `crates/voicen-core/src/overlay.rs`. tauri behaviour comes from the pinned sources in the core image's cargo registry cache (`tauri-2.12.1`, `tauri-runtime-wry-2.12.1`, matching `Cargo.lock`), not from Context7 or memory. **Frame.** T-173 review 1 #1 claimed that the receipt does not cover an outside `Destroyed` that has not reached the mailbox yet, so the test's single visibility read can come before the rebuild. Expected: after an outside destroy, a newer shown state gives exactly one visible overlay, and the test reads it only once it exists. The follow-up's line refs are stale: the publish is now `tests/overlay.rs:1002-1007` and `run` is `src/overlay.rs:311-343`.

**Hypotheses.**
1. *The gap is real and the receipt settles on a stale handle.* Confirmed from source:
   - runtime-wry `handle_event_loop` (`lib.rs:4224-4233`) calls `callback(RunEvent::WindowEvent{Destroyed})` before the window's listeners. That callback is tauri's `make_run_event_loop_callback` → `on_event_loop_event`, which calls `manager.on_window_close(label)` (`app.rs:2714`; `manager/mod.rs:643-657`, whose comment says the same), then the user's run callback (`app.rs:1495-1496`).
   - Only after that does our `on_window_event` closure (`overlay.rs` `build_window`) call `shared.destroyed(generation)`.
   - The test's `eventually(!is_window(old) && get_webview_window(LABEL).is_none())` can return inside that gap, and so can a real Alt+F4 followed by a state change.
2. *The product rebuilds a moment later, so only the test read is wrong* (the review's assumption). **Refuted:**
   - In the gap the wake carries `destroyed = []` and Processing. The reducer is `Live`, the state is newer and shown, so it answers `Emit(seq)` (core `overlay.rs:318`).
   - `emit_to` goes through `emit_filter` over the webviews that still exist; there are none, so it returns `Ok(())` (`manager/mod.rs:622-627`). `failed = false`.
   - The handle is still `Some`, so the thread settles `{seq, window: true, failed: false}`.
   - Next wake: `destroyed = [g]`, same seq. `gone`, and the phase goes to `Absent`, but `rebuild_wanted` is false (`:295`: only from `Destroying`) and `newer` is false. So `:309` does not build: `Nothing`.
   - Result: no overlay until the next state. The core property test even allows this ending: `GenWorld::apply`'s `None` arm (`:1098-1102`, "the emit is lost"), and the post-settle check expects no window.
   - So option B of the follow-up (record the handled destroy, wait on it) would make the test wait and then fail for real. Or, if the test waited before publishing, it would no longer exercise the gap while the product kept losing the state.
3. *A second path.* Yes: `call_indicator.rs` `run` (`:346-355`) has the same shape: snapshot, `on_wake_visible`, Emit to a gone window. The indicator takes clicks, so a user can close it more easily than the click-through overlay. The requested-destroy path is safe: in `Destroying` the reducer only records the wanted state and rebuilds on `Destroyed` (`rebuild_wanted`), which is invariant 2's original argument.
4. *This class was fixed before.* Partly:
   - T-057 review 1 findings 1–3 fixed the order of `Destroyed` versus state inside the mailbox: one wake hands over both, and generations ignore stale `Destroyed` events. T-172 made `window_gone` the reducer's answer.
   - All of them assume that "the Destroyed is in the mailbox" is the same moment as "the label is free". `docs/decisions/overlay.md` §2 names the gap but argues only that a build is safe after it. It does not consider an Emit or a shown state that arrives inside it.
   - The Destroy-failure rule (`overlay_class::execute`) already uses the probe this fix needs: `get_webview_window(T::LABEL).is_none()`, then post a synthetic `Destroyed` for the current generation.
   - `docs/failures.md` has no entry of class `overlay` and no receipt class row. F-019 / `os-answer-deadline-race` (T-173's class) is a different mechanism: a clock against a cold build. F-036 is a pixel read once after the indicator's receipt, also different. **Not a recurrence with incidents:** no CI sighting (below), and the earlier fixes did not fail on their own inputs. This task completes T-057's invariant for the window before `Destroyed`. I do not recommend an rca; the orchestrator may decide otherwise.

**Root cause.** See the front matter. It explains the predicted symptom: red only on `one_after_newer`, with receipt `{seq: Processing, window: true, failed: false}`, no warning, and a visibility read of `false`. It also explains why CI has not shown it: the gap is two consecutive steps of one main-thread dispatch, and our listener's place in runtime-wry's listener `HashMap` order is random.

**Invariant / seam / options.** See the front matter.
- Why the label probe and not an `IsWindow(hwnd)` probe: the HWND dies before tauri frees the label, and a Build answered then would fail with `WindowLabelAlreadyExists`. The label is the fact the build depends on, and the test reads the same map (`get_webview_window`).
- Residual: tauri removes the windows map entry, then the webviews map entry, in one `on_window_close`. `get_webview_window` reads the second, and `get_window` (the first) needs tauri's `unstable` feature. A state published in that sub-gap still counts as published "before" the window went, under the invariant's own definition.
- The probe slightly widens "same wake": a state published just before the label was freed, but taken after it, is rebuilt. That is today's same-wake behaviour (finding 1), not a new product rule.
- MockRuntime cannot host the red test: its `destroy` never frees tauri's maps. `Webview::close` frees only the webviews map, so a rebuild would hit `WindowLabelAlreadyExists` on the windows map. That is why the red test is on Wry, held in the run callback. The developer confirms that the hook's `RunEvent::WindowEvent{label: "overlay", Destroyed}` runs before the window listeners, as the cited sources say, by having the hook record that `shared`'s mailbox still lacks the generation. If that cannot be observed, record why.
