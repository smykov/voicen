## Context

Second instance of class `ci-toolchain` (F-001, fixed by T-033). Found by the T-030 re-analysis after its VERIFY_FAIL round 1 (docs/tasks/T-030.verify/1.md; CI run 37159339288): the `src-tauri/tests/settings_ipc.rs` exe exits `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND` on windows-latest. Investigator's cause (from locked sources, not yet observed in the binary): tauri-build embeds its Common-Controls v6 manifest only into bin targets (`cargo:rustc-link-arg-bins` via tauri-winres / embed-resource), so integration-test exes load comctl32 v5.82, which lacks `TaskDialogIndirect` imported by muda's About dialog (tauri default feature `common-controls-v6`). Shared mechanism with F-001: tauri-build's link outputs reach different subsets of cargo targets (search paths: every target in the invocation; link-args: every target of the package; manifest resource: bins only), and the Windows job links doctests and integration tests that each get a different subset — visible only in Windows CI after review.

T-030 is deferred into this task (`absorbed_by: T-035`); T-014 (CODE_COMPLETE, unpushed) adds `src-tauri/tests/autostart.rs`, which hits the same failure. Proposed exit (a) code: `src-tauri/build.rs` emits `cargo:rustc-link-arg-tests=/MANIFEST:EMBED` and `/MANIFESTINPUT:<dir>\windows-app-manifest.xml` (a byte copy of tauri-build 2.7.1's manifest) on windows-msvc only — the release bin keeps tauri-build's manifest unchanged; upstream tauri does the same for its own tests. A possible exit (c) — a process/CI guard that fails when any built Windows test exe does not start — is the owner's decision.

## Investigation

Investigator, 2026-10-04. Scope: the class-level analysis. The instance (F-002) was found and analysed in docs/tasks/T-030.md, "Re-analysis after VERIFY_FAIL round 1". F-001 is analysed in docs/tasks/T-033.md. Both are cited here and not derived again.

**Tools.** Serena indexes TypeScript only (decision #3), so I used grep and file reads for Rust, TOML and YAML. Locked crate sources: `.teamwright/cache/core/_usr_local_cargo_registry/src/` (tauri 2.12.1 build.rs, tauri-build 2.7.1 windows-app-manifest.xml). Cargo source: `gh api` on rust-lang/cargo branch `rust-1.99.0`, path `src/compiler/custom_build.rs` and `src/compiler/build_runner/mod.rs`. CI log: `gh run view 37159339288 --log-failed`. Metrics: `python3 scripts/metrics/teamwright-metrics`. I did not use context7: the question is about cargo and tauri internals at the pinned versions, and the source is the primary record. There is no Windows host, so binary-level confirmation is still the decision rule in T-030 (outcomes i / ii / iii).

### Frame (class level)

- **Observed, twice:**
  - F-001: the windows job was red from T-003 until T-033 (link error in a voicen-core doctest).
  - F-002: the windows job is red at f2e239b (settings_ipc exe does not start).
  - Both times every `deploys: true` task behind it was blocked. Both times the defect was first seen after review: F-001 by the T-030 analysis, F-002 by T-030's verify round 1.
- **Expected:** every test exe that the Windows job builds links and runs to its `test result` line. Then the tauri build, install and smoke run.
- **Symptoms vs guesses:** the two symptoms differ: a link error (LNK1120) and a loader error (0xc0000139). The shared mechanism below is what makes them one class. It is shown from cargo's scope table and from tauri-build's outputs, not from the matching label.

### Hypotheses

1. **One mechanism: build-script link outputs are scoped for the app bin, but other exe kinds are linked too.** Confirmed.
   - cargo 1.99 `custom_build.rs:266-277` `LinkArgTarget::applies_to` is a closed table: `All` reaches every target, `Bin` → `is_bin()`, `Test` → `is_test()`, `Bench`, `Example`, `Cdylib` (not in test mode).
   - `rustc-link-search` is outside that table. It is a per-invocation `native_dirs` set that every doctest receives (T-033: `build_runner/mod.rs:301-312`, `cargo_test.rs:231-233`). Doctests get only their own package's matching link args (`mod.rs:251-270`).
   - tauri-build uses three of these scopes for one goal, "the app exe links and starts":
     - the stub search dir (invocation-wide);
     - the CRT args (`All`, package-wide);
     - the manifest (`Bin`).
   - Any other exe kind that reaches tauri code gets a partial subset. F-001 is the search dir without the args. F-002 is the args without the manifest.
2. **Two unrelated defects that only share the `ci-toolchain` label.** Refuted. They have the same producer (src-tauri/build.rs → tauri-build), the same mechanism (hypothesis 1) and the same detection point. A fix for either one at another level (for example, dropping the static VC runtime or the `common-controls-v6` feature) changes the release binary. Both instances already rejected that option for that reason (T-033 rejected `staticVCRuntime: false`; T-030 rejected option C).
3. **The class lives in architecture: decision #5 puts the shell's only check after review.** Partly. Decision #5 explains why the class shows late, not why it happens. The mechanism is closed in one seam (build.rs). The F-001 half is closed in ci.yml, which is already done. Metrics do not mark a hotspot here: there are no recurring areas, and `src-tauri/build.rs` has no fix commits in the hotspot table. So /arch-review is not warranted for this class.
4. **The class lives in process: the rule had no check.** Partly. F-001's rule is T1 (a ci.yml comment plus the reviewer), and it covers only the search-path half across packages. Nothing in the working path told the T-030 author that integration-test exes do not get the manifest. A reviewer could not have seen it either, because the shell is never linked before review (`docs/process/principles.md` §3, canon vs path). The gate check in the decision moves the precondition of the code invariant to T3 on Linux, before review. A latency fix for all Windows-only defects is a separate and wider question (optional exit (c) below).
5. **This class was fixed before.** Yes. T-033 (F-001, d8349af) split the Windows test step by package. It held for what it covered: in run 37159339288 the step `cargo test --workspace --exclude voicen` shows `Doc-tests voicen_core` with 2 passed and no LNK4003 anywhere in the log. But its invariant names one output (the stub search dir) and one exe kind (other packages' doctests). It does not name "every exe kind the voicen package links". The next exe kind, integration tests with a tauri runtime (T-030, first added in a727b4b), hit the next output, the manifest. Earlier patches of the class: d8349af only. No earlier change touched src-tauri/build.rs (`git log -- src-tauri/build.rs`: skeleton only).

### Root cause

See `analysis.root_cause`. It explains every symptom of both entries:
- only on MSVC;
- only test exes, while the release exe links and starts;
- F-001 only in other packages' doctests;
- F-002 only in the integration test that reaches tauri window creation, while credentials.rs, which reaches no tauri code, passes;
- each seen only after review.

Contradicting evidence: none. Not yet observed: the F-002 import name in the binary (T-030 decision rule).

### Recommended exit

**Recommended exit**: (a) code. The class lives in one seam, src-tauri/build.rs: the producer of the shell's link configuration. cargo's scope table is closed (custom_build.rs:266-277), so the invariant can be stated over all exe kinds:
- bin: tauri's outputs;
- tests: the same manifest, through rustc-link-arg-tests;
- lib/bin unit-test exes, lib doctests, benches, examples: no selector can reach them without also reaching the bin. `All` would duplicate the bin's RT_MANIFEST (T-030 option D). So these kinds must not contain tests, and a Linux check enforces that.

The F-001 half needs nothing new: ci.yml's split already stops other packages from sharing the invocation.

### Options

- **A (recommended): build.rs test manifest plus a Linux gate check plus the written rule.**
  - **build.rs:** as T-030 option A (detail and risks there).
  - **Gate check:** for example `scripts/ci/shell-test-layout.sh`, called from a new Makefile target that `check` depends on. It runs on the host, because it is a plain grep with no toolchain. It fails on any of:
    - `#[cfg(test)]` or `#[test]` under `src-tauri/src`;
    - a `///` or `//!` code fence under `src-tauri/src` other than ```` ```text ````;
    - `src-tauri/benches`, `src-tauri/examples`, or `[[bench]]` / `[[example]]` in src-tauri/Cargo.toml.

    The message names the rule and the file docs/decisions/ci-toolchain.md. Its exit: move the test to `src-tauri/tests/` or into voicen-core. If a new exe kind is ever really needed, extend build.rs and the rule together in one reviewed change.
  - **Why this removes the cause:** every shell exe that contains tests is a kind that build.rs configures fully. New integration tests need no action.
  - **Red before the fix:**
    - Manifest: run 37159339288 (settings_ipc 0xc0000139) against this task's windows run.
    - Gate check: on HEAD before the change, add `#[cfg(test)] mod t {}` to src-tauri/src/lib.rs and run `make check`. It stays green (no guard). With the check it goes red, and on HEAD without the mutation it is green. Do not commit the mutation.
  - **Risk:**
    - The check forbids pure-logic unit tests in src-tauri/src. That is intended: platform-independent logic belongs in voicen-core (CLAUDE.md), and Windows logic is tested in src-tauri/tests.
    - The manifest copy can drift on a tauri-build upgrade. The pin comment and the area file make that visible. An optional drift check (compare the copy with the locked tauri-build's file) can be added later. Not required.
  - **Rollback:** revert build.rs, the manifest, the script and the Makefile line.
- **B: build.rs plus the written rule only (T0).** It fixes the instance, but the third instance (for example a `#[cfg(test)]` module in src-tauri/src that builds an app) would again surface only in Windows CI after review. It does not satisfy the failures.md rule that a second entry moves the rule up a tier.
- **C: A plus a CI step that fails unless every built test exe printed a `test result` line.** Not recommended: redundant. cargo already turns the step red when an exe does not start (run 37159339288, exit code 1), and the change adds no `continue-on-error`. A smaller optional improvement is `--no-fail-fast` on the windows `cargo test -p voicen` step. With it, one red run lists every exe that cannot start, instead of stopping at the first. It is diagnostic only and not needed for the invariant.
- **Fallback for the build.rs half** (T-030 outcome iii, a linker or mt problem): `embed_resource::compile_for_tests`. It needs owner consent for a direct build-dependency (decision #9).
- **Rejected** (in T-030): drop `common-controls-v6` (it changes the release and is a case list); a manifest on all targets (it changes the release manifest or duplicates RT_MANIFEST).

### Optional owner decision: exit (c), detection latency (not blocking exit (a))

Both entries cost a red windows job after review, because shell code is first linked on Windows only after it is CODE_COMPLETE and pushed: decision #5 plus the pre-push gate (`TEAMWRIGHT_PUSH_STATUSES`). For src-tauri, the canon "gate green before NEEDS_REVIEW" has no working path. This affects every Windows-only defect, not only this class, and exit (a) closes this class without it.

Draft for the owner, only if wanted:
- A new principle, or a superseding entry for the gate rule: "a task that changes src-tauri reaches NEEDS_REVIEW only with a green Windows CI run of its commit".
- The working path it needs:
  - ci.yml also runs the windows job up to `cargo test -p voicen` on pushes to `ci/T-*` branches, or on `workflow_dispatch`;
  - the pre-push gate gets a recorded exit for pushes to `ci/*` refs.
- Tier: T1 (reviewer checks that the run is linked in the task) and T3 later if it is missed.

This changes PRINCIPLES.md (minor version) and the push rule, so it is the owner's decision with a decisions.md row. My recommendation: decide it if a third Windows-only defect of any class appears. It is not needed to close T-035.
