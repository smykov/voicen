## Investigation

**Frame.** Observed: with `post_processing.enabled = true` and a hand-edited `post_processing.model` of `"  gpt-x  "` in `settings.json`, the chat request body carries `"model": "  gpt-x  "`. Expected: `"gpt-x"`, the same rule as the transcription engines (decisions/settings.md, T-169). This is from reading the code; nothing was run (investigator does not write tests). Reproduced only by reading: `load_or_init` → `snapshot()` → `pipeline.rs:384-385` → `ChatPostProcessor::process` → `send` → `json!({"model": settings.model, ...})`.

**Hypotheses.**
1. *`send` reads the model raw.* Confirmed: `chat.rs:104`.
2. *Load does not normalize.* Confirmed: `service.rs:309-310` puts the `parse_file` result straight into `current` (`:334`); `normalize` has two callers, `save` (`:405`) and `connection_test.rs:235` (overlay). `parse_file` (`settings/mod.rs:297-307`) only fills `calls.primary_language`.
3. *Validate would refuse it.* Refuted: `post_process/settings.rs:51` checks `model_name(..).is_none()`, so padded is valid, and validate runs only on save anyway.
4. *A second path trims already (UI, IPC, shell).* Refuted as a guard: the UI binds the field raw (`src/lib/settings/tabs/PostProcessing.svelte:65`), `src-tauri/src` never touches `post_processing` (grep), and core `save` trims via `normalize`, which covers only edits saved through the app, not a hand-edited file. The connection test normalizes its overlay, so its post-processing check is already trimmed. Dictation is not.
5. *Class fixed before.* Yes, for transcription: T-169 (0606112b) added `settings::model_name` and routed `normalize`, both validates and both `engine_for` arms through it (`engine/mod.rs:89,100`). Test pattern: `tests/openai_client.rs::api_set_model_is_sent_trimmed`. T-169's analysis named `chat::send` as an "optional follow-up". Its review r1#2 turned that into this task.

**Recurrence check.** The class is "an untrimmed settings value sent on the wire". Earlier instances: T-169 (transcription API model), T-046 (typed key sent untrimmed, `typed_key_is_sent_trimmed_without_reading_the_store`), T-171 (padded `VOICEN_COMMIT`). `docs/failures.md` has no F-entry for it (grep for trim/model). This is not a fix that failed to hold. It is the remainder T-169 knowingly scoped out. Its invariant ("model_name is the only reader") is enforced by review only. **Second raw reader, still open:** `call::final_pass::api_engine` (`final_pass.rs:665-669`) passes `Some(settings.api.model.clone())`, so a padded `api.model` is sent padded in the call final pass. The contract (`docs/decisions/call-final-pass.md:93`, `specs/007-call-mode-record/contracts/core-call.md`) only says "a blank model is not checked". Padded is not addressed. T-229 only scopes the docs. No task fixes that code. The orchestrator should file it as a follow-up, or open an rca if a third raw reader turns up. It is outside this task's Acceptance.

**Seam choice.** Send-time in `chat::send`, through `model_name`:
- `send` is the one place the ChatRequest body is built, and `process` is its only caller. The fix holds whatever the settings came from: loaded file, saved draft, connection-test overlay, or `PostProcessingSettings` built by tests or `pipeline.retry` callers.
- It follows the T-169 rule: "every reader goes through `model_name`; don't trim by hand".
- Normalize-on-load would also fix `api_engine`. But it covers only `SettingsService` snapshots, it changes load semantics for every field `normalize` touches (base URLs, `schema_version`, `storage_root`), and the in-memory snapshot would then differ from the file bytes. That is a wider behaviour change than this task needs.

**Blank model.** `model_name(..).unwrap_or("")` keeps today's behaviour for a hand-edited blank with `enabled = true`: it sends `""` and the server answers, giving `Skipped(Http)` or `InvalidKey`. Turning blank into `Skipped(NotConfigured)` is a product choice and stays out of scope.

**Red test to follow.** `crates/voicen-core/tests/post_process_chat.rs` has the wiremock harness: `server_with`, `chat_reply`, `run`, `only_request`, `pp_settings`, `creds_with_key`. `reply_is_applied_trimmed_from_one_chat_completions_request` already asserts `body["model"] == json!(MODEL)`. The new test `padded_model_is_sent_trimmed_in_the_chat_body` copies that test with `model` set to `"  gpt-x  "` and asserts `body["model"] == json!("gpt-x")` and `Applied`. Optional mutant for the catalog: drop the `model_name` call at `chat.rs:104`.

**Docs in the same commit.** `docs/decisions/settings.md` (§ "A model name is set only when non-empty after trim", "Where it is enforced": add `post_process::chat::send`). `specs/003-llm-post-processing/data-model.md` › ChatRequest (`<snapshot.model>` sent trimmed). Coordinate with T-229, which lists `chat::send` as an exception: after this fix it is no longer one.

**Size.** Small: one seam, one production line plus one import, one test, two doc lines. `checker: false` holds, since no guard path is touched.

**Tools.** Serena `get_symbols_overview` / `find_symbol` on `chat.rs`, `settings/mod.rs` and `tests/post_process_chat.rs`. `find_referencing_symbols` on `model_name` returned nothing, so call sites came from grep over `*.rs`. Context7 was not needed: no library API changes, and `serde_json::json!` usage is unchanged.
