## Context

FR-03 (toggle; 10 min maximum stops and processes with a notice), FR-22.

## Acceptance

- [ ] Toggle: press → speak 10 s → press → 10 s processed
- [ ] Esc while recording discards; Esc otherwise reaches the focused app
- [ ] Failure branch: recording reaches 10 min → stopped, processed, notice "maximum length reached" — verified by a core test with instants supplied by the test (no clock port; T-042 controller `tick(at)`)
- [ ] Test that fails without the change: `crates/voicen-core recording-control tests`

## Investigation

Tools: Serena and Context7 were not connected in this session (no `mcp__serena__*` / `mcp__context7__*` tools); context came from grep and file reads over `crates/voicen-core/src`, `crates/voicen-core/tests`, `src-tauri/src`, `src-tauri/tests`, `i18n/`, `specs/001-dictation-via-api`, `docs/decisions/{dictation-session,windows-shell}.md`. No Rust was run (nothing to reproduce: the feature is absent, see evidence).

**Frame.** Observed: with `mode = toggle` a press+release records like hold (decision #63, test `toggle_mode_behaves_as_hold`); a recording has no length limit; Esc does nothing while recording. Expected (FR-03, FR-22, decision #1, spec 001 US3, data-model "Recording"): toggle press → press = one job (`Toggled`, no 0.3 s minimum); at 10 min in either mode the recording stops, is processed, and `notice.max_length` is shown; Esc while recording discards (`Cancelled`, nothing sent, indicator off, mic closed, a later hold release does nothing); Esc while idle reaches the focused app; a refused Esc claim keeps recording and emits `Warning{esc_unavailable}`.

**What exists.**
- T-042 controller `RecordingController` (sans-IO, every instant from the caller): `press` (live → `Ignored` as auto-repeat), `release` (`MIN_HOLD` for all), `tick(at)` / `next_deadline()` (message expiry only), `live_id()`, `notice()`. `Live` holds `id, ctx, started_at`; the mode is not there (`C` is opaque `PressContext`, which carries the press-time `Settings` snapshot incl. `mode`).
- T-051 session `DictationSession`: `hotkey_pressed` (returns at once while live), `hotkey_released` (the only stop path: `releasing` mutex → state lock → `release` → `stopping` hold → capture stop outside the lock → `finish` → queue), `run_timer` (ticks at `next_deadline`, holds the state lock, never takes `releasing`).
- T-006 shell `win/hotkey.rs`: one hidden window, `RegisterHotKey(HOTKEY_ID, MOD_NOREPEAT | modifiers)`, `WM_HOTKEY` → `hotkey_pressed(at)`, a 10 ms `GetAsyncKeyState` poll → `hotkey_released(at)`. Press and release are reported in both modes; the shell reads no mode (windows-shell.md rule 1) — that stays: toggle is decided in core from press/release events.
- Settings: `settings::Mode {Hold, Toggle}` (default Hold), field `recording.mode`, Recording tab in the UI. `HotkeyRegistrar::prepare(hotkey, mode)` already carries the mode (T-055).
- Hotkey grammar: at least one modifier, never `Esc` (`settings/hotkey.rs`, `hotkey.esc_reserved`), so Esc can never collide with the user's hotkey.
- Events/diag: `WarningCode::EscUnavailable` and `WarningKind::EscUnavailable` (`esc_unavailable`) exist, never emitted. `diag/observer.rs` matches `RecordingEnd` exhaustively (new variants will not compile without a mapping; good).
- i18n: `notice.max_length` is in `contracts/messages.md` (en "Maximum length reached", ru "Достигнута максимальная длительность") but **missing** from `i18n/en.json`, `i18n/ru.json` and `i18n.rs` `messages!` — T-009 adds it (parity tests are T-005's).
- Toasts: no notifier yet (T-007, TODO). The max-length notice is shown on the overlay through the controller now; its toast comes with T-007's notifier like every other notice.

**Hypotheses.**
1. *Toggle/max/Esc are simply not built* — confirmed (evidence block).
2. *A second path decides recording ends* — the risk, not a finding: today only `hotkey_released` stops a capture. Adding the max-length stop on the timer thread or Esc on the hotkey thread as separate stop code would make a second and third path (P-011). Hence the invariant: one session stop path.
3. *The class was handled before* — no `docs/failures.md` entry of class `recording-control`; T-042 and T-051 explicitly deferred these inputs to T-009 (T-042 analysis seam, decision #63/#64).
4. *Esc can be caught "only while recording" with `RegisterHotKey(VK_ESCAPE)` alone* — **not proven, likely incomplete in hold mode.** The hotkey always has ≥ 1 modifier, and during a hold the user is holding it; a registration with modifiers = 0 is, as far as I understand `RegisterHotKey`, matched against the exact modifier state, so Ctrl+Alt+(Esc) would not fire a `(0, VK_ESCAPE)` hotkey. I could not check this against Microsoft's docs in this session (no docs tool); it must be settled by a red Windows CI test (Esc pressed with the hotkey's modifiers held while recording in hold mode). The approach covers it by registering Esc under both modifier sets (none, and the hotkey's modifiers, each `MOD_NOREPEAT`).
5. *A low-level keyboard hook is needed instead* — rejected below (option C).

**Options.**

- **A (recommended) — controller + session in core, `CancelKey` port, shell registers Esc.**
  - Controller: `Live` gains `mode` (passed to `press` from the session's snapshot; the mode of the press that started the recording governs, a save mid-recording does not change it, P-013). `press` while live: hold → `Ignored` (auto-repeat, as now), toggle → a `StopTicket` with end `Toggled` (so `Press` gains a `Stop(StopTicket)` variant). `release`: toggle → `Ignored` (no `MIN_HOLD`, data-model "min hold hold mode only"). `MAX_LENGTH = 10 min` (decision #1); `next_deadline = min(message.until, started_at + MAX_LENGTH)`; `tick(at)` at `>= started_at + MAX_LENGTH` ends the recording with end `MaxLength`, shows `notice.max_length` (3 s, tray unchanged, like `notice()`) and hands out a `StopTicket` (so `tick` returns `Option<StopTicket<C>>`). `cancel(at) -> Option<RecordingId>`: live → idle, end `Cancelled`, no ticket, no message. `RecordingEnd` + `Toggled`, `MaxLength`, `Cancelled` (data-model already lists them).
  - Session: one private stop path `stop(ticket)` used by `hotkey_released`, the toggle `hotkey_pressed`, and the timer's max-length tick; each takes `releasing` before the state lock (queue order = recording order; the timer must drop the state lock and re-take it under `releasing` when the deadline is a recording's). `hotkey_pressed` no longer returns early while live: the controller decides. New input `esc_pressed(at)`: `cancel` under the lock, capture taken out and stopped outside it (NFR-02), `RecordingEnded{Cancelled}` emitted, published at once. New port `CancelKey` (platform.rs, with a fake): `set(claimed: bool)`, non-blocking (called under the lock, same rule as `Indicator`); the session calls it whenever `live_id().is_some()` differs from the last value sent (not held back by `stopping`, so Esc is released at the stop, not at the `finish`). Input `cancel_key_result(claimed: bool, at)`: `false` while the same recording is live → one `Warning{EscUnavailable}`, recording continues.
  - Diag: `RecordingEnded{Toggled|MaxLength}` → no line (the job closes it); `Cancelled` → closes the record with a new `DictationOutcome::Cancelled` (`outcome=cancelled`, INFO), spec 006 data-model row and `docs/decisions/diagnostics-log.md` updated in the same commit.
  - Shell: the hotkey thread implements `CancelKey` by posting a thread message (`WM_APP`) to itself; on it, `RegisterHotKey(ESC_ID, MOD_NOREPEAT, VK_ESCAPE)` plus `ESC_MOD_ID` with the hotkey's modifiers (from `win32_data`, not computed in the shell), or `UnregisterHotKey` for both; the result goes back as `cancel_key_result`. `WM_HOTKEY` with an Esc id → `esc_pressed(at)`. Posting keeps every register/unregister on the thread that owns the window and in queue order with `WM_HOTKEY`, whichever thread ended the recording (timer for max-length).
  - Removes the cause: every end is a controller decision, every stop one path, the claim follows `live_id`. Red → green: the core tests in `approach`; `toggle_mode_behaves_as_hold` is replaced (decision #63 ends with this task). Risk: the timer thread now runs the stop path (capture stop + conversion of up to 10 min of audio, ~19 MB at 16 kHz mono i16 after mixing) on the timer thread — the 3 s message expiry waits meanwhile (acceptable; the same Q6 "conversion on the input thread" measurement is open in dictation-session.md). Rollback: revert the commit; decision #63 behaviour returns.
- **B — shell owns the Esc claim:** the hotkey thread registers Esc after `hotkey_pressed` and polls `live_id()` on its 10 ms timer to unregister. Fewer core changes, but the shell decides "is a recording on" (P-010 second owner, windows-shell.md rule 1), the poll must also run for the whole toggle recording, and every case is Windows-CI-only. Rejected.
- **C — `WH_KEYBOARD_LL` hook while recording:** sees Esc under any modifiers and can swallow it, but the hook procedure runs on the hotkey thread, which blocks in `hotkey_pressed` for the bounded device open (up to `OPEN_BUDGET` 3 s); Windows drops a hook that exceeds `LowLevelHooksTimeout` silently. Kept only as the fallback if A's modifier-set registration proves impossible on Windows CI.

**Recommended:** A. Red first: `recording::tests::max_length_stops_at_exactly_10_min_in_both_modes_with_notice_max_length` (the failure branch of the Acceptance; instants supplied by the test, no clock port) together with the other controller tests listed in `analysis.approach`, then the session tests, then the Windows CI tests in `src-tauri/tests/hotkey.rs`.

**Split / scope.** Two seams (core controller+session, shell hotkey thread), but the behaviour is settled by spec 001 (US3, data-model "Recording", tasks T044–T046) and the core part is Linux-provable alone; the shell part is one adapter of a new port. It fits one task; if the orchestrator wants smaller units, the natural cut is core (T044/T045 + i18n + diag) then shell (T046), the shell half depending on the port. Coordinate with T-055 (ANALYSIS), which also changes `win/hotkey.rs` (re-registration on save): whichever lands second rebases on the other; the Esc ids must not reuse `HOTKEY_ID`.

**Windows-only proof (verify_exception).** `src-tauri/tests/hotkey.rs` on the Windows CI runner: Esc while recording (hold, with the hotkey's modifiers held; toggle, no modifiers) discards — no job, capture closed; Esc while idle reaches the test window (`WM_KEYDOWN VK_ESCAPE` received); after a max-length stop driven through the session, Esc is unregistered again; a refused Esc registration (Esc pre-registered by the test) gives `esc_unavailable` and the recording continues. The 10-minute stop itself is proven only in core (no 10-minute CI step); the owner's manual check: quickstart §3 step 2 (toggle 10 s, Esc in toggle and in hold, Esc in Notepad while idle).

**Open points (none blocking; defaults proposed).**
- Q1 (owner, non-blocking): Esc under the hotkey's modifiers. If the hotkey is e.g. Ctrl+Shift+X, the hold-mode claim registers Ctrl+Shift+Esc (Windows' Task Manager shortcut) while recording; Ctrl+Esc and Alt+Esc are system shortcuts too. Options: (a) claim Esc both bare and under the hotkey's modifiers while recording — the system shortcut is unavailable only during a recording, and a refused registration just gives `esc_unavailable` (recommended); (b) claim bare Esc only — in hold mode Esc works only after the user lets go of the modifiers, which ends the hold, so effectively Esc cancel works only in toggle mode; (c) hook (option C). Default (a) unless the owner says otherwise.
- Q2 (owner, non-blocking): toggle after a max-length stop. The next press starts a new recording (data-model: Idle after `MaxLength`), so a user who presses to "stop" at 10:05 starts a fresh recording; the notice is the only cue. Options: (a) as specified (recommended, no new state); (b) ignore the first press within N s after a max-length stop. Default (a).
- Release scope: decision #63 kept T-009 at P3 ("no Esc cancel in release 1"); nothing here changes that.
