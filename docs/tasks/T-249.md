## Context

Split from T-205 by the owner (decisions #350, Q5 (a)); the evidence is T-205's Investigation (hypotheses 3 and 4, option A). GitHub sets `GITHUB_TOKEN` permissions only per workflow or job, and the agent job needs write scopes, so an `actions: read` token cannot be given to one step; any token inside the session is readable by the whole session (it runs as the runner's OS user, and `curl` is not denied). Per #350: a separate `ci-read` job with job-level `permissions: actions: read`, checked out at main's commit (`github.sha`) and run on GitHub-hosted `ubuntu-latest`, runs `scripts/tw-wip-run` in contour mode for `task/<ID>` (built by T-205) and hands the agent job a result file (the `CI:` line, or red with the failed jobs and the bounded failed-step log) for the review and implement stages. No session holds a token. This replaces #259's "token in the session" path. Seams (to be confirmed by the analysis): `teamwright-agent.yml` (job body only: its header stays byte-identical to `scripts/ci/contour-heads/`), a pinned fragment under `scripts/ci/`, `scripts/ci/release-guard.sh` R3 (`permissions` outside the owned head) and its self-test, `docs/process/gates.md` (drop the main-tree workaround for contour reviews), `docs/decisions/ci-toolchain.md`, CLAUDE.md's workflow row (the `tw-wip-run` row and gates.md's lines on the reader's branch and templates are T-205's, with the reader change). Guard change (`scripts/ci/`): `checker: true`, `analysis.decides_on` required.
