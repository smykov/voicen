## Context

First Windows run of the T-001/T-015/T-016/T-039/T-047 tail (push 1201495..9fedb17): `api_pipeline::no_event_or_failure_carries_key_query_or_transcript` panicked at `crates/voicen-core/tests/api_pipeline.rs:1125` — "refused: Failed(Timeout), expected Failed(CannotReach { host: \"127.0.0.1:1\" })". The test runs every scenario under `Timeouts { connect: 2 s, api_transcription: 300 ms, .. }`; on windows-latest a refused loopback connect is answered only after SYN retries (~2.1 s, T-047 reviews), so the 300 ms total fires first. On Linux the refusal is immediate, so the local gate cannot see it. `cargo test` stopped at this binary, so the later binaries (fakes, local_download, local_download_refused, local_store, openai_client, settings_apply) have not run on Windows at all for this code — including T-047's `refused_addr()` probe and T-016's refused-port test. main is red; no deploying task in the tail can reach DEPLOYED until this is fixed.

## Acceptance

- [ ] Every voicen-core test that expects a refused connect gives the refusal time to arrive on Windows (no total/connect timeout below the Windows refusal time on that path), while the guarantees the tests pin stay bitten
- [ ] Failure branch: the Windows CI job runs `cargo test --workspace --exclude voicen` to the end with every binary green (CI evidence on the fix commit); the timeout scenarios still end `Timeout`
- [ ] Test that fails without the change: the failing Windows run above (evidence), plus an audit in the analysis of every voicen-core test that combines a refused/unroutable address with a timeout
