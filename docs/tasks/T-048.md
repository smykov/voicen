## Context

First Windows run of the T-001/T-015/T-016/T-039/T-047 tail (push 1201495..9fedb17): `api_pipeline::no_event_or_failure_carries_key_query_or_transcript` panicked at `crates/voicen-core/tests/api_pipeline.rs:1125` — "refused: Failed(Timeout), expected Failed(CannotReach { host: \"127.0.0.1:1\" })". The test runs every scenario under `Timeouts { connect: 2 s, api_transcription: 300 ms, .. }`; on windows-latest a refused loopback connect is answered only after SYN retries (~2.1 s, T-047 reviews), so the 300 ms total fires first. On Linux the refusal is immediate, so the local gate cannot see it. `cargo test` stopped at this binary, so the later binaries (fakes, local_download, local_download_refused, local_store, openai_client, settings_apply) have not run on Windows at all for this code — including T-047's `refused_addr()` probe and T-016's refused-port test. main is red; no deploying task in the tail can reach DEPLOYED until this is fixed.

## Acceptance

- [ ] Every voicen-core test that expects a refused connect gives the refusal time to arrive on Windows (no total/connect timeout below the Windows refusal time on that path), while the guarantees the tests pin stay bitten
- [ ] Failure branch: the Windows CI job runs `cargo test --workspace --exclude voicen` to the end with every binary green (CI evidence on the fix commit); the timeout scenarios still end `Timeout`
- [ ] Test that fails without the change: the failing Windows run above (evidence), plus an audit in the analysis of every voicen-core test that combines a refused/unroutable address with a timeout

## Investigation

**Tools.** I used grep and file reads. Serena does not index Rust here (decision #3). I took the reqwest 0.13.5, hyper-util 0.1.21, socket2 0.6.5 and windows-sys 0.61.2 sources from the gate's cargo cache (`.teamwright/cache/core/_usr_local_cargo_registry/src/...`), not context7, because the exact pinned source was available locally. The CI logs come from `gh run view 37204170764 --log-failed` and `gh run view 37183609259 --log`. Grep scope: `crates/voicen-core/{src,tests}` and `src-tauri/tests`. Patterns: `refused_addr()`, `refused_port`, `192.0.2`, `.invalid`, `127.0.0.1:`, `connect:`, `api_transcription:`, `download_no_data`, `took`, `elapsed()`, `END_WAIT`, `TcpStream|TcpListener`. I did not run anything on Linux: Linux refuses at once, so the defect cannot show there.

**Frame.** Observed on the Windows runner: the leak test's "refused" scenario ends `Failed(Timeout)`. Expected: `Failed(CannotReach{"127.0.0.1:1"})`. On the Linux gate it is green, because the refusal is immediate. Not a hypothesis: the CI timestamps (below) give the Windows refusal time directly. What is inferred: the *cause* of the ~2.17 s is the SYN retry after the RST. That is the T-047 reviews' explanation, and I have not verified it in Windows documentation. The fix does not depend on why it takes 2.17 s, only on the fact that it does.

**Hypotheses.**
1. *A total deadline below the refusal time decides the reason.* Confirmed. See the mechanism and timeline below.
2. *Port 1 is filtered (SYN dropped) on windows-latest, so this is a blackhole, not a refusal.* Refuted. The `refused_addr()` probe asserts `ConnectionRefused` and passed (`refused_addr_tests::*` ok), in 2.17 s, not at its 5 s cap.
3. *The same concern sits on a second path.* Confirmed: `local_download_refused` (download path, same 2 s deadlines). The openai_client refused cases have a milder form (connect 2 s races the 2.17 s refusal). See the audit.
4. *This class was fixed before.* Partly. T-047 review 1 flagged `refused_host_is_cannot_reach`'s `took < 2 s` against the ~2.1 s Windows refusal, and round 2 changed it to `< Timeouts::default().connect - 1 s`. T-047 review 2 then audited the other refused cases and judged the leak test's refused scenario robust ("no timing assertion ... a connect timeout gives CannotReach too"). That audit missed `ms.api_transcription = 300 ms`: a *total* deadline, which gives Timeout, not CannotReach. The fact was fixed at one site, and the audit of the siblings modelled only the connect timeout.

**Mechanism (reqwest 0.13.5 source).**
- `OpenAiCompatibleEngine::send` (engine/openai.rs:120-136): `Client::builder().connect_timeout(connect)`, then `.timeout(api_transcription)` per request.
- The blocking `execute_request` (blocking/client.rs:1493-1527) takes the total as `wait::timeout(f, timeout)`. The deadline is `Instant::now() + d` at the call (blocking/wait.rs:15-20), on the caller thread, *before* the request reaches the runtime thread where the connector's `connect_timeout` timer starts (connect.rs:144-150). On expiry: `Err(Waited::TimedOut(e)) => crate::error::request(e)`. The source is `reqwest::error::TimedOut`. No `hyper_util::client::legacy::Error` is in the chain, and no `io::Error`.
- `Error::is_connect` (error.rs:158-172) is true only through `hyper_util::client::legacy::Error::is_connect`. So for a total expiry: `connect = false`, `timeout = true`, `io = None`.
- `failure::classify` (failure.rs:164-190) → `Send{timeout: true}` → `Timeout`. `DownloadFailure::from_transport` (download.rs:105-130) → neither dns, connect nor io unreachable → `DownloadInterrupted`.
- A connect-timeout expiry, and a refusal, come through the connector: `is_connect = true` → `CannotReach{host}` / `SourceUnreachable{host}` (the `classify_table` rows "refused 127.0.0.1:9" and "192.0.2.1 connect_timeout", failure.rs:289-294).
- So with a refused address the expected reason holds only if the refusal, or the connect timeout, comes before every whole-request deadline. In the download client the blocking `ClientBuilder::timeout` (download.rs:404-406, `no_data`) is the same `wait::timeout` total over `send()`; the blocking handle keeps it (blocking/client.rs:1419-1420) and it is not passed to the inner client.

**A Windows knob?** Two exist, and neither belongs in a test:
- System-wide: the TCP SYN-retransmission setting (netsh/registry). It is admin-only and machine-global, and it changes the CI runner, not the product. A test must not change it, and it would make a green CI depend on runner state. I have not checked its exact name or minimum value in Windows docs.
- Per socket: `TCP_MAXRT` / `TCP_MAXRTMS` (windows-sys 0.61.2 defines `TCP_MAXRT = 5`, `TCP_MAXRTMS = 14`). It would have to be set by the product's connector. reqwest 0.13.5, hyper-util 0.1.21 and socket2 0.6.5 neither set nor expose it (grep `MAXRT`: no match). reqwest's `tcp_user_timeout` is Linux/Android/Fuchsia only (async_impl/client.rs:179, :1806). It would change product behaviour on real networks.

Recommendation: tests budget for the refusal time. For users, a refused local server on Windows takes ~2 s before "cannot reach", which is inside FR-24's 5 s connect limit. If the owner wants a faster failure there, that is a separate product question (an OQ), not this fix.

**Approach options.**
- **A (recommended): one budget in `tests/common`.**
  - `pub const REFUSAL_BUDGET: Duration = Duration::from_secs(5)`. The `refused_addr()` probe uses it as its timeout and also asserts `probe_elapsed < REFUSAL_BUDGET / 2`. That makes the environment assumption explicit and checked: a platform whose refusal grows past 2.5 s fails loudly at the probe, naming the budget, instead of a later misclassification.
  - `pub fn refused_timeouts() -> Timeouts` = connect `REFUSAL_BUDGET`, `api_transcription`/`local_server`/`post_processing`/`download_no_data` = `2 * REFUSAL_BUDGET`; `builtin` stays at the default.
  - Callers: the leak test's "refused" scenario gets its own Timeouts (add a Timeouts column to the scenario tuple, or run the refused case with `refused_timeouts()`). `ms` stays for the slow-server "timeout" scenario, which must still end `Timeout`. openai_client's two refused cases use `refused_timeouts()` via a `req_refused()`. `local_download_refused` builds its fixture with `refused_timeouts()`; `common::download` needs a `fixture_with_timeouts` or equivalent, because `timeouts(no_data)` hard-codes connect 2 s.
  - Why it removes the cause: every deadline is above 2 × the measured refusal time, so the refusal decides the reason on both OSes. Side gain: on Windows #3/#4 and #1 now really exercise a refusal (connect 5 s > 2.17 s), so the T-047 mutation bites there too.
  - Cost: ~2.2 s more wall time per refused case on Windows; none on Linux.
  - Risk: low (tests only). Rollback: revert the commit.
- **B: per-OS constants** (`cfg!(windows)` → 5 s, else 300 ms). Keeps Linux fast, but adds two truths for one fact and makes the Linux gate prove nothing about the Windows values. Rejected under P-010.
- **C: a measured budget** (`refused_addr()` returns the probe's elapsed time; tests derive their deadlines from it). Adaptive, but deadlines then depend on runner load, which hurts reproducibility. Rejected.

**Red / green.**
- No test can go red on Linux for #1/#2: Linux refuses at once, and the gate container cannot delay an RST (no NET_ADMIN). The red evidence is the failing Windows run 37204170764 (#1). #2 is predicted from source, not observed.
- The one Linux-checkable piece is the probe's `elapsed < REFUSAL_BUDGET / 2` assertion, which is green on Linux and pins the budget's assumption.
- The Linux gate shows only that the refused cases still expect `CannotReach`/`SourceUnreachable` and the timeout cases still expect `Timeout`/`DownloadInterrupted`. Re-run the T-047 mutation and expect the same 4 red.
- **The fix is proven only by a Windows CI run on the fix commit** in which `cargo test --workspace --exclude voicen` runs to the end with every binary green: api_pipeline, local_download_refused, openai_client and the binaries that never ran (fakes, local_download, local_store, settings_apply). Recommended in the same change: `cargo test --workspace --exclude voicen --no-fail-fast` at `.github/workflows/ci.yml:60`, so one red binary no longer hides the others. That is why 6 binaries have no Windows evidence today. The step still fails at the end.

**Recurrence.** F-004 (`test-port-race`) is a different class. Its cause is the port's ownership, not timing. The Windows ~2 s refusal fact is not in `docs/failures.md`. It first appeared within the last day as a T-047 review-1 out-of-diff note and was fixed at one site in T-047 round 2 (`took < 2 s` → `< 4 s`). That round's audit then judged the sibling safe on a model that left out the whole-request deadline. This is the second appearance of the fact. It is the first CI failure of the class, and no earlier fix of this class failed again: the first appearance was caught in review and fixed correctly at its own site. So I recommend **no separate rca**. T-048 already does the class-wide audit and routes every refused case through one seam. Add instead:
- `docs/failures.md` F-005, class `windows-refused-connect-timing` (count 1, tier T1 plus the probe's budget assertion): "Windows CI red at 9fedb17. The api_pipeline leak test's refused scenario ended Timeout. A refused loopback connect takes ~2.17 s on windows-latest (immediate on Linux), and the test's 300 ms total fired first. - An area invariant (new `docs/decisions/core-tests.md`, or wherever the orchestrator keeps core test rules), with defect T-048 and T-047 r1. What breaks if violated: the Linux gate is green while Windows CI misclassifies, and the refused path is tested only on Linux.

A third appearance after this fix would warrant an rca. So would a refused-case deadline that slips back under the budget.
