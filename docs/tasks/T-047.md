## Context

Found by the T-016 review round 1 (#1) and its test fix (027aa47): a `refused_port()` helper that binds `127.0.0.1:0`, reads the port and releases it, while sibling tests in the same binary bind `127.0.0.1:0` in parallel (wiremock and raw listeners), can hand the "refused" port to another test's server — the refused request then succeeds against it, and that server counts an extra request. T-016 fixed its own case by moving the refused-port test into its own test binary (cargo runs binaries one after another). The same helper exists in `crates/voicen-core/tests/openai_client.rs:202` and `tests/api_pipeline.rs:230`, used by `refused_loopback_port_is_cannot_reach_host_port`, the case around `openai_client.rs:659` and `refused_host_is_cannot_reach`. A flaky `make check` blocks every task's gate.

## Acceptance

- [ ] No test that expects a refused connection shares a process with tests that bind ephemeral ports (or every port-binding test in that binary is serialized by one lock), in every voicen-core test binary
- [ ] Failure branch: each refused-port test still fails if the client stops classifying a refused connect as `CannotReach{host:port}` (mutation shown in the review)
- [ ] Test that fails without the change: a loop of at least 50 runs of the affected binaries with zero failures (evidence in the task), and a reproduction of the race before the fix if one can be made deterministic
