## Context

Found by the T-016 review round 1 (#1) and its test fix (027aa47): a `refused_port()` helper that binds `127.0.0.1:0`, reads the port and releases it, while sibling tests in the same binary bind `127.0.0.1:0` in parallel (wiremock and raw listeners), can hand the "refused" port to another test's server — the refused request then succeeds against it, and that server counts an extra request. T-016 fixed its own case by moving the refused-port test into its own test binary (cargo runs binaries one after another). The same helper exists in `crates/voicen-core/tests/openai_client.rs:202` and `tests/api_pipeline.rs:230`, used by `refused_loopback_port_is_cannot_reach_host_port`, the case around `openai_client.rs:659` and `refused_host_is_cannot_reach`. A flaky `make check` blocks every task's gate.

## Acceptance

- [ ] No voicen-core test connects to a port it has released: every address a test expects to be refused comes from one shared helper (`common::refused_addr()`, a fixed port below the ephemeral range, probed as refused at each use — decision #53); `local_download_refused` keeps its own binary for its refused-then-serve case
- [ ] Failure branch: each refused-port test still fails if the client stops classifying a refused connect as `CannotReach{host:port}` (mutation shown in the review)
- [ ] Test that fails without the change: a loop of at least 50 runs of the affected binaries with zero failures (evidence in the task), and a reproduction of the race before the fix if one can be made deterministic

## Investigation

**Tools.** Serena does not index Rust here (decision #3), so I used grep. Patterns: `127.0.0.1:0`, `TcpListener::bind`, `MockServer`, `refused`, `local_addr`. Scope: `crates/voicen-core/{src,tests}` and `src-tauri/{src,tests}`, plus the wiremock-0.6.5 source in the cargo registry cache. Context7 was not needed: I relied on no package API. Whoever writes option B must look up the socket2 0.6.5 `Socket::new/bind/listen` API.

**Frame.** Each refused-port test expects `CannotReach{127.0.0.1:<port>}`. That expectation only holds while nothing listens on the port. The helper gives no such guarantee: the port is released before the client connects. The client builds a reqwest blocking client first, so the window lasts milliseconds. During it, sibling tests in the same process bind `127.0.0.1:0`. Cargo runs test binaries one after another, so only binds inside the same binary matter. The gate container also has its own network namespace, so processes outside it cannot take the port.

**Inventory: helpers that bind and release.**
- `tests/openai_client.rs:202`, used at `:472` and `:659`.
- `tests/api_pipeline.rs:230`, used at `:736` and `:1012`.
- `tests/local_download_refused.rs:27`. This one is fixed by isolation (027aa47): it is alone in its binary.

Who else binds `127.0.0.1:0` in those processes:
- wiremock pooled servers, in every `server_with` test of both binaries (`builder.rs:107`; the pool reuses servers, so most binds happen while the tests start together).
- `partial_body_server` (`openai_client.rs:238`).
- `common::Server::start` (`common/mod.rs:153`), in `local_download` only.

There are no binds in `src-tauri/tests` or in the core lib tests. Windows CI also runs these binaries (`cargo test --workspace --exclude voicen`, ci.yml:60), so the race exists there too. I have not measured how Windows allocates ephemeral ports.

**Hypotheses.**
1. *Port reissued to a sibling server.* **Confirmed** as the mechanism, by code and by the kernel measurement above. The test fails with `ServerError{404}` or `UnexpectedResponse`, and the sibling fails too: a one-shot `partial_body_server` gets `CannotReach`, a wiremock count gets one too many.
2. *TCP self-connect.* The client's own source port equals the released port. Possible in principle, since a released port is free for `connect()` as well. In 3000 connects to a released port in the default range I saw 0 self-connects, so it is a minor second path of the same invariant.
3. *Second path of the same concern.* Yes: three copies of the helper. T-016 fixed one, by isolation.
4. *Class fixed before.* Yes, T-016 review 1 #1 (027aa47). That is the first instance; this task is the same class found at the same time in other binaries, not a recurrence after a fix. `docs/failures.md` has no `test-port-race` entry (F-001…F-003 only).

**Reproduction attempts.**
- Baseline: 10+10 runs green with the default range. 40+40 runs green with the range narrowed to 512 ports.
- With 64 and 128 ports, `openai_client` failed 9/20 and 14/40. Most of those failures were range exhaustion (`expect("bind 127.0.0.1:0")` at :203/:238, wiremock `builder.rs:107`), so the runs are confounded. One run (64 ports) showed the crossed request itself: `stall_mid_body…` got `CannotReach{127.0.0.1:40053}` instead of `UnexpectedResponse`. Its one-shot `partial_body_server` accept had been used up by another connection. That run also had exhaustion failures, so it supports the mechanism but does not prove it alone.
- A port-thief process with a 4-port range: confounded by TCP self-connect (`UnexpectedResponse` on the test's own port).

Conclusion: the window is too short to reproduce the race end to end and deterministically on unchanged binaries. The deterministic red test is therefore the structural one in `approach`. The current per-run flake rate is low, roughly the number of sibling binds inside the window times 1.4e-4. It is still a P-005 flake in the gate.

**Options. Std-only checks requested by the orchestrator. All measured in voicen-rust:1.99 with python3 over the same kernel calls, uid 1000, in both the default range and a range of 8 ports.**

| Option | Refused? | Can a sibling's bind(0) or connect() get it? | Cost and risk |
|---|---|---|---|
| A. `127.0.0.1:1`, fixed, below the ephemeral range | 3000/3000 ECONNREFUSED | No: outside the range, so autobind never picks it. 0 self-connects. | std only. Assumes nothing listens on TCP 1. That holds in the gate's netns, and the per-use probe checks it. Unverified on windows-latest, so the first Windows CI run proves it. It cannot serve the retry half of `local_download_refused`. |
| B. socket2 socket, bound, never `listen()`, held for the test's duration (round-2 reviewer) | 3000/3000 ECONNREFUSED | No: 100000 sibling bind(0) calls with and without SO_REUSEADDR, 0 hits. Linux autobind treats a non-listening REUSEADDR owner as a conflict, and connect() skips ports created by bind, so 0 self-connects. Only an explicit `bind(port)` with SO_REUSEADDR could take it. No test does that outside `local_download_refused`. | Calling `listen()` later on the same socket turns it into the server (measured: then CONNECTED). That would close the `start_on` re-bind gap of T-016 as well. Needs socket2 as a direct dev-dependency. That is outside the decision #9 dev list (wiremock, tokio), so the owner decides. It adds no crate (socket2 0.6.5 is already in the lock via reqwest/hyper-util/tokio/wiremock), and cargo-about ignores dev dependencies (`docs/decisions/licenses.md`), so THIRD-PARTY-NOTICES does not change. Windows: a bound socket that is not listening answers a SYN with RST, which gives WSAECONNREFUSED after Windows' SYN retries, not a timeout. That is the same path the current released-port tests take there. Not verified on a runner by me. |
| C. Own binary per refused case (T-016) | yes | No sibling binds in the same process. | Std only and consistent with T-016. But: four binaries (or two, if each leak test's refused case is split out of its leak test, which weakens the "every path in one test" leak tests). Extra link time in the gate. It depends on cargo running binaries one after another, which cargo-nextest does not. "One test per file" is an unchecked rule. |
| D. Shared lock in tests/common | yes | Only if every bind goes through the lock | Every `MockServer::start` and raw bind would need it. Nothing checks that, and a new test brings the race back. Rejected. |
| E. Std: the local port of a connected `TcpStream` (bound, no listener) | **1 self-connect in 3000** in both ranges | The port is reserved, but connect() may reuse it as a source port | Rejected. |
| F. Std `TcpListener` kept bound | not refused (it listens, so the connect succeeds and hangs) | — | Std has no bind without listen. Rejected. |

Recommendation: A (std-only, smallest diff, call sites stay in place). If the owner prefers no assumption about the environment, and wants one mechanism for both the refused-only and the refused-then-serve cases, choose B and record the dependency consent in `docs/decisions.md`.

**Process rule, for the owner or orchestrator to decide.** No rca: the two instances were found together, not after a fix. Suggested:
- A `docs/failures.md` entry (class `test-port-race`, T-016 #1 and T-047).
- An invariant in a core-tests area decision: "a refused address never comes from a released port; use `common::refused_addr()`".
- Optionally a T3 guard in `make check`: a grep over `crates/*/tests` that refuses `TcpListener::bind("127.0.0.1:0")` outside `tests/common`. That would also stop a fourth copy of the helper.

T-016's "a refused-port test lives alone in its binary" stays valid for `local_download_refused`, but it should not become the general rule. Option C is costly and nothing checks it.
