## Context

T-060 carried T-076 review 3 Low #2: when post-processing fails with an HTTP error, the dictation line does not say which status the provider returned, so the owner's log cannot tell a 401 from a 429 or a 5xx. OQ-67 asked whether to add it to the closed log grammar; the owner chose (a) (decisions #205): `pp_http_status=` on the dictation line, a closed integer, no body text (FR-20, NFR-04: never transcript text, audio or keys).

## Acceptance

- [ ] A post-processing attempt that ended with an HTTP status writes `pp_http_status=<integer>` on its dictation line, next to the existing post-processing fields
- [ ] The value is the status code only: no reason phrase, no response body, no header (closed grammar, `docs/decisions/diagnostics-log.md` updated with the field and its rule)
- [ ] Failure branch: post-processing that failed without an HTTP response (timeout, connection refused) or did not run writes no `pp_http_status=` field, verified by a log-format test
- [ ] Test that fails without the change: a diag format test with a scripted 429 from post-processing

## Investigation

Tools: Serena loaded; code read with grep and file reads (rg over `crates/` and `src-tauri/`). No library API is involved, so no docs lookup.

- **Where the line is built:** `diag::format::write_dictation` (core) writes `pp=`, `pp_reason=` (only on a skip), and `pp_ms=` inside the timings loop, from `DictationLine.post_processing: Option<PostProcessTrace>`. `LogObserver` (`diag/observer.rs`) copies `JobFinished.post_processing` into the record. src-tauri never builds or touches `PostProcessTrace`, `SkipKind` or `DictationLine`, so the shell does not change.
- **Where the status goes missing:** for every non-2xx, `engine/http.rs` returns `TransportError::Status(u16)`. Then `failure::classify` maps 401/403 to `InvalidApiKey` (the status is dropped there, a mapping shared with transcription) and every other status to `ServerError{status}`. `SkipReason::from_failure` maps that to `SkipReason::Http{status}`. A cross-origin 3xx is also `Http` (T-186). `SkipReason::kind()` then drops the status into the unit `SkipKind::Http`, which T-076 made status-free on purpose (`docs/decisions/diagnostics-log.md`, T-076 bullet: "no host and no status").
- **No status by construction:** timeout (`SkipReason::Timeout`), refused or DNS (`Unreachable{host}`), `NotConfigured`, `InvalidResponse` (a 2xx with a bad body, or a body read error), `NotRun`/off, and a job that never reached the stage (no trace).
- **Precedent:** the transcription `http_status=` is written only on `failure=server_error`. The 401/403 case is already `invalid_api_key`, with no status (`pipeline.rs` `release`). Putting `pp_http_status` exactly on `pp_reason=http` follows the same pattern.
- **Grammar pins:** `tests/diag_support/mod.rs` `check_closed`: the key/value table (add `("dictation","pp_http_status")`, a u16) and the presence rules next to the T-076 `pp_reason`/`pp_ms` rules. `PP_REASONS` does not change.
- **Test for the scripted 429:** `tests/diag_pipeline.rs::post_processing_outcome_is_logged_without_prompt_reply_host_or_key`. Its wiremock chat servers come from `chat_with(ResponseTemplate::new(..))` (`tests/common/mock_http.rs`), and the "skipped http 500" row is the model for a 429 row. Its redaction checks then also cover the new row. The format-level twin is `tests/diag_format.rs::dictation_line_carries_pp_keys_per_post_processing_result` and its `all_skip_kinds`/`all_pp_results` tables, which also need `Http{status}` for an exhaustive enumeration, including `u16::MAX` as for `http_status`.
- **Recurrence:** `docs/failures.md` has no `diag-grammar` or `diagnostics-log` entry. The closest is the guard-model row, which is unrelated. No task other than T-190 has `class: diag-grammar`. Recurrence: none.
- **Size:** small. One seam: the closed post-processing trace in voicen-core (`SkipKind` → `format.rs`). All of it is Linux-testable, and the shell is untouched.

**Open point for the owner (scope; #205 does not settle it):** Acceptance 1 says "an attempt that ended with an HTTP status". Read literally, that also covers 401/403 (`pp_reason=invalid_key`) and 2xx responses (`applied`, `invalid_response`). The recommendation above writes the key only on `pp_reason=http`, as the transcription `http_status=` precedent does. Logging 401 apart from 403 would also need `classify`/`SkipReason::InvalidKey` to keep the status, a second seam shared with transcription. If the owner wants a wider set, it becomes an OQ row before IN_PROGRESS.
