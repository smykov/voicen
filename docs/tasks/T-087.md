## Context

Split out of the T-086 audit (decision #124). `scripts/ci/telegram-guard.sh` makes sure a step that reads the Telegram secrets runs only on a push to `main` or a `v*` tag. It decides on its own model of YAML and of GitHub expressions, and it leaks.

Probe T1: a step with no `if:` whose `run: |` holds the line `# ${{ secrets.TELEGRAM_BOT_TOKEN }}`. The guard exits 0 because it drops that line as a comment. GitHub expands `${{ }}` in `run:` before the shell starts, and release-guard R4 allows this token anywhere. The proposal is that the raw token `secrets.TELEGRAM_` (any case, comments included) may occur only inside one owned step literal, compared byte for byte the way R9 does it. That rule lives either in `telegram-guard.sh` or as R10 of `release-guard.sh`; the analysis decides which.

## Acceptance

- [ ] The Telegram send step(s) are byte-identical to an owned copy. The raw token `secrets.TELEGRAM_` occurs nowhere else in `.github/workflows`, comments included. The guard keeps no YAML or expression reader, and its `decides_on` is named.
- [ ] Failure branch: probe T1 is refused, and so are a second, unpinned step reading the token and the owned step with its `if:` changed. Each fixture is red against the old guard.
- [ ] `docs/decisions/ci-toolchain.md` (the guard table from T-086) lists the guard with its `decides_on`. `make check` is green.

## Investigation

Investigator, 2026-10-11. Serena was not used: no `mcp__serena__*` or `mcp__context7__*` tools were available in this session. The guards were read whole with `cat`/`sed`, and the references were found with `grep -rn` over the repo (excluding `.git` and `node_modules`). Probes ran on copies only, under `/root/.claude/jobs/97682091/tmp/t087`. `bin/mk.py` builds the probe dirs, `bin/move.py` writes the comment-moved copy `ci-moved.yml`, and `bin/r10.sh` is a throwaway awk prototype of R10. The claim that GitHub expands `${{ }}` in `run:` before the shell starts is taken from T-086 §2 and was not re-checked against the GitHub docs here. The developer should cite the docs page (expressions in `run`, and the context-availability table) when writing the guard header.

### 1. Frame

- **Expected (T-070, decisions #93):** a step that GitHub hands the Telegram secrets to runs only on a push to `main` or a `v*` tag, after every earlier step succeeded.
- **Observed:** `telegram-guard.sh` and `release-guard.sh` both exit 0 on workflows where a step with no `if:`, or with a weaker `if:` than the reviewed one, gets the token.
- **Where it reproduces:** on the host, in copies of `.github/workflows`, with no CI needed.

### 2. Hypotheses and evidence

Each probe is a copy of `.github/workflows` with one edit. Set `p/` is the current `ci.yml`. Set `q/` is the same with the T-026 comment block moved (see §4). Results are identical in both sets.

| Probe | Edit | old `telegram-guard.sh ci.yml` | `release-guard.sh <dir>` | prototype R10 |
|---|---|---|---|---|
| T0 | none (real) | 0 | 0 | ok (q/) |
| T1 | step with no `if:`, `run: \|` holding `# ${{ secrets.TELEGRAM_BOT_TOKEN }}` | **0** | **0** | refused (token beyond the literal + literal differs) |
| T2 | second step, `if:` = push && (main \|\| v*), `env: T: ${{ secrets.TELEGRAM_BOT_TOKEN }}` | **0** (counts "2 step(s)") | **0** | refused |
| T3 | owned send step, `&& steps.telegram-installer.outputs.send == 'true'` dropped from its `if:` | **0** | **0** | refused at the `if:` line |
| T4 | `other.yml` (the real header) with a job whose step reads the token, no `if:` | **0** on `ci.yml`; exit 1 only if `other.yml` is passed by hand, which the gate never does | **0** | refused at `other.yml:32` |

- **H1, the comment skip drops a line that GitHub evaluates. Confirmed (T1).** The awk main rule `line ~ /^[ \t]*(#.*)?$/ { next }` in `telegram-guard.sh` skips every line whose first non-blank is `#`, even inside a block scalar. GitHub still reads that line as `run:` text.
- **H2, the expression parser accepts shapes that are not the reviewed step. Confirmed (T2, T3).** `judge()` asks only for two top-level `&&` operands and no status function, so a second step with that `if:` passes. So does the send step with another operand changed.
- **H3, a second path: another workflow file. Confirmed (T4).** `telegram-guard.sh` takes one file. `telegram-guard.test.sh` passes only `real=.github/workflows/ci.yml`, and the Makefile target runs only that test. `release-guard.sh` reads the whole dir, but its R4 accepts `secrets.TELEGRAM_BOT_TOKEN` / `_CHAT_ID` anywhere.
- **H4, this class was fixed before. Yes, by design rather than by patch.** The class is `guard-model` (F-003: T-035…T-038; F-015: T-026, T-085). P-020 (decisions #120) is the rule, and T-086 (decisions #124) assigned this guard to T-087. `git log -- scripts/ci/telegram-guard.sh scripts/ci/telegram-guard.test.sh` shows two commits, fb2dba8 and 5c4f453 (T-070 validation 1, M6). No later patch exists and no leak was seen in CI. T-070 review 5's probes (job/workflow `env:`, `secrets['…']`, `if: >-`) were refused, and none of them put the token on a `#` line or in a second file.
- **H5, other secret spellings or YAML tricks reach the secret without the raw text `secrets.TELEGRAM_`. Refuted, given release-guard's other rules.** R4 refuses every other `secrets` occurrence (`secrets['…']`, `toJSON(secrets)`, `secrets: inherit`, other case). R6 refuses the escapes that could spell the token, and R8 refuses YAML tags. A YAML anchor or alias of the send step would need an anchor inside the literal, which is a byte difference. Aliasing a parent node (a whole `steps:` list) copies the step together with its own `if:`, so the invariant still holds.

### 3. Root cause

`telegram-guard.sh` passes when its own reading of YAML (step tracker, comment skip, scalar reader) and of GitHub expressions finds no violation, and it reads only `ci.yml`. So a token line it reads as a comment, a step shape it does not model, or a second workflow file passes. Meanwhile release-guard R4 allows these two names anywhere. This mechanism explains all four probes. Nothing contradicts it: the old guard's 24 cases still pass, because they are shapes it models.

### 4. Where the rule belongs: R10 of `release-guard.sh`, not `telegram-guard.sh`

1. **The token premise lives in release-guard.** P-020 accepts a raw token only if the consuming tool cannot spell it another way. For `secrets.TELEGRAM_` that holds only through R4, R6 and R8. A standalone guard would either rest on another guard's rules, which its own fixtures could not show, or have to duplicate them (P-010). Example: `"${{ secr\x65ts.TELEGRAM_BOT_TOKEN }}"` passes a standalone token rule and is refused only by R6.
2. **Scope.** release-guard already reads every regular file in the dir, comments included, so T4 is closed without new plumbing.
3. **Mechanism already reviewed.** R9 (T-084) is the same shape: a raw token, a count, and an owned copy compared from the token's line. It also has the same terminator trick (the next step's first line ends the literal, so no key can be appended). R10 reuses `count()`, the owned-copy loader and the listing format.
4. **Cost is known.** All 134 release-guard fixtures already contain the non-owned Telegram step `if: github.ref == 'refs/heads/main'` (grep). With R10, the 131 v-* fixtures gain an R10 line but stay exit 1, because `run()` matches some output line (as for R9, T-084 §5). Only `ok-release`, `ok-lookalikes` and `ok-tag-lookalikes` need the owned copy. `owned_guard` must also copy the new owned file, or the R7 header cases exit 3.

The cost of choosing R10 is a broader guard: release-guard's header and ok line then cover "the only secret reader is the owned send step" as well as the write token. That is accepted, because R4 already speaks about secrets.

**Proposed owned copy** `scripts/ci/telegram-send-step.yml`. The name is a suggestion; it would sit next to `release-upload.yml`, and the pair is edited together. It is the real lines from `      - name: Send the installer to Telegram (main and v* tags only)` through `        run: bash scripts/ci/telegram-send.sh "$INSTALLER" "$CAPTION"`, followed by `      - name: SHA-256 of the installer`. Today the 9-line T-026 comment block (`# T-026 (decisions #102, #103): …`) sits between the send step and that line, and a comment does not end a YAML step. The developer moves the block right after `      - name: SHA-256 of the installer` (simulated in `ci-moved.yml`; release-guard R1–R9 exit 0 on it). The moved comment must not contain `gh`, `permissions`, `secrets`, `vars`, `!!`, `upload-artifact` or `secrets.telegram_`, and today it contains none of them.

**R10 as prototyped** (`bin/r10.sh`):
- Count `secrets.telegram_` per lower-cased line with `index()`, comments included, across files in glob order and then line order.
- The total must equal the owned copy's count, which is 2 and is computed from the copy, not hard-coded.
- The lines from (first token line − the copy's first-token offset) on must equal the copy byte for byte.
- What is listed: the line where the count first exceeds the copy's count; the first differing line; or, with no token, the first file's `jobs:` line (as R9 does).
- Cannot run (exit 3): the copy is missing, empty, holds no token, or does not start with the send step's name line.
- Zero tokens is refused (`v-telegram-none`), so deleting the send needs an edit of the owned copy. This matches #93, which made the send part of the build. If the owner wants deletion to be free, that is a one-line change, but it should be decided rather than assumed.

**Not caught (deliberate only; name it in the header, as for R9):**
- The owned literal moved, with the real step deleted, into a place that is not that step. Examples: a `run: |` block scalar of a job whose keys are indented 3 columns, or a step `name: |`.
- Whether GitHub then expands the secret depends on that key's context availability (check the docs). The send then no longer happens on `main`, and the owner sees no installer.
- `telegram-send.sh` itself writing the token to `GITHUB_ENV` or a file. That is covered by `telegram-send.test.sh`, not by this guard.

### 5. Options

- **A (recommended): R10 in `release-guard.sh`, telegram-guard retired.**
  - Removes the cause, because no reader is left: the pass depends only on a byte comparison and a raw token count.
  - Red first, against today's guard: `v-telegram-t1`, `-second-step`, `-if-changed`, `-second-file`, `-m6`, `-key-appended` (`continue-on-error: true` after `run:`) and `-none`. Each is `ok-release` with the owned step plus one edit, each exits 0 today and must exit 1 naming R10 at its line. Add the real-dir mutations M6 and event_name-dropped (ported from `telegram-guard.test.sh`), plus an `expect` that the owned copy equals the real `ci.yml` lines.
  - Risk: R10's alignment arithmetic, and fixture churn in three ok-* dirs.
  - Rollback: revert the commit. telegram-guard comes back with it.
- **B: rewrite `telegram-guard.sh` dir-wide with the same literal and token.** Release-guard's fixtures stay untouched, but the token premise rests on R4/R6/R8 of another guard (see §4 point 1), and the owned-copy loader is duplicated. Not recommended.
- **C: drop the comment skip in `telegram-guard.sh`.** This is a symptom patch that keeps the YAML and expression readers. It fails P-020, and the reviewer would return `REJECT_RECURRENCE`. Rejected.

### 6. Size

**Small: one seam** (`release-guard.sh` plus its owned copy and test). The behaviour is settled by #93 and #124, and no spec is needed. The diff also touches `.github/workflows/ci.yml` (the comment move), the Makefile, `CLAUDE.md` and docs. Because the diff is outside `docs/**`, P-016 requires a green `wip/T-087` run. The step's text does not change, so no Windows behaviour changes. One owner-visible choice: zero tokens is refused (§4).
