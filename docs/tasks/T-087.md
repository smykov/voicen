## Context

Split out of the T-086 audit (decision #124). `scripts/ci/telegram-guard.sh` makes sure a step that reads the Telegram secrets runs only on a push to `main` or a `v*` tag. It decides on its own model of YAML and of GitHub expressions, and it leaks.

Probe T1: a step with no `if:` whose `run: |` holds the line `# ${{ secrets.TELEGRAM_BOT_TOKEN }}`. The guard exits 0 because it drops that line as a comment. GitHub expands `${{ }}` in `run:` before the shell starts, and release-guard R4 allows this token anywhere. The proposal is that the raw token `secrets.TELEGRAM_` (any case, comments included) may occur only inside one owned step literal, compared byte for byte the way R9 does it. That rule lives either in `telegram-guard.sh` or as R10 of `release-guard.sh`; the analysis decides which.

## Acceptance

- [ ] The Telegram send step(s) are byte-identical to an owned copy. The raw token `secrets.TELEGRAM_` occurs nowhere else in `.github/workflows`, comments included. The guard keeps no YAML or expression reader, and its `decides_on` is named.
- [ ] Failure branch: probe T1 is refused, and so are a second, unpinned step reading the token and the owned step with its `if:` changed. Each fixture is red against the old guard.
- [ ] `docs/decisions/ci-toolchain.md` (the guard table from T-086) lists the guard with its `decides_on`. `make check` is green.
