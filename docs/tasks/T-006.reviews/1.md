What I verified by reading, with no finding:
- **Bounded calls under the session lock.** `CpalSource::start` waits at most `OPEN_BUDGET` on a mic-open thread. A late send fails and drops the stream on the opener. In the narrow window between `Timeout` and the receiver drop, the buffered stream is dropped with the receiver, which is still closed at once. Its join cannot deadlock because the data callback takes only `CaptureSink`'s own lock, and `stop` runs outside the session lock (`dictation.rs:345-349`). `capture_start_window` sends no message: GetForegroundWindow, GetAncestor, GetWindowThreadProcessId, then process/token queries. `ShellIndicator` only forwards to `TrayPart::set_tray` (store + post).
- **Hotkey thread.** It stamps on arrival, sends the mask before `hotkey_pressed`, and polls with a 10 ms `WM_TIMER` over `win32_data::released`. It holds no lock of its own. `ready` is sent before the first session call, so `start` never waits on a session input. Drop posts WM_QUIT and joins, and the thread unregisters, kills the timer and destroys its window on itself.
- **Clipboard.** It registers the formats before opening and closes the clipboard by guard on every path. A `GlobalAlloc` block is freed only when `SetClipboardData` refuses it, and the exclusion formats are written before the text. The `unsafe` blocks are sound as written: lock/unlock pairing, and the size equals `size_of_val(data)`.
- **Paste.** Root owner + pid comparison, the u64-aligned `TOKEN_MANDATORY_LABEL` buffer, null checks on the SID sub-authority pointers, the RAII `CloseHandle`, unknown = elevated through `win32_data::target_elevated`, and `PasteError` when `SendInput` inserts fewer than 4 events.
- **`run()` and credentials.** `release_parts` makes one `release_credentials()` Arc, clones it into `load_settings` and returns the same Arc. `run()` hands it to `release_ports` → `DictationPorts.credentials`. That is the SettingsService's own instance (lib.rs `release_parts`, `run`). Only a primary reaches `start_dictation` (after `assemble`, before `app.run`), and the handle lives in the run closure.
- **`request_with`.** It goes through `post` → the one opener queue → the same `catch_unwind` arm and the same `settings_window_failed` line and receipt. Its test asserts no `os_code`, `FailedToReceiveMessage`, and that the next request runs.
- **No OS text or transcript in logs or errors.** `capture_error` uses fixed literals and its test plants a canary. Warning lines carry kind plus Win32 code only. The `io::Error` texts in `start_dictation` and `HotkeyThread` are fixed and never logged (`raw_os_error()` only). `dictation_e2e` asserts that the transcript canary is absent from the log.
