What the brief asked to check:

- **The clipboard retry and bounded-error tests really exercise a held clipboard.** Both tests now assert a precondition before they write: `try_open_clipboard().is_none()` (clipboard.rs:79, :124). This is `OpenClipboard(None)` on the test thread. `WinClipboard` makes the same call (`OpenClipboard(None)`, src/win/clipboard.rs:64), and the tests call the adapter on that same thread. So the precondition proves that the adapter's own open is refused, on the same thread, at the moment of the write.
  - Neither test can pass on a hold that blocks nobody.
  - If a window-owned hold also fails to refuse the open, the tests fail loudly with a precondition message. They do not pass.
  - Row 9 keeps its `took + TICK >= left` bite. `left` is still a lower bound: `asked` is taken before the holder thread spawns, and the hold is timed from the successful open.
  - The holder pumps its owner thread, closes the clipboard before `DestroyWindow`, and reports a failed window or open as `Err` text in the `clipboard` precondition.
- **The Alt/0xE8 path plus clearing the message record cannot make hotkey.rs test 5 pass vacuously.** `bring_to_front` returns only after the injected Alt key-up is in the record (win32_support/mod.rs:515-528). It sends the mask key down/up before that Alt-up, and only after the window is in front.
  - The window thread dispatches keyboard input in order, so this path's 0xE8 messages are recorded before the Alt-up. The clear at :529 removes them all.
  - So test 5's `mask_down && mask_up` can come only from keys sent after the clear. The test sends no 0xE8 during the hold (its `Keys::release` sends key-ups only), so those keys can come only from the hotkey thread. The clear makes the "mask key seen" bite stronger than before: earlier, a stray test-side mask could not be told apart.
  - The "no WM_CHAR / no menu" checks are not loosened. A late `WM_SYSCOMMAND` from this path's own Alt-up, recorded after the clear, could only turn the test red, never green. And the mask key makes such a message unlikely.
  - Alt is read up before `bring_to_front` returns (`Keys::release` waits on `GetAsyncKeyState`). So a following Ctrl+V (paste.rs row 12) or modifier wait (row 15) cannot run as Ctrl+Alt.
  - In delivery.rs row 19, the gate opens only after `b.front()` returns.

It then creates a new window and brings it to the front through the same Alt → `SetForegroundWindow` → 0xE8 → Alt-up order that `bring_to_front` uses. Keys are armed in a `Release` guard, and the probe waits until Alt reads up. The fact appears in `WINDOW_FACTS`, so the step guard's end-line count (13) comes out right.
