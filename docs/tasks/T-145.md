## Investigation

Tools: Serena for Rust symbols (`get_symbols_overview` of call.rs and lib.rs; `find_symbol` bodies of `on_run_event`, `start_calls`, `serve`). grep and file reads for core session.rs / events.rs / storage.rs ranges, hotkey.rs, the NSIS hooks, the ci.yml / ps1 steps, the spec and the tasks. tao 0.37.1 source is not available on this host: the only copy is a checker fixture, `scripts/ci/fixtures/helper-windows/.../tao-0.37.1`. The claim that the app ends inside its WM_ENDSESSION handler therefore rests on T-024's CI step and run 39009159665, not on the tao source. Context7 was not needed: no new library API beyond Win32 `MessageBoxW`, whose flags the developer checks against the `windows` crate pinned in Cargo.lock.

**Frame.** Expected (spec 007 FR-007, FR-008, FR-017; R14; quickstart 4–6):
- Exit while recording asks first.
- Shutdown, logoff and installer close finalize without a question. The pass of such a call starts by itself at the next start.
- Sleep stops the call and the user is told on wake.
- A lock changes nothing.
- A forced kill is recovered at the next start.

Observed on main 7b0f4fa9: none of this is wired. The shell does not involve the call at any of these ends, and nothing calls core's recovery (see `analysis.root_cause` (1)–(5)). Every dependency is DONE (T-128, T-144, T-007).

**Hypotheses.**
1. *The exit path never reaches the call.* Confirmed: `on_run_event`'s Exit arm and `TrayAction::Exit` have no call code. Drop does not run (windows-shell.md).
2. *A second path handles the concern.* Refuted for exit and sleep. The tick thread stops only for storage failure, 4 h and low disk. `DictationSession::suspended` is dictation-only. For recovery the second path is only planned: T-147's Context names "the start-up restart". D4 assigns the one recover call to T-145 so there are not two.
3. *This class was fixed before.* No. `class: call-lifecycle` has no earlier task, and docs/failures.md has no entry for it. T-010 built the suspend branch for dictation only, and T-024 built the WM_ENDSESSION clean end for the log only. Both are reused here, not repaired.
4. *Core already does the finalize.* Confirmed. `CallSession::stop` → `finish` writes the EOS page, syncs (`OpusOgg::finish`: flush + sync_data after EOS), writes meta `ready-to-transcribe` and releases the folder. So R14's `finalize(SystemEnd)` is `stop(SystemEnd)`, and core needs no new function. The one core change is D1 (the Sleep notice).
5. *The installer close needs its own handler.* Refuted. Restart Manager sends WM_QUERYENDSESSION/WM_ENDSESSION (installer-hooks.nsh comment, CI run 39009159665), which is the same RunEvent::Exit. The `installer-ended` note only classifies a forced kill in diag.

**Where the sleep notice disagrees.** Core's I12 (call-session.md) and the test `stop_closes_both_files_readable_and_reports_it` say `Sleep → CallSavedTranscribing`. The data-model notices table, quickstart 6 and US4 #9 say `stopped{sleep}` on wake. Core's `CallNotice::message` already maps `Stopped{Sleep}` to `notice.stopped.sleep`, which no path emits today. D1 follows the spec. This is developer-level: it is spec text, not a new product choice.

**Risks.**
- The exit stop takes the session lock on the main thread. That is an exception to #223, acceptable because nothing inside the lock waits on the main thread: `TrayPart::set_call_recording` is a non-blocking `want`, and `emit_to` does not block either.
- A slow `toggle_record` start holding the lock can push the stop past 2 s. The outcome is still safe: a cut-off leaves `recording`, which becomes `recovered`.
- A pass running at exit is cut. Its `transcribing` meta is reset by recover.
- If PBT_APMRESUMEAUTOMATIC is lost, the held items wait for the next request (D1).

**Owner questions.** None. Quickstart 5 and 6 stay the owner's manual checks, per `verify_exception`.
