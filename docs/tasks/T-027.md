## Context

NFR-12; `cargo-about` in the `voicen-rust` image; npm licenses too; whisper models' license listed.

## Acceptance

- [ ] `make licenses-check` (part of `make check`, so the CI `gate` job) fails, naming the component, on any shipped dependency outside the accepted list of decision #9: Windows-target Rust crates, npm packages in the client bundle, and the manual list (models, NSIS)
- [ ] `THIRD-PARTY-NOTICES.txt` is generated by `make licenses`, committed, and `make licenses-check` fails with a diff when it is stale (bundling it into the installer is T-025, spec 006 T029/T030)
- [ ] Failure branch: a GPL-3.0 or unlicensed crate → the check fails naming it — permanently by the fixture workspace `licenses/fixtures/gpl/` in the gate, and once by `make licenses-check` in a throwaway `git worktree` with a GPL crate added to src-tauri; no network → the check says it cannot run, not "license failure"
- [ ] Test that fails without the change: `scripts/licenses/*.test.mjs (node --test) and the cargo-about fixture run in make licenses-check`

## Investigation

Investigator, 2026-10-03. Read: spec 006 (US6, FR-031..FR-033, research R13, contracts/installer-ci.md, ipc.md, tasks.md T029/T030/T034–T036), requirements NFR-12, decisions #5 #9 #10 #11 #12, Makefile, ci.yml, docker/rust.Dockerfile, Cargo.toml/Cargo.lock, src-tauri/Cargo.toml + tauri.conf.json, package.json, playwright/vitest configs, PRINCIPLES.md (P-002, P-004, P-005, P-010, P-011), docs/failures.md, docs/decisions/. Tools: Serena not used (no TypeScript symbols involved). context7 is not connected (`mcp__context7__*` absent), so cargo-about behaviour below is **unverified against its docs**. The Tauri claims come from `node_modules/@tauri-apps/cli@2.12.1/config.schema.json`. Nothing was installed or rebuilt.

**Frame.** Expected (NFR-12, FR-031..033):
- the gate fails, naming the component, on any shipped dependency whose license is unaccepted or unknown;
- a notices file listing every shipped component ships with the app;
- the gate fails when that file is stale.

Observed: no check and no file exist. The planned npm input misses the shipped Svelte code.

**Hypotheses.**
1. *The npm prod set equals the shipped set.* Refuted. `pnpm licenses list --prod --json` lists 1 package (@tauri-apps/api 2.12.1). The built bundle contains the Svelte 5 runtime and the SvelteKit client (`grep svelte.dev/e/ build/…/BIAHnwUw.js`, `__sveltekit_` in B5r922Jl.js), and both are devDependencies. Checking all packages instead (no `--prod`) is too broad. That run finds BlueOak-1.0.0 (minimatch) and MPL-2.0 (lightningcss, 3 packages), both dev tools that never ship. BlueOak is not on #9's list, so that check would fail on code we never ship. Not measured: the exact bundled set (a throwaway build with a module-listing plugin was not permitted). Known so far: svelte 5.57.1, @sveltejs/kit 2.70.3, @tauri-apps/api 2.12.1, and probably esm-env, clsx and devalue. All are MIT or Apache-2.0 OR MIT.
2. *Linux cannot resolve src-tauri's Windows-only crates.* Refuted for license purposes:
   - Cargo.lock is platform-independent. It contains windows, windows-sys, windows_x86_64_msvc, webview2-com and wry, and also gtk, webkit2gtk and objc2*.
   - `rustc --print cfg --target x86_64-pc-windows-msvc` runs in voicen-rust:1.99 with only the Linux target installed. So `cargo metadata --filter-platform x86_64-pc-windows-msvc`, which is what cargo-about's `targets` uses, can select the Windows set without compiling anything.
   - It does need the crate sources. Offline it fails with `failed to download adler2 v2.0.1`.
   - The target filter is required. Without it, the Linux-only gtk/webkit2gtk tree and the Apple objc2 tree would be checked and listed, and they are not shipped.
   - Build-dependencies also need excluding (`ignore-build-dependencies`). Example: target-lexicon reaches us only through cfg-expr, a build-time tool.
3. *The same concern is handled on a second path.* Partly confirmed, as a risk rather than a defect:
   - The license list exists twice: decision #9 (owner) has MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib, Unicode-3.0, MPL-2.0, Unlicense, CC0-1.0, while research R13 proposes adding Apache-2.0 WITH LLVM-exception, 0BSD, BSL-1.0, Unicode-DFS-2016 and CDLA-Permissive-2.0. #9 is the owner's decision. about.toml must hold exactly #9 (P-010), and R13's extras stay out until the owner adds a row.
   - Spec 002 T039 and spec 001 T004 (fixtures LICENSES.md) plan their own license notes. Their entries must go into this task's manual list, not into separate files (P-011).
4. *This class was fixed before.* Refuted. docs/failures.md has only the placeholder row, no task has `class: license` except this one, and `git log` has no license commits. Recurrence: none.

**Settled points**

1. *Rust coverage.*
   - cargo-about runs over the whole workspace (voicen-core, src-tauri, and later voicen-whisper per #12, which is not a member yet). about.toml sets `targets = ["x86_64-pc-windows-msvc"]`, `ignore-build-dependencies = true` and `ignore-dev-dependencies = true`.
   - It runs on Linux in the image. It needs the sources of the Windows-target crates. Count not measured: the lock has 418 packages across all platforms, and the Windows subset is smaller.
   - Features resolve as src-tauri requests them, which is the shipped set. If core's `silero`/whisper feature is enabled only by the shell, it is covered. If only by a CI flag, cargo-about needs `--features`.
   - Determinism: pin the cargo-about version in the Dockerfile and disable clearlydefined.io lookups (`no-clearly-defined`; key **to verify**). Otherwise the generated file can change between runs without any lock change.
   - To verify against the pinned version's README/source before use: that `generate` exits non-zero on an unaccepted or undeterminable license (or needs `--fail`), and that path (unpublished) crates are checked.
   - npm: no new tool is needed. pnpm 8.15's built-in `pnpm licenses list --json` works here, and package.json `license` fields can also be read directly. But the *set* must come from the bundle (hypothesis 1).
2. *Notices file.* `THIRD-PARTY-NOTICES.txt` sits at the repo root, is generated by `make licenses` on the Linux side and is **committed**.
   - Why committed: the `windows` job has no Docker image and no cargo-about, and `pnpm tauri build` must find the file. Generating it there would need a second install on the Windows runner.
   - `make licenses-check` regenerates it into a temp file and fails on any difference (FR-032).
   - Contents: name, version, SPDX id and license text per component (MIT requires the copyright and permission text). No absolute paths: pnpm output has machine-specific `path` values. MPL-2.0 entries carry a source URL.
   - Name: use the contract name `THIRD-PARTY-NOTICES.txt` everywhere, not the task's "THIRD_PARTY" (P-010).
   - Installing: `bundle.resources` in **map form** `{"../THIRD-PARTY-NOTICES.txt": "THIRD-PARTY-NOTICES.txt"}` puts it at `$RESOURCE/THIRD-PARTY-NOTICES.txt` (schema text). The list form keeps the relative path. With `../` it lands in an `_up_` folder; this is known Tauri behaviour, **not verified** here. `$RESOURCE` is the NSIS install dir.
   - That edit plus the smoke assertion "install dir contains THIRD-PARTY-NOTICES.txt" are spec T029/T030, which is T-025's scope (D4). Until this task lands, spec tasks.md calls for a placeholder file.
3. *Models.* The hand-kept list holds the non-package components:
   - whisper.cpp/ggml (MIT, vendored by whisper-rs-sys; the crate license covers only the Rust part);
   - Silero VAD model (MIT, bundled by 001);
   - downloadable whisper ggml models (MIT, OpenAI Whisper weights via ggerganov/whisper.cpp; listed, marked "downloaded at run time, not bundled");
   - NSIS (zlib, installer only), and the speech-gate test fixtures are not shipped.

   Keep the list as **JSON** (`licenses/manual.json`), not TOML: node has no built-in TOML parser, and a parser package would be a new dependency. about.toml's `accepted` array is the only TOML the node script reads. Use a narrow, tested reader that fails loudly if it cannot parse.
4. *Failure branch without a push.*
   - (a) A permanent fixture in the gate. `licenses/fixtures/gpl/` is a standalone workspace with its own `[workspace]` so the root workspace ignores it. It has path-only crates `gpl-fixture` (`license = "GPL-3.0-only"`) and `nolicense-fixture` (no license). cargo-about runs on it with the real about.toml, and the check asserts a non-zero exit and both names in the output. It is offline, with no download. The node tests cover the npm side with fixture JSON.
   - (b) One recorded run for the Acceptance line: in a throwaway `git worktree` on a local branch, add a GPL-3.0 crate to src-tauri and run `make licenses-check`. Expect failure naming the crate.
   - The gate runs the same image locally and in CI, so this is the CI behaviour. A real CI run would need a pushed PR, because CI triggers only on push to main and on PRs. That is not done from a DEV session.
5. *Gate placement.* In `make check` (contract installer-ci.md: gate "incl. licenses-check").
   - It catches an unaccepted dependency before NEEDS_REVIEW (P-004).
   - The Windows job cannot run it (no image).
   - It needs a fresh client build (`pnpm build`) for the bundle list, so the target runs it itself rather than relying on e2e's webServer, which may reuse a server.
   - Cost, estimated, not measured:
     - first local run downloads the Windows-target crate sources (network to crates.io), then they are cached in .teamwright/cache/core;
     - each CI gate run downloads them again (no cargo cache in the gate job) and compiles cargo-about during `make core-image` (no Docker layer cache in CI), probably several minutes;
     - cargo-about itself plus the node check take seconds once sources are present.

   Without network, the check is *not runnable* (cargo exits 101). It must not report that as a license failure.
6. *Size.* Medium. It is one concern with one output, already designed (spec 006 Phase 8 = T034–T036), and it touches three file groups: image + about.toml/template, scripts/licenses + vite plugin + tests, and Makefile + committed notices. No product code. Everything is verifiable on Linux once bundling moves to T-025 (`deploys: false` and `surface: none` then stay correct). No new spec is needed.

**Approach options**
- **A. As R13 wrote it** (cargo-about + `pnpm licenses list --prod`). Rejected: it checks 1 npm package while the Svelte/Kit runtime ships unchecked (hypothesis 1).
- **A′. Move svelte and @sveltejs/kit to `dependencies`, then use `--prod`.** Simple, but it rests on a convention nothing enforces. The next devDependency imported into src ships unchecked (P-002: a list, not an invariant). It also pulls Kit's server-only dependencies into the notices.
- **B (recommended). The bundle-derived npm set.** An inline Vite plugin, no new dependency, client build only (skip the SSR/prerender build, which does not ship). It writes `target/licenses/npm-bundled.json` (name@version per module under node_modules), and scripts/licenses evaluates each package's package.json license against about.toml.
  - Red test first: node tests with a GPL fixture plus the Rust fixture workspace. Both are red before the implementation exists.
  - Bite check (P-005): add `GPL-3.0-only` to about.toml's accepted list and the fixture test goes red. Empty the bundle list and the check fails rather than passing vacuously.
  - Risk: the plugin depends on Rollup's `chunk.modules` / module ids. Mitigation: a sanity assertion that `svelte` is in the list.
  - Rollback: remove `licenses-check` from `make check`.

**Owner / orchestrator points**
- D1. How to install cargo-about. #9 consents to it but not to a method or version. Options: `cargo install cargo-about --locked --version <pin>` (compiled at every CI image build), or a pinned release binary with a sha256 check (a different download path).
- D2. The accepted list is #9 exactly. The first real run may surface crates whose only licenses are outside #9. Example: `webpki-roots` (CDLA-Permissive-2.0) when reqwest+rustls arrives with T-001. Not checked: crate sources are not cached, so the current lock's crate licenses could not be read beyond the 11 cached crates (all accepted; unicode-ident = `(MIT OR Apache-2.0) AND Unicode-3.0`). Each such crate is an owner decision and a new decisions row, never an about.toml edit by a developer.
- D3. The gate gets a network dependency on crates.io (full Windows-target crate sources). Optional: an actions/cache step for `.teamwright/cache/core` in the gate job.
- D4. Acceptance "notices bundled in the installer" is spec T029/T030, which is T-025 (deploys: true, Windows CI). Move it there and reword it here to "THIRD-PARTY-NOTICES.txt generated, committed and checked for staleness by the gate". Alternatively keep it and set T-027 `deploys: true` with Windows CI evidence.
- D5. The Acceptance wording "the license job" → it is `make licenses-check` inside the `gate` job (contract). The throwaway-branch proof is a local worktree run plus the permanent fixture, not a pushed branch.
- Docs in the same commit (P-014): CLAUDE.md commands (`make licenses`), docs/architecture.md (release/licensing), a new docs/decisions/ci.md (or release.md) recording the invariant, and the rule that every dependency change regenerates the notices in the same commit.
