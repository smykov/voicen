## Context

Part 2 of the T-007 split (decision #274). The only real `TempAudioStore` today is the shell's `NoPendingAudio`, whose `put_pending` always fails, so the shipped app never keeps a pending recording and never cleans up at start or exit. This task adds a file store in `voicen-core` (`FsTempAudioStore`, e.g. `crates/voicen-core/src/pending.rs`) under `paths::data_dir()/tmp/audio`, swaps it in for `NoPendingAudio` in the shell's `start_dictation`, and runs `delete_all` before the session starts and at `RunEvent::Exit` (FR-032). It runs in parallel with T-007 (core notifier and retry), which uses the store through the existing port. The T-007 analysis (its `## Investigation`, invariant I3) is the starting point.

From T-001 review round 1: `put_pending` must not leave a partial file on `Err`. Moved from T-144 by OQ-80, decision #251: the cleanup never deletes under any call root (spec 007 FR-020, req NFR-06).

## Acceptance

- [ ] Core: `put_pending` leaves either the whole file or none — red test: a write that fails midway leaves no file of the store's pattern
- [ ] Core: the cleanup deletes only regular files of its own name pattern directly in its own folder, never recursively (other files and subfolders survive)
- [ ] Core: the cleanup deletes nothing when its folder equals, lies inside, or contains the current or any earlier calls root (`settings::roots::effective_root`, `calls.earlier_roots`). Red tests for the equal and ancestor cases (the "inside" case alone passes against any non-recursive cleanup, F-024): a calls root equal to or above the temp folder, with a file of the cleanup's own pattern in it, survives
- [ ] Shell: `NoPendingAudio` replaced by the file store; `delete_all` runs at start (stale files of an earlier session removed) and at `RunEvent::Exit` — Windows CI
- [ ] Failure branch: the store's folder cannot be created or written → `put_pending` returns `Err`, the failure is reported as today (`pending_store_failure_reports_without_pending`) and no partial file remains
- [ ] Test that fails without the change: `crates/voicen-core` pending store tests; a shell test in `src-tauri/tests/`

### Frame

- **Observed:** the shipped app never keeps a pending recording, and nothing is deleted at start or exit. `NoPendingAudio` (`dictation.rs:173-198`) fails every put. Nothing calls `delete_all`.
- **Expected (FR-032, NFR-06, spec 007 FR-020, decision #251):**
  - one pending WAV under `<data>/tmp/audio/`;
  - stale files removed at start and everything removed at exit;
  - the cleanup never touches a calls root.

### Hypotheses

1. **Missing feature (confirmed).** No file store exists. The `impl TempAudioStore` list is: the fake, `dictation_session.rs` `BlockingStore`, `NoPendingAudio`.
2. **A second path handles cleanup (refuted).** No other code removes files under `tmp`. The `.part` cleanup in `LocalModels::open` is for `models_dir`, and `crash::remove_stale_tmp` is for `logs`.
3. **Fixed before (refuted).** No earlier patch of this class. `recurrence_of: []` stands.

### Acceptance, item by item

- **Atomic put.** Encode with `audio::wav::encode` (`audio/wav.rs:14`).
  - Write `pending-<id>.wav.part` (truncate is fine: ids are per process and start cleanup runs first).
  - Then `fs::rename` onto `pending-<id>.wav`. The std docs say rename replaces an existing `to` (Windows: `MoveFileExW`, falling back to `SetFileInformationByHandle`).
  - On any Err, `remove_file(.part)` and return the original error.
  - The writer is injectable, like the `open` closure of `call/storage.rs:377-386`, so a test can fail a write midway on Linux. Permission tricks do not work under root in Docker (`settings/roots.rs` tests note this).
  - Real-disk failure branches: the target name exists as a directory (rename fails); `tmp` is a regular file (`create_dir_all` fails).
  - The folder is created lazily at put (`create_dir_all`).
  - `get_pending` needs a reader for its own WAV. Only `call/wav_source.rs` and `test_support` have readers, and both are test-only. Add a small private decoder: the 44-byte header written by `encode`, checked, then i16 LE.
- **Own-pattern, non-recursive cleanup.** `read_dir` of the folder only. A name is deleted only when it parses as `pending-<u64>.wav` or `pending-<u64>.wav.part`, and only when `DirEntry::file_type()` is a regular file (not followed on Windows: a link or a directory never counts). Precedent: `crash::remove_stale_tmp` and `crash_files` (`diag/crash.rs:463-496`). The `.part` files are part of the pattern, so a crash leftover goes at the next start. A missing folder is `Ok(())`.
- **Calls-roots guard.**
  - **Source of the roots:** a closure given to the constructor, called at every put and delete. The shell builds it over the managed `Arc<SettingsService>`, through a new `SettingsService::call_roots()`. It returns `effective_root(&snapshot.calls, &deps.call_roots.default_root())`, then `snapshot.calls.earlier_roots`.
  - **Why an accessor:** the default root lives only in `SettingsDeps.call_roots` (`settings_ipc.rs:98`), and `effective_root` is documented as the one resolution of the current root (`roots.rs:131-133`).
  - **Settings read failure:** `snapshot()` cannot fail (in memory, poison recovered). The failure case is `LoadOutcome::Unavailable` (`service.rs:307, 319, 327`): the settings file could not be read, defaults are in force, and the real roots are unknown. `call_roots()` then returns `None`, and the guard fails closed: put returns Err (no pending, reported as today) and the deletes delete nothing. This matches decision #19 ("no dependency is called while Unavailable").
  - **Reset** (a corrupt file is backed up and replaced by defaults) forgets the old roots for the whole app (the calls list too). The store treats it as Loaded. The own-pattern, non-recursive rule still protects a forgotten root: a calls root holds call folders and at most `.voicen-write-probe` at top level (`CallStore::list`, `FsCallRoots::probe`). That is a residual risk, not a gap in the guard.
  - **Comparison:** canonicalise the folder and each root where they exist. This resolves junctions, and on Windows both sides come back in the same `\\?\` form. Where a path does not exist, fall back to a lexical comparison: components normalised, ASCII case-insensitive on Windows. Then check equal, `folder.starts_with(root)` and `root.starts_with(folder)`, component-wise.
  - **Red tests:** equal and ancestor first. The "contains" case alone passes against any non-recursive cleanup (F-024 class).
- **Shell swap, start and exit.**
  - `DictationPorts.temp_audio` replaces the hard-wired `Arc::new(NoPendingAudio)` (`dictation.rs:135`).
  - `start_dictation` calls `delete_all` before `DictationSession::start`. That way no put can race it, and the hotkey thread does not exist yet.
  - It manages the store (newtype `PendingAudio(Arc<dyn TempAudioStore>)`). The `RunEvent::Exit` arm of `on_run_event` (`lib.rs:232-236`) calls `delete_all` on it if it is managed, next to `SessionEnd::end`. `Exit` is the only clean end; the process ends by tao's `process::exit` (`dictation-session.md:91`).
  - Recommended: a failed start cleanup writes one warning line with the kind and `os_code` only, like `ModelsCleanupFailed` (`lib.rs:388-395`). The new `WarningKind` is checked against `docs/decisions/diagnostics-log.md`. An exit failure is ignored; the next start retries.
- **Failure branch.** Put errors reach `keep_pending`, which already turns them into "no pending, older audio deleted, failure shown" (`pipeline.rs:409-425`). `pending_store_failure_reports_without_pending` (`tests/api_pipeline.rs:1099`) stays as it is: fake-based. The new fs tests prove "no partial file".

### Residual risks

- A job still in `put_pending` when Exit runs `delete_all` can rename its file after the cleanup. The session is not stopped at exit (T-052). That file survives this exit and is removed at the next start. FR-032 allows that ("stale ... deleted at the next start"). Do not add a wait on the event loop.
- Ids restart at 1 in each process (`pipeline.rs:404-408`). A stale `pending-1.wav` that the start cleanup failed to delete is replaced by the rename, never read as the new one. The slot only holds ids of this process.

### Not settled, no owner question needed

- **Store refuses put under a failed guard (recommended yes).** Otherwise, files written while the roots are unknown could never be deleted in that session. This is inside decision #251's "never under"; it needs no new decision.
- **The warning line for a failed start cleanup:** a diagnostics-log choice for the developer and reviewer.
