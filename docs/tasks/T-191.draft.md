## 1. Header, line 3 — the version rule for several amendments in one unreleased task (T-113 r2#4)

Was:

> **Version:** 1.4.0 — bumped in a separate commit on every amendment, recorded in `docs/decisions.md` (major: removed or reversed · minor: added or moved up a tier · patch: wording). Amendments are owner decisions; see `docs/process/principles.md` §2a.

Proposed:

> **Version:** 1.4.1 — bumped in a separate commit on every amendment, recorded in `docs/decisions.md` (major: removed or reversed · minor: added or moved up a tier · patch: wording). Amendments made in one task before its version reaches `origin/main` share one version: the bump takes the highest kind among them, and each amendment still gets its own `docs/decisions.md` row. Amendments are owner decisions; see `docs/process/principles.md` §2a.

Why: P-020 was reworded twice at 1.4.0 (#154, then #155) inside T-113, and 1.4.0 was not on `origin/main` yet. Only one text ever shipped under that number. The rule makes that the norm instead of a deviation.

## 2. Header, line 9 — "accepted entries are not edited" against in-place amendments (T-113 r1#6)

Was:

> Accepted entries are not edited. To change one, add a new entry and mark the old one `Superseded by P-NNN`.

Proposed:

> An accepted entry keeps its meaning. When a principle is removed or its meaning reversed (a major change), a new entry is added and the old one is marked `Superseded by P-NNN`. A tier move or a change to the wording or "How checked" (minor or patch) is made in the entry itself, as an amendment by §2a: a separate commit, a version bump, a `docs/decisions.md` row.

Why: P-016 (95ac854 → 3b15455 → 95e1688) and P-020 (#154, #155) were amended in place, as §2a allows. Line 9 forbade that.

## 3. P-016 "Not covered" — rust-cache wording and the tag-only release job (T-066 r2#1, T-026 r1#6)

Was (end of the "How checked" bullet):

> Not covered: a step gated on `main` (`if: github.ref == 'refs/heads/main'`, rust-cache `save-if`) never runs on `wip/<ID>`, so its first execution is the next push to `main`; such steps are kept to cache saves and the installer's Telegram send (decisions #95), each consuming only outputs of steps that did run on the wip run and unable to turn `main` red (`docs/decisions/ci-toolchain.md` › "Every CI-only premise runs on a `wip/<ID>` run before review").

Proposed:

> Not covered: a step or a save gated on `main` never runs on `wip/<ID>`, so its first execution is the next push to `main`. Examples: a step under `if: github.ref == 'refs/heads/main'`, or the save inside rust-cache's post step under `save-if`, where the post step itself runs on wip and only its save is skipped. Such steps are kept to cache saves and the installer's Telegram send (decisions #95). Each consumes only outputs of steps that did run on the wip run and cannot turn `main` red. The tag-only `release` job (`v*` tags) never runs on `wip/<ID>` or `main` either. Its one step `scripts/ci/release.sh` runs `scripts/ci/release-check.sh` first, and the check's pass path and failure branch run in the windows job on every other ref. Only the publish call itself is first executed by the tag push (`docs/decisions/ci-toolchain.md` › "Every CI-only premise runs on a `wip/<ID>` run before review", › release).

Why: the review of T-066 round 2 saw "Post Run Swatinem/rust-cache@v2: success" on a wip run, so "never runs" was wrong for the post step. The review of T-026 round 1 found a third class of step that never runs on wip, and `ci-toolchain.md` already records it, but P-016 did not.
