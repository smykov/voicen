- **#4b, frozen publication after a release-path panic: closed.**
  - Placement and drop order.
    - `StopInFlight` (`dictation.rs:167-180`) is declared after `_order` (the `releasing` guard) and outside both session-lock blocks.
    - On unwind, any session guard from an inner block is dropped first, then `StopInFlight`, then `_order`.
    - So the guard locks `state` while holding only `releasing`, which keeps the order `releasing` → `state`.
  - Arming. The guard is armed only together with `stopping` (`:339`) and disarmed in the `finish` critical section, before that section's publish (`:386`).
    - Every early return (`Ignored`, and `Discarded`, where `stopping` is false) happens unarmed.
    - So the guard can be dropped armed only during an unwind; it never publishes twice on the normal path.
    - If the `finish` publish itself panics, the guard is already disarmed, so it does not publish again.
    - `stopping` is written nowhere else.
  - Poisoned locks.
    - A panic while holding `state` (in `ctrl.finish`) poisons it. The guard and every later lock use `lock()` → `PoisonError::into_inner` (`:114-116`), and the timer's `wait`/`wait_timeout` do the same.
    - The guard takes `state` while already panicking, so it does not poison it again.
    - The `releasing` guard dropped during the unwind does poison `releasing`. The test's second release goes through that poisoned mutex and works.
  - The residual abort is accepted, not a finding. Under unwinding, an `Indicator` that panics inside the guard's publish makes a second panic during an unwind, which aborts. This needs two independent adapter faults.
    - The release profile is `panic = "abort"` (`Cargo.toml:12-16`, workspace root, which also covers `src-tauri`). A single panic already ends the shipped app, so the residual adds no release-mode risk.
    - In tests, an abort kills the test binary loudly.
    - Wrapping that publish in `catch_unwind` would buy nothing the release build can use.
  - The test `a_panic_in_the_release_path_does_not_freeze_publication` (`dictation_session.rs:1052-1117`) is deterministic.
    - `PanicOnStopSource` delivers its chunks synchronously inside `start`, and `stop` panics on the caller's thread, between arming and `finish`.
    - After `release`, the controller has no live recording, no queued job and no message (the press dropped it; `recording/mod.rs:257-310`). So the guard publishes overlay Hidden and tray Idle, and `next_deadline()` is `None`: the timer cannot publish anything.
    - `wait_jobs(1)` waits for a `JobFinished` event and a last overlay of Hidden. The second release publishes Processing before it returns, so the earlier Hidden cannot satisfy the wait.
    - It passed 10 of 10 repeat runs.
  - Bite, by reading.
    - Without the guard, `stopping` stays true, so the first assertion gets `[Recording]` instead of `[Recording, Hidden]`. This matches the developer's red report.
    - With a guard that clears `stopping` but does not publish, the first assertion is also red. In that case the next press would publish nothing either, because `published_overlay` would still be Recording.
    - The disarm at `:386` is not pinned by a test. That is harmless: `publish` is idempotent under the lock.
