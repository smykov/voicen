**Hypotheses.**
1. *Thread oversubscription of the spin barrier (libtest parallelism × engine threads).* Confirmed in mechanism, not in size. Available parallelism is 4 (the `silero-timing` line in the same job). libtest defaults to that many test threads, and `ci.yml:173` passes no `--test-threads`. `thread_count()` = min(4, 8) = 4. `ggml_barrier` (ggml-cpu.c:547) spins on `n_barrier_passed` with `ggml_thread_cpu_relax()` and returns at once only for `n_threads == 1`. OpenMP is off (whisper-rs-sys build.rs:289-290; the `openmp` feature is not enabled, pinned by `direct_dependencies_are_voicen_core_and_whisper_rs`). The same shape cost Silero 40 s per decision against 17-20 ms (T-043 table), and the fix there had the predicted effect on Windows. What would refute it: one transcription alone also taking tens of seconds. That figure is missing (see below).
2. *whisper.cpp built without optimisation under `cargo test`.* Refuted. whisper-rs-sys build.rs:267-275 sets `RelWithDebInfo` under `debug_assertions`, with `.profile("Release")` (build.rs:184). `.cargo/config.toml` forces `/O2` for both build types. T-043 Investigation reached the same result for the same build.
3. *The work itself is large (30 s encoder window per call; the 60 s abort baseline).* Partly true, but not the cause. Every call encodes at least one 30 s mel window, and `pre_requested_abort_returns_promptly` encodes two windows plus decoding. That is the longest single piece of work, but the 1 s clip tests alone cost 90-190 s each. `pre_requested_abort_returns_promptly` finished 13 s after the last other test ended (22:19:55 → 22:20:08), which fits fast progress once it ran alone. That is an inference, not a measurement.
4. *A second path handles the same concern.* Yes, and it is already fixed: `SileroDetector` has a fixed `VAD_THREADS = 1` (silero.rs:43, T-043). `thread_count` has a single caller (`WhisperLoader::load`). In production, `residency` serialises transcriptions. Upcoming paths that will run ggml next to a transcription: T-102 (shell VAD gate, a 1-thread decision before the engine call) and T-135 (Silero speech spans for the call final pass, possibly next to a transcription of another track). Their combined thread budget is not owned by any task yet (see D1).

T-099 r1#5 (this binary, 283 s, "serialise the model tests with one lock"), T-043 r2#1 and T-099 v3#N2 (the abort test's ratio) were T-060 follow-ups and are now Acceptance 3-5 of this task (#201). **Abort assertion without a clock (Acceptance 5, T-099 v3#N2).**

*Why the current test does not bite.* It has two checks. (1) `clock reads >= 1`: `WhisperModel::transcribe` calls `abort.requested()` itself after `state.full` returns, so with limit zero that one read happens even when neither stop callback is installed. The check is always met. (2) `aborted * 4 <= baseline`: the only real check, a ratio of two wall-clock readings, which load can push either way. That is the F-013/F-021 shape: the clock decides the verdict.

*What cannot carry a clock-free check (searched, with source):*
- The test's own clock. `Abort::requested` latches (`speech_model.rs:64-72`): after the first true it returns without reading the clock, so the reads after the stop, which are exactly the work to be bounded, are not counted. A stepping clock that fires at read K counts only the reads before the stop.
- whisper.cpp's timing figures. `whisper_get_timings` (`whisper.h:445`, `src/whisper.cpp:4245`) reads `ctx->state` only. whisper-rs builds the context with `whisper_init_from_file_with_params_no_state` (`whisper_ctx.rs:55`) and transcribes on a separate `WhisperState`, so `ctx->state` is null and the call returns null (`:4246`). Its fields are also `ggml_time_us` durations, so wall-clock again. `n_encode`/`n_decode` (`:843-844`) have no public per-state accessor (`whisper.h`, searched for `timings` and `_from_state`).
- A counter inside `abort_requested` / `encoder_may_start`. It disappears with the callbacks, so the mutant from v3#N2 (both removed) would read 0 and pass.
- A progress-callback counter. whisper.cpp calls `progress_callback` once at the top of each main-loop iteration (`:7001-7006`). It would bite, but it adds a production callback only for the test. It shows nothing that the segment count misses: with only `encoder_may_start` removed it also reads 1.

*What carries it: whisper.cpp's segment count of the run.* `whisper_full_with_state` clears `result_all` at the start of every run (`:6801`). It computes the mel (`:6803-6808`), and then, at the top of the first loop iteration, asks `encoder_begin_callback` and `break`s on false (`:7012-7016`) before the first `whisper_encode_internal` (`:7020`). With a limit-zero `Abort`, `encoder_may_start` returns false at that first call, so the run ends with `whisper_full_n_segments_from_state` (`whisper.h:631`; whisper-rs `WhisperState::full_n_segments`) = 0. If both stop callbacks are removed, the aborted call is the same computation as the unaborted baseline on the same audio and model, so it ends with the baseline's segment count, which the test asserts is > 0 (60 s of the clip repeated every 2 s). That makes the assertion deterministic on any load. (Superseded by review 1: under mutant 01 the second run on one model left 12 segments against the baseline's 24, so "the same computation" does not give the same count; cause not established, T-109 r1#5. The assertion needs only `> 0`.) If only `abort_requested` is removed, `encoder_may_start` still stops before the first window (0 segments). If only `encoder_may_start` is removed, the first encoder graph runs to its end, because the sched helper passes no abort callback (`:190`, `:2406`), and the abort check after it (`:2455`) makes `whisper_full` return -6 with 0 segments. That bounds the work to one window, and the test does not tell this case apart. That is acceptable: the v3#N2 mutant is "both removed", and whisper.cpp exposes no per-state encode count that could separate it.

*What the assertion does not cover, by design:* the mel of the whole input (`:6803-6808`) runs before any callback and cannot be aborted. It is linear in the audio length and not decided by the `Abort`. This is written down in the test comment and in `docs/decisions/builtin-engine.md`, not hidden behind a time bound.

*Surface it needs.* The test holds `Box<dyn SpeechModel>`, and `transcribe` returns `Err(LocalEngineFailed)` whenever the `Abort` fired (decision #133), so the trait shows neither the segments nor the text. Under D2's rule (doc(hidden), no settings field, no env variable), it needs a concrete load that returns `WhisperModel`. `SpeechModelLoader::load` boxes that load, so there is still one load path. It also needs `WhisperModel`'s segment count of the last run (`state.full_n_segments()`). No core change: `Abort` and `SpeechModel` stay as they are.

*Red first.* Unlike the thread figure, this one can go red without a clock. On wip, one throwaway commit on top of the rewritten test deletes the two callback-setting lines in `WhisperModel::transcribe`. That Windows run must fail on `segments == 0`. The commit is then dropped, and the run id is cited under `## Tests`. The reviewed head never contains it.

**What is missing and how the implement stage gets it** (approach decided in #200: lock and figure first). There is no Windows figure for one transcription alone, at any thread count. Without it the engine policy (Acceptance 2) would be a guess, and the Silero answer (1 thread) does not carry over (T-043 r2#1 (b)). The way to get it: the first commit on `wip/T-109` adds the print-only `whisper-timing` test. It runs as a child of the test binary (the `quiet_child_run` shape: `--exact <child> --ignored --nocapture --test-threads=1`) while the parent holds the file lock, so nothing else in the process computes. Per count n ∈ {1, 2, 3, 4} it loads tiny and times 3 runs each of the 1 s clip and `long_audio(30)`. It prints `whisper-timing: threads n, 1 s clip best X ms, 30 s best Y ms, available parallelism P` to stderr past libtest's capture. The developer cites the run id and the lines under `## Tests`. The parent asserts only that the child passed. No figure is compared to a limit. A Linux surrogate (as T-043) is optional, because the Windows log is the evidence. The table is posted under `## Tests` and as a `## Notes` line with the run id. The orchestrator shows it to the owner before the step-2 commit sets B (#200). The step-2 CI run prints the chosen count next to the table.

**Owner decisions (answered, #200 and #201).**
- **D1, production thread policy — decided (#200):** the best measured count, capped below parallelism, at least 1: `thread_count() = max(1, min(B, P − 1))`. B is the count with the lowest 30 s figure in the windows-latest `whisper-timing` table (ties go to fewer threads), and P is the available parallelism. The owner sees the table before B is set (see above). Why: a spin barrier with as many threads as CPUs stalls whenever any other process takes a CPU (T-043: Silero at 4 threads alone on 4 pinned CPUs took 403-1657 ms against 29-105 ms on 6 CPUs), and the VAD decision, the UI and the paste need a core. Consequence: on the 4-vCPU runner the engine runs at most 3 threads, even if 4 measures fastest. The table still includes 4, so that cost is visible.
- **D2, test-only thread knob — decided (#200):** `#[doc(hidden)] pub fn WhisperLoader::with_threads(NonZero<usize>)` is kept, so every Windows run prints the chosen count against the alternatives. It is not a user setting (no settings field, no env variable). The abort test's concrete load and last-run segment count (above) follow the same rule.
- **D3, where it is written — decided (#200):** `docs/decisions/builtin-engine.md` from `_area-template.md` (VAD 1 thread; engine policy with the table; the spin-barrier mechanism; I3 and the mel caveat; what breaks if violated), plus a `docs/decisions.md` row recording B, in the step-2 commit.
