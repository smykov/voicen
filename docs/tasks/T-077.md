## Context

Owner, 2026-10-08: every push, build and release must carry a new version; Telegram receives installers with the same version each time. Today `Cargo.toml` (workspace), `src-tauri/tauri.conf.json` and `package.json` all say `0.1.0`, and nothing changes them. Decision #98: CI stamps `MAJOR.MINOR.<github.run_number>` into these fields before the build, without committing. A `vX.Y.Z` tag build uses the tag's version. MAJOR.MINOR stay in the repository. FR-18 (About and the log show the version) and the Telegram caption then show the stamped version.

## Acceptance

- [ ] A CI build on `main` or `wip/**` builds the installer, the exe's `CARGO_PKG_VERSION` (About, log start line) and the Telegram caption with the version `MAJOR.MINOR.<run_number>`, where MAJOR.MINOR is taken from the repository version. Two consecutive runs give different, increasing versions.
- [ ] A `vX.Y.Z` tag build uses `X.Y.Z`.
- [ ] Failure branch: a malformed repository version, or a tag that is not `vX.Y.Z`, fails the stamping step with a message naming it. The build does not continue with `0.1.0` or a mixed version: the three fields agree, and the existing caption check (`_<version>_` in the installer name) still holds.
- [ ] The Windows smoke shows the installed exe reports the stamped version (startup log line).
- [ ] Docs: `docs/decisions/ci-toolchain.md` (how the version is stamped) and the README/quickstart if it mentions the version.
- [ ] Test that fails without the change: named in `## Tests` (e.g. a `make check` fixture test of the stamping script).

## Investigation

Tools: Serena and Context7 were not connected in this session; used grep, file reads, `gh run list`, `gh api` (Swatinem/rust-cache source at v2 = 6323deb), `strings` on the pinned tauri-cli 2.12.1 binary, and a throwaway cargo workspace in the `voicen-rust:1.99` image (`--network none`).

**Frame.** Observed: every installer (Telegram, artifact), About and the start log line say `0.1.0` on every run. Expected (decision #98): `MAJOR.MINOR.<github.run_number>` per CI run, `X.Y.Z` on a `vX.Y.Z` tag. Not a defect of code that exists: no path derives a version; the three committed literals are the only source.

**Hypotheses.**
1. *No CI step computes a version* — confirmed: `ci.yml` has no version step; `crates/voicen-core/build.rs` stamps only `VOICEN_COMMIT`.
2. *A second path carries the version* — checked: `voicen_core::build_info` reads `CARGO_PKG_VERSION` (both crates use `version.workspace = true`); the UI's `src/lib/buildInfo.ts` gets it over IPC (no own source); NSIS takes `tauri.conf.json > version` (tauri-cli 2.12.1 embedded template: `VIProductVersion "${VERSIONWITHBUILD}"`, `FileVersion`/`ProductVersion` `${VERSION}`; "If removed the version number from `Cargo.toml` is used"); the Telegram premise reads `tauri.conf.json`. `package.json`'s version feeds nothing at build time (tauri.conf.json has a literal, not a path). `Cargo.lock` holds the two members' versions (derived). No other version source found (grep for `0.1.0` across code, scripts, workflows).
3. *Fixed before* — no earlier task of class `build-version`; T-070 introduced the `_<version>_` check, which holds whatever the version is.

**Where the version flows in `ci.yml`.**
- `gate`: `make check` on the committed tree. It must not stamp: `scripts/licenses/rust.sh` runs `cargo fetch --locked` and `scripts/ci/helper-windows.sh` runs `cargo metadata --locked`; with a changed workspace version cargo refuses (`error: cannot update the lock file ... because --locked was passed`, exit 101, reproduced in the docker workspace). So gate and windows are not two stamping runs that must agree: only the windows job stamps; the gate proves the script on fixtures. No other job builds an installer.
- `windows`: checkout → pnpm/node → rust-toolchain → `Swatinem/rust-cache` → `Commit of this build` (VOICEN_COMMIT) → `pnpm install --frozen-lockfile` → save pnpm store → `cargo test` ×2 → `pnpm tauri build` → install smoke steps → upload artifact → `Installer for Telegram` → failure-branch / send.
  - Stamp step goes after the pnpm store save and before `cargo test --workspace`, so every compile of the job sees one version. Cache keys are unaffected either way: rust-cache v2 (`src/config.ts`) hashes member manifests with `package.version` zeroed, does not hash the virtual root manifest, and hashes only registry entries of `Cargo.lock` (no `source`/`checksum` = workspace members filtered out); the key is computed at restore and kept in state for the post save. `pnpm-lock.yaml` (lockfile 6.0) has no root version, so `--frozen-lockfile` is unaffected; stamping after install avoids the question.
  - `Cargo.lock`: `cargo test` / `tauri build` (tauri-cli 2.12.1 binary has no `--locked` string) would silently rewrite the two member entries offline (reproduced: plain `cargo run --offline` updated `version = "0.1.58"`). Recommended: the script rewrites exactly those two entries (the `[[package]]` blocks `voicen` and `voicen-core` without `source`) so the stamped tree passes `--locked` too and nothing depends on an implicit rewrite.
  - Install smoke (first step, `Install silently, launch, ...`): `$expected = "($env:VOICEN_COMMIT) started"` can become `"voicen $env:VOICEN_VERSION ($env:VOICEN_COMMIT) started"` — the format is pinned by `diag_format.rs::started_line_carries_version_commit_and_pid` (`" INFO voicen 0.1.0 (abc1234) started pid=4242"` for the fake build). This satisfies the Acceptance "smoke shows the installed exe reports the stamped version". Change only that step: the later steps (`$expected` in the loaded-launch, single-instance, hotkey steps) only need "a new start line" and stay commit-based.
  - Same-version `/P` reinstall (decision #76): not in `ci.yml` yet (T-025 is TODO). With stamping, the CI reinstall uses the same run's installer, still same-version, so #76 (3) holds; the owner's interactive two-build upgrade in Windows Sandbox now gets two distinct versions without a bump commit.
  - `Installer for Telegram`: reads `tauri.conf.json` after stamping, so `_<version>_` and the caption `Voicen <V>, ...` follow automatically. Add one line: the read version must equal `$VOICEN_VERSION` (a mixed tree is red, not sent).
- Tests unaffected by a stamped version: `diag_format.rs` hard-codes `0.1.0` only for `fake_build()`; the real-build half uses `build_info()`; `build_info.rs` unit tests compare with `env!("CARGO_PKG_VERSION")`. `telegram-send.test.sh` / `telegram-failure-branch.test.sh` use literal fixture names, independent of the repo version.

**`make check` tripwires on `ci.yml`.** None needs a change for a new `run:` step: `ci-wip.sh` classifies only `uses:` (a `run:` step is not judged) and pins `push.branches`; `telegram-guard.sh` judges only steps that reference the Telegram secrets (the stamp step must not); `setup-node-cache.sh` only setup-node steps; `ci-credentials.sh` only Credential Manager names; `shell-test-layout.sh` only `--doc`/`rustdoc`. A new target `check-version-stamp` is added to `check:` and `.PHONY`.

**Script contract (for the developer).** `scripts/ci/version-stamp.sh <ref_type> <ref_name> <run_number> [root]` (root defaults to `.`, so the test runs on fixture copies). Reads `[workspace.package] version` of `Cargo.toml`, top-level `"version"` of `tauri.conf.json` and `package.json`; all three must be equal and match `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` (else exit 1 naming file and value). `ref_type=tag`: `ref_name` must match `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` (else exit 1 naming the tag; the trigger `tags: ["v*"]` also starts on `vfoo`, `v1.2`, `v1.2.3-rc1`) → V = X.Y.Z. Otherwise V = MAJOR.MINOR.run_number, run_number `^[1-9][0-9]*$` and ≤ 65535. Writes V, re-reads all five places, prints `version: V` and appends `VOICEN_VERSION=V` to `$GITHUB_ENV` when set. Writes nothing unless every input is valid. Host bash + sed/awk (node is on both the runner and the host if JSON parsing is preferred; `.gitattributes` keeps `*.sh` LF for Git Bash). Inputs from `${{ github.ref_type }}`, `${{ github.ref_name }}`, `${{ github.run_number }}` passed via `env:`, not interpolated into the script text.

**Limits.** Windows `VS_FIXEDFILEINFO` / NSIS `VIProductVersion` fields are 16-bit: each of MAJOR, MINOR, PATCH ≤ 65535 (the 4th field is the semver build metadata, 0 here). Current run_number is 58 (`gh run list -w ci.yml`), so the limit is far; the script refuses > 65535 rather than produce an installer NSIS or Windows would reject. Tag components get the same bound. MSI's 255 limits do not apply (bundle target is `nsis` only).

**run_number vs run_attempt.** A re-run keeps `run_number`, so attempt 2 rebuilds the same commit with the same version. Acceptable: same source, same run; the caption carries the run URL. Making attempts distinct would need a 4th component (semver `+<attempt>`, which tauri maps to VIProductVersion's 4th field, but it also changes the installer name and `CARGO_PKG_VERSION`) — not recommended, outside #98. Other properties of `run_number`: one counter per workflow shared by `main`, `wip/**` and pull-request runs, so `main` installers increase but skip numbers; renaming or recreating `ci.yml` restarts it at 1 (versions would go backwards) — document in `docs/decisions/ci-toolchain.md` that a workflow rename needs a MINOR bump.

**Open for the owner (not blocking T-077).** Spec 006 Clarification Q5 / FR-029 (T-026): "a tag whose version differs from the app version fails the release". Under #98 a tag build's app version *is* the tag, so that check can no longer fail as written. Possible readings: drop it, or require the tag's MAJOR.MINOR to equal the repository MAJOR.MINOR (then the stamp script would refuse a mismatched tag). This is a product decision for T-026; the orchestrator should add it to `docs/open-questions.md`. T-077 implements #98 literally (tag → its own version, no MAJOR.MINOR check).

**Options.**
- **A (recommended): one stamp script in `scripts/ci`, one windows step, fixture test in `make check`.** Removes the cause (a per-run V derived and written in one place before any compile); red test: `version-stamp.test.sh` (missing script). Risk: a regex edit hitting another `version` line — covered by fixtures with extra `version` keys (dependency tables in Cargo.toml, nested `"version"` in JSON). Rollback: delete the step; the tree is never committed, so builds fall back to the repository version.
- **B: drop `version` from `tauri.conf.json`** (tauri then uses `Cargo.toml`), stamp only Cargo.toml + package.json. One fewer field, but it changes the committed config #98 names, and the Telegram premise would have to read Cargo.toml. Not recommended.
- **C: inline sed in `ci.yml` + `tauri build --config '{"version":...}'`.** No host test possible (P-016 would be the only proof), failure branch not testable offline. Rejected.

**Seam overlap with T-034** (IN_PROGRESS, `/projects/voicen.worktrees/T-034`): T-034 rewrites the step `A launch with a loaded settings.json shows no window` (its `$expected`, `Get-StartCount`, start-line wait). T-077 touches: a new step before `cargo test --workspace`, the `$expected` line of the first install step, and one line in `Installer for Telegram`. No hunk overlaps if T-077 leaves the loaded-launch step alone (it should). Either order works; if T-034 lands first, T-077 rebases trivially. Neither should change the other's step.
