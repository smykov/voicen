## Context

Owner, 2026-10-08: every push, build and release must carry a new version; Telegram receives installers with the same version each time. Today `Cargo.toml` (workspace), `src-tauri/tauri.conf.json` and `package.json` all say `0.1.0`, and nothing changes them. Decision #98: CI stamps `MAJOR.MINOR.<github.run_number>` into these fields before the build, without committing. A `vX.Y.Z` tag build uses the tag's version. MAJOR.MINOR stay in the repository. FR-18 (About and the log show the version) and the Telegram caption then show the stamped version.

## Acceptance

- [ ] A CI build on `main` or `wip/**` builds the installer, the exe's `CARGO_PKG_VERSION` (About, log start line) and the Telegram caption with the version `MAJOR.MINOR.<run_number>`, where MAJOR.MINOR is taken from the repository version. Two consecutive runs give different, increasing versions.
- [ ] A `vX.Y.Z` tag build uses `X.Y.Z`.
- [ ] Failure branch: a malformed repository version, or a tag that is not `vX.Y.Z`, fails the stamping step with a message naming it. The build does not continue with `0.1.0` or a mixed version: the three fields agree, and the existing caption check (`_<version>_` in the installer name) still holds.
- [ ] The Windows smoke shows the installed exe reports the stamped version (startup log line).
- [ ] Docs: `docs/decisions/ci-toolchain.md` (how the version is stamped) and the README/quickstart if it mentions the version.
- [ ] Test that fails without the change: named in `## Tests` (e.g. a `make check` fixture test of the stamping script).
