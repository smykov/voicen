## Context

From T-056 review round 1 (#2): T-056 (`deploys: false`, `surface: none`) gets no verify record, so "the GitHub time is recorded at verify" had no owner. The gate job does not cache `target/`, so `make check-shell-windows` builds cold on every CI run (locally 131 s, the spike 214–372 s), and the Windows job waits for the gate. Read the first CI runs after T-056 is pushed (`gh run view <id> --job <gate> --log`), record the measured cold time of the `check-shell-windows` step in `docs/decisions/ci-toolchain.md`, and decide (with the numbers) whether to add a `target/` cache to the gate job (actions/cache keyed on Cargo.lock + rust-toolchain + the image digest) or keep it cold. Any ci.yml change keeps F-001/F-002 rules (no `--doc`/rustdoc steps).

## Investigation

**Frame.** Observed: since T-056 (decision #66), `make check` runs `check-shell-windows` (Makefile:53-54, two `cargo check -p voicen --target x86_64-pc-windows-gnu` invocations) cold on every CI gate run. The gate caches only the cargo registry (ci.yml:28-35), not `target/`. The windows job `needs: gate` (ci.yml:40), so every gate second delays it. Expected: ci-toolchain.md records the GitHub cold time and a reasoned cache decision. Today it says "not measured yet" (:125, :172). This is a measurement and a config decision, not a defect.

**Hypotheses.**
1. The cold step is a large share of the gate, so a cache pays. Refuted: about 98 s of a 439-597 s gate (16-18 %). The larger uncached items are the image build (135-151 s), check-core (~100 s cold) and e2e (~95 s).
2. A `target/` cache is cheap. Refuted: the repo's Actions cache is at its limit (10.51 GB, 10 entries, `gh api repos/smykov/voicen/actions/cache/usage`), and the windows rust-cache's 2 GiB entries take 49-127 s to restore and up to 341 s to save.
3. The proposed key (Cargo.lock + rust-toolchain + image digest) gives hits. Refuted: the image is rebuilt from an unpinned `rust:1.99-bookworm` with `apt-get update`, so the digest changes on every run (sha256:3566742141d7 vs sha256:a5d0d2ae9e3a). The repo has no `rust-toolchain*` file.
4. A warm cache can hide a type error. Not proven either way in CI. By mechanism it is unlikely: cargo fingerprints path packages (voicen-core, voicen) by dep-info mtime against source mtime, and checkout gives the sources a newer mtime than restored artifacts, so both crates are always re-checked. Only third-party artifacts would be reused. Moot under the recommendation.
5. A second path / the class was fixed before. The windows job caches with Swatinem/rust-cache@v2 (ci.yml:52), which is a separate runner, target and key. docs/failures.md has no cache or CI-time entry, and the ci-toolchain class F-001/F-002 is about links and starts, not cache. **Recurrence: none.**

How the columns were measured:
- "~total" runs from the recipe's echo line to the next recipe's echo line, so it includes docker start and teardown.
- The windows job's step times are its own.
- In the windows job, Swatinem restore took 49-127 s and its post save 0-341 s (the save runs only on a key change).
- Actions cache, as of 2026-10-06: four `v0-rust-windows-*` entries of 1.60-2.13 GiB, plus registry and pnpm entries, 10.51 GB in total.

Under a warm cache the gnu deps (tauri, aws-lc-sys's mingw C build) would be reused and voicen-core and voicen re-checked. T-056 measured a warm re-check at 3-5 s after a shell edit, on a local 6-core host. So the saving per run is at most about 85-95 s, before the restore of a ~1 GB `target/` (gnu target plus host build scripts, per T-056).

**Root cause.** The question is open only because T-056 had no verify step to own the GitHub measurement, and the cache was never costed against the repo's cache quota or the per-run image digest. Nothing contradicts this.

**Invariant / seam.** As in the analysis block. The edit is docs-only, in `docs/decisions/ci-toolchain.md`, plus a `docs/decisions.md` row.

**Options.**
- **(A) Keep cold. Recommended.**
  - Record the table's summary: the cold time is 77-102 s, typically ~98 s, about 17 % of the gate, with run ids 37465516406 and 37245716605. Record the reasons: the cache quota is at its limit and eviction would hit the costlier windows cache; the key cannot hit; the ceiling saving is ~1.5 min of ~20-25 min wall time.
  - Risk: none to correctness.
  - Rollback: none needed.
- **(B) Add a `target/` cache**, keyed on `hashFiles('docker/rust.Dockerfile','Cargo.lock')` with restore-keys.
  - Needs the Acceptance failure-branch demo: a branch with a planted shell type error and a warm cache, gate red.
  - Risks: eviction of windows rust-cache entries; restore and save time eating most of the saving; artifacts from a different apt/mingw image build being reused (cargo does not fingerprint the C compiler's package version).
  - Rollback: delete the step.
- **(C) Cache the toolchain image** (buildx `type=gha` layer cache or a prebuilt published image).
  - Targets the larger 135-151 s; cargo-about's build alone is 83-107 s.
  - The same quota concern applies to a gha layer cache, and a prebuilt image needs registry setup.
  - Out of scope; a candidate follow-up task if the owner wants a faster gate.

**Owner decision?** The numbers point one way (A), so it is not a genuine toss-up. The developer records it in ci-toolchain.md, and the orchestrator adds a `docs/decisions.md` row: was "T-058 decides", decided "keep cold", by agent recommendation, ratified by the owner. It becomes an owner call only if the owner wants ~1.5 min per push enough to accept the quota risk, or wants (C) opened.
