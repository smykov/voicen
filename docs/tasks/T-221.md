## Context

From follow-up T-146 r1#1 (Medium, correctness), owner's grouping 2026-11-17: `Drop for PassQueue` waits for the whole running pass instead of cancelling it; a shell drop on exit hangs, while FR-028 expects the pass to restart at next start — cancel in drop with a test, or have T-147 never drop the queue (crates/voicen-core final_pass.rs:1630).

## Acceptance

- [ ] Dropping a `PassQueue` with a running pass returns promptly (cancels the pass), and the pass is picked up again at the next start (FR-028).
- [ ] Failure branch: a pass blocked in its engine call, then drop → drop dispatches nothing more and returns when the in-flight requests answer (bound: the engine's request timeout, FR-24; decisions #307), verified by a core test with a blocking fake engine.
- [ ] Test that fails without the change: `queue_tests::dropping_the_queue_with_a_running_pass_cancels_it_and_the_next_start_queues_it_again`

## Investigation

Tools: Serena (`get_symbols_overview`, `find_symbol` over `call/final_pass.rs` and `final_pass/queue_tests.rs`); grep for docs, `src-tauri` call sites and `docs/failures.md`. Serena line numbers are 0-based; the `file:line` above are the 1-based lines confirmed with Read.

**Frame.** Observed: `PassQueue::drop` (final_pass.rs:1646-1657) sets `closing`, clears `queued` and joins the worker. The running pass gets no cancel, so `work` only sees `closing` after `runner.run` returns, i.e. after the whole pass (for an hour-long call, many minutes). Expected (follow-up T-146 r1#1, FR-028): a drop ends the running pass promptly, and that call runs again at the next start.

**Hypotheses.**
1. *Drop never touches the token.* Confirmed: there is no `cancel()` in Drop, although `Slots.running` carries the token (final_pass.rs:1512-1518) and `PassQueue::cancel` (1604-1621) already uses it.
2. *The shell drops the queue at exit, so exit hangs.* Refuted for the current code. `start_calls` (src-tauri/src/call.rs:292-329) `app.manage`s the `Arc<PassQueue>` and gives a clone to `ShellCallShell` inside the managed `CallSession`, which the `call-requests` worker also holds. The process ends with tao's `process::exit` after `RunEvent::Exit` (decisions/windows-shell.md:19, decisions/dictation-session.md:99), so no `Drop` runs at app exit. The only real drop in the shell is the `start_calls` error path (`spawn_worker` failing, line 318-325), where the queue is idle and Drop returns at once. So T-147's option "never drop the queue" already holds; it should be written down there, not built.
3. *Cancel ends the pass at once.* Refuted. `Run::drive` (1034-1086) checks the token before each dispatch and on each answer, but the requests run on `std::thread::scope` threads, and the scope joins them. A cancel therefore takes effect only when the in-flight `transcribe_timed` calls return. For the real engine that is bounded by the per-request HTTP timeout (FR-24; decisions/call-final-pass.md item 4 says so: "may wait for in-flight HTTP up to the FR-24 timeout"). For a fake engine that blocks forever it is unbounded. `TimedTranscriber::transcribe_timed` takes no cancel argument.
4. *Second path.* None. Every pass goes through `PassQueue` (decisions/call-final-pass.md, queue invariant). `cancel` is the only other path that ends a running pass, and it already sets the token.
5. *Fixed before.* No. `docs/failures.md` has no `call-final-pass` entry (the decisions doc says first sighting) and no worker-join / exit-hang class. The closest sibling is `DictationSession`'s Drop (decisions/dictation-session.md "Drop lets the job in flight finish ... and joins both threads"): it deliberately joins, and it is also not on the exit path.

**Restart after a cancel or exit (FR-028).** Both ways already lead to a requeue:
- A cancelled pass writes `meta.json` back to `ready-to-transcribe` with the results it started with (final_pass.rs:1217-1220, Q1).
- A hard exit leaves `transcribing`.
- `CallStore::recover` (storage.rs:455-465) queues `ready-to-transcribe` and turns `transcribing` back into it. Pinned by `queue_tests::a_redo_cut_off_mid_pass_restarts_at_the_next_start_for_the_same_track_only` and `the_calls_of_the_start_up_queue_run_oldest_first`.
- The shell does not call `recover` yet (grep `recover(` / `Recovery` in `src-tauri/src`: no match). That is T-147's scope, not this task's.

**Bounding a pass blocked in the engine.** Cancel-then-join returns when the in-flight requests answer. The worst case is three concurrent requests, each bounded by its own FR-24 timeout. A fixed bound regardless of the engine is possible only by not joining: wait on `changed` with a timeout until `running` is `None`, then drop the `JoinHandle`. The trade-offs:
- the detached pass still writes `meta.json` and logs `final_finished` later;
- a new `PassQueue` over the same store (a test, or a future restart of the call part) can then run a second pass on that folder, breaking the one-pass-at-a-time invariant;
- the runner's ports (`Arc`s) stay alive after the queue is gone, the hazard the dictation-session Drop invariant names.

At process exit none of this matters, because Drop does not run there.

**Existing tests.** No `queue_tests` test drops a queue with a running pass: every test opens the gate and calls `wait_idle` first, or never starts a pass. So none pins the waiting behaviour and none has to change. `PureRunner` ignores its token, so a test that panics mid-way still waits up to 20 s on the gate during teardown. That is unchanged by option A, and harmless.

**Root cause.** Drop treats "closing" as "stop taking new work" and never asks the running pass to stop, so it waits for the full pass. The exit-hang symptom cited in the follow-up cannot happen in the current shell; the defect is in core's Drop contract.

**Recommended exit / scope.** One seam (`PassQueue::drop`), small. One open point, which the owner decides (`decides_on`): acceptance bullet 2's "within a bound while blocked inside the engine call" needs option B (detach), which conflicts with two recorded invariants. Option A gives "no further dispatch, returns when the in-flight requests answer (FR-24 bound)". Recommended: A, with bullet 2 reworded.

**Tests to write first (option A).**
- `queue_tests::dropping_the_queue_with_a_running_pass_cancels_it_and_the_next_start_queues_it_again`. Red today: the token is never set, so `wait_for("the cancel token")` times out.
- `queue_tests::drop_while_the_engine_call_is_blocked_dispatches_nothing_more_and_returns_when_it_answers`. The failure branch: the dropper thread has not returned while the gate is shut, the token is set, and after `gate.open()` it returns with exactly 3 requests sent and no transcript.
- Under option B, the second test would instead be `drop_returns_within_the_bound_while_the_engine_call_never_returns`: the gate is never opened, and a bounded poll on the dropper's flag is used (no clock read).

**Docs in the same commit.** The `PassQueue` doc comment ("Dropping it lets the running pass end"), the queue_tests header lines 22-23, a Drop item under "Queue, cancel and Transcribe again" in docs/decisions/call-final-pass.md, and a note in T-147 that the shell never drops the queue (managed state + `process::exit`).
