## Context

CI run 37783297296 (wip/T-020 @ 6d32613, Linux gate) failed only in `crates/voicen-core/tests/openai_client.rs:778` `no_failure_contains_query_key_or_transcript`: "invalid host: Err(CannotReach { host: \"voicen-test.invalid\" }), expected Err(NetworkUnavailable)". T-020 did not touch `failure.rs`, `send_error` or the client builder (moved unchanged to `engine::http`); the same binary's `invalid_host_is_network_unavailable` passed on the same host in ~0.1 s.

Developer's probe (T-020, throwaway): in reqwest 0.13.5 `connect_timeout` wraps the whole connector, DNS included; when the lookup outlasts it the error is `is_dns=false, is_connect=true, is_timeout=true` and `classify` returns `CannotReach`. The failing test finished ~3.7 s after the previous one, consistent with a lost UDP query and the glibc 5 s retry against the test's 2 s connect timeout. So the `.invalid` tests assume the resolver answers within `Timeouts.connect`.

Same family, seen repeatedly under host load: `tests/api_pipeline.rs` `blackhole_connect_is_bounded_by_connect_timeout` (e.g. 1.78 s vs a < 1.5 s bound) and `configured_api_timeout_fails_the_job_with_timeout` (T-020 local runs).

Open for the analysis: whether the fix is test-only (a connect timeout longer than the resolver retry for `.invalid` cases, like `refused_timeouts`; looser bounds) or a contract decision on how a DNS lookup that times out is classified (FR-017/FR-13 wording); check `tests/local_server.rs` for the same `.invalid` timing.

## Acceptance

- [ ] The `.invalid` cases in `tests/openai_client.rs` (and any in `tests/local_server.rs`) do not depend on the resolver answering within the connect timeout
- [ ] The blackhole / configured-timeout bounds in `tests/api_pipeline.rs` hold under the documented host load, or the tolerance is justified in the test
- [ ] The ±0.5 s wall-clock cases in `tests/post_process_timeout.rs` (T-020 r1#4) hold under the documented host load, or the tolerance is justified in the test
- [ ] Failure branch: with the resolver blackholed (`TW_DOCKER_ARGS="--dns 192.0.2.1"`), both `.invalid` cases still give `NetworkUnavailable` (the resolver budget outlasts the OS retry), and the `unresolvable_host()` probe fails loudly as an environment problem when the lookup does not fail within its budget. Which reason a lookup cut off by the connect timeout gives is moved to T-079 (OQ-22)
- [ ] Test that fails without the change: the two `.invalid` cases under `--dns 192.0.2.1` (red today with `CannotReach{voicen-test.invalid}`)

## Investigation

**Frame.** Observed: in CI run 37783297296, `no_failure_contains_query_key_or_transcript` got `CannotReach{voicen-test.invalid}` where `NetworkUnavailable` was expected. Under host load, these overran their bounds: `api_pipeline` blackhole (1.78 s against < 1.5 s), `configured_api_timeout`, `post_process_timeout` ±0.5 s and T-046 `api_test_uses_the_forms_api_limit` (6.33 s against 5.9 s). Expected: each test decides only what it names. Context tools: Serena was not available in this session (no `mcp__serena__*` tools), so I used grep and file reads over `crates/voicen-core/{src,tests}`. For reqwest I read the 0.13.5 source in the cargo registry cache (`.teamwright/cache/core/_usr_local_cargo_registry`), not context7. `.invalid` occurs only in `tests/openai_client.rs`, at 2 call sites. The `api.example.com` hosts in `local_server.rs::local_settings` and `diag_pipeline.rs` are never contacted.

**Hypotheses.**
1. The lookup outlasts the connect timer and is classified by the timer's flags. **Confirmed** (below).
2. Fixed wall-clock margins are smaller than the variance of host-load overhead in the timed window. **Confirmed** (below).
3. A second path, outside `engine::http`, builds its own client. **Partly true.** `local_models::download` builds its own `Client::builder().connect_timeout(...)`, so it has the same DNS-under-timer behaviour (FR-27 path, `SourceUnreachable`). No `.invalid` test exists there, so it is out of this flake. It matters for option (b).
4. This class was fixed before. **Yes, in shape.** F-005 / T-048: a deadline below the Windows refusal time decided the reason. Its invariant (`docs/decisions/core-tests.md`, "Every deadline on a refused path leaves the Windows refusal time") was scoped to refused addresses only, so the resolver path was left open. `recurrence_of` is empty; the orchestrator decides whether this widens the class `windows-refused-connect-timing` into "deadline races an OS answer".
5. A regression from T-020. **Refuted.** `http::client` and `send_error` are unchanged since T-040, and the failure reproduces on the current main with no diff.

**Evidence.**
- reqwest 0.13.5: `async_impl::ClientBuilder::build` calls `connector_builder.set_timeout(config.connect_timeout)`. `connect::ConnectorService::call` wraps `connect_with_maybe_proxy` (DNS, TCP, TLS) in `with_timeout`, which yields `error::TimedOut`. `Error::is_dns` looks only for `DnsError`, which is created only when the resolver itself returns an error (`dns::resolve::DynResolver::call`). So a lookup cut off by the timer has no dns flag.
- Repro (no code change, voicen-rust:1.99, `TW_DOCKER_ARGS="--dns 192.0.2.1"`, prebuilt test binaries):
  - `invalid_host_is_network_unavailable`: `left: Err(CannotReach { host: "voicen-test.invalid" })`; the single test took 20.18 s.
  - `no_failure_contains_query_key_or_transcript`: `invalid host: Err(CannotReach { host: "voicen-test.invalid" }), expected Err(NetworkUnavailable)`, the CI message.
- Throwaway probe (deleted, not committed), raw `reqwest::blocking`:

  | DNS | connect | error at | flags | then `drop(client)` |
  |---|---|---|---|---|
  | normal | 2 s | 0.17 s | dns, connect | 2 ms |
  | blackholed | 2 s | 2.11 s | connect, timeout (chain: Connect → "operation timed out") | **18.0 s** |
  | blackholed | 30 s | 20.13 s | dns, connect (EAI_AGAIN) | 1 ms |

  The drop waits because `blocking::InnerClientHandle::drop` joins the runtime thread, and the runtime's drop waits for the getaddrinfo task in the blocking pool. `OpenAiCompatibleEngine::send` and `post_process::chat::send` drop the client before they return. So today a dictation against a resolver that does not answer returns after the resolver's full retry (about 20 s with glibc), not after the connect setting. That is a product finding beyond the flake. Windows' GetAddrInfoW schedule was not measured here.
- Client build (`Client::builder().connect_timeout(..).build()`, debug build):
  - The cost per build: a thread, a current-thread runtime, and `rustls_platform_verifier::Verifier::new` → `rustls_native_certs::load_native_certs` (the whole CA bundle) on every call.
  - Sequential: 64–247 ms.
  - 8 in parallel: 147–407 ms with the host at load average ~5 on 6 cores, and 95–781 ms with 4 other test binaries running.
  - Every timed window includes it: `openai_client` (`transcribe` → `send`), `api_pipeline` and `local_server` (`Harness::run` → `run_job`: VAD, WAV, client build, request, drop), `post_process_timeout` (two clients per job), and T-046 `connection_test::run`.
- Bounds under load (the same container ran openai_client, local_server, api_pipeline, post_process_timeout and the probe concurrently, 3 rounds). This load is heavier than one `make check`, which runs binaries one after another. The "documented host load" in the Acceptance is not quantified anywhere in `docs/`.
  - `configured_post_processing_timeout_delivers_the_raw_transcript` failed in 2 of 3 rounds: "took 5.55 s against a 1.81 s baseline: 3.74 s", and "took 7.75 s against a 0.46 s baseline: 7.29 s". A single cold baseline sample inflates or deflates the stage.
  - The api_pipeline and local_server bounds held in these 3 rounds; the reported 1.78 s blackhole run is T-020's.
- T-046's 6.33 s against a 5.9 s ceiling: the window is the whole of `connection_test::run`, a 5 s deadline plus overhead that includes a client build. The fixed 0.9 s margin is the same class (2). It is not class (1): a loopback mock involves no DNS.

**Root cause.**
- (1) The `.invalid` assertions assume the system resolver answers within `Timeouts.connect` (2 s), because reqwest times the lookup as part of connect. A lost answer turns the result into CannotReach.
- (2) The timing assertions use fixed margins of 0.4–1.5 s over a window whose overhead (per-call client build with CA parse and thread, drop, VAD, WAV) varies by more than that under host load. Single-sample baselines amplify the variance.

Both explain every reported symptom. Contradicting evidence: none. The stage of 7.29 s exceeds what client-build variance alone explains; it shows scheduler starvation under my heavier-than-gate load, which only strengthens (2).

**Is the fix test-only?**
- Test-only for the flakes, yes, in either option below.
- The Acceptance line "a slow or lost DNS answer maps to a documented FailureReason" needs a **contract decision**. `contracts/openai-transcription.md` names both "DNS failure → NetworkUnavailable" and "connect not established in 5 s → CannotReach", and a lookup cut off by the connect timer satisfies both. `classify` cannot tell it apart from a blackholed connect: the flags are identical to the `192.0.2.1 connect_timeout` row.
- Decision #51 already maps every DNS failure in "Test connection" to CannotReach, so this question concerns dictation (and post-processing) only.

**Draft OQ for the owner.** A DNS lookup that gets no answer within the connect timeout (Wi-Fi up but no internet, a dead resolver) currently fails the job as "cannot reach <host>". The job also returns only when the OS resolver gives up (about 20 s on Linux; Windows not measured), not at the connect setting.
- (a) Keep CannotReach{host}; document the row in the contract and in `classify_table`. The wall-clock overrun becomes its own bug task.
- (b) NetworkUnavailable: `engine::http::client` gets a reqwest `dns_resolver` that runs the system lookup off the tokio blocking pool and gives up at the connect deadline with a DNS error (`is_dns`). Routes through the same seam: the engine, the chat post-processor, and `local_models::download`'s own builder (its reason is `SourceUnreachable`, so its mapping must be checked). The job then ends at the connect setting. This is a new product task (`deploys: true`, Windows CI proof). Risk: a detached lookup thread lingers until the OS resolver returns. Rollback: drop the resolver, back to (a).
- (c) Leave it unspecified; this fails the Acceptance.

Proposal (agent): **(b)**. "Network unavailable" is the truthful reason when nothing answers DNS, it matches FR-11's "network off → network unavailable", and it restores FR-24's connect bound.

**Approach (recommended for T-078, test-only; product change only via the OQ answer).**
1. `tests/common/mod.rs`:
   - `RESOLVER_BUDGET`, above the worst system retry: glibc 2 attempts × 5 s with A and AAAA = 20 s measured; Windows must be checked in CI.
   - `resolver_timeouts()`: connect = budget, total = 2 × budget, the same pattern as `refused_timeouts`.
   - `unresolvable_host()`: probes `voicen-test.invalid:80` with `ToSocketAddrs` and panics loudly as an environment problem when the lookup does not fail within budget / 2.
   - Both openai_client `.invalid` cases use them. Exhaustive-destructure test as for `refused_timeouts`.
   - Red/green: the `--dns 192.0.2.1` run above, red today and NetworkUnavailable after the fix (slow, about 20 s, but correct).
2. Timing bounds: lower side = the deadline minus timer slack (a deadline never fires early). Upper side = below the nearest wrong-deadline bite (for example the 7 s server answer, the 30 s/60 s defaults, the 3 s total in blackhole), with the overhead allowance written in the test. Where the bite is close, move it: larger server delays such as 10 s instead of 7 s. In post_process_timeout, take the baseline as the minimum of 2–3 runs, or bound the stage against the bites instead of ±0.5 s. T-046 applies the same rule on its own branch (delay 6 s → for example 9 s, ceiling below it).
3. Pin (Acceptance line 4): a `failure::classify_table` row "DNS lookup cut by the connect timeout (connect+timeout, no dns; T-078 probe)" plus the contract row, for the reason the owner picks. Under (b) the product task adds the end-to-end pin with an injected never-answering resolver.
4. Update `docs/decisions/core-tests.md`: widen the F-005 invariant to "a deadline never races an OS answer". Add an F-entry. Not chosen: a local resolver stub (needs `--dns` or a resolver seam in production code; heavier than the budget for a test-only fix).
