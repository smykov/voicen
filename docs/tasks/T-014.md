## Context

FR-19 (default off). Owns the `Autostart` trait, the autostart step of T-003's save transaction and `reconcile` (spec 004 T056–T058; decision #21).

## Acceptance

- [ ] On → HKCU Run entry present; off → absent
- [ ] Startup reconciles the Run value with the saved setting (on → written with the current exe path, off → removed; no call while `Unavailable`), through `load_settings` (J4) — Windows CI
- [ ] Failure branch: registry write refused → save refused as a whole (Q1), old state kept — verified by a core test with a failing fake `Autostart`
- [ ] Test that fails without the change: `crates/voicen-core settings::service::tests::autostart_failure_refuses_and_changes_nothing` (and the reconcile tests); `src-tauri/tests/autostart.rs` (Windows CI)

Scope (decision #35): the General-tab toggle with its Playwright case (spec T059), "logon start opens no window (tray only)" and the owner's real-logon check moved to T-034.

## Investigation

**Frame.** Expected (FR-19, spec 004 FR-019, US5): on → a per-user logon start entry; off → none; a write or remove failure refuses the whole save (Q1); at logon the app starts tray-only. Observed: `start_with_windows` is a plain field. `save` stores it in `settings.json` and nothing reaches Windows. This is a need, not a defect, so no reproduction applies. Recurrence: `docs/failures.md` has only F-001 (Windows CI link); class `autostart` has no earlier tasks or commits (`git log -- docs/tasks/T-014.md`: planning commits only). `recurrence_of: []` stands.

**Where I looked.** For Rust I used grep and file reads, as instructed (Serena indexes TypeScript only). I read `crates/voicen-core/src/settings/{service,mod,gate}.rs`, `src-tauri/src/{lib,settings_ipc,credentials,paths}.rs`, `src-tauri/{Cargo.toml,tauri.conf.json}`, `.github/workflows/ci.yml`, spec 004 (spec, research R-3/R-5/R-10/R-11, data-model, core-traits, tasks T056–T059), spec 006 (uninstaller removes the Run value, value name owned by 004), and decisions #9, #19, #21, #23, #34. For the `windows` crate I read the 0.62.2 source in `.teamwright/cache/core/.../windows-0.62.2` rather than Context7: these are generated Win32 bindings, so the version in the lock file is the authority. `grep -rni autostart` over crates, src-tauri, src, i18n and e2e finds only the existing field, FieldId, ErrorCode and the ignored `launched_by_autostart` parameter.

### Settled design

**1. Trait (core, `crates/voicen-core/src/autostart.rs`; contract shape kept).**
- `Autostart: Send + Sync { fn is_enabled(&self) -> Result<bool, AutostartError>; fn set(&self, enabled: bool) -> Result<(), AutostartError>; }`
- `is_enabled` = a value with the release (or test) name exists in the HKCU Run key, whatever its data.
- `set(true)` always writes the current command, so it is idempotent and also fixes a stale path. `set(false)` deletes, and an absent value is `Ok`.
- `AutostartError { os_code: i32 }` mirrors `CredentialError`. It never carries the exe path, which contains the Windows user name.
- `ReconcileAction { None, Written, Removed, Failed }` with `as_str()` = `none|written|removed|failed` (R-11; T-008 logs it).

**2. Save step (R-3 step 3; data-model state machine).**
- Position: after the hotkey placeholder (`service.rs:311`), before the keys (`:313`), so after `validate` and after T-010's future `prepare`.
- The step runs only when `settings.start_with_windows != snapshot().start_with_windows`. The snapshot is read under `save_lock`. T056 says "applied only when changed". This also keeps unrelated saves working when the Run key cannot be written.
- On failure: `Refused { errors: [FieldError(general.start_with_windows, autostart.failed)], form_error: None }`, with no key or file touched. Once T-010 lands, its prepared hotkey is aborted here.
- Undo: `set(old)`. Order, in reverse of the steps: keys in reverse slot order, then autostart, then (T-010) the hotkey abort.
- Double failure: if `set(old)` fails, `PartiallyRestored.not_restored` includes `general.start_with_windows`. Fields are listed in step order: autostart first, then the key fields in slot order.
- Follow-on doc and catalog updates:
  - `FormError` doc and `core-traits.md` "naming exactly the key fields" → "the fields".
  - `docs/decisions/settings.md` I2 gains the autostart step.
  - `settings.partially_restored` en/ru text currently says "some API keys". It must become "some settings ... check the highlighted fields".
- `Unavailable`: no autostart call (#19); the existing test is extended.

**3. Reconcile (`SettingsService::reconcile_autostart(&self) -> ReconcileAction`, under `save_lock`).**
- `Unavailable` → `None` with no Autostart call. The in-memory defaults say off, and acting on them would delete the entry of a user whose real file merely could not be read (#19 by analogy).
- Snapshot on → `set(true)` (refreshes the path) → `Written`, or `Failed` on error.
- Snapshot off → `is_enabled()`:
  - `false` → `None`.
  - `true` → `set(false)` → `Removed`, or `Failed`.
  - `is_enabled` error → `Failed`.
- `FirstRun` and `Reset` reconcile from the defaults, so a leftover entry is removed. This matches the settings window, which shows the option off ("rewritten from the settings file", R-3/R-5).
- Reconcile never touches the file or the credential store.
- The shell calls it inside `settings_ipc::load_settings`, right after `load_or_init`, so the release app and the tests share it (J4).
- Known limit kept (R-5): a value disabled in Task Manager (`StartupApproved\Run`) is not overridden.

**4. Fake (`FakeAutostart`, `test-fakes`).**
- In-memory `enabled` state: `new()` = off, `enabled()` = on.
- Call log `AutostartCall::{IsEnabled, Set(bool)}`, failed calls included.
- Injectable failures: `fail_set(value: bool, err)` per value, so `set(true)` can succeed while the undo `set(false)` fails; and `fail_is_enabled(err)`. A failed `set` leaves the state unchanged.
- `World`, `fs_deps` and `tests/settings_apply.rs` construct it (3 core `SettingsDeps` sites, plus `settings_ipc.rs:45`).

**5. Windows impl (`src-tauri/src/autostart.rs`, `#[cfg(windows)]` like `credentials`).**
- `WinAutostart::new()` uses `RUN_VALUE_NAME = "Voicen"`, the one constant. The 006 NSIS hook must use the same literal; note it in 006's contract.
- `with_value_name(n)` is for tests, so a dev machine's real value is never touched.
- Subkey `Software\Microsoft\Windows\CurrentVersion\Run` under `HKEY_CURRENT_USER`. Data is `REG_SZ` UTF-16 with a terminating NUL counted in `cbdata`: `"<current_exe>" --autostart` (quoted path, `AUTOSTART_ARG`).
- Calls: `RegSetKeyValueW`; `RegDeleteKeyValueW` with `ERROR_FILE_NOT_FOUND` → `Ok`; `RegGetValueW` with a null buffer for `is_enabled`. In 0.62.2 all three return `WIN32_ERROR`, not `Result`.
- `std::env::current_exe()` failure → `AutostartError`.
- Feature: add `"Win32_System_Registry"` to the existing `windows = "0.62"` target dependency. This adds no new crate (#9 consent, 0.62.2 already locked). Run `make licenses` to confirm the notices are unchanged.
- To check against the Win32 docs during implementation, not from memory: whether `RegSetKeyValueW` creates a missing subkey. The Run key exists on every profile, so this affects only an error branch.
- `launched_by_autostart(args) -> bool` (`--autostart` present) is defined here. T-004's startup executor passes it to `startup_action`, which already returns the same action with or without it (`gate.rs:62`, US5-3).

**6. Red tests.**

Core (Linux gate, `settings::service::tests`, next to the existing transaction tests):
- `autostart_failure_refuses_and_changes_nothing`: the Acceptance failure branch, and the test named by the "fails without the change" line.
- `autostart_applied_only_when_changed`: on → `[Set(true)]`; the same value again → no call; off → `[Set(false)]`; an invalid draft → no Autostart call.
- `key_failure_restores_autostart`: `[Set(true), Set(false)]`, fake off, `key.store_failed`.
- `file_write_failure_restores_keys_then_autostart`: undo order asserted across both fakes' logs.
- `autostart_undo_failure_reports_partially_restored`: `not_restored` = `[general.start_with_windows]` (plus key fields when those fail too).
- `save_refused_while_unavailable`: extended so the autostart log stays empty.
- `reconcile_autostart_*`:
  - on + absent → `Written`.
  - on + present → `Set(true)` called, `Written`.
  - off + present → `Removed`.
  - off + absent → `None`, no `Set`.
  - `Unavailable` → no call.
  - `set` or `is_enabled` error → `Failed`.
  - No file or credential call in any case.

Windows CI (`src-tauri/tests/autostart.rs`, run by the existing `cargo test -p voicen` step):
- `set(true)` writes `"<test exe>" --autostart` as `REG_SZ`.
- `set(false)` removes it, and runs twice → `Ok`.
- A stale value written directly is rewritten by `set(true)`.
- `RUN_VALUE_NAME == "Voicen"`.
- Through `load_settings` + `build_app` (mock runtime) with `with_value_name(test)` and a TempDir data dir:
  - `settings_save` on → value present; off → absent.
  - A `settings.json` with on + absent value → present after `load_settings` (reconcile).
- Each test removes its own value.
- The registry-refusal branch stays a core fake test, as the Acceptance says. Forcing an ACL refusal on HKCU Run in CI is not needed.

Install smoke (`ci.yml`, after the first-run check): set `start_with_windows: true` in the installed `settings.json`, launch `voicen.exe --autostart`, and assert that `HKCU\...\Run\Voicen` equals `"$env:LOCALAPPDATA\Voicen\voicen.exe" --autostart`. Then set false, relaunch, and assert the value is absent. This proves reconcile in the deployed app.

### Acceptance "Logon start opens no window (tray only)"

This cannot be met or verified from this seam today:
- `tauri.conf.json:13-19` declares a static window that opens at every start, logon included. R-10 replaces it with the on-demand `settings` window, created by T-004's startup executor (spec T025). `run()` drops the load outcome (`lib.rs:82`).
- No tray exists until T-006 (T-001 is `BLOCKED`).
- `startup_action` already gives `TrayOnly` for `Loaded` regardless of `--autostart`. So "no window at logon" is the same behaviour as "no window at any `Loaded` start". It belongs to T-004 (executor) plus T-006 (tray), not to the flag.

How it can be verified once those land:
- Windows CI, after T-004: launch the installed exe with `--autostart` and a readable `settings.json`, wait, and assert the process has no visible top-level window (`MainWindowHandle -eq 0`, or `EnumWindows` + `IsWindowVisible`).
- After T-006: assert the tray icon. There is no enumeration API for it, so this is the owner's check.
- A real logon from the Run value: owner manual only (SC-007, spec T066).

If T-014 shipped before T-004, a user with the option on (reachable only by hand-editing, since no toggle exists yet) would get the 800x600 window at logon. That is harmless, but it is not the Acceptance.

### Verification and `surface`

- `surface: ui` needs a `kind: ui` record (gates.md, verify gate 3). A manual record does not replace it.
- The only Playwright case is the General-tab toggle and the `autostart.failed` highlight (spec T059, `e2e/settings-save.spec.ts`). Both need T-004's settings route and IPC mock (spec T013). So as written, T-014 cannot reach `VERIFIED` before T-004.
- The current `verify_exception` covers only the real-logon manual record, and it needs the owner's acceptance (sessions.md:87).
- Under option B, the core+shell part is `surface: none`, `deploys: true`. A `smoke` record suffices (the install-smoke Run-value check above, plus the Windows CI tests as gate proof), and no `verify_exception` is needed for it. The exception moves to the follow-up together with the owner's reboot check.

### Options

- **A. Keep T-014 whole** and add `depends_on: [T-004, T-006]`. One task, one verification (Playwright + owner reboot). It waits behind the blocked T-001 → T-006 chain, and its core and shell parts sit idle.
- **B (recommended). Narrow T-014** to core + shell (sections 1–6): `surface: none`, `deploys: true`, `verify_exception: ""`. Acceptance: the on/off Run value (Windows CI + install smoke), the failure branch (core fake), and the red test above. A follow-up task, depending on T-004 and T-006, takes spec T059 (toggle, `error.autostart.failed` en/ru, Playwright refusal highlight; `surface: ui`) and "logon start opens no window, tray only" (CI no-visible-window check + owner reboot under a `verify_exception`). Alternatively, these go into the Acceptance of T-004 and T-006 directly.
  - Why it removes the need: every path that changes the setting (save, startup) goes through the one Autostart seam now. The UI part is only a view of an existing field.
  - Risk: low. Default off means reconcile makes no OS write for existing users (`is_enabled` read only).
  - Rollback: revert the commit, then delete the `Voicen` Run value if it was written (reconcile no longer runs).
- **C. Core only** (trait, step, reconcile, fake; `deploys: false`), with the Windows impl in a shell task. Rejected: the trait has exactly one impl and one call site, and the T-030 precedent split a much larger shell. Splitting here adds a review round for about 100 lines.

**Seam-sized?** Not as written: core service, Windows shell, UI tab (needs T-004), and startup window/tray (T-004/T-006). Narrowed to option B, yes. One concern, Autostart, covering its trait, its one Windows impl and its one startup call. This matches the size of T-032 plus a thin T-030 slice.

### Questions for the owner / orchestrator

- **Q1. Blocks the start of implementation.** Choose A or B. B changes Acceptance, `surface` and `verify_exception` and creates a follow-up (or extends T-004/T-006). By precedent (#23, #34) the orchestrator can decide this under the owner's 2026-10-03 instruction. The decision gets a `docs/decisions.md` row.
- **Q2. Does not block implementation; blocks `VERIFIED` of whichever task holds the logon check.** The owner accepts the `verify_exception` for the real-logon manual check (SC-007 / spec T066).
- **Settled here, not owner-level** (follow R-3/R-5/#19):
  - Reconcile is a no-op while `Unavailable`.
  - `Reset`/`FirstRun` remove a leftover Run value.
  - The step runs only when the value changed against the snapshot.
  - The `settings.partially_restored` wording becomes "settings", not "API keys".
- **Routing note.** `error.<code>` messages (spec T044) have no owning task (grep over `docs/tasks`). The UI cannot show the `autostart.failed` reason until someone owns them. This concerns T-004 or the follow-up, not this seam.

**Coordination.** T-010's hotkey step goes before this step, and its `prepare` must be aborted on an autostart failure and in the undo chain. T-010 should read this section when it is analysed. 006's uninstaller hook deletes `RUN_VALUE_NAME` (`Voicen`).
