## Context

FR-09, FR-24 (15 s), NFR-11; clarifications Q1–Q4 of spec 003. The `post_process::settings` data type, `STARTER_PROMPT` and its defaults come from T-003; the key is read with `CredentialStore::read(KeySlot::PostProcessing)` (decision #21). Reuse T-040's client setup, `classify` and the `authorization()` key rule — no second HTTP client or `bearer_auth`.

### Design notes the spec assumed differently (settled by existing decisions, not open)

1. **Sync, not async.** Spec 003 contracts use `async fn process` and `tokio::time::timeout`; decision #42 (OQ-05 (a)) made engines synchronous with blocking reqwest. reqwest 0.13.5 blocking carries the request-level `timeout` into the response body as `TotalTimeoutBody`, so `.connect_timeout(timeouts.connect)` + `.timeout(timeouts.post_processing)` bounds connect to last body byte (same mechanism T-040 measured for transcription). No tokio in the product path.
2. **One client, no new role on the engine.** `OpenAiCompatibleEngine` is an `Engine` (audio → text); a chat request is not a third `Endpoint` variant. Extract crate-private helpers in `engine/openai.rs` — `authorization(Option<&Secret>)`, `client(connect)`, `endpoint_url(base, &[..])` (the same `pop_if_empty().extend()` join that keeps a query), the 1 MiB capped read — and call them from both `OpenAiCompatibleEngine::send` and `ChatPostProcessor`. The existing `tests/openai_client.rs` is the regression proof for the refactor. Fix the stale header line in `engine/openai.rs` ("for T-020's connection test": the connection test is FR-14, not this task) in the same commit.
3. **Reason mapping** via `failure::classify` then `FailureReason → SkipReason`: `InvalidApiKey` (401/403, unusable key) → `InvalidKey`; `NetworkUnavailable` and `CannotReach` → `Unreachable { host }` (spec US2-2: DNS → "cannot reach"); `Timeout` → `Timeout`; `ServerError{status}` → `Http{status}`; `UnexpectedResponse` and an empty-after-trim / non-string `choices[0].message.content` → `InvalidResponse`. Host from `host_port(base)` only. `KeyStoreUnavailable`/`EngineNotConfigured` cannot come out of `classify`.
4. **Key read error = no key** (spec Edge Cases, data-model, research R5) — deliberately unlike transcription's decision #44 (`KeyStoreUnavailable`). Spec-settled; noted so the reviewer does not "fix" it toward #44. Key read happens only when `enabled` (FR-002/NFR-05).
5. **Ordering (FR-23)** holds by construction: the session's one FIFO worker runs `run_job` serially (decision #48); a 15 s stage delays later jobs, which spec 003 Edge Cases accept.
6. **Redirects:** default policy (≤10, `Authorization`/`Cookie` removed when host, port or scheme differ — `redirect.rs` `remove_sensitive_headers`). A wiremock test can show it with two servers on 127.0.0.1 with different ports. Residual (not in the Acceptance, same as the transcription engine today): a cross-host 307/308 re-sends the body (prompt + transcript) to the other host, and a reply from the redirect target is used. Changing that means `redirect::Policy` in the shared client setup, which also changes the transcription engine — orchestrator's call, not this task.
7. **Tests follow core-tests.md (F-004, F-005):** refused cases use `common::refused_addr()` + `refused_timeouts()`; the timeout case uses a server that accepts and stays silent. Research R8's "bind, drop, reuse the port" and "non-routable 10.255.255.1" must not be used.
8. **Log:** `docs/decisions/diagnostics-log.md` says one dictation is one line and `LogEvent` fields are closed enums. Spec 003's separate `post_process outcome=… duration_ms=…` line would contradict that; the fit is a closed `pp=applied|skipped|off` + reason tag + `pp_ms` on the dictation line (new `DictationEvent` fields, exhaustive `LogObserver`, `diag_format.rs` grammar, `diag_pipeline.rs` redaction run). That is the diag seam; spec puts it in Phase 5 (T026), and T-021's Context does not take it. Recommend a follow-up task or an explicit addition to T-021; no change needed for T-020's Acceptance. Today a skipped job logs as `outcome=text`, with no text, so no leak.

### Size

As written (`design_ref` Phases 1–4) the task is **large**: (1) post_process + the shared HTTP helpers, (2) the pipeline stage, (3) the recording controller's `JobEnd`/tray rule, (4) the catalog, plus (5) `src-tauri` wiring (spec T012), (6) the toast via T-007's notifier (spec T021; T-007 is TODO, no toast exists in the shell), (7) a Playwright overlay test (spec T020; low value since the overlay text is rendered in core), and two unsettled behaviours (below). It already has a spec (spec-kit 003), so it does not need the spec tool again; it needs a **split** and two decisions.

**Recommended narrowing** (matches the current Acceptance, `surface: none`, `deploys: false`): T-020 = items (1)–(4), all in `crates/voicen-core` plus `i18n/{en,ru}.json`, proven on Linux. That is one vertical change to the one pipeline stage; the `JobEnd` change is the extension of 001's notice channel that spec 003 lists under "Extended (owned elsewhere)". Items (5) and (6) go to a new Windows follow-up task (depends on T-020 and T-007; waits on OQ-14); (7) is replaced by a core `overlay_payload` / `job_finished` unit test; the log fields go to a follow-up (note 8).

### Changes outside `crates/voicen-core`

- **`src-tauri` — yes, eventually, and held under OQ-14:** `src-tauri/src/dictation.rs` `start_dictation` must install `ChatPostProcessor` instead of `PassThrough` (and update its module doc) or the feature never runs in the app. `src-tauri/tests/{hotkey,tray}.rs` keep `PassThrough`. With `PassThrough` kept in core and only `PostProcessor`'s signature changed in core, `src-tauri` compiles unchanged, so T-020 itself needs **no** `src-tauri` edit.
- **`i18n/en.json`, `i18n/ru.json` — yes:** the five `notice.post_processing_skipped.*` ids (texts in `contracts/ipc.md`) plus their `messages!` constants in `i18n.rs`; core `i18n::tests` (parity, `message_ids_exist_in_both_catalogs`) pin them. Plus one id if open question 1 is answered (a).
- **`src/` UI — no:** the overlay renders core-built text; no UI code reads a post-processing notice (toast is shell-side, T-007). The settings tab and privacy note are T-021.

### Open questions (not settled by spec 003 or decisions)

1. **Enabled but unusable stored config.** Save-time validation for post-processing does not exist until T-021 (`settings/validate.rs` checks nothing while enabled; `settings/service.rs` comment "a malformed or empty one is saved"), and a hand-edited `settings.json` bypasses save anyway. With `enabled: true` and a base URL that fails `check_base_url` (empty, malformed, userinfo), no request can be built and none of Q1's five reasons fits. Options: (a) a sixth reason `not_configured` → "Post-processing skipped — not set up. Check the Post-processing settings." (en/ru), raw delivered, tray error — extends the owner-confirmed closed list of Q1, so **owner decision**; (b) map to `InvalidResponse` (wrong text); (c) `NotRun` silently (violates "notify skipped", FR-003). Proposal (agent): (a). Empty model/prompt with a valid URL: send as stored, the provider's 4xx gives `Http{status}` (no new rule). In every option no key is read before the URL check (as `engine_for`).
2. **One overlay slot, two notices.** With auto-paste off every delivery carries `notice.copied`; a missing start window or failed Ctrl+V carries `notice.copied_paste_manually` (`delivery.rs` `DeliveryResult::notice`). A skipped post-processing on such a job has two messages for one 3 s overlay slot. Options: (a) skip notice on the overlay, tray Error; the copy notice is lost; (b) the delivery notice on the overlay (the user has to act on it), the skip shown by tray Error (and by the toast once T-007 exists); (c) one combined message id per pair. Proposal (agent): (b) for `copied_paste_manually`, (a) for `copied` (auto-paste off is the user's own setting, so "copied" is no news). UX choice → orchestrator decides whether it needs the owner.
