## Context

Split from T-004 by decision #38 (T-004 analysis, option A). The shell decides the startup action (`settings::gate::startup_action` over the `LoadOutcome` that `run()` keeps as `_load_outcome`, src-tauri/src/lib.rs) but never carries it out, and `tauri.conf.json` opens a static `main` window at every start. This task adds `src-tauri/src/settings_window.rs` with `open(tab, field)` as the only way to create the `settings` window (at most one; a second `open` focuses it and emits `settings://focus`), the startup executor on `RunEvent::Ready` in `run()` as a function the tests call directly, `app.windows: []` in `tauri.conf.json`, and the capability moved to the `settings` label (event listen, `core:window:allow-destroy`). Findings from the T-004 analysis: tauri checks every `plugin:*` command against the window label; destroying the last window exits the app unless prevented (`prevent_exit` belongs with T-006's tray — until then closing the first-run window ends the app, accepted interim, #38); `setup` never runs from `build_app`. Shell tests follow the layout rule (#36/#37: only `src-tauri/tests/*.rs`). The `outcome=` log line is T-008's. The page side of `open(tab, field)` (focus from `?field=` / `settings://focus`, the discard prompt) is T-039's (decision #40).

## Acceptance

- [ ] Windows CI: `OpenSettings(Engine)` from a FirstRun outcome creates exactly one `settings` window at `settings?tab=engine`; `TrayOnly` (Loaded) creates none; a second `open` leaves one window and emits `settings://focus`
- [ ] The `settings` window may listen to `settings://changed` and close itself (capability check); no window is created from `tauri.conf.json`
- [ ] Install smoke: first launch shows a visible settings window; a launch with a loaded settings file shows none
- [ ] Failure branch: a startup outcome of `Unavailable` opens the window (with `unavailable` set in the view) and no save succeeds — Windows CI test over `load_settings` with an unreadable file
- [ ] Test that fails without the change: `src-tauri/tests/settings_window.rs` (Windows CI) and the install-smoke window check

### Mock runtime: what tests can and cannot do (tauri 2.12.1)

- **Window creation works without the event loop.** `MockRuntime::create_window` inserts the window synchronously and keeps the URL in the dispatcher (`mock_runtime.rs:1228-1290`; `url()` at :620). `show`, `unminimize`, `set_focus` and `is_visible` are no-ops returning `Ok`. Existing harnesses already build `settings` windows on `build_app`'s mock app (`tests/settings_ipc.rs:47-53`).
  - `WebviewUrl::App(p)` resolves to `app_url.join(p)` (`manager/webview.rs:469-486`), so the query survives. Tests should assert path `/settings` and the query pairs, not the origin: it is `http://tauri.localhost` with `mock_context`, and devUrl `http://localhost:1420` with `generate_context!` in a debug build.
- **Events can be asserted synchronously.** `emit_to(label, …)` filters by `AnyLabel`. A Rust `app.listen_any` handler (target Any) always matches and runs inside the emit call (`manager/mod.rs:582-626`, `event/listener.rs:208-233`), so tests need no timeout. JS listeners registered with `listen` (target Any) in that webview receive it too (`listener.rs:309-334`).
- **Do not call `.run()` in a test.** `MockRuntime::run` sends `Ready` and then loops with a 1 s sleep until the last window closes (`mock_runtime.rs:1353-1420`). With `TrayOnly` it never returns. So `on_ready` must be a plain function the tests call with `app.handle()`. Only the install smoke proves that `run()` actually calls it.
- **Close and destroy cannot be tested in the mock.** While not running, `destroy` removes the window from the mock map only (`mock_runtime.rs:84-97`). Tauri's manager drops it only from the run callback (`on_window_close`, `manager/mod.rs:640`), so "closed, then open creates a new window" cannot be tested here. Do not write that case.
- **ACL in tests.** `mock_context` carries an empty `Resolved` (`test/mod.rs:143`), so every `plugin:*` call is refused there. `generate_context!(test = true)` expands to `fn inner<R: Runtime, …>() -> Context<R>` (codegen `context.rs:455-470`). It reads `capabilities.json` and `acl-manifests.json` from `OUT_DIR` (:377-410), which cargo sets for every target of a package that has a build script, integration tests included. It also exposes `config().app.windows`.
  - This lets one test check "no config window" with the tool's own parse of `tauri.conf.json`, and check the capability through the real ACL path (`webview/mod.rs:2077-2107`; debug builds reject with "… not allowed on window \"settings\" …").
  - Not yet compiled on Windows. If `generate_context!` does not build in a test exe, the fallback is to parse `tauri.conf.json` and `capabilities/default.json` with serde_json in the test. That is weaker, because it reads JSON, not tauri's resolution.
- **Where the window is created.** Tauri itself builds config windows in `setup()` on `RuntimeRunEvent::Ready`, immediately before the user's Ready callback, on the same thread (`app.rs:1442-1447`, `2688-2694`). Building the `settings` window in the Ready callback is therefore the same context. The WebView2 deadlock note (`webview_window.rs:58, 115`) is about sync commands and webview event handlers, not about this callback.

### Settled shapes

- **`open(app, tab, field)`:**
  - If `get_webview_window(LABEL)` exists: `unminimize`, `show`, `set_focus`, then `emit_to(LABEL, "settings://focus", FocusRequest { tab: tab.as_str(), field })`, with `field` omitted when `None` (contracts/ipc.md:39 `field?: FieldId`).
  - Otherwise: `WebviewWindowBuilder::new(app, LABEL, WebviewUrl::App(format!("settings?tab={}{}", tab.as_str(), field.map(|f| format!("&field={}", f.as_str())).unwrap_or_default()).into()))` with `.title("Voicen")` and `.inner_size(800.0, 600.0)` (the old config values). It is destroyed on close (the default).
  - Tokens are closed sets of `[a-z_.]`: the six tab tokens from contracts/ipc.md and `FieldId::as_str`. No URL encoding is needed.
  - `SettingsTab::as_str` belongs beside the enum in core `settings/gate.rs`, with a wildcard-free match and a core test pinning the six tokens. That file is not touched by the parallel T-040 work. `post_processing` is not a tab on the page yet, so the page falls back to Engine (`initialTab`, `src/routes/settings/+page.svelte:36-39`). Settings for it come with T-021.
- **`on_ready(app, &outcome, launched_by_autostart)`:** it calls `startup_action` and then `open(tab, None)` or does nothing. It makes no decision of its own (spec T025, gate.rs:62).
  - The Reset and Unavailable notices are already shown by the page from `SettingsView.reset_notice` / `unavailable` (T-004). The toasts are T-006's.
  - `run()` moves the outcome into the run closure. Ready fires once.
- **Capability (`capabilities/default.json`):** `"windows": ["settings"]`, and a description naming the settings window. Two choices for permissions:
  - Least privilege, recommended: exactly what the page and T-039 call. `core:event:allow-listen` and `core:event:allow-unlisten` cover `listen` in `settingsApi.ts`, the `settings://focus` listener, and `onCloseRequested`, which is a `listen` on `tauri://close-requested`. `core:window:allow-destroy` covers `onCloseRequested` calling `this.destroy()` (`@tauri-apps/api` window.js:2028-2036). Neither `core:window:default` nor `core:event:default` includes destroy.
  - Or keep `core:default` and add `core:window:allow-destroy`.
  - App commands (`settings_get`, `settings_save`, …) are not ACL-checked: there is no app ACL manifest (`webview/mod.rs:2077`).
  - With no `main` window left, the old `main` entry is dead and goes.
- **Unavailable branch:** a directory at `settings.json`, as in `tests/autostart.rs:364`. Then `load_settings` → `Unavailable` → `on_ready` → one window at `tab=engine`. `settings_get` from that window → `unavailable: true`. `settings_save` → `Refused` with form `settings_unavailable`. The data dir is unchanged. Core already pins the refusal (`service.rs` `read_io_error_is_unavailable`), so this test proves only the shell route.
- **Install smoke (ci.yml):**
  - **First-launch step:** add `$win` to the poll loop condition, as `$p = Get-Process -Id $proc.Id -ErrorAction SilentlyContinue; $win = $p -and $p.MainWindowHandle -ne 0 -and $p.MainWindowTitle -eq 'Voicen'`. Use a fresh `Get-Process` each poll, or `$proc.Refresh()`, because `Process` caches the main-window state. Fail with `no visible Voicen window after the first launch`.
  - **Loaded launch** (the `off` relaunch in the T-014 step, or a new step): wait for the start line, then sample for 10 s. Fail on the first non-zero `MainWindowHandle` with `a window is visible on a launch with a loaded settings.json`.
  - **Why `MainWindowHandle` works here.** .NET picks a top-level, unowned window with `WS_VISIBLE`. tao's hidden event-target window has no `WS_VISIBLE`, and WebView2's windows are child windows or belong to other processes (msedgewebview2.exe). So no `Add-Type`/`EnumWindows` is needed. `IsWindowVisible` reads the style bit, so the check holds even if the runner's desktop is not interactive. That is my reasoning, not something observed yet: the first CI run confirms it.
  - **Why the two checks bite as a pair.** Today the first-launch check passes because the static window also shows. The Loaded check is red today. After the change, removing the executor turns the first-launch check red, and putting a config window back turns the Loaded check red.
  - **Flakiness.** The visible check polls up to 30 s, like the other checks. The `none` check is a bounded negative: no positive "Ready reached" marker exists, because the start line is written before the load and the `outcome=` line is T-008's. It can therefore only give a false pass for a window slower than 10 s, never a false fail.
  - specs/006 `contracts/installer-ci.md` (windows row, failure texts) changes in the same commit.
- **Docs in the same commit:**
  - `docs/decisions/settings-ui.md` (S1 as an invariant);
  - `docs/architecture.md` (startup: `on_ready` → `settings_window::open`; the shell row);
  - `contracts/installer-ci.md`.
