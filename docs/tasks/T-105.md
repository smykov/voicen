## Context

Spec 006 FR-003 asks for the OS version on the first log line of every primary session. T-008 shipped `Started { build, pid }` without it; `data-model.md` planned `os: OsVersion` for T-024, whose analysis (`decides_on` (b)) moved it out: it changes the closed log grammar and every start-line matcher, and no T-024 Acceptance line needs it. Moved here by decision #140. T-024 already builds `OsVersion` (shell `RtlGetVersion`) for `SessionStart` and crash files.

Touch points named by T-024's analysis: `crates/voicen-core/src/diag/event.rs:24` (`Started`), `tests/diag_support`, `diag_format.rs` (start-line format test), `src-tauri/tests/diag.rs`, `src-tauri/tests/single_instance.rs`, the `ci.yml` start-line greps. Append `os=` after `pid=` so the `started pid=<n>(\D|$)` matchers keep matching.

## Acceptance

- [ ] `Started` carries `os: OsVersion`; the line reads `voicen <version> (<commit>) started pid=<n> os=<major.minor.build>`
- [ ] Every start-line matcher (core tests, shell tests, `ci.yml`) still matches; the install smoke checks `os=` on the installed app
- [ ] Failure branch: the OS version cannot be read → the line is still written, with a closed placeholder chosen in the analysis (no free text), verified by a core test
- [ ] `specs/006-diagnostics-and-release/data-model.md` and `contracts/core-diag.md` say `os` ships with T-105 (shipped)

## Investigation

**Tools.** Serena's Rust language server failed to start (`find_referencing_symbols` on `LogEvent/Started`: "language server manager is not initialized … LanguageServerTerminatedException"). The orchestrator may need to run `serena project index` or restart the server. Context therefore came from grep and sed over `crates/`, `src-tauri/`, `.github/workflows/ci.yml`, `scripts/ci/`, `docs/` and `specs/006-*`. No library API is involved (`RtlGetVersion` is already wired by T-024), so Context7 was not needed. No Rust was run: the change is additive, and every claim below about a matcher comes from reading its text.

**Frame.** Spec 006 FR-003 asks for the version, commit, OS version and start time on the first line of each primary session. The line shipped today has the version, commit and time, but no OS version: `voicen <v> (<c>) started pid=<n>`. Decision #140 moved `os` here from T-024.

**Hypotheses.**
1. The field is missing from the closed event, so no producer can write it. Confirmed: `event.rs:24` and `format.rs:225-233`.
2. A second path writes a start line. Refuted: `LogEvent::Started` is built only by `src-tauri/src/diag.rs:35` (`diag::start`) and by core tests. The crash-file `os:` line (`crash.rs:348`) and the session marker are separate grammars. The marker has no `os` and is not touched.
3. Some matcher anchors on `pid=<n>` at the end of the line. Confirmed for three: `diag_format.rs:881` (`ends_with`), `src-tauri/tests/diag.rs:215` (exact equality) and `diag_support/mod.rs:538/561` (closed key set). All other matchers search a substring or end at a non-digit; see the table.
4. This class was fixed before. Refuted: `docs/failures.md` has no `diag-log-grammar` (or `diagnostics-log`) entry. The nearest precedent is T-076, which added `pp=`/`pp_reason=`/`pp_ms=` to the dictation line, extended the closed sets in `diag_support` and caused no failure. Recurrence: none. Separately, T-060 holds a review follow-up (T-024 r5#1) that would rename `class: diag-log-grammar` to the existing `diagnostics-log` class (T-008, T-023, T-076). That is a metadata decision for the orchestrator; this analysis does not change it.

**Guard paths.** No byte-exact owned fragment holds start-line text. I searched `scripts/ci/*.yml`, `action-lines.txt` and `cache-steps/` for `started` and `os=`: no hit. The two matchers under `scripts/ci/` already tolerate the suffix, so the change needs no staged path under `scripts/ci/` or `scripts/licenses/` and no `Makefile`/`*.mk` change. The pre-commit guard trigger (#155) does not fire, and `checker: false` holds. The new install-smoke check goes into an inline `ci.yml` step that no fragment pins (the step around `:244`). It must not contain the word `uses`, any action name or `secrets.TELEGRAM_`. If the developer instead puts the check into `crash-records.ps1` or a new `scripts/ci/*.ps1`, the task becomes `checker: true` with `decides_on`. That is not recommended.

**Placeholder for the failure branch (OS version unreadable): `os=0.0.0`, named `OsVersion::UNKNOWN` in core.** Reasons:
- It is already the shipped failure value of the only OS-version source: `src-tauri/src/win/crash.rs:61-82` returns `0.0.0` when `RtlGetVersion` fails, and so does the non-Windows adapter at `src-tauri/src/diag.rs:177`. The same session's `crash-*.txt` / `abnormal_end` files and native-fault head already write `os: 0.0.0`, so the log line and the crash files agree with no second convention.
- It is closed and has no free text: the grammar stays one form, `u32.u32.u32`. `diag_support` checks one value shape, and no alternation is needed in core tests or CI.
- It cannot collide with a real value: Windows 10/11 report major 10, and no NT release reported major 0. The install smoke rejects it explicitly (major >= 10, build > 0).
- The cost: a reader must know that `0.0.0` means "unknown". It is documented in `contracts/core-diag.md` and `docs/decisions/diagnostics-log.md`, and named by the const rather than repeated as a literal.

Rejected alternatives:
- `os=unknown` with `Option<OsVersion>`: the log would disagree with the crash files unless `CrashFields.os`, `render_crash_file` and `NativeFaultWriter`'s pre-rendered head change too. That widens the task into the crash grammar.
- Omitting `os=` on failure: FR-003 wants the OS version on every start, and the grammar would need an optional key.

`RtlGetVersion` cannot be forced to fail on the runner. The failure branch is therefore proven by a core test that formats and writes `Started { os: OsVersion::UNKNOWN }`, plus both adapters returning the const. The Windows proof covers the success path only.

**Size.** One seam, small: core `LogEvent::Started` + `format::write_message` + the test grammar, and one shell producer (`diag::start`, signature unchanged). It touches no new service, no IPC, no UI and no stored state, so it does not need Spec Kit. The Windows side is one changed shell test expectation and one install-smoke assertion. `diag::start` and `diag::begin_session` each call `os_version()` (two `RtlGetVersion` calls per start, same value). Passing one value through both would change `diag::start`'s signature and its ~20 test callers for no behavioural gain, so it is not recommended.

**Red test first:** `diag_format.rs` `started_line_carries_version_commit_pid_and_os` (the updated `ends_with` assertion and `pairs == [pid, os]`) and `started_line_with_an_unreadable_os_version_writes_the_placeholder`. Both fail to compile or fail on main, because `Started` has no `os`.
