- **Ordering.** `on_run_event(Ready)` posts Ready's `request` synchronously, and only then does `run_with_driver` spawn the driver. The opener is one `mpsc` queue read by one thread. So the driver's `request_with` probe is always queued behind Ready's open, and its receipt can only answer after `open` has returned. Tauri attaches the window before `build()` returns, so `get_webview_window(LABEL)` is a fact once the probe answers. The opener writes `settings_window_failed` before Ready's job's `done.send`, so the log read after the probe is complete. That is stronger than the old read taken at the budget.
- **Failure branches still red.** If Ready never posts (no `OpenSettings`), the probe answers at once with no window, so the test is red. A failed build is red, and its `settings_window_failed` line is in the log. A missing opener gives `Disconnected` → `Some(Err)` → no window → red. A hung build is held by `OPENER_HANG` 120 s, which is under `WATCHDOG` 180 s.
- **Bite.** All three planned mutations of the helper settle by reading: a probe off the queue, a hang bound below 25 s, and a hard-coded `true` (caught by `window_after`). Each turns the new test red because the open is held 25 s. No assertion was removed or loosened; the old assertion moved word for word into `assert_opened_on_ready`.
- **Second paths outside lifecycle.rs.** Every other `get_webview_window(LABEL)` and `wait_timeout(BUDGET)` site is in a MockRuntime test (`settings_window.rs`, `tray.rs`, `single_instance.rs`, `hotkey_registrar.rs` via `win32_support::AppRig`, `local_models.rs`). None of them builds a WebView2 window, so they are not this class. The only Wry users are `overlay.rs` and `overlay_ipc.rs` (already deferred) and lifecycle.rs itself (#1).
