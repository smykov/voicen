### What exists vs what is absent, per Acceptance line

- **A1, every reason → message and indicator; a newer failure replaces the pending recording: mostly built.** `FailureReason::message_id` covers every variant, as `every_reason` and `message_ids_per_reason` show. `RecordingController::job_finished(Failed)` sets `error = true` and `show(reason.message_id(), reason.message_params())`, and `fail` does the same for capture failures. Replacement is `Pipeline::keep_pending`, pinned by `api_pipeline.rs::newer_failure_replaces_pending_and_deletes_old_audio`. Absent: no test runs every reason of `every_reason()` through `job_finished` to the indicator, and no rule covers a failed retry (it must keep the same id, not take a new one through `keep_pending`).
- **A2, Focus Assist: overlay "invalid API key" for 3 s and tray error.** The overlay and tray paths exist: `ShellIndicator` → `overlay::OverlayPart` (T-057's code is in the tree; T-057 itself is `DEFERRED`, absorbed by T-065) and `tray::TrayPart`. Focus Assist matters only because it hides toasts, which do not exist yet. This line is the owner's check after part 3.
- **A3, one hotkey id.** contracts/messages.md lists three ids for the one event: `failure.hotkey_unavailable` (toast + overlay + settings), `notice.hotkey_unavailable` (overlay, T-055) and `notice.hotkey_failed_startup` (toast, `{hotkey}`). `i18n/en.json` has only `notice.hotkey_unavailable`, raised in `DictationSession::hotkey_registration`. Recommendation: Q4.
- **A4, `notice.mic_fallback` as a toast.** It is raised with `st.ctrl.notice_with(NOTICE_MIC_FALLBACK, ...)` in `DictationSession::hotkey_pressed`, which goes through `show`. With the outbox (I1) it gets its toast with no code at that site.
- **A5, network off → Retry → delivered per FR-10; a failed retry keeps the audio.** Absent: no retry entry anywhere. `Pipeline`'s `Job` doc says "T-007 adds a second constructor". `PendingRecording` has no start window. The worker channel is `mpsc::channel::<Job>()` of `FinishedRecording<PressContext>` only. The controller's `queued` set is keyed by `RecordingId`, so a retry needs an entry there to show Processing. `tray::menu` drops `retry_available`. There is no toast. In the app nothing is ever pending (`NoPendingAudio`).
  - Delivery to the original start window: `delivery::deliver(text, auto_paste, start_window, ...)` already decides Pasted or CopyManual. The retry passes it the stored `StartWindow` and the click snapshot's `auto_paste`.
  - Speech gate: data-model "Retry" lists `NoSpeech` only as "the engine now returns empty text", and the audio already passed the gate at its first run. So the retry path calls the engine factory and skips `SpeechGate::decide`.
- **A6, cleanup never deletes under a calls root.** Absent: `NoPendingAudio::delete_all` is a no-op, and no file store exists (grep for `impl TempAudioStore` in `crates` and `src-tauri`: only the fake, the test `BlockingStore` and `NoPendingAudio`). The guard compares paths canonicalised where they exist, and lexically normalised and case-insensitively on Windows otherwise. It uses `symlink_metadata`, so it never follows a junction. The red test needs the equal and ancestor cases (see `approach`).
  - `put_pending` must leave no partial file on `Err` (from T-001 review round 1). Write `pending-<id>.wav.part`, then rename; on `Err`, remove the `.part`. The cleanup pattern includes `.part`, so a crash leftover is removed at the next start. `audio/wav.rs` is the existing encoder.

### Notes items

- **Dead worker, unwind builds (T-051 r1 #2).** Confirmed by reading:
  - `run_worker` has no guard around `pipeline.run_job(job)`. A panic ends the thread and drops `jobs`, the receiver.
  - `stop_recording` then queues with `let _ = queue.send(job)`, so the `Err` is dropped.
  - The controller has already counted the job in `queued`, so the overlay stays `Processing` and nothing is logged.
  - The session lock is poison-tolerant (`lock` uses `PoisonError::into_inner`), so the rest of the session keeps running.
  - Detection seams: a drop guard in `run_worker`, like `StopInFlight`, which marks the worker dead under the lock, clears `queued`, shows the notice and writes a log line; and the `send` result in `stop_recording`. No message id or `FailureReason` exists for this: Q1.
- **Release with `panic = "abort"` (T-051 r2 #5).** In `voicen.exe` a `run_job` panic ends the process. T-100's panic hook writes a `crash-*.txt`, and the next start's `Session::begin` gives the previous-session verdict (`docs/decisions/diagnostics-log.md`, "One record per abnormal session end"). FR-032 deletes the stale temp audio at that start, so the pending retry is lost by spec. The Open line in `docs/decisions/dictation-session.md` ("If `run_job` ever panicked ... no restart is built") is amended after Q2 is decided.
- **Logs-folder notice (T-071 r1 #3).** `logs_folder::request` → `open` → `warn` writes only `WarningKind::LogsFolderFailed`. Spec 006 FR-017 and contracts/ipc.md name the id `error.open_logs_folder` ("Cannot open the logs folder: {reason}"); it is not in `i18n/en.json`. Hook: in the `logs-folder` thread, on `Err`, call `DictationSession::notice_with(error.open_logs_folder, [reason])`. That thread is not the main thread, and the session lock is free there. `{reason}` maps the `io::ErrorKind` to the existing `logs_reason.*` nested ids, and the OS text is never shown. Surface: Q6.
- **Which settings snapshot a Retry uses (T-073 note).** Already decided, so it needs no owner question. Spec Clarification 4 and FR-027 say: "the settings current at the moment Retry is clicked (engine, base URL, model, key, language)". Timeouts are settings (decision #99) and are derived per job with `Timeouts::from_settings` from the job's snapshot (FR-018, `Pipeline::process`). A retry job carrying the click snapshot therefore uses the new limits with no extra code. The snapshot is taken on the input thread (`SettingsService::snapshot`, as at a press). The pending slot is read only on the worker, which keeps the dictation-session invariant "`retry_available` is the pending slot, read on the worker".
- **Duplicated hotkey id:** Q4.
- **Cleanup vs calls roots (OQ-80, decision #251):** I3 and A6 above.

### Constraints already decided that the developer must keep

- dictation-session.md: one FIFO worker is the only caller of `run_job` and `job_finished`; `Pipeline::pending()` is read only on the worker. The tray and toast Retry handlers therefore only enqueue: they never read the slot, and the worker checks the id. Indicator calls stay under the lock, and Notifier calls go outside it.
- `Indicator` and `ShellRequests` doc rules: no blocking, no callback into the session under the lock. The toast `Show` is a COM call, so the shell notifier posts to its own thread, like the overlay thread (`docs/decisions/overlay.md`).
- windows-shell.md: `on_tray_icon_event` and `on_menu_event` run on the main thread and never take the session lock, so Retry goes through `spawn_blocking`, like `tray_menu_opened`. It also records an untested risk: the menu is rebuilt while shown when `retry_available` changes during `TrackPopupMenu`. That becomes reachable with this task (windows-shell.md T-007 line).
- FR-20 / NFR-04 and P-009: no transcript, audio or key in the log or a toast argument. The toast argument is `retry:<id>` only.
- Spec 001 FR-029 / Clarification 3: a retry enters the order at the click, which the FIFO channel gives. T-011 (TODO) later replaces the worker with its delivery queue and has to carry the `Job` enum over.

### Toast activation (technical risk behind Q5)

research.md R-16 plans `CreateToastNotifierWithId(AUMID)` and an `Activated` handler. Microsoft's docs (context7, learn.microsoft.com "author-coclasses") say a desktop app's toast button reaches the app from Action Center only through a COM activator. That takes an `INotificationActivationCallback` registered with `CoRegisterClassObject`, `PKEY_AppUserModel_ToastActivatorCLSID` on the Start-menu shortcut, and `HKCU\Software\Classes\CLSID\{...}\LocalServer32`. The `Activated` event only covers a click on the popup while that toast object is alive. With Focus Assist on, a toast goes straight to Action Center, so an `Activated`-only design would fail exactly in scenario 6's setting. The installer's `CreateOrUpdateStartMenuShortcut` sets only `SetLnkAppUserModelId`. This is from documentation only; it has not been run on a runner.

- **Q5 (technical, Windows; owner if it changes the installer): how a toast's Retry reaches the app.**
  - (a) Recommended: a COM activator. `INotificationActivationCallback` registered with `CoRegisterClassObject` while the app runs; the NSIS hook writes `ToastActivatorCLSID` on the Start-menu shortcut and the `HKCU` CLSID `LocalServer32`. This works from Action Center, which is where toasts go under Focus Assist. A cold activation, with the app not running, just starts the app: the pending audio is already gone (FR-032), so nothing is retried.
  - (b) The `Activated` event only, as research R-16 plans. No installer change, but Retry from Action Center does nothing, and the tray Retry is the only working route under Focus Assist.
  - (b) needs an owner-accepted limitation of FR-027 ("retry from the failure notification").
- **Q6 (product, small): where the logs-folder failure is shown (spec 006 FR-017 "notify").**
  - Recommended: `error.open_logs_folder` ("Cannot open the logs folder: {reason}", `{reason}` a `logs_reason.*` id from the `io::ErrorKind`), on the overlay for 3 s and as a toast, through `DictationSession::notice_with`. This is the same path as `notice.logs_unwritable`, and the tray Error state does not change.
  - Alternative: a toast only.
- **Q7 (diagnostics, small): the log line of a retry.**
  - Today `diag::observer` closes a recording's record at its first `JobFinished`. A retry that reuses the original `RecordingId` writes a second `dictation` line for that id, without the recording-start fields.
  - Recommended: reuse the id. Check the line against `docs/decisions/diagnostics-log.md`, and add a closed `origin=retry` key if a reader needs to tell the lines apart.
  - The developer settles this with the reviewer, not the owner, unless the line format of spec 006 changes.
