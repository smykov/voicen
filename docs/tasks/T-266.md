## Investigation

**Frame.** Observed: in CI 45465360769, attempt 1, the call with a dictation had a mic track 1914 samples (48 kHz), about 39.9 ms, longer than the system track and the baseline. System, drops and device changes were equal. Expected: both tracks equal the call recorded alone. It reproduces only on Windows CI, at random. Attempt 2 and the main runs 45452515249 and 45529997012 were green.

**Tools.** Serena was loaded. The code was read with grep and file reads in the worktree (session.rs, capture.rs, wav_source.rs, call_shell_support/mod.rs, call_dictation.rs). The CI log came from `gh run view 45465360769 --attempt 1 --log-failed`: without `--attempt 1` the log is empty, because the re-run is green. Nothing was built or run locally (shell tests are Windows-only).

**Hypotheses.**
1. *A wall-clock pause plus the per-track feed order sets off the writer's D3 stall fill (confirmed).* Confirms if the extra length equals what `advance_to` + `place` produce for the last pump, and only the mic grows. Both hold to the sample, see below.
2. *The dictation shares or disturbs the call capture (a product defect, FR-009).* Refuted. A shared capture would show as a drop, a device change, or a system-track change. The meta has 0/0 and the system is equal to the baseline. The excess is the exact signature of the stall-fill path, and the dictation's audio port (`CountingAudio`) is a separate `RealtimeSource`.
3. *The sample count follows the wall clock through `pump_for`.* Refuted as stated in Context. `WavTrackSource::pump` has no clock: it pushes the blocks whose synthetic stamp is <= `START_MS + ms`. So the fed stamps are fixed (2020 ms per track). The wall clock enters only through the writer's `STALL` check on `Seen.last_event` (mono).
4. *The same concern on a second path.* Same exposure: `esc_during_a_dictation_discards_only_the_dictation` (`thread::sleep(SETTLE)`, 1 s, then `pump_for(PUMP_MS)`, then the same equality). `recorded_alone` is exposed only if the start-to-first-pump gap passes 500 ms. Other WAV-backed shell tests (call_chain, call_hotkey, call_ipc, call_launch, call_lifecycle, call_tray) use the same `pump`, but grep finds no other `duration_48k` / `read_tracks` assertion in `src-tauri/tests`. They get the fix without needing it.
5. *This class was fixed before.* Closest is F-031 / T-203: a writer drain-order effect, which T-203 left as a follow-up hypothesis: "a lane held off past `STALL` ... zero-filled by `Writer::advance` ... its real blocks then placed late and head-dropped". This sighting is that fill-and-late-blocks mechanism. It was demonstrated here, but set off by the test feed (one track's whole burst before the other's after a long pause), not by product overload or by drain order. T-239 refuted drain fairness for F-033 (a different mechanism). T-267 (same class `flaky-timing-test`) is a paint premise in call_indicator, a different mechanism. There is no earlier patch of this mechanism, so `recurrence_of` stays empty.

**Mechanism, step by step (the last pump of the failing test).**
- `pump_for(DURING_MS)` left both tracks at stamp 1520 ms (blocks 0..1500, 20 ms each, `with_block_ms(20)`). Then `thread::sleep(HOLD)` (1500 ms) and `assert_pasted` run: no track event for more than `STALL` (500 ms).
- `pump_for(PUMP_MS)` loops over `opened` in open order: system first (`open_tracks`: "Opens the system track, then the mic"). It pushes 25 system blocks 1520..2000 (`last_end` 2020), then 25 mic blocks.
- If the writer's round (`IDLE` 2 ms wake) runs `drain()` while the mic channel is still empty, it takes all system blocks. Mic is checked first, so it was empty and the system was drained. Then `advance()` runs: mic `last_event` is older than `STALL` → `advance_track(Mic, system.last_end = 2020)` → `Timeline::advance_to` fills zeros to 2020 - 200 = 1820 ms.
- The mic blocks at 1520..1760 have error < -40 ms: each block is dropped whole (`head = min(frames_for(-error), len)`). The block at 1780 has error -40 ms, which is not `< -STEP_SAMPLES`, so it is steered and placed. The rest follows: the mic ends at 1820 + 240 = 2060 ms.
- 2060 ms x 48 = 98880. Observed 98874: 2 samples at 16 kHz (6 at 48 kHz) of resampler position rounding. The system is 2020 ms = 96960, the same as the baseline. Difference 1914 = 3 x 638 = 3 x (`STEP_SAMPLES` 640 - 2).
- If the writer wakes after some mic blocks are queued, the mic's `last_event` is fresh before `advance()` and nothing is filled: green. That window is the flake.

**Root or symptom.** Root at the test seam. The product does what `docs/decisions/call-session.md` I9 says: a live track that delivered nothing for 500 ms of mono follows the other, 200 ms behind. A real WASAPI feed delivers both tracks in real time, so neither track gets a half-second lead in stamps after both went quiet. The harness's sequential feed creates that lead. The test's own rule ("compared with the same call recorded alone over the same pumps") holds only if the writer never sees one track ahead of the other by >= the hold-off.

**Recommended fix (option A).** `WavSource::pump_for` / `pump` step all opened sources together, 20 ms at a time, up to the target stamp. The lead is then at most one block, under `HOLD_OFF_SAMPLES` (200 ms), so `advance_to` cannot fill a live track whatever the wall pause. The red test is a feed-order test on `WavSource` (recording sink, max lead <= 20 ms), red today with a 1500 ms lead. The acceptance tests keep the exact equality, which still catches a drop, a gap or a device change (Acceptance 2). A wait longer than `STALL` before the pumps is optional: it makes the stalled-both state certain on every run.
