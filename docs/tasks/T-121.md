## Investigation

Tools: Serena loaded (ToolSearch select). `get_symbols_overview` on `crates/voicen-core/src/settings/gate.rs` worked; `find_referencing_symbols` for `second_launch_action` returned nothing (src-tauri is Windows-only and not resolved by the Linux language server), so callers were found with grep over `crates/` and `src-tauri/` for `launched_by_autostart`, `AUTOSTART_ARG`, `on_second_instance`, `SecondLaunchAction`, `LaunchArgs`, `CallSwitch`. No new library API (the plugin callback's `Vec<String>` argv and `std::env::args_os()` are already in use), so no context7 lookup.

**Frame.** Feature. Today a second launch is classified by one bool (`--autostart` anywhere in argv, exact match). Expected (FR-003, FR-043, #184): `--call record` reaching the running instance is a distinct decision `StartCallRecord`; an unknown `--call` value is refused without action; the pre-007 rows are unchanged.

**Hypotheses checked.**
1. *A second parser of the same argument*: today core never sees argv (the shell parses, core gets a bool). After the change the risk is a second `--call` reader in T-128's first-launch path; invariant I1 closes it (T-128 calls `LaunchArgs::parse(std::env::args_os())`). `win::purge::from_args` parses `--purge-credentials` separately, runs in `main` before `run()` and exits; the contract keeps it unchanged - a different argument, not a second path of this concern.
2. *Logging inside the callback*: the contract says "the primary logs `CallSwitchRefused`", while windows-shell.md forbids any side effect in the second-instance callback beyond posting one request and `on_second_instance`'s doc says it writes no log line. The only queue in the primary today is the settings opener (`settings_window::request`), the wrong owner. The event itself is T-118's (DONE; nothing writes it yet). Settled by #197: T-128 writes it.
3. *Behaviour change of `launched_by_autostart` through delegation*: the shell test pins exact, case-sensitive, any-position matching (`--autostart-later`, `--other`, empty argv). `LaunchArgs::parse` keeps any-position scanning for `--autostart` (argv[0] included, as today), otherwise the delegated fn changes meaning. The first proposal for `[exe,--call,--autostart]` (the value swallowed, autostart false) did change it: today's scan answers true, and installer-ci.md keeps `--autostart` unchanged. Corrected in I5 and the parse table; the action stays `TrayOnly` either way.
4. *Exhaustive match breaks*: `StartCallRecord` makes `tray.rs::on_second_instance`'s match non-exhaustive, so the shell moves in the same commit (Acceptance says so); proven only on the Windows `wip/T-121` run.
5. *Earlier fix of this class*: none; `docs/failures.md` (re-read 2026-10-31, keywords launch, instance, argv, autostart, `--call`) has no entry on argv or launch arguments, F-008 is about the smoke's window predicate, and class `call-launch` is new.

**Findings the developer needs.**
- Parse edges the spec leaves open (developer follows the approach's table, reviewer checks against I3 and I5): `--call` as last argument, `--call RECORD`, `--call --autostart`, repeated `--call`, `--call=record`. Only an argument exactly equal to `--call` is an occurrence, and only the first one decides. So `--call=record` is `None`: no recording, and a second launch fronts settings like any other unknown argument, with no refusal line. A later `--call bogus` does not undo `--call record`.
- `StartCallRecord` wins over the autostart `TrayOnly` row (contract). The Run value never passes `--call`, so no logon start records.
- `startup_action` / `startup_action_after_hotkey` keep their `launched_by_autostart: bool` parameter (the contract changes only `second_launch_action`); `release_launched_by_autostart` keeps working through the delegated shell fn.
- `on_second_instance` returns `Option<Receipt>`: `StartCallRecord` (no-op) and `Unknown` both return `None` until T-128.
- docs/architecture.md describes the old table in the start-order row ("core `second_launch_action`: `--autostart` opens nothing, otherwise `request(Front)`") and lists `on_second_instance` as a `launched_by_autostart` reader in the start-with-Windows row; update both in the same commit. docs/decisions/windows-shell.md never stated the table (Code line and Don't only), so it needs no edit; the earlier analysis was wrong on this.
- Handoff to T-128: `second_launch_action` gives `TrayOnly` for `Unknown`, the same as a plain `--autostart`, so the action alone cannot trigger the refusal line; T-128's callback reads `LaunchArgs.call`. T-128's Acceptance has no line for `call_switch_refused` (only its Notes, #197). #223 (T-122's menu rebuild) is about muda's flip on a click; a `--call` launch has no click, so it does not reach T-121.
- T-120 is DONE; its gate.rs changes are in the tree and do not touch this task's symbols. T-128 already depends on T-121.

**Decision (#197, owner, 2026-10-24).** T-128 writes `call_switch_refused reason=unknown_value`: one writer for first and second launch, inside its posted request; no callback exception; no T-118 dependency here. T-121's Acceptance line 2 already reads so. The alternative (`depends_on: [T-118]` and a windows-shell.md exception for one log write in the callback) is rejected. core-call.md's "the primary logs" still holds; the T014 wording in tasks.md ("logged ...") is met by T-128, not here.

**Re-check 2026-10-31 at 1f9c22e3.** Serena `find_referencing_symbols` on `second_launch_action` again returned nothing, so callers come from grep over the whole tree without docs/tasks, including scripts, Makefile and `.github`: no new caller, no guard or CI script names these symbols. Installer smoke passes `--autostart` only, no `--call` yet.

**Size.** Small: one core seam plus two mechanical shell call-site moves. Behaviour settled; the parse edges are fixed in the approach's table, subject to review.
