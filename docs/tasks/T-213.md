## Context

Second half of T-210, split off by the owner (decision #279). T-210 ships the shell toast notifier (toast thread, sink port, toasts without a Retry button), the core `PendingId` toast-argument codec, the tray Retry arm and the logs-folder notice. This task adds what makes a Retry button on the toast work. A desktop toast button with no activator does nothing, so the button lands only here.

The T-210 analysis is the starting point: `## Investigation` › Size ("New (toast Retry)"), "Seam details and residual risks" (NSIS COM write through `System::Call`, upgrade path in `NSIS_HOOK_POSTINSTALL`, test isolation of the per-process CLSID registration), and its invariants I6 (every Retry input reaches core only as `DictationSession::retry`; the toast argument is `retry:<id>` only, parsed by the one core codec) and I7 (every install leaves the shortcut's `ToastActivatorCLSID` and `HKCU\Software\Classes\CLSID\{C}\LocalServer32` pointing at this `voicen.exe`; every uninstall that removes the program removes both).

- COM activator: `INotificationActivationCallback` registered with `CoRegisterClassObject(CLSCTX_LOCAL_SERVER, REGCLS_MULTIPLEUSE)` on T-210's toast thread; `Activate` copies the args, stamps the instant and hands off with `spawn_blocking` to `session.retry(at, Some(id))`. A stale or malformed id runs nothing.
- The toast gets the `action.retry` button only when the offer carries `retry = Some(id)`.
- `LaunchArgs` reads `-Embedding` as a no-window second launch (TrayOnly). A cold activation (app not running) only starts the app: the pending audio is gone by FR-032.
- Installer: `installer-hooks.nsh` only (the fork diff stays unchanged; no line with the token `rmdir`). One CLSID: a Rust const and one `!define` in the hooks, pinned equal by a shell test.
- FR-20 / NFR-04: the toast argument is `retry:<id>` only; no OS text in logs.

### Frame

- **Observed.**
  - T-210's toast shows one text line with no button. `ShellNotifier::notify` drops `_retry`, and `toast_xml` builds no `<actions>`.
  - Nothing can call back into the app: no activator, no CLSID, no installer write.
  - `voicen.exe -Embedding` as a second launch is parsed as a plain launch. `second_launch_action` then returns `FrontSettings`, which opens a window.
  - The "Transcript ready" toast cannot carry Open, because `Notifier` has no way to express it and `call::offer` passes `None`.
- **Expected.**
  - Spec 001 US2 / FR-027 (Retry from the toast, also from Action Center under Focus Assist, #274 Q5 (a)).
  - Spec 007 FR-030 ("Transcript ready" with "Open", which opens the call in the Calls window).
  - The Acceptance above.

### Hypotheses

1. **Missing feature (confirmed).** No activator, no button, no `-Embedding`, no installer CLSID. Grep for `CoRegisterClassObject`, `INotificationActivationCallback`, `ToastActivator`, `Embedding` and `CLSID` in `src-tauri/`, `crates/` and `src-tauri/windows/` finds only doc comments naming T-213.
2. **The same concern on a second path (checked).** Messages reach `ShellNotifier` from two places: core's session outbox (`dictation.rs` `Locked` drop, with `retry`) and the shell's `call.rs` (`serve` for refusals, `offer` for `ShellCallShell` and `ShellPassEvents`), plus `win/hotkey.rs` (call hotkey conflict, `None`).
   - The button concern therefore has two sources: Retry from the outbox and Open from `CallNotice::TranscriptReady`.
   - Both must arrive as one typed action through the one `notify` parameter, so `win/toast.rs` stays the only place that builds a button. Option B (a second notifier method for call notices) was rejected for this reason.
   - There is one activation path only if no `Activated` event handler is ever attached. With a registered activator and the shortcut's CLSID, Windows routes both the popup click and the Action Center click to `Activate`.
3. **Stale id across processes (confirmed by reading; not run).**
   - `Pipeline::build` sets `last_pending_id: AtomicU64::new(0)`, and `keep_pending` hands out `fetch_add(1) + 1`. So every process's first pending id is 1.
   - FR-032 deletes the old audio at start, but the old toasts stay in Action Center: desktop toasts persist after the process ends until dismissed or expired.
   - Clicking an old `retry:1` while a new session holds pending id 1 re-runs the new recording, which the toast never named.
   - The Acceptance line "A stale id ... run nothing" covers this. The closed fix is in core (ids unique across processes).
   - Remembering offered ids in the shell (option C) is not closed, because the new process may have offered the same number.
   - Optional UX on top, not needed for the invariant: the toast thread removes the previous session's Retry toasts at start (`ToastNotificationManager::History().RemoveGroup` with a `retry` group).
4. **Open lands on a closed window (confirmed by reading).**
   - `call::open_transcript` only does `emit_to(LABEL, CALLS_OPEN, …)`, and its doc says it "neither opens the window nor waits for its page".
   - `call::open_calls(app, Some(CallRef))` builds or focuses the window and emits once after the page's first `calls_list`. `specs/007 contracts/ipc.md` names it "the shell entry".
   - After a call ends, the Calls window is usually closed, so the Acceptance wording ("calls `open_transcript`") would meet the letter but not FR-030. See Q2.
5. **Class fixed before (checked).** `docs/failures.md` F-001..F-031 has no toast, activator or CLSID entry. `class: failure-feedback` holds T-007, T-209, T-210, T-211 and T-213, none an earlier patch of this class. So `recurrence_of: []` stands.

### Seam details and residual risks

- **Activator thread and lifetime.**
  - Register on T-210's `toast` thread, which runs the shared MTA `ComGuard` and lives for the process, so the class object stays alive.
  - `ShellNotifier` is built in `release_parts` before the app exists, so registration is a message posted to that thread by `ShellNotifier::attach(route)` from `run()`, after `start_dictation_with` and `call::start_calls`.
  - Offers shown before attach carry no button. Startup notices are not retryable and carry no call, so nothing is lost.
- **`Activate` contract (F-016).**
  - It runs on a COM RPC thread, and its `PCWSTR`s are valid only during the call, so it copies them first.
  - It must return promptly and never take the session lock (`docs/decisions/windows-shell.md`, the main-thread rule extended to RPC threads).
  - It must not panic across the FFI boundary (release aborts on panic): no `unwrap` on the arguments.
  - It returns `S_OK` for arguments that run nothing.
  - The user-input array is unused (no input fields).
- **Cold activation.**
  - COM starts `voicen.exe -Embedding` as the primary and waits for the class registration, then calls `Activate`.
  - For Retry this finds nothing pending (FR-032), so nothing runs, as #274 Q5 says.
  - For Open the result depends on Q1.
  - A COM launch during a running primary's startup, before attach, is a second instance. It exits through the single-instance plugin, and `-Embedding` maps to `TrayOnly`, so no window opens.
- **Failure branch.** If registration fails, the thread writes one warning line and buttons stay off, so there is never a dead button (#279). The line uses the HRESULT as `os_code` and no text. Recommended: a new `WarningKind` `toast_activator_failed`, documented in `docs/decisions/diagnostics-log.md`. Reusing `toast_failed` is the reviewer's alternative.
- **Test isolation (F-012, F-006).** `CoRegisterClassObject` is per process, so `feedback.rs` registers once per test binary (`OnceLock`) or serialises. The logic tests call `Activate` on the object directly and need no registration. Any `pwsh` in a shell test goes through the bounded helper.
- **Installer.**
  - POSTINSTALL runs on every install, the fork's update mode included, and the fork's shortcut creation returns early there. So the property is set on the existing `.lnk` there, and an install from before T-213 gets it on its first update.
  - The key value is the bare exe path; COM appends `-Embedding`.
  - A `/UPDATE` uninstall deleting the key is harmless, because the following POSTINSTALL writes it again.
  - `/NS` installs and dev builds get no working toasts at all. That is T-210's accepted failure branch.
- **Top-level windows (F-008).** An MTA local-server registration creates no window. Only an STA would create `OleMainThreadWndClass`. The `wip/` run's install-smoke census proves it. If a new helper window does appear, the fix is a `scripts/ci/helper-windows.txt` entry, a guard change: then `checker: true` and `decides_on` with the class literal.
- **Features.** Add `Win32_UI_Notifications` to the `windows` feature list in `src-tauri/Cargo.toml`. Checked in the 0.62.2 source: it defines `INotificationActivationCallback_Impl`. `Win32_System_Com`, `UI_Notifications` and `Data_Xml_Dom` are already on. No new crate, so `make licenses` is unchanged.
- **ACL.** No new `#[tauri::command]`, so `build.rs` `APP_COMMANDS` and the capabilities do not change.

### Open questions for the owner (needed before `IN_PROGRESS`)

- **Q1: what the Open button's toast argument holds, and what an Open click does after Voicen was restarted.**
  - Background: the Context says "the toast argument is `retry:<id>` only" (written before #298 added Open). Windows keeps a toast's arguments in its notification store until the toast is dismissed or expires.
  - **(a) Recommended:** the argument is `open:<call id>` only (a date-time folder name). The root stays in the running app's memory, recorded when the toast is shown. An Open clicked after a restart only starts the app, the same rule as Retry (#274 Q5). No file path is ever written into a toast.
  - **(b)** The argument also carries the calls root (a path under the user's profile, so it names the Windows user). An Open click opens the call even after a restart, provided the folder still exists.
  - (c) After a restart, open the call under the current settings' root. This contradicts #298 Q3 and is not recommended.
- **Q2: which entry the Open click calls.**
  - Background: Acceptance line 4 names `call::open_transcript`, which only emits to an already-open Calls window. With the window closed (usual after a call) nothing visible happens, against FR-030.
  - **(a) Recommended:** the click calls `call::open_calls(app, Some({root, id}))`, which opens or focuses the Calls window and selects the call; the contract already names it as the shell entry. `open_transcript` is then removed or made a wrapper of `open_calls`, and Acceptance line 4 is reworded.
  - **(b)** Keep `open_transcript` as written: Open works only while the Calls window is open.
