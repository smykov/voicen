## Investigation

Investigator, 2026-11-24 (main tree; Serena not used: the scope is workflow YAML, shell and the runner host's scripts, read with Read/grep and over ssh on runner-105; context7 `/rust-lang/cargo` for the package-cache lock).

**1. The premise "checkout cleans `.teamwright/cache`" is wrong; "each hop builds cold" is right.** The voicen pool (`/etc/gha-pool/voicen.env`, `IMAGE=gha-runner:2.338.1-e-claude`) starts one JIT runner container per job through `/opt/gha-pool/runner-once.sh`: `WORK=/srv/gha-work/$NAME`, mounts `docker.sock`, `$WORK:$WORK` and `$RUNS_DIR:$RUNS_DIR` only, and a systemd unit runs `rm -rf $WORK` when the container ends. The workspace of run 45316103610 was `/srv/gha-work/voicen-20261124-041533/voicen/voicen` (its `runs.jsonl`). So the tree, `target/`, the registry in `.teamwright/cache/core/` and any shared sccache dir are new every hop; `clean: false` would change nothing. Container user is root (image `User` empty), so `tw-run` runs core containers as `0:0` and `RUNS_DIR` (root-owned) is writable. Core containers are siblings on VM 105's daemon, not limited by the runner's `--cpus 4 --memory 2g`.

**2. How big the cold build is.** Run 45316103610 (T-205 implement, 59 min): the first core gate log has 214 `Compiling` lines (aws-lc-sys, opusic-sys, cmake twice: host and windows-gnu builds) and `Finished dev 22.17s`, `Finished test 39.51s`; every later Rust build in the hop is 0.2-6 s (and the `_top` gate's 1m24s test build is 3 crates: the workspace crate, which sccache never caches). Gates took 752 + 941 + 589 s, i.e. about 38 of the 59 minutes, almost all test, e2e and license work. T-217's probe measured sccache cold 48 s -> warm 31 s and 81 -> 67 s; C compiles inside build scripts (aws-lc-sys, opusic-sys: the slowest crates here) are never cached. So: a prebuild that runs in the background while the session reads (its first gate came about 12 min after the job start) takes the ~1-1.5 min cold build off the critical path; a shared sccache on top saves ~15-20 s *inside the background prebuild*, i.e. about nothing on the critical path; a cargo registry kept between hops saves the download only (seconds to tens of seconds, also inside the prebuild). Expected gain of the whole task: about 1-1.5 min per hop (~2 %), far from the gate's own duration (T-264, T-262, T-263 hold the large items).

**3. Where a persistent cache could live (option B).** It must be visible inside the runner container (`tw-run` checks `[ -d "$h" ]` there) and on the host (the daemon resolves `-v` sources there). Only `RUNS_DIR` meets both today without a host change; `runner-pool.sh` prunes only `[0-9]*` entries of it ("кэш остаётся"), so `$RUNS_DIR/cache/core/_tw-sccache` survives. A dedicated mount like ai-resume's `EXTRA_DOCKER="-v /srv/gha-pip-cache:..."` is cleaner but is a host-config change (owner, `/etc/gha-pool/voicen.env`). Finding it: one symlink `<workspace>/.teamwright/cache/core/shared/_tw-sccache -> $RUNS_DIR/cache/core/_tw-sccache` made by the prebuild script; `tw-run` and `voicen-core-entry.sh` stay unchanged (the symlink path exists on the host at the same path, so the bind follows it). `TW_CACHE_ROOT` is the wrong tool: it moves the whole `CROOT` (registry and `home`) to the shared place too. Concurrency is already handled for sccache: the entry's `flock -n /tw-sccache/.rw.lock` gives one READ_WRITE server host-wide, every other container READ_ONLY (T-217).

**4. The cargo registry must not be shared as a mount.** `tw-run` mounts `/usr/local/cargo/registry` only; cargo's lock files (`.package-cache`, `.package-cache-mutate`) live at `$CARGO_HOME` = `/usr/local/cargo` (docker/rust.Dockerfile), inside each container's own filesystem. Five parallel hops (MAX_PARALLEL 5) sharing that dir would extract into it with no common lock. If the owner keeps acceptance 1's registry: seed it by copy (`cp -a` from a host dir into the hop's `.teamwright/cache/core/_usr_local_cargo_registry` before the prebuild) and refresh the host copy only under a host `flock -n`; recommended instead: drop it (download time is small and off the critical path). Side observation, not proven as a failure: locally, a `tw-mutants`/`tw-test` copy with `TW_CACHE_ROOT` = the main checkout shares the main tree's registry the same way; worth an open question if it is ever seen.

**5. Prebuild: what, and why not `cargo test --workspace --no-run`.** The gate never builds the workspace for Linux: `voicen-whisper` and the shell are linted only, with `DOCS_RS=1` (whisper-rs-sys skips its cmake build of whisper.cpp) and the shell for `x86_64-pc-windows-gnu` (Makefile `check-whisper`, `check-shell-windows`). `--workspace` would build whisper.cpp and the Tauri shell for Linux, which the gate never needs (and may not build). The prebuild runs the gate's own Rust commands: `cargo clippy -p voicen-core --all-targets -- -D warnings`, `cargo test -p voicen-core --no-run`, `DOCS_RS=1 cargo clippy -p voicen-whisper --all-targets -- -D warnings`, the two `DOCS_RS=1 cargo clippy -p voicen --target x86_64-pc-windows-gnu ...` lines, in one `scripts/tw-run core` call each, same args and env (otherwise fingerprints differ and the gate recompiles; a missing `DOCS_RS=1` would start the whisper.cpp cmake build). A lint or compile error there is the session's to find: the prebuild ignores the exit code beyond the warning. UI prebuild: none; `pnpm install` is already in the preflight, and the e2e builds into a run-private `target/e2e/run-*` dir every run by design (docs/decisions/ui-e2e.md), so no build would be reused.

**6. No race with the session's gate.** The prebuild and the session's core containers share `/work/target` on one host filesystem, so cargo's build-directory lock serialises them (the session's first build prints "Blocking waiting for file lock" and then finds the artefacts). Bounds: `timeout` inside the container command (e.g. 1500 s; SIGTERM reaches cargo), output to `$RUNNER_TEMP/prebuild.log`, exit code to `$RUNNER_TEMP/prebuild.rc`; started with `nohup ... &` so the step ends at once. Load (#296: 5 parallel stages are safe only if builds do not coincide): pass `TW_DOCKER_ARGS='-e CARGO_BUILD_JOBS=2'` to the prebuild. Docker missing is already a preflight failure, so the prebuild never runs without it. Warning: the bytes after "The stage" are pinned (`contour-push.yml`), so the stage step itself, after `claude` returns, prints one `::warning::` when `prebuild.rc` is missing or non-zero (one `if` line, inside the unpinned step; never `exit`).

**7. Warming on `main` without a write token.** With option A there is nothing persistent to warm. With option B the next hop's prebuild is the warmer (acceptance 3 allows it): the first container of the day takes the writer lock. A separate push-to-`main` job on the `claude` pool would be a second seam (a new workflow or a `ci.yml` job on `[self-hosted, claude]`, both under the release-guard's workflow rules and the R15 / action-line pins) and costs a runner slot of VM 105's memory budget on every `main` push; if the owner wants it, it is its own task, not part of T-261.

**8. Recurrence:** none. `docs/failures.md` has no cache or cold-build entry; the nearest class is `contour-stage-loses-work` (F-032, unrelated mechanism). T-217 (sccache for local trees) is the predecessor, not a failed fix: it was opt-in and documented "CI never has the dir".

**Owner question (before IN_PROGRESS):** acceptance bullets 1 and 3 (host sccache + registry, warm on `main`) and the UI part of bullet 2 buy almost nothing on the critical path (sections 2, 4, 5). Choose: **(A, recommended)** reword to a background prebuild of the gate's Rust commands only, with bullet 4's failure branch for the prebuild (warning, never red); **(B)** A plus the shared sccache via the `RUNS_DIR` symlink, warmed by the next hop, no registry sharing, no main job; **(C)** drop T-261 (gain ~2 % of a hop) and spend the slot on T-264/T-262.
