## Context

Found in T-086 review 1 (finding 1, decisions #125). `scripts/ci/nsis-fork.sh` makes sure the NSIS template fork, the `@tauri-apps/cli` version that `package.json` pins and the version pnpm installs are the same (T-025, decisions #76). Its header-line half and its `python3` `json` half conform to P-020. Its lockfile half (the awk block that reads `pnpm-lock.yaml`) is its own reader of YAML: it tracks a top-level key by column 0 and an entry by indent, takes the last `version:` line, and strips one quote from each end.

The reviewer's probe on a throwaway copy:
```
    version: 2.13.0
    specifier: '2.12.1
    version: 2.12.1'
```
The guard exits 0 ("fork of tauri-cli 2.12.1"), while PyYAML 6.0.1 reads `version: 2.13.0`.

Possible ways, for the analysis to choose from: read the lockfile with a real YAML loader (the tool itself); compare against what pnpm reports (`pnpm list --json`) or against the installed `node_modules/@tauri-apps/cli/package.json`; or pin the lockfile entry as an owned literal.

## Acceptance

- [ ] The installed-version check decides on a tool's own reading or an owned literal, with no awk YAML reader left. Its `decides_on` is named.
- [ ] Failure branch: the reviewer's probe above is refused, and the fixture is red against the old guard. The existing nsis-fork fixtures' guarantees still hold.
- [ ] The guard table in `docs/decisions/ci-toolchain.md` and `docs/decisions/installer.md` are updated. `make check` is green.

## Investigation

**Frame.** Observed: `nsis-fork.sh` exits 0 ("fork of tauri-cli 2.12.1") on a lockfile whose `@tauri-apps/cli` entry YAML reads as version 2.13.0. Expected: refused, because pnpm would install a CLI the fork does not follow. Reproduced at c3b5db5 on repo copies under `/tmp/t093probe.PHcM` (`probe/`, `probe2/`, `clean/`). Serena was not used: I read `scripts/ci/nsis-fork.sh`, `nsis-fork.test.sh`, `Makefile`, `ci.yml` and the decision docs, and grepped them.

**Hypotheses.**
1. The awk line model reads a different value than YAML. Confirmed: both probes exit 0 on the old guard. PyYAML reads 2.13.0, and pnpm 8.15.0 reads 2.13.0 too: probe2's frozen install fails only on the missing `/@tauri-apps/cli/2.13.0` package.
2. pnpm's frozen-lockfile check already closes the gap. Only partly. It refuses the reviewer's probe on the specifier (ERR_PNPM_OUTDATED_LOCKFILE). It does not check that the importer version satisfies the specifier, so probe2 gets through.
3. The same concern is handled on a second path. Refuted. `grep nsis` in `ci.yml` finds no other check. The windows job runs `pnpm install --frozen-lockfile` and builds with whatever version that installs.
4. This class was fixed before. Yes, as a class (guard-model: F-003, F-015, P-020; rewrites T-087 to T-092). This guard's lockfile half was never patched. It was wrongly classed as a literal in T-086 and corrected in decision #125. This is a planned split task, not a recurrence: `recurrence_of` stays empty.

**Where each source is available.** The guard runs only in `make check`: on the local host, and in the CI gate job after `scripts/tw-run ui -- pnpm install --frozen-lockfile` writes `node_modules` into the workspace. The windows job does not run it. `node_modules/@tauri-apps/cli/package.json` exists in both places, and the guard can read it with the python3 json that it already uses. `pnpm list --json` gives the same fact, but only with a docker run. No YAML loader is a declared dependency anywhere:
- PyYAML is a Debian package on this host and is absent from `voicen-rust:1.99`.
- `yaml@1.10.3` is only transitive in `node_modules`.
- pnpm 8.15.0 does not export its lockfile reader.

**Root cause.** See `analysis.root_cause`. It explains both probes and the earlier refusal of a double-quoted key: that key is a shape the line model does not match, so the guard fails closed.

**Recommended.** Option A: decide on pnpm's install result plus the owned header line, and read no YAML. Size: small, one seam (`nsis-fork.sh` and its test) plus three docs. No new dependency and no owner decision needed.

**T-088.** It does not block this task. T-088 is BLOCKED because the owner must decide how a YAML reader in `release-guard.sh` fragments closes (round 3, a narrower claim, or `/arch-review` for the class). T-093 removes a reader instead of tightening one, and it touches no file T-088 touches. If the owner sends the guard-model class to `/arch-review`, A is already the shape that review would ask for: a tool's own output plus an owned literal, as in T-092.
