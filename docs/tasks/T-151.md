**Decisions the tests pin beyond the analysis:**
- The expected track duration is the same call recorded alone over the same three pumps (`BEFORE_MS`, `DURING_MS`, `PUMP_MS`), not a number written in the test: the recorder's exact `duration_48k` of a pumped span (pre-skip, 20 ms blocks) is not known here, and equality with a dictation-free baseline is what "continuous" means. The baseline is recorded first, on its own `CallRig` (no hotkey thread), and dropped before the composed app is built.
- The call is started by the call hotkey (one press), not by `call::request`, so the dictation's call slot (`start_dictation_with`) is on the path of mutant 02.
- Esc claim during the hold is read through `esc_claim` with `refused = || false` (the test has no observer of the log's `EscUnavailable` warning); the probe still requires Esc held bare and under Ctrl+Alt.
- `esc_released` is polled (the release side is safe to poll, T-108).
- Pumps of the call's tracks run on the test thread, before, during and after the hold, so the track timeline is deterministic and the hold is the only real-time part (F-014).
- The overlay half of `ShellIndicator` is the real one on the mock app; if its window ever takes focus in CI the paste assertions will show it.

## Investigation

**Frame.** US7 #1, #3-#5 (spec FR-009; req FR-22 `(v6, r3#18)`, FR-36, NFR-02 `(v6, r3#2)`). Expected: a dictation during a call records on its own stream and pastes, the call's mic track goes on without a gap, the tray goes Recording then CallRecording, Esc is only the dictation's, and nothing is open while both are idle. No symptom is reported; this is a feature task whose risk is in the composition, not in either session.

**Hypotheses (where the composition could break) and what was found.**
1. *The two captures share something* (one stream, an exclusive open, one opener). Refuted by reading: `win::capture::CpalSource` and `win::track_capture::CpalTrackSource` each call `cpal::default_host()` and open on their own `open_bounded` thread; cpal 0.18.2 WASAPI opens only in shared mode (registry source, `host/wasapi/device.rs`, `AUDCLNT_SHAREMODE_SHARED` at both `share_mode` sites). Whether a real endpoint accepts two shared streams together is the owner's R24 check (the runner has no capture endpoint, NFR-22).
2. *Esc is a second path*: the call claims or reacts to Esc. Refuted in core: `call/session.rs` module doc and call-session I6, pinned by `dictation_session.rs::dictation_and_esc_never_change_a_running_call`. The call hotkey slot never claims Esc (windows-shell.md hotkey invariant, T-129). Not yet proven through the shell with a real test window.
3. *The tray loses one half*: the dictation or call publish overwrites the other. Refuted by reading: both write separate fields of one `tray::Shared` view (`set_tray`, `set_call_recording`) and `render` applies `shown(view.state, view.call_recording)`; `run()` gives both sessions the same `TrayPart`. Not proven end to end: every existing call+dictation shell test uses `FakeIndicator` for the dictation, so `tray::applied` never sees the dictation half.
4. *Something opens a capture while idle* (a track opened at `start_calls`, a device watcher). Refuted by reading: `start_calls` builds the session and threads and "starts no call"; `NotifyFactory`/`ComCheck` are not capture streams. Not observable in the rig today: core's `WavHandle` counts nothing, so `WavSource` needs an open-handle counter.
5. *This class was fixed before*: no `docs/failures.md` entry or task for dictation/call interference; T-129 pinned the hotkey half (`call_hotkey.rs` section (d)).

**Conclusion.** No product defect is shown by evidence; every expected property follows from the ports as they are. T072's tests are therefore likely to be green on their first run apart from compile reds on new test support (owner answer 1 below). A product fix (T073) is needed only if a test goes red; the seam for it is the port that test names.

**Dependency on T-145.** Not a behaviour dependency (exit/sleep are outside US7), but a merge one: T-145 adds `CallPorts.exit_confirm`, `CallRequest::{Sleep, Resumed, Exit}`, edits `call_shell_support/mod.rs`, `call_hotkey.rs` and `win/hotkey.rs`. `call_dictation.rs` builds `CallPorts` through the rig and needs the same support file, so DEV starts after T-145 is on `main` (decisions #349; `depends_on` carries T-145).

**Size.** Small: one area (shell), one new test file plus test-support additions; no spec-tool work.

**Owner's machine.** Yes, for the Acceptance line "two shared-mode streams on one endpoint and the NFR-02 start figure from the log" (R24): a call with Record on, a dictation hold into Notepad, then read `press_to_frame_ms` of that dictation line and check `mic.opus` has no gap. Everything else is Windows CI.
