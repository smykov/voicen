## Context

First end-to-end slice of the release-1 flow (requirements §2) on the walking skeleton, in the part the Linux host and an API test can prove: the `voicen-core` pipeline from a recorded buffer to the text that would be delivered. Requirements: FR-06, FR-12, FR-24 (connect 5 s, API 30 s), FR-11 (pending audio), NFR-06, NFR-07 (engine failure never panics). Foundations from spec 001 Phase 2: `Timeouts`, `AudioBuffer` + WAV encoding, platform traits with fakes, `DictationEvent`. Dependencies per decisions #9. Settings and keys come from T-003 (decision #21): `DictationSettings` is a projection of `SettingsService::snapshot()` (no own file, loader or defaults), the key is read with `CredentialStore::read(KeySlot::TranscriptionApi)` as a `Secret`. The API surface: add `api_test_command` for area `core` (an integration test binary that runs the pipeline against a local mock OpenAI-compatible HTTP server) through `.teamwright/config.next.yml` — the owner applies it.

## Acceptance

- [ ] A 3 s speech fixture sent through the pipeline to a mock `/v1/audio/transcriptions` returns the mock's text as the delivery text; the request is multipart with 16 kHz mono WAV, `model`, `language` (auto = omitted) and `Authorization: Bearer <key>`
- [ ] Silence, 1 s cough and keyboard-noise fixtures make no HTTP request and yield outcome `NoSpeech` (FR-12)
- [ ] `api_test_command` for area `core` exists in `.teamwright/config.yml` and runs these tests
- [ ] Failure branch: mock answers 401 → outcome `Failed(InvalidApiKey)`, nothing to paste, the audio stays as the pending recording; no answer in 30 s → `Failed(Timeout)`; unreachable host → `Failed(CannotReach(host))` within 5 s connect — verified by the API test and the absence of any paste/clipboard call on the fakes
- [ ] Test that fails without the change: `crates/voicen-core/tests/api_pipeline.rs (red before the change)`

## Investigation

**Frame.** This is a feature, not a defect. The "cause" is the missing core seams. Observed: voicen-core holds only settings, keys, i18n, clock and build info (`src/lib.rs:3-12`). Expected: a recorded buffer goes through the speech gate, the OpenAI-compatible client and post-processing to an outcome, with the failure branch (no paste, audio kept). Where it is proven: the Linux gate with fakes and wiremock, and the same test binaries in the Windows job (`ci.yml:60`, `cargo test --workspace --exclude voicen`).

**Recurrence check.** `docs/failures.md` has one entry, F-001, class `ci-toolchain`: tauri-build's stub `msvcrt.lib` reached voicen-core doctests through cargo's shared search paths. This task is class `transcription-pipeline`, a different class, so there is no recurrence and `recurrence_of: []` is correct. One adjacent risk of the same class: `reqwest` with `rustls` brings `aws-lc-sys`, the first C library in voicen-core. The shell links it with tauri's static VC runtime (`/NODEFAULTLIB:msvcrt`, `libcmt`; T-033 analysis). F-001's mechanism does not apply, because voicen-core tests run in their own invocation (`ci.yml:60`). Whether the shell links cleanly is proven only by the first Windows CI run of the engine task. If it fails, that is a new `ci-toolchain` entry, the second of the class.

**Hypotheses checked.**
1. *Pieces already exist under other names.* Refuted for the pipeline (grep over `crates/voicen-core/src` for `Engine`, `AudioBuffer`, `Timeouts`, `SpeechGate`, `Pending`, `reqwest`: no hits; Serena does not index Rust, decision #3). One port does exist: `clock::Clock` (`clock.rs:7-9`, wall clock `SystemTime`). The spec's `Clock { now() -> Instant }` (contracts/core-traits.md) would be a second port with the same name (P-011). Instead, extend the existing trait with a monotonic `instant()`, or pass `Instant`s in from the caller.
2. *The same concern is handled on a second path.* Planned three times. The HTTP client is reused by 002's local server (T-018) and 003's chat transport (T-020), so it must be one `OpenAiCompatibleEngine`. The VAD is planned twice: specs/001 R-6 puts `vad/silero.rs` and `whisper-rs` into voicen-core behind feature `silero`, but decision #12 and specs/002 R-1 say "voicen-core has no dependency on whisper-rs". #12 is later and covers whisper-rs as a whole, so `SileroDetector` belongs in `crates/voicen-whisper`, implementing core's `SpeechDetector`, injected by the shell. The specs/001 plan, R-6 and T005 must be updated in the task that builds it.
3. *The class was fixed before.* No: no earlier task or failure in `transcription-pipeline`.
4. *The contract as written cannot be built as is.* Confirmed in five places:
   - (a) Spec T002's reqwest feature `rustls-tls` does not exist in the locked reqwest 0.13.5. Use `default-features = false`, `["blocking", "multipart", "json", "rustls"]`, and keep `system-proxy` so the Windows proxy settings apply as in other apps; the developer confirms that last choice. The crates.io licenses (queried 2026-10-03) are all inside `about.toml`: aws-lc-rs 1.18.1 "ISC AND (Apache-2.0 OR ISC)"; aws-lc-sys 0.45.0 "ISC AND (Apache-2.0 OR ISC) AND Apache-2.0 AND MIT AND BSD-3-Clause AND (…OR MIT) AND (…OR MIT-0)"; rubato 5.0.1 and wiremock 0.6.5 MIT/Apache-2.0. `make licenses-check` confirms on the resolved versions. rubato's API changed across majors, so the developer checks the docs for the pinned version.
   - (b) URL join. The contract says `{base_url_trimmed}/audio/transcriptions` (string append), but #27(2) allows a query string (`https://x/v1?api-version=…`), and string append would put the path after the query. The request URL must be built by one function on the parsed URL: append the path segments `audio`, `transcriptions`, drop one empty trailing segment, keep the query.
   - (c) `FailureReason` has no row for `CredentialStore::read` → `Err(CredentialError)`. Do not send the request without a key: that turns the cause into a misleading 401. A small contract decision, see the questions below.
   - (d) reqwest errors carry the full URL, query included (`blocking/client.rs:1525`, `with_url`). They must never be formatted into a `FailureReason`, an event or a log (P-009, #30); only the classification flags and `host[:port]` leave the adapter.
   - (e) The blocking client panics when built or used inside a tokio runtime (`blocking/client.rs:113`). Tests must run the wiremock server in a runtime and call the engine on a plain thread (`spawn_blocking` or `std::thread`). In T-006, the shell must run jobs on a std worker thread, never inside a Tauri async command.
5. *Timeouts as reqwest implements them meet FR-24.* Confirmed. `RequestBuilder::timeout` runs "from when the request starts connecting until the response body has finished" (`blocking/request.rs:357-361`), which is Clarification 1. Set it per request from `Timeouts::api_transcription`, and set `ClientBuilder::connect_timeout(Timeouts::connect)`; the client default timeout is 30 s (`blocking/client.rs:385`), so set it explicitly too. The 1 MiB cap must be enforced by reading through `Read::take(1 MiB + 1)` (blocking `Response: Read`), not by `json()`.

**Error classification (pure function over a small `TransportError`, then the reqwest adapter).**
- Status 401/403 → `InvalidApiKey`.
- Any other non-2xx → `ServerError{status}`.
- `is_dns()` (`error.rs:176`), or an io `NetworkUnreachable`/`HostUnreachable` in the source chain → `NetworkUnavailable`.
- `is_connect()` (`error.rs:158`) with `ConnectionRefused`, or with `is_timeout()` (connect timeout) → `CannotReach{host[:port]}`.
- `is_timeout()` and not connect → `Timeout`.
- Body not JSON, `text` missing or not a string, more than 1 MiB, invalid UTF-8, or reset mid-body → `UnexpectedResponse`.
- 2xx with empty or whitespace-only `text` → `Ok("")`, which the pipeline turns into `NoSpeech`.

Check `is_connect` before `is_timeout`. Probes in `voicen-rust:1.99`: a refused `127.0.0.1` port fails at once, so the `CannotReach` adapter test is deterministic; a `.invalid` host fails DNS at once (RFC 6761); `192.0.2.1:80` (RFC 5737) blackholes, so a connect-timeout adapter test with a ms-scale `Timeouts` works here. It is environment-dependent on `windows-latest` (a fast ENETUNREACH would give `NetworkUnavailable`), so the "within 5 s" claim rests on three things: the pure mapping test, a test that `Timeouts::default().connect == 5 s` is what the client gets, and the 192.0.2.1 test as an extra.

**Trait shapes settled (from contracts/core-traits.md, with the deltas above).**
- `AudioBuffer`: 16 kHz mono i16, constructible only through `AudioBuffer::from_frames(samples, rate, channels)` (mix-down + rubato) or from 16 kHz mono samples. `audio::wav::encode(&AudioBuffer) -> Vec<u8>`: RIFF PCM 16-bit, 16 000 Hz, 1 channel, written by hand (no `hound`, which is not consented).
- `Timeouts { connect: 5 s, api_transcription: 30 s, local_server: 60 s, post_processing: 15 s, builtin: 120 s (#7) }`, one constructor; tests build it with milliseconds.
- `Engine::transcribe(&self, &AudioBuffer, &TranscribeRequest) -> Result<String, FailureReason>`, synchronous per #22 and specs/001 R-7, pending OQ-05.
- `EngineFactory: Fn(&DictationSettings, &dyn CredentialStore) -> Result<Box<dyn Engine>, FailureReason>`, called per job.
- `DictationSettings: From<&Settings>`. `SettingsSource` over `SettingsService::snapshot()`. P-013 test through `SettingsService::load_or_init` with `FakeSettingsFile`.

**Pipeline and pending recording.**
- `Pipeline::run_job(&self, job: DictationJob { audio, start_window, stopped_at }) -> JobResult { outcome: JobOutcome, delivery: Option<DeliveryResult> }`, synchronous on the caller's thread. Steps: settings snapshot → gate → (speech) factory with a credential read → transcribe → `PassThrough` → deliver (clipboard write first, then the data-model `DeliveryDecision` table → `send_ctrl_v` or copy-only).
- "Pending recording" in core for T-001 means one slot in `Pipeline`: `Option<PendingRecording { id, start_window, reason }>`, with its audio written through `TempAudioStore::put_pending(id, &audio)`. A newer failure replaces it and deletes the old audio; Text and NoSpeech do not touch it. A clipboard write failure counts as `Failed(ClipboardUnavailable)` and also becomes pending.
- Left to T-007: retry, the fs `TempAudioStore` with start/exit cleanup, the Notifier/Indicator calls and the full replacement rule table.
- Delivery must be in the pipeline. The Acceptance's "no paste/clipboard call on the fakes" only bites if the success path calls them.

**`DictationEvent`.** Exactly the data-model variants and fields (allowlist, no text, audio, URL, header or key). T-001 emits `SpeechGate`, `JobFinished`, `Delivered` and `Warning{vad_fallback}`. `RecordingStarted`/`RecordingEnded` come with the recording controller. Redaction test: the key `sk-test-SECRET` and `TRANSCRIPT-MARKER` appear in no event and in no `FailureReason` `Debug`/`Display`.

**Left to T-006 (shell, Windows CI).** `CpalSource` feeding `AudioBuffer::from_frames`, the Win32 `Clipboard`/`Paster`, the hotkey thread, tray and overlay, and wiring `Pipeline` with real ports on one std worker thread (FIFO keeps recording order until T-011). Unowned once T-001 is narrowed, routing needed: the core `RecordingController` hold mode (spec T014/T019) and `IndicatorState` (T012). Proposal: one core task before T-006, which T-009 later extends. T-006 also needs a `TempAudioStore` before T-007 builds the fs one: either move the fs store into the pipeline task, or order T-007's store first.

**Speech gate (FR-12): what spec 001 settles.**
- Primary is Silero through whisper.cpp's VAD (`whisper-rs`, consented in #9) with the bundled ggml Silero model (< 1 MB, MIT, requirements §8). Fallback is an energy detector (R-5).
- The quickstart's `silero`/`test-audio` features are spec 001 R-4/R-6. By #12, Silero lives in `crates/voicen-whisper`, not in core. The image already has cmake/clang (`docker/rust.Dockerfile:5`), but #12 keeps the native build out of the Linux gate.
- On Linux the gate is the energy detector. As R-5 is written ("≥ 0.3 s of frames ≥ 12 dB above the floor", in total), keyboard noise counts as speech: 8 clicks/s × 3 s × one 30 ms frame = 0.72 s. The rule needs a minimum run, so that only runs of ≥ 3 frames (90 ms) count. The speech-gate task pins the constants.
- Limit: an energy detector cannot reliably tell a long cough from speech, and synthetic fixtures check the rule only against its own model of the sounds. FR-12's cough/keyboard behaviour on real audio is proven only by Silero on real recordings (Windows CI) and by the owner.
- No new crate is needed for T-001. The model file and the Silero task are owner/routing items (questions below). No task owns `SileroDetector` today (T-017 is stage 2).

**Fixtures.** For T-001 and the gate task, generate them in test code, deterministic (a fixed-seed LCG; `rand` is not consented), 16 kHz mono i16. No binary files, no license. None exist in the repo today (`crates/voicen-core/tests/` holds only `fakes.rs` and `settings_apply.rs`).
- Speech, 3 s: harmonic voiced signal, f0 gliding 110-220 Hz, 6-8 harmonics, ~4 Hz syllable envelope.
- Silence, 3 s: a -60 dBFS noise floor (not digital zero).
- Cough, 1 s: one broadband burst, 10 ms attack, ~150 ms decay, then the floor.
- Keyboard, 3 s: 10-20 ms decaying clicks at random 6-8/s.

Silero on synthetic speech proves nothing. The Windows-CI Silero test needs real clips: either the owner records them (he holds the copyright, so MIT) or CC0 sources are used (CC-BY is outside `about.toml`).

**`api_test_command`** for area `core`, for `.teamwright/config.next.yml` (in the area's docker runner like `test_command`): `cargo test -p voicen-core --test api_pipeline --test openai_client`. The kind is in-process (the mock server and the pipeline in one test process); the same binaries run on `windows-latest` in `ci.yml:60` for the deployed commit. cargo has no stable JUnit/JSON output, so evidence is the captured run log. The owner applies it with `apply --config`; this does not block development, only the Acceptance checkbox.

**Seam-size verdict.** Not seam-sized as written. The design_ref "Phase 1-3 (core tasks)" covers spec T002, T004-T012 and T013-T023 (core parts). The T-003 precedent (#20, #23) split at six seams and ~30 red tests; this is about ten modules and about 40 red tests. Proposed split; the orchestrator decides:

Message ids: each task adds its own to both catalogs (decision #23 N3).
