## Context

Found by T-078's investigation (`docs/tasks/T-078.md` ## Investigation, evidence and draft options). reqwest 0.13.5's `connect_timeout` wraps the system lookup. When the resolver does not answer, the error carries connect+timeout and no dns flag, and `failure::classify` returns `CannotReach{host}`. The client drop then blocks until getaddrinfo returns: about 20 s in total on Linux with a blackholed resolver (`TW_DOCKER_ARGS="--dns 192.0.2.1"`). That is past FR-24's 5 s connect limit. `local_models::download` builds its own client with the same behaviour. Which reason is right is OQ-22 (owner).

## Acceptance

- [ ] A lookup that gets no answer within the connect timeout maps to the reason the owner picks in OQ-22, pinned by a `failure::classify_table` row and the `contracts/openai-transcription.md` row (moved here from T-078 Acceptance line 4)
- [ ] Failure branch: with a resolver that never answers, a dictation job (and post-processing, and the model download) ends within the connect setting plus a stated allowance, not at the OS resolver's give-up time — pinned by a test with an injected never-answering resolver or a blackholed DNS
- [ ] Test that fails without the change: the never-answering-resolver test above

## Investigation

**Frame.**
- Observed: a resolver that does not answer within `Timeouts.connect` gives `CannotReach{host}` in dictation, and the job returns only when the OS resolver gives up (~20 s on Linux; Windows not measured), not at the connect setting (FR-24, default 5 s).
- Expected (decision #106, OQ-22 (b)): the lookup gives up at the connect deadline with a DNS error, reported as NetworkUnavailable. This covers the engine, the post-processor and the model download (download: SourceUnreachable, its existing DNS reason). Test connection stays CannotReach (#51).
- Tools: Serena was not connected in this session (no `mcp__serena__*` tools), so I used grep and file reads over `crates/voicen-core/{src,tests}` and `src-tauri/src`. Library APIs come from the vendored sources (`.teamwright/cache/core/_usr_local_cargo_registry/src/index.crates.io-*/`), pinned by Cargo.lock: reqwest 0.13.5, hyper-util 0.1.21, tokio 1.53.1. I did not use context7; the vendored source is authoritative for the pinned versions. No cargo run; the reproduction is T-078's.

**Hypotheses.**
1. The connect timer cuts the lookup without a dns flag. **Confirmed.**
   - reqwest `connect.rs:904-917` `with_timeout` wraps the whole connector in `tokio::time::timeout` and yields `TimedOut`.
   - `async_impl/client.rs:922` `connector_builder.set_timeout(config.connect_timeout)`.
   - `DnsError` is created only in `DynResolver::call` from the resolver's own `Err` (`dns/resolve.rs:124-128`). `Error::is_dns` looks only for it (`error.rs:176-188`).
   - `engine::openai::send_error` copies the flags as they are, and `failure::classify` checks dns, then connect, so the result is `CannotReach`.
2. The job outlives the error because of the drop. **Confirmed.**
   - hyper-util `GaiResolver::call` runs `spawn_blocking(... to_socket_addrs())` (`connect/dns.rs:117-124`).
   - The blocking client's `InnerClientHandle::drop` joins the runtime thread (`blocking/client.rs:1402-1415`). That thread ends with `drop(rt)` (1470), and tokio's `BlockingPool::drop` calls `shutdown(None)`, an unbounded wait (`runtime/blocking/pool.rs:282-285`).
   - T-078's probe: error at 2.11 s, then `drop(client)` takes 18.0 s.
   - `OpenAiCompatibleEngine::send` and `post_process::chat::send` drop the client before they return.
3. A second path handles the same concern. **Confirmed, one more.** `Downloader::transfer` builds its own `Client::builder().connect_timeout(..).timeout(download_no_data)`: same resolver, same drop wait. Its reason does not change: `from_transport` already maps dns and connect alike to `SourceUnreachable{host}`. Only the wait changes.
   - `connection_test::run` → `engine_for` → `OpenAiCompatibleEngine::transcribe` takes the engine path. Its `from_failure` maps `NetworkUnavailable` → `CannotReach{host_of(raw)}`, so #51 holds with no change there.
   - The shell has no reqwest client (grep `src-tauri/src`: none).
4. This class was fixed before. **Related, not the same.** F-013 / T-078 / T-080 made the tests independent of the resolver: `OsAnswer::unresolvable` with `OS_ANSWER_BUDGET` deadlines. The product behaviour was deferred here on purpose (decisions #100, #106). `recurrence_of` stays empty.
5. hickory is already available. **Refuted.** `hickory` is not in Cargo.lock. reqwest's `hickory-dns` feature would add the hickory-resolver tree, a license review and different Windows resolver semantics (it does not use the OS resolver configuration the way GetAddrInfoW does). Not needed.

**Root cause.** See `analysis.root_cause`. It explains both symptoms:
- the reason: no dns flag;
- the wait: the blocking-pool lookup is awaited at the runtime drop.

Contradicting evidence: none. When the connect setting outlasts the OS give-up, the lookup itself fails with EAI_AGAIN, gets the dns flag, and is already NetworkUnavailable (probe row "30 s → 20.13 s, dns").

**Why the resolver must not race the connect timer with its own deadline.**
- A resolver that gives up at `connect` with its own sleep starts a few µs after reqwest's sleep. tokio rounds both deadlines to a 1 ms tick. In the same tick, `Timeout` polls the inner future first, so the DNS error wins. Across a tick boundary, or when the runtime thread is starved, reqwest's `TimedOut` wins and the result is CannotReach again.
- A margin (resolver at `connect − ε`, or the client at `connect + ε`) only makes the race rarer. That is the clock-race class of F-005 / F-013 moved into the product.
- So the dns fact is recorded by the resolver, not won by a timer. A pending lookup future dropped by the timer, or by the total request deadline, sets the client's `lookup_unanswered`. An optional resolver deadline at `connect` may then return a real `DnsError` first; both outcomes classify the same.
- To the user this is what #106 says: the lookup ends at the connect deadline and is reported as network unavailable. The DNS fact comes from the resolver's record when reqwest's timer ends first. I note this as an implementation reading of #106, not a change to it.

**Options.**
- **A (recommended): `DeadlineResolver` + lookup record, in `engine::http`.**
  - Lookup on a detached `std::thread` (named, logs nothing; the host name is never logged).
  - A std-only oneshot (`Mutex<Option<result>>` + `Waker`) for the future.
  - A drop guard that sets `Arc<AtomicBool>` when the future is dropped before an answer.
  - `engine::http` returns the client with its record; `send_capped` and the download's send read it into `send_error`.
  - The detached thread ends when the OS resolver returns. Nothing joins it, so neither the runtime drop nor the job waits for it.
  - No new crate. Only `reqwest::dns` public items and std. If the developer prefers `futures-channel` or `tokio::sync::oneshot`: both are already in Cargo.lock (no new license), but adding either as a direct dependency still goes in the commit with `make licenses` checked.
  - Why it removes the cause: no blocking-pool task to await, and the dns fact no longer depends on which timer fires.
  - Risk: one detached thread per unanswered lookup, alive until the OS gives up (~20 s), bounded by user retries. IP-literal hosts never reach the resolver (hyper-util `connect/http.rs:557-559`), so `127.0.0.1` local servers are unchanged; `localhost` goes through the thread.
  - With the system proxy, the proxy host's lookup goes through the same resolver and gets the same treatment.
  - Rollback: revert to the default resolver; behaviour returns to today's.
- **B: resolver with its own deadline at `connect − margin`, no record.** Smaller change, but the race above stays: probabilistic under load. Rejected.
- **C: reqwest `hickory-dns` feature with a resolver timeout.** New dependency tree and license review. It does not take the Windows OS resolver configuration the same way. It still needs the record for the timer race. Rejected.

- Keep the row "192.0.2.1 connect_timeout: connect + timeout → CannotReach": a TCP blackhole has an answered lookup or an IP literal, so its record stays false. Bite: a record set on every drop, or set after an answer.
- Contract `specs/001-dictation-via-api/contracts/openai-transcription.md` › Classification: in the table row "DNS failure" and rule 2, add "including a lookup with no answer by the connect deadline (T-079, #106)". The rule-3 text "connect not established in 5 s" then means after the lookup answered.
- `DownloadFailure::from_transport` is unchanged (dns → SourceUnreachable).
- Total deadline shorter than the connect setting (allowed by the bounds, e.g. connect 60 s, post-processing 5 s): a lookup still pending when the total deadline fires is NetworkUnavailable by the invariant, not Timeout. Post-processing gives the raw transcript either way. See open question 1.
