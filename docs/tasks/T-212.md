## Context

Owner check of build 0.1.397 (and 0.1.192 before it) on Windows 10.0.26300, hotkey Ctrl+Alt+Space, mode hold: `voicen.log` has `WARN warning kind=esc_unavailable` before every recording. The owner confirms (2026-11-12) that **Esc does cancel the recording**. So the warning is a false alarm.

Lead (not yet an analysis): `src-tauri/src/win/hotkey.rs` `cancel_key` registers two claims, bare Esc (`ESC_ID`) and Esc under the active hotkey's modifiers (`ESC_MOD_ID`, here Ctrl+Alt+Esc). It reports `cancel_key_result(self.esc && self.esc_mod, …)`, so a refusal of the modified claim alone makes `DictationSession::cancel_key_result` emit `Warning{EscUnavailable}`, although bare Esc is registered and cancels. Why Ctrl+Alt+Esc is refused on the owner's PC (system-reserved, another program) is unknown. The analysis decides what the warning must mean: bare Esc refused (cancel impossible) vs. only the modified one refused (cancel needs releasing the modifiers first). In hold mode the modifiers are held while recording, so whether Esc cancels while Ctrl+Alt are still down is part of the question.

## Acceptance

- [ ] `esc_unavailable` is logged only when Esc cannot cancel the recording at all; a refusal of only the modified claim is either not a warning or its own closed code (the analysis decides; `docs/decisions/diagnostics-log.md` names it)
- [ ] Failure branch: bare Esc refused (another program holds it) → `esc_unavailable` once per recording, the recording goes on — Windows CI shell test
- [ ] Owner's log on Windows after the fix: no `esc_unavailable` before recordings while Esc cancels
- [ ] Test that fails without the change: a shell test in `src-tauri/tests/` with the modified Esc claim held by another registration

## Investigation

Tools: Serena (`get_symbols_overview`, `find_symbol`) on `src-tauri/src/win/hotkey.rs` and `crates/voicen-core/src/recording/mod.rs`; grep for docs, tests and the call sites of `cancel_key_result` (Serena references not needed beyond that; grep found one shell caller, `hotkey.rs:895`, plus core tests); context7 `/websites/learn_microsoft_en-us_windows_win32_api` for `RegisterHotKey`.

**Frame.** Observed: in hold mode with Ctrl+Alt+Space, `WARN warning kind=esc_unavailable` before every recording, and Esc cancels (owner, 2026-11-12). Expected: the warning only when Esc cannot cancel the recording (FR-22, Acceptance line 1). Reproduces only on the owner's Windows 10.0.26300. Symptom: the warning. Guess (task lead): only the modified claim is refused.

**How a cancel can happen, per mode (the mechanism).**
- Both claims are made for every live recording (`Registrations::cancel_key`, `hotkey.rs:885-893`); `WM_HOTKEY` on either id calls `esc_pressed` (`:1043`); `RecordingController::cancel` cancels in either mode (`recording/mod.rs:434-439`).
- Hold: the recording ends at the first hotkey key found up (`win32_data::released`, `win32_data.rs:154-160`; `RecordingController::release`, `recording/mod.rs:414-428`). Every hotkey has at least one modifier (`settings/hotkey.rs:5`, `:246`). So bare Esc, which needs every modifier up, can only be pressed after the hold has already stopped and been sent for transcription. During a hold only Esc with the hotkey's modifiers held can cancel. That claim is `ESC_MOD_ID`, and this is why it exists (OQ-21 (1), decisions #105: `RegisterHotKey` matches the exact modifier state).
- Toggle: the hotkey has been released, so bare `ESC_ID` cancels. The modified claim only covers Esc pressed before letting go of the modifiers.
- So which claim cancels is decided by the live recording's mode (`Live.mode`, fixed at the press, `recording/mod.rs:382-387`), which only core knows. The shell reads no mode (windows-shell.md rule 1, T-009 Investigation :48).

**Hypotheses.**
1. *The modified claim is refused, the bare one is held* (task lead). Refuted by the owner's report if the exact-match premise holds: in hold mode, with the modified claim refused, Esc pressed with Ctrl+Alt+Space held does nothing, and Esc after release comes too late. The owner says Esc cancels, so this would also need the owner to have pressed Esc in some other way. Not proven either way: the line carries no claim id and no `os_code` (`cancel_key_result` emits a bare `Warning{EscUnavailable}`).
2. *The bare claim is refused, the modified one is held.* Fits every symptom: the warning comes on every recording (`esc && esc_mod` is false) and Ctrl+Alt+Esc cancels the hold. Most likely. Who holds bare Esc on that PC is unknown and does not matter to the fix.
3. *Bare Esc does fire under held modifiers (the premise is wrong).* Then hypothesis 1 would also fit. Neither Microsoft's page ("the keys that must be pressed in combination") nor T-009 (`T-009.md:59`, "not proven") settles it, and no CI test holds one claim only. `tests/hotkey.rs:636` claims both, and its "bite: only bare Esc claimed" was not shown as a run. Shell test (4) below settles it in Windows CI.
4. *A second path / self-collision* (the app refuses its own claim). Checked: no other `RegisterHotKey` of Esc in `src-tauri/src` or `src` (grep). The claim is deduplicated (`if !self.esc` / `if !self.esc_mod`, and `Shared::publish` posts only on a change, `dictation.rs:294-300`). A modifier-less hotkey, whose modified claim would equal the bare one, is impossible (`hotkey.no_modifier`). Refuted for the code. A second running instance was not examined (single-instance plugin present).
5. *This class was fixed before.* See Recurrence: no.

**Root cause.** The shell reduces two claims with mode-dependent meaning to one bool (`hotkey.rs:895`), and core warns on that bool without the recording's mode (`dictation.rs:619-630`). So a refusal of the claim that cannot cancel this recording anyway is reported as "Esc unavailable". This explains the false alarm under either hypothesis 1 or 2. Under hypothesis 1 in hold mode the warning would actually be true, and that contradicts the owner's "Esc cancels". That contradiction is why hypothesis 2 is preferred, and test (4) checks it.

**Choice between the two options offered.** Both (a) "warn only when bare is refused" and (b) "a new closed code for a modified-only refusal" are mode-blind, and both fail Acceptance:
- (a) still warns in the owner's likely case (hypothesis 2, bare refused, Esc cancels). It also goes silent in the one real hold-mode failure (modified refused: Esc cannot cancel a hold).
- (b) has the same blind spot and adds a closed code to diagnostics-log.md for an outcome whose meaning depends on the mode.

Acceptance line 1 already fixes the product meaning ("only when Esc cannot cancel the recording at all"). The evidence turns that into a mode rule, so this is not a new product decision: **Option A**, a mode-aware meaning decided in core, with no new code. Acceptance line 2 ("bare Esc refused → `esc_unavailable`") holds for toggle mode. For hold mode the matching branch is "the modified claim refused". The record's line 2 should say which mode it means; the orchestrator words it, and the red tests below cover both.

**Invariant.** `Warning{EscUnavailable}` for a live recording iff the claim that can cancel it under its mode was refused (Hold → `ESC_MOD_ID`, Toggle → `ESC_ID`). The shell reports outcomes, and core gives them their meaning.

**Seam.** One contract, the CancelKey result: `DictationSession::cancel_key_result(bare, modified, at)` (or a small result struct), plus a `RecordingController` accessor for the live mode next to `live_id`. The change touches two crates: core holds the decision, and the shell's one call site (`Registrations::cancel_key`) passes `self.esc` and `self.esc_mod` separately. The shell gains no mode knowledge.

**Approach.**
- *A (recommended):* as in `analysis.approach`.
  - Red tests, core: `crates/voicen-core/tests/dictation_session.rs`, one test per mode × outcome. Today `(false,true)` and `(true,false)` warn in both modes.
  - Red tests, shell (Windows CI, `src-tauri/tests/hotkey.rs`): plant the collision with `win32_support::TakenHotkey::take_esc(MOD_CONTROL | MOD_ALT)` (the modified claim) or `take_esc(0)` (bare). Each is a thread-associated `RegisterHotKey(None, own id, …)` of the test thread, so the hotkey thread's claim on its window gets 1409. Plant before `rig.press_hotkey()` and after `assert_hotkey_free()` / `assert_esc_free()`, so no probe overlaps the pending claim (F-020, windows-shell.md T-108 rule). Read the warning after `esc_claim`'s ordering (Recording indicator, then `hotkey_round_trip`), not by polling. Tests (1) to (4) are listed in `analysis.approach`.
    - (1) is the Acceptance-line-4 red test.
    - (2) is the owner's case.
    - (3) replaces today's hold-mode `a_refused_esc_claim_keeps_recording_and_warns_esc_unavailable` (it encodes the defect) with the toggle failure branch.
    - (4) is the hold failure branch and the CI proof of OQ-21's exact-match premise. If (4) shows bare Esc cancelling a hold, hypothesis 3 is true, and the invariant becomes "warn only when both claims are refused" in hold mode; the developer reports back.
  - Risk: low. The `cancel_key_result` signature changes in the core tests, and the claims themselves are unchanged (Esc is still intercepted only while recording, FR-22). Rollback: revert the commit.
- *B:* the shell gets the live mode with the claim request (`CancelKey::set(Some(mode))`) and reports one already-decided bool. Rejected: the shell would then judge recording semantics (windows-shell.md rule 1, dictation-session.md "a claim the shell decides on its own … is a second owner").
- *C (workaround, labelled):* drop the warning for any partial refusal. Rejected: it silences the real hold-mode failure.
