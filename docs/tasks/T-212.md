## Context

Owner check of build 0.1.397 (and 0.1.192 before it) on Windows 10.0.26300, hotkey Ctrl+Alt+Space, mode hold: `voicen.log` has `WARN warning kind=esc_unavailable` before every recording. The owner confirms (2026-11-12) that **Esc does cancel the recording**. So the warning is a false alarm.

Lead (not yet an analysis): `src-tauri/src/win/hotkey.rs` `cancel_key` registers two claims, bare Esc (`ESC_ID`) and Esc under the active hotkey's modifiers (`ESC_MOD_ID`, here Ctrl+Alt+Esc). It reports `cancel_key_result(self.esc && self.esc_mod, …)`, so a refusal of the modified claim alone makes `DictationSession::cancel_key_result` emit `Warning{EscUnavailable}`, although bare Esc is registered and cancels. Why Ctrl+Alt+Esc is refused on the owner's PC (system-reserved, another program) is unknown. The analysis decides what the warning must mean: bare Esc refused (cancel impossible) vs. only the modified one refused (cancel needs releasing the modifiers first). In hold mode the modifiers are held while recording, so whether Esc cancels while Ctrl+Alt are still down is part of the question.

## Acceptance

- [ ] `esc_unavailable` is logged only when Esc cannot cancel the recording at all; a refusal of only the modified claim is either not a warning or its own closed code (the analysis decides; `docs/decisions/diagnostics-log.md` names it)
- [ ] Failure branch: bare Esc refused (another program holds it) → `esc_unavailable` once per recording, the recording goes on — Windows CI shell test
- [ ] Owner's log on Windows after the fix: no `esc_unavailable` before recordings while Esc cancels
- [ ] Test that fails without the change: a shell test in `src-tauri/tests/` with the modified Esc claim held by another registration
