## Investigation

Context tools: Serena loaded but not used (it indexes Rust only; the seam is bash and workflow YAML), so grep and file reads; context7 `/github/docs` for `GITHUB_TOKEN` permission levels; read-only `gh run view` for runs 45102866589 and 45129205331.

**Frame.** Observed: a contour stage (review, and as of 2026-11-23 also implement) cannot read the `ci.yml` run of `wip/<ID>`. T-145 implement round 3 (run 45129205331) needed the failing test of red run 45102866589 (@ 47ecf23a, `wip/T-145`, `workflow_dispatch`), got REST 403 on `actions/jobs/<id>/logs` without a token, and escalated; the owner read `gh run view --log-failed` in the main tree and pushed the answer into the record (bc3b5c9a, decisions #342). **Hypotheses and evidence.**
1. *tw-wip-run refuses the contour branch* — confirmed: the branch regex accepts only `refs/heads/tw/<ID>`; the contour checks out `task/<ID>` ('Task branch, git hooks, the kit').
2. *The session has no token* — confirmed, by design (T-202 review 1 finding 1): `persist-credentials: false`, the stage step's env holds only `CLAUDE_CODE_OAUTH_TOKEN`, `MCP_TIMEOUT`, `SYSTEM_PROMPT`; the job token reaches only the push and chain steps. A public repo's run list is readable anonymously, but `gh` needs a login and job logs need auth (the 403).
3. *An actions-read token for one step is possible* — refuted: GitHub sets `GITHUB_TOKEN` permissions at workflow or `jobs.<job_id>` level only (context7 `/github/docs`, `authenticate-with-github_token.md`, `section-assigning-permissions-to-jobs-specific.md`); the agent job needs contents, issues and actions write. So an `actions: read` token is either a PAT secret (refused today by release-guard R4: only `secrets.CLAUDE_CODE_OAUTH_TOKEN` in `teamwright-agent.yml`) or a separate job's token (refused today by R3: `permissions` only in the owned head). A separate job's token ends with that job and cannot reach the session.
4. *"Usable only by that program" can hold for a token in the session* — refuted by the contour's own named limits (`docs/decisions/ci-toolchain.md`, contour exception): the session runs as the runner's OS user, so any env value or file it can pass to `tw-wip-run` it can read itself, and `curl` is not denied (only `Bash(gh:*)`). Acceptance 2 cannot be met with a token inside the session; acceptance 5's "a token with more than actions: read is refused" has no runtime check for a fine-grained PAT, only a static one for a job's `permissions:` block.
5. *tw-wip-run would have answered T-145* — refuted: on a red run it prints `FAILED JOB: <name>` from `run view --json jobs`; here that is "Windows build, install and smoke test", one job holding every shell test. The fix needed the failed step's log (`--log-failed`), which no owned template reads.
6. *Second path* — the main-tree workaround (`gates.md` › Contour review and the `CI:` line) and #342's one-time `task/<ID>` push are the two hand paths; the worktree path (`tw/<ID>`, owner's `gh` login) works and stays unchanged.
7. *Fixed before* — no F-entry covers the contour CI read (checked `docs/failures.md` F-001..F-034 on 2026-11-24: grep for `wip-run`, `CI read`, `log-failed`, `actions: read`; F-032 is the stage timeout, F-034 the T-145 Windows test itself, neither this class); OQ-83/#259 is the planned close, #342 its first sighting in the implement stage.
