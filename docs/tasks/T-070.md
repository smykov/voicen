## Context

The owner asked to have the built app sent to Telegram, as in their other projects (ECHO.me `/projects/echo-me/.github/workflows/flutter.yml` "Send Debug APK to Telegram"; AI Resume `/projects/ai-resume/.github/workflows/apk.yml` "Send the arm64 APK to Telegram"). The repository secrets `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are set (`gh secret list`, 2026-10-07). Which builds: decisions #93.

The installer is the NSIS `target/release/bundle/nsis/*-setup.exe` uploaded as `voicen-installer-<commit>` by the Windows job of `.github/workflows/ci.yml` (about 3.9 MB zipped in run 37579051772; the Telegram bot upload limit is 50 MB).

## Acceptance

- [ ] On a push to `main` or a `v*` tag, after every Windows install/smoke step is green, the job sends the `*-setup.exe` to `TELEGRAM_CHAT_ID` with a caption naming the version, the ref and the short commit (and the run link).
- [ ] Not sent for `pull_request`, `wip/**` or any other ref; not sent when an earlier step failed.
- [ ] The token never appears in a command line, log or file: it is passed to curl as config on stdin (the AI Resume pattern), not as an argument or URL in argv.
- [ ] No `TELEGRAM_BOT_TOKEN` (forks, a missing secret) → the step sends nothing and succeeds with one log line.
- [ ] Failure branch: the Telegram API refuses or is unreachable → the outcome is visible in the run (the analysis decides red step vs warning annotation, with the reason), and the token is not printed.
- [ ] P-016: the premises the step can check without sending (exactly one installer found, size under the limit, caption built) run on the `wip/T-070` CI run; the actual send is named as a `main`-only step in the ci-toolchain invariant's blind-spot list.
- [ ] `make check` tripwires stay green (`check-ci-wip` classifies the new step); docs (`CLAUDE.md` ci.yml row if it lists outputs, `docs/decisions/ci-toolchain.md`) updated.

## Investigation

Tools: Serena and Context7 were not used (CI YAML and shell, no indexed symbols or package API); grep and file reads over `.github/workflows/ci.yml`, `scripts/ci/*.sh`, `.gitleaks.toml`, `scripts/hooks/pre-commit`, `docs/decisions/ci-toolchain.md`, `PRINCIPLES.md` P-016 and the two reference workflows. curl option behaviour (`-K -`, `--fail-with-body`, curl >= 7.76) is from curl's manual knowledge, not a pinned doc: the premise step should print `curl --version` on the wip run so the send step's flags are proven against the runner's curl.

**Pattern.** AI Resume (`apk.yml`, step "Send the arm64 APK to Telegram"): `printf 'url = "...bot%s/sendDocument"' "$TOKEN" | curl -sS --fail -K - -F ...`. `printf` is a bash builtin, so the token is only on curl's stdin, never in a process argv; GitHub's secret masking is a second layer, not the guarantee. ECHO.me (`flutter.yml`, "Send Debug APK to Telegram") puts the token in the URL argument and has no `--fail`: take only its caption idea (version, ref, short commit) and add the run link `$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID`.

**Placement and shell.** After `actions/upload-artifact` (so the artifact exists even if Telegram fails) and before the runner probe, which is last with `!cancelled()` by design (its comment: "a probe defect cannot skip the deploy steps"). `shell: bash` (Git Bash on windows-latest, as the probe and "Commit of this build" steps already use; it has curl). Version: `src-tauri/tauri.conf.json` `"version"` (the value tauri stamps into the installer name `Voicen_<version>_x64-setup.exe`); read with sed as AI Resume does, and the premise step checks the found file name contains `_<version>_` so a version-source mismatch shows on wip. Commit: `$VOICEN_COMMIT`; ref: `$GITHUB_REF_NAME`.

**`if:`** on the send step only: `github.event_name == 'push' && (github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/tags/v'))`; no status function, so the implicit `success()` keeps it from running after any red step (Acceptance 2). `pull_request` and `wip/**` evaluate it to false.

**Failure branch: warning, not red.** Recommend `::warning::` + exit 0 for a Telegram/API/network error (print curl's exit code and the API's `description`, never the URL or config). Reasons: (1) the main run's Windows job is the "deployed" evidence the verifier reads for every `deploys: true` task; a notification failure after a green smoke would make a correct delivery look failed; (2) precedent in `docs/decisions/ci-toolchain.md`: the existing main-only steps (cache saves) also fail with a warning, never red; (3) the installer is still in the run artifact. Premise defects stay red: not exactly one `*-setup.exe`, or the name/version mismatch, fail the premise step on every ref, so they are caught on wip/T-070. Size >= 50 MB (Bot API upload limit): `::warning::` and a `send=false` output (the send step then logs "not sent: too large"); a growing installer is not a product defect and must not block a task's wip run.

**P-016.** The premise step runs on wip/T-070 and on every later wip run: one installer, size, version in name, caption printed (caption has no secret), `curl --version`. The send step itself is main/tag-only, so it joins the blind-spot list in `docs/decisions/ci-toolchain.md` (P-016 paragraph: "keep main-only steps to cache saves ...") and the P-016 "Not covered" text: the list must be widened to "cache saves and the Telegram send, each consuming only outputs of a step that did run on the wip run". `PRINCIPLES.md` P-016 quotes the same restriction ("such steps are kept to cache saves"); agents do not edit `PRINCIPLES.md`, so the developer updates the decisions doc and the orchestrator flags the P-016 wording to the owner (see question below).

**make check tripwires.** `check-ci-wip` (`scripts/ci/ci-wip.sh`) classifies only `uses:` steps; a block-style `run:` step passes, and the push trigger is unchanged. Do not use a third-party Telegram action: an unclassified `uses:` is a fail-closed violation. `check-ci-credentials` matches Credential Manager entry points only (cmdkey, vaultcmd, `Cred<Upper>`...): not touched. `check-shell-layout` refuses `--doc`/rustdoc in workflow steps: not touched. Secret scan: `TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}` matches neither `.gitleaks.toml` `generic-secret-assignment` (value starts with `$`, excluded) nor the pre-commit fallback (`:` form needs a quoted literal; `${...}` is a placeholder). No literal token anywhere.

**Docs in the same commit.** `docs/decisions/ci-toolchain.md` (the main-only list), `CLAUDE.md` ci.yml row (add "sends the installer to Telegram on main and v* tags"), `docs/architecture.md` only if it lists CI outputs.

**Owner question (not product; process wording).** `PRINCIPLES.md` P-016 "How checked" says main-only steps "are kept to cache saves whose inputs come from steps that did run on the wip run". Decision 93 adds a main-only step that is not a cache save. Does the owner ratify widening that sentence to "cache saves and the installer's Telegram send, each consuming only outputs of a step that ran on the wip run" (a P-016 wording amendment, owner-only), or is the decisions-doc entry enough? This does not block implementation: the design already meets the rule's intent (all inputs come from a wip-run step).
