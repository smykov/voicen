### The four points the caller raised

1. **GatedIndicator / TrayGate vs the T-009 tests.** `Rig::build(mode, None)` passes the same `FakeIndicator` as before. Only `Rig::gated` wraps it, and only the three new T-108 tests call that. The T-009 tests that moved to `esc_claim` (hold-mode Esc, toggle, max-length) now prove strictly more than before. They require the claim to have run (indicator, then round trip), no `Warning{EscUnavailable}`, and both combinations held. The failure branch still bites. If the shell never claims, the single `esc_claimed()` reads false, so the test gets `Err`. If the shell claims but reports a false success, the test also gets `Err`. If the shell never releases, `eventually(WAIT, esc_released)` fails. The planted collisions are deterministic. `Shared::publish` (`dictation.rs`) calls `cancel_key.set` before `indicator.set_tray`. `hotkey_pressed` runs on the hotkey thread (`WM_HOTKEY` arm). The gate therefore holds the only thread that could run the CancelKey request. Nothing to change.
2. **`esc_claim` / `hotkey_round_trip` in `hotkey.rs` instead of `win32_support`.** I accept this on substance. `esc_claim` needs `Rig` (indicator, observer, registrar), which is local to `hotkey.rs`, and `hotkey.rs` is the only file that probes Esc, so the rule still has one home. The task never says why it departs from the seam its analysis named, though (#4, Low).
3. **The round trip vs the active hotkey and the Esc ids.** It is safe. `Registrations::handle` handles `Prepare` by registering under the id that is not `active_id`. That is `SPARE_ID` (2) at startup, so never `ESC_ID` (3) or `ESC_MOD_ID` (4). It handles `Abort` by unregistering `pending.id` only. `WM_HOTKEY` matches `active_id` and the Esc ids only, so a spare registration cannot start a press. The one `stale` release in `Prepare` drops only an earlier pending prepare, and these rigs make no saves. All requests share one mpsc channel that the `WM_REGISTRAR` arm drains in order, so the CancelKey request queued earlier runs before the `Prepare`. `REQUEST_BUDGET` (10 s) is longer than the `SETTLE` (1 s) the pending-window tests hold the thread for. The read-back (`TakenHotkey::take()` refused, `combo_is_free(Ctrl+Alt+F9)`) runs only after the round trip, when nothing is pending.
4. **A new class `test-probe-takes-claimed-resource` vs folding into `test-port-race`.** A class of its own is acceptable. F-004's mechanism is a released port that the kernel hands back to someone else. F-020's is a probe that takes the very name the code under test needs. The rules differ, and F-012 set the precedent. See #5 for a counting side effect.

## Verdict rationale

The root cause is named with direct evidence: the red run printed `[Warning { code: EscUnavailable }]` under the old "Esc not claimed" message. The fix sits on the test side, where the analysis put it, and enforces the invariant through FIFO ordering signals rather than a clock. The round trip touches only the spare id, the T-009 tests prove strictly more than before, and CI is red then green at the right shas. One thing blocks. The docs this task adds state the rule in general terms and claim it has no other violation, but `a_registered_hotkey_stays_registered_across_a_resume_and_an_unlock` in the same file probes a registration still pending on the hotkey thread behind a `thread::sleep(SETTLE)`, the pattern the new "Don't" bans. Fix it with `hotkey_round_trip`, or record it as a known exception and correct the class row (#1). After that, and with the Low items optional, this can be approved.
