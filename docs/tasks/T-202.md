## Context

Owner decision #249 (option A): voicen moves to the teamwright autonomous contour on GitHub. The infrastructure exists outside the repository:
- a self-hosted runner `voicen-*` on host 105, labels `self-hosted, Linux, X64, claude`, one job at a time;
- `RUNS_DIR=/srv/gha-voicen-runs`;
- repo variable `TEAMWRIGHT_AUTH=subscription`;
- secret `CLAUDE_CODE_OAUTH_TOKEN`, set by the owner.

The kit ships no workflow (kit `docs/process/plugin.md` § tw-github, `docs/usage.md` § contour). The owner's other contour projects (smykov/spisok-pokupok, smykov/ai-resume) carry `teamwright-agent.yml` and `teamwright-next.yml` that can serve as the model; read them with `gh` (read-only).

The contour workflows need `contents: write` (and the matching issues and pull-requests scopes) to push `task/<ID>` branches and open pull requests. The project's CI guard refuses that. `make check-release-guard` (`scripts/ci/release-guard.sh`, rules R1-R10 over every file in `.github/workflows`) requires the workflow-level `permissions: contents: read` block (R1). The guard set also pins the other rules (`docs/decisions/ci-toolchain.md`, CLAUDE.md "Where things live" row for `.github/workflows/ci.yml`):
- `scripts/ci/action-lines.txt` and `scripts/ci/cache-steps/`: every line naming an action;
- `secrets.TELEGRAM_` only in the Telegram send step;
- the release job is the last job.

This is a guard change: `checker: true`, `analysis.decides_on` required, full review.

### 1. Frame

- Observed: the contour cannot be added; any file in `.github/workflows` that writes contents is refused by `make check-release-guard`.
- Expected (decision #249, option A): `teamwright-agent.yml` and `teamwright-next.yml` run on `[self-hosted, Linux, X64, claude]` with a write token. Every other workflow keeps a read-only token, and every other rule of the guard set still holds.
- This is not a defect. The guard does what T-085 / T-088 (decisions #120, #124, P-020) made it do. Its invariant "only the release job's token can write repository contents" is the thing the owner has now decided to widen. `recurrence_of` stays empty.

So the rules a contour file cannot satisfy are exactly R1, R3, R4, R5, plus R11 for its new action. R6 is not one of them: the model files trip it only on `\` line continuations, which can be written as single lines. In `release-guard.sh` the only rule that reads a file's name is R7 (`F[k] ~ /(^|\/)ci\.yml$/`). Every other rule is name-blind.

### 3. Hypotheses

1. **The guard is name-blind, so no single file can have a write token.** Confirmed by p2 and by the code: R1, R3, R4 and R5 hold for every `F[k]`.
2. **A second path also enumerates workflow files and would refuse the contour.** Checked:
   - `ci-credentials.sh` reads every `*.yml` / `*.yaml` in the dir and refuses Credential Manager names (`Cred<Upper>`, `cmdkey`, `vaultcmd`, ...). The contour files must not name any of them.
   - `whisper-model-key.test.sh` reads only `ci.yml`.
   - `release-guard.test.sh` copies `"$real"/*` for every real-dir mutation (`mutate`, lines 665-676). So the contour files must pass every rule in each of those copies, and they will, once they pass in the real dir.
   - `_task.py` and `tw-gate` treat `.github/` as non-code, so a later change to only the contour files needs no gate run and no `CI:` line.
   - No other `make check` target reads `.github/workflows`. I searched `scripts/`, `Makefile` and `*.mk` with grep for `.github` and `workflows`.
3. **This class was fixed before.** Partly. The guard's model was rewritten twice (F-015 / T-085, then T-088) to decide only on literals and raw tokens (P-020). So the exception must be a literal too. A reader of `permissions:` YAML is REJECT_RECURRENCE (ci-toolchain.md "Don't").
4. **Write is needed only for the push.** Refuted. `teamwright-next.yml` also needs `actions: write` (`gh workflow run`), `issues: write` and `pull-requests: write`, and the model's queue lock is a `contents: write` ref (`refs/tw-lock/queue`).
