## Code, read cold against the analysis (I1–I5, D1–D5)

- **I1/I2** `lib.rs::end_of_process`: the order is `call::finalize_on_exit` (gate `Exiting`, then `stop(SystemEnd)`), then `SessionEnd::end`, then `PendingAudio`. So `call_stopped` comes before `exited`. Every step is a no-op the second time. The `RunEvent::Exit` arm and the `win::end_session` hook (`take_end` once, `run_end` joins the `end-session` thread) are its only callers.
- **I3/D2** `tray.rs::exit`: this goes through `call::request_exit`, and `app.exit(0)` runs only without a call part. `Worker::serve(Exit)` either ends the loop through `end_loop` (`run_on_main_thread`) or calls `ask_exit` on the `call-exit-question` thread, guarded by the `asking` AtomicBool. A Yes posts `ExitConfirmed`, which sets the gate to exiting, stops with `Exit`, then ends the loop. The main thread never waits, and neither does the worker.
- **I4/D1** `hotkey.rs`: the suspend arm calls `on_suspend`. The resume arm (`LIFECYCLE_RESUME` only) calls `on_resume`. Unlock now only reasserts. In `serve`, `Sleep` holds the gate before `stop(Sleep)`. Every other request, `Resumed` included, releases the gate first. Core `notice_stopped` moves only `Sleep` into `Stopped{reason}`.
- **I5** `Worker::recover`: this runs on the worker before the request loop. It is the only `CallStore::recover`, and it enqueues `Recovery.queue` straight to the pass queue. That is correct: the gate is `Normal` at start, and recovery is not a session notice.
- **Seam (c)** `DeliveryGate`: `ShellCallShell::{notice, call_ready}` are the only session deliveries, and both go through `pass`. `Exiting` is final, and `hold` and `release` leave it alone. Refusal notices from `serve` go to the notifier directly. They answer a request, come after the release, and are not stop hand-offs, so this matches the seam.
