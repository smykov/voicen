## Investigation

Context gathering: Serena tools were not available in this session, so I used grep and file reads over `crates/`, `src/`, `src-tauri/src`, `e2e/` and `specs/002-local-transcription/`. No library API is new here: `std::fs::remove_file` and existing serde/tauri patterns. Because no package API is involved, I made no context7 lookup.

### Frame

- **Expected (spec US4, FR-021–FR-023, contracts/ipc.md:39):** deleting a downloaded model removes the file and the model lists as `not_downloaded`. If it was the selected built-in model, it is unloaded if loaded and the engine becomes `none`, persisted. Deleting while a transcription holds the model is refused with `model_in_use` and nothing changes. A removal error is `delete_failed`, and the model stays downloaded and usable.
- **Observed:** no delete path exists in any layer (evidence in the frontmatter).

### What exists, and what does not

1. **Coordinator:** `LocalModels` (service.rs) owns the store, the downloader and the transient `Downloading`/`Failed` map. Decision #57 makes it the one place the shell talks to, so delete belongs there. `ModelStore::delete` (core-traits.md:33) would sit beside it and could not clear a transient `Failed`. Without that clearing, a model whose `Failed` was hidden by a disk `Downloaded` (model-download.md, "Exception") would show `failed` again after the delete.
2. **Residency:** T-017 (TODO) owns `ModelResidency`. Its contract `unload_if(id) -> Result<(), InUse>` (core-traits.md:104) checks and unloads, but between that call and the removal a `prewarm`/`acquire` could load the file again. The port therefore returns a guard that blocks loads of `id` until the delete is over: `release_for_delete(id) -> Result<guard, InUse>`. Until T-017 the production value is `NoResidency`: never in use, nothing loaded, and `LocalModelView.loaded` stays false. Core tests use a fake that can answer `InUse`, records whether the final file still existed when it was called, and records when its guard drops.
3. **Settings reset:** `SettingsService::save` is the only writer, and it is wrong for this job. Step (2) reads all three credential slots, so a Credential Manager failure refuses the save. Step (3) revalidates the whole stored settings, so any field invalid in the file refuses it. A `SaveRequest` built from `snapshot()` outside `save_lock` overwrites a save that lands in between. The plan is a new `SettingsService::forget_model(id: &str) -> Result<ForgetOutcome { engine_reset: bool }, WriteFailed>`, run under `save_lock`:
   - `Unavailable` → no call (decision #19).
   - `model_id != Some(id)` → no write.
   - Otherwise: `model_id = None`, `engine = None` if it was `BuiltinLocal`, then `write_atomic`, swap and publish.
   - Publishing reaches `spawn_change_bridge`, so `settings://changed` reaches the window with no new emit path.
   - This keeps "one writer of settings.json" (decision #21; P-011).
4. **Order and failures inside `LocalModels::delete`:**
   1. Parse `id`. An unknown id is `not_downloaded`.
   2. Lock the transient map. A `Downloading` id is `not_downloaded`. So is an id whose `path_if_downloaded` is `None`.
   3. `release_for_delete`. `InUse` → `model_in_use`, nothing changed.
   4. `remove_file`. `NotFound` counts as removed. Any other error → `delete_failed`, with the settings untouched and the model still on disk. It was unloaded and reloads on next use, which is "usable" in FR-023's sense.
   5. Drop the transient entry of `id`.
   6. `settings.forget_model(id)`. Its write failure does not undo the removal; it is reported as `resetFailed`.
   7. Drop the guard.

   Holding the transient lock across the delete serialises it with `download`/`list`. That is deadlock-free: `forget_model` takes `save_lock`, and settings validation reads only the store, never the transient map.
5. **Event:** contracts/ipc.md:70 lists "deleted" among `local-model://state` causes. ipc.md:72 and model-download.md ("Events are emitted after the state update", "Don't: emit from the command") say every event comes from the download thread. Delete emits nothing. The UI re-lists after the delete invoke settles, as decision M's I4 already does for download, and ipc.md:70 is corrected.
6. **I/O failure on the Linux gate:** the container runs as uid 0 (`scripts/tw-run` passes `-u $(id -u)`, and `id -u` is 0 here). Permission tricks therefore do not make `remove_file` fail on a regular file, and the T-016 trick (a file in place of the dir) makes the model not downloaded in the first place. The plan:
   - `LocalModels` holds a private `remove: fn(&Path) -> io::Result<()>`, which `open` sets to `std::fs::remove_file`.
   - A `#[cfg(test)]` unit test in service.rs replaces it. That is allowed in voicen-core; only src-tauri forbids it.
   - A Windows CI shell test (`src-tauri/tests/local_models.rs`) holds the model file open without `FILE_SHARE_DELETE` and expects `delete_failed`, still `downloaded`, and `settings_get` unchanged. That is the real "locked" branch.
7. **UI:** `BuiltinLocal.svelte` is mounted only while the draft engine is `builtin_local` (settings-ui.md M). Delete is offered only on `downloaded` rows. It asks in an in-page `role="alertdialog"`, the same pattern as decision D, and no `window.confirm`. A confirmed delete calls `deleteLocalModel(id)` in `localModelsApi.ts`, the only IPC module (C). The button stays disabled until the invoke and the re-list after it have settled. A refusal goes through `asFailureReason` and appears in the section's existing `role="alert"`; anything that is not a FailureReason shows `error.ipc_unavailable`. A refusal changes no row. With a clean draft, `settings://changed` → `applyView` gives engine `none` and the section unmounts. No draft write is made in the UI (U1). Message ids are needed for `model_in_use`, `delete_failed` and `not_downloaded`, plus UI-only `local_models.delete*` labels, in en/ru through `messages!` (T-005), and the codes are added to `ReasonView`.
8. **Mock:** `e2e/support/tauriMock.ts` rejects unknown commands. It gets `local_model_delete`, with a scripted outcome or rejection queue. On `engineReset: true` it emits `settings://changed` with the scripted view, as the bridge does. It never validates (decision #38).

### Red tests (write first)

**Core:** `crates/voicen-core/tests/local_model_delete.rs`. These are the "model-delete tests" of the Acceptance; spec tasks.md T032 named `local_store.rs`, and a file of its own keeps the filter exact. Each test fails today because `LocalModels::delete` does not exist. Then each must bite on its own branch:
1. Delete of a downloaded `small` that is not selected: the file is gone, `list()` and `store().is_downloaded` say not downloaded, `engineReset` is false, and the fake `SettingsFile` has no write.
2. **Failure branch, selected:** `engine = builtin_local`, `model_id = small` → `engine = none`, `model_id = null` in the persisted bytes and in the snapshot received from `subscribe()`, `engineReset` true.
3. **Failure branch, loaded:** the fake `ModelRelease` saw the file still on disk when it was called, and its guard dropped after the removal.
4. In use → `model_in_use`. The file, the settings bytes and the list are unchanged, and no removal happened.
5. `not_downloaded`: for a model not on disk, for a model in `Downloading` (the fake server holds the body), and for an unknown id.
6. A transient `Failed` hidden by a disk `Downloaded` does not come back after the delete: the model lists `not_downloaded`.
7. The settings write fails after the removal (`fail_write`) → the file is gone, the outcome is `resetFailed`, and the snapshot is unchanged.
8. `Unavailable` settings → no file write, no credential call.
9. `model_id = small` with `engine = api` → `model_id` cleared, engine `api`, `engineReset` false (owner question 2).
10. Wire: `DeleteOutcome` serialises as `{engineReset, resetFailed}`, and the three codes as `ReasonView`. Added to `e2e/fixtures/local-models-wire.json` through `e2e_local_models_wire_fixture_matches_core`.
11. `delete_failed`: a `#[cfg(test)]` unit test in service.rs (injected remove error) → still downloaded, settings untouched. Plus the Windows CI lock test (item 6 above).

**Playwright** (`e2e/local-models.spec.ts`):
- Delete is shown only on downloaded rows.
- Keep in the dialog sends nothing. Confirm sends `local_model_delete {id:"small"}`, and the re-list shows `small` not downloaded with Download, and not selectable.
- **Failure branch:** `engineReset: true` with a clean draft → the Engine select shows `none` and the model section is gone.
- **Failure branch:** `model_in_use` and `delete_failed` show their message in the section, and `small` stays downloaded and selected.
- A non-FailureReason rejection → `error.ipc_unavailable`, never the rejection text.
- Delete and the other Delete buttons stay disabled while the invoke and its re-list are held.
- **T-045 Low #9:** mark base's `.model-status` element while `not_downloaded`, emit `failed`, and assert that the same marked element now contains `local-model-reason`.

### Folded-in review notes

- **T-044 Low (1):** in `a_failed_never_hides_a_model_downloaded_on_disk_and_a_retry_does_not_bring_it_back`, remove the `states()` call between `put` and `refused`, so the refusal meets the transient `Failed`. Then `std::fs::remove_file` the final file and expect `not_downloaded`: a restored `Failed` would show `failed`. Do not use `delete` there, because it clears the transient entry itself and the test would stop biting. Fix the comment accordingly.
- **T-044 Low (2):** reword the accepted gap in model-download.md and the comment at download.rs:373-376. The stale end state lasts until the new download's first progress event, or until its own end event if that comes first. If the new download had already ended before the late event was recorded, the stale state stays until the next start. A late `Failed` over a finished download is still hidden by the disk `Downloaded` rule.

### Owner / orchestrator questions

None of these blocks the task; each has a default above.
1. **Dependency on T-017** (orchestrator): T-019 defines the `ModelRelease` port with `NoResidency` instead of waiting for T-017. In the meantime "unload the loaded model first" is proven only with the core fake. Alternative: add T-017 to `depends_on`, which blocks T-019 until T-017 is done.
2. **Owner, product:** if `builtin_local.model_id` names the deleted model while another engine is active, the default clears `model_id` and keeps the engine (`engineReset` false). The spec only covers the selected-and-active case.
3. **Owner, product:** if the file was removed but the settings write fails, the default reports success with `resetFailed: true` and the section shows `settings.write_failed`. The engine stays `builtin_local` pointing at a missing model, and FR-07's "no local model" branch then applies at the next hotkey. This changes the contract `{ engineReset }`.
4. **Informational:** deleting the selected model with a clean draft switches the window to engine `none`, and the model list disappears with it. That follows from spec US4 together with decision M. With a dirty draft, the draft keeps `builtin_local`+id, and Save is refused with `model.not_downloaded` on the select (U2).
