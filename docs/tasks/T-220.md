## Context

From follow-up T-128 r1#2 (Medium, silent-degradation), owner's grouping 2026-11-17: `let _ = call::start_calls(...)` drops a start failure with no log line, leaving every call entry a silent no-op; write one closed `LogEvent` (e.g. `call_start_failed`) on `Err`, like `dictation_start_failed` (src-tauri/src/lib.rs:511). Check first whether later work already changed this site. No transcript text, audio or keys in the line (FR-20, NFR-04).

## Investigation

Tools: Serena was loaded. The searches were plain text (ripgrep over the repo, excluding `docs/tasks/**`) for `start_calls`, `dictation_start_failed`, `call_start_failed`, `DictationStartFailed`, plus the pins of the last two added kinds (`call_hotkey_register_failed`, `pending_audio_cleanup_failed`). The code was read directly. No library API is involved, so context7 was not needed.

**Frame.** Observed: `lib.rs::run` calls `let _ = call::start_calls(app.handle(), release_call_ports(..))`. When it returns `Err`, the call part is not managed. Every call entry then does nothing and writes nothing: tray Record, Calls, the call hotkey's `call::request`, `--call record` and the five `calls_*` commands, which answer an empty list or `notFound`. The log has no line saying why. Expected: one closed warning line, as dictation writes `dictation_start_failed`, and the app keeps running.

**Already fixed?** No. At 75c8cfd4 the call site is unchanged (`lib.rs::run`, the `let _ = call::start_calls(` statement). The later commits to `lib.rs` and `call.rs` (T-139 fea47f4d, T-142 0df65f4c, T-213 1792800e) did not touch it. `call_start_failed` appears nowhere outside this task record.

**Hypotheses.**
1. *start_calls logs internally, so the `let _` loses nothing.* Refuted: `call::start_calls` has `Err` returns for no Log, no SettingsService, an existing call part (AlreadyExists), and `spawn_tick` / `spawn_worker` / `spawn_opener` failing. None of them writes a line.
2. *A second path reports it (tray, notifier, smoke).* Refuted: no `WarningKind` or `LogEvent` names a call start. `call::request` on an app without a part is a no-op by design, and `call_launch.rs::the_call_part_is_started_by_call_start_calls_not_by_build_app` pins "no line". The sibling `let _` sites in `lib.rs` are covered or deliberate. `settings_window::on_ready` is logged by its opener thread (`settings_window_failed`). `tray::on_second_instance` writes nothing, by its contract. `PendingAudio::delete_all` on exit is ignored on purpose because the next start retries.
3. *This class was fixed before.* The pattern exists for dictation (T-006): `dictation::start_dictation_with` writes `Warning{DictationStartFailed, os_code}` through its `failed` closure on every `Err` after the Log is found. The call part (T-128) copied the structure but not the logging. This is not a recurrence at this site, which was never fixed. It is the same family as F-024 (a swallowed error), but F-024's mechanism is the test-writer's bite check missing a swallow. Here the swallow is in production code at the caller, and review found it (T-128 r1#2). No `recurrence_of` and no rca.
4. *The Err could carry something not loggable.* Checked: the reasons are `io::Error` with static English messages and `raw_os_error()` from `thread::Builder::spawn`. Only the closed kind and the OS code go into the line. There is no transcript, audio, key or path (FR-20, NFR-04, P-009).

**Root cause.** The call part's one wiring function returns its failures without logging them, and its only production caller drops the `Result`. Core's closed `WarningKind` has no call-start kind, so a correct writer has no literal to use.

**Reason kind.** The closed `Warning` grammar is `warning kind=<literal> [os_code=<n>]` (`diag/format.rs`). It has no `reason=` key. The task's model, `dictation_start_failed`, uses the kind plus `os_code` only. Option A follows that exactly. A thread-spawn failure carries its OS code, and a wiring failure (missing part, already started) has none. A separate `reason=` field (no_settings | already_started | thread) would be a new line shape. That is Option B below, and I do not recommend it for this P3.

**Seam.** `call::start_calls`. A `failed` closure is built right after the Log is found and wraps the five later `Err` returns, the same way dictation does it. The first `Err` (no managed Log) cannot log, the same as dictation. In `run()` assemble always manages the Log, so that `Err` does not happen in production. Core changes vocabulary only: `WarningKind::CallStartFailed` and the `call_start_failed` literal. `lib.rs::run` keeps `let _ =`, and only its comment changes to "logged where it failed (`call_start_failed`)". This is one seam and the behaviour is settled. It is not large work.

**Options.**
- **A (recommended): a Warning kind written inside `start_calls`.** It removes the cause because every failing path goes through the one function. Red tests:
  - Linux gate: in `crates/voicen-core/tests/diag_format.rs::all_warning_kinds`, add `(WarningKind::CallStartFailed, "call_start_failed")`, match arm `=> 20` and count 21. Add `"call_start_failed"` to `tests/diag_support/mod.rs::WARNING_KINDS`; the line-grammar validator reads it, and `diag_format.rs` asserts that the two lengths are equal. These fail to compile before the variant exists, then pass once `event.rs` and `format.rs` have it.
  - Windows CI: `src-tauri/tests/call_launch.rs::a_second_start_calls_writes_one_call_start_failed_line`. Steps:
    1. `CallRig::started(..)`.
    2. A second start through a new `CallRig::try_start` in `call_shell_support/mod.rs` that returns the `io::Result` (`start_ports` keeps its `expect`).
    3. Assert `Err` with `ErrorKind::AlreadyExists`.
    4. Assert `rig.count(&["warning", "kind=call_start_failed"]) == 1`.
    5. Assert the first `CallSession` is still managed and a tray Record still produces `call_requested`.

    Before the change the count is 0. It is the only failure that can be forced through the public API: the rig always manages the Log and the SettingsService, and a thread spawn cannot be made to fail. The count also checks the Ok path, because the first start must leave the count at 0, which you can assert before the second start.

  Risk: low. It is additive and the line is WARN. Rollback: revert the commit.
- **B: a dedicated `LogEvent::CallStartFailed { reason }` with a closed reason enum.** It gives a finer reason, but it adds a new event shape to the grammar validator, format tests and docs for no user-facing gain. Its red tests would be the same as A's. Higher churn.
- **C: log in `run()` on the `Err` (`if let Err(e) = start_calls(..) { log.write(..) }`).** This is a workaround at the caller. The Windows shell test cannot see it, because no test runs `run()` (T-128 r1#1), and it splits from the dictation pattern. Not recommended.

**Docs in the same commit.**
- `docs/decisions/diagnostics-log.md`: the Warning-kind list gets `call_start_failed` with its four causes.
- `docs/decisions/windows-shell.md` § "The shell's call part has one request worker...": "a failed `start_calls` writes one `call_start_failed` line; the app runs on with call entries as no-ops"; the test is cited there.
- The `lib.rs::run` comment.

No guard path is touched (`scripts/ci`, `Makefile`), so `checker: false` and `decides_on` stay empty.

**Open decision.** None blocking. The acceptance wording "with the reason kind" is read as the closed warning kind plus `os_code` where one exists, the same as the named model `dictation_start_failed`. If the owner wants a distinct `reason=` field, that is Option B and changes the line grammar. It should be recorded as a decision first.
