## Context

Split out of the T-086 audit (decision #124). `scripts/ci/helper-windows.sh` has two rules:
- The main rule decides on the token `CreateWindowEx`, the owned manifest and `cargo metadata`, and conforms to P-020.
- The product-class rule (no product window class may be listed as a visible helper) decides on the call-syntax regex `window_classname\("[^"]*"\)`, and it leaks.

The probe: `"Tauri Window"` passed through a `const` exits 0 even with `Tauri Window` listed as `visible-helper`, while the base fixture exits 1. The proposal is a raw-token rule: a class listed as a visible helper must not occur as raw text in a product-window crate.

## Acceptance

- [ ] The product-class rule decides on a raw token, keeps no call-syntax reader, and its `decides_on` is named.
- [ ] Failure branch: the `const` probe is refused, and the fixture is red against the old guard. The existing helper-windows fixtures stay as they are.
- [ ] `docs/decisions/overlay.md` §5 and the guard table in `docs/decisions/ci-toolchain.md` are updated. `make check` is green.

## Investigation

**Method.** I used grep and file reads on `scripts/ci/helper-windows.sh`, its harness, the fixtures and the registry sources (shell scripts and fixture text are not indexed by Serena). I did not need context7 because no library API is called: the facts about tauri come from the pinned sources in the registry cache, tauri-runtime-wry 2.12.1, tauri 2.12.1, tauri-utils 2.10.1 and tao 0.37.1. I got the real graph from `cargo metadata --locked --filter-platform x86_64-pc-windows-msvc --manifest-path src-tauri/Cargo.toml` in the core image (through the host wrapper). It has 298 packages; the workspace members are voicen and voicen-core. Probes, the prototype and the logs are in `/root/.claude/jobs/97682091/tmp/t091-inv/`: `old/` and `new/` hold the guard copies, plus `probes/`, `fx.*.out`, `real*.out` and `realgraph.txt`. HEAD is 8b67150.

### 1. The leak (red baseline)
The product-class rule has three parts, and all three use one reader:
- `scan_one` captures `window_classname("…")` with an ERE;
- the manifest loop compares each resolved `visible-helper` class with the captures (`grep -qxF`);
- an empty capture set means cannot run.

So the rule decides on its own model of a Rust call. Each probe below is `v-product-class-helper` (`Tauri Window` listed as `visible-helper` for tauri-runtime-wry) with only the runtime's line changed:

| Probe | Runtime line | Old guard | Prototype |
|---|---|---|---|
| base | `window_classname("Tauri Window")` | 1 | 1 |
| p1 (T-086) | `const PRODUCT_CLASS = "Tauri Window"` … `window_classname(PRODUCT_CLASS)` + `window_classname("Tauri Overlay")` | **0** | 1 |
| p2 | const only | 3 | 1 |
| p3 | `window_classname( "Tauri Window" )` | **0** | 1 |
| p4 | `window_classname(r"Tauri Window")` | **0** | 1 |
| p5 | `window_classname(String::from("Tauri Window"))` | **0** | 1 |
| p6 | literal on the next line | **0** | 1 |
| p7 | `"Tauri \u{57}indow"` | 0 | 0 (residual) |
| p8 | `concat!("Tauri ", "Window")` | 0 | 0 (residual) |
| p9 | only in a `//` comment, another class in the call | 1 | 1 |

### 2. Where product classes come from (sources checked)
- **tauri-runtime-wry 2.12.1** `WindowBuilderWrapper::new` sets the default `"Tauri Window"` under `cfg(windows)`. `WindowBuilderWrapper::with_config` starts from `new()` and then applies `config.window_classname`. Every tauri window goes through one of these, including the overlay (`src-tauri/src/overlay.rs` `WebviewWindowBuilder::new`) and the settings window. Neither of those sets a class.
- **The app**: `tauri.conf.json` `windowClassname` (the tauri-utils `WindowConfig::window_classname` field, default `None`) and any `.window_classname(...)` call in `src-tauri/src`. None exist today. CI builds with `pnpm tauri build` and no `--config`.
  - **The old rule never looks here, so this is a second path.** The graph walk drops workspace members (`seen - members`), and `tauri.conf.json` is read only for `identifier`.
- **tauri 2.12.1** only passes the class through (`WindowBuilder::window_classname`, `WebviewWindowBuilder::window_classname`). It has no literal.
- **tao 0.37.1** has the default `"Window Class"` (`platform_impl/windows/mod.rs`, `PlatformSpecificWindowBuilderAttributes`). Tauri windows never get it, because runtime-wry always sets a class.
  - tao cannot be a product crate under a raw-token rule: its source holds its own visible helper `Tao Thread Event Target`.
  - Exempting "the entry's own crate" would reopen the probe, because the probe lists the runtime's class under the runtime's own entry.

### 3. Which crates count as product-window crates, and how that is decided
- **An owned list in the script, matched by package name against the cargo-metadata graph: `tauri-runtime-wry`.**
- **A required crate:** if it is not in the graph, the guard cannot run. That replaces "no literal captured" as the proof that the rule's input exists.
- **Plus the owned app dir:** `--app-dir`, default `src-tauri`, minus `tests/`.

Rejected ways to decide the set:
- **Derived from cargo metadata.** Metadata says which packages are linked, not which one names a window class. Any rule derived from it (dependents of tao, implementors of tauri-runtime) would be a model.
- **Every crate in the graph.** This false-refuses tao's own helper, and an own-crate exemption reopens p1.

Optional: add `tauri`, `tauri-utils` and `tauri-runtime` to the list as scanned-when-present (not required). That would catch the default literal moving between tauri crates. Measured: none of them holds a helper class today. They are not required because the committed fixture graphs only hold tauri-runtime-wry.

### 4. False positives
I grepped the whole repo and the 298-package graph for the resolved visible-helper classes of the committed and fixture manifests: `Tao Thread Event Target`, `dev.voicen.app-sic`, `dev.voicen.app-sic-0`, `Tauri Window` and `Voicen Main Window`.
- **Graph.** Each class occurs only in its own crate: tao, tauri-plugin-single-instance (`format!("{id}-sic")`, so the resolved class never occurs) and tauri-runtime-wry. None occurs in tauri-runtime-wry, so the committed manifest passes. Prototype: real graph exit 0.
- **App dir.** `src-tauri/tests/smoke_predicate.rs` holds `Tao Thread Event Target` and `Tauri Window` (consts `TAO_EVENT_TARGET`, `TAURI_WINDOW`) and `{id}-sic` as test data. That is why the app dir excludes `tests/`. No other src-tauri file holds a helper class: I checked the tracked files and also the untracked `gen/`.
- **Other places that are not scanned and need no handling.** `scripts/ci/helper-windows.txt` and the harness comments, `visible-windows.ps1`, `ci.yml` (`tray_icon_app` is a hidden helper and not checked), and `src-tauri/tests/lifecycle.rs` and `tray.rs` (`tray_icon_app`).
- **Case.** The match is case-sensitive, on purpose. The predicate compares classes ordinally (`VoicenWindows.Shown` uses `Array.IndexOf`; `helper_windows::is_helper` uses `==`), so a differently cased listing never excludes a product window.
- **Substrings.** A short visible-helper class that is a substring of runtime text is refused. That is fail-closed, and it errs loud.

### 5. Options
- **A (minimum):** the owned crate list with the raw-token rule; the app dir is not scanned.
  - It closes p1–p6.
  - The app path stays a gap. Log it as a follow-up task.
- **A+app (recommended):** A plus `--app-dir`. The default `src-tauri` keeps every committed fixture's verdict, because the real app dir holds no fixture class (§4). The identifier is read from `<app-dir>/tauri.conf.json`.
  - About 15 more lines.
  - It closes the invariant over every source that names a product class.
- **B (rejected): keep the reader and widen the regex** (spaces, `r"`, a const lookup). This is the patch-the-model path that P-020 forbids (REJECT_RECURRENCE).

**Default-mode wiring.** The registry paths exist only in the core image. Steps:
1. Pre-read the manifest's resolved visible-helper classes on the host.
2. Write them to `target/helper-windows/run.*/helper-classes.txt` next to `roots.txt`.
3. `--scan-roots` reads that file and prints `H <crate>@<version> <class>` per hit, plus `D <crate>@<version>` per owned product crate found, so the required-crate check needs no second docker run.

In graph mode the same `scan_one` runs on the host. The app-dir grep is always on the host.

**Fixtures.**
- The 18 committed fixture dirs stay byte-identical. 17 keep their exit codes and needles. The prototype's message names `<key>`, the class and the product crate, so the `tauri-runtime-wry@2.12.1`, `Tauri Window` and `Voicen Main Window` needles still match.
- **c-no-product-class** has to change in the harness table: 3 becomes 0 (`ok:`), with a comment. Its exit 3 exists only because the call-syntax reader found no literal, so it cannot stay without keeping the reader. This needs the orchestrator to accept it: the Acceptance says the fixtures "stay as they are", and the files do.
- **Grep-shim rows.** "window_classname grep fails on tao" no longer applies, because tao is not a product crate (prototype: exit 0). Drop it or re-key it. "… fails on tauri-runtime-wry" is re-keyed to the helper-class grep on the runtime dir (prototype: exit 3, `grep failed on …/tauri-runtime-wry-2.12.1/src`).
- **Harness header.** The comment "every fixture graph holds tauri-runtime-wry with its window_classname literal" is reworded.

**Red tests (each red on the old guard).**
- v-product-class-const: p1, old 0, want 1.
- v-product-class-spelling: p3–p6, old 0, want 1.
- c-no-product-crate: graph without tauri-runtime-wry. Old 3, but only for "no literal". Want 3 with the needle naming the owned crate, so the old guard is red on the needle.
- v-app-class: `--app-dir` fixture with `"windowClassname": "Tao Thread Event Target"`. Old 3 (unknown option), want 1.

**Docs.**
- `docs/decisions/overlay.md` §5, the host-tripwire bullet: the product classes are now the raw class tokens in tauri-runtime-wry and the app dir. Not caught: an escaped or `concat!` class.
- `docs/decisions/ci-toolchain.md`: the helper-windows enforcement bullets, and the product-class guard-table row becomes `token + literal + platform`, conforms.
- The comments in the `helper-windows.txt` header and the guard header.

**Residuals (Not caught).**
- A class written with escapes, `concat!`, or built at run time (p7, p8; the old guard leaked these too).
- The default literal moving to a crate that is not on the owned list. A version bump of tauri-runtime-wry is re-read anyway.
- A class from a build-time `--config` (unused).

### 6. Recurrence
- The class is guard-model: F-003, F-015, the T-086 audit, T-087, T-088 (BLOCKED) and T-089.
- T-091 is the planned P-020 application from decisions #124. It is not a new recurrence: the defect was found by the audit probe, not in CI or review, and nothing was patched before.
- The new rule adds no reader. It decides on raw class tokens, the owned crate list and dir, and cargo metadata.
- The one point to note is c-no-product-class. It encoded the old reader's own input check, which is the guard-model mechanism inside a fixture.

**Size.** Small: one seam (`helper-windows.sh`), plus its harness, 4 new fixtures and 3 doc spots.
