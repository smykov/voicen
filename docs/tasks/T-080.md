## Context

Opened by the T-078 review, round 1 (`docs/tasks/T-078.reviews/1.md`, verdict `REJECT_RECURRENCE`). Owner: `problem-investigator`.

Class `os-answer-deadline-race` in `docs/failures.md` (renamed by T-078 from `windows-refused-connect-timing`), now 2 entries:

- F-005 (T-048; first sighting in T-047 reviews 1-2): a whole-request deadline below the Windows refusal time (~2.17 s) decided the failure reason. Fix: `REFUSAL_BUDGET` / `refused_timeouts()` / the `refused_addr()` probe in `crates/voicen-core/tests/common/mod.rs`.
- F-013 (T-078): reqwest 0.13.5 times the DNS lookup inside `connect_timeout`; a lost UDP answer made the `.invalid` cases `CannotReach`. Fix (kept as a temporary workaround, see T-078): the mirror of F-005's, `RESOLVER_BUDGET` / `resolver_timeouts()` / the `unresolvable_host()` probe. The same entry also logs a second mechanism, fixed wall-clock margins under host load, fixed by widening bounds through `common::OVERHEAD_ALLOWANCE` (earlier bound widenings of the same kind: T-047 2 s → 4 s, T-046 on its own branch).

Each instance got its own budget constant, probe and timeouts helper; whether a new test uses them is checked by review only (T1). `docs/failures.md` and `docs/process/principles.md` §2 say a second entry of a class moves its rule up a tier, which is an owner decision (exit (c)); T-078 left it as a sentence in the class row with no vehicle to the owner. This task is that vehicle.

Signals for the exit (the investigator recommends, the owner decides (b) and (c)):
- (a) code: both instances live in one seam (`tests/common/mod.rs`); a single "deadline vs OS answer" helper or a guard could replace per-kind budgets.
- (b) architecture: the race on the resolver path exists because the product times DNS inside the connect timeout and builds an HTTP client (thread + CA-bundle parse, 64-781 ms measured) per call; T-079 / OQ-22 owns the reason and the ~20 s wait, nothing owns the per-call build cost that sits in every timed window (and in NFR-01's stop → paste path). `local_models::download` builds its own client with the same DNS-under-timer behaviour (second path).
- (c) process: the rule is T1 only and the class has recurred; candidates are a `make check` tripwire (no `.invalid` / refused literal outside the helpers, no fixed `Duration` upper bound in a timeout test without `OVERHEAD_ALLOWANCE`) or a PRINCIPLES.md entry. Also open: whether the host load a timing test must withstand is documented anywhere (T-078 found it is not).

Note for the analysis: spec 003 SC-003 fixes the post-processing give-up tolerance at ≤ 0.5 s; any bound rule must respect it or go to the owner as a spec change.

## Investigation

**How I looked.** Serena was not connected (no `mcp__serena__*` tools), so I used `git log`/`git diff`/`git merge-base`, grep and file reads over `crates/voicen-core/{src,tests}`, the `tw/T-078` and `tw/T-046` branches, `docs/`, `specs/003-*`. I made no runs: the T-078 records already hold the red/green evidence for the resolver mechanism, and this analysis only needed history and code structure. I did not re-read reqwest; the T-078 Investigation's source reading is used as is. Metrics: `python3 -I scripts/metrics/teamwright-metrics`.

**Frame.** The class is `os-answer-deadline-race`. A core test's verdict was decided by which of two clocks ran out first, where the test sets one clock and does not control the other. The test-side clock is a `Timeouts` field or a `took <` ceiling. The other clock is one of:
- the Windows refusal time (F-005);
- the glibc resolver retry schedule (F-013);
- host scheduling and per-call client build under load (F-013 mechanism 2, T-047, T-046).

Expected: a test decides only what it names.

**Hypotheses.**
1. *Each fix drew the invariant per kind of uncontrolled clock, so the next kind stays open.* **Confirmed.**
   - F-005's invariant reads "every deadline on a refused path" (`docs/decisions/core-tests.md`).
   - The `.invalid` tests came in with T-040 (37e0ba4, 2026-10-04 07:38). That commit is an ancestor of F-005's fix bf52b2f, so they were already in the tree when the invariant was written and were left out by its wording.
   - T-078 then added a second budget, probe and helper (`RESOLVER_BUDGET`, `unresolvable_host()`, `resolver_timeouts()`) and a third constant for load (`OVERHEAD_ALLOWANCE`).
   - The reviewer's "a third helper tomorrow" holds: the blackhole test already says the unrouted case is vacuous on Windows (`api_pipeline::blackhole_connect_is_bounded_by_connect_timeout`), and nothing sizes its deadlines.
2. *The rule is enforced only by review (T1), and review missed it.* **Refuted as the cause of F-013, true as a gap.** No reviewer skipped a rule: the `.invalid` tests predate it, and the rule as worded did not cover them. Moving the per-kind rule up a tier (a grep for refused-path deadlines) would not have caught F-013. A guard helps only once the invariant is kind-independent.
3. *The product causes the race (DNS timed inside the connect timeout; an HTTP client built per call).* **Partly true. The product is not where the class lives.**
   - DNS under the timer is why the resolver is in the race at all. Under OQ-22 option (b), a fast DNS failure and a lookup cut off at the deadline would both give `NetworkUnavailable`, and that instance would disappear. Under OQ-22 (a) it stays.
   - The Windows refusal time and host load are not product behaviour, so a product change cannot close the class. The product defect (the job waits about 20 s, past FR-24) is already owned by T-079 / OQ-22.
   - Client build: `OpenAiCompatibleEngine::send` and `post_process::chat::send` call `http::client(connect)` before `RequestBuilder::timeout(deadline)`, so no product deadline includes the build cost. It falls only inside test wall-clock windows.
   - Its effect on NFR-01 (64-247 ms of a 3 s p90 budget, measured sequentially in a debug build) is a possible performance task, not part of this class. Not proposed here: it is not needed to close the class, and the lifecycle allows at most two spawned tasks.
4. *The same concern is handled on a second path.* **Yes, in two places.**
   - `local_models::download::transfer` builds its own `Client::builder().connect_timeout(..)`, a second product path with DNS under the timer (T-079's scope).
   - On the test side, `tw/T-046` (`connection_test`) solved mechanism 2 differently. It dropped the ceilings ("every longer wrong limit lets the 6 s answer through as Ok, so the Timeout assertion catches it; a ceiling caught nothing more and tripped under host load"), while T-078 widened them. So two patterns for one concern exist today.
5. *Fixed before.* **Yes:** F-005 / T-048, the T-047 r1-2 widening of 2 s → 4 s, T-046 r1 #2 and F-013 / T-078. They are listed under "Earlier patches" below.

**Evidence.**
- Ceilings still on `main` (`grep -n "took <\|elapsed <\|< Duration::from\|stage <=" crates/voicen-core/tests/*.rs`): 14 wall-clock ceilings in six files, and T-078 touched only five of them.
  - `local_download::cancel_during_steady_transfer_ends_cancelled_quickly` asserts `took < 1 s`, but its stated bite ("the download finishes instead") is already caught by the `Cancelled` outcome. This is a latent instance of mechanism 2 that no task owns.
- The bites of T-078's widened ceilings can be caught by the outcome, with no ceiling:
  - In `blackhole_connect_is_bounded_by_connect_timeout`, with the original 3 s total, the production 5 s connect would end as `Timeout` instead of `CannotReach`. So that bite is caught by the reason. That total timer starts at `send`, after the client build, so build cost is not in the race. T-078 raised the total to 10 s, which turned an outcome-caught bite into a wall-clock one and needed `OVERHEAD_ALLOWANCE`.
  - In the configured-timeout cases, the longer wrong limits (30 s, 60 s, 600 s) are already caught by `Delivered`. A retry after the timeout is caught by the mock's request count. The too-early limit (the 2 s connect value) is caught by the lower bound.
- The one ceiling a spec requires is SC-003 (spec 003 `spec.md`: "measured tolerance ≤ 0.5 s"), mirrored in contract guarantee 4. The 15 s case never failed. The 5 s case failed only under a load the T-078 Investigation calls heavier than the gate, and once on a cold single-sample baseline, which min-of-3 fixes. The T-078 reviewer's run of four binaries, sequential as in the gate, passed. No document says which host load a timing test must hold under; the owner's host limits (Playwright workers=2, cargo -j2, one heavy gate per agent at a time) are the closest thing. → OQ-23.
- Hotspots: neither `tests/common` nor `src/engine/http.rs` is in the recurring areas or the hotspots (teamwright-metrics, 2026-10). The class stays inside one test seam plus its callers.

**Root cause.** Core tests let a clock they do not control decide the verdict. Each fix closed one kind of such clock (refusal, then resolver, then load) with its own budget, instead of stating a kind-independent rule in the shared test seam, so every kind not yet listed stays open. This explains all the instances:
- F-005: refusal vs a 300 ms total.
- F-013 (1): the resolver retry vs a 2 s connect.
- F-013 (2), T-047 and T-046: host load vs fixed ceilings.
- It also explains why F-013 got past F-005's rule: the rule was scoped by kind.

Contradicting evidence: none. The resolver instance also has a product contributor (DNS under the connect timer), which T-079 owns. Removing it would close only that kind.

**Invariant (closed).**
- (I1) An OS-answer target (refused, unresolvable, unrouted) exists in a core test only as a `tests/common` case that carries its own deadlines. Every product deadline of that case is at least one `OS_ANSWER_BUDGET`, and the target's own probe proves the budget is at least twice the measured answer time. A new kind of OS answer adds only a probe, not a budget or a helper.
- (I2) A wall-clock reading in a core test decides only a lower bound, because a deadline never fires early. A wrong longer limit is caught by the outcome: the server answers between the right and the wrong limit, or the mock's request count shows it. The only ceiling is a spec-stated tolerance (today SC-003), asserted through one `tests/common` helper that names the spec id and the documented load (OQ-23).

**Seam and paths.**
- `crates/voicen-core/tests/common`:
  - One case type (target + timeouts; `refused_addr`/`unresolvable_host` no longer public on their own).
  - One budget, one probe per kind.
  - One timing module: `at_least(took, deadline)` and `within_spec(stage, want, tol, "SC-003")`, replacing `OVERHEAD_ALLOWANCE`.
- Callers routed through it: `openai_client`, `api_pipeline`, `local_server`, `diag_pipeline`, `local_download`, `local_download_refused`, `post_process_chat`, `post_process_timeout`, and T-046's `connection_test` when it merges.
- `fakes.rs` and the `silent_server` hold loop use `Instant` for non-assertion purposes; they move into `common` or use a helper there.

**Approach options.**
1. **(Recommended) exit (a): the invariant in `tests/common` plus a `make check` tripwire (T3)** with fixtures, in the pattern of `make check-setup-node-cache`. The tripwire fails on:
   - an OS-answer literal outside `tests/common` (`voicen-test.invalid`, `127.0.0.1:1`, the blackhole target `192.0.2.1`; `settings_log.rs`'s `192.0.2.10` is log data and must stay outside the pattern by exact match);
   - a bare `Instant::now()` / `.elapsed()` in `crates/voicen-core/tests/*.rs` outside `common`.

   It decides on raw text the tool cannot reinterpret (F-003 lesson). Red first, on a throwaway copy:
   - (i) a test with `voicen-test.invalid` and a 2 s connect outside the helper → the tripwire fails;
   - (ii) a test with `assert!(took < Duration::from_millis(1500))` → the tripwire fails;
   - (iii) the `--dns 192.0.2.1` run of the two `openai_client` cases stays green through the new case type (it is red on `main`, 0/2);
   - (iv) `within_spec` with a 0.6 s stage over a 0.5 s tolerance → red.

   Record the class move from T1 to T3 in `docs/decisions.md`, `docs/decisions/core-tests.md` (one invariant replacing "refused path") and the `docs/failures.md` class row. Risk: migrating about 67 `Instant`/`elapsed` uses across 12 files, which is mechanical. Rollback: revert the commit; the T-078 workaround stays underneath.
2. **Exit (c): a PRINCIPLES.md entry ("a test verdict never races a clock the test does not control") at T1/T2.** Same artefact as option 1's rule, but as a project principle. It needs the owner and a version bump, and without option 1's tripwire it stays review-only, which is the gap the reviewer named. Worth considering only if the owner wants the rule project-wide (shell tests, e2e). Today the class has no instance outside `voicen-core` tests.
3. **Exit (b): `/arch-review` of `engine::http`** (one shared client, a resolver with its own deadline). This would close only the resolver kind and the build-cost noise. The refusal and load kinds remain, and T-079 already owns the product resolver change. Not recommended.

**Recommended exit**: (a) code. The class lives in one seam (`tests/common`) and its callers. A kind-independent invariant there, with a T3 tripwire, closes every known kind and the plausible next ones (unrouted, proxy, download path) without a new helper per kind. The reviewer's three signals:
- "both cases in `tests/common`": supports (a);
- "the product times DNS inside connect and builds a client per call": real, but product-side and owned by T-079 / OQ-22; no product deadline includes the build cost;
- "the rule is review-only": answered by the tripwire inside (a). A tier move of the old per-kind rule would not have caught F-013.

**T-078 workaround.** Keep 5762a9c as a marked temporary (`RCA: T-080`), because it removes a real CI flake that blocks P-016 `wip/` runs. Pushing it needs the owner's `tail_code: ratified` on T-078. Drop these hunks:
- `post_process_timeout.rs`: restore `stage <= want + SLACK` in both cases, and keep the min-of-3 baseline;
- the guarantee 4 edit in `specs/003-llm-post-processing/contracts/core-post-process.md`, from ad9ae62 (this also clears review #5);
- in the same commit, fix T-078's review findings #3 and #4 (stale classify-pin text, "is CannotReach" comments → T-079 / OQ-22).

Everything else in it is replaced, not built on, by option 1: `RESOLVER_BUDGET` and `OVERHEAD_ALLOWANCE` fold into `OS_ANSWER_BUDGET` and the timing module, and the blackhole total goes back to 3 s with no ceiling.
