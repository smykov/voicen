The first window is encoded at `seek = 0` and covers frames 0..3000, so clip 2 is not in its input at all. Every segment of window 1, the first one included, comes from audio that holds only clip 1.
- **The first window's input is the same as the single-clip run's.** `log_mel_spectrogram` pads 30 s of zeros (3197) and clamps to `max - 8` over the whole mel (3229-3240). Both clips are the same samples and start on a frame boundary (488000 / 160 = 3050), so the maximum is the same in both runs. Frames 0..3000 are identical: the clip, then zeros in both, with the same reflective pad at the start.
- **The first segment is a prefix of the single-clip transcript.** Decoding is greedy with the same input and no prompt, so both runs produce the same tokens until the single-clip run stops at "end of audio reached" (7369, `seek + seek_delta + delta_min >= seek_end` with seek_end of about 100 frames). The 33 s run decodes on, or skips the chunk (7725-7730). So under 03, `text` (the first segment only) names the clip at most `one_clip` times, and `mentions(&text) > one_clip` fails. Mutant 03 is credibly killed. Review 1 missed this and validation 1 caught it; the old `>= 2` was satisfied by one clip ("speech" + "bubble").
- **Robustness on correct code.** Window 1 of the 33 s run gives at least the single-clip tokens. Window 2 holds clip 2 whole: after a single-timestamp ending, seek moves to 3000 and the window covers 30-33 s with the clip at a 0.5 s offset. The prompt is cleared at `seek + 500 >= seek_end` (7027) and `no_context` is set, so the second window cannot just copy window 1. With 1 thread, greedy decoding at temperature 0 and a SHA-pinned tiny model, the run is deterministic. It is not flaky between runs; a change of whisper.cpp or the model would show as a red test, not an intermittent one. CI 42667760197 shows it green on the real tiny model.
