## Context

CI run 38161876395 (attempt 1) on `wip/T-092` @ dd292f4: the Windows job failed in `cargo test -p voicen --no-fail-fast` on one shell test, `src-tauri/tests/local_models.rs` `deleting_the_selected_model_through_ipc_resets_the_engine_and_the_window_hears_it`, at `local_models.rs:679` (the assertion on `heard`, the first `settings://changed` payload). `heard` had `engine: "builtin_local"`, `builtin_local.model_id: "small"`, while the `settings_get` view and `service.snapshot()` at 669–675 already showed `none`, so the reset itself worked. First failure since the test was added (7a30c46, T-019, about 57 runs). Found by the orchestrator; logged here per P-016 so the re-run of 38161876395 can count. Analysis of why it is outside T-092's diff: `docs/tasks/T-092.md` › Investigation › "CI red at dd292f4".

Suspected race: the test subscribes (`w.changed_events()`) after its precondition `w.save(...)`. `settings_ipc::spawn_change_bridge` emits from its own thread with `service.view()` read at emit time, so the save's event can land after the subscription and before `forget_model`'s swap, and `recv_timeout` takes it as the delete's event. The sibling tests in `src-tauri/tests/settings_ipc.rs` subscribe before any save.

## Acceptance

- [ ] Root cause confirmed or refuted with evidence; the fix is test-only unless the analysis shows a product defect (the bridge and the settings decisions stay as they are).
- [ ] The test can no longer take an earlier save's event as the delete's (e.g. subscribe before the save and consume the save's `builtin_local` event first, or receive until the `engine == "none"` payload and assert exactly one), without weakening what it asserts.
- [ ] An F-entry for the class in `docs/failures.md`; Windows CI green.

## Tests

Option A, test-only, in `src-tauri/tests/local_models.rs::deleting_the_selected_model_through_ipc_resets_the_engine_and_the_window_hears_it`. Every existing assertion is kept.

**Guarantee → test (all in that test body):**
- The listener exists before the first publish of the test: `w.changed_events()` is now called before `w.save(&builtin_local("small"))`.
- The save's event is matched to the save. It is received with `recv_timeout(END_WAIT)` before `w.delete` is called, and it must equal `saved["Saved"]["view"]` with `engine == "builtin_local"`.
- The delete's event is the reset view. The next event must have `engine == "none"` (as before) and must equal the `settings_get` view (new).
- One event per delete: `changed.recv_timeout(QUIET)` is `Err` (new).
- No local-model event from a delete: `drain(&local, QUIET)` is empty (unchanged).

**Red evidence:** the race cannot be forced on demand without changing `settings_ipc::spawn_change_bridge`, which is out of scope. The red runs are the two recorded CI failures at the old `local_models.rs:679`, both with `heard` = the save's view (`builtin_local`/`small`): run 38161876395 attempt 1 (`wip/T-092` @ dd292f4) and run 39015017170 attempt 1 (`wip/T-024` @ 824d7fd). The reviewer checks the fix by reading the code: `w.delete` is invoked only after the save's event has been received.

**Bite check (reasoned, not run).** The shell tests build only on Windows CI, and none of these can be run on the Linux host. Each line names a change to the test or to the product and the assertion that catches it:
- The test calls `w.delete` before receiving the save's event (the old order with an early subscribe). Not deterministic: if the bridge emits late, the save's emit after the swap carries `none`, and the delete's emit also carries `none`. The first `recv` then sees `none` ≠ the `builtin_local` saved view, and the `heard_save == saved_view` assertion goes red. An early save emit gives a pass. So the order is enforced by the test text plus review, not by a deterministic red.
- The test accepts any first payload as the delete's (old shape, subscribe after save). This is the recorded flake: `heard["settings"]["engine"] == "none"` red with `builtin_local` (CI runs above). The new body can no longer take the save's event as the delete's, because that event is received and checked first.
- Product publishes twice for one delete (e.g. `LocalModels::delete` calling `settings.forget_model` twice, or `swap_and_publish` sending twice). Caught by `changed.recv_timeout(QUIET).is_err()` → "more than one settings://changed for one delete". The old test passed this.
- Product publishes twice for one save (`swap_and_publish` sending twice in `settings_save`). The second save event arrives as `heard`. The bridge reads the view at emit time, so it can be `builtin_local` (red on `engine == "none"`) or `none` (then the delete's own event trips the QUIET check). Red either way.
- The save publishes nothing (the bridge not spawned, or `subscribe` not wired): `recv_timeout(END_WAIT)` for the save panics with "no settings://changed after the precondition save".
- The delete's event carries a view other than `settings_get`'s (e.g. the bridge emits the published snapshot re-serialised differently, or a stale field). Caught by `assert_eq!(heard, view, ...)`.
- The delete does not reset (command not given the managed service): existing asserts on `engineReset`, `settings_get` and `service.snapshot()` stay red, unchanged.

- `scripts/tw-run core -- cargo fmt -p voicen --check`: clean.

## Investigation

**Frame.** Observed: `heard` (first `settings://changed` payload after the subscription) is the precondition save's view (`engine: builtin_local`, `builtin_local.model_id: small`), while `settings_get` and `service.snapshot()` already show the reset (`engine: none`). Expected: the first event heard after the subscription is the delete's. Reproduces only on the Windows CI runner, attempt 1, twice in about 60 runs: run 38161876395 a1 (`wip/T-092` @ dd292f4) and run 39015017170 a1 (`wip/T-024` @ 824d7fd). Both fail at `local_models.rs:679` with the same payload (`gh run view <id> --attempt 1 --log-failed`). `git diff 7a30c46 824d7fd -- src-tauri/tests/local_models.rs` is empty, so the test has not changed since it was added.

**Hypotheses.**
1. *The save's event is emitted late, after the subscription* (suspected). Confirmed if the bridge emits on its own thread after `settings_save` has returned and the payload is read when the emit happens. Refuted if the emit is synchronous inside `save`. **Confirmed** (see below).
2. *`delete` publishes twice, or publishes before the swap.* Refuted: `SettingsService::forget_model` calls `swap_and_publish` once, under `save_lock`, after `write_atomic`. `swap_and_publish` writes `current` before it sends to the subscribers. `LocalModels::delete` is the only caller (`local_models/service.rs`, one `settings.forget_model` call).
3. *The same concern on a second path* (another emitter of `settings://changed`). Refuted: J3 (`docs/decisions/settings.md`) says only `spawn_change_bridge` emits. A grep for `SETTINGS_CHANGED` / `settings://changed` in `src-tauri/src` finds only the bridge.
4. *A product defect: the bridge emits a stale view.* Refuted as a product defect. The bridge ignores `_snapshot` and emits `service.view()` read at emit time. A late emit therefore carries the view at that moment, which is never older than the publish that triggered it. Events arrive in publish order (one thread, one FIFO channel), and the emit after the last swap always carries the final view, so a window always ends on the state in force. The bridge and the settings decisions stay as they are.
5. *This class was fixed before.* Checked against `docs/failures.md`: F-004 / F-012 (sibling tests share an OS resource), F-005 / F-013 (OS-answer deadlines), F-014 (synthetic input timing), F-017 (native dialog close lag) are different mechanisms. T-097 (`lifecycle.rs`, Ready does not open the window within 20 s) is a timing budget on window creation, not event ordering, so it is a different class. No earlier entry for "test subscribes after the trigger of an async event". **First occurrence of the class.**

**Evidence for 1.**
- `settings_ipc::spawn_change_bridge`: `service.subscribe()` is taken in the caller, then a thread named `settings-changed` runs `for _snapshot in changes { ... app.emit(SETTINGS_CHANGED, service.view()) }`. The payload is `view()` at emit time, not the published snapshot.
- `SettingsService::swap_and_publish` (core `settings/service.rs`) only does `tx.send(snapshot)` on an `mpsc` channel. `settings_save` returns `Saved` as soon as the send is queued, before the bridge thread has run.
- tauri 2.12.1 `event/listener.rs` `Listeners::emit_filter` calls each handler synchronously on the emitting thread (`(callback)(Event::new(id, payload))`). `World::changed_events` therefore gets the save's event if, and only if, the bridge thread's `emit` runs after `listen_any`. The payload is `builtin_local` only if `view()` also ran before `forget_model`'s swap. That window lies between `local_models.rs:657` (subscribe) and the swap inside `w.delete` at :660. A bridge thread delayed on a loaded runner lands in that window, and the payload in both reds has exactly that shape. If the bridge runs earlier (the usual case), the listener is not registered yet and the event is lost, so the test passes. If it runs after the swap, two `none` events arrive and the test passes too. That explains a rare red with this exact payload.
- Sibling tests in `src-tauri/tests/settings_ipc.rs` call `h.changed_events()` before any save (`saved_emits_changed_once_refused_emits_nothing`, `key_store_write_refused_is_key_store_failed_and_nothing_written`, `canary_key_never_in_data_dir_or_log`, `test_connection_refused_loopback_port_is_cannot_reach`). `saved_emits_changed_once_refused_emits_nothing` receives each event before it starts the next save, and none of them has flaked.
- Where I searched for other listeners: `grep` for `changed_events`, `settings://changed` and `listen_any` in `src-tauri/tests/*.rs`. `local_models.rs` is the only file that subscribes to `settings://changed` after a save. Other `listen_any` users (`overlay_ipc.rs`, `settings_window.rs`, `tray.rs`, `single_instance.rs`, `hotkey_registrar.rs`) listen to other events. I did not audit them for the same shape. Serena was not used: its tools were not exposed in this session, so grep and file reads were used instead.

**Root cause.** The test registers its listener after a publish whose emit runs asynchronously on the bridge thread, so an emit of the earlier publish can be matched to the later one. This explains the payload (`builtin_local`/`small`, `first_run: true`), the correct state at 668-675, the rarity, and why only attempt 1 failed. No evidence contradicts it.

**Invariant.** A shell test that asserts on a `settings://changed` payload subscribes before the first publish of the test and receives, in order, the event of every publish it caused before it starts the next one, so each received event is matched to exactly one publish.

**Approach.**
- *A (recommended, test-only):* subscribe before `w.save`. `recv_timeout(END_WAIT)` the save's event and assert it equals `saved["Saved"]["view"]` (engine `builtin_local`) **before** calling `w.delete`. Then `heard` = the next event: assert engine `none` and equality with the `settings_get` view, then `changed.recv_timeout(QUIET).is_err()` (exactly one event for the delete). Receiving before the delete is what closes the race. If the test asserts `builtin_local` on the first event without waiting first, it can still flake, because the bridge reads the view at emit time and a late first emit after the swap would carry `none`. This strengthens the test: it now also pins one event per publish. Risk: none to the product. Rollback: revert the test commit.
- *B:* keep the order and receive until the `none` payload, skipping earlier ones. This is weaker: it cannot detect a duplicate or a missing save event, and it hides an extra delete event unless a quiet check is added. Not recommended.
- *Red before / green after:* the race cannot be forced on demand without changing the bridge, which is out of scope. The red evidence is the two recorded CI runs. The green is a Windows CI run with A. The reviewer checks the order of operations: the delete is invoked only after the save's event is received.
