## Investigation

**Frame.** Feature task (spec 007 G05, T010/T011; FR-046, req FR-15). Observed: the catalog has none of the call ids, so every later call task would show raw ids or have to add its own ids. Expected: every contracts/ipc.md "Message catalog" row in EN and RU, the Rust-originated ones declared with `messages!`, and the existing parity and existence tests covering them. Size: one seam in one area (core: `i18n.rs` plus the two JSON files). The behaviour is settled except for the owner points below. Not large.

**How I looked.** Serena `get_symbols_overview` and `find_symbol` on `crates/voicen-core/src/i18n.rs` returned the macro, `text` (`pub fn text(lang, id: MessageId, args: &[(&str, &str)]) -> String`) and the test list. `find_referencing_symbols` on `TRAY_TOOLTIP_RECORDING` returned "no symbol": constants made by the macro are not indexed. So for consumers of the ids (`tray.rs:54,95`), the JSON files, the TS tests and the task files I fell back to grep. I read the contract table, data-model "CallWarning and CallNotice" / "Speaker" / "Call.title", core-call.md "Log lines", the G04/G05/G06 text in tasks.md, docs/decisions/i18n.md, decisions #195–#197, and the analyses of T-118, T-120 and T-122. No library API is involved, so no docs lookup was needed.

**Hypotheses checked.**
1. *A second path for the same concern (a second catalog or a second completeness test):* refuted as a need. The existing tests (`catalog_parity_holds_for_the_real_catalogs`, `message_ids_exist_in_both_catalogs`) cover any id once it is declared. The new tests only pin that the ids exist, their placeholders and the fixed texts, as the T-020/T-054 precedents do. i18n.md "Don't: add a second catalog, completeness test or parity test in another feature" is respected.
2. *Fixed before (recurrence):* no. `docs/failures.md` has no i18n or catalog row (grep count 0). i18n.md lists "Defect that produced it: none yet" for every invariant except the UI `tWire` one (T-004 r1), which this task does not touch. No recurrence.
3. *The UI mirrors the id list:* refuted. `MessageId = keyof typeof en` and the parity test are generic, and `postProcessingCatalog.test.ts` lists only post-processing ids. Acceptance 5 holds with no `src/` change, and `conformance.json` is untouched.
4. *Every contract id belongs in `messages!` (the contract says so):* refuted by the area invariant. Only Rust-originated ids are declared there, and UI-only ids are JSON-only `t()` literals (`error.ipc_unavailable`, `local_models.*`). See D4.
5. *T-119 can run before T-118 (tasks.md says G04 and G05 are independent):* refuted for acceptance 4. "Covers every part × reason of `CallRefused`" needs T-118's `RefusedPart` / `RefusedReason`, unless the lists are taken as literals. See D1.

**Findings beyond the acceptance.**
- `notice.stopped.storage` versus `StopReason::StorageError` (`storage_error`). Also, `StopReason` has 8 values but only 4 have a toast (`user`, `hotkey`, `exit` and `system_end` have none), and T-118's `CallNotice::Stopped{reason: StopReason}` can hold a reason with no id. The mapping that T-126 or T-144 writes must cover this (an `Option`, or a narrower notice reason). This is not T-119's to change; it is recorded so the catalog keeps the contract spelling `storage`.
- `warning.communications_device` versus `CallWarning::CommunicationsDeviceDiffers`: the names differ, but there is no conflict. The mapping is explicit (D3).
- The default title needs two-digit args. T-119's render test passes "05", "03", "09", "07"; the padding (and local time) belongs to whoever builds the title (T-125).
- The contract leaves most EN wordings as "…". RU is fixed only for the speaker labels. The developer drafts the rest in the catalog's existing style (D5).
- `calls.error.*` and `calls.failed.*` / `calls.state.*` will be picked by the UI from a wire code. i18n.md allows only two rule-built casts (`errorMessageId`, `fieldLabelId`), so the UI tasks (T-143/T-154) must map by an exhaustive switch with literal ids (the `connectionTest.ts` precedent). A third cast needs its own core test. This note is for those tasks.
- The 18 refusal ids include pairs the session can never produce (for example `root.no_device`, `mic.unwritable`). The acceptance asks for the full product, which keeps the mapping total. The texts for unreachable pairs are generic (D6).

**Owner decision points** (recommendation first):
- **D1 — dependency on T-118.** *Recommended:* `depends_on: [T-116, T-118]`. The part × reason, `FailReason` and `Track` families are checked over T-118's enums through exhaustive test-local suffix fns, so a new variant fails to compile until it has an id. T-118 is IN_PROGRESS with red tests committed, so the wait is short. *Alternative:* keep T-119 independent and parse the families from contracts/core-call.md (option B in `approach`). The catalog would follow the contract text, not the type.
- **D2 — `settings.calls.storage_unwritable` {reason}.** *Recommended:* drop the row. Decision #196 makes the refusal a `FieldError` with code `storage.unwritable` (T-120) and a closed `UnwritableReason`, and the settings window renders `t(error.<code>)`. T-119 amends the contracts/ipc.md row to point at `error.storage.unwritable` (T-120) and does not add the id. How the reason is shown (reason ids, owned by T-120 or T-155) stays with T-120/T-155. *Alternative:* add it as written; then T-120 or T-155 must state which of the two texts the window shows. Acceptance 1 then counts 86 ids.
- **D3 — enum-to-id mapping for `CallNotice` / `CallWarning` / refusals.** *Recommended:* not in T-119. T-119 declares the constants and tests the families. The production mapping functions belong to T-126, the first producer, which tests them against the same enums. *Alternative:* T-119 also adds the mapping functions in a new `call/messages.rs`. That gives one map earlier, but it grows T-119 beyond the catalog and touches T-118's module.
- **D4 — which ids go into `messages!`.** *Recommended:* only the 51 Rust-originated ids (i18n.md invariant). T-119 amends the contracts/ipc.md sentence "the ids are declared in `messages!`" to "Rust-originated ids are declared …; UI-only ids are `t()` literals". *Alternative:* declare all 85. That breaks no test, but it makes `MESSAGE_IDS` claim ids Rust never sends, against the area's rule.
- **D5 — wording.** *Recommended:* the developer writes the EN texts the contract leaves open and all RU texts except the fixed ones, in the existing catalog style. The reviewer checks them against the contract's meaning, and the owner can amend later. *Alternative:* the owner supplies the texts before T011.
- **D6 — unreachable refusal pairs.** *Recommended:* keep the full 3 × 6 product (acceptance 4), with a plain "<part> — <reason>" text for each. *Alternative:* one `notice.call_refused` with nested `{part}` / `{reason}` ids (the `mic_reason` precedent). That means fewer texts, but it changes the contract ids and acceptance 4.
