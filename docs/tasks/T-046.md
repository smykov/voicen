## Context

Split from T-013 by decision #51 (T-013 analysis, option A — read T-013's analysis block and Investigation: they are this task's design). Core: `crates/voicen-core/src/connection_test.rs` (`ConnectionTestRequest` / `ConnectionTestResult` with serde, the bundled clip, the result mapping) entered only through `SettingsService::test_connection(&self, req, &Timeouts)`; the request goes only through `engine_for` → `OpenAiCompatibleEngine::transcribe` with the snapshot overlaid by the form values after the save's `normalize` and the key from the save's key rule (`key_step`/`normalize` made crate-visible, not copied); the credential store only through a read-only view; a DNS failure maps to `CannotReach{host}` in the tester (`classify` unchanged); latency by `Instant` (#47(2)); a pin of every result kind in `e2e/fixtures/settings-wire.json`; stale contract text fixed (core-traits.md `async fn test`, the wall `Clock` in R-9, clock.rs, architecture.md). Local-server cases (model omitted, 60 s) come through T-018's `engine_for` arm. Shell: `settings_ipc::settings_test_connection` as an async command running the blocking call via `tauri::async_runtime::spawn_blocking` (a sync `#[tauri::command(async)]` body runs on a tokio worker, where reqwest's blocking client panics in debug builds); its test only in `src-tauri/tests/settings_ipc.rs` (Windows CI). The speech clip: a public-domain recording per decision #59 (CC0 or explicit PD dedication, recorded in licenses/manual.json).

## Acceptance

- [ ] Core tests against a mock server: 200 → Ok with latency ≥ the server's delay; nothing saved (settings file and snapshot unchanged, the credential store sees only reads); the typed key is sent trimmed, `Untouched` sends the stored key, `Clear` sends none
- [ ] Failure branch: refused port and unresolvable host → `CannotReach{host}`; 401/403 → `InvalidKey`; timeout, HTTP 500 and a non-JSON body each map to their kind; a malformed URL or an API engine with no key → `Invalid`, no request; no key or URL query in any result — core tests; Windows CI: the command over a refused loopback port returns `CannotReach` (no tokio-worker panic)
- [ ] Test that fails without the change: `crates/voicen-core/tests/connection_test.rs`; `src-tauri/tests/settings_ipc.rs` (Windows CI)

## Investigation

Tools: Serena and context7 are not connected in this session. I used grep and file reads, and ran nothing. This analysis builds on T-013's analysis and Investigation, which decision #51 adopted as the design. It records only what changed since then and what the implementer needs to decide.

**Frame.** Spec 004 US4 / FR-017 need a "Test connection" for the api and local_server engines. It uses the form values, unsaved ones included, and the stored key when the key field is untouched. It saves nothing. It reports OK with the latency in ms, or the reason it failed. T-046 builds the core and shell halves; T-013 builds the UI. Today no test request can be sent from either side (`lib.rs:39-43` has no command, and core has no `connection_test` module).

**What changed since T-013's analysis (2026-10-04).**
- **T-018 is DONE.** `engine_for` has the LocalServer arm (`engine/mod.rs:73-84`): it reads the local-server slot once, trims the model, and leaves out a model that is empty. The local-server cases (US4-5, model omitted, 60 s) are now ordinary red tests of this task, not a dependency wait.
- **T-073 is DONE (#97, #99).** The durations are settings (`Settings.timeouts: TimeoutSettings`). `Timeouts::from_settings` (`timeouts.rs:123-135`) clamps them into the #99 bounds, and the pipeline derives them once per job from that job's snapshot (`pipeline.rs:240-244`). T-073 also rewrote R-9 (`research.md:71`) and FR-017 (`spec.md:214`): the test's connect and request limits are "as currently entered in the form", taken "from the form's `timeouts` values, clamped by `Timeouts::from_settings`". Its analysis routed the same point here (`T-073.md:190`): "the ConnectionTester must use the form's timeouts (the unsaved draft), not `Timeouts::default()`".
- **T-008 is DONE.** R-11 (`research.md:86`) lists a `settings test_connection result=<kind> latency_ms=<n>` log line. T-008 could not add it because no tester existed. This is choice (iv) below.

**Which timeouts the test uses (the question from the brief).** It uses the form's values, as the spec now says. Spec, R-9 and the T-073 analysis agree, so this needs no owner decision. The details:
- The request carries the form's whole `TimeoutSettings`. `data-model.md:84` does not have the field yet; the implementing commit adds it there and in `contracts/ipc.md`.
- Core turns them into durations with `Timeouts::from_settings`, the one conversion site. The engine role then picks connect + `api_transcription` for api and connect + `local_server` for local_server (`openai.rs:161,169-171`). SC-006's bound becomes "connect + the engine's limit as entered".
- The snapshot's saved timeouts are wrong, because the edge case "the result refers to the values at the click" (`spec.md:148`) covers unsaved edits. `Timeouts::default()` is wrong too: it ignores the setting entirely, which is the bug T-073 warned about.
- **Where the conversion runs.** #51 gave the signature `test_connection(&self, req, &Timeouts)`, which predates T-073. Under that signature the shell would have to build the `Timeouts`. That is a second conversion site, and `Timeouts::default()` would be the easy mistake there.
- Recommended instead: `test_connection(&self, req)` derives the durations itself through `connection_test::request_timeouts(&req)`. Tests override them with a `#[cfg(any(test, feature = "test-fakes"))] test_connection_with_timeouts(req, Timeouts)`, the same pattern as `Pipeline::with_timeouts` (`pipeline.rs:155-159`). The shell passes no durations at all.
- The model downloader's fixed limits (#99 Q1) are not involved.

**Hypotheses.**
1. *The parts exist; only the tester and its wiring are missing.* Confirmed: engine_for, the client, classify and host_port exist, and nothing calls them for a test.
2. *A second path for the same concern.* This is a risk in three places:
   - a tester that builds its own client, URL or key rule (T-013 H2; the reuse points are crate-private, so the tester lives in core);
   - a second durations conversion in the shell (above);
   - a second validation rule set. The tester must reuse `validate` (`validate.rs:40-108`) and keep only the errors of the fields it uses, rather than re-implementing the URL and key checks.
3. *The shared mapping already gives the required messages.* Refuted for DNS, as in T-013: `.invalid` gives `NetworkUnavailable` (`tests/openai_client.rs:539-545`). The tester maps `NetworkUnavailable` to `CannotReach{host_port(base)}` and leaves `classify` unchanged (#51).
4. *The obvious shell command works.* Refuted, as in T-013 H4. `settings_save` is a sync body under `#[tauri::command(async)]` (`settings_ipc.rs:120-130`), and a blocking reqwest call there panics in debug builds on a tokio worker. Use `async fn` + `tauri::async_runtime::spawn_blocking`; `tray.rs:458` already uses it.
5. *This class was fixed before.* No for the connection test: there is no F-entry, and `class: settings-ui` has no recurrence. The related class, durations taken from a constant instead of the settings, was closed by T-073 for the pipeline. This task is the third reader of those durations, and the red test `request_timeouts` keeps it from reopening that class.

**Design (as T-013's analysis and #51, with these deltas).**
- **Wire request:** `{engine: "api" | "local_server", base_url, model, key: KeyEdit, timeouts: TimeoutSettings}`.
  - `engine` is a closed `TestEngine` enum, not `EngineKind`. "none" and "builtin_local" cannot be tested, so they are refused at deserialize.
  - Any deserialize error is one fixed text, because the input carries a key (as `SaveRequest`, `service.rs:215-232`).
- **Steps of `test_connection`:**
  1. Overlay the request's engine, URL, model and timeouts on a clone of the snapshot. Run `normalize` (`service.rs:542`).
  2. Run the key rule (`key_step`, `service.rs:565`). For `Untouched` or a blank `Replace`, read only the selected slot, once, and never while `Unavailable` (#19, #33(b)). A read error gives the result `KeyStoreUnavailable` (#51).
  3. Run `validate` with that presence. Keep only the errors on the selected engine's base URL, model and key fields; any left → `Invalid`, no request. URL errors are checked before the key read, so a malformed URL gives `Invalid` with no credential call, as `engine_for` checks the URL before reading a key.
  4. Call `engine_for(&overlaid, &view)`. The view is read-only: `read` returns the resolved key from memory, and `write`/`delete` return `Err` without delegating.
  5. Call `transcribe(clip, {language: None, timeouts: request_timeouts})`, timed with `Instant` (#47(2)). No VAD.
  6. Map the outcome with an exhaustive match (no wildcard).
- **The clip** (#59 (c)):
  - **Choice:** a CC0 or public-domain speech recording (e.g. LibriVox), trimmed to about 1 s and converted to 16 kHz mono s16le.
  - **Recording:** source URL, title, reader and licence go into `licenses/manual.json`, then run `make licenses`.
  - **Asset:** `AudioBuffer` is i16 samples (`audio/mod.rs:20`) and the engine encodes the WAV itself (`openai.rs:115`). So the simplest asset is raw PCM (`include_bytes!` + `i16::from_le_bytes`, built with `AudioBuffer::from_16k_mono`), with a unit test that checks the length and that it is not silent. No WAV-decoder dependency is needed.
  - **Note for the implementer:** fetching the recording needs network access, and resampling needs a tool (sox/ffmpeg) or a small script. It is a setup step, not an owner decision, because #59 already decided it.
- **Stale contract text, fixed in the implementing commit:**
  - `core-traits.md:114-121`: `async fn test`; becomes a sync `SettingsService::test_connection`.
  - `core-traits.md:57`, `clock.rs:1-2`, `architecture.md:76`: remove "connection tester" from the wall-clock users.
  - `data-model.md:84-85`: add `timeouts` to the request, and `KeyStoreUnavailable` to the results.

**Non-blocking choices (orchestrator; defaults proposed).**
- (i) **Form timeouts outside the #99 bounds** (e.g. the API limit typed as 2 s). R-9 says clamp. FR-017 says "as entered", and T-013's T053 expects "a refused-form result highlights fields". Default: add `timeouts.connect` and the selected engine's limit field to the `Invalid` filter, so the user sees the same `timeout.range` error as a save would give. `from_settings` still clamps afterwards as a guard. The alternative is to clamp silently (R-9 literally).
- (ii) **FR-017 wording.** FR-017 lists a connect timeout under both "cannot reach" and "timeout". `classify` maps a connect timeout to `CannotReach` (`failure.rs:182`), as R-9 does. Default: keep `classify`, and in the implementing commit narrow FR-017's "timeout" to "the request limit exceeded".
- (iii) **A test while `Unavailable` (#19).** Allowed: it saves nothing, and `Untouched` means no key with no credential call.
- (iv) **R-11's `settings test_connection` log line** is not in this task's Acceptance. Default: add it here. That means one typed `LogEvent` with the result kind and `latency_ms`, no host (T-008 Q1), a `format.rs` row, a case in `tests/settings_log.rs`, and the shell writes it like `settings_save`. If the orchestrator wants it out of scope, it becomes a follow-up task.

**Recommended:** option A (analysis.approach). It needs no owner decision and no new OQ: the timeouts choice is settled by FR-017, R-9 and the T-073 analysis, and the clip by #59.
