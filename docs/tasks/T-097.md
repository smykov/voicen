## Investigation

**Frame.** Observed: on Windows CI, `lifecycle.rs::destroying_the_last_window_keeps_the_app_running` sometimes panics at line 310 ("Ready did not open the first-run settings window within 20s; the opener logged no failed open"), the app's log holding only `started`, `settings load outcome=first_run`, `autostart reconcile action=none`. Expected: the first-run window is open when the driver looks. It reproduces only on the first Wry test of the lifecycle exe on some runners; a re-run at the same sha is green.

**Sightings** (searched every `ci.yml` run listed by `gh run list --limit 200`, attempt 1 and 2 `--log-failed`, for `lifecycle.rs:<line>:<col>` panics):

| Run | sha | Test time | Next 4 tests | Note |
|---|---|---|---|---|
| 37280075413 a1 | 5c76e5c | 37.7 s | ~50 ms each | T-006 verify 1, re-run green |
| 38256295268 a1 | edd910d | 35.3 s | 1.6 s in all | this task; a2 green, 15.1 s |
| 38265381642 a1 | 742972a (main) | 21.6 s | 1.9 s in all | not logged before this analysis |

24 green runs (2026-10-12..18) put the same test at 3.9-20.4 s (median about 9 s; 38991351748: 20.4 s, so about 19 s of build against the 20 s budget). After the window opens the test spends about 1.1-1.5 s (destroy, round trips, 1 s sleep), so the build alone ranges about 2.5-19 s green and about 21.6 s and 35 s red.

**Hypotheses.**

1. *A cold first WebView2 build slower than the 20 s budget* (confirmed). Confirms: the loop ended after the budget, when the build returned; no failure line; later builds in the same process are fast. Refutes: the loop ending at once after `end_loop`.
2. *Ready never asked for the window* (refuted). `on_run_event` Ready calls `settings_window::on_ready`, which for `FirstRun` posts `OpenTarget::Tab` through `request` (no wait). Had no build been running, the main thread would have been idle, and `end_loop` (posted at the budget) would end the loop within ms, as it does in the 4 sibling tests. Instead the loop ended 1.6 s and 15 s after the budget: the main thread was still inside `WebviewWindowBuilder::build` (wry-0.57.0 `create_environment` / `create_controller` wait in `webview2_com::wait_with_pump`, a nested `GetMessage` pump on the main thread, webview2-com-0.39.1 lib.rs:60-81; tao runs the queued exit task only after it). A second explanation for a busy main thread was looked for and not found: tray install and the managed state run in `wire` before `run_return`; the overlay is not shown on `FirstRun`.
3. *The build failed* (refuted): the opener writes `settings_window_failed` for an `Err` and for a panic (`start_opener`); neither line is in the log at the budget, and the log is read before `end_loop`.
4. *The same concern on a second path / a regression from the pushed tail* (refuted). T-054 adds the logs-notice latch to `release_parts`/`wire`/`start_dictation`; `build_app` passes `Parts::new` (`logs_notice: None`, no session) and the test never calls `start_dictation`, so none of it runs. `git log` on `lifecycle.rs` and `settings_window.rs`: last changes 7aa05a2 (T-055) and b83612a (T-006 VERIFY_FAIL 1, which added the log-at-budget message); the third sighting is on another sha (742972a).
5. *Same class as F-018 (`test-event-subscribed-after-trigger`)* (refuted). F-018 is an event emitted by a background thread before the test listened. Here the test polls state (`get_webview_window`), which cannot be missed; the window is just not attached yet (tauri-2.12.1 window/mod.rs:410-415: `attach_window` after the runtime `create_window` returns; tauri-runtime-wry-2.12.1 lib.rs:300-333: the opener thread blocks on `rx.recv()` until the main thread has built it).
6. *This class was fixed before* (yes, in core only). The class is `os-answer-deadline-race` (F-005, F-013; rca T-080): a verdict decided by a clock the test does not control. Its rule I2 (a wall-clock reading decides only a lower bound; a ceiling only as a spec tolerance) is enforced by clippy in voicen-core; the class row in `docs/failures.md` lists "the shell tests (`src-tauri/tests`)" as not checked. T-006 verify 1 recorded this test as a flake and widened nothing; the BUDGET comment ("Windows-sized: a cold WebView2 creation on the runner, F-005") already sized a ceiling against the same uncontrolled clock.

**Root cause.** A wall-clock ceiling (20 s) on an OS-side duration, the first cold WebView2 environment and controller creation of the test process, decides the verdict; on slow runners that build takes longer (21.6 s, 35 s, 37.7 s observed). No product defect: Ready posts the open at once, and the open then waits only for tauri/wry/WebView2. Not shown (would need a timed build): which part of the cold build is slow (browser process start, profile creation, runner antivirus); the fix does not depend on it.

**Seam and approach.** See `analysis`. The opener runs requests one at a time in posting order (`start_opener`, `request`), and `request_with` is the existing test seam onto the same queue, so a probe posted by the driver after Ready returns only once Ready's open has finished (Ok or Err); the test then checks `get_webview_window(LABEL)` and reads the log for `settings_window_failed`. A slow build no longer fails the test; a failed build or a missing request still does (no window after the probe), and a build that never finishes still ends the exe through the watchdog or a hang bound under it. Deterministic red test: hold the opener with a `request_with` job sleeping past `BUDGET`, posted before `run_return`, so Ready's open queues behind it.

**Size.** Small: one seam (test helper in `src-tauri/tests/lifecycle.rs`), no product code. Follow-up audit: the cold-build `poll(BUDGET)` in `overlay.rs` (overlay thread, a different queue) and `crash.rs`.

**Recurrence.** Three sightings of this test (table above), the 38265381642 one red on `main` and unlogged. Class `os-answer-deadline-race` (F-005, F-013), not F-018. Per the rules a recurrence of a known class opens a `type: rca` task; the orchestrator decides whether T-097 goes on as a test fix with an F-entry under that class (widening its "not checked" list) or an rca with `recurrence_of: [T-006, T-080]`.
