## Context

Owner decision #119 (2026-10-10): the installer is no longer uploaded as a GitHub artifact on ordinary runs, so the windows job can never go red on the Actions artifact storage quota. On `main` the installer is only sent to Telegram, as now (T-070, `scripts/ci/telegram-send.sh`). The artifact is still uploaded on a `v*` tag run, because the tag-only `release` job (T-026) downloads `voicen-installer-<commit>` and publishes it on GitHub Releases.

Today, in `.github/workflows/ci.yml`:
- The windows job runs `actions/upload-artifact@v4` on every ref, with `name: voicen-installer-${{ env.VOICEN_COMMIT }}` and `path: target/release/bundle/nsis/*-setup.exe`.
- The `release` job downloads the artifact by the same name with `actions/download-artifact@v4`.

Other places affected:
- `docs/decisions/ci-toolchain.md` says that after a failed Telegram send "the installer stays in the run artifact". That will no longer be true on `main`.
- `scripts/ci/ci-wip.sh` classifies `actions/upload-artifact` as an action that never saves a cache. `make check` must stay green.

T-084 depends on T-085, the rca that absorbed T-026 (review 4 REJECT_RECURRENCE, class guard-model). T-085 rewrites the release job and its guard. Start T-084 only after T-085 is VERIFIED or DONE. The failure branch reuses T-085's owned-literal mechanism: the upload step, with its tag `if:` and `retention-days: 1`, is pinned byte for byte. T-084 adds no new awk reader of `ci.yml`.

## Acceptance

- [ ] A push to `main` or `wip/**`, or a `pull_request` run, uploads no artifact from the windows job. Shown by a `wip/T-084` run where `gh api .../runs/<id>/artifacts` lists none.
- [ ] A `v*` tag run uploads the installer artifact with `retention-days: 1`, and the `release` job still downloads it by the same name.
- [ ] Failure branch: `make check` refuses a change that makes the upload run on a non-tag ref. It also refuses a change that drops the upload on tags while the release job still downloads it. Either a `ci.yml` tripwire with fixtures or an extension of `scripts/ci/release-guard.sh` does this.
- [ ] `docs/decisions/ci-toolchain.md` no longer says the installer stays in the run artifact on `main`. It says what happens instead when the Telegram send fails: the run log names the failure, and the build can be re-run.

## Investigation

Investigator, 2026-10-10. Serena tools were not available in this session; context gathered with grep and file reads (scope: `.github/workflows/`, `scripts/ci/` incl. fixtures, `Makefile`, `docs/`, `specs/`, `PRINCIPLES.md`). context7 not available either; the `actions/upload-artifact` inputs were read from the action's own `action.yml` at ref `v4` (`gh api repos/actions/upload-artifact/contents/action.yml?ref=v4`).

**1. Frame.** Observed: the windows job uploads `voicen-installer-<commit>` on every ref with default retention (`ci.yml` windows job, the `actions/upload-artifact@v4` step right after the uninstall smoke; `with:` holds `name` and `path` only). Expected (decision #119): upload only on `v*` tag runs, `retention-days: 1`; the tag-only `release` job keeps downloading it by the same name. Nothing is broken today; the quota risk is the motivation.

**2. Hypotheses.**
- H1, the upload step has no condition. Confirmed: no `if:` on the step, and the windows job has no job `if:`.
- H2, the release job needs a change. Refuted: `release-job.yml` downloads `voicen-installer-${{ env.VOICEN_COMMIT }}`, and both jobs set `VOICEN_COMMIT` with `git rev-parse --short=7 HEAD` on the same checkout. The tag upload keeps the name, so R2's owned copy and the release block stay byte-identical. No edit to `release-job.yml` or `release-header.yml`.
- H3, a second path uploads or consumes the artifact. Refuted: in the workflows dir `upload-artifact` occurs once and `download-artifact` once, in the release block (grep, comments included). The `voicen-symbols-<commit>` artifact in `specs/006-.../quickstart.md` item 6 does not exist in `ci.yml` (stale spec text, outside scope).
- H4, an existing guard interacts with the new step. Refuted by a prototype, a copy of `ci.yml` with `if: ${{ github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v') }}`, `retention-days: 1` and `if-no-files-found: error`: `release-guard.sh`, `ci-wip.sh` and `telegram-guard.sh` all exit 0. `github` is not the word `gh` (R5). The step holds no `permissions`, `secrets` or `vars` (R3/R4), no escape (R6) and no `!!` (R8). It is not in the header (R7) and not in the release block (R2). Caveat for the developer: a new **comment** near the step must not hold the word `gh`, `permissions`, `secrets` or `vars`, or `!!`. R3-R5 and R8 read comments as text.
- H5, this class was fixed before. No `ci-deploy` class or entry in `docs/failures.md`. The nearest classes: `guard-model` (F-003, F-015), which is a risk if the failure branch adds a reader, so P-020 applies; and `ci-premise-unchecked-before-main`, see §6.

**3. The gap the failure branch closes.** `release-guard.sh` exits 0 on today's `ci.yml`, where the upload is unconditional. It would also exit 0 with the upload removed. R2 pins the consumer (the release job always downloads the artifact) but nothing pins the producer. `ci-wip.sh` lists `actions/upload-artifact` among actions that never save a cache (`ci-wip.sh` `endstep`, the never-saves list). That stays true: an artifact is not a cache. It reads neither the step's `if:` nor its `with:`, and it needs no change.

**4. Rule R9 (P-020: decides on a raw token plus an owned literal, no reader).**
- Token: `upload-artifact`, matched by `index()` on the lower-cased line, in every file of the dir, comments included. It must occur exactly once. Zero occurrences means the tag upload was dropped while R2 guarantees a release job that downloads it. Two or more means a second upload. Any case counts, because GitHub resolves `owner/repo` case-insensitively. Sub-actions such as `actions/upload-artifact/merge` and forks named `*/upload-artifact` hold the token too.
- Literal: an owned copy `scripts/ci/release-upload.yml` (exit 3 when it is missing, unreadable or does not start with `      - uses: actions/upload-artifact@v4`). It is compared byte for byte with the N lines that start at the token's line. Proposed text, with the predicate copied from the release job's `if:` so that artifact and consumer run on the same runs:
  ```
        - uses: actions/upload-artifact@v4
          if: ${{ github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v') }}
          with:
            name: voicen-installer-${{ env.VOICEN_COMMIT }}
            path: target/release/bundle/nsis/*-setup.exe
            retention-days: 1
            if-no-files-found: error
        - name: Installer for Telegram
  ```
  `if-no-files-found: error` (default `warn`) makes a tag run with no installer fail in the windows job, not later at the download. The last line is optional. It is the next step's first line and ends the step without an indentation reader, so no key such as `continue-on-error:` can be appended after the literal. To use it, move the T-070 comment block above the upload step so that `- name: Installer for Telegram` follows the step directly.
- Listed line: the token's line (count errors) or the first differing line (literal errors), as R2 does.
- Not caught (deliberate only): the literal placed in another job. On a tag the release job's download then fails loudly before `release.sh` runs, so this is no silent pass. Also not caught: a `run:` step that uploads through the artifact client API without the action. Unclassified third-party actions are already refused by `ci-wip.sh`, fail-closed.
- An extension of `release-guard.sh` makes T-084 a guard change. P-020 asks a `checker: true` task to name `decides_on`, which the analysis does. The orchestrator should set `checker: true` in the front matter (not done here: the investigator edits only `analysis` and this section).

**5. Fixtures and test cost (Option A).** `scripts/ci/fixtures/release-guard/` has 124 case dirs. Each fixture's `ci.yml` holds the old unconditional upload step. `release-guard.test.sh` `run` checks the exit code plus *some* matching output line. So the v-* fixtures still exit 1 and still name their rule, and an extra R9 line does not break them. Only the 3 ok-* fixtures (`ok-release`, `ok-lookalikes`, `ok-tag-lookalikes`) need the owned step text. Real-file mutations can reuse the existing `mutate` and `inwin` scope in `release-guard.test.sh`.

**6. Premise only a tag can run (P-016 / class `ci-premise-unchecked-before-main`).** With the change, the upload step never runs on `wip/<ID>`. Acceptance 1 even requires that a wip run lists no artifact. The step's first execution is therefore the first `v*` tag, the same shape as the main-only Telegram send. Mitigation:
- its `name` and `path` are unchanged from the step proven on every ref today;
- `Installer for Telegram` checks exactly one `*-setup.exe` on every ref;
- `retention-days: 1` is inside the action's documented range (minimum 1).

The verifier can prove acceptance 1 on a `wip/T-084` run (`gh api repos/<repo>/actions/runs/<id>/artifacts` → `total_count: 0`). Acceptance 2 can be proven only by a `v*` tag run, and no tag is pushed before the owner decides (#118). The verify record should say so, or the owner accepts it as a `verify_exception`.

**7. Consequences to record in docs (same commit).**
- `docs/decisions/ci-toolchain.md` (Telegram paragraph): "the installer stays in the run artifact" becomes this. A failed send is a `::warning::` in the `main` run log with curl's exit code and the API description. The installer is then not stored anywhere for that run. Re-run the workflow (same commit, same run number, so the same version) to rebuild and resend.
- Add R9 and the third owned copy to the release-guard paragraph.
- A failed release job can be re-run only within 1 day. After that the artifact is gone, and the whole workflow must be re-run.
- Also update `scripts/ci/telegram-send.sh` header line 19, `docs/architecture.md` "owner's Windows PC" row ("installer artifact from CI" becomes Telegram on `main`, GitHub Release on tags), the `release-guard.sh` header (R9, a 3rd owned copy, "edit both together"), and the `CLAUDE.md` `ci.yml` row (the upload step is byte-identical to `scripts/ci/release-upload.yml`).
- Product consequence for the owner, not decided here: an installer of 50 MB or more is never sent to Telegram (`send=false`, a warning) and is now not uploaded either. On `main` it would reach the owner nowhere, although NFR-09 allows up to 100 MB. If that matters, it is an open question, not a code change in this task.

**Recommended:** Option A, R9 in `release-guard.sh`. One seam and settled behaviour, so this is a small task, not spec work. Red first: the real-dir case and the new `v-upload-*` fixtures in `release-guard.test.sh`.

**Recurrence:** none. No F-entry or task of class `ci-deploy`. The task must not add a reader of `ci.yml`: the class `guard-model` (F-003, F-015) is avoided by deciding on a token and an owned literal (P-020).
