## Investigation

**Frame.** Feature (spec 007 G08, T016/T017). Today the tray shows one of four dictation states and a flat three-item menu. Expected (FR-003, FR-006): a call-recording state shown with the precedence dictation `HotkeyError` > dictation `Recording` > `CallRecording` > `Error` > `Idle`, and a menu with "Call" › "Record" (check) / "Stop" and "Calls". Per FR-004, a call-hotkey conflict never sets the hotkey-error state.

**How I looked.** Serena loaded: `get_symbols_overview` on `tray.rs`, and `find_symbol TrayState` (found in `recording/indicator.rs`, not `recording.rs`). `find_referencing_symbols` on `TrayState` returned `{}`, which is a known blind spot, so the callers were found by grep over `crates/voicen-core/src`, `src-tauri/src` and `src-tauri/tests`. Context7 `/tauri-apps/tauri` confirms that tauri 2 (lock: 2.12.1) has `Submenu` and the menu `set_checked` command. I did not see `CheckMenuItem` named in the returned snippet, so T-128 must check that API in the pinned source. Read: spec FR-003/004/006/043, data-model "CallSession" and "Tray state", contracts/core-call.md, contracts/ipc.md catalog, research R24, tasks.md G08/G14/G37, decisions #194–#196.

**Findings beyond the acceptance.**
1. *Windows compile break that `make check` cannot see.* Adding a `TrayState` variant breaks `src-tauri/tests/tray.rs::all_states` (wildcard-free match). Adding `TrayAction` variants breaks `src-tauri/src/tray.rs::on_menu_event` (exhaustive `Option<TrayAction>` match). Changing `menu`'s signature or return type breaks `build_menu` and `tests/tray.rs::expected`. tasks.md lists G08 as core-only. T-122 must carry a shell compile follow-through and cite a green `wip/T-122` run (P-016) whatever D1 decides.
2. *The catalog has no tooltip for the new state.* `tooltip()` must map every state, and contracts/ipc.md lists only `tray.call`, `tray.call.record`, `tray.call.stop` and `tray.calls`.
3. *The input is a bool, not `CallState`.* T-118's `CallState` is the stored meta.json lifecycle (`recording`, `ready-to-transcribe`, ...). The tray reads CallSession's `record: bool` (data-model), so T-122 does not need T-118. It needs the catalog ids from T-119 (G05), unless it adds them itself.
4. *Where the two inputs meet* is T-128's: `TrayPart::set_tray` today stores the dictation session's one state. T-122 only supplies the pure `shown` function. The FR-006 Error is the dictation `Error` only: call warnings go to the indicator and toasts (FR-006 second sentence), never to the tray.

**Owner decision points** (my recommendation first):
- **D1: how the menu change reaches `main` before T-128 wires the actions.** (a, recommended) T-122 also makes the shell render the rows (`Submenu` with a check item) and adds the new `on_menu_event` arms as explicit no-ops marked for T-128. Between T-122 and T-128, `main` then shows "Call"/"Calls" items that do nothing. (b) Same diff, but `main` gets it only together with T-128. (c) A temporary table input that keeps the call rows hidden until T-128. Note: G14 already must not reach `main` before G42.
- **D2: menu order.** Recommended: "Call" › {Record, Stop}, "Calls", Settings, Open logs folder, (Retry from T-007), Exit. Exit stays last (the T-052 invariant). The spec gives no order.
- **D3: is "Stop" enabled only while recording?** Recommended: yes, enabled iff `call_recording` (one more column in the table, tested). The spec is silent.
- **D4: tooltip and icon for `CallRecording`.** Recommended: a new catalog id `tray.tooltip.call_recording` (EN "Voicen — recording a call", RU text by the owner/T-119), and reuse the red-dot `TrayIconKind::Recording` image, so no new asset and no shell `image()` change. The alternative is a fifth icon (new png, shell change, OQ-11-style design question). Either way contracts/ipc.md needs the tooltip row.
- **D5: who adds the `tray.call*` ids.** Recommended: T-119 (it owns every ipc.md catalog id). T-122 adds `T-119` to `depends_on`, plus the D4 tooltip id if T-119 has not taken it.

**Dependency on T-119.** Waits for T-119 before anything goes green; only the red tests can be written earlier. (1) `tooltip()` and `TrayAction::label()` return a `MessageId`, and its field is private to `i18n` (i18n.rs:50 `pub struct MessageId(&'static str)`). The only way to get one is a constant from the `messages!` declaration in i18n.rs, and that is T-119's seam (D5). The exhaustive `tooltip` match for `CallRecording` cannot compile without `TRAY_TOOLTIP_CALL_RECORDING`, and the three new labels cannot compile without the `TRAY_CALL*` constants. (2) Any constant added there joins `MESSAGE_IDS`. `i18n::tests::message_ids_exist_in_both_catalogs` (i18n.rs:837) then fails in `make check` unless both `i18n/en.json` and `i18n/ru.json` carry the id, and `catalog_parity_holds_for_the_real_catalogs` (i18n.rs:808) requires the pair to match. (3) The tray tests that already exist require the ids to be declared and texted: `menu_item_labels_are_the_contract_ids_and_declared` (tray.rs:238) and `each_state_has_its_own_tooltip_id_from_the_contract` (tray.rs:259) check `MESSAGE_IDS.contains`, and `tray_texts_are_the_contract_texts_in_en_and_ru` (tray.rs:282) checks the RU text, which T-119 supplies. What does not depend on T-119: nothing in the gate parses specs/007…/contracts/ipc.md (grep for `include_str!`/`read_to_string` of `.md` under crates, src, src-tauri, e2e, scripts finds only the 001 messages.md and 004 ipc.md), and the UI catalog tests do not check tray ids. So contracts/ipc.md is not a blocker. `shown()`, the new variant, the `icon` arm and the row type could compile alone, but the commit cannot be green without the ids. Adding the ids in T-122 would go against D5. Note: T-119 itself depends on T-116 and T-118.
