## Context

Decision #272. The contour review of T-188 (run 43148171046) ran without Serena. The session's init line shows `serena` `connected`, but its only Serena tools were `mcp__serena__initial_instructions` and `mcp__serena__serena_repl`: the runner image `gha-runner:2.338.1-e-claude` has no `/root/.serena/serena_config.yml`, so Serena 2.1.1 starts with its default REPL interface. The role files (`.claude/agents/**`, pinned by `scripts/ci/role-heads/`) allow `mcp__serena__find_symbol`, `find_referencing_symbols`, `get_symbols_overview`, … — tools that exist only with `agent_interface: tools`, which the VPS sets in `~/.serena/serena_config.yml`. So every role agent spawned in the contour had no Serena tool at all and fell back to grep.

Possible seams (the analysis decides): the runner image (`/opt/gha-pool/Dockerfile.voicen`, the owner's infrastructure on VM 105: a `serena_config.yml` with `agent_interface: tools`), the `serena` entry of `.mcp.json` or the contour workflow's MCP step (`.github/workflows/teamwright-agent.yml` › `MCP servers and toolchain images`; header pinned by `scripts/ci/contour-heads/`, `.github/` closed to contour sessions), or the project's `.serena/project.yml` (untracked today, so absent in a contour checkout).

## Acceptance

- [ ] A contour stage session's init line lists `mcp__serena__find_symbol` (and the other Serena tools the role files allow), not only `serena_repl`
- [ ] A role agent spawned in a contour session (e.g. `code-reviewer`) calls a Serena tool successfully; its record does not say "Serena not reachable"
- [ ] Failure branch: when `serena` is missing on the runner, the MCP step still takes its grep fallback with the `no serena on the runner` warning (unchanged)
- [ ] Local sessions on the VPS keep the classic tools (their behaviour unchanged)
- [ ] `docs/decisions/context-tools.md` names the interface requirement

## Investigation

Tools: Serena was not used, because the scope is JSON, YAML and Serena's own Python package, which the project's Serena does not index. I used grep and file reads on `.mcp.json`, `.github/workflows/teamwright-agent.yml`, `.claude/settings.json`, `scripts/ci/role-heads/`, `docs/decisions/context-tools.md`, `docs/process/stage-protocol.md` and the installed serena-agent 2.1.1.dev0 source (`serena/cli.py`, `serena/mcp.py`, `serena/config/serena_config.py`, `serena/agent.py`, `resources/*.template.yml`). For the `--allowedTools` rule syntax I used context7 `/anthropics/claude-code`: `mcp__<server>__<tool>` names one tool, and a `-p` run refuses any ask. I did not check the runner's serena version from here. Decision #272 calls it 2.1.1, which is the version that has the flag (see risk below).

**Reproduction (the red/green probe for the developer).** Start serena with an empty `HOME` (no global config, as on the old runner image) and send `initialize`, `notifications/initialized` and `tools/list` over stdio. Use `serena start-mcp-server --context claude-code --enable-web-dashboard false` with and without `--agent-interface tools`. Result on this host, 2026-11-18:
- Without the flag: `activate_project`, `initial_instructions`, `serena_repl`. The new `~/.serena/serena_config.yml` has `agent_interface: REPL` (the template's default for new users). This matches run 43148171046.
- With the flag: `get_symbols_overview`, `find_symbol`, `find_referencing_symbols`, `find_implementations`, `find_declaration`, plus the edit tools (`replace_symbol_body`, `insert_*`, `rename_symbol`, `safe_delete_symbol`, `replace_content`, `replace_in_files`), the memory tools, `get_diagnostics_for_file`, `onboarding`, `get_current_config` and `initial_instructions`. The config file still says REPL, so the flag wins over the global file.

**Precedence.** `SerenaConfig.determine_agent_interface` picks the project config first, then the global config, then TOOLS. The flag replaces the global value (`SerenaMCPFactory.create_mcp_server`). `project.template.yml` leaves `agent_interface:` empty, so the `project.yml` that T-233's `serena project index .` generates in the contour checkout does not override it. The local `.serena/project.yml` also leaves it empty (its line 200), so VPS sessions keep tools, from their global file today and from the flag after the change.

**Relation to T-233 (decisions #308, CODE_COMPLETE).** T-233 fixes whether the server *connects*: it builds the index in the preflight and raises `MCP_TIMEOUT`. It does not touch which interface the server *exposes*, so it absorbs nothing from T-208. The two depend on each other for evidence. A contour session that times out shows no tool list. A session that connects in REPL mode still fails stage-protocol §0, because §0 probes with `get_symbols_overview`, which does not exist in REPL. The owner already patched the runner image outside the repo on 2026-11-12, so the contour has probably had tools since then. That has not been observed, because the T-217 run hit CONNECT_TIMEOUT first. What is left for T-208:
1. A repo-owned guarantee that does not depend on a runner image shared by six projects.
2. The stage session's allowlist.
3. The docs entry.
4. One contour acceptance run. With T-233 on `main`, the next stage run can prove T-208 and T-233 together.

**Finding: once the classic tools are present, the contour stage session auto-allows Serena's edit tools.** The `claude -p` line passes `--allowedTools "...,mcp__serena,..."`, which allows every tool of the server under `--permission-mode acceptEdits`. The gate hooks (`analysis-gate`, `review-gate`, `verify-gate`) match only `Edit|Write|Bash`. So `replace_symbol_body`, `rename_symbol`, `write_memory` and the rest would be an unhooked write path in the contour. That violates `docs/decisions/context-tools.md` ("A Serena edit, memory or shell tool ... would bypass the Edit/Write gates, which must stay the only write path"). The REPL interface had a similar hole through `serena_repl`, which was also allowed. Narrowing to the five read tools closes both:
- The subagents' calls need the same five, because their `tools:` lines name exactly these (`scripts/ci/role-heads/`, 7 roles).
- §0 needs only `get_symbols_overview`.
- Exposed tools that are not allowed are refused (a `-p` run cannot answer an ask), and they still appear in the init line, so Acceptance 1 holds.

**Guards and paths.**
- `.mcp.json` is not a guard path (`scripts/ci/`, `scripts/licenses/`, `Makefile`, `*.mk`), and no checker reads it (grep over `scripts/`, `Makefile`). The state guard (`scripts/hooks/_hookio.py::guard_kit`) asks a person before any write to it. So the change runs in a main-tree session with the owner approving that prompt, never in the contour.
- The `--allowedTools` edit is on the stage step's `claude -p` line. That line is outside the header (byte-pinned by `scripts/ci/contour-heads/teamwright-agent.yml`) and outside the `contour-upload.yml` tail. The new text adds no `uses`, `secrets`, escape, `<<` or column-0 line (release-guard R4–R13 as listed in T-233's investigation).
- **`checker: false`.**

**Failure branch (Acceptance 3).** With no serena on the runner, the preflight's `else` branch copies only `context7` into `mcp.json` and warns `no serena on the runner`. The new arg sits inside the `serena` entry, so that branch does not change.

**Risk.** A serena older than the `--agent-interface` option would exit with a click usage error. The server would then fail to start, and §0 would stop the stage (visible, not silent). The host's 2.1.1.dev0 has the option, and #272 names 2.1.1 on the runner. The developer confirms the runner's version once, from the image (`serena --version`, through the owner or monitoring), before the push.

**Side finding, out of scope.** `docs/process/stage-protocol.md` line 33 (the code-search line) names `search_for_pattern`. The `claude-code` context does not expose that tool (absent from the tools/list above, and context-tools.md says so too). This is worth a small docs task, or a kit note, since the stage protocol may be kit text.
