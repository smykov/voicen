## Context

Session review of 2026-10-23 (T-116). The red-test run of `test-writer-core` took 34 min, about 19 of them on a bite check of **23** wrong implementations (the role asks for 2–3), run one by one against a reference implementation the test-writer wrote itself and in the main tree's shared `target/` (the main test binary was then stale and had to be rebuilt by `touch`).

Despite 23 mutants, acceptance `docs/tasks/T-116.validation/1.md` FAILED: `self.flush()?` / `self.sync(now)?` in `OpusOgg::encode_frame` could be swallowed (`let _ = …`) with every test green. The fake `Sink` failed the n-th call **and every later one**, so `finish` re-raised the same `StorageOp` and the tests could not tell whether `push` reported the error. Review round 1 also claimed those mutants were caught. The gap was closed in T-116 by `push_fails_on_the_page_whose_flush_fails` / `…_periodic_sync_fails` (one-shot failures).

So the count of wrong implementations did not buy the one that mattered: the error swallowed where it first occurs, with a fake that fails exactly once.

Seam candidates: `.claude/agents/test-writer-core.md` and `test-writer-ui.md` step 4 "Bite check", possibly `docs/process/` and the teamwright kit template the role files are rendered from (the router already reports render drift on role files; `scripts/ci/role-heads/` owns their front matter only).

## Acceptance

- [ ] The test-writer role's bite check requires, for every failure branch in Acceptance, one wrong implementation that swallows the error **at the call that first fails** (not only at the end), and says that error fakes fail exactly one call unless the guarantee is about repeated failures
- [ ] The bite check is bounded: 2–3 wrong implementations plus one per failure branch (the `checker: true` exhaustive sweep stays as it is), and it runs with its own `CARGO_TARGET_DIR` (never the main tree's `target/`)
- [ ] The rule lands where it survives a kit re-render (local role file and, if the role text is kit-owned, an upstream note or the project's adaptation), and `make check` (incl. `check-role-tools`) stays green
- [ ] Failure branch: replaying T-116's red-test stage against the new role text would demand the M2/M7 mutants (`let _ = self.flush()` / `let _ = self.sync(now)` in `encode_frame`); shown in `## Tests` by citing the role lines that require them

## Investigation

Tools: Serena was loaded, but there is no code symbol to navigate here (the seam is role text in Markdown). I read the role files, kit templates, hooks and records with grep, sed and diff. The kit templates were under `~/.claude/plugins/cache/teamwright/teamwright/0.12.0/` and `~/.claude/plugins/marketplaces/teamwright-next/`. No library API is involved, so context7 was not used.

**Frame.** Observed: the T-116 red-test stage ran 23 wrong implementations in about 19 minutes and still missed M2 and M7. Its builds also shared the main tree's `target/`. Expected: a bounded bite check that kills a swallowed error at the call where it first occurs, with each failure counted on its own.

**Hypotheses.**
1. *The step 4 text does not ask for a swallow at the origin site, and says nothing about how the fake fails.* Confirmed. In `test-writer-core.md:115`, "swallow the error" is one example among several. T-116's W4 (`T-116.md:81`) swallowed every flush and every sync at once. The sticky fake then failed again in `finish`, so the test went red for the wrong reason and W4 counted as caught. M2 and M7 swallow one site each and survived (`T-116.validation/1.md:34-35`).
2. *No bound, and no command for running inside the copy.* Confirmed. Step 4 says "2–3" but nothing stops a larger count. The only run command, `:22` and `:114`, runs in the working tree. Nothing tells the test-writer how to build inside the copy.
3. *The kit already fixed this and the fix did not land here (a second path).* Partly confirmed. Kit 0.12.0 has a minimal-sketch rule, which cites "23 such implementations" from this project. It also has a mandatory swallowed-error mutant per failure branch, `tw-test` and `tw-mutants --tree` (copy runs, `copy_env`), and a failure-branch second spawn. None of this reached `.claude/agents/`. `f1b1d0ce` (0.8.2 → 0.12.0) does not touch the role files. `installed.json` still holds the 0.8.2 render hash for them, and the installer never overwrites a file it did not write (kit `skills/adopt/SKILL.md:112`). Two consequences follow. The role tells the agent to run `scripts/tw-run core -- cargo test`, which `scripts/hooks/test-guard.sh` now refuses (default `block`). And `docs/process/sessions.md:138` expects a `failure-branch bite` spawn that the role file does not describe. Even 0.12.0 has no rule for one-shot fakes, and it does not say to swallow one site at a time.
4. *This class was fixed before.* Not as a rule. `docs/failures.md` has no matching entry or class: I grepped for `toothless|bite|swallow|sticky|mutant` and got no hits. No other task has `class: toothless-test`. The same shape has still occurred, unlogged:
   - T-065 validation 1, M5a–c (`T-065.validation/1.md:28-32`): a fixture made *every* grep fail, so a later "cannot run" hid the grep-error branch.
   - T-116 validation 1, M2 and M7.
   - T-116 validation 3, C12 and F4: a swallowed flush in `create` and in `finish`, closed with one-shot fakes (`T-116.md:135-150`).

   That is two tasks and three rounds. Each time, the gap was closed by test patches inside the task, never by the role.

**Root cause.** The bite-check rule names "swallow the error" without saying where to swallow or how the fake fails. So an all-sites-at-once swallow, run against a sticky fake, counts as caught, while a single-site swallow survives. The rule also sets no bound and no copy-run command. The kit text that would add part of this never reached the role files, because the 0.12.0 upgrade left them as unmerged conflicts. This explains all three symptoms: too many mutants, the missed M2 and M7, and the shared `target/`. Contradicting evidence: none found. One point is unverified: the exact command the T-116 test-writer used to build in the main `target/`. I could not see its transcript, so the "shared target" mechanism is inferred from the role text, which offers only working-tree commands.

**Recommended exit (c-like, inside a chore): role text.** The tests did what the role allowed. I did not find a checkable tripwire worth adding now. Checking whether a catalog has one swallow mutant per Failure-branch line belongs in the kit's `tw-mutants`, not in this project's `scripts/ci`. So `checker: false` and `decides_on: ""` hold, as long as the front matter stays byte-equal to `scripts/ci/role-heads/`. Adopting the 0.12.0 front matter description, which mentions the second spawn, would be a guard change and is not recommended.

**What the developer writes (Option A), in both role files:**
- Merge in the kit 0.12.0 body. Fill the `{{AREA}}`, `{{TEST_FRAMEWORK}}` and other placeholders from `.teamwright/config.yml`. Keep the Tools block between the markers and the #194 paragraph exactly as they are.
- Add the project rule to step 4 and to second-spawn step 2: "For each failure branch, one wrong implementation or mutant swallows the error *at the call that first fails*. Swallow one propagation site per mutant, and leave the other sites propagating. Error fakes fail exactly one call (the n-th) unless the guarantee is about repeated failures; a fake that keeps failing lets a later call re-raise the same error and hides the swallow."
- Add the bound: "2–3 wrong implementations plus one per failure branch; the `checker: true` sweep is unchanged."
- Add the copy rule: "Bite-check builds run only through `scripts/tw-test <area> --tree` and `scripts/tw-mutants <area> <ID> --tree`, in the copy's own target, never the working tree's."
- The UI file gets the same rule. For the UI, the copy's build output plays the role of `CARGO_TARGET_DIR`.

**Replay for the failure branch in Acceptance.** T-116's failure branch is "an io::Error from write, flush or sync maps to StorageError". It has three propagation sites inside `push`: `encode_frame`'s flush, its periodic sync, and the write. The new rule demands one site per mutant, so it demands `let _ = self.flush()` (M2) and `let _ = self.sync(now)` (M7), each against a fake that fails once. W4 would no longer satisfy it. The developer cites these role lines under `## Tests`.

It is not required for the Acceptance line: a `--tree` copy already builds in its own target. Without it, though, each copy builds cold (libopus included), which costs bite-check time.
