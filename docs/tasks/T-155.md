## Investigation

**How I looked.** Serena (`find_symbol`, `find_referencing_symbols`) on the Rust side: `provider_host`, `SettingsView`, `SettingsTab`, `UnwritableReason`, the validate rule. `find_referencing_symbols` on `provider_host` returned nothing, so I confirmed it with grep: the only user is `call/session.rs` plus tests. The TS and Svelte files under `src/` and `e2e/` were read and grepped, because Serena indexes Rust only. I also read the records of T-119, T-120 and T-129, decisions #196, #198 and #306, OQ-87, `docs/decisions/settings-ui.md` (U1, U2, R, L, W, F), `docs/failures.md`, and spec 007 (US9, FR-031, FR-038 to FR-040, FR-046, `contracts/ipc.md`, `data-model.md` CallSettings). I ran no code.

**What already exists (dependencies DONE).**
- T-120 added the `calls` section on the settings wire, with validation:
  - `calls.hotkey` equal to the dictation hotkey is refused from either side.
  - An unknown `primary_language` gives `language.unsupported`.
  - An unwritable `storage_root` gives `storage.unwritable` plus a closed `reason`.
  - `SettingsTab::Calls` exists (token `calls`).
  - Labels `settings.field_label.calls.*`, `error.hotkey.equals_dictation`, `error.storage.unwritable`.
  - The fixture key `refused_storage_unwritable`.
- T-119 added `settings.tab.calls` and `settings.calls.provider_notice {host}` (EN and RU).
- T-129 handles live re-registration of a changed `calls.hotkey` on save. A save-time conflict comes back as `calls.hotkey` / `hotkey.unavailable`. Nothing on the UI side is needed for "applies without a restart".

**Rust/IPC gap (second seam).** The provider line needs the host of `settings.api.base_url` when it is not loopback. Core has this rule (`settings::url::provider_host`, the same rule the call session uses for its once-per-host notice), but no wire carries its result to the window:
- `SettingsView` has no such field.
- `contracts/ipc.md:67` says the settings commands are unchanged.
- settings-ui.md W ("Don't: classify a URL, scheme or host in the UI") and P-010 rule out computing it in TS.

So the task needs a small core change: one `SettingsView` field filled in `view_with`. Two `SettingsView` literals change, plus a fixture regeneration. src-tauri does not change. Decision #306 already chose a `SettingsView` field for the same kind of gap (the startup call-hotkey mark, T-232, after this task). The contract line has to name the field in the same commit. Everything else the tab needs is already on the wire. The UI half of the work is: the `reason` in the TS `FieldError` type, and keeping it in `errorsByField`.

**The fixture is core-pinned, so the "extended settings-wire fixture" means core tests.** The precedent is T-021, a ui-surface task that added a core-pinned fixture key. New keys:
- `refused_call_hotkey_equals_dictation` (call side)
- `refused_dictation_hotkey_equals_call` (dictation side)
- `refused_call_hotkey_unavailable` (registrar refuses `prepare_call`)
- `loopback_api_view` (api.base_url `http://localhost:8000/v1`, `provider_host` null)

`first_run_view` also gains `provider_host: "api.openai.com"`.

**Spec points the developer must not guess.**
1. *Reason wording versus #198.* T080 and the Acceptance quote "This folder can't be written: {reason}". That is the template id `settings.calls.storage_unwritable`, which #198 dropped. `error.storage.unwritable` must stay placeholder-free (i18n.rs test). Recommended, consistent with both: six UI-only full-sentence ids, `settings.calls.unwritable.<reason>` ("This folder can't be written: access denied", and so on, RU alongside). They are chosen by an exhaustive switch over the closed `UnwritableReason` union. This uses no placeholder and no cast, and matches the T-120 test comment "the per-reason texts belong to the Calls tab". The tasks.md T080 bullet and contracts/ipc.md:153 should be aligned in the same commit. If the owner prefers the generic `error.storage.unwritable` sentence plus a separate reason line, the tests change, not the seam.
2. *Provider line: saved or draft value?* FR-031 speaks of the configured engine. The recommendation shows it from the saved view (`baseline.provider_host`), so it follows a Save, not typing on the Engine tab. It is based on `api.base_url` whatever `settings.engine` is, because the 1a final engine is always the API engine, as in `CallSession::new_provider_host`.
3. *Storage folder control.* The spec names no folder picker. A text input (empty = default root, with a hint) is enough for FR-039/FR-040, and no dialog dependency is added.
4. *Tab position.* Spec 004 FR-001 fixes six tabs; the spec does not place Calls. Recommended: between History and General (General stays last), recorded in settings-ui.md F.
5. *Out of scope.*
   - The startup call-hotkey mark (US9 #3) is T-232 (decision #306). This task marks the field only from a save error, as the Acceptance says.
   - Listing calls across earlier roots (US9 #5) belongs to the Calls page and core.
   - The primary-language default (US9 #6) is core (T-120). The tab only shows the stored value.
