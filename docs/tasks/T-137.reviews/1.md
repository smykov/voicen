What I verified by reading `final_pass.rs`:

- **Length bound.** The limit is `base + max`, and every chunk start is at least `base`. Spans are clamped to `window_start.max(known_end)`, so a new span never starts before `base`. After a hard cut, `prev_end = base = limit`. The pick branch's end is capped by `.min(limit)`, so `end - start <= max` holds.
- **Disjoint chunks.** Disjointness follows from `start >= prev_end`. Each span stays in exactly one chunk: the pick branch moves whole spans, and the hard cut splits a span at `limit` into `taken` and `rest`.
- **Carry stays below the limit.** When the window is full and spans are pending, `decide` always returns `Some`. When the loop ends, either the window is not full (carry < max) or nothing is pending (carry ≤ `PAD_MS`).
- **Held audio (`ChunkPlanner`).** It holds only `[base, known_end)`, at most window plus carry, which is ≤ 120 s under the caller's budget (FR-018). It is trimmed only after all ranges of the feed have been sliced.
- **Time-less fallback.** `recut_timeless` follows `contracts/core-call.md`: re-cut into ≤ 30 s phrases.
