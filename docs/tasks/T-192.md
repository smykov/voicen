## Context

Process review 2026-10-25, proposal 1 (decisions #208). In the 2026-10-24 parallel run, 11 of 11 worktrees stopped `BLOCKED` on the P-016 `wip/<ID>` push: a headless `claude -p` stage session in a worktree may not push. The permission `Bash(git push -f origin HEAD:wip/*)` exists only in the main tree's gitignored `.claude/settings.local.json`, which worktrees do not get. `CLAUDE.md` › Rules allows the CI-only push to "the orchestrator" only. Decision #202 already allows `wip/<ID>` pushes; `main` stays the owner's.

## Investigation

**Frame.** Expected: a headless worktree stage session pushes `wip/<ID>` (red-tests step 4, P-016, #202, #208). Observed: T-102 stopped 10 times and T-156 11 times (`.teamwright/parallel/<ID>.json`: 12 stages, outcome `limit`); `origin` had neither branch until the orchestrator pushed them.

**Three independent blocks, all must go for the last Acceptance line.**

1. **Kit prompt.** The session text "Do not push, do not merge" is `tw-parallel.py::AUTONOMY`, passed by `--append-system-prompt` in `DEFAULT_ARGS`. It is not in a stage skill; `red-tests/SKILL.md` step 4 orders the push. T-102's third-run note says these instructions outrank #202 for the session, and later runs did not attempt the push. A `CLAUDE.md` line is unlikely to change that (inference from those notes, not tested).
2. **Kit deny.** `DEFAULT_ARGS` has `--allowedTools "Bash ..."` and `--disallowedTools "Bash(git push:*) Bash(git merge:*) Bash(gh:*)"`. Per the permissions docs an allow rule cannot carve an exception out of a deny. So the planned allow rule has no effect on a plain `git push` in these sessions, and Bash is already allowed tool-wide.
3. **Project deny.** `.claude/settings.json` denies `Bash(git push -f *)`. The exact rule Acceptance line 1 names, `git push -f origin HEAD:wip/*`, matches that deny, so it is dead in every session, the same for the copy in `settings.local.json`. Deleting the deny would widen force push to every ref.

**A fourth stop follows the push.** `Bash(gh:*)` also denies `gh run watch`, which step 4 needs to record the result. The Notes show `gh run list` refused repeatedly. A push alone would leave the stage unable to read its run.

**Hypotheses.** Settings file missing from worktrees (process review's reading): refuted as the whole cause, worktrees do get the committed `settings.json` and the rule would still lose to blocks 2 and 3. A second path: the kit's other launch modes; `tw-next.py` headless notes describe a `wip/` branch for CI jobs, outside this run, not examined further. Fixed before: #202 settled the policy for the orchestrator only and never reached the launcher.

**`HEAD:wip/*` does not cover the need.** `ci.yml` job `windows` has `needs: gate`. Runs 41170174023 (`wip/T-102` @ 422d4546) and 41170176759 (`wip/T-156` @ ebbcf23e): Gate failure, Windows and Release skipped (checked with `gh run view`). T-156 needs `5047c0ff`, an ancestor of HEAD that changes only `ci.yml`. `wip/T-156` is now at ebbcf23e, so that move is not a fast-forward and needs force or a delete. T-102's plan is a commit with only the `ci.yml` change on top of 92b15b32, so not an ancestor of HEAD: "reachable from HEAD" is too narrow, "descends from the fork point from main" covers both. A rule cannot express this: `git push origin *:wip/*` also matches `git push origin HEAD:main x:wip/y`, because `*` spans spaces. The same applies to the trailing `*` of `HEAD:wip/*`: `git push -f origin HEAD:wip/x HEAD:main` matches it, and `git push -f origin HEAD:wip/x +HEAD:refs/tags/v1` too. Only a program can pin source and destination. A red run at a non-HEAD sha still does not satisfy P-016's `CI:` line unless only `docs/**` follows it.

**`git -C *` in a committed allow rule.** Unsafe. The Claude Code errors reference gives this exact shape a warning: a wildcard before the rest of the command also matches options inserted there, and for git `-c` and `--exec-path` can run arbitrary commands. `git -C . -c core.sshCommand=<cmd> push -f origin HEAD:wip/x` and `git -C /other/repo push -f origin HEAD:wip/x` both match (the second acts on another repository's `origin`); `-c core.hooksPath=/dev/null` also drops the pre-push hook. Narrowest rule shapes, if a rule is wanted: no `-C` at all (a stage's cwd is its worktree), or an exact path per worktree, which cannot be committed since the id varies. Pinned to the script, the rule is `Bash(scripts/tw-wip-push)` and `Bash(scripts/tw-wip-push *)`, with the script refusing everything but one commit argument. The wildcard rule in `.claude/settings.local.json` should go; it is the owner's file.

**Related hole, not exploited and not tested.** Per the docs `Bash(git push *)` does not match `git -C . push origin main`. With `--allowedTools Bash`, the kit's deny therefore should not stop a headless `git -C . push`, to any ref, and neither do the project's `git push -f` denies. Only the pre-push hook stands there, which passes approved tasks and is switched off by `-c core.hooksPath`. Project denies `Bash(git -C * push*)` and `Bash(git -c * push*)` narrow the usual forms, but the docs say a deny is no boundary (`sh -c` still escapes); a PreToolUse hook reading the command is the stronger check.

**Auto-mode classifier.** Established: headless sessions run `--permission-mode acceptEdits`, so the auto-mode classifier does not apply to them by that mode; it matters to the orchestrator session. Docs: `autoMode` is read from user settings, project settings are ignored; a command matching an allow rule, other than arbitrary-code rules, skips the classifier. The user settings hold `autoMode.environment` only, naming `origin` as the trusted repo, and an allow for `git push origin --delete wip/*`. Not established: the refused command's exact text (`.teamwright/logs/tools.jsonl` and `perms.jsonl` carry no entry naming `wip/T-102` or `wip/T-156`, by grep; the Notes are the only source), whether a project allow on the script skips the classifier in this version 2.1.316, and whether the classifier would pass the script without one. No test was run: it takes a `claude` session, and this role spawns none. The bypass of a refused action by a new allow rule is itself what the owner has to approve; the orchestrator should not retry the refused move on the strength of this analysis.

**Options.**

- **A (recommended): project script + launch args.** `scripts/tw-wip-push [<commit>]` derives `<ID>` from branch `tw/<ID>` (a main-tree mode takes an explicit id matching a `docs/tasks/<ID>.md`), remote fixed, refspec `+<commit>:refs/heads/wip/<ID>`, runs hooks, no `TEAMWRIGHT_ALLOW_PUSH`; a `watch` subcommand reads that branch's run. A project launch entry sets `TEAMWRIGHT_CLAUDE_ARGS` to the kit's defaults with the denials kept and the prompt line "Do not push except through scripts/tw-wip-push". Removes all blocks, covers a chosen sha. Red: the bare-remote shell test in `analysis.approach`, then the headless-log evidence. Risk: the script's name is not matched by the kit's deny, so it is a deliberate path around that deny, and a launch without the env keeps the old prompt. Env fallback: `make check` cannot see it, so the launcher must be the documented route. Rollback: remove rule and script.
- **B: settings rule only, as Acceptance line 1 says.** Does not remove the cause (blocks 1, 2, 3). Rejected.
- **C: kit change** (a `wip` exception in `AUTONOMY` and args), feedback upstream. Right long term; 0.15.0 still has the same text, so it does not serve today. Send as feedback alongside A.
- A variant that drops the force: a fresh `wip/<ID>-red-<n>` per red run. `ci.yml` triggers on `wip/**`, so no `+`; costs branch cleanup. Force limited to the script's own ref is simpler.
