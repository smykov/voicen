## Investigation

Tools: YAML, bash and markdown only (no Rust/TS symbol in scope), so grep and file reads; Serena was loaded but not needed. Docs: context7 `/github/docs` (unversioned platform docs, read 2026-11-18).

**Frame.** Observed: adding the `teamwright` label to Issues #16–#20 started nothing for ~2 h; a manual `gh workflow run teamwright-next.yml -f task_id=… -f issue=… -f hop=0` started the chains. Expected (kit assumption, decisions #265 and #308 "the label goes on #N again"): the label starts the chain. Second symptom: T-182 (Issue #16), already `CODE_COMPLETE` with no new commits, ended with `pull request create failed: No commits between main and task/<ID>` instead of a clear end.

**Hypotheses.**
1. *The dispatcher has no label trigger.* Confirmed: `teamwright-next.yml` lines 10–31 (and the byte-identical owned head `scripts/ci/contour-heads/teamwright-next.yml`) list only `workflow_dispatch`. `teamwright-agent.yml` is also dispatch-only. No other workflow exists (`release-guard.test.sh` pins the dir to exactly three files), so nothing in the repo listens to `issues`.
2. *A second path starts chains (kit-side).* `tw-sprint.py` is not in this repository (grep of `scripts/`, `.claude/`). The task context says `--start` only sets the label. Nothing in the repo turns a label into a dispatch. Refuted as a repo cause; the kit's assumption is the requirement.
3. *The label event fires but is filtered (actor, `if:`).* Refuted: with no `issues` trigger, no run is created at all. The run list for that window showed only the manual runs.
4. *Fixed before.* No earlier task added a label trigger. `git log -- .github/workflows/teamwright-next.yml` shows only T-202 (creation) and T-216 (MAX_PARALLEL). Not a recurrence; `type: chore` stands.
5. *CODE_COMPLETE error.* Confirmed by reading the `CODE_COMPLETE | VERIFIED | DONE` branch of the "Next stage" step. With no `task/<ID>` the ref falls back to `origin/$MAIN`; the step still runs `gh workflow run ci.yml --ref task/<ID>` (`|| true`) and `gh pr create --head task/<ID>`. No existence check and no ahead check, so a task finished in the main tree gets GitHub's error as its final message.

**Root cause.** The owned dispatcher head has `workflow_dispatch` as its only trigger, so the label event the kit relies on reaches no workflow. The end branch opens a PR without asking git whether there is anything to merge.

**Design constraints found.**
- A concurrency group expression may use only `github`, `inputs`, `vars` (context7 `/github/docs`, section-using-concurrency.md), and expressions have no regex or substring. A label run therefore cannot compute `teamwright-next-<ID>` from the title. If the dispatcher job itself ran on `issues` events, a label start and a manual start of the same task would sit in different groups and both pass the busy count. With today's literal group `teamwright-next-${{ inputs.task_id }}`, every label event would share the empty group `teamwright-next-`. GitHub keeps one pending run per group and cancels the older ones, so a sprint labelling five Issues at once would lose three starts.
- A `workflow_dispatch` made with `GITHUB_TOKEN` always creates a run (actions-do-not-trigger-workflows.md); the contour already relies on this (next → agent → next). `issues` runs use the workflow file on the default branch.
- The Issue title is attacker-shaped text: anyone can open an Issue on the public repo, and the owner may label it. It must reach the runner only through `env:` and be reduced to the regex group before any use. The job `if:` (actor == owner) is evaluated before a runner is assigned, so a non-owner label never reaches the self-hosted runner (the R14 rationale "owner-started triggers only" holds).
- Pins that move with the head: R14 (real file = owned head = header of fixture `ok-contour/teamwright-next.yml`, `release-guard.test.sh`); `contour-busy.test.sh` pins the group line `  group: teamwright-next-${{ inputs.task_id }}` literally. `actions/checkout@v5` at step indentation is already the owned line 1 of `action-lines.txt` (R11 is satisfied by a second use). R5 is waived for contour files, so `gh` in the relay is allowed.

**Options.**
- **A: relay job in `teamwright-next.yml` (recommended).** Header: `issues: types: [labeled]`; group `teamwright-next-${{ inputs.task_id || format('issue-{0}', github.event.issue.number) }}`; run-name likewise. New job `start`: `if: github.event_name == 'issues' && github.event.label.name == 'teamwright' && github.event.issue.state == 'open' && github.actor == github.repository_owner`. It checks out, sets `TITLE: ${{ github.event.issue.title }}` in step env, runs `scripts/ci/contour-label.sh "$TITLE"` → `start T-NNN` or `bad <why>`. On `start` it dispatches hop 0 with `task_id` and `issue`; on `bad` it posts one Issue comment and exits 0. Job `next` adds `github.event_name == 'workflow_dispatch'` to its `if:`. Every hop then runs in the per-task group, so label + manual serialize. The second hop 0 then sees `own` from `contour-busy.sh`. Today that waits 3 min and ends red with "previous stage did not end"; change it to: at `HOP=0` with empty `PREV_STAGE`, `own` → say "chain of <ID> already running; this start does nothing", exit 0. Why it removes the cause: the label event now has a listener, and every start ends up as the same dispatch. Red first: `scripts/ci/contour-label.test.sh`, which covers the script cases and pins on the real file; it is red because the script and the trigger are absent. Also red first: the updated group literal in `contour-busy.test.sh`. Risk: small. The relay holds a runner for seconds. A label added by `GITHUB_TOKEN` starts nothing, which is fine because the contour never labels. Rollback: revert the commit (head and its pair together).
- **B: dispatcher job runs directly on `issues`, parses the title in the step.** Rejected. Its group cannot be per task (see constraints), so acceptance 2 fails and simultaneous labels cancel each other.
- **C: separate `teamwright-label.yml`.** Rejected. A third workflow file is refused by R14's name literals and R5, and would need a guard-rule change plus a new write-token file, which is a wider exception than A.

**CODE_COMPLETE with nothing to merge (decided here, no OQ).** The contour has no verify stage: the agent's `stage` choice is analyze, red-tests, implement and review only, and verify needs the task's surface (Windows/deployed). So "route to verify" means an explicit end, not a new stage. In the `CODE_COMPLETE | VERIFIED | DONE` branch: if `task/<ID>` is absent, or `git rev-list --count "origin/$MAIN..FETCH_HEAD"` is 0, say `**<ID>**: <status>, nothing to merge from task/<ID>; verification runs locally (/teamwright:verify <ID>)`, exit 0, with no `ci.yml` run and no `gh pr create`. Otherwise keep today's behaviour. Adding a contour verify stage would be a separate owner decision and is not needed for the Acceptance.
