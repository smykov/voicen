Not covered by a test:
- **That every test takes `serial()` first.** Only a source scan could check this, and a source scan is not a test. The reviewer checks it.

## Investigation

**Framing.** Observed: in `src-tauri/tests/purge_credentials.rs`, `Planted::add` gets `Ok` from raw `CredWriteW` for a fresh target and then raw `CredReadW` (`raw_exists`) does not see it (assert at line 105). Expected: a written entry is readable at once. Reproduces only on the Windows runner (no Windows host), intermittently. Symptom vs guess: the log only proves "`CredReadW` returned an error"; whether it was `ERROR_NOT_FOUND` is a guess, because `raw_exists` drops the error.

**Data (all Windows jobs since the test landed, e98856a, `gh api .../jobs/<id>/logs`).**

| Run / attempt | Ref | purge_credentials | Failing test, prefix | ms after `running 5 tests` |
|---|---|---|---|---|
| 37419266451, 37444780779, 37465516406, 37502781812, 37530828511, 37579051772 | main | 5 ok each (37498788064 skipped the job) | — | — |
| 37569807954 a1, 37575065255 a1, 37583834468 a1 | wip | ok | — | — |

- In every red attempt the failing plant is the **first** `Planted::add` of that test. The FAILED line is printed first, about 3 ms after the binary starts, while the other four tests are still running. That is the burst where every test thread makes its first Credential Manager call at once.
- Red and green attempts show the same test exe (`purge_credentials-bf4db1999ce6bff4.exe`), image `windows-2025-vs2026` 20260925.250.1, provisioner 20260901.588, region northcentralus. Attempt 1 (red) and attempt 2 (green) of 37569806425 are at the same sha. The libtest order changes from run to run (real parallelism).
- wip against main: 3/8 against 0/5. Fisher's exact test puts that around p≈0.2, which is not significant. The T-066 `ci.yml` changes (rust-cache `save-if` on main only, pnpm store) cannot be told apart in the data: the test binary is the same and the image is the same.
- Control: `src-tauri/tests/credentials.rs` is green 13/13 in the same jobs. It has five parallel tests with the same raw `CredWriteW` (GENERIC, `CRED_PERSIST_LOCAL_MACHINE`, user `voicen`), `CredReadW` and `CredDeleteW`, but no `CredEnumerateW`. Only `purge_credentials.rs` also enumerates (the purge, `WinCredentialNamespace::list`) while other threads write. That is suggestive (13/13 against 10/13) but not significant.

**Hypotheses.**

1. *A test deletes or overwrites a sibling's target (race inside the binary).* **Refuted by code.**
   - Prefixes are `voicen-test-<pid>-<n>-<nanos>/`. `n` comes from a process-wide atomic, so two prefixes never share `n`. The trailing `/` comes right after the decimal nanos, so `…-1-…/` can never be a string prefix of `…-10-…/`: the separator after `n` is `-`, and the prefix ends in `/`.
   - `voicen_core::secrets::purge_credentials` lists `<p>Voicen/*`. Even if `CredEnumerateW` matched more (its filter may be case-insensitive), the policy removes only `entries.filter(|e| e.target.starts_with(&prefix))`, which is a case-sensitive check against the test's own prefix. `FailOne` and `WinCredentialNamespace::remove` delete an entry the policy passed them, by exact target.
   - `Planted::drop` deletes only the exact targets that test registered.
   - No other process touches Credential Manager during the step: cargo runs the test binaries one after another, and the installed-exe purge step (ci.yml step "The installed voicen.exe --purge-credentials …") comes later.
   - Only grep and reads were used. Serena was not callable in this session.
2. *Credential Manager answers a read-back with an error under concurrent access from the test threads (a lost write, or a transient read failure).* **Consistent with everything, not proven.**
   - Every failure falls in the ~3 ms opening burst. The control binary without enumeration has never failed.
   - The Microsoft docs say nothing about concurrency for CredWriteW, CredReadW or CredEnumerateW (learn.microsoft.com, fetched 2026-10-07). They list only `ERROR_NOT_FOUND`, `ERROR_NO_SUCH_LOGON_SESSION` and `ERROR_INVALID_FLAGS` for CredReadW.
   - Missing evidence: the Win32 code, and whether `CredEnumerateW` lists the target at the moment `CredReadW` misses it.
3. *Build or cache difference (T-066 ci.yml).* **Refuted.** The same exe passes and fails at the same sha, on the same image.
4. *Runner or image drift.* **Refuted for these runs.** The image and provisioner versions are identical in red and green.
5. *This class was fixed before.* Related, not the same:
   - F-009 (run 37444780779): a `cmdkey` plant could not be confirmed by read-back. The Win32 error was discarded there too, and H1/H2 (write refused or read missed) were never settled. That fix moved CI steps to `scripts/ci/credentials.ps1`, which prints every Win32 error. This file's own `raw_exists` was not changed.
   - F-007: a Windows premise first checked on CI. The task was first filed under class `ci-premise-unchecked-before-main`; after review 1 #2 it is `parallel-tests-share-session-state` (F-012's own row in `docs/failures.md`), because P-016 already caught it on `wip/` (0 red `main` runs) and its rule, the `serial()` lock, is not that class's rule.
   - F-004 (shared state between sibling tests in one binary) is the same shape: a sibling test in the same binary breaks a premise.

**Root cause (as far as proven).** Parallel test threads in one binary share Credential Manager. A read-back that runs during their concurrent opening calls can fail even though the plant's write returned Ok, and the test throws the Win32 code away, so the cause cannot be named. In-binary cross-deletion is excluded.

**Invariant and seam.** See `analysis`. The lock goes in `purge_credentials.rs`, and in `credentials.rs` for the same reason. Take the guard as the first `let _serial = serial();` of each test so that it is dropped after `Planted` (reverse declaration order), and the cleanup deletes also run under the lock. Cross-binary concurrency does not exist, because cargo runs test binaries one at a time.

**Options.**

- **(A) Recommended: diagnostic, then serialisation.**
  - Read-back returns `windows::core::Error`. The premise panic names `CredReadW`, the HRESULT and the Win32 code, and adds a report-only `CredEnumerateW(<exact target>)` look (listed: yes / no / err). It still panics.
  - Then the `SERIAL` lock.
  - Red test first: `read_back_of_a_never_written_target_names_its_win32_error` (CredReadW of a fresh never-written target → Err 1168, and the message contains it).
  - Why it removes the cause: the only concurrency that differs between the red and green binaries goes away, and a future miss names its code.
  - Risk: if the miss also happens without concurrency, the lock does not help, but the diagnostic then names the code (exit (a) is then wrong, and this becomes an rca).
  - Rollback: revert the commit.
- **(B) Diagnostic only.** This satisfies Acceptance 1 and 2 to the letter, but the binary stays red about 25% of the time, and under P-016 that keeps blocking every non-docs task (T-070 now).
- **(C) `--test-threads=1` for `cargo test -p voicen` in ci.yml.** It serialises every shell binary, slows the step and is invisible to a local run. Not recommended.
- **Rejected:** retrying the read until it succeeds. That is a workaround that would hide a lost write.

**Product impact.** The product never makes these calls concurrently within one process in a way the tests model. `--purge-credentials` runs alone in its own process at uninstall, and `WinCredentialStore` writes from the settings save. Whether a running app and an uninstall purge can overlap (app writing while purge enumerates) is a separate question for T-025. It is not shown by these tests.

**Question for the owner.** Should the developer push commit (1) (diagnostic, no lock) to `wip/T-069` alone first and re-run until a red attempt names the Win32 code (at about 25% per attempt, roughly 4 attempts of ~8 min each), so the mechanism is named before the lock removes it? Or ship (1)+(2) together, unblock T-070 now, and accept that the mechanism stays "concurrency inside Credential Manager, code unknown" (logged as an F-entry with that limit)? Recommendation: ship together. The diagnostic stays in place for any future miss, and P-016 is blocked now.

**Tools.** Serena and context7 were not callable here (no MCP tools exposed). I used grep and file reads for the code, and learn.microsoft.com directly for the Win32 docs (CredWriteW, CredReadW, CredEnumerateW). CI evidence came from `gh api repos/smykov/voicen/actions/jobs/<id>/logs`.

**Answer (orchestrator, 2026-10-07):** ship (1)+(2) together, as recommended. This is a technical choice, not a product one; the owner is told in the session report.
