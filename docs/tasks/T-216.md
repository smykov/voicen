## Investigation

Tools: Serena not used (YAML/bash only, as the orchestrator directed); grep and file reads over `.github/workflows`, `scripts/ci`, `Makefile`, `docs/`; context7 `/github/docs` for concurrency; `/opt/gha-pool/README.md`, `runner-once.sh`, `runner-pool.sh` read (not the env file).

**Concurrency.** Today both groups are repository-wide, so a third queued dispatch or stage cancels the pending one, and the chain ends with no comment (T-202 already noted this, `docs/tasks/T-202.md` design note). With `teamwright-agent-${{ inputs.task_id }}` / `teamwright-next-${{ inputs.task_id }}` (workflow-level concurrency accepts the `inputs` context) groups are per task: only a duplicate dispatch of the same task can replace that task's own pending run, which is intended. A 6th task never reaches a concurrency queue: its dispatcher stops it by count. Jobs waiting for a free runner are queued, not concurrency-pending, and are not cancelled. The prefixes differ, so the two workflows' groups never collide.

**>limit: stop, not wait.** A wait loop holds one pool runner idle for up to 15 minutes, then turns red; a stop with the Issue comment (exit 0, like the hop-limit and nothing-moved stops) lets the owner or queue re-label. The own-run wait (18 x 10 s) stays: the chain step starts the dispatcher before the stage job's keep/upload steps end.

**The count.** `contour-busy.sh` takes the task id from `displayTitle` (`^teamwright agent (T-[0-9]{3,}) `, the run-name of teamwright-agent.yml:9), counts distinct other ids over runs with `status != "completed"` (queued, waiting, pending, requested and in_progress all hold or will hold a runner), and treats a title it cannot parse as one more other task (fail-closed). `--limit 50` stays (well above 5 unfinished runs). Extracting it into a script is the testable seam: the inline jq cannot be fed faked JSON without a workflow runner, and the release-guard harness checks raw text, not behaviour (and P-020 forbids a shell reader in the guard). The script runs from the dispatcher's checkout of `main` (host bash + jq, as today).

**Limit value (decisions #292 -> #294).** The design is for N parallel tasks; N is `MAX_PARALLEL` in teamwright-next.yml job env (below `jobs:`, so not in the byte-pinned head), 2 now (VM 105 RAM), 5 when VM 105 grows: that is one line plus the docs that name the number (CLAUDE.md row, ci-toolchain.md). No test pins the number itself. The task title and Acceptance still say 5; the orchestrator aligns them with #294 (outside this block). Per #293 there is no red-tests stage: the developer writes `contour-busy.test.sh` with the change, and it still has to be red on today's tree (no script, inline `*other*` check).

**Shared state with several tasks at once (2 now, 5 later)** (checked, no change needed unless noted):
- Pushes: the push step (teamwright-agent.yml, "Push task/<ID>...") writes only `refs/heads/task/$TASK_ID` and, after implement, `wip/$TASK_ID`, each from a fresh repo in `RUNNER_TEMP`; `scripts/tw-wip-push` is not used by the contour (grep). Nothing writes `main`; the dispatcher only dispatches `--ref $MAIN` and opens a PR per task.
- `ci.yml` dispatch on `wip/<ID>`: its group is `ci-refs/heads/wip/<ID>` (ci.yml:18-20), per task, on GitHub-hosted runners: no interaction.
- Runner workspaces are per JIT container (`/srv/gha-work/<NAME>`); `RUNS_DIR/<run id>` is per run; `tw-run` caches live under the workspace (`.teamwright/cache`, tw-run `CROOT`): no sharing.
- Docker: every runner uses the host socket of VM 105, so `voicen-rust` / `voicen-ui` images are shared. A missing image may be built by two preflights at once (same tag, same Dockerfile, last one wins): duplicate work, not a corruption. Not changed.
- Artifacts `teamwright-agent-<ID>-<run>-<attempt>` and Issue comments are per task.
- Merge-time only: numbered append-only logs (`docs/decisions.md` rows, F-NNN, OQ-NN) written on two task branches can collide at PR merge; reviewer's concern, not a runtime hazard.

**Residual (document under ci-toolchain.md Not caught):** with per-task dispatcher groups two dispatchers of different tasks can count at the same moment and both start, so the limit can be exceeded by the number of simultaneous dispatchers minus one; the pool's `MAX` caps real parallelism anyway. Owner infra, outside the repo: the voicen pool row says `MAX 1`, CPU/RAM 4 / 8g per container; stages and dispatchers share the `claude` label, so `MAX` >= `MAX_PARALLEL` + 1 (3 now: 2 stages + 1 dispatcher) avoids dispatcher latency; parallel Claude sessions on one subscription token may hit usage limits.

**Guard and docs in the same commit:** both heads' concurrency lines and comments (agent :1-6, :35-39; next :1-6, :33-36), `scripts/ci/contour-heads/*`, every header copy in `scripts/ci/fixtures/release-guard/{ok,v}-contour-*` (release-guard.test.sh:930 compares ok-contour with the heads; the `cdiff` cases are relative to ok-contour; `v-contour-extra-scope-*` keep their one mutation), new `scripts/ci/contour-busy.sh`, `scripts/ci/contour-busy.test.sh` (+ `scripts/ci/fixtures/contour-busy/`), Makefile target `check-contour-busy` added to `check:`; `CLAUDE.md` row (contour: per-task groups, up to `MAX_PARALLEL` tasks, 2 now, decisions #294); `docs/decisions/ci-toolchain.md` R14 paragraph (the head pins per-task `concurrency:`), checker table row for `check-contour-busy`, and Not caught (count race).
