### What was checked by reading (the caller's list)

- **The predicate against the pinned sources:**
  - tao 0.37.1 `event_loop.rs:629-687` registers the class `w!("Tao Thread Event Target")` and creates it with `WS_EX_TOOLWINDOW` among its ex-styles. It is top-level and unowned (parent `None`).
  - tao then calls `SetWindowLongPtrW(GWL_STYLE, WS_VISIBLE | WS_POPUP)`. This replaces only the style and leaves the ex-style alone, so the window is excluded twice: once by the `WS_EX_TOOLWINDOW` test and once by the class-name test.
  - The settings window is a normal tao window. `window_state.rs:238-275` never adds `WS_EX_TOOLWINDOW`; the "on taskbar" flag adds `WS_EX_APPWINDOW` instead. `settings_window::open` sets no parent, owner or skip-taskbar. So that window counts as shown.
  - wry 0.57.0 `webview2/mod.rs:257-268` creates its container with `Some(parent)`, which makes it a child window that `EnumWindows` does not list. WebView2's renderer windows belong to `msedgewebview2.exe`, a different PID.
  - The tray (tray-icon 0.25.1) and the IME windows have no `WS_VISIBLE`. No tray exists before T-006 anyway.
  - `run()` does not spawn or re-exec itself (no `Command::new` or single-instance code in `src-tauri/src`), so the PID from `Start-Process -PassThru` is the PID that owns the windows.
- **Do the checks bite (by reading):**
  - First launch requires exactly one shown window with the title `-ceq 'Voicen'`. Removing the executor gives zero windows (red). A second shown window also turns it red.
  - Loaded launch requires zero shown windows for 10 s while the process stays alive. A config window put back is visible, unowned and not a tool window (red).
  - The title is set at `CreateWindowExW` (`.title(TITLE)`), and the page `<title>` does not change it (round 1).
- **P/Invoke and charset:**
  - `GetClassNameW` and `GetWindowTextW` use `CharSet.Unicode`, so `StringBuilder` is marshalled as LPWSTR, and `cls.Capacity` is exactly the 256 and 512 passed to the constructors.
  - `GetWindowLongW` has no `CharSet` (Ansi). With `ExactSpelling = false`, the runtime first probes the name as written, and `user32.dll` on x64 exports `GetWindowLongW`. It has no string parameters.
  - `GetWindowLongW` instead of `GetWindowLongPtrW` is correct for `GWL_EXSTYLE`: ex-styles are 32-bit, and only pointer-sized indices need the `Ptr` form.
  - `GetWindowThreadProcessId(IntPtr, out uint)`, `GetWindow(IntPtr, uint)` returning `IntPtr`, `IsWindowVisible` returning a 4-byte BOOL marshalled as `bool`, and `GW_OWNER = 4`, `GWL_EXSTYLE = -20`, `WS_EX_TOOLWINDOW = 0x80` all match the Win32 declarations.
  - `GetWindowTextW` on another process's window reads the cached text without sending `WM_GETTEXT`, so the call cannot hang.
- **Delegate lifetime:**
  - `EnumWindows` calls back only during the call. The delegate is a local that is passed as an argument, and `GC.KeepAlive(cb)` comes after the call.
  - The callback never throws: it makes no allocations that can fail beyond normal managed ones, and it runs no PowerShell code.
- **Compiles under Add-Type (pwsh 7, Roslyn):**
  - In pwsh 7, compiler warnings are written as errors unless `-IgnoreWarnings` is passed, and `$ErrorActionPreference = 'Stop'` (prepended by the runner) would make them fatal. So I checked for warnings.
  - The public fields of a public class do not raise CS0649. Every constant is used. The private nested delegate is used only by the private extern, so CS0051 does not apply. Unused lambda parameters produce no warning. `#nullable` is off by default, so CS8618 does not apply.
  - `List<T>`, `StringBuilder`, `GC` and `DllImport` are all in pwsh's default reference set.
- **Dot-sourcing and Add-Type re-definition:**
  - Each `shell: pwsh` step is a new `pwsh` process, so the type is compiled once per step and steps cannot collide.
  - Dot-sourcing the same source twice in one session is a no-op in pwsh 7 (identical source is cached). Only different source under the same type name fails.
  - `./scripts/ci/visible-windows.ps1` resolves against the step's default working directory, `$GITHUB_WORKSPACE`.
  - The execution policy already allows the runner's own temporary `.ps1`, and the checked-out file carries no Mark-of-the-Web.
  - The here-string markers `@'` and `'@` sit alone at the end and start of their lines, and line endings do not matter for them.
  - `[VoicenWindows]` inside the function body resolves at run time, after `Add-Type` has run.
- **PowerShell semantics:**
  - In `Get-ShownWindows`, unary `,` binds looser than `::`. The function therefore returns the array as one object, including the empty array, so `.Count` and `[0]` behave as intended.
  - In `Format-ShownWindows`, an empty array returns `none`, and public C# fields are exposed as properties (`$_.Class`, `$_.Title`).
  - No `Set-StrictMode`, and nothing in the code depends on it.
  - `continue` inside the `for` loop only skips the window probe. The log, settings and Run flags have already been updated for that iteration.
  - `$proc.HasExited` works on the `Start-Process -PassThru` object for a process of the same user.
- **Timing:**
  - First launch: up to 30 polls of 1 s each, plus one enumeration per poll (milliseconds). The Roslyn compile at dot-source time costs a few seconds once per step, before the launch.
  - Loaded launch: it waits for its own start line, counting lines in the append-mode log, then samples 10 times at 1 s intervals. As documented, this is a bounded negative.
- **Single source:** both steps call the same function, and `installer-ci.md` points to the script instead of restating a second rule.
- **Secrets:** the log prints only the class and title of the app's own windows. No user data is involved.
