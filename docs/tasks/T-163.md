## Context

T-140 ships the WER scorer and a per-utterance harness (decision #200, option A). SC-004, FR-047 and R23 ask for the WER of the final pass, measured on LibriSpeech concatenated per speaker group so that the chunker and the VAD run. That needs T-138 (final-pass runner), T-137 (chunker) and T-134 (speech spans). Two points are left for the analysis. First, does the measurement go through energy spans in a core example, or through Silero in a voicen-whisper example? Second, does a ~30 min concatenated WAV fit the provider's upload limit?

Owner 2026-11-08 (OQ-81, decisions #252): the SC-004 figure counts on **energy spans**. The core example runs `run_pass` with `primary: None` in the `core` image; SC-004 is recorded as "final pass, energy spans (the fallback path)", and no Silero figure is claimed; R23 and T051 stay as written. **Both sets go through the pass**: `librispeech` and the Russian `pairs` mode use the one final-pass transcription path in the example.

## Acceptance

- [ ] The example measures the set's WER through the final-pass runner on concatenated speaker groups, with the same `wer::score` / `wer::normalize`
- [ ] Which span source is measured (energy or Silero) is recorded and owner-confirmed
- [ ] Failure branch: a set shorter than 30 min or a missing reference is refused; no transcript or key is printed, held by a test of the shape T-140 chose (T-140 validation r1)

**The two open points of ## Context.**
- **Upload limit: settled, no owner needed.** The concatenated group is never one request. The pass sends chunks of at most `TIMED_MAX_MS` = 120 s (time-less at most 30 s) as 16-bit WAV, which is at most about 3.84 MB per request.
- **Energy or Silero: needs the owner (OQ-81).** A core example can use only energy spans (`primary: None`, the pass's own fallback). Silero needs a `voicen-whisper` target, which only the Windows MSVC job builds. R23 names a `voicen-core` example. The app's primary will be Silero (T-139), so the energy figure is the fallback path's. Acceptance 2 requires the owner's confirmation in any case.

**Second owner point (in OQ-81).** FR-047 asks for "the final's WER" for both sets, so the Russian `pairs` mode should go through the pass as well. That leaves one transcription path in the example. Recommended: yes.

**Behaviour changes of the owner tool.**
- `VOICEN_WER_KEY` becomes required, because `run_pass` refuses a missing key (FR-022). Keyless local servers can no longer be measured.
- The per-request deadline comes from `Settings.timeouts.api_transcription_s`, set to 120 s as today's `REQUEST_TIMEOUT`.
- The quickstart step 8 text changes with it.

**Dependency T-138 and mutant 101.** T-163 is not affected. Mutant 101 (`Lane::refill` reading one window ahead) changes only how far ahead a lane decodes, which is about 3.84 MB per track, bounded. It does not change which chunks are sent, in what order, or what is merged. Validation 4 states the product code is correct. The owner's choice is either (a) one more deterministic test or (b) accept as a follow-up, and neither changes `run_pass`'s signature or output. If (a) ever finds and fixes a real read-ahead, the example's figures do not move.
