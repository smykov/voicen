## Context

§2 success 3, spec 006 Q5.

## Acceptance

- [ ] Tag `vX.Y.Z` with X.Y = the repository's MAJOR.MINOR and Z ≥ the tag run's `github.run_number` (e.g. `v0.1.200`; run 100 is already used) on a matching build → release with the installer and its SHA-256
- [ ] Failure branch (#102): tag MAJOR.MINOR ≠ repository MAJOR.MINOR (e.g. `v0.2.200` on a `0.1` tree) → the release job fails naming both, nothing published — verified by the release job on a test tag
- [ ] Failure branch (#103): tag patch below the tag run's `github.run_number` (e.g. `v0.1.1`) → the release job fails naming the patch and the run number, nothing published
- [ ] Test that fails without the change: `release job version check`

## Investigation

**Frame.** Expected (spec 006 US5 AC 3-6, FR-029): a pushed `vX.Y.Z` tag, after gate and windows pass, creates GitHub Release `vX.Y.Z` with the installer and a SHA-256 checksum; a tag/app version mismatch fails naming both and publishes nothing; an existing release is not overwritten. Observed: `.github/workflows/ci.yml` triggers on `v*` tags but has only `gate` and `windows`; a tag run builds, smoke-tests, uploads `voicen-installer-<commit>` as a run artifact and sends it to Telegram. No release step, no `permissions:` anywhere (default token), no checksum.

**Hypotheses.** (1) Feature simply absent - confirmed (job list, `grep -n permissions` empty). (2) Second path: the Telegram send is the only other outward publication on tags; it stays as is and must not move into the release job (telegram-guard pins its `if:`). Releasing must not create a second version computation: `scripts/ci/version-stamp.sh` remains the one place V is computed (P-010). (3) Class fixed before: none, `class: ci-deploy` siblings T-002 (deploy smoke), T-070 (Telegram) give the pattern: premise on every ref, outward step gated, host-tested script, guard tripwire.

### What "app version" means under decision #98

- `version-stamp.sh` (T-077): branch/PR builds get `<repo MAJOR.MINOR>.<run_number>`; a tag build gets `X.Y.Z` from the tag and ignores the repo's MAJOR.MINOR. It writes V into `Cargo.toml`, `tauri.conf.json`, `package.json`, `Cargo.lock` of the build tree (not committed); installer name `Voicen_<V>_x64-setup.exe`; `CARGO_PKG_VERSION` = V (start-line check).
- So for a tag build the **stamped** version equals the tag by construction. "Tag != stamped" can only fail on a stamping/build defect (e.g. a stale or second installer, a stamp regression). Still worth checking against the artifact (it is what gets published), but it cannot be the owner's Q5 rule.
- The **committed** version (`0.1.0` in all three files) carries a meaningless patch under #98. "Tag != committed X.Y.Z" refuses every tag except `vX.Y.0`, i.e. it needs a bump commit per release, which #98 rejected ("no extra commits"). Not viable.
- **Decided rules** (the check `release-check.sh` makes, besides the artifact check: exactly one installer, `_X.Y.Z_` in its name):
  - **#102 (OQ-18 b):** tag `X.Y` must equal the committed MAJOR.MINOR (read from the unstamped checkout, the same three files `version-stamp.sh` reads); `v0.2.200` on a `0.1` tree fails naming `0.2` and `0.1`.
  - **#103 (OQ-20 b):** tag patch `Z` must be ≥ the tag run's own `github.run_number` (passed through `env:`); `github.run_number` counts every run of `ci.yml` on every ref, so each earlier CI build has a lower number and the release is higher than all of them. `Z` = run number is allowed (no earlier build had it). Refusal names both: `tag patch 99 is below this run's number 100`. A re-run keeps the run number, so a re-run of an accepted tag still passes (and then stops on "release already exists"). The latest run number is already 100 (2026-10-09), so the decision's example `v0.1.100` would now be refused; the acceptance names the rule plus an example (`v0.1.200`).
- Both rules run in the release job (the acceptance: "the release job fails naming both"); the windows-job premise runs the same script so its pass path and failure branch are proven on every `wip/` run (below). They are not added to `version-stamp.sh`: a refused tag still builds and its Telegram copy is sent from the windows job (not a GitHub publication). See remaining note at the end.

### Placement in ci.yml

- New job `release`: `needs: [gate, windows]`, `runs-on: ubuntu-24.04`, job-level `if: ${{ github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v') }}`, job-level `permissions: contents: write` (only this job; no workflow-level write). Steps: `actions/checkout@v5` (committed tree, unstamped: gives MAJOR.MINOR), `actions/download-artifact@v4` with `name: voicen-installer-<commit>` (same major as the `upload-artifact@v4` step; the commit comes from a windows job output or `git rev-parse --short=7 HEAD`), `scripts/ci/release-check.sh "$GITHUB_REF_NAME" . <dir>` (inputs via `env:`, never interpolated), `sha256sum` -> `SHA256SUMS.txt` in sha256sum format, release notes file (FR-030 SmartScreen line, version, commit), then `gh release create "$GITHUB_REF_NAME" <installer> SHA256SUMS.txt --verify-tag --title ... --notes-file ...` with `GH_TOKEN: ${{ github.token }}`. gh 2.101 (local `gh release create --help`) creates a draft, uploads assets, then publishes, so a failed upload leaves an unpublished draft, not a half release; the runner's gh version must be read in the step log (`gh --version`). No third-party release action: `check-ci-wip` classifies every `uses:` fail-closed and only knows checkout, cache restore/save, upload/download-artifact, rust-toolchain, rust-cache, setup-node, pnpm; a new action would turn it red, gh needs none.
- Never runs on `wip/**`: the job `if:` is false there (shown as skipped), so no publish and no write token use. P-016 caveat (as for the Telegram send): the publish step's first execution is the owner's first tag. Mitigation below: everything before `gh release create` also runs on every wip run.
- Windows job, after `upload-artifact`, a premise step on every ref: print the installer's SHA-256 (cross-check for the release evidence: the release's `SHA256SUMS.txt` must match it) and run `release-check.sh "v$VOICEN_VERSION" "$RUN_NUMBER" . target/release/bundle/nsis` (pass path on a real runner: wip builds are `<repo MAJOR.MINOR>.<run>`, so #102 holds and the patch equals the run number, the #103 boundary). On non-tag refs, failure-branch steps run it with synthetic bad tags — `v<MAJOR>.<MINOR+1>.<run>` (#102) and `v<MAJOR>.<MINOR>.<run-1>` (#103; skipped when run = 1) — and are red unless the script exits 1 naming both values (pattern of `telegram-failure-branch.sh`). The existing release-exists check needs `gh release view`, which needs the token: in the release job only (stubbed in the host test).
- Telegram: unchanged. It runs inside the windows job on tags, before and independent of the release job; `release` must not read the Telegram secrets (`check-telegram-guard` would flag a step without its `if:`).
- Concurrency: tags already get a per-run group; nothing to change.
- Tripwires that must stay green: `check-ci-wip` (push branches unchanged; only `actions/checkout` and `actions/download-artifact` added, both classified), `check-telegram-guard`, `check-telegram-send`, `check-telegram-failure-branch`, `check-version-stamp` (script unchanged unless the owner wants the rule in the stamp), `check-ci-credentials` (no Cred* calls), `check-setup-node-cache` (no setup-node in `release`), `check-shell-layout`, `check-nsis-fork`, licenses (no dependency change). New: `check-release-check` (the script) and a release-guard tripwire on the real `ci.yml` (fixtures + real file, like `telegram-guard.sh`): every step calling `gh release` (create/upload/edit/delete) is in a job whose `if:` has `github.event_name=='push'` and `startsWith(github.ref,'refs/tags/v')` as top-level `&&` operands, with no status function and no `continue-on-error`; that job `needs` both `gate` and `windows`; a `release-check.sh` step precedes the first `gh release` write step in the same job; `contents: write` appears only on that job. This pins the "nothing published" guarantee that no wip run can show (lesson of T-070 mutation M6).
