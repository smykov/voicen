### Round-2 #1: closed

**Fix.** `+page.svelte:307` is `{t("settings.saved")}{#if hasWarnings}{` ${t("settings.saved_with_warnings")}`}{/if}`. The built client confirms the leading space survives compilation. `build/_app/immutable/nodes/3.*.js` sets the branch's text node to `` ` ${H(`settings.saved_with_warnings`)}` ``. Only the `{#if}` branch carries the space, so the no-warning status stays `settings.saved` alone. The `exactly(en("settings.saved"))` checks still pass, and the gate is green.

The template literal is an acceptable substitute for the `{" "}` that round 2 suggested. eslint's `svelte/no-useless-mustaches` refuses `{" "}`, and the comment at `:303-305` records why the space sits inside the expression.

**Test.** `sentences(first, second)` matches `^\s*first\s+second\s*$` and is applied with `toHaveText` in:
- the field-level test (`:435`);
- the form-level-only test (`:479`);
- the ru test (`:248`), so both languages are covered.

**Does the test bite?** Yes. In Playwright 1.63.0, `ExpectedTextMatcher.matches` (playwright-core `coreBundle.js`) does not normalize whitespace on the RegExp path. It tests the raw text. The old markup rendered `Settings saved.Review…` with no whitespace between the sentences (round-2 compile evidence). `\s+` needs at least one whitespace character, so all three assertions turn red on the old markup. I settled this by reading and ran no mutation: this is a Medium wording guarantee, not a critical one.

**`\s+` vs a literal single space.** `\s+` is the right strength. Because the RegExp path sees raw text, the `^\s*` / `\s*$` anchors are needed anyway to absorb the newline and indentation inside `<p>`. Between the sentences, the user-visible guarantee is "separated". HTML collapses any whitespace run to one space, and assistive technology reads it as a word break. A literal single space would also reject a legitimate line-break separator in the markup, and it would catch no additional user-visible defect.

The one thing `\s+` accepts that a literal space would not is U+00A0. That is still a visible separator, so it is no defect.
