### Points the orchestrator asked about

- **Is the summary in the status on every save with warnings?** Yes, as far as the DOM goes:
  - `save()` sets `saved = false; warnings = {}` before the await. It sets `saved` and `warnings` from each outcome.
  - `hasWarnings` is derived from the page `warnings`, not from `renderedFields`, so it covers field-level and form-level warnings alike. The second announcement test bites on a field-level-only derivation.
  - The `<p role="status">` is unmounted at the start of every save and mounted again with its text on a `Saved`. A language switch re-renders the text in place.
  - Caveat, not a T-015 finding: this "insert a live region that already holds its text" pattern was inherited from T-004's "Saved". Screen readers announce a live region more reliably when its content changes than when the region is inserted (NVDA/JAWS behaviour varies). The summary is exactly as audible as "Saved" is today. See the note below.
- **Does the UI-only id follow `docs/decisions/i18n.md` and its parity tests?** Yes.
  - `t("settings.saved_with_warnings")` is a `MessageId` literal, so svelte-check refuses it without an `en` key (lint green).
  - The parity tests (`catalog_parity_holds_for_the_real_catalogs` in core, `catalogProblems` in `i18n.test.ts`) refuse a missing or empty `ru` text.
  - The id has no Rust declaration and needs none (rule: "A UI-only id … needs no Rust declaration"). Precedent: `settings.field.not_restored` is not pinned in core either. Only `error.ipc_unavailable` is, through T-004's `settings_window_message_ids_exist`.
  - No new `as MessageId` cast was added.
  - The en/ru texts carry no placeholders and read correctly.
- **No new rule in the UI.** `hasWarnings` only counts keys. It holds no URL, scheme or host logic. W's "Don't" list grew consistently: no assertive live region, no silent warning, no warning text repeated in the status.
