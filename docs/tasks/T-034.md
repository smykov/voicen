## Context

Split from T-014 by decision #35 (T-014 analysis, option B). T-014 builds the `Autostart` trait, the save step with undo, `reconcile_autostart`, `WinAutostart` (HKCU Run value `Voicen`, data `"<exe>" --autostart`) and `launched_by_autostart(args)`. This task adds what needs the settings window (T-004) and the tray (T-006): the General-tab "Start with Windows" toggle over `settings_save` with its Playwright case (spec T059), and the logon behaviour — a start with `--autostart` opens no window, only the tray (FR-19; `startup_action` already returns `TrayOnly` for `Loaded`). A real logon can only be checked by the owner on Windows (SC-007 / spec T066): that needs a `verify_exception` the owner accepts — ask when this task reaches verification.

## Acceptance

- [ ] The General tab shows the toggle from `settings.start_with_windows`; switching it and saving sends `start_with_windows` through `settings_save` (Playwright, mocked IPC)
- [ ] Failure branch: `settings_save` returns `Refused` with `general.start_with_windows: autostart.failed` → the field shows the reason and is highlighted (`aria-invalid`); the draft keeps the user's value, as for every field (`docs/decisions/settings-ui.md`), and nothing is saved (Playwright)
- [ ] Windows CI: the installed exe started with `--autostart` and a loaded settings file opens no visible top-level window
- [ ] Owner, on Windows: with the setting on, after a real logon Voicen runs in the tray and no window opens
- [ ] Test that fails without the change: the Playwright case for the toggle and the Windows CI `--autostart` start check

## Investigation

**Frame.** Expected (FR-19, spec 004 US5, Acceptance): a General-tab "Start with Windows" toggle over `settings_save`; a refused Run-value write shows `error.autostart.failed` on the field and nothing is saved; a start with `--autostart` and a readable `settings.json` opens no window, only the tray; owner checks a real logon. Observed: the field exists on the wire and in core, but no control renders it; the deployed `--autostart` start is checked only for the Run value. This is a need, not a defect. Recurrence: class `autostart` has only T-014 (DONE, need); `docs/failures.md` has no autostart entry. `recurrence_of: []` stands.

**Where I looked.** Serena and Context7 were not used: plain grep and file reads instead. I ran `grep -rni "autostart|start_with_windows"` over `crates`, `src-tauri/{src,tests}`, `src`, `e2e`, `i18n` and `ci.yml`. I read `General.svelte`, `Output.svelte`, `draft.ts` (`applyOutcome`), `+page.svelte` (tabs, `renderedFields`), the e2e (L) cases, `settings_window.rs::on_ready`, `gate.rs::startup_action`, the install-smoke steps (`ci.yml:236-318`), spec 004 US5 and tasks T025/T059/T066, `docs/decisions/settings-ui.md` and decision #35. No library API is involved: the UI uses only existing Svelte bindings.

**What already exists (no work):**
- Core: `start_with_windows` (`settings/mod.rs:117`), FieldId `general.start_with_windows`, ErrorCode `autostart.failed`, the save step with undo, and `reconcile_autostart` (T-014).
- Shell: `WinAutostart`, `launched_by_autostart`, and `release_launched_by_autostart` passed to `on_run_event` → `settings_window::on_ready` → `startup_action`, which never consults the flag (`gate.rs:99`; US5-3).
- Shell tests:
  - `settings_window.rs::loaded_opens_no_window` (autostart false/true).
  - `first_run_launched_by_autostart_still_opens_the_window`.
  - `single_instance.rs::a_second_launch_by_autostart_opens_no_window`.
  - `autostart.rs::settings_save_with_a_refused_registry_write_is_autostart_failed`: the failure branch end to end through IPC, with `settings.json` unchanged.
- i18n: `error.autostart.failed` ("...Nothing was saved."), `settings.field_label.general.start_with_windows`.
- Static window removed: `tauri.conf.json` `windows: []`.

**What is missing:**
1. The control. `General.svelte` renders only `ui_language`. Every control uses a `settings.field.<x>` label (`en.json:74-85`), and none exists for this field.
2. A Playwright case. Spec T059's `e2e/settings-save.spec.ts` was never created. The save cases live in `settings-first-run.spec.ts` (`calls(page, "settings_save")`).
3. The deployed check. The `--autostart` launch in the Run-value step (`ci.yml:264`) asserts only the Run value. The no-window step (`ci.yml:278-318`) starts without arguments and asserts no tray.

**Q1 — Acceptance line 2 contradicts an area invariant.** The line says "the toggle returns to the saved value". But `docs/decisions/settings-ui.md` (Refused mapping) and `draft.ts::applyOutcome` keep the draft on every Refused, for every field. Reverting this one field would:
- add a per-field rule to the one mapping;
- make the highlighted control show a value the user did not choose.

The catalog text already says "Nothing was saved", and the core/shell tests prove nothing was saved. Recommendation: keep the draft (the toggle stays as the user set it, `aria-invalid`, `error.autostart.failed` under it, Save still dirty) and reword the Acceptance to that. Alternative: a field-specific revert in `applyOutcome`, which needs a new `settings-ui.md` invariant. This is a decision for the orchestrator or owner, not the developer.

**Effect on existing e2e.** The two (L) cases in `settings-focus-close.spec.ts` stay valid. `/settings` opens on Engine, and the General tab is not rendered there, so `general.start_with_windows` is still listed. Their comments "no control until T-034" must change. Add one assertion: on the General tab the label leaves the list and the toggle has `aria-invalid="true"`.

**Options:**
- **A (recommended).**
  - UI: a checkbox in `General.svelte` (pattern of `Output.svelte`), `settings.field.start_with_windows` in en/ru, new `e2e/settings-autostart.spec.ts`, and the (L) update.
  - CI: run the existing loaded-launch no-window step for `@()` and `@('--autostart')`, plus a `tray_icon_app` assertion, so one predicate covers both.
  - Risk: low. Rollback: revert the commit.
  - `ci.yml` is shared with T-061 (active in this tree), so the planner must serialize the two.
- **B.** Assert no window and the tray inside the Run-value step's `--autostart` launch instead. Fewer lines, but that launch is force-stopped as soon as the value appears, so the 10 s window sample would be cut short or duplicated. Not recommended.
- **C.** A shell integration test only (mock runtime). It already exists (`loaded_opens_no_window`), and it does not cover the deployed exe that the Acceptance asks for.

**Red tests (A):**
1. `e2e/settings-autostart.spec.ts`. Specs import from `e2e/support/boot`; run them with `pnpm e2e`.
   - "General tab shows Start with Windows from the saved view; toggling it and saving sends start_with_windows through settings_save once". Use `getByLabel(en("settings.field.start_with_windows"))` and assert the checked state from `view.settings.start_with_windows`. After the click and Save, `calls(page, "settings_save")[0].args` has `start_with_windows: true` and the other fields unchanged. This is red today: the control is missing.
   - Failure branch: `queueSaveOutcome` `Refused { errors: [{ field: "general.start_with_windows", code: "autostart.failed" }], form_error: null }` → the toggle has `aria-invalid="true"` and is described by `en("error.autostart.failed")`; the draft follows Q1's decision; no Saved status.
   - Optionally a Saved round trip: `Saved.view` with the field on → the toggle is checked and the draft is clean.
2. The i18n parity tests and svelte-check fail until `settings.field.start_with_windows` exists in both catalogs.
3. Windows CI, extended loaded-launch step: zero shown windows for 10 s after the start line, plus `tray_icon_app` present, for the `--autostart` argument list. This is a regression pin on today's code, which T-037 already built. Its bite is held by the shell tests above (`on_ready` deciding on the flag would fail `loaded_opens_no_window`).
