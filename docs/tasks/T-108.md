## Context

CI run 39299815752 (wip/T-099 @ 28aba7a, windows job, step `cargo test -p voicen --no-fail-fast`): `src-tauri/tests/hotkey.rs::esc_is_released_after_a_max_length_stop` panicked at `src-tauri/tests/hotkey.rs:725:5` with "Esc not claimed". The other 15 tests of the `hotkey` binary passed. `esc_claimed()` (`hotkey.rs:576`) probes Esc both bare and under Ctrl+Alt, and `eventually` waits `WAIT` = 3 s (`src-tauri/tests/win32_support/mod.rs:77`). The same test passed on earlier runs, including CI 39296012262 at 3186c2b. T-099's diff does not touch `src-tauri`. The investigator decides whether this is a probe race (another process holding or freeing Esc, or the hotkey thread's claim arriving after the 3 s window) or a real gap in the claim on press, and checks `docs/failures.md` and T-009 / T-043 for an earlier case of this class.

## Tests

Test-writer (red; runs only in Windows CI, Linux compile-checks with `make check-shell-windows`). The three tests are in `src-tauri/tests/hotkey.rs`, section `T-108: the Esc claim check never races the claim it checks`. Each one stops the hotkey thread inside the session's first `set_tray(Recording)`: `GatedIndicator` records the call in the rig's `FakeIndicator`, then waits on `TrayGate`. By then `Shared::publish` has queued the CancelKey request, but the thread cannot run it yet, so each collision is planted, not left to timing. The test seam is `hotkey.rs::esc_claim(rig: &Rig) -> Result<(), String>`. Its doc comment is the contract. Its body today is the T-009 check, unchanged: `eventually(WAIT, esc_claimed)`, which returns `Err("Esc not claimed")` when it fails. The developer replaces the body and keeps the signature. The developer may also move the probe into `win32_support`, add a `HotkeyRegistrarHandle` to `Rig` (attached in `start_hotkey`) for the round trip, and migrate the max-length, hold-mode-Esc, toggle and idle tests.

Characterization: none needed. The T-009 Esc tests already pin today's behaviour, and the extracted `esc_claim` body is that behaviour.

## Investigation

Tools: Serena was not used (grep and file reads over src-tauri and crates/voicen-core, which is enough for code this size). CI logs came from `gh run view --attempt N --log` and `--log-failed`. No library API decision depends on docs. The RegisterHotKey refusal is shown by this repo's own green test, not from memory.

**Frame.** Observed: in attempt 1 of run 39299815752, `esc_claimed()` stayed false for the whole 3 s WAIT after the press reached the session. The test took 3.06 s. Expected: the claim is visible within milliseconds; green runs take 75-140 ms for the whole test. Attempt 2 at the same sha was green. 1 sighting in about 112 Windows attempts since T-009.

**Hypotheses.**
1. *The probe collides with the claim* (confirmed by mechanism and timing; the direct trace is missing). `esc_is_free` registers the combination it checks. The hotkey thread claims each combination once (`Registrations::cancel_key`, no retry). The CancelKey request is queued after `audio.start`, which is the signal the test starts probing on. If the thread's `RegisterHotKey` lands inside the probe's register/unregister pair, the claim is refused for the rest of the recording and the probe never sees both combinations held. This fits the full-window failure (a permanent state, not a delay), the rarity (a microsecond hold every 10 ms, widened by preemption on a busy VM) and attempt 2 being green. The same exposure exists in `esc_while_recording_in_hold_mode_discards_with_the_hotkey_held`.
2. *Another process holds or frees Esc*: refuted. `assert_esc_free` passed at the start of this test and of the next one. A foreign holder makes the probe fail to register, so `esc_claimed` becomes true, not false.
3. *A second path / sibling tests in the binary*: refuted. Every Esc test takes `serial()` first, and cargo runs test binaries one at a time. No other file in `src-tauri/tests` probes Esc (grep `esc_is_free|esc_claimed`).
4. *The claim arrives after 3 s (hotkey-thread stall)*: not excluded, but nothing supports it. The thread had just handled the WM_HOTKEY press. Every other hotkey test in the job kept its usual timing, and the next test passed 1.08 s later. A longer WAIT would not fix hypothesis 1, because the claim is never retried.
5. *Max-length timer vs claim ordering*: refuted. `session.tick(pressed_at + MAX_LENGTH)` runs after the failing assert.
6. *A real gap in the claim on press* (product): no evidence. Shared::publish syncs the claim on every change of `live_id()`. A refusal by a real foreign owner is FR-22's specified EscUnavailable path. 105 runs since T-009 were green on this test.

**Missing proof.** The assert message does not print `rig.observer.events()`. The cheapest direct proof is a `Warning{EscUnavailable}` in the failing run, so the recommended fix prints the events in every Esc assert. A future red then names the collision, or shows that hypothesis 4 holds.

**Recurrence.** No. This is not os-answer-deadline-race: the verdict is not set by a clock, since a longer WAIT stays red. The test's probe changes the state it observes. F-014 (hotkey.rs, synthetic hold released early) is another test and another mechanism, and was never investigated. The closest logged entry is F-004 / test-port-race: a probe takes and releases a shared OS name, and that loses against a concurrent user of the same name. Same family, different resource and rule. No earlier task touched the Esc probe (grep `esc_is_free` in docs: only T-009's design lines). First sighting. A new F-entry with class candidate `test-probe-takes-claimed-resource`, related to F-004, is the orchestrator's call. Folding it into test-port-race instead would raise that class's count to 2.

**Owner question.** None needed for the recommended option (tests only). It becomes an owner question only if the fix should move into the product: retrying a refused Esc claim (option C) would change FR-22's EscUnavailable behaviour.
