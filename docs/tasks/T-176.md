## Investigation

**Frame.** Three Low review findings carried by T-060 §4 P7b (decisions #201): T-071 r1#1, T-071 r1#2 and T-012 r1#5. Expected: each item keeps its own doc; Win32 codes come from the `windows` crate; the non-directory branch of `ShellOpener` is tested; the process never builds a second `CpalSource` without a word. Observed on main 5d4f1fed: all three findings still hold (see `analysis.evidence`). The Acceptance line numbers are stale (lib.rs grew since T-071 and T-012), so the developer finds the spots by symbol.

**Hypotheses checked.**
- H1, already fixed by a later task (T-166 touched lib.rs for clippy): refuted. T-166 is DONE and changed lib.rs only for its lint fixes. The doc block is still above `install_logs_folder`, the const is still hand-written, and the `map_or_else(release_microphones, ..)` is still in `release_ports`.
- H2, a second path reads `Microphones`: refuted. grep of `Microphones` over src-tauri/src and src-tauri/tests finds only the struct, `wire`'s `manage`, `release_ports` and the `settings_list_microphones` `State` parameter. A `State` extractor already fails the command when the type is not managed, so `release_ports` is the only path with a silent fallback. Serena's index is stale, so this is grep only.
- H3, the non-directory branch is tested indirectly: refuted. `a_file_at_the_logs_path_is_never_opened_and_gives_one_warning` injects `FakeOpener`, so `logs_folder`'s own `is_dir` check is what it pins, not `ShellOpener`'s guard. `ShellOpener` keeps the guard as defence in depth (docs/decisions/windows-shell.md: "refuses a non-directory itself").
- H4, `windows` 0.62.2 lacks the constant: refuted. `Win32/Foundation/mod.rs:1771` has `ERROR_DIRECTORY: WIN32_ERROR = WIN32_ERROR(267u32)`, and `Win32_Foundation` is already enabled. The pinned crate source in `.teamwright/cache` was read; context7 was not needed.
- H5, this class was fixed before: no F-entry; these are one-off review leftovers.

**Why a panic and not a log line.** The fallback hides a wiring regression. With a log line the app would run with two sources: the settings list from one, the press from another. That breaks windows-shell.md invariant 2 ("lists through the same managed `AudioSource`"). A panic in `run()` comes before the loop, after the panic hook is installed (T-024), so it leaves a crash record. `run()` already treats impossible wiring states the same way (`.expect("assemble returned the app, so it ran the parts")`). It is not a product decision, so there is no OQ.

**Size.** One area (shell) plus a one-line core refactor. Small; no spec needed.
