## Investigation

**Refresh at ef52d65** (the first analysis was written at 1172cf7). I checked every claim again with grep and file reads. Serena and Context7 were not callable in this session. Package sources (windows 0.62.2, tray-icon 0.25.1) were read from the core image's cargo cache. Nothing was built or run: the host is Linux.

What changed since 1172cf7:
- `win/hotkey.rs` is unchanged (no commit).
- `lib.rs` `on_run_event` (T-024) still handles only `Ready`, `ExitRequested` and `Exit`. No power or session path was added.
- In the core, T-103 moved every `src` clock read to `crate::clock::instant` and enforces it with a deny lint (`check-ban-canary`). New core code takes its instant from the shell, and core unit tests use `crate::clock::instant()`.
- T-054 added `DictationSession::notice_with`. It does not touch `hotkey_registration`.
- `diag::observer` matches `RecordingEnd` exhaustively, so `Suspended` needs an arm there. This is new in the seam list.
- OQ-28 is answered by decision #131 (a). The conditional parts of the old analysis are now fixed decisions.

**Frame.** FR-26 / spec 001 US4 scenarios 3-4 (FR-013, SC-006) require that after sleep/resume, lock/unlock and an Explorer restart:
- the first press records;
- the tray icon is back;
- a failed re-registration takes the startup failure branch, once per transition registered → failed (decision #131).

Observed: no incident. No owner report and no `docs/failures.md` entry. This is a need: no code observes these events.

**What already exists (do not re-plan).**
- T-006 (VERIFIED): the hotkey thread with one hidden top-level STATIC window. It registers once at start and reports through `DictationSession::hotkey_registration`.
- T-055 (DONE): the two-step registrar (`Prepare` / `Commit` / `Abort` into the same thread).
  - Acceptance 1 is delivered: a taken hotkey on save is refused and the old one stays.
  - The startup half of Acceptance 3 is delivered: tray `HotkeyError`, `notice.hotkey_unavailable` for 3 s, settings on Recording / `recording.hotkey`, and the install-smoke step.
  - Evidence is in the analysis block.
- T-009 (DONE): Esc claims on the same thread. The session decides them from `live_id()`, so ending a recording on suspend releases them by itself.
- T-012 (VERIFIED): `RecordingController::device_lost` and the session's loss thread → `stop_recording`. Suspend copies this pattern.
- tray-icon 0.25.1 re-adds the icon on `TaskbarCreated` with the last icon, tooltip and visibility.
- The toast is not done yet: T-007 (TODO), on the same `hotkey_registration(false)` path.
- The Context sentence "also owns the hotkey step of T-032's save transaction and its tests" is stale: T-055 did that.

**Hypotheses.**
1. *Nothing receives the power or session notifications.* **Confirmed.**
   - The window is the system STATIC class, so its procedure is STATIC's.
   - `run`'s `match` sees only posted messages (`WM_REGISTRAR`, `WM_HOTKEY`, `WM_TIMER`).
   - `WTSRegisterSessionNotification` is never called, so `WM_WTSSESSION_CHANGE` is never even sent.
   - The window is top-level, not message-only, so it can receive broadcasts. Per the Win32 docs (from memory, the developer checks this), `WM_POWERBROADCAST` and `WM_WTSSESSION_CHANGE` reach a window through its procedure. That is why a procedure of ours is needed and a new `match` arm alone is not enough.
2. *The same concern is handled on a second path.* **Refuted.**
   - A grep over `src-tauri/src` and `crates/voicen-core/src` finds no power, session or suspend handling.
   - `on_run_event` has no arm for it.
   - tao's and tray-icon's windows are not ours to hook. `windows-shell.md` keeps the main thread free of session inputs.
   - The only existing path is tray-icon's `TaskbarCreated` handler, and it covers only the icon.
3. *The OS keeps `RegisterHotKey` registrations across sleep and lock, so re-registering is unnecessary.* **Open; CI cannot settle it** (the runner cannot sleep or lock). The re-registration stays either way:
   - it is harmless when the registration survived;
   - spec research R and FR-013 chose it;
   - it is the only retry for a hotkey that failed at startup (T-055 Q2 handed that retry to T-010).
4. *An Explorer restart breaks the hotkey.* **Not expected, unverified.** `RegisterHotKey` belongs to our window, not to Explorer. Covered by the `tests/tray.rs` pin and the owner check.
5. *This class was fixed before.* **No.** `docs/failures.md` F-001..F-016 has no `hotkey-registration` entry, so this is not a recurrence. F-014 (a SendInput hold ended early on the hosted runner) is another class. It shapes the tests: they prove registration with the 1409 probe (`TakenHotkey::take`), not with synthetic holds. Only test 8 uses one hold.
6. *A recording live at suspend is already ended.* **Refuted.**
   - There is no suspend input and no `Suspended` end.
   - After resume, the release poll would end the hold as `Released`, with the sleep counted as held time.
   - The spec edge case ("sleep while recording") says: stop and process, like a lost device.
7. *The notice rule already notifies once.* **Refuted.** `DictationSession::hotkey_registration(false)` notifies and asks for settings on every call, also when `ctrl.hotkey_error()` is already true. Today this never shows, because the only `false` caller is the startup one. The resume and unlock retry would make it show at every unlock, which decision #131 forbids.

**Root cause.** See the analysis block. It is a missing observer (a need), not a defect.

**Size verdict: one task, small.** There is one OS event source and three small adjacent changes:
- Shell (`win/hotkey.rs`): window procedure, session registration, `reassert`, suspend arm.
- Core (`recording/mod.rs` + `dictation.rs` + one arm in `diag/observer.rs`): `Suspended`.
- Core (`dictation.rs`): the transition rule in `hotkey_registration`.

The behaviour is settled by spec 001 (US4, edge case, research R, core-traits.md) and decision #131, and the task already has a `design_ref`, so no new spec is needed. If the orchestrator wants one seam per task, the core part could split off as a precursor that can be tested on Linux (`Suspended` + notify-once). I do not recommend it: the shell tests are the proof of both, and the split adds a Windows CI round for no isolation gain. No owner question is open.
