## Context

Narrowed by owner decision #63: the two-phase registrar, the save step and the startup failure branch moved to T-055 (P1); this task keeps recovery after sleep, lock and Explorer restart (release 2). FR-05, FR-26; two-phase registrar used by settings (spec 004 dependency). Also owns the hotkey step of T-032's save transaction and its tests (spec 004 T032, T041; decision #23): refused save keeps the old hotkey registered.

OQ-28 answered by decision #131 (option (a), the analysis's Q1 = "notify once"): the notice and the settings window come only on the transition working → failed; while already failing, resume and unlock retry silently (a success clears the error). This is the reading of FR-26's failure branch; spec 001 US4 scenario 4 (and data-model.md if the notice rule is written there) is reworded in the implementing commit.

## Acceptance

- [ ] A taken hotkey in settings → "hotkey unavailable", the old one stays
- [ ] After sleep/resume the hotkey records (owner check)
- [ ] Failure branch: saved hotkey cannot be registered at startup → tray error state + notice + settings open on the hotkey field — verified on Windows CI by registering the hotkey from another process first
- [ ] Test that fails without the change: `src-tauri/tests/hotkey.rs`

## Investigation

**Frame.** FR-26 / spec 001 US4 scenarios 3-4 (FR-013, SC-006): after sleep/resume, lock/unlock and an Explorer restart the first press records, the tray icon is back, and a failed re-registration takes the startup failure branch. Observed: no incident; no owner report or `docs/failures.md` entry says the hotkey dies after sleep or unlock. This is a need: no code observes these events. Read at 1172cf7 with grep and sed (Serena and Context7 were not callable in this session). Nothing was built or run: the host is Linux and there is no Windows.

**What already exists (do not re-plan).**
- T-006: the hotkey thread (`win/hotkey.rs`), one hidden top-level STATIC window, registers once at start and reports through `DictationSession::hotkey_registration`.
- T-055 (DONE): the two-step registrar (Prepare/Commit/Abort into the same thread). A taken hotkey on save is refused and the old one stays (Acceptance line 1). At startup, `hotkey_registration(false)` gives tray `HotkeyError`, `notice.hotkey_unavailable` for 3 s, and settings on Recording / `recording.hotkey` (Acceptance line 3, all but the toast). Tests: `hotkey_registrar.rs` (5 tests) and the install-smoke step "Loaded launch with Ctrl+Alt+Space taken". CI 37781212648 @ 77a7906 and 37786923563 @ 177a7eb.
- T-037: `settings_window::open(tab, field)`. T-052 / T-057: the tray.
- tray-icon 0.25.1 (`platform_impl/windows/mod.rs`) already removes and re-adds the icon on `TaskbarCreated`. It uses the last icon and tooltip that were set, so the `HotkeyError` or Idle image comes back as it was.
- Still missing from Acceptance line 3: the toast. It belongs to T-007 (TODO), on the same `hotkey_registration(false)` path (T-055 Notes).
- The Context sentence "also owns the hotkey step of T-032's save transaction and its tests" is stale: T-055 did that.

**Hypotheses.**
1. *Nothing receives the power or session notifications.* **Confirmed**:
   - The hotkey window is the system STATIC class, so any message sent to it goes to STATIC's procedure, not ours.
   - `run` acts only on posted `WM_REGISTRAR`, `WM_HOTKEY` and `WM_TIMER`.
   - No `WTSRegisterSessionNotification` call exists, so the session-change message is never even sent.
   - The window is top-level, not message-only, so it is eligible for `WM_POWERBROADCAST` (research.md R: message-only windows get no broadcasts). Unverified from memory: `WM_POWERBROADCAST` is sent, not posted, so the loop's `match` can never see it. A procedure of our own (option A) or a subclass (option B) covers both cases.
2. *The same concern is handled on a second path.* **Refuted**: grep over `src-tauri/src` and `crates/voicen-core/src` finds `WM_POWERBROADCAST`, `PBT_`, `WTS*`, `TaskbarCreated` and `Suspended` only in comments. tao and the tray window are not ours to hook: the `windows-shell.md` invariants keep the main thread free of session inputs. The tray-icon `TaskbarCreated` handler is the one existing path, and it covers the icon only.
3. *The OS keeps RegisterHotKey registrations across sleep and lock, so re-registering is unnecessary.* **Open, cannot be settled on CI**: the runner cannot sleep or lock. The spec (research.md R, FR-013) chose to re-register anyway, and FR-26 is checked by the owner. Re-registering from the active codes is harmless when the registration survived, and it is the only retry for a hotkey that failed at startup (T-055 Q2 handed that retry to T-010). So it is kept whatever the answer.
4. *Explorer restart breaks the hotkey.* **Not expected, unverified**: `RegisterHotKey` belongs to the hotkey thread's window, which Explorer does not own. The tray half is tray-icon's (evidence above). Left to a CI pin (test 9) plus the owner check.
5. *This class was fixed before.* **No**: `docs/failures.md` has no entry of class `hotkey-registration` or `hotkey`. F-014 is synthetic-input timing in `hotkey.rs` and is a different class. Not a recurrence.
6. *A recording live at suspend is already ended.* **Refuted**: `RecordingEnd` has no `Suspended`, and no suspend input exists. After resume, the release poll would end the hold as `Released`, with sleep time counted as held time and no defined rule. The spec's edge case says: stop and process, like a lost device (core-traits.md assigns the input and variant to T-010).

**Root cause.** See the analysis block. It is a missing observer (need), not a defect.

**Size verdict: small enough for one task, not large.** There are two adjacent seams driven by the same OS events:
- the hotkey thread's window and loop (shell);
- the controller's suspend input (core, beside `device_lost`).

Behaviour is already settled by spec 001 (US4, edge case "sleep while recording", research R, core-traits.md) except Q1 below. The work is already in the spec tool (`design_ref`), so no new spec is needed. Splitting the suspend stop into its own task is possible if the orchestrator prefers one seam per task.

**Owner question (Q1, product).** `hotkey_registration(false)` shows the notice and opens settings on the hotkey field on every call. With the retry on every resume and unlock, a hotkey that stays taken would pop the settings window at every unlock. Options:
- (a) Notify and open only on the transition into `HotkeyError` (working → failed), and retry silently while already failing. Proposed default.
- (b) Repeat the full startup branch on every failed retry (the literal reading of spec scenario 4).
- (c) Repeat only the 3 s overlay notice, without the window.

**Acceptance as it should read (for the orchestrator; I did not change it).**
- Line 1 and the startup half of line 3 are delivered by T-055. Mark them done with the evidence above, or drop them. The toast stays with T-007.
- Left:
  - simulated resume and unlock re-register the hotkey, also out of `HotkeyError` (Windows CI);
  - a failed re-register takes the startup branch per Q1;
  - suspend during a hold ends it as `Suspended` and processes it;
  - `TaskbarCreated` brings the icon back (CI pin);
  - the owner's SC-006 check: sleep/resume, lock/unlock and an Explorer restart, 3 of 3 presses each.
- Test file: `src-tauri/tests/hotkey.rs` (plus a pin in `tests/tray.rs`).

**Unverified facts the developer must check against the pinned sources or MS docs:**
- whether `WM_POWERBROADCAST` is sent or posted to a hidden top-level window;
- whether Modern Standby machines get `PBT_APMSUSPEND`;
- `WTSRegisterSessionNotification` needs the window on the calling thread. On a failure, write one warning line (`hotkey_thread_failed` with the OS code) and keep the hotkey working.
