**Design (recommended).**
1. **`win/hotkey.rs`, the hotkey thread (R-1, R-2).**
   - One std thread with a hidden top-level window: no `WS_VISIBLE`, so the smoke predicate drops it (`visible-windows.ps1:46`); top-level rather than `HWND_MESSAGE`, so T-010 can receive broadcasts later.
   - At start: `RegisterHotKey(hwnd, id, codes.modifiers, codes.vk)` with `win32_data::hotkey_codes(parse_hotkey(snapshot.hotkey))` (`MOD_NOREPEAT` always set), then `session.hotkey_registration(ok, at)`. A string that does not parse counts as not registered.
   - `WM_HOTKEY`: first one `SendInput` of the menu-mask key down/up (0xE8, R-2), then `session.hotkey_pressed(at)` with `at` stamped on arrival. Then a 10 ms poll, with the message loop still pumping (timer or `MsgWaitForMultipleObjects`): `win32_data::released(&codes.poll, |vk| GetAsyncKeyState(vk) < 0)`. The first tick that finds a key up stamps the release and calls `session.hotkey_released(at)`.
   - Nothing else: no repeat count, no hold timing, no `mode` (#63), no settings re-read (T-055 adds re-registration as a request to this thread).
   - A handle owns the thread: dropping it posts a quit message, joins and unregisters. In `run()` it lives as long as the process (tao's `process::exit` ends it). Tests drop it to free the global hotkey for the next test.
   - Lock contract: it holds no lock of its own across session calls. `hotkey_pressed` blocks it for the device open (bounded by design 2), and the release poll cannot run meanwhile: a release during the open is stamped at the first poll after it. The log's `press_to_frame_ms` shows the open time (FR-007: ≤ 200 ms at p95).
   - Failures (window class, window, thread spawn, registration with its OS code, 1409 = already registered) are typed `Warning` lines (#45, T-008 touch points); no `eprintln!`.
2. **`win/capture.rs`, `CpalSource: AudioSource` on the Windows default input device** (#64; T-012 adds the choice).
   - `start(sink)`: the open runs on an opener thread: `default_host().default_input_device()` (`None` = `NoDevice`), `default_input_config()`, `build_input_stream` for the config's sample format (converted to f32 into the sink, `Instant::now()` stamped in the callback), `play()`. `start` waits for the result at most `OPEN_BUDGET` (Q1). On timeout it returns `Err(Other(<fixed literal>))`; the opener's late send then fails and drops the stream, so the device closes at once (NFR-02). This bounds `start` although cpal's activation is unbounded (hypothesis 5), and keeps COM setup off the hotkey thread. One opener thread per open or one long-lived opener is the developer's choice.
   - Handle: owns the `cpal::Stream`. `stop` drops it (joins the stream thread) and returns `Ok`; `Drop` does the same. The data callback calls only `sink.frames` (the session's own short lock, `dictation.rs:509-526`), never the session, so a drop under the session lock (`dictation.rs:422`) cannot deadlock. The error callback decides nothing and never calls the session; a device lost mid-recording just ends the frames, and the release processes what arrived (FR-031's outcome; the automatic stop and its notice are T-012's). It records into an atomic, never a mutex the drop path also takes.
   - Errors, one pure mapping (P-009): `DeviceNotAvailable` → `NoDevice`, `PermissionDenied` → `AccessDenied`, `DeviceBusy` → `DeviceBusy`, anything else → `Other(<fixed literal>)`; cpal's message is never copied. Per hypothesis 4, a privacy denial on WASAPI then most likely reads "the device could not be opened" (`mic_reason.other`); see Q2.
3. **`win/clipboard.rs`, `WinClipboard: Clipboard` (R-11).** `OpenClipboard` with up to 10 × 20 ms retries, `EmptyClipboard`, `SetClipboardData(CF_UNICODETEXT)` from a `GMEM_MOVEABLE` block, plus the registered formats `ExcludeClipboardContentFromMonitorProcessing` (present), `CanIncludeInClipboardHistory` (DWORD 0) and `CanUploadToCloudClipboard` (DWORD 0); `CloseClipboard` on every path; any failure → `ClipboardError` (the pipeline makes it `Failed(ClipboardUnavailable)`). It runs on the worker with no session lock. Which window, if any, owns the clipboard (`OpenClipboard(None)` or a window of the calling thread) I could not check against Microsoft's docs here; the clipboard test that reads the formats back pins it.
4. **`win/paste.rs`, `WinPaster: Paster` (R-12).** Stateless apart from our own integrity level, read once at construction (no mutex across methods).
