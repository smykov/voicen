## Context

Narrowed by decision #64 (analysis option A): T-006 keeps the Windows adapters and their wiring to the core session (T-051): the RegisterHotKey thread (with the 0xE8 menu-mask key), cpal on the Windows default input device, the clipboard with history exclusion, the SendInput paster, and one wiring function used by `run()` and the tests — the shortest path to stage 1's "hotkey → API transcript pasted into Notepad". Moved out: the core session → T-051; tray, `prevent_exit`, single instance, serialized `open` → T-052 (Acceptance "second launch" moved there); the overlay → T-053; the microphone list and Recording-tab field → T-012 (changes #38 Q5); Esc (FR-22) stays with T-009; toggle behaves as hold until T-009 (#63). T-056 (windows-gnu type check) lands first if it works. The text below is the original context, for reference. Completes the release-1 flow on Windows: FR-01 (tray, single instance), FR-02 (hold mode, < 0.3 s discarded), FR-04 (indicator; overlay never takes focus), FR-10 (clipboard with history exclusion, wait for modifiers ≤ 1 s, Ctrl+V into the start window, hotkey not passed on), FR-22 (Esc cancels only while recording), NFR-02 (mic opened on press). Shell code in `src-tauri` over the core pipeline from T-001. Also wires the settings subscribers that need the tray: tray menu rebuild and the notifier on `SettingsService::subscribe()` (moved from T-030 by decision #34). Also owns `settings_list_microphones` and the Recording-tab microphone field (decision #38), `prevent_exit` when the last window closes (the tray keeps the app alive), and routing tray / second-instance / engine-none requests to `settings_window::open` (T-037). Note from T-037 review round 1: `open` checks for the window and then builds it, so two concurrent callers on different threads get "already exists" instead of a focus — serialize calls (main thread) or make `open` treat that error as focus. Note from T-037 review round 2: the install smoke's window predicate (`scripts/ci/visible-windows.ps1`) ignores tool windows on purpose — an overlay or skip-taskbar window added here would slip past "a loaded start shows nothing"; revisit the script with the overlay. Note from T-042: `OverlayState::Message` params may carry a nested id (`mic_reason.*` for `failure.microphone_unavailable`) that only Rust `text()` resolves — render the overlay text in the shell, or mirror the nested-id rule in `src/lib/i18n` with conformance cases (docs/decisions/i18n.md). Also (T-042 review round 2 Low #5): add to specs/001 data-model.md:160 the rule from core-traits.md:172 — a message raised during a live recording shows after release only for what is left of its 3 s. Note from T-001 review round 2: run `Pipeline::run_job` on one std worker in FIFO order — `deliver` (clipboard write, modifier wait ≤ 1 s, Ctrl+V) is not serialized across jobs, so two concurrent jobs can paste one transcript into the other's window (research R-10); the pending-slot lock does not make concurrent jobs safe.

## Investigation

### Analysis 2026-10-04

**Frame.** This is a feature. Expected: spec 001 US1 on Windows, plus the items routed here by decisions #34, #38, #45, #48 and the T-001/T-037/T-042 review notes (Context). Observed: core has every stage of a job and none of the wiring. The shell has none of the Windows I/O (see `analysis.evidence`). Where it can be proven:
- the Linux gate, for anything platform-free;
- Windows CI, for the Win32 adapters (decision #5);
- the owner's PC, for a real microphone, Notepad and an elevated target.

**Recurrence.** Class `windows-shell`. `docs/failures.md` has no entry of this class, so `recurrence_of: []` stands. The rules of other classes still bind this shell:
- **F-001/F-002 (`ci-toolchain`).**
  - Shell tests only in `src-tauri/tests/*.rs`.
  - No `#[cfg(test)]` in `src-tauri/src`.
  - Keep arrays and inline tables in `Cargo.toml` on one line. The new `windows` feature list is long, and the guard refuses a split array.
  - After adding the `tray-icon` feature and the single-instance plugin, check `target/*/build/voicen-*/output` for new bins-only link lines on the first Windows run. T-030 named `LoadIconMetric` and tray-icon's common-controls-v6 imports as the next v6-only risk; the test manifest in `build.rs` covers them only if nothing moved to bins-only.
- **F-003 (`guard-model`).** The install-smoke window predicate (`scripts/ci/visible-windows.ps1`) must keep deciding on raw window facts when the overlay arrives. Do not add a model of which tool windows are ours.
- **F-004/F-005.** Any refused or timeout path in a shell test uses `common::refused_addr()` / `REFUSAL_BUDGET`. A timeout test uses a slow server. Windows timing assertions get budgets, not Linux-sized deadlines.

**Hypotheses.**
1. *Parts exist under other names.* True for core: `Pipeline`, `RecordingController`, `dictation_gate`, ports with fakes, events, `AudioBuffer::from_frames`, `HotkeyRegistrar`, and the std `Server` in `test_support/local_models.rs`. False for the shell: grep over `src-tauri` finds no hotkey, capture, clipboard, paste, tray or overlay code.
2. *The same concern on a second path.* Four risks:
   - (a) Orchestration in the shell (gate → press → capture → finish → worker → `job_finished` → render) would be a second owner beside the controller. T-044's lesson (#57) applies: a platform-free coordinator belongs in core.
   - (b) A tray or overlay that reads `Pipeline::pending()` or keeps its own state would drift from the controller, and `pending()` blocks (T-007 note).
   - (c) Three callers of `settings_window::open` on different threads (tray, second instance, engine-none hotkey) race its check-then-build.
   - (d) A hotkey thread that re-reads settings would bypass T-010's two-phase registrar.

   All four are closed by the invariant and the seam.
3. *The class was fixed before.* No.
4. *The scope fits one task.* Refuted. Spec 001 T024–T027, T029–T033 and the routed items cover three seams (core session, Win32 dictation I/O, app lifecycle/tray) plus an overlay with UI and shell halves. That is about 45 tests, more than the T-003/T-001 split line, with a review round multiplied by every Windows CI round.

**Keeping Windows CI rounds few.**
1. All decisions go to T-051 on Linux, so the Windows code only carries out decisions.
2. The first T-006 push carries the red tests plus a runner-capability probe binary. The probe checks:
   - whether `SetForegroundWindow` holds for a test window;

   - `RegisterHotKey` plus a synthetic press;

   It is unknown whether windows-latest has an interactive desktop that accepts foreground changes, and whether it has any audio input. The probe tells which Acceptance lines CI can prove and which fall to the owner (NFR-02 "no stream before press" probably falls to the owner).
