## Investigation

**Frame.** Observed: CI 39296012262 (wip/T-099 @ 3186c2b), windows job, step `cargo test --workspace --exclude voicen --no-fail-fast`: `default_deadline_skips_a_silent_server_at_15_s` got the right outcome (`Skipped(Timeout)`, `at_least(took, 15 s)` passed) but `within_spec` (tests/common/timing.rs:155) found the stage at 16.394 s, 0.894 s past the 15.5 s ceiling. Expected under decision #107 (a): within 15 s ± 0.5 s on the runner's own load. Linux gate of the same run: green.

**Where the 1.39 s goes (proven down to the window, not to the phase).** Timestamps from `gh run view --log`, relative to `Running tests\post_process_timeout.rs`:

| run | unanswered connect | unanswered pp | configured 5 s | default 15 s |
|---|---|---|---|---|
| 39296012262 (red) | +1.05 | +5.05 | +12.185 | **+16.465 FAILED** |
| 39299815752 | +1.06 | +5.05 | +12.182 | +15.046 |
| 39366493906 | +1.04 | +5.05 | +12.128 | +15.035 |
| 39375257460 | +1.06 | +5.06 | +12.170 | +15.063 |

- Whole binary >= baseline runs + the timed call, so in the red run took ≈ 16.39-16.46 s and the three baselines together <= ~71 ms: the overshoot is in the timed silent call, not in the baseline (an inflated baseline would have shrunk the stage).
- The three sibling tests in the same process ended on schedule, so there was no stall in [0, 12.18 s]. The stall overlaps (12.18 s, 16.47 s], i.e. the wake-up at 15 s or the teardown after it.
- The runner was stalled right then: `settings_log.exe` (no network, 6 trivial tests), started 0.2 s after the failure, took 1.42 s from `Running` to `running 6 tests` (17:55:49.643 → 17:55:51.059; 12 ms in green 39299815752). Same magnitude (≈1.4 s) as the overshoot. No other binary in the step was slow by more than 0.5 s.
- Which phase inside the call absorbed it (timer wake-up, the reqwest runtime thread's join in `Client` drop, `classify`) cannot be named from the log: the test records no phase times. That is a gap, not a hypothesis.

**Distribution.** 59 recent `ci.yml` runs (38085575634 .. 39375257460) downloaded and parsed: 56 windows samples green at 15.025-15.067 s for the whole binary (stage <= ~67 ms over 15 s, so >= 430 ms margin), the Linux gate at 15.14-15.41 s; one windows outlier, this one, at 16.465 s. Not a near-miss distribution; a one-off ~1.4 s runner stall (≈1 in 57 windows runs).

**Hypotheses.**
1. Runner-wide stall inside the window. Confirmed by the settings_log start-up stall and the on-time siblings (above).
2. Product deadline late (wrong deadline, reqwest semantics). Refuted: 56 samples at 15.0x s; reqwest 0.13.5 `blocking::wait::timeout` parks to an absolute deadline computed in `execute_request` (a stall mid-sleep cannot extend it), and async `PendingRequest::poll` checks `total_timeout` before the in-flight response; no retry path exceeds the blocking 15 s wait.
3. Windows timer resolution / tokio timer. Refuted: 15.6 ms granularity and tokio's 1 ms wheel cannot give 1.39 s, and the 56 green samples show no drift.
4. Baseline measurement / listener / connect. Refuted for the baseline (see above: a slow baseline shortens the stage). Connect and the listener to 127.0.0.1 lie inside the 15 s total timer (the timer starts at `execute_request`, after `engine::http::client` built the client), so a slow connect cannot extend the stage; only the client build before the timer and the teardown after it can.
5. Second path / fixed before. This is the case class F-013 already logged ("post_process_timeout ±0.5 s stage, 2 of 3 loaded rounds red"); T-080 (rca) kept SC-003 as the single permitted ceiling on the premise that it holds on the reference load, and #107 (a) names the CI runners as part of that load. That premise is now falsified by one sample on the runner's own load.

**Recurrence.** Yes: class `os-answer-deadline-race` (docs/failures.md class row, count 3: F-005, F-013, F-019), the shape "a verdict decided by a clock the test does not control", now in the one ceiling T-080's I2 left (docs/decisions/core-tests.md: "Its only use today is SC-003 in `post_process_timeout`"). Per CLAUDE.md: stop patching, open a `type: rca` task with `recurrence_of: [T-080]` (and F-013 / T-078 as earlier patches of the same test). Earlier patches of this test: T-078 5762a9c (min-of-3 baseline; removed the cold-baseline false red, not a stall in the timed run), T-080 (kept the ceiling through `within_spec` under #107 (a); does not hold when the VM itself stalls). Not a hotspot (`teamwright-metrics`: tests/common, post_process absent from recurring areas and hotspots).

**Root cause.** The SC-003 check is a wall-clock ceiling on one sample of an end-to-end window on a shared VM; a VM stall that overlaps the wake-up or teardown pushes the return past the ceiling while the product deadline is correct. No baseline or tolerance tuning removes this; only an outcome-based verdict does.

**Recommended exit (for the rca task): (a) code, conditional on an owner amendment of the measurement.** Replace the ceiling with an outcome bracket (server answers 200 with a valid body at 15.5 s after accept; correct deadline → `Skipped(Timeout)`, any deadline > 15.5 s → `Applied`), keep `at_least(took, 15 s)`; `within_spec` then has no caller (keep it with its contract tests, or retire it with the docs). This is the shape I2 already prefers for every other deadline. It is robust to stalls because the async side checks its timer before the response: a stall can only turn the bracket answer into the correct Timeout (worst case a rare false green for a wrong deadline within the stall, never a false red). Red first: the case with an injected 1.4 s delay after `process()` inside the measured closure is red on today's `within_spec` and green on the bracket; failure branch: a 16 s deadline is red as `Applied`.

**Owner question (not decided here).** Decision #107 records "SC-003 stays ≤ 0.5 s over the fastest of 3 baseline runs", and SC-003 says "measured tolerance ≤ 0.5 s". Which do you want? (A) SC-003's tolerance is checked by the outcome bracket (the product's deadline is ≤ 15.5 s from send), and a wall-clock overshoot caused by a host stall is not a defect: amends #107's measurement wording, SC-003 itself unchanged; (B) keep the wall-clock ceiling and widen it for CI runners (amends SC-003 / #107); (C) keep both as they are and accept a ≈2 % windows flake (conflicts with P-016: a re-run pass needs the red attempt logged as its own task or F-entry each time).
