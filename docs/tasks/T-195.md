A green re-run under P-016 counts only if each red attempt's failure is logged as its own task or F-entry; this task is that entry. ### 3. connection_test "2 requests"

- **Hypotheses.** (a) A client retry. Refuted: the reqwest 0.13.5 default policy is `ProtocolNacks` (h2 GOAWAY / REFUSED_STREAM only), `http2` is off in `crates/voicen-core/Cargo.toml`, and hyper-util's canceled-request retry re-sends only a request the first connection never delivered. (b) The engine or `connection_test::run` sends twice. Refuted: the module doc says one request, and the file's other request-count checks (`only_request`, `received(&server)`) passed in the same run (35 passed). (c) A late request from a sibling test reaches the pooled server after the next checkout. Consistent with all symptoms; read in code, not reproduced. (d) The same concern on a second path. Confirmed: 15 `MockServer::start()` sites in 8 core test files, 7 of which read request logs (`openai_client`, `post_process_chat`, `api_pipeline`, `diag_pipeline`, `local_server`, `connection_test`, `wer_example`). (e) Fixed before? No. F-004, F-012 and F-020 are the same family (a test shares a resource with siblings; family note in `docs/failures.md`), but none of them is about the mock server pool.
- **Why it is only seen under load.** The sibling's client gives up at 300 ms (`SHORT_LIMIT`). Normally the server thread has recorded the request long before that. When it has not, the late record lands in whichever test holds the server next.
- **Red test design (deterministic, no load needed).** In a binary of its own, so no other test takes the idle server: borrow `MockServer::start()`, open a raw `TcpStream`, write the request head with a `Content-Length` but only part of the body, and drop the server (it goes back to the pool). Borrow `MockServer::start()` again: the pool holds one idle server, so the same one comes back after `reset`. Write the rest of the body, wait for the response, and read the second borrower's `received_requests()`. It has 1 entry today. With `mock_http::start()` (unpooled) the second server is a different one, and its log is empty.
- **Build constraint.** `tests/common/mod.rs` is also compiled by `src-tauri/tests/settings_ipc.rs`, and `src-tauri` has no `wiremock` dev-dependency. So `mock_http.rs` is not a `pub mod` of `common/mod.rs`. Each user includes it by `#[path]`, as `refused_addr_tests.rs` is included.
- **Family.** Recommended F-entry: a new class `test-shares-mock-server-pool` with a family count of 4. The family note says the owner sets tiers in a process review.

### 4b. Selector router (#246)

Added on 2026-11-06 at a4e75c2d after decision #246; (1)–(3) not re-investigated. Read with grep and file reads (not code Serena indexes): `scripts/tw-test` header and `_cmd_py`, `scripts/tw-run` header, `scripts/e2e.sh`, `package.json`, the ui area in `.teamwright/config.yml`, `Makefile` `check-ui`, `docs/decisions/ui-e2e.md` E3, `docs/process/gates.md` (guard trigger). Context7: `/vitest-dev/vitest/v5.0.3` (`vitest list --json`, location filter: a line with no test fails the suite) and `/microsoft/playwright` (`file:line`; 'No tests found' fails unless `--pass-with-no-tests`; main docs, not pinned to 1.63.0). Nothing run.

- **How tw-test calls it.** With selectors and a `test_select_command`, `{tests}` becomes the selectors, each `shlex.quote`d and space-joined. Without selectors tw-test runs `test_command` (`pnpm test`), so the router never gets an empty list from tw-test. The command runs through `scripts/tw-run ui --` (docker, `voicen-ui:1.63.0`, default network; tw-run's `TW_DOCKER_ARGS` comes only from the environment, not from the config). tw-test's verdict is the command's exit code (0 = PASS); 75 means still running, 2 is tw-test's own usage error (a router exit 2 just shows as FAIL). The cache key includes files the command names, so the config should name `node scripts/ui-test-select.mjs {tests}` and not a package.json alias. `--fresh` only skips the cache; the router does not see it.
- **How `pnpm e2e` takes selectors.** `scripts/e2e.sh` passes `"$@"` to `playwright test`. Inside the image (`/ms-playwright/.docker-info` exists, which is the case under tw-run) it checks the Playwright version and `exec`s Playwright directly. `file:line` is Playwright's own location filter (`testDir: "e2e"`).
- **Why two scripts.** `pnpm test` stays unit-only: `make check-ui` runs `pnpm test` and then `scripts/e2e.sh` from the host with `--network none`. If `pnpm test` could start Playwright, a `pnpm test e2e/...` inside the lint/test container would skip that host re-entry. The router reuses `ui-unit-test.mjs` for its unit group, so the vitest-side check lives in one place.
- **Why count per selector.** Both runners take the union of their selectors, so one unmatched selector next to a matched one still exits 0. vitest's 'Couldn't find file' exits 0 (reproduced). So exit codes cannot show 'matches no test'. The router checks file existence and then lists each selector with the runner's own list (`vitest list --json <sel>`, `playwright test --list <sel>`). A count of 0 exits 1 and names the selector and its runner, before anything runs. Then the unit group runs, then the e2e group. The exit code is 0 only if both are 0, else the first non-zero. Not verified: whether `playwright test --list` starts the config's `webServer` (a build). The developer checks this; if it does, the e2e count comes from one `--list --reporter=json` run over the whole e2e group, with tests mapped back to selectors by file and line.
- **Network.** Under tw-test the routed e2e run uses tw-run's default bridge network, not `--network none`. E3 already records this form (`scripts/tw-run ui -- pnpm e2e`: a private netns, not measured by the churn script). The E3 entry in `docs/decisions/ui-e2e.md` should name the router as one more way into that form.
- **Guard paths.** `scripts/ui-test-select.mjs`, `scripts/ui-test-select.test.ts`, `scripts/ui-unit-test.mjs`, `vitest.config.ts` and `package.json` are not under `scripts/ci/` or `scripts/licenses/`, and none is `Makefile` or `*.mk`, so `checker` stays false. The router's test runs in the gate through vitest's include, not through a new Makefile target, which would be a guard change.

**Owner question (not blocking):** should `e2e/` selectors routed through tw-test run with `--network none`, as `make check` does? tw-test cannot pass docker arguments from the config, so this would need teamwright feedback (an area-level `docker_args`) or a router that re-enters docker from the host. The task goes ahead on the documented bridge form.
