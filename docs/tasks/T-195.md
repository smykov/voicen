## Context

Three tests fail under host load and are so far only noted in T-060: the e2e boot 5 s limit, the `local_download` trickle test, the `connection_test` 2 requests test. A green re-run under P-016 counts only if each red attempt's failure is logged as its own task or F-entry; this task is that entry. Owner decision #246 (2026-11-06), on the investigation's non-blocking question 1: the ui area gets a `test_select_command`, so `scripts/tw-test ui <selectors>` runs `e2e/` selectors through `pnpm e2e` and `src/` selectors through vitest. ### 1. e2e boot 5 s

- **Hypotheses.** (a) The 5 s expect default on the first render. Confirmed: 14 specs call `page.goto` in their own `open*()` and then wait with no `timeout`, and the config has no `expect` key. (b) F-010's netns churn. Refuted for these sightings: T-111 r4#1 found no `ERR_NETWORK_CHANGED`, and since T-064 e2e runs in a private netns. (c) A UI regression. Refuted: the tests are green alone and on CI, and T-111 touched no `src/` or `e2e/`. (d) The same concern on a second path. Confirmed: the boot-failure inner run's healthy scenario has its own 5 s wait (`boot-failure.inner.ts` "healthy boot passes").
- **What made the host slow.** It is not only "load". `scripts/tw-gate` waits only for a run of the *same area*. The `core` area and `--top` both run `make check`, so twice in the main tree they ran at the same time: `core-20261030T231453Z` / `_top-20261030T231454Z` and `core-20261030T233832Z` / `_top-20261030T233834Z`, all at head 72786c6. That doubles the load. Both runs also wrote one `/work/test-results/`, and every failure in those four logs is `ENOENT` on a trace file. That is the T-021 v1 flake, which T-177 owns: this is the first evidence of its cause, so pass it to T-177. tw-gate is a kit file, so serializing the two is teamwright feedback, not this task's.
- **The 30 s test timeout under load** (T-186 r2#2, `settings-focus-close` 7–13 s alone, red at about 5× load) is not this task's 5 s limit. I1 does not make a test faster than its own budget. The load cap does that.
- **Class.** The symptom matches `e2e-boot-flake` (F-010, count 1), but the mechanism is different (a deadline that is not the subject, not the netns). I recommend a new F-entry under a new class, `e2e-boot-deadline`, rather than F-010's count 2, which would reopen its tier. The orchestrator or owner decides.
- **The broken-boot scenarios** of the inner run (`aborted page chunk ...`, `... answers 500 ...`) keep their 5 s waits. Their verdict is that they fail, so a longer wait would only slow them. The structural test exempts `e2e/fixtures/**` scenarios that expect a failure, or lists them by title.

### 3. connection_test "2 requests"

- **Hypotheses.** (a) A client retry. Refuted: the reqwest 0.13.5 default policy is `ProtocolNacks` (h2 GOAWAY / REFUSED_STREAM only), `http2` is off in `crates/voicen-core/Cargo.toml`, and hyper-util's canceled-request retry re-sends only a request the first connection never delivered. (b) The engine or `connection_test::run` sends twice. Refuted: the module doc says one request, and the file's other request-count checks (`only_request`, `received(&server)`) passed in the same run (35 passed). (c) A late request from a sibling test reaches the pooled server after the next checkout. Consistent with all symptoms; read in code, not reproduced. (d) The same concern on a second path. Confirmed: 15 `MockServer::start()` sites in 8 core test files, 7 of which read request logs (`openai_client`, `post_process_chat`, `api_pipeline`, `diag_pipeline`, `local_server`, `connection_test`, `wer_example`). (e) Fixed before? No. F-004, F-012 and F-020 are the same family (a test shares a resource with siblings; family note in `docs/failures.md`), but none of them is about the mock server pool.
- **Why it is only seen under load.** The sibling's client gives up at 300 ms (`SHORT_LIMIT`). Normally the server thread has recorded the request long before that. When it has not, the late record lands in whichever test holds the server next.
- **Red test design (deterministic, no load needed).** In a binary of its own, so no other test takes the idle server: borrow `MockServer::start()`, open a raw `TcpStream`, write the request head with a `Content-Length` but only part of the body, and drop the server (it goes back to the pool). Borrow `MockServer::start()` again: the pool holds one idle server, so the same one comes back after `reset`. Write the rest of the body, wait for the response, and read the second borrower's `received_requests()`. It has 1 entry today. With `mock_http::start()` (unpooled) the second server is a different one, and its log is empty.
- **Build constraint.** `tests/common/mod.rs` is also compiled by `src-tauri/tests/settings_ipc.rs`, and `src-tauri` has no `wiremock` dev-dependency. So `mock_http.rs` is not a `pub mod` of `common/mod.rs`. Each user includes it by `#[path]`, as `refused_addr_tests.rs` is included.
- **Family.** Recommended F-entry: a new class `test-shares-mock-server-pool` with a family count of 4. The family note says the owner sets tiers in a process review.
