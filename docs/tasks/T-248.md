## Context

From T-222's analysis (Investigation, hypothesis 3, sibling of the same invariant: a call attached to running captures starts from their current device state); the owner split it into its own task (decisions #344, Q2 (a)). `Captures.mic_id` / `system_id` / `warnings` are set once in `CallSession::spawn` and never updated by a device-thread reopen (only `DeviceLane.endpoint` is), and `open_call` reads them for `create_files` (`meta.json`) and `begin_call` (`call_started mic= system=`). So a record start on running subtitles names the captures' original endpoints even after the device thread reopened a track elsewhere, and a mic reopened on the default under subtitles gives no `MicChanged` (`Writer::outcome` returns before it when no call records). Reachable only from 1b (`crates/voicen-core/src/call/session.rs`).

## Acceptance

- [ ] A record start on running subtitles: `call_started mic=` / `system=` and `meta.json` name the devices currently open at record start, not the captures' original ones.
- [ ] A mic reopened on the default under subtitles gives the `MicChanged` warning once at record start (or as decided by its analysis).
- [ ] Failure branch: subtitles on, the mic is lost and reopened on another device, record on → `call_started` and `meta.json` name the reopened device, verified by a core session test.
- [ ] Test that fails without the change: `<test name>`
