## Context

Re-adoption to teamwright 0.8.2 (2026-10-10), inventory step: `.github/workflows/ci.yml` runs the whole workflow (Linux gate, Windows build, silent install, smoke) on every push to `main` and `wip/**`, including pushes that carry only `chore(task)` status commits and records. The kit proposes `paths-ignore: ["docs/tasks/**"]` on the `push` trigger and, for `pull_request` (where a path filter sees the whole PR diff), a `changes` job running `scripts/tw-ci-changes` in front of the gate jobs. The owner chose to create this task.

Owner decision #144 (2026-10-19): option A — push `paths-ignore: ["docs/tasks/**"]` only; the pull_request `changes` job is dropped from scope (no PRs are used; the kit's fail-open design goes to the kit as feedback); the tag bullet is met by the docs citation plus the next real release run.

Constraints to keep:

- Never `[skip ci]` on status commits: the tip of every delivery is a status commit (DRAIN).
- P-016: a `CI: <run> @ <sha>` line stays valid when only `docs/**` changed after `<sha>`, so a record-only push to `wip/<ID>` needs no run.
- Tags (`v*`): the `release` job must still run on a tag push (path filters do not apply to tag pushes; check this, do not assume).
- The `make check` tripwires on `ci.yml` (`check-ci-wip`, `check-telegram-guard`, `check-release-guard`, ...) stay green, or are updated in the same change.

## Acceptance

- [ ] A push to `main` or `wip/**` whose diff is only under `docs/tasks/**` starts no `ci.yml` run (shown by one such push)
- [ ] A `v*` tag push still runs the `release` job: the `tags:` line is unchanged and the GitHub docs citation ("Path filters are not evaluated for pushes of tags") is recorded; the next real release run is the run proof (#144)
- [ ] Failure branch: a push that changes code together with task records still runs the full CI (shown by a run on `wip/T-083` with such a commit)
- [ ] `make check` is green and its `ci.yml` tripwires cover the new trigger shape (a fixture that drops `paths-ignore` is refused)
- [ ] `docs/decisions/ci-toolchain.md` no longer forbids the `docs/tasks/**` filter (#144 supersedes that Don't); a wider filter is still refused

## Investigation

Tools: Serena and Context7 MCP tools were not available in this session; context came from file reads, grep, `gh` and the GitHub docs source fetched with curl (github/docs, `main`, 2026-10-18).

### 1. Frame

Observed: every push to `main` or `wip/**` starts the full `ci.yml` (Gate ~ make check in two images, then the Windows build, silent install and smoke, and on `main` an installer build sent to Telegram with a new run-number version), also when the push carries only `chore(task)` records. Expected: a push whose whole diff is under `docs/tasks/**` starts no run; code pushes and `v*` tags behave as today. Not a defect class, a cost: no failure entry.

### 2. Hypotheses

1. No path filter on the `push` trigger. Confirmed: `ci.yml:8-11` = `release-header.yml:8-11`, no `paths`/`paths-ignore`.
2. Something else re-triggers (a second workflow, `workflow_run`, the `pull_request` trigger). Refuted: `.github/workflows` holds only `ci.yml`; all record-only runs listed by `gh run list` are `event: push`; `gh pr list --state all` is empty.
3. A filter is absent by deliberate rule (the "second path" that keeps it absent). Confirmed: `docs/decisions/ci-toolchain.md` Don't line ("add a `paths-ignore` to it") and `release-guard.test.sh:758-759` (`trigger-paths`, refused as R7). The reason recorded there is P-016's wip run, which a `docs/tasks/**`-only filter does not weaken (P-016 already accepts a cited sha after which only `docs/**` changed).
4. Fixed before. Refuted: no F-entry, task or decision row about CI cost or path filters (grep `paths-ignore`, `skip ci`, `path filter` in `docs/failures.md`, `docs/decisions.md`, `PRINCIPLES.md`); T-066/T-088 only made sure a filter is refused.

### 3. GitHub semantics (cited, not assumed)

From `data/reusables/actions/workflows/triggering-a-workflow-paths1.md`, `-paths3.md`, `-paths5.md` and `run-on-specific-branches-or-tags1.md` (the sources of the workflow-syntax page, section `on.<push|pull_request|pull_request_target>.<paths|paths-ignore>`):

- "Path filters are not evaluated for pushes of tags." With `branches`, `tags` and `paths-ignore` in one `push` trigger, a `v*` tag push is decided by `tags` alone; a branch push needs both the branch filter and the path filter satisfied.
- `paths-ignore`: the workflow is skipped only when all changed paths match; any other path runs it. A commit with code and records together runs.
- Diff base: existing branch, two-dot `before..after` of the push; new branch, two-dot against the parent of the deepest commit pushed; pull request, three-dot over the whole PR (so a PR with code never skips on later record-only pushes: the reason the kit adds a `changes` job). More than 1,000 commits or a diff timeout: always runs. No changed files (an empty commit): no run.
- Not verified on a real tag push. The release job publishes a public GitHub Release (`release.sh`, `gh release create`), and `release-check.sh` needs `X.Y` = committed MAJOR.MINOR and `Z` >= run number, so a "test tag" is a real release. The docs sentence plus an unchanged `tags:` line and R2/R7 literals are the available evidence; the run proof is the next real release (owner decides, item 6).

### 4. Effects checked

- **wip/<ID> (P-016):** the flow pushes `wip/<ID>` right after committing tests or code, so that push always carries code and runs. A later record-only push to the same branch creates no run and therefore cancels nothing (concurrency is per run; there is none). P-016 already accepts the code sha's run when only `docs/**` changed after it. Residual: a new `wip/<ID>` whose code commits are already on the remote under another ref (a parallel branch) pushes only records, so GitHub diffs only those and skips; then the run of that code lives on the other ref. Rare; the orchestrator re-runs or cites with a note. An empty commit does not force a run (no changed files).
- **main / DRAIN / DEPLOYED:** a DRAIN push carries the code with its status commits on top; the push diff includes code, so it runs, the installer goes to Telegram and verifiers cite that run (T-006 verify records cite main runs at the deployed code and treat later `docs/tasks` commits as no code change). `DEPLOYED` is set by pre-push, not by the pipeline (`docs/process/lifecycle.md`: "no hook reads the pipeline"). A later record-only push to `main` (`VERIFIED→DONE`) loses only a rebuild of identical code with a new run-number version, a second Telegram installer, and a cache refresh; nothing cites those. One behaviour change: a red flaky main run is no longer "re-tried" by the next record-only push; a re-run is `gh run rerun` (already P-016's rule for wip).
- **Tags:** `tags: ["v*"]` unchanged; the release job's `needs: [gate, windows]` and its `if:` are R2's owned literal, untouched; gate and windows get no `if:` in Option A.
- **Run number:** fewer runs only lower future run numbers; `release-check.sh` requires `Z >= run number`, which gets easier, not harder.
- **make check tripwires:** R7 refuses any header edit unless `release-header.yml` and every fixture carrying the header change in the same commit (`release-guard.test.sh` header comment at line 129-133: "an edit of the ci.yml header edits the owned copy and every such fixture together"; 175 fixture files hold the branches line). The header is plain text for R1, R4-R6, R8, R11 (no `uses` / action token in the new line), R12 (before `jobs:`) and R13. `check-ci-wip` is an alias of `check-release-guard`. No other guard reads `on:` (Telegram, release, upload, cache fragments are below `jobs:`).
- **The kit's `changes` job (`scripts/tw-ci-changes`, installed, identical to the 0.8.2 template):** it answers `code=false` when `before..after` holds only records, but never checks that a run at `before` passed. A record-only push after a red or cancelled code run therefore yields a run whose Gate and Windows jobs are skipped and whose conclusion is `success` (the kit's own usage note: "A skipped job counts as passed for required checks"). On a PR that is a green check on red code; on `wip/` (if it ran on pushes) a run citable as "green" under P-016. Checking the previous run's result would need an `actions: read` token, which R3 and decision #120 allow only in the release job. Its record set (`docs/tasks/`, `docs/sprints/`, `docs/process-reviews/`, `docs/decisions.md`, `docs/open-questions.md`) is also wider than the kit's push filter (`docs/tasks/**`). The kit snippet also names `actions/checkout@v4` and `ubuntu-latest`. The owned line is `@v5` (R11), and this repo uses `ubuntu-24.04`. This repo has no pull requests (none ever), so that job would guard nothing used and add a fail-open path. Worth kit feedback.

### 5. Root cause, invariant, seam

See `analysis`. Size: small, one seam (the owned header literal). The diff is wide but mechanical: about 175 fixtures get one inserted line, and the docs change with it.

### 6. Owner decisions needed before IN_PROGRESS

1. Supersede the `docs/decisions/ci-toolchain.md` Don't ("add a `paths-ignore` to it") with a row in `docs/decisions.md`: `paths-ignore: ["docs/tasks/**"]` exactly, nothing wider. Wider options are a choice to make here: the kit's record set or `docs/**`, which matches P-016. Both widen what a docs-only `main` push skips. The gate reads no file under `docs/` (grep of Makefile, `scripts/ci/*.sh`, ci.yml), so skipping such pushes skips no check.
2. Acceptance bullet 2, bullet 4 part 2 and bullet 5 part 2 (the `changes` job, `tw-ci-changes` answering `code=true`, the job dependency fixture) → drop them (recommended: no PRs, fail-open design), or keep them as Option B with an `if: github.event_name == 'pull_request'` guard and the false-green residual recorded.
3. Acceptance bullet 3 (tag push runs release): accept the docs citation plus the unchanged `tags:` line and R2/R7 literals now, with the next real `vX.Y.Z` release as the run proof, or plan a real release for it. Nothing should push a throwaway `v*` tag, because that publishes a public release.

**Recurrence:** none. No F-entry or earlier task of this class (`ci-hygiene` is new). Related only as the rule being relaxed: T-066 (decisions #90) and T-088 (R7 on ci.yml) made a trigger filter refusable. Their reason, the P-016 wip run, still holds under a `docs/tasks/**`-only filter.
