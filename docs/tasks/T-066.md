## Context

Opened by the T-061 review, round 5 (`docs/tasks/T-061.reviews/5.md`, verdict `REJECT_RECURRENCE`).

Class `windows-premise-unchecked-on-host` (`docs/failures.md`): a Windows-only premise is written on the Linux dev host, where it cannot be run (no Windows, and for pwsh/C# not even parsed). It is first checked by a push to `main` that triggers the Windows CI job. Logged entries:

- F-007: T-061 `purge_credentials.rs` DOMAIN_PASSWORD plant refused by `CredWriteW` (verify 1 and verify 2, two CI rounds).

Related, with the same outer mechanism and listed in the class row: F-002 (shell test exes without the manifest, first run on CI), F-005 (Windows refused-connect timing), F-008 (helper-window predicate, the install smoke only).

Each entry was fixed locally, and every local fix is again Windows code first run by a CI push. The T-061 verify-3 fix (ac7a558) is new P/Invoke C# plus pwsh that was not parsed on the host. Its `make check` tripwire refuses one tool name (`cmdkey`). The class row's proposal ("a Windows-premise probe on a throwaway CI branch before a Windows fixture is committed") has been waiting for the owner since F-007 and was not applied.

T-061 is absorbed here (`absorbed_by: T-066` once the orchestrator defers it). Its ac7a558 patch stays in the tree as a **temporary workaround** that points to this task (see the review record).

## Investigation

Investigator, 2026-10-06. Tools: Serena and context7 were not connected in this session (no `mcp__serena__*` / `mcp__context7__*` tools). I used grep, file reads, `git log` and `gh run list` / `gh run view`, read-only. Most of the material (YAML, pwsh, process docs, the kit's docs under the plugin directory) is not indexed by a language server anyway. No code was changed.

### Frame

- **Observed:** a change whose correctness depends on something only CI can run passes the Linux gate and review. It is delivered to `main`, and its first execution is the delivery run, which goes red. That something can be a Win32 input contract, a runner tool, pwsh/C# the host does not parse, link args, Windows network timing, the install window census, or an action default. Then follows a local fix that is again first run on `main`.
- **Expected:** such a premise runs on the CI runner before review, and a wrong premise is red there, never on `main`.
- **Where it shows:** the GitHub Actions history of `smykov/voicen` (workflow `CI`, `.github/workflows/ci.yml`, the only workflow).

### Root cause

A premise that only CI can run is executed for the first time by the delivery push to `main`. The workflow runs only on `main` (Evidence 1), the kit's pre-review CI path is unwired and contradicted by the project canon (Evidence 3), and the lifecycle counts a change as ready on Linux-gate evidence alone (Evidence 4). This explains all symptoms:
- every red is on `main`;
- the reds span unrelated code seams (H2);
- each local fix recurs as another unprobed premise (T-061 twice);
- the owner is repeatedly asked to ratify pushes of unapproved code just to get a Windows run (H5);
- the same mechanism hit the Linux Gate job (F-011). Hence the T-068 note is right: the invariant is about **CI-only** premises, not Windows-only.

### Invariant

No task whose diff touches anything outside `docs/**` reaches `CODE_COMPLETE` unless a green run of the full CI workflow (Gate and Windows jobs) on `wip/<ID>`, at the reviewed head commit, is cited in the task. A red `wip` run returns the task before review. "Proven by the next push to `main`" is never evidence.

The scope is deliberately "anything outside `docs/**`", not a list of Windows paths. F-005 was a `crates/voicen-core` test and F-011 a workflow default. A path list would be the allowlist P-002 warns about, and deciding "is this premise Windows-only?" is the judgement that failed each time.

### Seam

**One CI entry before review.**
- `.github/workflows/ci.yml` runs on `push` to `main` and `wip/**`.
- The orchestrator reaches it through `git push origin HEAD:wip/<ID>`, which pre-push already treats as not a delivery.
- The lifecycle DoD for `NEEDS_REVIEW → CODE_COMPLETE` and the code-reviewer checklist require the cited green run at the reviewed head.

**Paths that must go through it:**
- shell tests (`src-tauri/tests`);
- install-smoke steps and `scripts/ci/*` helpers;
- action and runner changes;
- core tests with Windows behaviour;
- runner-fact probes.

The "ratify a push to `main` to get a Windows run" route (decisions #68, #74, #79, #80) is retired by it.

### Options

- **A. (recommended) Process amendment plus wiring: every non-docs task gets a pre-review `wip/<ID>` run.**
  - New `P-016`, "A premise only CI can run is run on CI before review", T1 + T2:
    - DoD line in `lifecycle.md` §3;
    - code-reviewer refuses `APPROVE` without a green run id at the reviewed head;
    - a `## Tests` line (or template field) `CI: <run id> @ <sha>`.
  - Wiring task, small (a), `deploys: false`, self-proving because a push uses the workflow file of the pushed commit:
    - `ci.yml` `push.branches: [main, "wip/**"]`;
    - a `concurrency` group per ref with cancel-in-progress for `wip/**`;
    - cache saves limited to `main`. The repo cache is at 10.51 GB of 10 GB (`docs/decisions/ci-toolchain.md`, T-058), so `wip` runs would evict `main`'s rust-cache entries. Check the `save-if`-style inputs of the pinned `Swatinem/rust-cache@v2` and `actions/cache@v6` in their docs; I did not verify them here, because context7 was not connected;
    - `ci_workflow: ci.yml` on areas `core` and `ui`;
    - `CLAUDE.md` / `AGENTS.md` rule 8 reworded: "never push from a DEV session, except the orchestrator's `wip/<ID>` CI-only push".
  - **Why it removes the cause:** the first execution of every CI-only premise moves from `main` to a branch that delivers nothing, before review. It covers all 10 reds, including F-011 (Gate job).
  - **Red before / green after (Acceptance failure branch):**
    - push a branch at current HEAD with step 18 reverted to the pre-ac7a558 `cmdkey` form (as at 7721946) to `wip/T-066-neg`: red at `premise: could not plant`, as in 37444780779, with `main` untouched;
    - push current HEAD to `wip/T-066`: green.
    - Optional second negative: `package-manager-cache` removed, red at the Gate setup-node step (F-011).
  - **Cost:** one full CI round per review round, about 7.5-10 min gate plus about 25 min windows (`ci-toolchain.md`). Free minutes on a public repo. Unreviewed code becomes visible on a public branch; the pre-commit secret scan still applies.
  - **Risk:** latency; `wip` branches pile up (delete after `DONE`).
  - **Rollback:** remove the trigger and supersede P-016.
  - **Enforcement limit:** the kit's review gate does not check CI evidence. A T3 needs kit feedback (`/teamwright:feedback`: "review gate requires a CI run id when the area has `ci_workflow`"). Until then this is T1 + T2 via the flow step.
- **B. As A, but scoped to Windows/CI paths** (`src-tauri/**`, `scripts/ci/**`, `.github/**`, lock files).
  - Cheaper in CI time.
  - It is a path allowlist (P-002): F-005 (`crates/voicen-core/tests`) would have been outside a natural first list. It also needs someone to decide "Windows-only?", which is the judgement that failed.
- **C. A `workflow_dispatch` premise-only job** (a separate workflow that runs a given script or test file on `windows-latest`), used before a fixture is committed, plus a T1 rule.
  - Cheap per run (a few minutes).
  - It does not run the real change: no install, no full build, no Gate job. So F-001, F-002, F-008 and F-011 would not have been caught.
  - It is opt-in per author judgement, the same weakness as today.
  - Useful as a complement to A for fast iteration, not as the exit.
- **D. Status quo plus per-instance host tripwires** (what was done). Rejected: 10 of 10 reds, and each tripwire models one instance (F-003).

**Recommended exit**: (c) process, combined with a small (a) wiring task (Option A). The class is a process defect: each change did what the process allowed (Linux gate plus review, then deliver). The working path for the canon's own CI-only rule is unwired, which is §3 canon/path drift. No single code seam exists (H2), and an architecture review would not change that Windows premises must run on Windows (H3). (b) is not recommended; the hotspot is a consequence.
