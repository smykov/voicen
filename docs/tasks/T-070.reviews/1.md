- **The token never reaches argv or a file.**
  - `printf` is a bash builtin, including in the forked pipeline subshell, so the token goes only to curl's stdin through `-K -`.
  - There is no `set -x`, `-v` or `--trace`.
  - curl's stderr is discarded, so a config-parse warning cannot echo the line.
  - The response body is kept in a variable. Only the extracted `description` is printed, with CR/LF stripped, so it cannot inject a workflow command.
  - Step outputs reach the send step through `env:`, not through `${{ }}` inside `run:`, so a ref name cannot inject script.
- **The `if:` is correct.** `github.event_name == 'push' && (refs/heads/main || startsWith refs/tags/v) && send == 'true'`.
  - With no status function, the implicit `success()` applies, and no earlier step in the windows job has `continue-on-error`.
  - The send step therefore cannot run after a red build or smoke.
  - Its `exit 0` affects only its own outcome, so a red smoke still makes the job red. The failure branch cannot hide a red smoke.
- **Forks and pull requests are safe.**
  - `pull_request` never matches the `if:`, and fork PRs get no secrets anyway.
  - `pull_request_target` is not used.
  - `main` and `v*` tags need write access.
  - The premise step reads no secret.
- **The send step cannot turn `main` red.**
  - The `set -e` paths are guarded: `|| rc=$?`, and the description pipeline is printf/tr/sed.
  - `--max-time 300` is less than `timeout-minutes: 10`.
- **The caption** holds the version, ref name, short commit and public run URL. It contains no user data.

## Verdict rationale

The design is sound: the token reaches curl on stdin, the `if:` cannot run after a red smoke or for PRs or forks, and the warning-only failure branch cannot hide a red build. The `make check` gate and the P-016 wip run are green. The blocker is #1. The Acceptance failure branch and the "token not printed" guarantee have never been executed. The only run planned to execute them is `main`, where masking would hide a leak. A fake-token run of the same code on wip would test both without sending anything. #2 is a one-row docs fix. #3 is the owner's wording decision and does not block. #4 and #5 are optional hardening.
