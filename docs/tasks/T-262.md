## Context

Option 4 of #360. `ci.yml` `windows: needs: gate` serialises the two jobs on every ref. On `wip/**` (and the contour's `workflow_dispatch`) the Windows job should start at once; `main`, `v*` tags and the release job keep `needs` (release: `needs: [gate, windows]`). The windows job head is byte-pinned (`scripts/ci/windows-head.yml`, R15): change both together.

Measured 2026-11-24 (decisions #360): a `wip/<ID>` `ci.yml` run takes 52 min serial (gate 21 + windows 24-31; runs 45344541978, 45346473438, 45332192687); T-247 needed 4 wip rounds, T-151 3. Cost of the change: Windows minutes are spent also when the gate turns out red.

Guard paths (workflows, `scripts/ci/`, byte-pinned heads and fragments) change in pairs; `checker: true`, `analysis.decides_on` (P-020).

## Investigation

Tools: Serena was not used (the code is YAML and shell, which Serena does not index); grep and file reads over `.github/workflows/`, `scripts/ci/`, `scripts/tw-wip-run` and `docs/`. Docs: context7 `/websites/github_en_actions` (workflow syntax `jobs.<job_id>.needs`, control jobs with conditions, YAML anchors and aliases).

**Frame.** Today: on `wip/<ID>` the windows job starts only after gate ends (52 min, decisions #360). Wanted: on `wip/**` both start together, and `main`, `v*` and pull requests keep the serial order.

**Hypotheses.**
1. The static `needs: gate` is the only thing that orders the jobs. Confirmed: it is the only `needs` besides release's, and no windows step reads a gate output or artifact.
2. A second path relies on the order (Telegram, cache saves, release). Refuted for wip: the Telegram send step, the `main`-only saves and the `v*`-only upload/release are each gated by their own `if:`, and release keeps `needs: [gate, windows]`. On `main` the order still matters (F-011: a red gate skipped windows, so no installer went to Telegram). That is why option C is rejected.
3. GitHub could make `needs` conditional through `if:`. Refuted: a job's `if:` is evaluated only after its needs complete, so a skip barrier job behind gate would still wait. Only a dependency that is skipped at run start, a job with no needs and a false `if:`, removes the wait. Per the docs, the dependent then needs a status function (`!cancelled()`) to run after a skipped need.
4. This class was fixed before. Refuted: no F-entry or task of a job-ordering class. T-230 made R15 and the windows head pin, which is the pin this task changes.

**Size.** One seam: ci.yml's job heads and their R15 pin. The diff is wide but mechanical: 201 of the 205 fixture `ci.yml` under `scripts/ci/fixtures/release-guard/` carry today's windows head. If R15 also pins the gate head and the gate-wip job, the ok fixtures (`ok-release`, `ok-contour`, the lookalike ones) need the new gate head and gate-wip job too. The v-fixtures need them only where an extra R15 line would change the expected rule. Regenerating them by one script is part of the task.

**Open for the owner (not blocking):** whether the contour's `task/<ID>` dispatch (`teamwright-next.yml`, CODE_COMPLETE pull request run) should also start windows at once. As written it stays serial, because only `refs/heads/wip/` is tested.
