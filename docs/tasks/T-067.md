## Context

OQ-10 answered (decisions #86): the overlay look and position stay as built in T-057, and the owner wants it click-through and out of Alt+Tab. T-057 left both out (`docs/decisions/overlay.md` §2): each needs a setter or a raw style change after creation, which tao turns into `SW_SHOW` and may activate the window, stealing focus from the target of the paste. Proposed approach (OQ-10): build the overlay hidden, set `WS_EX_TRANSPARENT | WS_EX_LAYERED` (click-through) and `WS_EX_TOOLWINDOW`, then show it with `SW_SHOWNOACTIVATE`. The install-smoke predicate counts a click-through overlay and a tool window shown at start (F-003, T-065): the overlay must still be counted as a product window where the smoke expects it.

- [x] A mouse click on the overlay's area reaches the window under it (Windows CI shell test: hit-test / click lands on the window behind)
- [x] The overlay does not appear in the Alt+Tab list (tool-window style, unowned top-level check in the shell test)

## Investigation

Analysis 2026-10-07 (investigator). Serena and context7 were not used in this session; facts come from grep and reads of the pinned sources in `.teamwright/cache/core/_usr_local_cargo_registry/src/index.crates.io-1949cf8c6b5b557f/` (Cargo.lock: tauri 2.12.1, tauri-runtime(-wry) 2.12.1, tao 0.37.1, wry 0.57.0, windows 0.62.2). The Win32 behaviour facts marked **(premise)** below come from the Win32 docs as I know them. I did not fetch them, so they are proven only by the red test on `wip/T-067` (P-016, decisions #90).

**Frame.** Observed: the overlay (T-057) takes clicks and is listed in Alt+Tab (`docs/decisions/overlay.md` "differs" #2). Expected (decisions #86): it lets clicks through, is not in Alt+Tab, and still never takes focus from the paste target. It reproduces only on Windows (shell, decisions #5).

**How the overlay is built and shown today** (`src-tauri/src/overlay.rs` `OverlayThread::build`). `WebviewWindowBuilder` with `decorations(false)`, `transparent(true)`, `shadow(false)`, `resizable(false)`, `always_on_top(true)`, `skip_taskbar(true)`, `focused(false)`, `focusable(false)`, `visible(true)`, a raw-Win32 position. tao creates it with `MARKER_DONT_FOCUS`, so its creation `set_visible(true)` diff ends in `SW_SHOWNOACTIVATE` (`window_state.rs:455-467`). No setter follows. Resulting ex-style from tao's flags (`window_state.rs:239-298`): `WS_EX_WINDOWEDGE|WS_EX_ACCEPTFILES|WS_EX_APPWINDOW|WS_EX_TOPMOST|WS_EX_NOACTIVATE`.
- `WS_EX_APPWINDOW` is set because the window is unowned: `Parent::None` → `ON_TASKBAR` (`window.rs:1280-1283`) → `WS_EX_APPWINDOW` (`window_state.rs:255-256`). `skip_taskbar(true)` does not clear it: it only calls `ITaskbarList::DeleteTab` (`window.rs:1219-1220`, `:1543-1549`).
- `WS_EX_TOOLWINDOW`: tao has no flag for it. `to_window_styles` never emits it. Only tao's own event-target window gets it, through a raw `CreateWindowExW` (`event_loop.rs:651-660`).
- Click-through: only `set_ignore_cursor_events` (`window.rs:530-540` → flag `IGNORE_CURSOR_EVENT` → `WS_EX_TRANSPARENT|WS_EX_LAYERED`, `window_state.rs:282-283`). In tauri it is posted, not run in place (runtime-wry `lib.rs:2292-2297`; handler `:3490-3492` drops the result).

**Why T-057 left both out, confirmed.** `MARKER_DONT_FOCUS` is removed when creation returns (`window.rs:1415-1420`). Any later flag diff on the visible window rewrites the whole `GWL_EXSTYLE` from tao's flags (`window_state.rs:412-431`, so a raw `WS_EX_TOOLWINDOW` is dropped) and ends in `ShowWindow(SW_SHOW)` (`:455-467`). `SW_SHOW` may activate. **(premise)** `WS_EX_NOACTIVATE` blocks activation by click, not by a programmatic show.

**Hypotheses.**
1. *A tauri/tao call can set both properties.* Refuted. There is no tool-window flag, and `APPWINDOW` cannot be cleared on an unowned window. The click-through setter on a visible window ends in `SW_SHOW`.
2. *A setter on a hidden window is safe.* True, but it does not help on its own. On a hidden window `apply_diff` writes the styles, shows nothing (`:405-409`, `:455` needs `VISIBLE`) and uses `SWP_NOACTIVATE` (`:441`). The problem is showing the window afterwards. tauri `show()` → tao `set_visible(true)` → `SW_SHOW`, because `MARKER_DONT_FOCUS` is gone, and the rewrite drops `TOOLWINDOW`. Also, tauri's `set_ignore_cursor_events` is posted to the main thread. A raw show from the overlay thread can therefore run before it, and the later `apply_diff` (tao still thinks the window is hidden) runs `ShowWindow(SW_HIDE)` and hides the shown overlay. Mixing tauri setters with raw calls is a race, so the approach uses raw calls only.
3. *Same concern on a second path.* Only one code path builds or shows label `overlay` (`overlay.rs` `OverlayThread::execute`/`build`; invariant 2). The settings window is a separate label and out of scope. The install smoke is the second consumer of the window shape. It already counts a click-through tool window of class `Tauri Window` (`smoke_predicate.rs` `a_click_through_overlay_window_counts`, with and without layered attributes). It reports such a window shown at start as `unlisted` drift that names both causes (`an_unlisted_product_class_window_is_drift_that_names_both_causes`). The `make check` tripwire refuses `Tauri Window` as a helper class. So the F-003 direction stays closed with no change to `scripts/ci/helper-windows.txt` or `visible-windows.ps1`. The census runs only at the first and loaded launch (`ci.yml` `Get-HelperDrift`). The T-006 hotkey-hold steps show the overlay but take no census. Latent risk to note: a future smoke step that runs the census during a press would see the overlay as `unlisted`, and that would be correct (a product window, never listed).
4. *This class was fixed before.* No `overlay` class in `docs/failures.md`. Related classes and what they bind here:
   - smoke-window-predicate (F-003, F-008): no exclusion by style, unowned check kept. This rules out the owner-window approach.
   - ci-premise-unchecked-before-main (F-001/2/5/7/8/9/11, decisions #90): the Win32 premises below are proven only by a green `wip/T-067` run before `CODE_COMPLETE`.
   - windows-ci-external-process (F-006): no new pwsh run.
   - F-005: every wait polls against `BUDGET`.

   `recurrence_of: []` stands.
5. *A layered window is not drawn without layered attributes.* Open risk; it decides the extra guard test. tao's event-target window relies on it ("isn't displayed to the user because of the LAYERED style", `event_loop.rs:683-686`). tao's own click-through, which tauri users run on visible transparent windows, also writes `WS_EX_LAYERED` with no `SetLayeredWindowAttributes`. So whether the WebView2 pill still paints after the bit is set on a hidden window and then shown is not settled from source. Hence the "drawn" guard test (below) and a fallback, `SetLayeredWindowAttributes(hwnd, 0, 255, LWA_ALPHA)`, used only if that guard goes red. It is not the default, because it changes the composition path of a DWM blur-behind transparent window (tao `on_create`, `window.rs:1203-1217`).

**Root cause.** See `analysis.root_cause`: tao's creation path has no tool-window flag, adds `APPWINDOW` to every unowned window, and offers click-through only as a post-creation diff that ends in `SW_SHOW`. Nothing contradicts it in the sources read.

**Invariant.** See `analysis.invariant`. It extends `docs/decisions/overlay.md` invariant 3, which today reads "built visible with `focused(false)`". It becomes: "built hidden; the one non-activating show comes after all overlay bits are written; no tao setter ever". The "Don't" list of §3 stays as it is.

**Seam and why it is safe against tao.** The function lives in `src-tauri/src/overlay.rs`, is called once per build on the "overlay" thread, and does no tao call:
- It reads `GetWindowLongPtrW(GWL_EXSTYLE)`, ORs in `TRANSPARENT|LAYERED|TOOLWINDOW` and clears `APPWINDOW`. `NOACTIVATE|TOPMOST` stay.
- It writes the style with `SetWindowLongPtrW`, using `SetLastError(0)` before and `GetLastError` after, because a return of 0 is ambiguous.
- `SetWindowPos(.., SWP_FRAMECHANGED|SWP_NOACTIVATE|SWP_NOMOVE|SWP_NOSIZE|SWP_NOZORDER)` applies the cached style. **(premise)**
- `ShowWindow(SW_SHOWNOACTIVATE)` shows it. The window already has `WS_EX_TOPMOST` from creation.

The hwnd comes from `WebviewWindow::hwnd()` (tauri `webview_window.rs:1966`, `cfg(windows)`), as the tests already read it.

Why this is safe against tao:
- tao's flags keep `VISIBLE` and `IGNORE_CURSOR_EVENT` unset, and tao never applies a diff by itself for this window (`event_loop.rs:1947` is a `MAXIMIZED=false` diff, which is empty for a non-maximised window, `:318-320`). The bits therefore hold until destroy. Any tao setter would hide the window and drop the bits, which §3's "Don't" already forbids. The `stable` check of the tests (facts unchanged for `SETTLE`) catches a rewrite once `Facts` carries the new bits.
- Calls across threads are allowed inside one process. `SetWindowPos`/`ShowWindow` send to the main thread and block like `build()` already does. The overlay thread holds no lock (invariant 1/2 unchanged).
- WebView2 content shows with its parent: runtime-wry never calls wry `with_visible`, and the wry default is `true` (`wry lib.rs:857`, `webview2/mod.rs:231-233`, `:610`). runtime-wry shows nothing after creation (only `WindowMessage::Show`, `lib.rs:3380`).
- Building with `visible(false)`: tao's `on_create` `set_visible(false)` is an empty diff (`window.rs:1229`). Nothing is shown before the raw show.

Building hidden first changes `placement()` order: it is unchanged, because it reads `GetForegroundWindow` before the build.
