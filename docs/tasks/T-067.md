## Context

OQ-10 answered (decisions #86): the overlay look and position stay as built in T-057, and the owner wants it click-through and out of Alt+Tab. T-057 left both out (`docs/decisions/overlay.md` §2): each needs a setter or a raw style change after creation, which tao turns into `SW_SHOW` and may activate the window, stealing focus from the target of the paste. Proposed approach (OQ-10): build the overlay hidden, set `WS_EX_TRANSPARENT | WS_EX_LAYERED` (click-through) and `WS_EX_TOOLWINDOW`, then show it with `SW_SHOWNOACTIVATE`. The install-smoke predicate counts a click-through overlay and a tool window shown at start (F-003, T-065): the overlay must still be counted as a product window where the smoke expects it.

## Acceptance

- [ ] While recording, the overlay window has `WS_EX_TRANSPARENT`, `WS_EX_LAYERED` and `WS_EX_TOOLWINDOW` set, and is not activated when shown: the window in front before the press stays the foreground window (Windows CI shell test)
- [ ] A mouse click on the overlay's area reaches the window under it (Windows CI shell test: hit-test / click lands on the window behind)
- [ ] The overlay does not appear in the Alt+Tab list (tool-window style, unowned top-level check in the shell test)
- [ ] Failure branch: a style that cannot be applied leaves the overlay hidden or shown without activation and writes one diagnostics line with the kind and OS code only (no text); the paste target keeps focus
- [ ] Install smoke and `scripts/ci/helper-windows.txt` census stay green: the overlay is not mistaken for a framework helper (F-003)
- [ ] Test that fails without the change: `src-tauri/tests/overlay.rs` (new test for the three ex-styles and no activation)
