## Investigation

Tools: Serena (`get_symbols_overview` and `find_symbol` on `src-tauri/src/overlay.rs` and `src-tauri/tests/lifecycle.rs`), grep for the `poll(` / `BUDGET` sites and the docs, and `gh run view 41861094915 --log-failed` (read-only). No Windows run was made: shell tests run only in Windows CI.

**Frame.** Observed: one Windows CI attempt red on `lifecycle.rs::destroying_the_overlay_as_the_last_window_keeps_the_app_while_the_tray_exists`, with "Recording built no `overlay` window within 20s" and no `overlay_failed` in the app's log. The same sha was green on a fresh run. Expected: the overlay's "shown" verdict does not depend on how long WebView2 takes to build the window.

**Hypotheses.**
1. *Cold first WebView2 build exceeds the 20 s ceiling (F-019 on the overlay path).* Confirmed:
   - The failing test was the first in its binary to take `serial()`. The first event in its log, the app's `started` line, comes at 16:17:33.025, 2 ms after `running 6 tests`.
   - It failed 40.1 s later. That is the 20 s poll plus about 20 s until `run_return` returned, so the main thread was still in the build when the driver gave up, as in F-019.
   - The next test built a settings window and passed in 1.8 s, so the WebView2 environment was warm by then.
   - No `overlay_failed` line, so the build did not fail.
2. *Load from sibling tests in the same process* (T-200's note). Refuted as the mechanism:
   - All 6 tests in lifecycle.rs take `serial()`.
   - The two tests reported "running for over 60 seconds" were blocked on that mutex, not running alongside.
   - Cargo runs test binaries one at a time.
3. *A second path: the overlay thread failed or never woke* (reducer gave `Nothing`, build error). Not supported:
   - No `overlay_failed` line.
   - core `lifecycle_tests` passed in the same job.
   - The shown state was the first state published, so the reducer answers `Build`.
   - Without a receipt this cannot be told apart from (1) inside the 20 s. That gap is the defect the fix closes.
4. *This class was fixed before.* Yes:
   - F-005, F-013 and F-021 were fixed in core (rca T-080, T-110).
   - F-019 was fixed in the shell by T-097 for the settings window only, through the opener's FIFO probe `request_with`.
   - T-097 left the overlay sites unfixed by name, because the overlay thread has no receipt (follow-up (1)). `lifecycle.rs::BUDGET`'s doc and the failures.md class row list this exact site as an unaudited ceiling.
   - T-097 did not fail: this site was out of its scope. The fix is this task.

**Audit of the overlay build waits** (all are `poll(BUDGET)` on a build the overlay thread runs):
- lifecycle.rs: `shown` in `destroying_the_overlay_as_the_last_window_keeps_the_app_while_the_tray_exists`. This is the red one.
- overlay.rs (Wry, `BUDGET` 20 s), the first-show, re-show and "one visible" waits in:
  - `recording_processing_and_message_show_the_overlay_while_the_target_keeps_the_foreground` (`shown_within_budget`)
  - `hidden_then_recording_at_once_leaves_exactly_one_visible_overlay` (`first_shown`, the second show, `one_within_budget`)
  - `an_overlay_destroyed_from_outside_is_rebuilt_by_a_newer_shown_state` (`first_shown`, both rebuild `one_visible` waits)
  - `set_overlay_returns_while_the_main_thread_is_blocked` (`shown_after_release`)
  - `the_overlay_is_click_through_out_of_alt_tab_and_shown_without_activation` (`shown_within_budget`)
  - `the_click_through_overlay_still_paints_its_page` (`shown_within_budget`)
  - Any of these can take the binary's cold first build: all of them take `serial()`, and the lock order is not fixed.
- overlay_ipc.rs (MockRuntime, `BUDGET` 10 s), in `overlay_ready_returns_the_newest_published_state_as_the_last_emit_carries_it`:
  - `built` (window plus the first emit)
  - `emitted_processing`
  - MockRuntime has no WebView2, so the risk is a host stall only. The wait is still a clock verdict on the overlay thread, and the receipt orders it the same way.

**Waits this task does not change** (not overlay builds; `BUDGET` is documented for these):
- Waits on a removal or a `Destroyed` event: the `gone` / `hidden_gone` / `hidden_label_freed` / `outside_gone` waits.
- The `holds_for(SETTLE)` "stays one" checks. They are a minimum hold, not a ceiling.
- The non-overlay waits in lifecycle.rs: `ended`, `applied`, the tray-removal `recv_timeout`, and `run_with_driver`'s report wait.
- In overlay.rs `set_overlay_returns_while_the_main_thread_is_blocked`: `main_blocked` and `released_by_driver`.
- The `drawn` screen-pixel wait in `the_click_through_overlay_still_paints_its_page`. It is a page render after the build and has no receipt. If it ever goes red, the page's own `overlay_ready` call is the ordering signal to use. Named residual, T1.

**Root cause.** The overlay thread (`overlay::run` → `OverlayThread::execute`) has no observable "handled seq N" outcome. So each overlay build wait in the shell tests is a wall-clock ceiling on tauri's `build()` return. On the binary's first WebView2 window, that return can take longer than the ceiling. This explains all the symptoms: red only on attempt 1, green at the same sha, no failure line, warm sibling builds fast, and the 40 s duration.

**Invariant / seam.** See the front matter. The receipt keeps the overlay decisions intact:
- Invariant 1: `set_overlay` / `publish` never waits on the receipt.
- The mailbox mutex is taken only to store the outcome after `execute`, never across a window call.
- The receipt is set only when the phase is not `Destroying`, so a Hidden→Recording pair settles after the rebuild.
- It is a test seam like `settings_window::request_with`: no command, so there is no `APP_COMMANDS` or capability change.
- It needs a short §2 note or a new "test seam" paragraph in `docs/decisions/overlay.md`.

**Options.**
- **A (recommended): the product receipt.**
  - Why it removes the cause: the verdict is ordered on the thread's own outcome. The only clock left is a hang bound (proposed 120 s, as `OPENER_HANG`, below each binary's `WATCHDOG`: 180 s lifecycle, 240 s overlay) that reports "build still running (hung)" by name.
  - Red first (lifecycle.rs): the 25 s main-thread hold reproduction is red on `poll(BUDGET)` and green on the receipt.
  - Failure branch (overlay_ipc.rs, MockRuntime): a pre-existing `overlay` label makes the build fail with `WindowLabelAlreadyExists`. The receipt says `failed` and the log has `overlay_failed`, and the test message names both.
  - Risk: a product change on the overlay thread; the core reducer is untouched.
  - Rollback: revert. No product caller uses the receipt.
  - The developer must check that the Rust `listen` used by overlay_ipc.rs's `emitted` sees `emit_to` before the receipt is published.
- **B: test-only hang-bound poll on "window present OR `overlay_failed` logged".**
  - No product change, and it would stop this flake in practice.
  - It still polls. A thread that handled the state and built nothing is reported only after the hang bound, and the emit wait stays unordered. It also falls short of design_ref's "receipt" and Acceptance 2's "without beating a wall-clock budget".
- **C: warm-up build; D: a bigger BUDGET.** Rejected by T-097: C moves the clock, D breaks I2.

**Recurrence.** Class `os-answer-deadline-race`. This is a new sighting of F-019, at a site the class row already listed as unaudited, not a new mechanism. No new rca is needed: T-173 is the planned code fix for that residual. When this lands, the docs change is:
- F-019's row gains the sighting (run 41861094915) and the overlay receipt as the ordering signal.
- The class row drops the "not audited" overlay list.

This run is literally such a sighting. It is at the site T-097 had excluded on purpose, so it does not show that T-097's fix failed. Whether to open follow-up (2) now is for the orchestrator or owner to decide. It is a guard and CI change (`checker: true`) outside this seam and does not block T-173.
