**Already built: no work for T-053 (corrects the Context).**
- **The 3 s and remaining-time rules are core's.**
  - `show` sets `until = at + 3 s` (`recording/mod.rs:432-438`).
  - `derive` puts Recording above Message (`indicator.rs:97-104`), so a message raised during a recording is not shown.
  - `release` calls `expire(at)` and keeps `until` (`recording/mod.rs:276-283`), so after the release the message shows only for what is left, or not at all.
  - `tick` and `next_deadline` (`:410-419`) expire it.
  - Pinned by `finish_err_while_next_recording_is_live_keeps_recording_then_tray_error` (`:1101`) and `notice_raised_while_recording_shows_after_release_for_the_rest_of_its_3s` (`:1373`). A job failure during a recording (`job_finished(Failed)` while live) goes through the same `show`/`expire` path.
- **The session publishes and expires.**
  - `Shared::publish` (`dictation.rs:143-158`) runs under the lock, deduplicated, and holds back while a stop is in flight (no Hidden between Recording and Processing).
  - `run_timer` (`:455-482`) ticks at `next_deadline` and publishes the result.
  - Nothing is published at start (`:205-213`).
  - Real-time tests: `message_expires_without_input` (`dictation_session.rs:1563`), `timer_follows_the_latest_deadline` (`:1606`).
- **data-model.md:180 already states the rule.** It was added by `00c07ca` (T-051), which `git log -S` confirms. The Context's "data-model.md:160 rule" doc item is done.
- **So the UI needs no expiry timer.** A UI timer would be a second timer next to `run_timer`, and the two can disagree. Example: a message replaced inside its 3 s would be hidden early by a UI timer that started for the first message. Invariant (5) forbids it.

**Hypotheses.**

2. *The same concern on a second path.* Five risks, each closed by the invariant:

   - (c) `set_overlay` building the window itself. Off the main thread `create_window` blocks on `rx.recv()` until the main thread has built the window (tauri-runtime-wry `lib.rs:300-336`), and that would happen under the session lock. On the main thread `send_user_message` runs inline (`lib.rs:263-277`). One such case: T-052's tray-menu handler calls `tray_menu_opened`, `expire` hides a message, and `publish` reaches `set_overlay`. Window creation would then run inside an event handler, the case tauri documents as a deadlock on Windows (`webview_window.rs:56-59`). Closed by (1)(2).

4. *The remaining-time rule needs new code.* Refuted (see "Already built"). The Acceptance's "core tests" for it can only be a regression pin at the session level, and it passes before any change. The red tests are the payload/text tests, the e2e and the shell test.

**Design (recommended).**
1. **Text: one renderer, Rust (confirms decision #64 / T-006 Q6).**
   - Every core message (`OverlayState::Message{id, params}`) is rendered by `voicen_core::i18n::text(lang, id, params)`, which resolves `mic_reason.*` one level deep in the same language. The page shows that text as given, as Svelte text, never `{@html}`.
   - The page renders only its own UI-only ids, `overlay.recording` (`{elapsed}` = m:ss) and `overlay.processing`, with `t`. They are added to `i18n/en.json` and `ru.json`. UI-only ids need no `messages!` (i18n.md).
   - The UI derives no language (i18n.md, settings-ui U1). The payload carries `lang`, the snapshot's `ui_language` at render time, and the page calls `setLanguage(lang)`.
   - Mirroring the nested rule in TS is rejected as a second renderer with a hand copy of `NESTED_IDS`.
2. **Wire (core, new `crates/voicen-core/src/overlay.rs`).**
   - `OverlayPayload { seq: u64, lang, state }`, with `state` = `recording { elapsedMs }` | `processing` | `message { text }` | `hidden`.
   - `overlay_payload(&OverlayState, UiLanguage, seq, elapsed) -> OverlayPayload` is a pure function.
   - `seq` is assigned in `set_overlay`, so it is monotonic in the controller's order. `elapsedMs` = now − the instant `set_overlay` received this Recording. That gives `overlay_ready` the right value for a webview that loads 100–300 ms late (R-13), and fills T-051 Q7's default.
   - `pending`, `durationMs` and `severity` are dropped (see Q-O3).
   - A core test compares `e2e/fixtures/overlay-wire.json` with core's own payloads: one per kind, and the microphone message in en and ru. This follows the pattern of `e2e_settings_wire_fixture_matches_core` (`settings/service.rs:2953-2983`). The Playwright nested-id case thus displays text that Rust rendered.
3. **UI.**
   - `src/lib/overlay/overlayApi.ts` is the one IPC module of spec 001 ipc.md (settings-ui C). The mock re-exports its wire type.
   - `src/lib/overlay/state.ts` holds `apply(current, payload)`: a payload is applied only if `payload.seq > current.seq`. This mirrors I2 (settings-ui M), because the `overlay_ready` reply and an `overlay://state` event can arrive in either order. It also holds `formatElapsed(ms)` → m:ss.
   - `src/routes/overlay/+page.svelte`: the listener is registered first, then `overlay_ready`. The page is display only (no buttons, no focusable element) with a transparent background. A rejected `listen` or `overlay_ready` shows nothing. A 1 s ticker only redraws the elapsed time.
4. **Shell (Windows).** `src-tauri/src/overlay.rs`:
   - `set(&OverlayState)` is what the shell `Indicator` forwards. It stores the newest `(seq, state, Instant)` in a mailbox (its own short mutex plus a condvar) and returns.
   - One overlay thread takes the newest state and carries out the platform-free lifecycle decision:
     - no window and the state is not Hidden → build;
     - live window → emit;
     - Hidden → destroy, then wait for its `Destroyed` before any rebuild;
     - intermediate states may coalesce.
   - This lifecycle reducer is pure. Put it in core `overlay.rs` with Linux tests (like #57, T-044), and the shell only executes it.
   - `build()` from that thread blocks only that thread, which holds no lock, as the tauri docs advise (`webview_window.rs:58-59`).
   - Window: label `overlay`, `WebviewUrl::App("overlay")`, `focused(false)`, `focusable(false)`, `always_on_top(true)`, `skip_taskbar(true)`, `decorations(false)`, `transparent(true)`, `shadow(false)`, `resizable(false)`, positioned bottom-centre of `work_area` of the monitor that holds `GetForegroundWindow()` at build. The foreground window is the start window, because the overlay never activates.
   - All styles are applied before the first show, and the first show is non-activating. Either build visible (tao's creation path gives `SW_SHOWNOACTIVATE`), or build hidden, apply `set_ignore_cursor_events(true)` while hidden (`apply_diff` then only hides, `window_state.rs:405-409`) and show with raw `ShowWindow(hwnd, SW_SHOWNOACTIVATE)`. No tao setter after that.
   - `WS_EX_TOOLWINDOW` (keeps the window out of Alt+Tab, R-13) is a raw style that tao overwrites at its next flag change. Set it last, or drop it if the CI test shows `WS_EX_NOACTIVATE` plus skip-taskbar is enough. That is a developer choice, and the test pins the result.
   - `overlay_ready` returns `overlay_payload` of the mailbox's current state. It never takes the session lock.
   - Nothing is logged about the payload.
5. **Capability.** A new `capabilities/overlay.json`: label `overlay`, exactly `core:event:allow-listen` and `core:event:allow-unlisten`. No destroy, because only the shell destroys the window. It is not added to `default.json`: `another_window_label_gets_no_permission` (`src-tauri/tests/settings_window.rs:485-512`) stays the guard for `settings`.
6. **Smoke (F-003).** In `visible-windows.ps1`, delete the `WS_EX_TOOLWINDOW` clause (`:47`). "Shown" becomes a visible, unowned, top-level window of the process whose class is not "Tao Thread Event Target".
   - By the T-037 r2 reading (reviews/2.md:29-35), tao's event target is still excluded by class, the settings window still counts, and the tray-icon and IME windows have no `WS_VISIBLE`. So the first launch (exactly one) and the Loaded launch (none) keep their meaning.
