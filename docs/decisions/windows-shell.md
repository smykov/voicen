# Windows shell: start order, single instance, exit and tray

**Code:** `src-tauri/src/lib.rs` (`assemble`, `wire`, `build_app`, `on_run_event`, `run`, `release_parts`), `src-tauri/src/settings_window.rs` (`request`, `Receipt`, the opener thread), `src-tauri/src/tray.rs` (`install`, `TrayPart`, `applied`, `on_menu_event`, `on_tray_icon_event`, `on_second_instance`), `src-tauri/src/logs_folder.rs` (`FolderOpener`, `install`, `request`) and `src-tauri/src/win/shell_open.rs` (`ShellOpener`, T-071), `src-tauri/icons/tray/`, `src-tauri/Cargo.toml` (`tauri` feature `tray-icon`, `tauri-plugin-single-instance`), core `crates/voicen-core/src/tray.rs` and `settings::gate::second_launch_action` · **Tests that pin it:** `src-tauri/tests/single_instance.rs`, `src-tauri/tests/tray.rs`, `src-tauri/tests/lifecycle.rs` (real Wry runtime), the T-052 cases of `src-tauri/tests/settings_window.rs`, core `tray::tests::*` and `settings::gate::tests::second_launch_action_table`, and the install smoke's second-launch and close-settings checks in `.github/workflows/ci.yml` (all shell tests: Windows CI only)

Task: T-052 (split from T-006 by decision #64). Class `windows-shell`; no `docs/failures.md` entry of this class yet, so the defects below are the risks the T-052 analysis found in the pinned sources (tauri 2.12.1, tauri-runtime-wry 2.12.1, tao 0.37.1, tray-icon 0.25.1, tauri-plugin-single-instance 2.5.2), not incidents. Owner defaults: OQ-11 (icons, `Front`, left click). Related: `docs/decisions/settings-ui.md` S1 (the window itself), `docs/decisions/diagnostics-log.md` (only the primary opens the log), `docs/decisions/dictation-session.md` (the `Indicator` rule). T-006 appends the dictation adapters and wiring below (code: `src-tauri/src/dictation.rs`, `src-tauri/src/win/{hotkey,capture,clipboard,paste}.rs`; tests: `src-tauri/tests/{hotkey,clipboard,paste,capture,dictation_e2e,delivery}.rs`, Windows CI only, plus core `win32_data` tests).

## Invariants

### No process touches the log, the data dir, the Run value or a window before tauri's `build()` has run the plugins' setup

- **Defect that produced it:** none in the failure log (T-008 review round 1 #3, widened by the T-052 analysis). `run()` opened the log, deleted every models `.part`, loaded (and on a first run wrote) `settings.json` and reconciled the Run value before `build()`. `build()` is where the single-instance plugin decides (tauri `app.rs:2607`), so a second launch did all of that to the primary's files before it exited.
- **What breaks if you violate it:** a second launch writes a `started` line into the primary's log (and can roll the file the primary holds), deletes the `.part` of the primary's running download, moves an unreadable `settings.json` aside, or rewrites the Run value.
- **Where it is enforced:** one assembly body, `assemble(builder, context, parts)`: `commands(builder).build(context)?` first, then `parts()` (in `run()`: `release_parts`, the log, `LocalModels::open` with its cleanup, `load_settings`), then `wire` (managed state, change bridge, opener thread, tray, language follower). A `build()` error returns before `parts` runs. `build_app` (the tests' wiring) is `assemble` with ready-made parts, so the tests run the same body. The plugin is registered first and only by `run()`; in a second instance it hands its argv to the primary and calls `process::exit(0)` inside `build()` (plugin `windows.rs:55-105`). Tests: `single_instance.rs` (`startup_side_effects_run_only_after_the_plugins_setup` with a probe plugin whose setup records what is on disk, `a_failing_plugin_setup_leaves_no_side_effect`); the install smoke's second launch (exit 0, no `started pid=<second>`, a planted `.part` kept).
- **Exception (T-061):** `main()`'s `--purge-credentials` branch (`win::purge::from_args`, exact argument only) exits before `run()` and touches only Credential Manager: no Tauri, no log, no window, no output.
- **Don't:** do anything with a side effect in `run()` before `assemble`, or inside the second-instance callback (it posts one request, nothing else); add a hand-written mutex check before `diag::start` (a second instance mechanism beside the plugin, P-011); declare `app.trayIcon` in `tauri.conf.json` (tauri builds it inside `build()` before the plugins, so a second instance would flash an icon; `tray.rs::config_declares_no_tray_icon`).

### The single-instance plugin is never registered by a test, and a real-runtime test never calls `App::run`

- **Defect that produced it:** none (T-052 analysis, "new hazard", F-003's spirit: a silent pass). The plugin's second-instance path calls `process::exit(0)` inside `build()`: a libtest exe that registers it while another app with the same identifier holds the mutex `<identifier>-sim` (the tests' `generate_context!(test = true)` has the release identifier) would end in mid-run with code 0, which cargo counts as a pass. `App::run` ends in `process::exit` too (tao `event_loop.rs:221-227`).
- **What breaks if you violate it:** a test exe that "passes" without running its tests.
- **Where it is enforced:** the plugin appears only in `run()`; `build_app` and every test build without it. `lifecycle.rs` drives the real Wry loop with `Builder::any_thread` and `App::run_return`, ends it only from inside a main-thread task, and has a watchdog that exits non-zero. The real plugin is proven only by the install smoke.
- **Don't:** register the plugin in `build_app`, `assemble` or a test; call `run` in a test.

### `settings_window::open` runs only on the one opener thread; every caller posts and never waits

- **Defect that produced it:** none in the failure log (T-052 analysis hypothesis 2(b)). tauri's label check (`manager/window.rs:70-72`) and the insert (`:116-117`) bracket the OS window creation (`window/mod.rs:390-415`), so two concurrent `open`s could both pass the check, build two windows, and leave one unmanaged on screen. In the real runtime the gap is a whole WebView2 creation.
- **What breaks if you violate it:** two settings windows (two drafts of one file), or a window built inside an event handler or the plugin's `WM_COPYDATA` window procedure, which tauri documents as a deadlock on Windows (`webview_window.rs:56-59`).
- **Where it is enforced:** `settings_window::start_opener` (called once by `wire`) starts the "settings-window" thread and manages its queue; `request(app, target)` sends one job (with its own `AppHandle`) and returns a `Receipt` at once. The opener runs jobs in posting order and writes a failed open as `settings_window_failed`. A panic inside one job is caught there (in builds that unwind, such as the tests): one `settings_window_failed` line without an OS code, that receipt reports the request as not completed (`Some(Err(FailedToReceiveMessage))`), and the next job runs; the release profile has `panic = "abort"`, so there a panic ends the process instead of leaving a dead opener that every later request would fail against silently (review round 1 #7). Runtime callers (`on_ready`, the tray item, the second instance, T-006's `ShellRequests`) drop the receipt; only tests wait on it. In the real runtime `create_window` from the opener posts to the main thread and waits there, which is tauri's own advice for building windows. Tests: `settings_window.rs` (one thread, no caller's, for the creation and every focus emit; `request` returns while its open is held; eight concurrent requests → one window; FIFO), `single_instance.rs`, `tray.rs::the_settings_item_opens_one_window_and_then_fronts_it`, `lifecycle.rs::destroying_the_last_window_keeps_the_app_running` (Ready opens through the opener on the real runtime). Details of the window: `settings-ui.md` S1.
- **Don't:** call `open` from any other thread at runtime, wait for a receipt on the main thread or in a window procedure, or add a lock inside `open` (see Rejected approaches).

### The tray changes only in one fire-and-forget main-thread task; `set_tray` and the language follower only store and post; the main thread never calls a session input

- **Defect that produced it:** none in the failure log (T-052 analysis hypothesis 2(c)). tauri's `TrayIcon::set_*` post to the main thread and wait for the result (`menu/mod.rs:26-40`, `tray/mod.rs:499-526`). The session calls `Indicator::set_tray` under its lock (`dictation-session.md`), so a `set_tray` that called a setter would block under the lock, and deadlock if the main thread were itself waiting for that lock (a tray handler calling `tray_menu_opened` inline). A press holds the lock across `AudioSource::start`.
- **What breaks if you violate it:** a frozen app (main thread and session waiting for each other), or a tray that shows an old state.
- **Where it is enforced:** `tray.rs`. `Shared::want` stores the change under a short lock, bumps a version and posts one `run_on_main_thread` task unless one is already posted. The task renders the latest view (icon, tooltip, and a new menu only when the language or `retry_available` changed) and repeats until no change came in during a render, then clears the flag, so one apply is in flight at a time and the last value always lands. No lock is held across a setter, so `applied()` never waits for an apply (in the mock runtime the setters `SendMessageW` to the test thread's tray window). "Menu opened" (`Click{Right, Up}`, or `Click{Left, Up}` while the one `MENU_ON_LEFT_CLICK` flag is set; tray-icon sends the click event, then shows the menu) is stamped on the main thread and handed to `DictationSession::tray_menu_opened` through `tauri::async_runtime::spawn_blocking`; the session is looked up as `Arc<DictationSession>` (managed by T-006). The language follower is its own `SettingsService::subscribe()`, taken before the snapshot that gives the start language, and acts only on a `ui_language` change; the menu cannot be updated "on open" (the click event arrives after `TrackPopupMenu` started). Tests: `lifecycle.rs::set_tray_returns_while_the_main_thread_is_blocked`, `tray.rs` (each state and retry flag reaches the icon; menu open clears Error through the session and keeps HotkeyError; a left click counts; hovering does not; the handler returns while a press holds the session lock; a ui_language save rebuilds menu and tooltip).
- **Don't:** call a `TrayIcon` setter from `set_tray`, the follower or any non-main thread; hold a lock across a setter; call a session input on the main thread; keep a tray state of its own (it shows only what the session publishes, `retry_available` included); read `Pipeline::pending()` for the menu.

### The process ends only by a programmatic exit; `ExitRequested { code: None }` is prevented while the tray exists

- **Defect that produced it:** decision #38 Q3 (interim): closing the first-run window ended the app. In tauri 2.12.1 `ExitRequested { code: None }` comes only from the last window's `Destroyed` (runtime-wry `lib.rs:4255-4270`); every programmatic exit carries `Some(code)` (`lib.rs:4300-4311`, `app.rs:581-587`). T-057's overlay is the only window on a Loaded start, so destroying it on `Hidden` would end the process without this rule.
- **What breaks if you violate it:** the app ends when the user closes the settings window (or the overlay hides); or, the other way, Exit no longer ends it; or Exit ends it but leaves the icon in the notification area until the user hovers over it, which reads as "Voicen is still running" (T-052 review round 1 #1).
- **Where it is enforced:** `on_run_event`: `Ready` → `settings_window::on_ready`; `ExitRequested { code: None }` → `api.prevent_exit()` only while `app.tray_by_id(TRAY_ID)` exists (without a tray there would be no way to end the process); `Some(_)` passes. The tray "Exit" item calls `app.exit(0)`. Exit ends the process without dropping the dictation session (`dictation-session.md`). Only tauri keeps the `TrayIcon` (its resources table): tray-icon deletes the icon and destroys its hidden window only when the last copy is dropped (tray-icon 0.25.1 lib.rs:388-395, windows/mod.rs:313-325), and tauri's `RunEvent::Exit` cleanup drops only its own copy (app.rs:1128-1131, 1449-1452), so the tray module stores none and looks the icon up for each render (`tray_by_id`; nothing after the cleanup). Tests: `lifecycle.rs` (`destroying_the_last_window_keeps_the_app_running`, `the_tray_exit_item_ends_the_loop_with_code_0`, which also checks that the `tray_icon_app` window that came with the app is gone once `run_return` returned), the install smoke (closing the settings window keeps the process for 10 s).
- **Don't:** prevent `Some(_)`; prevent without a tray; end the process any other way than `AppHandle::exit`; keep a `TrayIcon` clone in managed state, a thread or a static.

### Menu items, their ids and texts, tooltips and icon kinds come from one core table

- **Defect that produced it:** none (P-010).
- **What breaks if you violate it:** a menu id the handler does not map, a tooltip in a hard-coded language, or two icons for one state.
- **Where it is enforced:** core `voicen_core::tray`: `menu(retry_available)` ([Settings, Exit] in T-052, [Settings, Open logs folder, Exit] since T-071; T-007 adds Retry, feature 005 History), `TrayAction::{as_str, from_id, label}`, `tooltip(TrayState)`, `icon(TrayState)`; the catalog ids are declared with `messages!` (`i18n.md`). The shell renders them with `i18n::text` in the settings' `ui_language`; images are the four `src-tauri/icons/tray/*.png` (32×32 RGBA, `include_image!` needs RGBA). An unknown menu id does nothing. Tests: core `tray::tests::*` (literal ids and texts from contracts/messages.md), `tray.rs::an_unknown_menu_id_does_nothing`.
- **Don't:** spell a menu id, catalog id or tooltip in the shell; add a catch-all arm to the menu handler.

### The Windows dictation adapters carry out and stamp; they decide nothing, and they keep the session's lock contracts

Task: T-006. Class `windows-shell`; no `docs/failures.md` entry, so the defects are the risks the T-006 analysis found in the pinned sources (cpal 0.18.2, windows 0.62.2), not incidents. Five rules:

1. **Hotkey events reach core only as `DictationSession::hotkey_pressed`, `hotkey_released`, `hotkey_registration`, `esc_pressed` and `cancel_key_result`, from the one hotkey thread, with instants stamped there; that thread is the only code that registers or releases the dictation hotkey.** T-055: besides the startup registration it serves the settings save's two-step registration as requests (`win::hotkey::HotkeyRegistrarHandle`, the shell's `HotkeyRegistrar`): `Prepare` registers the new combination under the spare id next to the active one, `Commit` releases the active id, makes the spare one active and reports `hotkey_registration(true)`, `Abort` releases the spare id; a hold in progress keeps polling the keys it was pressed with. `RegisterHotKey` must run on the thread that owns the window, hence requests, not calls from the save thread. The thread never takes the settings save lock (a save waits on it, bounded by 10 s; an unanswered prepare is `Unavailable` and the thread releases what it registered for it). The startup registration is reported before `HotkeyThread::start` returns, so a failure (tray `HotkeyError`, `notice.hotkey_unavailable`, settings on Recording / `recording.hotkey`) is posted before `Ready` (on the real runtime the install smoke proves the settings window appears; the tray state and the notice are proven on MockRuntime only, see the T-006 note below), whose executor then posts no tab (`startup_action_after_hotkey`, T-055 Q1). The `RegisterHotKey` codes, the poll groups and release rule, the elevated rule, the menu-mask key (0xE8) and the modifier-wait keys come from `voicen_core::win32_data`. T-009: the thread also serves the session's Esc claim (`win::hotkey::CancelKeyHandle`, the `CancelKey` port) over the same request channel: a claim registers Esc bare (`ESC_ID`) and under the active hotkey's modifiers (`ESC_MOD_ID`, OQ-21 (1): in hold mode the user holds them) and reports `cancel_key_result(both registered)` (a refusal writes no `hotkey_register_failed` line: the session's `Warning{EscUnavailable}` is its line); a release unregisters both; `WM_HOTKEY` on an Esc id calls `esc_pressed`. The thread never decides when Esc is claimed: the session asks, following `live_id()`. Why: a thread that counts repeats, debounces, times the 0.3 s, reads `mode` or decides "a recording is on" is a second owner beside the controller (T-006 hypothesis 2(a), T-009 option B rejected).
2. **Every port call made under the session lock returns within a bound that no library wait can exceed, sends no message to a foreign window, never calls a session input and never waits for a thread that does; no adapter holds one mutex across its methods.** The calls are `Paster::capture_start_window`, `AudioSource::devices`, `AudioSource::start`, dropping a `CaptureHandle` and `Indicator`. Why: cpal 0.18.2 activates the default device with an unbounded wait inside `default_input_config` (`device.rs:754-760`, `:396-407`), and the client is cached, so `build_input_stream`'s timeout no longer applies; a `SendMessage` or `GetWindowText` to a hung target would hold the session lock. Enforced: `CpalSource::devices` (the input endpoints, each with its WASAPI endpoint id) and `CpalSource::start` (opens the id core chose with `HostTrait::device_by_id`, never "the default" on its own, T-012) both run on a mic-open thread and wait at most `OPEN_BUDGET` (3 s, OQ-12, decisions #85), a stream that opens later fails the send and is dropped at once; `WinPaster` reads only process facts of the foreground root owner; the data callback calls only `FrameSink::frames`, the error callback (`win::capture::device_loss_callback`) only calls `FrameSink::device_lost` once per stream, which hands the loss to the session's loss thread and never takes the session lock (T-012: every stream error means the device is gone; the session ends the recording through its one stop path). The settings command `settings_list_microphones` lists through the same managed `AudioSource` (`settings_ipc::Microphones`), off the session lock; a listing error gives an empty list.
3. **The microphone is open only from a successful `start` until `stop` or drop returns.** A stream that opens after `start` gave up is closed at once (NFR-02). `Stream`'s drop joins cpal's stream thread, so no callback runs after it.
4. **No OS text leaves an adapter.** `CaptureError` kinds with fixed literals (`capture_error`: `DeviceNotAvailable` → `NoDevice`, `PermissionDenied` → `AccessDenied`, `DeviceBusy` → `DeviceBusy`, anything else → `Other(<literal>)`), `ClipboardError`, `PasteError`, and typed `Warning` lines whose only OS fact is the Win32 code (`win::os_code`). cpal's WASAPI error map never yields `PermissionDenied` (`E_ACCESSDENIED` falls to `BackendError`, the code survives only in the message), so a Windows privacy denial most likely reads `mic_reason.other`; the owner's check reads the log line `outcome=capture_failed mic=...` (T-006 Q2 default; no HRESULT probe until that shows it is needed).
5. **One wiring function builds the only `DictationSession`.** `dictation::start_dictation` (see `docs/architecture.md`) takes the managed `SettingsService` and `Log`, makes one `LogObserver`, uses the `SettingsService`'s own `CredentialStore` instance (`PipelineDeps.credentials` must be it), manages `Arc<DictationSession>`, starts the hotkey thread and attaches it to the `SettingsService`'s own `HotkeyRegistrarHandle` (`DictationPorts::hotkeys`, T-055) and to the session's `CancelKeyHandle` (built inside, not a port; T-009) (T-055: until then, and after the handle is dropped, the registrar fails closed and a changed hotkey is refused); a second call for an app that has a session starts nothing and writes `dictation_start_failed`. It is a sibling of `build_app`, not inside it, so the nine `build_app` test call sites do not start a hotkey thread or register a global hotkey. `run()` calls it after `assemble` and before `app.run`.

- **What breaks if you violate it:** a frozen session lock (every input waits), a microphone that stays open, a second observer or credential store writing double lines or reading another instance's keys, every shell test registering the real hotkey.
- **Where it is enforced:** the adapters' own files and `dictation.rs`; tests (Windows CI): `hotkey.rs` (a synthetic hold opens one capture and closes it on release; any key up releases; no `WM_CHAR` or menu activation; a taken hotkey gives `HotkeyError` and `hotkey_register_failed` with `os_code=1409`; dropping the handle frees the hotkey), `clipboard.rs` (text plus the three formats; retry; held past the retries gives `ClipboardError`), `paste.rs` (root owner and integrity; Ctrl+V into an edit control; another window in front gives `CopyManual`; the modifier wait is bounded), `capture.rs` (error map without OS text), `dictation_e2e.rs` (a hold through the real wiring pastes), `hotkey_registrar.rs` (T-055: a saved hotkey is registered and the old one freed; a taken one is refused and the old one keeps working; a later refusal frees the prepared one; a hotkey taken at start opens settings on the hotkey field and a save recovers; dropping the handle frees a committed hotkey) and its install-smoke step in `ci.yml` (T-055: a Loaded launch with Ctrl+Alt+Space taken → a shown settings window, `hotkey_register_failed os_code=1409`, the app alive), `delivery.rs` (window replaced or elevated gives `copy_manual`; `AccessDenied` shows no Recording state; engine none opens settings on Engine), the install smoke (while the app runs, `RegisterHotKey(Ctrl+Alt+Space)` from PowerShell fails with 1409; and two hold steps, `scripts/ci/hotkey-hold.ps1`, send a real 3 s `SendInput` hold: on a loaded launch (engine `local_server` at a refused loopback address) exactly one new `dictation rec=` line, no blocked line, and the process still alive; on a first launch exactly one `dictation outcome=blocked reason=no_engine` line and no `dictation rec=` line; runner facts in `docs/decisions/windows-ci-runner.md`). `win32_data` against the `windows` crate constants: `hotkey.rs`.
- **Don't:** open the device on the hotkey thread without a bound; add a mutex held across adapter methods; call a session input from a port; copy cpal's or Windows' message into an error or a log line; build a second session or observer; put the wiring in `build_app`.

### "Open logs folder" has one path, never runs on the main thread, and ends every failure in one line

- **Defect that produced it:** none (T-071, the owner's request; spec 006 FR-017).
- **What breaks if you violate it:** the Explorer launch (`ShellExecuteEx` can block on shell extensions) freezes the tray and every main-thread task; verb "open" on a file would run it; a path or OS text in the log (#45).
- **Where it is enforced:** `tray::on_menu_event` maps `TrayAction::OpenLogs` to `logs_folder::request(app)`, which returns at once: a "logs-folder" thread does `create_dir_all` on the installed dir, calls the injected `FolderOpener` only when it `is_dir()`, and writes any failure (spawn, create, not a directory, open) as exactly one `warning kind=logs_folder_failed [os_code=N]`. `run()` installs `paths::log_dir()` with `win::shell_open::ShellOpener` (option A): `ShellExecuteExW` verb "open" on the directory, `SEE_MASK_NOASYNC | SEE_MASK_FLAG_NO_UI` (no error dialog), under `CoInitializeEx(COINIT_APARTMENTTHREADED)` on that thread, balanced by `CoUninitialize`; the folder is opened, nothing selected; it never creates the folder (a missing path is `Err` with Win32 code 2) and refuses a non-directory itself. No new crate: `windows` 0.62.2 features `Win32_UI_Shell` and `Win32_System_Com`. Without `install` a click does nothing (the forgotten `install` in `run()` is the owner's manual check). Tests: `tray.rs::the_open_logs_item_creates_and_opens_the_logs_dir_off_the_main_thread`, `a_failing_opener_writes_one_logs_folder_failed_line_and_the_app_keeps_working`, `a_file_at_the_logs_path_is_never_opened_and_gives_one_warning`, `the_shell_opener_refuses_a_missing_folder_with_code_2_and_no_window` (only the failure branch: a success opens an Explorer window on the runner, F-006).
- **Don't:** open the folder inline in the menu handler; open it from a second place (the later About button, spec 006 FR-017, goes through `logs_folder::request`); hand a path to the shell without the `is_dir` check; log the path or the OS text.

### `Applied.icon` and `Applied.tooltip` record only a setter that returned `Ok`

- **Defect that produced it:** none in the failure log (T-052 validation 1, F1). They were written from the core table even when the setter failed, and tauri 2.12.1's `TrayIcon` has no getter, so deleting `set_icon` / `set_tooltip` kept every test green.
- **What breaks if you violate it:** the tray tests prove the table, not the icon.
- **Where it is enforced:** `tray.rs` `Shared::apply`: `icon` and `tooltip` are written only when their setter returned `Ok`; `state`, `retry_available` and `lang` stay what the task asked for. Tests in `tests/tray.rs` fail when a setter is removed.
- **Don't:** record `icon` or `tooltip` from the table; add a getter-based read-back (none exists).

### The opener's test seam `request_with` runs through the same loop and the same `catch_unwind`

- **Defect that produced it:** none (T-052 review round 2, Low #9: the panic branch had no test, and a panicking focus listener is ruled out because it poisons tauri's listener mutex).
- **Where it is enforced:** `settings_window.rs`: `request` and `request_with` both post a `Job` with `Work::Target` or `Work::Run` through `post`; the opener loop runs either under `catch_unwind` and writes the same `settings_window_failed` line and receipt. `request_with` is for tests only (no production caller).
- **Don't:** give a test its own thread or a second path around the loop; call `request_with` from production code.

## Rejected approaches

| Approach | Why rejected | Ref |
|---|---|---|
| A `run_on_main_thread` hop for non-main callers of `open` | serialises in the real runtime only; the mock runs tasks inline on the caller while the loop is not running (`mock_runtime.rs:84-96`), so it is not provable; it builds inline from main-thread callers (the second instance inside `WM_COPYDATA`) | T-052 analysis hypothesis 5, option A |
| A mutex inside `open` | deadlock: the main thread blocks on it while the holder waits in `create_window` for the main thread | T-052 option C |
| `WebviewLabelAlreadyExists` treated as focus | leaves the two-window case open | T-052 option D |
| A tray from `tauri.conf.json` `app.trayIcon` | built inside `build()` before the plugins decide: a second instance flashes an icon | T-052 hypothesis 2(e) |
| The plugin registered in `build_app` or a test | its `process::exit(0)` inside `build()` would end a test exe as a pass | T-052 "new hazard" |
| `App::run` in a real-runtime test | ends in `process::exit` | T-052, tao `event_loop.rs:221-227` |
| A hand-written instance mutex before `diag::start` | a second instance mechanism beside the plugin (P-011) | T-052 options |
| Proving tray Exit through UIA in the smoke | depends on Explorer and the overflow flyout on the runner and on tray-icon's private `WM_USER_TRAYICON`; kept as the owner's manual check | T-052 options |
| cpal's open on the hotkey thread without a bound (`default_input_config` then `build_input_stream` with a timeout) | the activation inside `default_input_config` is unbounded and the client is cached, so the timeout never applies; the session calls `start` under its lock | T-006 hypothesis 5 |
| Reading "access denied" from cpal's message or kind | `E_ACCESSDENIED` becomes `BackendError`, the HRESULT lives only in OS text, which is never parsed (P-009) | T-006 hypothesis 4 |
| Reading the privacy ConsentStore registry to detect a denied microphone | a model of Windows policy, not a fact of the call (F-003) | T-006 analysis |
| The core std `Server` (`test_support::local_models`) as a transcription mock | it answers with model bytes and reads only a request head; tests inject a test `Engine` through `engine_factory` | T-006 hypothesis 6 |
