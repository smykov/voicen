# Windows shell: start order, single instance, exit and tray

**Code:** `src-tauri/src/lib.rs` (`assemble`, `wire`, `build_app`, `on_run_event`, `run`, `release_parts`), `src-tauri/src/settings_window.rs` (`request`, `Receipt`, the opener thread), `src-tauri/src/tray.rs` (`install`, `TrayPart`, `applied`, `on_menu_event`, `on_tray_icon_event`, `on_second_instance`), `src-tauri/icons/tray/`, `src-tauri/Cargo.toml` (`tauri` feature `tray-icon`, `tauri-plugin-single-instance`), core `crates/voicen-core/src/tray.rs` and `settings::gate::second_launch_action` · **Tests that pin it:** `src-tauri/tests/single_instance.rs`, `src-tauri/tests/tray.rs`, `src-tauri/tests/lifecycle.rs` (real Wry runtime), the T-052 cases of `src-tauri/tests/settings_window.rs`, core `tray::tests::*` and `settings::gate::tests::second_launch_action_table`, and the install smoke's second-launch and close-settings checks in `.github/workflows/ci.yml` (all shell tests: Windows CI only)

Task: T-052 (split from T-006 by decision #64). Class `windows-shell`; no `docs/failures.md` entry of this class yet, so the defects below are the risks the T-052 analysis found in the pinned sources (tauri 2.12.1, tauri-runtime-wry 2.12.1, tao 0.37.1, tray-icon 0.25.1, tauri-plugin-single-instance 2.5.2), not incidents. Owner defaults: OQ-11 (icons, `Front`, left click). Related: `docs/decisions/settings-ui.md` S1 (the window itself), `docs/decisions/diagnostics-log.md` (only the primary opens the log), `docs/decisions/dictation-session.md` (the `Indicator` rule).

## Invariants

### No process touches the log, the data dir, the Run value or a window before tauri's `build()` has run the plugins' setup

- **Defect that produced it:** none in the failure log (T-008 review round 1 #3, widened by the T-052 analysis). `run()` opened the log, deleted every models `.part`, loaded (and on a first run wrote) `settings.json` and reconciled the Run value before `build()`. `build()` is where the single-instance plugin decides (tauri `app.rs:2607`), so a second launch did all of that to the primary's files before it exited.
- **What breaks if you violate it:** a second launch writes a `started` line into the primary's log (and can roll the file the primary holds), deletes the `.part` of the primary's running download, moves an unreadable `settings.json` aside, or rewrites the Run value.
- **Where it is enforced:** one assembly body, `assemble(builder, context, parts)`: `commands(builder).build(context)?` first, then `parts()` (in `run()`: `release_parts`, the log, `LocalModels::open` with its cleanup, `load_settings`), then `wire` (managed state, change bridge, opener thread, tray, language follower). A `build()` error returns before `parts` runs. `build_app` (the tests' wiring) is `assemble` with ready-made parts, so the tests run the same body. The plugin is registered first and only by `run()`; in a second instance it hands its argv to the primary and calls `process::exit(0)` inside `build()` (plugin `windows.rs:55-105`). Tests: `single_instance.rs` (`startup_side_effects_run_only_after_the_plugins_setup` with a probe plugin whose setup records what is on disk, `a_failing_plugin_setup_leaves_no_side_effect`); the install smoke's second launch (exit 0, no `started pid=<second>`, a planted `.part` kept).
- **Don't:** do anything with a side effect in `run()` before `assemble`, or inside the second-instance callback (it posts one request, nothing else); add a hand-written mutex check before `diag::start` (a second instance mechanism beside the plugin, P-011); declare `app.trayIcon` in `tauri.conf.json` (tauri builds it inside `build()` before the plugins, so a second instance would flash an icon; `tray.rs::config_declares_no_tray_icon`).

### The single-instance plugin is never registered by a test, and a real-runtime test never calls `App::run`

- **Defect that produced it:** none (T-052 analysis, "new hazard", F-003's spirit: a silent pass). The plugin's second-instance path calls `process::exit(0)` inside `build()`: a libtest exe that registers it while another app with the same identifier holds the mutex `<identifier>-sim` (the tests' `generate_context!(test = true)` has the release identifier) would end in mid-run with code 0, which cargo counts as a pass. `App::run` ends in `process::exit` too (tao `event_loop.rs:221-227`).
- **What breaks if you violate it:** a test exe that "passes" without running its tests.
- **Where it is enforced:** the plugin appears only in `run()`; `build_app` and every test build without it. `lifecycle.rs` drives the real Wry loop with `Builder::any_thread` and `App::run_return`, ends it only from inside a main-thread task, and has a watchdog that exits non-zero. The real plugin is proven only by the install smoke.
- **Don't:** register the plugin in `build_app`, `assemble` or a test; call `run` in a test.

### `settings_window::open` runs only on the one opener thread; every caller posts and never waits

- **Defect that produced it:** none in the failure log (T-052 analysis hypothesis 2(b)). tauri's label check (`manager/window.rs:70-72`) and the insert (`:116-117`) bracket the OS window creation (`window/mod.rs:390-415`), so two concurrent `open`s could both pass the check, build two windows, and leave one unmanaged on screen. In the real runtime the gap is a whole WebView2 creation.
- **What breaks if you violate it:** two settings windows (two drafts of one file), or a window built inside an event handler or the plugin's `WM_COPYDATA` window procedure, which tauri documents as a deadlock on Windows (`webview_window.rs:56-59`).
- **Where it is enforced:** `settings_window::start_opener` (called once by `wire`) starts the "settings-window" thread and manages its queue; `request(app, target)` sends one job (with its own `AppHandle`) and returns a `Receipt` at once. The opener runs jobs in posting order and writes a failed open as `settings_window_failed`. Runtime callers (`on_ready`, the tray item, the second instance, T-006's `ShellRequests`) drop the receipt; only tests wait on it. In the real runtime `create_window` from the opener posts to the main thread and waits there, which is tauri's own advice for building windows. Tests: `settings_window.rs` (one thread, no caller's, for the creation and every focus emit; `request` returns while its open is held; eight concurrent requests → one window; FIFO), `single_instance.rs`, `tray.rs::the_settings_item_opens_one_window_and_then_fronts_it`, `lifecycle.rs::destroying_the_last_window_keeps_the_app_running` (Ready opens through the opener on the real runtime). Details of the window: `settings-ui.md` S1.
- **Don't:** call `open` from any other thread at runtime, wait for a receipt on the main thread or in a window procedure, or add a lock inside `open` (see Rejected approaches).

### The tray changes only in one fire-and-forget main-thread task; `set_tray` and the language follower only store and post; the main thread never calls a session input

- **Defect that produced it:** none in the failure log (T-052 analysis hypothesis 2(c)). tauri's `TrayIcon::set_*` post to the main thread and wait for the result (`menu/mod.rs:26-40`, `tray/mod.rs:499-526`). The session calls `Indicator::set_tray` under its lock (`dictation-session.md`), so a `set_tray` that called a setter would block under the lock, and deadlock if the main thread were itself waiting for that lock (a tray handler calling `tray_menu_opened` inline). A press holds the lock across `AudioSource::start`.
- **What breaks if you violate it:** a frozen app (main thread and session waiting for each other), or a tray that shows an old state.
- **Where it is enforced:** `tray.rs`. `Shared::want` stores the change under a short lock, bumps a version and posts one `run_on_main_thread` task unless one is already posted. The task renders the latest view (icon, tooltip, and a new menu only when the language or `retry_available` changed) and repeats until no change came in during a render, then clears the flag, so one apply is in flight at a time and the last value always lands. No lock is held across a setter, so `applied()` never waits for an apply (in the mock runtime the setters `SendMessageW` to the test thread's tray window). "Menu opened" (`Click{Right, Up}`, or `Click{Left, Up}` while the one `MENU_ON_LEFT_CLICK` flag is set; tray-icon sends the click event, then shows the menu) is stamped on the main thread and handed to `DictationSession::tray_menu_opened` through `tauri::async_runtime::spawn_blocking`; the session is looked up as `Arc<DictationSession>` (managed by T-006). The language follower is its own `SettingsService::subscribe()`, taken before the snapshot that gives the start language, and acts only on a `ui_language` change; the menu cannot be updated "on open" (the click event arrives after `TrackPopupMenu` started). Tests: `lifecycle.rs::set_tray_returns_while_the_main_thread_is_blocked`, `tray.rs` (each state and retry flag reaches the icon; menu open clears Error through the session and keeps HotkeyError; a left click counts; hovering does not; the handler returns while a press holds the session lock; a ui_language save rebuilds menu and tooltip).
- **Don't:** call a `TrayIcon` setter from `set_tray`, the follower or any non-main thread; hold a lock across a setter; call a session input on the main thread; keep a tray state of its own (it shows only what the session publishes, `retry_available` included); read `Pipeline::pending()` for the menu.

### The process ends only by a programmatic exit; `ExitRequested { code: None }` is prevented while the tray exists

- **Defect that produced it:** decision #38 Q3 (interim): closing the first-run window ended the app. In tauri 2.12.1 `ExitRequested { code: None }` comes only from the last window's `Destroyed` (runtime-wry `lib.rs:4255-4270`); every programmatic exit carries `Some(code)` (`lib.rs:4300-4311`, `app.rs:581-587`). T-057's overlay is the only window on a Loaded start, so destroying it on `Hidden` would end the process without this rule.
- **What breaks if you violate it:** the app ends when the user closes the settings window (or the overlay hides); or, the other way, Exit no longer ends it.
- **Where it is enforced:** `on_run_event`: `Ready` → `settings_window::on_ready`; `ExitRequested { code: None }` → `api.prevent_exit()` only while `app.tray_by_id(TRAY_ID)` exists (without a tray there would be no way to end the process); `Some(_)` passes. The tray "Exit" item calls `app.exit(0)`. Exit ends the process without dropping the dictation session (`dictation-session.md`). Tests: `lifecycle.rs` (`destroying_the_last_window_keeps_the_app_running`, `the_tray_exit_item_ends_the_loop_with_code_0`), the install smoke (closing the settings window keeps the process for 10 s).
- **Don't:** prevent `Some(_)`; prevent without a tray; end the process any other way than `AppHandle::exit`.

### Menu items, their ids and texts, tooltips and icon kinds come from one core table

- **Defect that produced it:** none (P-010).
- **What breaks if you violate it:** a menu id the handler does not map, a tooltip in a hard-coded language, or two icons for one state.
- **Where it is enforced:** core `voicen_core::tray`: `menu(retry_available)` ([Settings, Exit] in T-052; T-007 adds Retry, T-054 "Open logs folder", feature 005 History), `TrayAction::{as_str, from_id, label}`, `tooltip(TrayState)`, `icon(TrayState)`; the catalog ids are declared with `messages!` (`i18n.md`). The shell renders them with `i18n::text` in the settings' `ui_language`; images are the four `src-tauri/icons/tray/*.png` (32×32 RGBA, `include_image!` needs RGBA). An unknown menu id does nothing. Tests: core `tray::tests::*` (literal ids and texts from contracts/messages.md), `tray.rs::an_unknown_menu_id_does_nothing`.
- **Don't:** spell a menu id, catalog id or tooltip in the shell; add a catch-all arm to the menu handler.

## Rejected approaches

| Approach | Why rejected | Ref |
|---|---|---|
| A `run_on_main_thread` hop for non-main callers of `open` | serialises in the real runtime only; the mock runs tasks inline on the caller while the loop is not running (`mock_runtime.rs:84-96`), so it is not provable; it builds inline from main-thread callers (the second instance inside `WM_COPYDATA`) | T-052 analysis hypothesis 5, option A |
| A mutex inside `open` | deadlock: the main thread blocks on it while the holder waits in `create_window` for the main thread | T-052 option C |
| `WebviewLabelAlreadyExists` treated as focus | leaves the two-window case open | T-052 option D |
| A tray from `tauri.conf.json` `app.trayIcon` | built inside `build()` before the plugins decide: a second instance flashes an icon | T-052 hypothesis 2(e) |
| The plugin registered in `build_app` or a test | its `process::exit(0)` inside `build()` would end a test exe as a pass | T-052 "new hazard" |
| `App::run` in a real-runtime test | ends in `process::exit` | T-052, tao `event_loop.rs:221-227` |
| A hand-written instance mutex before `diag::start` | a second instance mechanism beside the plugin (P-011) | T-052 options |
| Proving tray Exit through UIA in the smoke | depends on Explorer and the overflow flyout on the runner and on tray-icon's private `WM_USER_TRAYICON`; kept as the owner's manual check | T-052 options |

## Open

- OQ-11 (owner, non-blocking): icon artwork, `Front` versus switching to Engine, left click. The defaults apply.
- Simultaneous launches: if the primary's plugin window is not found yet, the second instance falls through and runs as a full instance (plugin `windows.rs:73-107`). Residual plugin behaviour, not closed here.
- A setter refused by the shell (no notification area: tray-icon's `NIM_MODIFY` fails) writes one `tray_failed` line per apply and the record still names what was set; tray-icon re-registers the icon on `TaskbarCreated` with the data it last stored. The first Windows CI run prints whether `windows-latest` has a notification area (`tray.rs` probe, `rect()`).
- T-007: replacing the menu while it is shown (`retry_available` changing during `TrackPopupMenu`) is not exercised. The menu is rebuilt only when the language or `retry_available` changes, and in T-052 `menu(true)` equals `menu(false)`, so only a language save changes its items.
- Real foreground and the real notification area are the owner's checks; CI proves "fronted" as the focus event (mock) and un-minimized (smoke).
