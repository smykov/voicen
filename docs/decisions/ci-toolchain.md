## Why this area exists

`src-tauri/build.rs` calls tauri-build, which emits the Windows link configuration that a tauri-linked exe needs to link and start. tauri-build scopes each part of it for the app bin, through different cargo scopes:

| Output | Cargo scope | Reaches |
|---|---|---|
| stub `msvcrt.lib` search dir (static VC runtime) | `rustc-link-search` | every target of the cargo invocation, including other packages' doctests |
| `/NODEFAULTLIB` CRT args | `rustc-link-arg` | every target of the `voicen` package |
| Common-Controls v6 manifest (embed-resource) | `rustc-link-arg-bins` | bin targets only |

cargo's link-arg scopes are a closed set (cargo rust-1.99.0 `src/compiler/custom_build.rs:266-277`): all, bins, tests (integration tests), benches, examples, cdylib. No selector reaches a lib unit-test exe, a bin unit-test exe or a lib doctest without also reaching the bin. Every other exe kind cargo links for the package gets only part of the configuration. On Windows that part either fails to link (F-001) or links and does not start (F-002). The shell is first linked in the windows job, after review (decisions #5), so each mismatch costs a red windows job that blocks every `deploys: true` task behind it.

The shell also compiles only for Windows: every `release_*` fn in `src-tauri/src/lib.rs` is a `compile_error!` under `cfg(not(windows))`, and `tests/credentials.rs` and `tests/autostart.rs` are `#![cfg(windows)]`. Until T-056 a plain Windows-only compile error therefore also showed first in the windows job, at about 25 minutes per CI round. `make check` now type-checks the shell for `x86_64-pc-windows-gnu` (last invariant below). That target uses a different toolchain from the shipped `x86_64-pc-windows-msvc` one, so the Linux check covers types only. Linking and starting stay with the windows job.

## Invariants

### Every Windows test exe of `voicen` gets the release exe's link configuration; only `src-tauri/tests/*.rs` contain shell tests

- **Defect that produced it:** F-002. At f2e239b (T-030) the `src-tauri/tests/settings_ipc.rs` exe exited `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND` before any test ran (run 37159339288). The manifest reached bin targets only, so the integration-test exe bound comctl32 v5.82, which lacks `TaskDialogIndirect` (imported by muda's About dialog, tauri default feature `common-controls-v6`). `tests/credentials.rs` creates no tauri app and passed.
- **What breaks if you violate it:** the exe fails to link or exits `0xc0000139`, and only in the windows job after review. The Linux gate never links the shell.
- **Where it is enforced:**
  - `src-tauri/build.rs`: after `tauri_build::build()`, on `windows` + `msvc` only, it emits `cargo:rustc-link-arg-tests=/MANIFEST:EMBED` and `/MANIFESTINPUT:<src-tauri>/windows-app-manifest.xml`. `-tests` reaches integration tests only, so the release bin keeps tauri-build's manifest unchanged. Upstream tauri does the same for its own tests (tauri 2.12.1 `build.rs`, `embed_manifest_for_tests`, tauri PR 4383).
  - `src-tauri/windows-app-manifest.xml` is a copy of tauri-build 2.7.1's `src/windows-app-manifest.xml`: the same elements, attributes and values (one `dependentAssembly`, `Microsoft.Windows.Common-Controls` 6.0.0.0, `processorArchitecture="*"`, `publicKeyToken="6595b64144ccf1df"`, `language="*"`). Only whitespace and comments differ. The comments sit inside the root element, never before it:
    - one names the source file and version;
    - one on the `publicKeyToken` line carries `teamwright:allow-secret`, because the commit secret scan reads `…Token="<16 hex>"` as a secret (it is the public key token of the Windows assembly; `docs/process/gates.md` › Secret scan, false-positive exit). That marker is why the copy cannot be byte-identical.
  - `src-tauri/Cargo.toml` sets `[lib] doctest = false`, so plain `cargo test` builds no lib doctest exe. `cargo test --doc` (and `cargo rustdoc … -- --test`) ignores the key and builds the lib doctests anyway (cargo rust-1.99.0 `src/ops/cargo_compile/unit_generator.rs:425-440`; plain `cargo test` checks `doctested()` at `:397-410`). So both switches are pinned: the key by step 3 of the check below, the invocation by its step 4. Bins and `tests/*.rs` never get doctests, whatever their `doctest` key says (`src/workspace/manifest.rs:1018-1025`).
  - `make check` runs `scripts/ci/shell-test-layout.sh` on the host (bash, find, sort, grep, awk; no toolchain). It fails, naming this file, when the package could produce a test exe that `build.rs` does not configure. Under `src-tauri/src` it reads each file with a small lexer (`scripts/ci/shell-test-layout.awk`) that drops every comment (doc comments included) and string, raw-string and char literals, so text inside them never counts. Doc comments are not checked at all (T-038, decisions #41). It refuses:
    - a test attribute anywhere on a line, with any whitespace or line breaks inside it: `#[test]`, `# [test]`, `#[<path>::test]`, `#[test_case(…)]` (any attribute whose name starts with `test`), also as an attribute argument of `cfg_attr` (`#[cfg_attr(windows, test)]`);
    - a `cfg` or `cfg_attr` predicate naming `test`, on one line or split across lines: `#[cfg(test)]`, `#![cfg(test)]`, `#[cfg(all(windows, test))]`, `#[cfg_attr(test, …)]`;
    - a block comment, string or attribute left open at the end of a file;
    - a source rustc compiles from outside the scanned files:
      - `#[path = …]`, also as a `cfg_attr` argument;
      - the token `include` anywhere in code, outside comments and strings: `include!`, a rename (`use core::include as pull;`) and `r#include!`. An identifier named `include` is refused too (fail-closed; the message says to rename it). Identifiers that only contain it (`included`, `include_count`) and `include_str!` / `include_bytes!` pass;
      - any symlink under `src-tauri/src`. It is refused, not followed: `find -L` would skip a dangling link silently and walk a linked dir outside `src`;
      - a line-start `path` key (bare or quoted) under a `[lib]`, `[[bin]]`, `[[test]]`, `[[bench]]` or `[[example]]` header of `src-tauri/Cargo.toml` (spaces inside the brackets, and quotes around a bare-key name such as `["lib"]`, allowed). `path` in dependency tables (`[dependencies.x]`, `[target.'cfg(windows)'.dev-dependencies.x]`) and inline `{ path = … }` pass;
    - `src-tauri/benches`, `src-tauri/examples`, or `[[bench]]` / `[[example]]` in `src-tauri/Cargo.toml`;
    - in `src-tauri/Cargo.toml` (raw lines, with the same table-header tracking): no line `doctest = false` (spaces and a trailing comment allowed) in the `[lib]` table, or no `[lib]` table; any other line containing `doctest` that is not a full-line `#` comment (`true`, a quoted or dotted key, an inline `lib = { … }`, the key under another table); and `"""` or `'''` anywhere, because a multi-line string could fake a `[lib]` header for the line tracker;
    - in `src-tauri/Cargo.toml`, every line outside a whitelist grammar (T-038 review rounds 1 to 3, decisions #42 B). The tracker does not parse TOML. A manifest passes only when every line is self-contained, its code (single-line strings blanked, the comment cut) is printable ASCII and tab, no quoted key or header holds a backslash, every line whose code starts with `[` is a header of bare or quoted dotted keys, a one-key header names its table bare or quoted with bare-key characters only, and nothing but blank lines and comments comes before the first header. Within that grammar a line is a table header exactly when TOML reads one, and a one-key header names exactly the table TOML opens. TOML can make a target table without a header only through a dotted key or an inline value: under a header those belong to that header's table (`lib.path` under `[package]` is `package.lib.path`), and at the root they are refused. So every `[lib]`, `[[bin]]`, `[[test]]`, `[[bench]]` and `[[example]]` table of a manifest that passes is opened by a header the tracker follows. It refuses:
      - a line that is not self-contained. Single-line basic strings (with `\"` and `\\` escapes) and literal strings (no escapes) are removed, then the comment; the `[`/`]` and `{`/`}` left must nest and close on the line, and no string may be left open. Otherwise an element of a multi-line array or inline table (`["lib"]`, `["dependencies"]`, `[1]`) would pose as a header: a fake `[lib]` with a fake pin, or the end of a target table before a `path` key. The message says "keep arrays and inline tables on one line";
      - a backslash in a quoted key (a basic or literal string followed by `=` or `.`, also inside an inline table) or anywhere in a table header before its comment: an escape such as `"p\u0061th"` or `[["b\u0069n"]]` spells `path` or `bin` past the tracker;
      - a line starting with `[` that the header pattern does not read (bare or quoted dotted keys in `[…]` or `[[…]]`): with every line self-contained it can only be a header, and the tracker must not stay in the previous table;
      - a header of one key whose quoted name holds a character other than `A-Z a-z 0-9 _ -`. The name is read from the string-aware scan, not the raw line: `["li b"]`, `["lib#x"]`, `["l'i'b"]` and `["l]i[b"]` name tables cargo ignores, and stripping their quotes would read `lib` (a fake pin, or a second table after a real `[lib]` without one). With the refusal quoting changes nothing, so `["lib"]` is `[lib]`. A dotted header never names a target table, so its keys may hold other characters (`[target.'cfg(windows)'.dependencies]` passes);
      - a byte outside printable ASCII and tab in code (strings blanked, the comment cut, after the trailing `\r` of a CRLF line is stripped, so CRLF files pass). A UTF-8 BOM, which cargo strips, or an invisible space before `[[bin]]` or a key would keep the line from reading as a header or key. Non-ASCII text inside strings and comments passes;
      - before the first header, any line other than a blank, whitespace-only or comment line: a line whose code (strings blanked, the comment cut) holds anything but spaces and tabs, or that holds a string. A root-level key makes a target table without any header, and cargo 1.99 builds it: `bin = [{ name = "voicen", path = "../outside/main.rs" }]` (also as `"bin" = …`) moves the bin source outside `src-tauri/src`, and `example = [{ …, test = true }]`, `bench = [{ …, test = true }]` or `test = [{ …, path = … }]` add test exes no `-tests` link arg reaches (T-038 review round 3, finding 1). Stable cargo has no root-level key (`cargo-features` is nightly-only), so every key there is refused, not only target names (`x = 1` too). A comment there may hold anything;
    - `--doc` or `rustdoc` in a `*.yml` / `*.yaml` file of `.github/workflows` (the check's second argument), for every package, because a raw scan cannot tell which package a step selects (voicen-core's doctests run in `cargo test --workspace --exclude voicen`). A missing workflows dir is "cannot run"; an empty one passes.

    Fail-closed false positives, on purpose: an array or inline table split over lines (for example the long `windows = { … features = [ … ] }` dependency line) is refused although TOML and cargo accept it, and so are a backslash in a quoted key that would be harmless, a one-key table name quoted with other characters (`["my table"]`), and a file saved with a UTF-8 BOM. Keep arrays and inline tables on one line, keys without escapes, one-key table names bare, and the file without a BOM.

    Not caught, because a raw scan cannot see them (each is loud on the Windows job, not silent):
    - tests that a proc macro generates from an attribute with another name;
    - a dependency's macro that expands to `include!` (for example an `include_proto!`-style macro). A test it pulls in still reaches the lib test exe;
    - a workflow that reaches `--doc` through a script or a `.cargo` alias. A doctest exe that fails to link or start fails the step.

    A `find`, `sort`, `grep` or `awk` error is "cannot run" (exit 3), never a pass. `make check-shell-layout-fixtures` pins the shapes above: each fixture shell dir must give its documented exit code (0, 1 or 3). `ok-doc-text` holds the sources of the 25 doc-shape fixtures and the b8b0b81 probes that T-038 dropped, plus code-looking text in every doc form, and must pass.
- **Rule for shell test authors:** put shell tests in `src-tauri/tests/<name>.rs`. They need no per-file setup; the manifest reaches every one of them. Put platform-independent logic and its unit tests in `crates/voicen-core`. Keep every shell source a regular file under `src-tauri/src`, reached without `#[path]`, `include` or a Cargo target `path`. Write examples in shell doc comments as ```` ```text ````: lib doctests never run, so a ```` ```rust ```` block would only look tested. This is a style rule (T1), not checked. If a new exe kind is really needed, extend `build.rs`, this file and the check together in one reviewed change.
- **Don't:**
  - add `#[cfg(test)]` modules or test attributes in `src-tauri/src`;
  - remove `doctest = false` from `[lib]` in `src-tauri/Cargo.toml`, or add another `doctest` key;
  - pass `--doc` or run `rustdoc --test` for `voicen` (in a workflow, a script or an alias), or put `--doc` / `rustdoc` in any workflow step (the check refuses it for every package);
  - split an array or inline table of `src-tauri/Cargo.toml` over lines, write an escape in a quoted key or a table header, quote a one-key table name with characters other than `A-Z a-z 0-9 _ -`, put any key before the first table header, or save the file with a BOM or with non-ASCII outside strings and comments;
  - emit the manifest with `cargo:rustc-link-arg` (it reaches the bin too and duplicates its `RT_MANIFEST`) or drop the `-tests` scope;
  - edit `windows-app-manifest.xml`, or upgrade tauri-build, without comparing the copy's elements and values with the new tauri-build's file;
  - upgrade tauri-build, tauri-winres or embed-resource without checking the shell's build-script output on the Windows runner (`target/*/build/voicen-*/output`). Every bins-only line there (`cargo:rustc-link-arg-bins=…`, `cargo:rustc-link-arg-bin=voicen=…`, and any output that moved from all targets to bins) must be mirrored to `cargo:rustc-link-arg-tests` in `build.rs`, or the integration tests silently miss it again. Today the only such output is the Common-Controls manifest;
  - add `/WX` to the test link args (upstream does, for its own workspace; here it would turn any unrelated test-link warning into an error, T-030).

### A doc block never becomes a Windows test exe

- **Defect that produced it:** F-003. The guard's doc-block scan (T-035, T-036) re-implemented rustc's doc desugaring, rustdoc's unindent and CommonMark in awk, and each review round found shapes it passed.
- **What breaks if you violate it:** a doctest exe links the shell with the partial build-script configuration (the F-001/F-002 mechanism). It turns red only on the Windows job, after review.
- **Where it is enforced:** the doctest switches are pinned: `[lib] doctest = false` (step 3 of `scripts/ci/shell-test-layout.sh`) and no `--doc` / `rustdoc` in `.github/workflows` (step 4), with their fixtures. Doc text itself is never read.
- **Don't:** bring back a check that decides on how rustdoc would read doc text (see Rejected approaches).

### Other packages' tests never share a cargo invocation with `voicen` on Windows

- **Defect that produced it:** F-001. From T-003 to T-033 a voicen-core doctest failed to link on windows-latest (LNK4003 on `target/debug/build/voicen-*/out/msvcrt.lib`, then LNK1120). cargo gives every build script's search dirs to every doctest of one invocation, but only the doctest's own package's link args (cargo rust-1.99.0 `cargo_test.rs:231`, `build_runner/mod.rs:301-312`).
- **What breaks if you violate it:** other crates' doctests link against the stub `msvcrt.lib` without the matching CRT args and fail to link.
- **Where it is enforced:** `.github/workflows/ci.yml`, windows job: `cargo test --workspace --exclude voicen --no-fail-fast` (so one red test binary does not hide the others; the step still exits non-zero, T-048), then `cargo test -p voicen` (the comment above the two steps). The reviewer checks it.
- **Don't:** merge the two steps back into `cargo test --workspace`.

### A test exe that cannot start turns the windows job red

- **Defect that produced it:** none; it is what makes the two invariants above observable. In run 37159339288 cargo ended the step with exit code 1 when the settings_ipc exe did not start.
- **Where it is enforced:** the windows test steps have no `continue-on-error`, `|| true` or `--no-run`. That includes the runner probe step (T-059): its guard counts lines with `awk`, which exits 0 on no match, so it needs no `|| true`.
- **Don't:** add any of them to the windows test steps.

### Every shell crate target type-checks for Windows in `make check`

- **Need that produced it:** no defect, only detection latency (decisions #5, #57, #63; T-056). Before this check a compile error in shell code or in a shell test reached review and first showed in the windows job.
- **What it covers:** every crate target the windows job builds for `voicen`, type-checked for `x86_64-pc-windows-gnu` in the dev profile. It runs two invocations:
  1. `cargo check -p voicen --target x86_64-pc-windows-gnu`: the lib and the bin with the release feature set in the dev profile. That means the default features, no dev-dependency features, and tauri without `custom-protocol`. It is the closest to `pnpm tauri build` that needs no built frontend, but it is not that build (see "What it does not cover");
  2. the same with `--tests`: the lib and bin unit-test crates and every `src-tauri/tests/*.rs`, with the test features (`tauri/test`, `voicen-core/test-fakes` from `[dev-dependencies]`), as `cargo test -p voicen` builds them.

  Both are needed:
  - A type error that is only in a test file passes (1) and fails (2). T-056 probe P-F2, re-run on the implemented image with `src-tauri/tests/credentials.rs` in `docs/tasks/T-056.reviews/1.md` (mutation 2).
  - Lib code that uses a `test-fakes`-only item (`voicen_core::secrets::FakeCredentialStore`) passes `--tests` and `--all-targets` and fails (1). With test targets selected, cargo unifies the dev-dependency features into the lib it checks (P-F3).
- **What it does not cover:** the gnu toolchain is not the shipped msvc one, so the check proves types only.
  - Nothing is linked, started or run. Link and start failures (the F-001 and F-002 class) stay with the windows job. The gnu build-script output has none of the msvc link configuration: no static-VC-runtime search dir, no `/NODEFAULTLIB`, and the test-manifest lines of `build.rs` are emitted for `windows` + `msvc` only. A gnu link or test build would therefore not stand in for those failures either.
  - What only `pnpm tauri build` compiles is not checked. That build uses the release profile with the CLI-managed `tauri/custom-protocol` feature (tauri 2.12.1 `src/lib.rs:32`). It changes two things:
    - The cfgs. tauri's build script turns the feature into `cfg(custom_protocol)` and turns `cfg(dev)` off (`build.rs:252-255`). tauri-build passes the `dev` cfg to the app crate (tauri-build 2.7.1 `src/lib.rs:715`, from `DEP_TAURI_DEV`, `:593-608`), but never `cfg(custom_protocol)` (`:660-661`): that cfg exists only inside tauri.
    - The context. `generate_context!()` (`src-tauri/src/lib.rs:166`) takes its production branch: it embeds `frontendDist` (`../build`) with CSP processing, and panics when that dir is missing (tauri-macros 2.7.1 `src/context.rs:155`, tauri-codegen 2.7.1 `src/context.rs:176-190`).

    So these are type-checked only by the windows job's `pnpm tauri build`: that production branch, tauri's own `cfg(custom_protocol)` code, and shell code under `cfg(not(dev))` or `cfg(not(debug_assertions))`. Shell code under the positive `cfg(dev)` / `cfg(debug_assertions)` is type-checked by the Linux check (dev profile) and never compiled by `pnpm tauri build`. Today the shell's only code of the first kind is the `windows_subsystem` attribute at `src-tauri/src/main.rs:2`; no shell code uses `cfg(dev)`, `custom_protocol` or `is_dev`. A third invocation with `--features tauri/custom-protocol` would need `pnpm build` first and goes beyond decision #63 (Open).
  - Code under `cfg(target_env = "msvc")` is not checked. Today no shell source or test uses `target_env` (only `build.rs` reads it), so the gnu and msvc checks see the same Rust code.
  - aws-lc-sys's C code is compiled with mingw gcc and the shipped prebuilt NASM objects (`.cargo/config.toml`), not with cl.exe and `/MD`. The CRT question (Open, W2) stays with the windows job.
  - A future dependency that cannot build for gnu would show as a red `check-shell-windows` with a green windows job. That needs a decision recorded here, not a workaround.
- **What breaks if you violate it:** a compile error in shell code or a shell test reaches review and shows first in the windows job.
- **Where it is enforced:**
  - Makefile `check-shell-windows` runs both invocations, joined by `&&`, in one `scripts/tw-run core` call. It is a prerequisite of `check`, after `check-core`: the shell depends on voicen-core, so a core error is reported first by the faster native check.
  - The `voicen-rust:1.99` image (`docker/rust.Dockerfile`) carries:
    - `gcc-mingw-w64-x86-64-win32`. Even under `cargo check`, aws-lc-sys's build script compiles aws-lc with it. Its binutils dependency brings `x86_64-w64-mingw32-windres`, which tauri-build uses to compile the app resource.
    - the rustup target `x86_64-pc-windows-gnu`. It is baked in because tw-run's containers are removed after each command, so adding it at run time would download it on every run.
  - On an image without the target the step fails with `error[E0463]: can't find crate for 'core'` and the hint that the target may not be installed. The fix is `make core-image`.
  - CI reaches the check through the gate job's existing `make core-image` and `make check`; `ci.yml` is unchanged.
  - Debug `cargo check` builds tauri without `custom-protocol`, so `generate_context!` runs in dev mode and needs no built frontend (`build/`). tauri-build writes `src-tauri/gen/schemas/*.json`, which is gitignored.
- **Cost (T-056, a 6-core Linux host):**
  - The first run after an image change builds cold: 131 s here. The spike measured 214 s, and 372 s at load average 14-16. aws-lc-sys's C build is on the critical path, and nothing is shared with `check-core`.
  - A warm no-op takes about 2 s, and 3 to 5 s after a shell edit.
  - `target/` grows by about 1 GB (`target/x86_64-pc-windows-gnu` plus host build scripts and proc macros under `target/debug`), and the image from 2.96 GB to 3.6 GB on disk (725 MB to 861 MB compressed).
- **Cost on GitHub (T-058, decisions #81):** `check-shell-windows` builds cold on every gate run: typically about 98 s (range 77-102 s over 9 of 10 main runs, one 55 s fast-runner outlier), e.g. run 37465516406 (gate job 112275432997: 1m29s plain + 6.5 s `--tests`) and 37245716605 (job 111563104238: 77 s). That is about a quarter of "Run make check" (254-397 s) and 15-20 % of the gate job (439-597 s); the windows job starts only when the gate ends.
  - **Decision: keep the gate cold, no `target/` cache.** A cache would save at most about 85-95 s of a 7.5-10 min gate. The repo's Actions cache is already 10.51 GB against the 10 GB default limit, so a roughly 1 GB entry would evict the windows job's rust-cache entries (1.6-2.1 GiB each). The key proposed in the task's Context (`Cargo.lock` + rust-toolchain + image digest) cannot hit: the image digest changes every run (unpinned `FROM rust:1.99-bookworm` and `apt-get update`) and there is no rust-toolchain file. A key on committed files (Dockerfile + `Cargo.lock`) would hit, but it would reuse artifacts built by a different apt/mingw image, e.g. aws-lc-sys's C build, which cargo does not fingerprint; a changed rustc is not a stale risk, cargo fingerprints the rustc version.
  - **Invariant:** no `target/` artifact from another run feeds `check-shell-windows`.
  - Not decided here: caching the image (the build is 135-151 s per run, 83-107 s of it cargo-about's release build) is a possible separate follow-up.
- **Don't:**
  - replace the two invocations with `--tests` alone or with `--all-targets` (P-F3: a release-only error passes);
  - add `cargo build`, `cargo test`, `--no-run` or any other link step for the gnu target;

### The helper-window manifest matches the shell's Windows dependency graph in `make check`

- **Defect that produced it:** F-008 (class `smoke-window-predicate`, T-065 rca). The install smoke's window predicate excluded framework helper windows by a list read from one library at a time; T-052 added tauri-plugin-single-instance, whose visible helper first showed up as a red smoke on every launch of the delivery run (run 37419266451), because nothing on the host connected the list to the dependency graph.
- **What breaks if you violate it:** a crate@version, or a feature change of a listed crate, that creates windows reaches the windows job unread, and its helper (if visible) fails the install smoke on every launch or, if the list is wrong the other way, a stale entry hides nothing and rots.
- **Where it is enforced:** Makefile `check-helper-windows-fixtures` (part of `make check`, before `check-core`) runs `scripts/ci/helper-windows.test.sh`, which runs the tripwire `scripts/ci/helper-windows.sh` on its fixtures (`scripts/ci/fixtures/helper-windows/`: listed, features, binding features, unlisted, stale, version change, feature change, feature dropped, binding with features, product class as visible helper, product class from source, no longer creates, comment mention, unknown verdict, helper without class, and cannot-run cases including no product class), on the real graph with the committed manifest `scripts/ci/helper-windows.txt` (must pass), with tao's entry removed or its feature list dropped (must fail naming tao) and with `Tauri Window` listed as a visible helper (must fail), and checks that `visible-windows.ps1`, `tests/helper_windows/mod.rs` and `overlay.rs` read the manifest instead of a class literal. In its default mode the tripwire:
  - runs `cargo metadata --locked --filter-platform x86_64-pc-windows-msvc --manifest-path src-tauri/Cargo.toml` in the core image (`scripts/tw-run core`, the registry cache `check-shell-windows` resolves); host `python3` walks the normal dependency edges from `voicen` (what `voicen.exe` links; build and dev dependencies never run in it) and drops workspace members (our own windows are never excluded, so they need no entry); each package's features are its `resolve.nodes[].features`;
  - greps each package's `src/` raw for `CreateWindowEx` (comments count: it errs loud), or its whole package dir when a lib, proc-macro or bin target lies outside `src/` (nine crates of the graph today, e.g. fnv with `lib.rs` at its root). The grep runs in the core image (`--scan-roots`), where the registry paths cargo reports exist; the same scan collects the product window classes, the `window_classname("<class>")` literals; `target/helper-windows/` holds the run's files and is removed after it;
  - keys a matching package `<crate>@<version>[<features sorted bytewise>]` (no brackets when it has none), or `<crate>@<version>` alone when the manifest lists it as `binding` (a bindings crate creates no window under any feature; keying windows/windows-sys by their ~50 Win32 features would trip on every feature src-tauri adds); a `binding` entry with a feature list is malformed;
  - exits 0 when the matching set equals the manifest's entries and no `visible-helper` class is a product window class, 1 on an unlisted or stale key, a malformed entry or a product class listed as a visible helper (each listed), 3 when it cannot run (cargo, docker, python3 or grep error, a package dir or `src/` missing, no product class literal in the graph): never a pass.
- **Cost:** two short `docker run`s (metadata and grep), a few seconds warm; `cargo metadata` needs the registry cache or crates.io access like `check-shell-windows`.
- **Don't:** narrow the graph (normal edges are the floor), the grep (any mention needs an entry) or the scan to make a bump pass; parse the sources to decide what "really" creates a window (F-003: decide on raw text); edit an entry without re-reading the cited source of that version.

### No Gate step needs pnpm on the host

- **Defect that produced it:** F-011 (class `ci-toolchain`, T-068). setup-node v5 caches for the package manager by itself when package.json has `packageManager` (`package-manager-cache` defaults to true) and runs `pnpm store path --silent` on the host; T-064 removed pnpm/action-setup from the Gate job, so the Gate went red at setup-node before any other step. The dev host has pnpm, so no local run could show it.
- **What breaks if you violate it:** the Gate job (and the Windows job behind `needs: gate`) fails at a setup step on main while `make check` is green locally.
- **Where it is enforced:** Makefile `check-setup-node-cache` (part of `make check`) runs `scripts/ci/setup-node-cache.test.sh`: `scripts/ci/setup-node-cache.sh` on the fixtures in `scripts/ci/fixtures/setup-node-cache/` and on the real `.github/workflows`. A job's `actions/setup-node@<ref>` step passes only when (a) `cache:` is unset or empty and `package-manager-cache: false`, (b) `cache: npm`, or (c) an earlier step of the same job uses `pnpm/action-setup@<ref>` and `cache:` is unset, empty or pnpm. Exit 1 on a violation (file:line, job, why), exit 3 when it cannot run. It reads switches written in the workflow, never a model of the action (F-003), and fails closed on shapes it cannot read (flow-style `with:`/step, anchors, expression or other `cache:` values, setup-node named outside a step's `uses:`). Not caught: an `if:` skipping the pnpm/action-setup step, a composite action or reusable workflow calling setup-node, pnpm reached by a run step. The Gate job in `.github/workflows/ci.yml` uses (a).
- **Don't:** drop `package-manager-cache: false` from the Gate setup-node step, or install host pnpm to satisfy it (the ui area runs in the voicen-ui image, T-064).

### Every CI-only premise runs on a `wip/<ID>` run before review

- **Defect that produced it:** class `ci-premise-unchecked-before-main` (rca T-066, decisions #90): all 10 red CI runs up to 2026-10-06 were pushes to `main` whose first execution of a CI-only premise went red: 37147276182 and 37151218166 (F-001), 37159339288 (F-002), 37204170764 (F-005), 37280075413 (T-006 verify 1), 37320512583 and 37365491860 (F-007, F-006), 37419266451 (F-008), 37444780779 (F-009), 37498788064 (F-011, the Linux Gate job). `ci.yml` ran only on `main`, tags and pull requests, so no change was run on CI before review; each local fix was again first run on `main`.
- **What breaks if you violate it:** a red `main` blocks every `deploys: true` task behind it and skips the later steps (step 18 sat skipped for three verify rounds behind F-008); each fix costs a ~35 min CI round on `main`, and the owner is asked to ratify pushes of unreviewed code just to get a Windows run (decisions #68, #74, #79, #80).
- **Where it is enforced:** P-016 (PRINCIPLES 1.1.0): every task with a diff outside `docs/**` cites `CI: <run> @ <sha>` under `## Tests`, a green full run (Gate and Windows jobs) on `wip/<ID>`, before `CODE_COMPLETE`; `<sha>` is the head commit of the reviewed diff or a commit after which only `docs/**` changed up to that head (the `CI:` line and the status commits come after the run); a green re-run (attempt n) at the same sha counts only if every red attempt's failure is outside the task's diff and is logged as its own task or F-entry, cited next to the `CI:` line. The code-reviewer refuses `APPROVE` without it. The orchestrator pushes `git push origin HEAD:wip/<ID>` (pre-push: not a delivery). `.github/workflows/ci.yml` runs on push to `main` and `wip/**`; a newer push to the same `wip/<ID>` cancels the older run (concurrency group per wip ref; other refs get a group per run, so no `main` run is queued behind or cancelled by another). Cache entries are saved from `main` only, because the repo cache is at its 10 GB limit (T-058) and wip entries would evict `main`'s: the cargo registry and the pnpm store through `actions/cache/restore` on every ref plus `actions/cache/save` with `if: github.ref == 'refs/heads/main' && ... cache-hit != 'true'`; `Swatinem/rust-cache@v2` with `save-if: ${{ github.ref == 'refs/heads/main' }}`; no cache in `actions/setup-node` (v5 saves in its post step on every ref, no switch). Makefile `check-ci-wip` (part of `make check`) runs `scripts/ci/ci-wip.test.sh`: `scripts/ci/ci-wip.sh` on the fixtures in `scripts/ci/fixtures/ci-wip/` and on the real `.github/workflows`. It fails (exit 1, file:line) when `ci.yml`'s `push.branches` does not name both `main` and `wip/**` or `push:` carries `branches-ignore`/`paths`/`paths-ignore`, or when any step can save a cache outside `main`: every `uses:` is classified, fail-closed (an unclassified action, a job-level `uses:`, flow-style steps or `with:` are violations). Not caught by `check-ci-wip`: a cache written by a run step, a composite action that caches inside. Not caught by P-016 at all: a step gated on `main` never runs on `wip/<ID>`, so its first execution is the next push to `main`. In `ci.yml` these are the three cache saves (`Save the cargo registry of the core image (main only)`, `Save the pnpm store (main only)` with `actions/cache/save@v6`, and the post-step save of `Swatinem/rust-cache@v2` under `save-if`) and the Telegram send of the installer (`Send the installer to Telegram (main and v* tags only)`, T-070, decisions #93; also runs on `v*` tags); keep main-only steps to cache saves and that send, each consuming only outputs of a step that did run on the wip run (the restore step's `cache-primary-key`, the `pnpm store path` step; for the send, the `Installer for Telegram` step, which on every ref checks exactly one `*-setup.exe`, the `tauri.conf.json` version in its name, the 50 MB Bot API limit, and prints the caption and `curl --version`). The send is one script, `scripts/ci/telegram-send.sh` (args: installer, caption; reads only `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`), and its failure branch is not main-only: the every-ref step `Telegram send failure branch (fake token, nothing reaches a chat)` runs the same script with an obviously fake, unmasked token, so Telegram refuses it, and is red unless the script exits 0, prints a `::warning::` with a non-zero curl exit code and Telegram's `description`, and the fake token appears nowhere in its output (masking cannot hide a leak there). `make check-telegram-send` (`scripts/ci/telegram-send.test.sh`, a stub `curl` on `PATH`) checks on the host that the token and chat id are in no curl argument and no output line, the caption is a `--form-string`, and every failure is one warning with exit 0. What stays main-only is the successful send with the real secrets: its first execution is the first `main` push after T-070, and that run is its proof. It never turns `main` red either: no token → one log line, exit 0; a Telegram or network failure → a `::warning::` with curl's exit code and the API's `description`, exit 0 (the installer stays in the run artifact); the token and the chat id reach curl only as config on stdin (`printf` builtin | `curl -K -`, `form-string` for the chat id), never argv, a file or a log. `.gitattributes` keeps `*.sh` LF so Git Bash on the runner can run the script. Their `if:` expressions are evaluated on wip runs too (to false). A failed save does not turn `main` red: `actions/cache/save@v6` (tag commit 55cc834, `src/saveImpl.ts`) catches every save error and logs a warning, and the save-only entry exits 0; `Swatinem/rust-cache@v2` (49a0bdc, `src/save.ts`) reports the error with `core.error` and exits 0. The failure mode is a cache that is not refreshed (slower, cold runs), seen only in the `main` run's warnings (read from the pinned sources with `gh api`, 2026-10-07). Action inputs were read from the pinned `action.yml` files (`Swatinem/rust-cache@v2` `save-if`, `actions/cache@v6` and its `restore`/`save` sub-actions, `actions/setup-node@v5`, `pnpm/action-setup@v4` `cache`), not from memory.
- **Don't:** count "the next push to `main`" as the proof of a CI-only premise; drop `wip/**` from the trigger, add a `paths-ignore` to it, or turn a cache save back on for every ref to speed up wip runs; push a `wip/` branch as a delivery.
