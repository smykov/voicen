## Invariants

### S1 — One settings window, one constructor, one startup decision

- **Defect that produced it:** none in the failure log (found in analysis, T-037). The shell computed the load outcome and dropped it, and tauri built the static `main` window from `tauri.conf.json` on every start, whatever the outcome, so a Loaded start showed a window and the capability belonged to a label the settings page never had.
- **What breaks if you violate it:** a second settings window (two drafts of one settings file), a window on every start including logon autostart, a page whose `listen` / close is refused by the ACL, or a startup rule decided in the shell beside core's `startup_action_after_hotkey`.
- **Where it is enforced:**
  - `settings_window::open(app, tab, field)` is the only code that builds the window labelled `settings`. If it exists, `open` unminimizes, shows and focuses it, leaves its URL unchanged and emits `settings://focus {tab, field?}` to it (field omitted when `None`); otherwise it builds it at `settings?tab=<token>[&field=<FieldId>]`, title `Voicen`. Both tokens are closed `[a-z_.]` sets (`SettingsTab::as_str`, `FieldId::as_str`), so the URL needs no encoding.
  - At runtime `open` runs only on the app's one opener thread ("settings-window", started by `assemble`'s wiring; T-052). Every caller posts with `settings_window::request(app, target)` and gets a `Receipt` at once; runtime callers drop it, only tests wait on it. The opener runs the requests one at a time, in posting order. tauri's label check (`manager/window.rs:70-72`) and the insert (`:116-117`) bracket the OS window creation, so two `open`s on different threads could both pass the check and build two windows, the second replacing the first in the manager's map; one thread makes that impossible for every caller. Targets: `Tab(tab, field)` = `open(tab, field)` (the startup executor; T-006's engine = none press, `(Engine, None)`; T-055's failed hotkey registration, `DictationSession::hotkey_registration(false)` → `SettingsRequests` → `(Recording, Some(recording.hotkey))`, posted from the hotkey thread outside the session lock — at startup before `Ready`, since the hotkey thread reports the registration before `HotkeyThread::start` returns); `Front` = the open window unminimized, shown and focused on the tab it shows, without `settings://focus`, or `open(Engine, None)` when none is open (the tray "Settings" item and a second launch; OQ-11 Q2 default). A failed open writes one `warning kind=settings_window_failed` line to the diagnostics log on the opener thread, with `os_code=<n>` for an I/O error. Only the kind and the code are written, no error text (T-008, decision #45; `docs/decisions/diagnostics-log.md`). A panic inside one request is caught on the opener thread (where panics unwind; release aborts) and written as `settings_window_failed` without an OS code, and the next request runs. A failed start of the thread writes `settings_opener_failed`, and every request then reports that it cannot run.
  - `settings_window::on_ready(app, &outcome, launched_by_autostart)` carries out core `startup_action_after_hotkey(outcome, launched_by_autostart, hotkey_registered)` and decides nothing else: a `request(Tab(tab, None))`, or nothing for `TrayOnly`. `hotkey_registered` is the managed session's `DictationSession::hotkey_registered()` (`true` when the app has no session); a failed startup registration makes it `TrayOnly`, because the registration's own request (above) already opened the window on the hotkey field (T-055, Q1: the hotkey field wins over the first-run Engine tab). `on_run_event` (`run()`'s loop callback) calls it once, on `RunEvent::Ready`, with `autostart::launched_by_autostart(args_os())`.
  - `tauri.conf.json` has `app.windows: []`. The one capability is granted to label `settings` only, with exactly `core:event:allow-listen`, `core:event:allow-unlisten`, `core:window:allow-destroy` (decision #45).
  - Tests: `src-tauri/tests/settings_window.rs` (FirstRun / Reset / Unavailable → one window at `tab=engine`; Loaded → none; a second `open` → one window, one focus event; tauri's own parse of the config and its real ACL; T-052: the creation and every focus emit on one thread that is no caller's, `request` returning while its open is held, eight concurrent requests → one window, seven focus events, no failure line, FIFO order and `Front` without a tab switch), `src-tauri/tests/single_instance.rs` (a second launch opens or fronts the one window), `src-tauri/tests/tray.rs` (the Settings item), `src-tauri/tests/hotkey_registrar.rs` (T-055: a hotkey taken at start → one window at `tab=recording&field=recording.hotkey`, no Engine tab), core `gate::tests::settings_tab_tokens_*` and `gate::tests::a_failed_hotkey_registration_keeps_the_startup_tab_away` (Q1), and the install smoke (first launch → a visible window titled `Voicen`; a Loaded launch, without arguments and with `--autostart` (T-034) → none for 10 s and the tray window present; a second launch fronts the one window; T-055: a Loaded launch with Ctrl+Alt+Space taken by another process → a visible window titled `Voicen`, `hotkey_register_failed os_code=1409` in the log, the process alive), which is the only proof that `run()` calls `on_ready` and that the hotkey thread's pre-`Ready` request opens the window on the real runtime.
- **Don't:** build a `settings` webview anywhere but `open` in shell code (test harnesses may), call `open` at runtime anywhere but the opener thread (post with `request`), wait for the opener on the main thread or in a window procedure, put a window back into `tauri.conf.json`, decide the startup window from the outcome in the shell, spell a tab token outside `SettingsTab::as_str`, grant `core:default` or another label in the capability, or navigate the open window instead of emitting `settings://focus`.

### U1 — The window derives nothing: every value comes from a SettingsView

- **Defect that produced it:** none in the failure log (found in analysis, T-004). Specs 001–003 each planned UI defaults or language lists beside core's (P-010).
- **What breaks if you violate it:** the window shows a default, a rule or a language that core does not have, so a value the window offers is refused or silently differs from what is stored.
- **Where it is enforced:** every view reaches the draft through `draft.ts`. `settings_get` and `settings://changed` go through `applyView`. A `Saved` outcome goes through `applyOutcome` → `draftFromView`. This is the same clean draft that `applyView` returns for a clean draft, and it must also drop the key edits (U3), so "one applyView" in the T-004 analysis is carried out as these two equivalent entry points. The UI language follows `draft.baseline.settings.ui_language` through one `$effect`, whatever path set the baseline. The speech-language options are exactly `settings_speech_languages` (decision #30; sorting by localized name changes the order only). The interface-language options iterate `LANGUAGES` from `$lib/i18n`, the one list in the UI. The e2e view data is core's own (`e2e/fixtures/settings-wire.json`, pinned by `e2e_settings_wire_fixture_matches_core`). The mock never validates: every refusal is scripted. Tests: the first-run, speech-language, "reflected without reload" and empty-URL cases of `settings-first-run.spec.ts`; `draft.test.ts` › `draftFromView / applyView`.
- **Don't:** build a default, a range or a required-field check in the UI, copy `WHISPER_ISO_639_1`, read the OS locale, or add a third entry point that sets the baseline without going through `draft.ts`.

### U2 — Every refusal reaches the user, localized, on its field

- **Defect that produced it:** T-004 review round 1 #3. A `partially_restored` refusal said "check the highlighted fields", but the field actually left changed (`not_restored`) was not highlighted.
- **What breaks if you violate it:** the user cannot see which value core refused or which value differs from before the save.
- **Where it is enforced:** `applyOutcome` (Refused) is the one mapping. Each `FieldError` becomes `error.<code>` (`errorMessageId`, no list of codes in the UI). Each `form_error.not_restored` field without a `FieldError` of its own becomes `settings.field.not_restored` (UI-only id). The next outcome replaces all of them. Each control carries `data-field="<FieldId>"`, its id comes from `controlId(field)`, and `aria-invalid` / `aria-describedby` point at `FieldMessage` (`errorId(field)`; `aria-describedby` comes from `describedBy`, which adds the warning id of W). The form error's `message` (typed `MessageId`) shows at form level. A rejected invoke shows `error.ipc_unavailable` and never the rejection text. The draft is kept in every case. Core guarantees the texts: `every_error_code_has_catalog_text` over `ErrorCode::ALL` (kept complete by hand, see `settings/mod.rs`) and `message_ids_exist_in_both_catalogs`. Tests: the refusal, form-level, rejected-invoke, unavailable and `partially_restored` cases of `settings-first-run.spec.ts`; `draft.test.ts` › `applyOutcome with partially_restored`, `error ids`.
- **Don't:** map only `errors` and drop `not_restored`, show a FieldId or a rejection text, keep a UI table of error codes, or render a wire id with anything but `t` (see i18n.md).

### U3 — No key value is shown or kept

- **Defect that produced it:** none in the failure log (found in analysis, T-004; NFR-04, FR-20). The `resetKey` path came from the implementation and was pinned by T-004 review round 1 #4.
- **What breaks if you violate it:** a key in the DOM, in a view or in a later request, or a stored key refused as missing.
- **Where it is enforced:** `KeyField` input is `type="password"` and starts empty. Presence shows as text only (`settings.key.saved`). The slot's `KeyEdit` is `Untouched` by default, `{Replace: typed}` once typed, and `Clear` from the "Remove key" button. An input emptied again goes back to `Untouched` (`resetKey`). A blank `Replace` would reach core's `validate`, which reads it as `key.required` for engine api even though a key is stored (settings.md I5). A `Saved` resets every slot to `Untouched`. Tests: the "masked", "stored API key" (Untouched, emptied → Untouched, Remove key → Clear) cases of `settings-first-run.spec.ts`; `draft.test.ts` › `resetKey`.
- **Don't:** prefill the input, keep a typed key after `Saved`, or send `{Replace: ""}`.

### No edit is lost to an in-flight save

- **Defect that produced it:** T-004 review round 1 #10. The inputs stayed editable while `settings_save` was pending, and the `Saved` draft replaced edits made in the meantime.
- **What breaks if you violate it:** a change the user made is silently dropped.
- **Where it is enforced:** the panel's `<fieldset disabled={saving}>` in `+page.svelte`. It unlocks with the saved values. Test: "an edit made while a save is in flight is not lost when Saved arrives".
- **Don't:** move a field outside the fieldset, or replace the draft with an outcome while it can still be edited.

### A number input shows what the user typed

- **Defect that produced it:** T-004 review round 1 #9. The history size used a `bind:value` accessor that coerced an empty entry to `0`, and Svelte wrote it back, so clearing and typing `5` gave `05`.
- **What breaks if you violate it:** the input fights the user.
- **Where it is enforced:** `tabs/History.svelte` keeps the typed entry. The draft holds the wire number, which is `0` for an entry that is not an unsigned whole number. Core refuses `0` with `history.size_range`, and the range is core's rule only. Test: "clearing the history size and typing a digit gives that digit, not a leading 0".
- **Don't:** use a coercing `bind:value` accessor on a number input.

### F — A focus request selects one tab by one rule and focuses an exact match only

- **Defect that produced it:** none in the failure log (need, T-039). The page read only `?tab=`, so `?field=` and `settings://focus` (sent by `settings_window::open`, S1) reached nothing.
- **What breaks if you violate it:** the shell asks for a field and the user sees another tab, a field on another tab gets "focused" through a FieldId → tab rule beside the shell's, or a malformed `field` throws in a selector.
- **Where it is enforced:** `+page.svelte`. `TABS` is the page's tab list, in the order Engine, Recording, Output, Post-processing, History, General (004 FR-001; Post-processing added by T-021, `tabs/PostProcessing.svelte`). `tabOf(tab)` is the one rule for the URL and the event: the requested tab if the page has it, else Engine. `?field=` on load and `settings://focus {tab, field?}` (`onFocusRequest` in `settingsApi.ts`) set the tab and a pending request (the listener is registered before `settings_get`, so a request sent while the page loads is kept and replaces the URL's); an `$effect`, which runs after the DOM update and once the draft and panel exist, focuses the panel's `[data-field]` element whose `dataset.field` equals the field exactly. No match focuses nothing and shows nothing. Tests: the (F) cases of `settings-focus-close.spec.ts` (URL, event twice, a field on another tab, selector syntax, `post_processing` → the Post-processing tab with its field focused and a token the page has no tab for (`diagnostics`) → Engine, a request during a pending `settings_get`); `settings-post-processing.spec.ts` › `?tab=post_processing&field=<FieldId>` for each of its five controls (T-021).
- **Don't:** derive a tab from the FieldId prefix, build a selector from `field`, match by `controlId` (it maps `.` and `-` alike), or show an error for an unmatched field.

### D — The window closes only through destroy, after a prompt when the draft is dirty

- **Defect that produced it:** none in the failure log (need, T-039). tauri prevents the native close whenever a JS `tauri://close-requested` listener exists, and `onCloseRequested` destroys the window after the handler unless `preventDefault()` ran before it returned (@tauri-apps/api 2.12.1).
- **What breaks if you violate it:** unsaved edits are lost without a question, or the window can no longer be closed (a throwing handler, a `close()` that re-emits close-requested and is not granted).
- **Where it is enforced:** `onCloseRequested` and `destroyWindow` in `settingsApi.ts` (the settings contract's IPC module, C); the handler in `+page.svelte` calls `preventDefault()` synchronously when `isDirty(draft)` and shows the in-page `role="alertdialog"` (keep editing: nothing changes; discard: `destroyWindow()`, on failure `error.ipc_unavailable`). A clean or not-yet-loaded draft is not prevented; the handler never throws. The close-requested listener is registered first, then `settings://changed` and `settings://focus`, all before `settings_get`. Only `settings://changed` and `settings_get` build a draft and both come after the guard, so no draft is ever editable without the close guard (T-039 review r2 Low 1, fixed in T-045: the guard used to be registered last, so a `settings://changed` arriving while its `listen` was pending built an unguarded draft); a failed `listen` leaves no draft at all (`error.ipc_unavailable`); while the draft is null the handler prevents nothing. While the prompt is open the page is `inert`; Escape keeps editing. The mock records `plugin:window|destroy` and rejects `plugin:window|close`, as the ACL does. Tests: the (D) cases of `settings-focus-close.spec.ts` (including "a settings://changed arriving before the close guard is registered", with the mock's `holdListen`); `tauri-mock.spec.ts` › destroy / close, holdListen.
- **Don't:** register a listener that can build a draft (or call `settings_get`) before the close guard, call `close()`, prevent after an `await`, add tauri's dialog plugin for the prompt (not a dependency, not granted; owner default Q2), or prevent a clean close.

### R — Untouched, Save sends the view back unchanged

- **Defect that produced it:** none in the failure log (need, T-039, spec 004 T036): nothing pinned that a control does not rewrite its value on mount or on a tab switch.
- **What breaks if you violate it:** opening the window and saving changes a setting the user never touched.
- **Where it is enforced:** `saveRequest` copies the draft; every control binds to its draft value. A select whose options arrive later (the built-in model select, M; the microphone select, P) is not rewritten: Svelte 5 writes a bound select back only on the user's change (and on mount with an `undefined` value, which `model_id: string | null` and the microphone getter's `id ?? ""` never are). Tests: the (R) cases of `settings-focus-close.spec.ts`, one per engine that renders its own controls: engine api, engine local_server, and engine builtin_local twice (the saved model downloaded and shown; the saved model not downloaded, no option, sent back unchanged). Each uses a full non-default `Settings` literal, key shape checked against core's fixture, visits all six tabs in their order (Recording renders `recording.microphone` with a saved id the mock does not list, so "not connected" is covered too, T-012; General renders `ui_language` and `start_with_windows`; Post-processing renders `post_processing.{enabled,base_url,model,key,prompt}`, T-021), and checks `request.settings` deep-equal to the view and every key `Untouched`.
- **Don't:** normalize a value in a control (`$effect.pre`, a select whose options are not loaded yet) so that it writes to the draft without a user edit.

### L — A field is named by one rule, `settings.field_label.<FieldId>`

- **Defect that produced it:** T-004 review round 2 (Low 1): a `not_restored` field without a control on the page (`engine.api.key` while another engine is selected, `general.start_with_windows` until T-034) was not named anywhere; the control labels are shared across fields and cannot name one.
- **What breaks if you violate it:** the user is told to check fields they cannot see, or sees a raw FieldId.
- **Where it is enforced:** `fieldLabelId(field)` in `draft.ts` (the second documented cast, i18n.md), backed by core `every_field_id_has_label_text` over `FieldId::ALL` (kept complete by hand, next to the enum). The form-level message lists by `t(fieldLabelId(f))` each `not_restored` field with no `[data-field]` control in the panel; the panel's controls are collected by a `MutationObserver`, so whatever decides to render a control (tab, engine, a later tab) needs no list here. A field with a control keeps its field-level message (U2). Tests: the two (L) cases of `settings-focus-close.spec.ts` (`engine.api.key` while engine is local_server; the list following the controls of the current tab: `general.start_with_windows` is listed on another tab and leaves the list on the General tab, where its toggle carries the field-level message).
- **Don't:** keep a TS FieldId → label table, show the raw FieldId, or list a field that has a control on the page.

### W — A save's warnings are rendered as core sent them, outside the Draft, by field or at form level

- **Defect that produced it:** none in the failure log (need, T-015, FR-29, spec 004 US6; decision #52). The UI dropped `Saved.warnings`; and the analysis found that anything kept in the Draft is wiped right after Saved, because the `settings://changed` echo of our own save goes through `applyView` → `draftFromView` on a clean draft.
- **What breaks if you violate it:** the user is not told that the key travels unencrypted, the warning flashes and vanishes with the echo, the UI warns by a URL rule of its own that disagrees with the url crate the client connects by (F-003 class, P-010), or a warning blocks or rewrites a save.
- **Where it is enforced:** core decides which field warns and with which text (`settings::url::is_insecure_remote`, docs/decisions/settings.md); `Warning.message` is typed `MessageId` in `settingsApi.ts` and rendered with `t` at render time (a language switch re-renders). `warningsByField` in `draft.ts` maps FieldId → the warning's own `message` (first wins; no id built from the code, no code list). `+page.svelte` keeps the result in page state beside `saved`: cleared when a save starts, set from a `Saved` outcome, kept through `settings://changed`. Each control passes `warnings` to `FieldMessage`, which renders the warning in a non-error style at `warningId(field)`; `describedBy(field, errors, warnings)` in `fields.ts` is the one `aria-describedby` rule (error id, warning id, or both); `aria-invalid` stays errors-only and nothing goes into `role="alert"`. A Saved with at least one warning (field-level or form-level) is announced politely: the existing "Saved" `role="status"` adds the one-line summary `t("settings.saved_with_warnings")` (UI-only id) after `t("settings.saved")`, without the field or the warning text, so each warning text is still on the page once; after a Saved without warnings the status is `settings.saved` only (T-015 review round 1 #3). Because they are cleared when a save starts, a save that ends `Refused` or in a rejected invoke shows no warning (review round 1 #1). A warning whose field has no `[data-field]` control in the panel (another tab or engine; e.g. `post_processing.base_url` while another tab than Post-processing is shown) is listed in `data-testid="settings-warnings"` by `t(fieldLabelId(field))` and its text, by the same `renderedFields` mechanism as L, so each warning shows exactly once. Every `FieldMessage` sits beside its control and gets the real warnings, including the built-in model select (T-045; until then `engine.builtin_local.model_id` had a `FieldMessage` with no control and got none). Tests: `e2e/settings-warning.spec.ts` (all ten, including the refused/rejected clear and the two status-summary cases); `draft.test.ts` › `warningsByField (T-015)`, `Saved warnings stay out of the Draft`; `ids.test.ts` (Warning.message is a MessageId).
- **Don't:** classify a URL, scheme or host in the UI, build `warning.<code>` ids, store warnings in the Draft, render a warning as an error (`aria-invalid`, `role="alert"`, an assertive live region), leave a warning silent (no summary in the Saved status), repeat the warning text in the status, disable Save for a warning, or render a control without passing `warnings` to its `FieldMessage` and `describedBy`.

### C — One IPC module per contract; no component imports `@tauri-apps/api`

- **Defect that produced it:** none in the failure log (found in analysis, T-045, decision #58). `settingsApi.ts` claimed to hold "the only invoke/listen/window calls of the settings window" while `buildInfo.ts` already held a second; adding spec 002's calls to `settingsApi.ts` would have mixed two contracts in one module.
- **What breaks if you violate it:** a wire declared twice (the mock and the window disagree), or a component calling a command no contract lists, outside the mock's reach.
- **Where it is enforced:** `src/lib/settings/settingsApi.ts` holds spec 004's calls and wire types; `src/lib/local-models/localModelsApi.ts` holds spec 002's (`local_models_list`, `local_model_download`, `local_model_cancel_download`, the two `local-model://` listeners, and the one TS declaration of that wire, `nameKey` and `messageKey` typed `MessageId`); `src/lib/overlay/overlayApi.ts` holds spec 001's (`overlay://state`, `overlay_ready`, and the one TS declaration of the overlay wire); `src/lib/buildInfo.ts` holds `get_build_info`. `e2e/support/tauriMock.ts` re-exports the wire types of the `*Api.ts` modules and rejects any other command. By review: `@tauri-apps/api` is imported only by these four files.
- **Don't:** call `invoke` / `listen` from a component, add a contract's commands to another contract's module, or declare a wire type again in the mock.

### M — The local-model section shows only what the list and the events say

- **Defect that produced it:** none in the failure log (need, T-045, spec 002 US1, decision #58). `local_models_list` and `local_model_download` are async commands, so their responses can overtake each other and the events; the download command emits nothing, and a fast failure can end before it returns.
- **What breaks if you violate it:** a row stuck in a state the shell no longer has (an optimistic `downloading` after a fast `failed`), a model offered that is not downloaded, two downloads started at once, or a raw byte count or rejection text on screen.
- **Where it is enforced:** `BuiltinLocal.svelte`, rendered by `tabs/Engine.svelte` in place of the T-004 placeholder only while the draft's engine is `builtin_local` (so only then is `local_models_list` called; a remount re-lists).
  - Rows (I2): the sequencer in `models.ts` (`listRequested`, `listReceived`, `eventReceived`, `applyEvent`). The rows are the newest issued list response overlaid in arrival order by the events received since it was issued; an older response is dropped; nothing else sets a state. Both listeners are registered before the first list, and a list is issued again after every download invoke settles.
  - Select (I3): `<select data-field="engine.builtin_local.model_id">` with `bind:value` on the draft's `model_id`, offering exactly `selectable(rows)` (the downloaded rows) plus a disabled `null` placeholder. Options appearing or vanishing never write the draft (R); a saved model that is not downloaded keeps its value and core refuses the save with `model.not_downloaded` on the field (U2). The control carries `controlId`, `aria-invalid`, `describedBy` and a `FieldMessage` with the real warnings, so F, L, W and U2 apply to it. No auto-select after a download.
  - Download / Retry (I4): disabled while `downloadBlocked(rows, invokePending)`. The invoke counts as pending until the re-list issued after it has settled, a failed re-list included: core is already `Downloading` when the command returns, and only that re-list shows it (T-045 review r1 #3). Cancel is offered on a downloading row; its end state comes as `local-model://state`.
  - Texts (I5): names `t(nameKey)`, reasons `t(messageKey, reasonArgs(reason, lang))`, labels UI-only `local_models.*` ids; every byte count (`sizeBytes`, `received`, `total`, the `needed` param) only through `formatSize(bytes, lang)` (binary units as Windows Explorer shows them, OQ-08 default; i18n.md). A failed row's reason is in the row (`local-model-reason`, not an alert), inside a polite live region that is mounted with the row, so a row turning `failed` changes the text of an existing region rather than inserting a new one (a region inserted together with its text is generally not announced; review r1 #6). A row listed `failed` when the section opens is shown, not announced. A refused download (a `FailureReason`, checked by `asFailureReason`), a rejection that is not one, and a rejected list or listen are shown in the section (`error.ipc_unavailable` for the last two kinds), never the rejection text; a refusal changes no row.
  - A download keeps running when the window closes, and a reopened window shows it from the list (OQ-09 default).
  - Tests: `e2e/local-models.spec.ts` (list, download with progress, blocked buttons, Download and Retry shown as `downloading` by the re-list alone, buttons disabled while the download invoke and then its re-list are held, interrupted / checksum failures, Retry, Cancel, disk-space refusal in en and ru, a non-contract rejection, restart selection, rejected list, `model.not_downloaded` on the select, list/event ordering, a download running at open); `models.test.ts`; `ids.test.ts`; the builtin_local (R) cases of `settings-focus-close.spec.ts`; the local-model cases of `tauri-mock.spec.ts`. - **Don't:** set a row's state in the UI (optimistic or by a rule), apply a list response that is not the newest, offer a model that is not downloaded, auto-select a model, format a size anywhere but `formatSize`, or render a reason with `role="alert"`.

### P — The microphone select shows the listed devices and keeps the saved one

- **Defect that produced it:** none in the failure log (need, T-012, req FR-27, spec 004 edge case "selected microphone not connected when settings open", decision #64). The saved `microphone` is `{ id, name }` (an endpoint id plus its last known name) and a select's `value` is a string, so the field cannot bind the object directly; an unplugged device is absent from the list (cpal lists active endpoints only).
- **What breaks if you violate it:** opening settings with the saved microphone unplugged silently switches it to the default (or another device) on the next Save, the Windows default device is saved as `null` (and then follows later default changes), a device is matched by its name, or a rejection text reaches the page.
- **Where it is enforced:** `src/lib/settings/MicrophoneField.svelte`, rendered by `tabs/Recording.svelte`; `listMicrophones()` and the wire type `InputDevice { id, name, is_default }` in `settingsApi.ts` (C; the mock re-exports it). `settings_list_microphones` is called once per mount (a remount re-lists, as M).
  - Options: `value=""` = `t("settings.microphone.system_default")` (microphone `null`), then the listed devices in list order by `value=<id>`, the `is_default` one (only) as `t("settings.microphone.windows_default", { name })`; a device the draft or the saved settings name whose id is not listed is one more option by its id, `t("settings.microphone.not_connected", { name })` once the list is known, its saved name while the list is pending or failed. Matching is by the whole id; the name is display only.
  - Draft (R): a function binding, getter `microphone?.id ?? ""` (never `undefined`, so mount writes nothing), setter only on the user's change: `""` → `null`, a listed device → `{ id, listed name }`, an unlisted one → the `{ id, name }` it came from. Options appearing later never write the draft.
  - A rejected list shows `t("error.ipc_unavailable")` under the field (`role="alert"`), never the rejection text; the draft is kept.
  - Tests: `e2e/settings-microphone.spec.ts` (list and marks, saved listed / chosen / Windows default by id / System default → null, not connected in en and ru and with an empty list, a list arriving after the draft, rejected list with a canary); the R round trips of `settings-focus-close.spec.ts`; the microphone cases of `tauri-mock.spec.ts`.
- **Don't:** write the draft when the list arrives, save the Windows-default device as `null` (or System default as the default device's id), match a saved device by name, drop a saved id that is not listed, or show the rejection text.

### A — About shows only this opening's build info, and the discard prompt wins

- **Defect that produced it:** none in the failure log (need, T-023, FR-18, spec 006 US1 and Clarification Q1). Since T-037 no window opens `/`, the only page that showed the version, so an installed build showed it nowhere in the UI.
- **What breaks if you violate it:** About shows a version from an earlier opening, an empty line or a rejection text (U2), or a modal About leaves the discard prompt inert so the user cannot answer it.
- **Where it is enforced:** `src/lib/about/About.svelte`, mounted only by `tabs/General.svelte`, reads build info only through `src/lib/buildInfo.ts` (`loadBuildInfo` → `get_build_info` → `voicen_core::build_info()`, the one resolver, C). Each opening clears the previous result and calls `get_build_info` once; an answer to an earlier opening is dropped; while pending nothing is shown. The line is `formatBuildInfo(info)` (`app.build_info`); a rejection shows `role="alert"` with `about.build_info_error` and no rejection text. The dialog is a native `<dialog>` opened with `showModal()` (Esc closes it, focus returns to the button) and `aria-labelledby` its title; it is moved to `<body>` so it is outside the panel's `<fieldset disabled={saving}>` and outside `<main>`, which goes inert under the discard prompt. The button stays in the fieldset (no About mid-save). The discard prompt wins: `onClose` in `+page.svelte` sets the bound `aboutOpen` to false before `confirmDiscard`, and About closes its dialog in a `$effect.pre`, before the page's effect focuses Keep editing. Texts are UI-only ids `about.button`, `about.title`, `about.close`, `about.license`, `about.build_info_error` (i18n.md). Not yet: FR-002's "Project page", "Third-party licenses" and "Open logs folder" buttons (need shell commands; follow-up). Tests: `e2e/about.spec.ts` (opening and call count, failure branch, no stale value or error, keyboard, RU, discard prompt wins); `tauri-mock.spec.ts` › setBuildInfo.
- **Don't:** load build info on mount or cache it across openings, show the rejection text, render the dialog inside the saving fieldset or `<main>`, open it with `show()` (non-modal), or show the discard prompt while About is open.
